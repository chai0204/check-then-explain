クライアントに基準を1行与えるだけです。

    echo 'server 127.0.0.1 iburst' >> /etc/chrony/chrony.conf
    systemctl restart chrony
    sleep 8

    chronyc sources -v
    #=> ^* localhost     8   6    17     2    +49ns[ +289ns] +/- 3392ns

    chronyc tracking
    #=> Reference ID    : 7F000001 (localhost)
    #   Stratum         : 9
    #   Leap status     : Normal

（ナノ秒の数値と時刻はあなたの環境で変わります。見るのは Reference ID と Stratum と
 Leap status の3行です。）

【なぜ時計を動かさずに「同期」になるのか】

  この檻の chronyd は -x 付きで起動しています。

    cat /etc/default/chrony
    #=> DAEMON_OPTS="-F -1 -x"

  -x は「時計を制御しない」指定です（man chronyd: disables the control of the system clock）。
  Ubuntu の既定（/etc/default/chrony）は -F 1 だけですが、Ubuntu の起動スクリプトは
  コンテナの中では -x を自動で足します（/usr/share/doc/chrony/README.container）。
  コンテナには時計を動かす権限（CAP_SYS_TIME）が無く、合わせようとしても落ちるだけだからです。
  実際に試せます。

    chronyc makestep          #=> 500 Failure   ← -x で時計を制御しないため
    date -s "2020-01-01 00:00:00"
    #=> date: cannot set date: Operation not permitted   ← CAP_SYS_TIME が無いため

  理由は chronyd が起動したときにログへ書いています。

    journalctl -u chrony | grep "control of system clock"
    #=> ... chronyd[...]: Disabled control of system clock

  実機の chronyd や ntpd の本来の仕事は、測ったずれでシステムクロックを合わせることです。
  この檻の chronyd は -x なので、「基準とのずれを測って報告する」ところで止まっています。
  ずれを実際に反映するかどうかは、起動の指定（-x）と権限が決めます。

【Stratum が 9 になる理由】

  基準サーバ側の設定を見てください。

    grep -vE '^\s*#|^\s*$' /etc/chrony/lab-ntp-server.conf
    #=> local stratum 8

  stratum 8 のサーバを基準にしたので、こちらは 9 になります。
  stratum は「基準から何段離れているか」です。

【試験との対応】

  ntpd 系では同じことを次の対応で見ます。chrony と ntpd は同時に入りません
  （どちらも Provides: time-daemon かつ Conflicts: time-daemon）。

    chronyc sources   ←→  ntpq -p
    chronyc tracking  ←→  ntpq -c rv
    /etc/chrony/chrony.conf ←→ /etc/ntp.conf
    （RHEL 系の chrony は /etc/chrony.conf、Ubuntu の ntpsec は /etc/ntpsec/ntp.conf）
    ntpdate -q <host>   … 問い合わせるだけで時計を動かさない（この檻でも動く）
