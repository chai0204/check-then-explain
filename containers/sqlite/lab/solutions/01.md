## コマンド

    cd ~/work/01
    sqlite3 notes.db 'CREATE TABLE notes(id INTEGER PRIMARY KEY, body TEXT); INSERT INTO notes(body) VALUES("最初のメモ");'
    ls -l notes.db
    file notes.db
    xxd -l 16 notes.db
    ps -ef
    ps -ef | grep -c '[s]qlite'
    ps -ef | grep -c 'sqlite'

## 著者の環境で出た出力

    $ ls -la notes.db
    -rw-r--r-- 1 lab lab 8192 Sep 30 19:07 notes.db

    $ file notes.db
    notes.db: SQLite 3.x database, last written using SQLite version 3045001,
    file counter 2, database pages 2, cookie 0x1, schema 4, UTF-8, version-valid-for 2

    $ xxd -l 16 notes.db
    00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.

    $ ps -ef | grep -c '[s]qlite'
    0

    $ ps -ef | grep -c 'sqlite'
    1

`ps -ef` そのものの出力は PID・時刻・起動の仕方で変わるので、ここには載せません。
出るのは **自分のシェルと、いま打った `ps` の2行だけ** です。

## 3つの観測が何を言っているか

**8192 バイト** — 1行しか入れていないのに 8KB あります。SQLite はページ単位で
確保するためで、既定のページサイズが 4096 バイト、それが2ページ分です。
（file の出力にも `database pages 2` と出ています。）

**先頭16バイト** — `SQLite format 3` という文字列がそのまま平文で入っています。
暗号化もヘッダの圧縮もしていません。`file` コマンドがこのファイルを判別できるのは、
まさにこの16バイトを見ているからです。

**ps の結果が 0 と 1 で割れる** — ここが肝心です。

`[s]qlite` は「grep 自身の行を数えない」ための定番の書き方です。パターンとしては
`sqlite` に一致しますが、`ps` の出力に並ぶ grep のコマンドラインは
`grep -c [s]qlite` という文字列なので、角括弧のせいで自分自身には当たりません。

- `[s]qlite` → **0**。本当の答え。sqlite のプロセスは1つも動いていない
- `sqlite` → 1。これは `grep sqlite` 自身の行

`ps -ef` をそのまま打てば2行しか出ません。自分のシェルと、いま打った `ps` だけです。

なお `grep -c` は**一致が0件のとき終了コード 1 を返します**。「0件だった」と
「コマンドが失敗した」が同じ値になるので、スクリプトで条件に使うときは
終了コードではなく出力の数字を見る必要があります。

## なぜこれが重要か

`ps` に何も出ないということは、**あなたが sqlite3 コマンドを打った瞬間だけ
プロセスが生き、終わったら消えている**ということです。
DB を「持っている」のはファイルだけで、待ち受けている者はいません。

これがこの教材の背骨です。以降の章で出てくる挙動は、ほぼ全部この1点から出てきます。
