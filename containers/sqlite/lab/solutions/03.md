## コマンド

    cd ~/work/03

    # トランザクションなし
    sqlite3 naive.db 'CREATE TABLE a(n INTEGER);'
    time (seq 1 2000 | sed 's/.*/INSERT INTO a VALUES(&);/' | sqlite3 naive.db)

    # トランザクションあり
    sqlite3 txn.db 'CREATE TABLE b(n INTEGER);'
    time ( { echo 'BEGIN;'; seq 1 2000 | sed 's/.*/INSERT INTO b VALUES(&);/'; echo 'COMMIT;'; } | sqlite3 txn.db )

    printf 'naive=%s\ntxn=%s\n' 12.996 0.048 > times.txt   # 自分の実測値に置き換える

## 著者の環境で出た出力

    $ time bash naive.sh
    real	0m12.996s
    user	0m0.078s
    sys	0m0.472s

    $ time bash txn.sh
    real	0m0.048s
    user	0m0.033s
    sys	0m0.012s

**12.996 秒 → 0.048 秒。約270倍です。**

## この差はどこから来ているか

`user`（CPU がユーザー空間で使った時間）を見てください。遅い側でも **0.078 秒**しかありません。
`sys` を足しても 0.55 秒程度です。つまり **12秒のうち12秒近くは、CPU が何もしていません。**

待っていたのはディスクです。

SQLite は既定で、**1つのトランザクションが終わるたびにディスクへの書き込みを確定させます**
（`fsync` を呼ぶ）。BEGIN で囲まなければ、**1つの INSERT 文が1つのトランザクション**になります。
つまり 2000 回の fsync が走りました。

BEGIN で囲むと、2000行がまとめて1つのトランザクションになり、fsync は1回で済みます。

## なぜ SQLite はこの設計なのか

背骨に戻ります。**まとめて書いてくれる常駐プロセスがいません。**

サーバ型の DB なら、サーバプロセスが複数のクライアントの書き込みを受け取り、
自分の判断でまとめてディスクに落とせます。書き込みを遅延させても、
サーバが生きている限りデータは失われません。

SQLite はライブラリなので、書いているのはあなたのプロセスです。
あなたのプロセスが終わった瞬間にメモリの内容は消えるので、
**「終わったら確定している」を守るには、その場で fsync するしかありません。**

速くしたければ、**どこまでを1つのまとまりとするかを、あなたが決める**必要があります。
その宣言が BEGIN です。
