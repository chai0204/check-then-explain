## コマンド

    cd ~/work/05
    mkdir sub
    sqlite3 sub/d.db 'CREATE TABLE t(n INTEGER); INSERT INTO t VALUES(1);'
    ls -ld sub; ls -l sub/d.db

    chmod 555 sub
    ls -ld sub; ls -l sub/d.db
    sqlite3 sub/d.db 'INSERT INTO t VALUES(2);'   >> observed.txt 2>&1
    sqlite3 sub/d.db 'SELECT count(*) FROM t;'    >> observed.txt 2>&1

    chmod 755 sub
    sqlite3 sub/d.db 'INSERT INTO t VALUES(2); SELECT count(*) FROM t;'

## 著者の環境で出た出力

    $ ls -ld sub; ls -l sub/d.db
    dr-xr-xr-x 2 lab lab 4096 Sep 30 19:08 sub
    -rw-r--r-- 1 lab lab 8192 Sep 30 19:08 sub/d.db

    $ sqlite3 sub/d.db 'INSERT INTO t VALUES(2);'
    Error: stepping, attempt to write a readonly database (8)

    $ sqlite3 sub/d.db 'SELECT count(*) FROM t;'
    1

    $ sqlite3 sub/d.db 'PRAGMA journal_mode=WAL;'
    Error: stepping, attempt to write a readonly database (8)

    $ chmod 755 sub
    $ sqlite3 sub/d.db 'INSERT INTO t VALUES(2); SELECT count(*) FROM t;'
    2

## 何が起きていたか

**DB ファイルの権限は `-rw-r--r--` のまま、一度も変えていません。**
変えたのはディレクトリの権限だけです。それでも SQLite は
「readonly database」と言って書き込みを拒否しました。

理由は、SQLite が書き込みのときに **DB ファイルの隣にもう1つファイルを作る**からです。
既定の journal_mode が `delete` のとき、作られるのは `d.db-journal` という
ロールバックジャーナルです。書き込みの直前に作られ、コミットが終わると消されます。

新しいファイルを作る操作は、そのファイルへの書き込みではなく
**ディレクトリへの書き込み**です。ディレクトリが `r-x` だと、
中身を読むことはできても、新しい名前を追加できません。

だから **DB ファイルに w があっても、書き込みは失敗します。**

## エラーメッセージが誤解を生む

`attempt to write a readonly database` は、原因ではなく**結果**を述べています。
SQLite から見れば「この DB は書き込めない状態だ」というのは正しい報告です。
しかし読者は `database` という語から DB ファイルの権限を疑い、
そこには問題がないので長く迷うことになります。

実務でこのエラーに出会ったときの確認順は次のとおりです。

1. DB ファイルの権限
2. **DB ファイルがあるディレクトリの権限** ← ここが抜けやすい
3. ファイルシステムが読み取り専用でマウントされていないか（`mount` で確認）
4. ディスクが満杯でないか（`df`）
5. SELinux / AppArmor のラベル

## WAL に逃げられない

上の出力で、`PRAGMA journal_mode=WAL;` **自体も同じエラーで拒否されています。**

journal_mode の変更は DB ヘッダへの書き込みであり、さらに WAL モードは
`d.db-wal` と `d.db-shm` という2つのファイルを新たに作ります。
どちらもディレクトリへの書き込みを必要とします。

つまり「WAL にすれば回避できる」という道はありません。

## 1章から4章がここに収束する

この教材の背骨は「**SQLite はサーバではなくライブラリである**」でした。
ここまで見てきたことは、全部この1点から出ています。

| 章 | 見たこと | サーバがいないと、どうなるか |
|---|---|---|
| 1 | DB がファイル1個で、`ps` に何も出ない | 待ち受ける者がいない。ファイルだけが DB |
| 2 | INTEGER 列に文字列が入る | 門番がいないので、弾くより受け取る設計になった |
| 3 | BEGIN で囲まないと270倍遅い | まとめて書いてくれる者がいない。fsync を自分で呼ぶ |
| 4 | WAL でも書き込みは1人だけ | 順番待ちを仲裁する者がいない。ロックはファイル上の印 |
| 5 | ディレクトリに書けないと DB にも書けない | **自分の作業領域を持てない。ジャーナルを DB の隣に置くしかない** |

サーバ型の DB なら、作業用のファイルは自分のデータディレクトリに作れます。
サーバは自分の領域を持っているからです。SQLite は**あなたのプロセスの一部**なので、
持ち物は DB ファイルとその隣しかありません。

この制約は弱点ではなく、SQLite が「設定も起動も要らない」ことと同じ理由から来ています。
持ち物が少ないから、置くだけで動きます。
