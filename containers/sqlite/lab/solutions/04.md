## コマンド

    cd ~/work/04
    sqlite3 lock.db 'CREATE TABLE t(n INTEGER);'
    sqlite3 lock.db 'PRAGMA journal_mode;'

    ./hold.sh lock.db 15 &
    sleep 1
    sqlite3 lock.db 'INSERT INTO t VALUES(1);'   >> observed.txt 2>&1
    sqlite3 lock.db 'SELECT count(*) FROM t;'    >> observed.txt 2>&1
    wait

    sqlite3 lock.db 'PRAGMA journal_mode=WAL;'

    ./hold.sh lock.db 15 &
    sleep 1
    sqlite3 lock.db 'INSERT INTO t VALUES(2);'   >> observed.txt 2>&1
    sqlite3 lock.db 'SELECT count(*) FROM t;'    >> observed.txt 2>&1
    wait

## 著者の環境で出た出力

    $ sqlite3 lock.db 'PRAGMA journal_mode;'
    delete

    --- 相手がトランザクションを開いている間 ---
    $ sqlite3 lock.db 'INSERT INTO t VALUES(2);'
    Error: stepping, database is locked (5)

    $ sqlite3 lock.db 'SELECT count(*) FROM t;'
    0

    --- WAL に変えて、同じことをする ---
    $ sqlite3 wal.db 'PRAGMA journal_mode=WAL; CREATE TABLE t(n INTEGER);'
    wal

    $ sqlite3 wal.db 'INSERT INTO t VALUES(2);'
    Error: stepping, database is locked (5)      ← WAL でも同じ

    $ sqlite3 wal.db 'SELECT count(*) FROM t;'
    0

## 3つの観測

**既定の journal_mode は `delete`** です。WAL は自分で選ばないと有効になりません。

**書き込みは `database is locked (5)` で拒否されます。** エラーコード 5 は SQLITE_BUSY で、
「いま他の誰かが書いている」という意味です。既定の `busy_timeout` は 0 なので、
待たずに即座に諦めます。

**読み取りは成功して 0 を返します。** 相手はすでに1行入れていますが、
まだ COMMIT していないので見えません。これは正しい振る舞いです（未確定の変更は他から見えない）。

## WAL で変わることと、変わらないこと

ここが最も誤解されている点です。

| | 既定（delete） | WAL |
|---|---|---|
| 同時に書ける人数 | 1人 | **1人（変わらない）** |
| 書き込み中に読み取れるか | 読める（古い値） | 読める（古い値） |
| 読み取り中に書き込めるか | **待たされる** | **待たされない** |

**WAL にしても、書き込みは1人だけです。** 上の実測で、WAL でも同じ
`database is locked` が出ていることを確かめました。

WAL が解決するのは「読み手が書き手を止めてしまう」問題です。既定モードでは、
長い SELECT が走っている間は書き込みがブロックされます。WAL では読み手が
古いスナップショットを見続けられるので、書き手は待たされません。

つまり **WAL は「読み書きの同時実行」を可能にしますが、「書き込みの同時実行」は可能にしません。**

## なぜ1人だけなのか

背骨に戻ります。**順番待ちを仲裁する者がいません。**

サーバ型の DB なら、サーバプロセスが複数の書き込み要求をキューに並べ、
順番に適用できます。要求が10件来ても、サーバが1件ずつ処理すれば全部通ります。

SQLite の「ロック」は、ファイルシステム上の印でしかありません。
各プロセスが「いま誰か書いているか」を印で確認し、書いていたら自分で諦めます。
並べてくれる者がいないので、**諦めるか、待つか（busy_timeout）を、呼ぶ側が決める**しかありません。

実務では `PRAGMA busy_timeout = 5000;` のように待つ時間を指定します。
それでも「1人だけ」は変わりません。書き込みが多いワークロードでは、
SQLite ではなくサーバ型を選ぶ理由がここにあります。
