## コマンド

    cd ~/work/02
    sqlite3 t.db 'CREATE TABLE loose(n INTEGER);'
    sqlite3 t.db 'INSERT INTO loose VALUES(42);'
    sqlite3 t.db 'INSERT INTO loose VALUES("abc");'
    sqlite3 t.db 'INSERT INTO loose VALUES("123");'
    sqlite3 t.db 'SELECT n, typeof(n) FROM loose;'
    sqlite3 t.db 'CREATE TABLE tight(n INTEGER) STRICT;'
    sqlite3 t.db 'INSERT INTO tight VALUES("abc");' 2> observed.txt
    cat observed.txt

## 著者の環境で出た出力

    $ sqlite3 t.db 'SELECT n, typeof(n) FROM loose;'
    42|integer
    abc|text
    123|integer

    $ sqlite3 t.db 'INSERT INTO tight VALUES("abc");'
    Error: stepping, cannot store TEXT value in INTEGER column tight.n (19)

## 3行の typeof が言っていること

**42 は integer、abc は text、"123" は integer。** 3つ目が肝心です。
`"123"` は文字列として書いたのに、integer として格納されています。

SQLite の列の型は制約ではなく **affinity（親和性）** です。INTEGER affinity を持つ列は
「入ってきた値が数値に変換できるなら変換する。できないならそのまま入れる」という振る舞いをします。

- `"123"` → 数値に変換できる → integer として保存
- `"abc"` → 変換できない → text のまま保存

つまり INTEGER という宣言は **拒否する約束ではなく、変換を試みる約束**です。

## STRICT を付けると

`cannot store TEXT value in INTEGER column` で拒否されます（エラーコード 19 = 制約違反）。
STRICT テーブルでは affinity による変換をせず、宣言した型以外を受け付けません。
3.37.0（2021年）で入った比較的新しい機能です。

## なぜ既定が緩いのか

背骨に戻ります。**SQLite にはサーバがいません。**

型を厳格にすると「誰が弾くのか」という問題になります。サーバ型の DB なら
サーバプロセスが門番として弾けますが、SQLite はあなたのプロセスの中のライブラリです。
弾く相手は、同じプロセスの中にいる自分自身のコードです。

SQLite は1つのファイルを様々なアプリが読み書きする用途を想定していて、
初期の設計では「厳しくして弾く」より「受け取って持っておく」を選びました。
STRICT は、後からその選択を上書きできるようにしたものです。
