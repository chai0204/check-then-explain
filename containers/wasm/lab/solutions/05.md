## 4つの答え

**1. import**

| モジュール | 関数 | 型 |
|---|---|---|
| env | read_file | (i32, i32) → i32 |
| env | http_post | (i32, i32) → なし |

**2. export** — `memory`（メモリ）と `_start`（関数）。

**3. メモリの初期データ** — 2つ。オフセット0に `/etc/passwd`、オフセット64に
`https://example.invalid/collect`。**どちらも平文で読めます。**

**4. 何をしようとしているか**

`_start` は 16 バイトの小さな関数です。import の型と Data の内容を合わせると、
「オフセット0から11バイト（= `/etc/passwd`）を `read_file` に渡し、
その後オフセット64から31バイト（= 送信先 URL）を `http_post` に渡す」という形が読めます。

つまり **ファイルを読んで、外部の URL へ送ろうとしている**モジュールです。

**ホストが import を渡さなかったら** — 何もできません。次のように拒否されます。

    $ wasmtime run mystery.wasm
    Error: failed to run main module `mystery.wasm`

    Caused by:
        0: failed to instantiate "mystery.wasm"
        1: unknown import: `env::read_file` has not been defined

`_start` の中の命令は1つも実行されていません。**インスタンス化の段階で止まっています。**

## 隠せないもの、隠せるもの

`/etc/passwd` も送信先 URL も、objdump で丸見えでした。WASM のバイナリは
暗号化されていないので、**文字列を隠すことはできません**（難読化はできますが、
それは「読みにくくする」だけで「読めなくする」ことではありません）。

一方で、**関数の中身の意図は完全には読めません**。16バイトの命令列から
「ファイルを読んで送る」と読めたのは、import の名前がそう名付けられていたからです。
名前が `f1` `f2` だったら、型と呼び出し順から推測するしかありません。

## 背骨がセキュリティの道具になる

> **WASM は外の世界を一切知らない。できることは全部、ホストが import として手渡したものだけである。**

第2章でこの背骨を提示し、第3章・第4章でデータと移植性が同じ構造であることを見ました。
ここで反転します。

**モジュールが何をできるかは、モジュールを読まなくても分かります。** import の一覧が
そのまま「要求している能力の一覧」だからです。そして渡すかどうかを決めるのはホスト、
つまりあなたです。

| 渡すもの | できること |
|---|---|
| 何も渡さない | 計算だけ。外に影響しない |
| `env.read_file` だけ渡す | 読める。送れない |
| 両方渡す | 読んで送れる |

サーバ上で他人のプラグインを動かす仕組みに WASM が使われるのは、この性質があるからです。
プロセスやコンテナで隔離するのではなく、**渡す関数を選ぶだけで能力を絞れます。**

## 5つの章で見たもの

| 章 | 見たこと | 背骨との関係 |
|---|---|---|
| 1 | 41バイトに型・名前・命令が全部入る。文字列型は無い | 持てるのは数値だけ |
| 2 | 同じ .wasm が3通りの結末になる | 能力は import 経由でしか来ない |
| 3 | 返るのは `ptr` と `len` の2数値。意味づけはホスト | データも同じ構造 |
| 4 | WASI があるホストでしか動かない。沈黙する結末もある | 移植性はホストが決める |
| 5 | import を見れば要求している能力が分かる | **渡す側が能力を選べる** |
