ja_JP.UTF-8 を生成してから、スクリプトの頭で LC_ALL=C を決めます。

    sudo locale-gen ja_JP.UTF-8
    #=> Generating locales (this might take a while)...
    #     ja_JP.UTF-8... done
    #   Generation complete.

    LANG=ja_JP.UTF-8 lab-report
    #=> 今月のログ: /var/log/archive/10月        ← 生成したので、日本語の月名になった

    sudo sed -i '2i export LC_ALL=C' /usr/local/bin/lab-report
    LC_ALL=ja_JP.UTF-8 lab-report
    #=> 今月のログ: /var/log/archive/Oct

【なぜ生成が先か】

  LANG=ja_JP.UTF-8 は名前を指すだけです。その名前のデータ（/usr/lib/locale/locale-archive の中）が無ければ、
  プログラムは黙って C ロケールで動きます。date は警告も出しません。生成する前は、どう呼んでも出力が同じなので、
  スクリプトが壊れていること自体に気づけません。

【LANG=C では足りない】

    sudo sed -i '2i export LANG=C' /usr/local/bin/lab-report
    LC_ALL=ja_JP.UTF-8 lab-report
    #=> 今月のログ: /var/log/archive/10月        ← 呼ぶ人の LC_ALL が勝つ

  強さの順は LC_ALL > LC_TIME などの LC_* > LANG です。スクリプトの中で確実に固定するなら LC_ALL=C です。
  「スクリプトでは LANG=C」とよく言われるのは、出力の形（日付・数・並び順・メッセージ）を
  ロケールに左右させないためで、そのために一番強い変数を決めるのが確実です。

【何が変わっていたか】

  date の既定の形がロケールの LC_TIME で決まり、ja_JP.UTF-8 では「2026年 10月 13日 火曜日 …」になります。
  awk の2列目は Oct ではなく 10月 になりました。ls -l の日付、sort の並び順（LC_COLLATE）、
  printf の桁区切り（LC_NUMERIC）も同じ理由でロケールに左右されます。
