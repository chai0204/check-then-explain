9. 文字コードは、読む側が決める

文字化けした「縺薙ｓ縺ｫ縺｡縺ｯ」を逆向きにもう一度変換すると、「こんにちは」に戻る。バイト列は1つも壊れていなかった。ファイルは自分の文字コードを名乗らないので、どう読むかは読む側が決めている。iconv の -f は、その「読み方」を渡すオプションである。

前提: 第8章まで読了所要 16分影響度 B出題範囲 1.08.3（重要度3）最終検証 2026-10-13

この章のゴール

  • 文字・コードポイント（Unicode）・バイト列（UTF-8 など）の関係を説明できる
  • ASCII・ISO-8859・UTF-8・ISO-2022-JP・Shift_JIS・EUC-JP の違いを、バイト列で見分けられる
  • iconv -f -t で変換し、変換できないときに何が起きるかを言える
  • 文字化けが「バイトの破損」ではなく「読み方の誤り」であることを示せる
ここで覚えなくていいこと: UTF-16 の BOM の細部、Unicode の正規化（NFC と NFD）、nkf、Windows 独自の拡張（CP932 と Shift_JIS の差、① や ～ の扱い）は扱わない。

文字は、バイト列として保存されている

この節で分かること: 同じ1文字が、文字コードごとに違うバイト列になること。

@@ printf 'A' | od -An -tx1
@@ printf 'あ' | od -An -tx1
@@ printf 'é' | od -An -tx1
@@ printf '\u3042\n'

A は1バイト（0x41）、é は2バイト、あ は3バイトだった。この端末は UTF-8 で読み書きしている。Unicode は世界の文字に番号（コードポイント）を振った表で、「あ」は U+3042 である（printf '\u3042\n' のように番号から文字を出せる）。UTF-8 は、その番号を1〜4バイトに詰める方式の1つで（いまの規格の上限は4バイト。古い定義では最大6バイトで、LinuC の例題の解説はこの書き方をしている）、ASCII（0x00〜0x7F の7ビットの英数字）の範囲はそのまま1バイトになる。同じ「あ」を、ほかの方式で書き出す。


@@ printf 'あ' | iconv -f UTF-8 -t UTF-16BE | od -An -tx1
@@ printf 'あ' | iconv -f UTF-8 -t SHIFT_JIS | od -An -tx1
@@ printf 'あ' | iconv -f UTF-8 -t EUC-JP | od -An -tx1
@@ printf 'あ' | iconv -f UTF-8 -t ISO-2022-JP | od -An -tx1
文字コード「あ」特徴
ASCII（表せない）7ビット。英数字と記号だけ
ISO-8859-1（Latin-1）（表せない）1バイト。ASCII ＋ 西欧の文字（é など）。ISO-8859-2〜16 は東欧・ギリシャ文字などの別の版
UTF-8e3 81 82Unicode を1〜4バイトで（古い定義では最大6バイト）。ASCII と互換。Linux の標準
UTF-1630 42Unicode を2または4バイトで（BE はバイトの並びが大きい方から）
Shift_JIS82 a0日本語。Windows で長く使われた。かな・漢字は2バイト、半角カタカナは1バイト
EUC-JPa4 a2日本語。古い Unix で使われた
ISO-2022-JP1b 24 42 24 22 1b 28 42日本語。7ビットだけで書き、ESC $ B と ESC ( B で文字の集合を切り替える。日本語の電子メールの伝統的な形（JIS コード）

UTF-16 の 30 42 は、コードポイント U+3042 の番号そのものである。ほかの方式は、それぞれ独自の規則で番号をバイトに置き換えている。

たとえ: 同じ住所を、郵便番号・緯度経度・地番という別々の書き方で表すのに近い。どの書き方かを知らない人に数字だけ渡しても、場所は分からない。
ただし崩れる点: 住所の書き方は桁数や形で見分けがつくことが多いが、文字コードは同じバイト列が別の方式でも「それらしい文字」として読めてしまう（次の節）。

文字化けは、バイトが壊れたのではない

この節で分かること: 文字化けの正体。

ふつうこう考える

「縺薙ｓ縺ｫ縺｡縺ｯ」のように化けた文字は、変換の途中でデータが壊れた結果である。 化けてしまったら、元の文には戻せないだろう。


@@ echo こんにちは | iconv -f SHIFT_JIS -t UTF-8
@@ echo こんにちは | iconv -f SHIFT_JIS -t UTF-8 | iconv -f UTF-8 -t SHIFT_JIS
だめな理由: 戻った。1回目は、UTF-8 のバイト列を「Shift_JIS だと思って」読んだ。e3 81 は Shift_JIS では「縺」という漢字に当たるので、それらしい文字の列ができた。 2回目は同じ読み違いを逆にたどっただけで、元のバイト列がそのまま出てきた。バイトそのものを比べると同じである。 文字化けは読み方の間違いで、ファイルの中身が壊れたわけではない。

@@ echo こんにちは | od -An -tx1
@@ echo こんにちは | iconv -f SHIFT_JIS -t UTF-8 | iconv -f UTF-8 -t SHIFT_JIS | od -An -tx1

ただし、化けた結果を「表せない文字は捨てる」ような変換にかけたり、手で編集して保存したりすると、そこで初めて情報が失われる。化けたら、まず元のファイルを残したまま、読み方（-f）を変えて試す。

たとえ: 暗号表を取り違えて手紙を読むのに近い。出てきた文はでたらめだが、手紙そのものは1文字も変わっていない。正しい暗号表で読み直せば元の文が出てくる。
ただし崩れる点: 暗号の手紙には「この表で読め」と書き添えることもあるが、ふつうのテキストファイルには、どの文字コードで書いたかの印がどこにも無い（UTF-16 の BOM など、一部の例外を除く）。

ファイルは、自分の文字コードを名乗らない

この節で分かること: 文字コードを見分ける道具の限界。

同じ文を4つの文字コードで保存する。


@@ mkdir -p ~/enc
@@ printf '日本語のメモ\n' > ~/enc/utf8.txt
@@ iconv -f UTF-8 -t SHIFT_JIS ~/enc/utf8.txt > ~/enc/sjis.txt
@@ iconv -f UTF-8 -t EUC-JP ~/enc/utf8.txt > ~/enc/euc.txt
@@ iconv -f UTF-8 -t ISO-2022-JP ~/enc/utf8.txt > ~/enc/jis.txt
@@ cd ~/enc && file *.txt
@@ cd ~/enc && wc -c *.txt

file は EUC-JP のファイルを「OpenPGP Public Key」（暗号の公開鍵のファイル）と言った。先頭のバイトの並びが、たまたまその形式の目印と一致したからである。file はバイトの並びから推測しているだけで、文字コードを知っているわけではない。実践編の演習08の EUC-JP のファイルは「ISO-8859 text」と判定される。ISO-8859 の系列が文字を置いているのは 0xA0〜0xFF で（0x80〜0x9F は制御文字）、EUC-JP の日本語のバイトは 0xA1〜0xFE だけを使うので、その範囲に収まって「ISO-8859 として読める」からである。Shift_JIS は 0x81〜0x9F も使うので、上の記録のとおり「Non-ISO extended-ASCII text」になる。ISO-2022-JP は全部のバイトが 0x80 未満なので「ASCII text」に見える。

バイト数は、UTF-8 が19（かな・漢字が3バイト×6＋改行）、Shift_JIS と EUC-JP が13（2バイト×6＋改行）、ISO-2022-JP も19（2バイト×6＋前後の切り替えの印3バイトずつ＋改行）である。


@@ cat -v ~/enc/sjis.txt
@@ od -c ~/enc/jis.txt
@@ iconv -f SHIFT_JIS -t UTF-8 ~/enc/sjis.txt
@@ iconv -f EUC-JP -t UTF-8 ~/enc/sjis.txt > /dev/null; echo $?

cat -v は表示できないバイトを M- 付きの記号で見せる。ISO-2022-JP には 033 $ B（ESC $ B）と 033 ( B という切り替えの印が入っている。正しい -f なら元の文になり、違う -f では途中で止まる。

手を動かす: 実践編の演習08は、文字コードのそろわない3つのファイル（中身は日本語）を UTF-8 に直す課題である。 判定は、変換後のファイルを元のファイルの正しい読み方と突き合わせる。file の言うことをうのみにすると、1つ外す。

変換できないとき

この節で分かること: 変換先に無い文字の扱いと、iconv のオプション。

@@ printf 'こんにちは\n' | iconv -f UTF-8 -t ISO-8859-1 > /dev/null; echo $?
@@ printf 'café\n' | iconv -f UTF-8 -t ISO-8859-1 | od -An -tx1

ISO-8859-1 に日本語は無いので失敗した。メッセージは「入力が不正（illegal input sequence）」と言うが、入力の UTF-8 は正しい。変換先に無い文字でも同じ言い方をする。é は ISO-8859-1 にあるので、1バイト（e9）になった。


@@ printf 'こんにちは\n' | iconv -f UTF-8 -t ASCII//TRANSLIT; echo $?
@@ printf 'café\n' | iconv -f UTF-8 -t ASCII//TRANSLIT
@@ iconv -l | grep -E '^(SHIFT_JIS|EUC-JP|ISO-2022-JP|ISO-8859-1|UTF-8|ASCII)//'

//TRANSLIT は「近い文字に置き換える」指定で、é は e になった。日本語は近い文字が無いので ? になり、終了コードは 0。失敗を報告せずに情報が消える。使うなら結果を目で確かめる。

たとえ: //TRANSLIT は、訳せない単語を「？」で埋めて納品する翻訳者に近い。似た綴りの単語がある言語どうしなら、それなりに読める訳になる（café → cafe）。
ただし崩れる点: 人の翻訳者なら「ここは訳せませんでした」と添えるが、iconv は終了コード 0 で何も言わない。スクリプトで $? だけを見ていると、成功に見える。
iconv の書き方意味
-f 文字コード入力をどう読むか（from）
-t 文字コード何で書き出すか（to）。//TRANSLIT で近い文字に置き換え、//IGNORE で表せない文字を捨てる
-c変換できない文字を捨てて続ける
-o ファイル結果をファイルに書く（> でも同じ）
-l使える文字コードの名前の一覧

9章を1本にする

この節で分かること: 主題1.08 の3つの副題に共通していたこと。

この章で見たのは「バイト列は文字コードを名乗らず、読む側（iconv -f・端末・file）が読み方を決める」ことだった。これは第1章からずっと同じ形をしている。

章書き換えたもの（台帳）それを読んで決める側
1/etc/passwd の4列目と /etc/group の4列目id とログイン（2つを合わせて所属を決める）
2/etc/passwd の6列目（ホーム）sudo・su・ログイン（ディレクトリが無くても止めはせず、警告して元の場所や / で始める）
3/etc/group のメンバー欄次のログイン（いまのシェルは読み直さない）
4/etc/shadow の2列目と8列目sshd と PAM（鍵の照合は2列目を読まない。期限は必ず読む）
5crontab の行と置き場所cron（ファイル名で実行ユーザを決める。Debian 系は . 付きの名前を読まない）
6/etc/cron.daily のファイル名と実行権run-parts と anacron（Debian 系の run-parts は名前で選び、anacron は日付で決める）
7/etc/at.allow と /etc/at.denyat（どちらも無ければ root だけ）
8LANG と LC_*C ライブラリ（実体が無ければ黙って C）
9バイト列iconv -f・端末（読み方を間違えると化ける）

管理コマンドが書き換えるのは、台帳（/etc やスプールにあるテキスト）の1行だけである。 その1行が効くかどうかは、台帳を読む側が、いつ・どの列を読むかで決まる。

だから「コマンドが成功した」ことと「狙った効果が出た」ことは別で、確かめるには読む側に聞くしかない （id、実際の ssh、run-parts --test、locale -a、iconv の結果）。主題1.08 の詳細欄にファイルのパスがたくさん並んでいるのは、それぞれが「誰かに読まれる台帳」だからである。

確認

Shift_JIS で書かれた memo.txt を、UTF-8 に変換して memo-utf8.txt に保存したい。正しいコマンドはどれか。

A. iconv -f UTF-8 -t SHIFT_JIS memo.txt > memo-utf8.txt　B. iconv -f SHIFT_JIS -t UTF-8 memo.txt > memo-utf8.txt　C. iconv -t SHIFT_JIS memo.txt -o memo-utf8.txt　D. iconv -l SHIFT_JIS UTF-8 memo.txt

答え

B。-f が元の読み方（from）、-t が書き出す文字コード（to）。A は逆向き。-o memo-utf8.txt を使って iconv -f SHIFT_JIS -t UTF-8 -o memo-utf8.txt memo.txt としてもよい。

確認

7ビットのバイトだけで日本語を表し、エスケープシーケンスで文字の集合を切り替える文字コードはどれか。

A. EUC-JP　B. Shift_JIS　C. ISO-2022-JP　D. UTF-8

答え

C。この章の「あ」は 1b 24 42 24 22 1b 28 42 で、すべて 0x80 未満だった。file は「ASCII text, with escape sequences」と判定する。 日本語の電子メールで長く使われてきた（JIS コードとも呼ばれる）。

確認

Unicode と UTF-8 の違いを説明せよ。また ASCII との関係も答えよ。

答え

Unicode は文字に番号（コードポイント。「あ」は U+3042）を振った文字の集合で、UTF-8 はその番号をバイト列に置き換える方式（符号化）の1つ。 UTF-8 は ASCII の範囲（0x00〜0x7F）をそのまま1バイトで表すので、ASCII だけのファイルはそのまま UTF-8 としても正しい。

この章で分かったこと

持ち帰ってほしいこと

  • Unicode は文字に番号を振った表、UTF-8 はそれを1〜4バイト（古い定義では最大6バイト）に詰める方式。ASCII（7ビット）と互換
  • 同じ文字でも、Shift_JIS・EUC-JP・ISO-2022-JP（7ビット＋エスケープ）・ISO-8859-1（日本語なし）でバイト列が違う
  • ファイルは文字コードを名乗らない。file は推測で、EUC-JP を ISO-8859 や OpenPGP Public Key と言うこともある
  • 文字化けは読み方の誤り。元のバイト列があれば、正しい iconv -f で戻せる
  • iconv -f 元 -t 先。表せない文字は失敗する（メッセージは「illegal input」）。//TRANSLIT は黙って ? に置き換え、終了コード 0
