4. 新しい形式の表（GPT）と、起動に使う区画

第3章では、vdb の MBR の表を読み、消した vdb1 を取り戻し、拡張・論理パーティションで5つ以上に分けた。この章では、もう1つの表の形式 GPT を練習機自身のディスク vda で読み、起動に使う区画（ESP）の役目を確かめてから、vdb を「UEFI で起動するサーバのディスク」として GPT で切り直す。

前提: 第3章まで読了前提: 練習機の中にいる所要 25分影響度 B出題範囲 1.05.2（重要度4）最終検証 2026-10-20

この章のゴール

  • MBR と GPT の違い（区画の数・大きさの上限・種類の表し方）を言える
  • ESP が何のための区画で、UEFI のファームウェアが起動のときにそれをどう見つけるかを説明できる
  • /・/boot・/var・/home・スワップを用途で分ける理由を言え、gdisk で GPT の表を作って種類を付けられる。parted で区画を消してから quit で抜けたとき、表がどうなっているかを確かめる
ここで覚えなくていいこと: Secure Boot（起動するプログラムの署名を確かめる仕組み）と shim の役目は扱わない。GRUB の設定ファイルの書き方（主題1.01 のコース）も扱わない。BIOS（古い起動の方式）で GPT のディスクから起動するしくみの細部も扱わない。

練習機自身のディスクの表を読む

この節で分かること: GPT の表を fdisk -l で読むと、MBR と何が違って見えるか。

第3章と同じ fdisk -l で、練習機の Linux が入っている vda を読む。

$ sudo fdisk -l /dev/vda

Disklabel type: gpt である。GPT（GUID Partition Table）は、MBR の制限をなくすために作られた新しい表の形式で、いまの PC やサーバはふつうこれを使う。Disk identifier が長いのは、GUID（128 ビットの番号。でたらめに選ぶので、世界中でほぼ重ならない）を使っているからである。表の Type の列には、種類の番号ではなく名前が出ている。最後の Partition table entries are not in disk order. は「表の行の順番が、ディスクの上の並び順と違う」という注意で、1 番の vda1 がディスクのいちばん後ろにあるために出る（困ることは無い）。

MBRGPT違いが何のためにあるか
区画の数基本4つまで（5つ目からは拡張・論理）ふつう 128 個まで、全部が同じ扱い拡張・論理という回り道をなくす
ディスクの大きさ2TiB まで事実上の上限なし（64 ビット）2TiB を超える大きなディスクを使う
表の置き場所先頭の1セクタだけ先頭と末尾の2か所片方が壊れても、もう片方から読み直せる
種類の表し方1バイトの番号（83 など）GUID。区画ごとにも固有の GUID（PARTUUID）を持つ番号の取り合いをなくし、区画を1つずつ見分けられる

起動の入口 — ESP

この節で分かること: vda の4つの区画の役目と、ファームウェアが ESP をどう見つけるか。

lsblk の PARTTYPENAME は、区画の種類の名前を出す列である。

$ lsblk -o NAME,SIZE,FSTYPE,PARTTYPENAME,MOUNTPOINTS /dev/vda

表を読む前に、起動の順番を押さえる。電源を入れると、OS より先にファームウェア（第1章で見た、機械に組み込まれたプログラム。PC ではマザーボード（CPU・メモリ・装置をつなぐ大きな基板）に入っている）が動く。いまの PC のファームウェアは UEFI という決まりに沿って作られていて、ディスクの中の決まった区画からブートローダ（カーネルを読み込んで起動するプログラム）を読む。ブートローダがカーネルを動かし、カーネルが / をマウントして、OS が動き出す。

区画種類（PARTTYPENAME）中身・マウント先何のためにあるか
vda15EFI Systemvfat → /boot/efiESP（EFI System Partition）。電源を入れたとき最初に読まれる、ブートローダの置き場所
vda16Linux extended bootext4 → /bootカーネル（Linux の本体）と、起動の途中で使うファイルの置き場所
vda1Linux filesystemext4 → /それ以外の全部（OS・プログラム・設定・利用者のファイル）
vda14BIOS boot（ファイルシステム無し）BIOS（古い起動の方式）で GPT のディスクから起動するときに使う。この練習機では使われていない

ファームウェアがブートローダを読みに行く「決まった区画」が ESP である。ESP は FAT（第1章で見た vfat）で作る。中を見る。/boot/efi は root にしか読めないようにマウントされているので、sudo を付ける。ls の -R は、下のディレクトリの中まで順に出すオプションである。

$ sudo ls -R /boot/efi/EFI

EFI の下に BOOT と ubuntu の2つのディレクトリがある。.efi は UEFI が実行できるプログラムの形である。ubuntu の shimx64.efi は、grubx64.efi（GRUB というブートローダ）を呼び出すプログラムで、BOOT の BOOTX64.EFI は、起動の候補が無い機械でファームウェアが動かす、決まった名前のファイルである。では、ファームウェアはどうやって、どの区画のどのファイルを動かすかを決めるのか。ファームウェアは、起動の候補をNVRAM（マザーボードの、電源を切っても消えないメモリ）に覚えている。efibootmgr は、その候補を読むコマンドである。

$ sudo efibootmgr

Boot0000〜Boot0002 が候補で、BootOrder がそれを試す順番、BootCurrent が今回の起動に使った候補である（Timeout は候補を選ぶ画面を出す秒数）。Ubuntu の候補の HD(15,GPT,9606bc98-…,…)/File(\EFI\ubuntu\shimx64.efi) は、「GPT の 15 番目の区画で、区画の番号（PARTUUID）が 9606bc98-… のものの中の、このファイル」と読む。blkid（区画やファイルシステムに書かれた種類・名前（LABEL。付け方は第5章）・番号を読むコマンド）で vda15 を読んで比べる。

$ sudo blkid /dev/vda15

最後の PARTUUID が、Ubuntu の候補の番号と一致している。ファームウェアは Linux より先に動くので、/dev/vda15 という名前も、/boot/efi というマウント先も知らない。知っているのは、GPT の表の上の番号と PARTUUID と、ファイルのパスだけである。/boot/efi にマウントしてあるのは、Linux がブートローダを更新するとき（パッケージの更新など）に中のファイルを書き換えるためである。

ところで、今回の起動（BootCurrent）は Ubuntu の 0002 ではなく 0001 だった。0001 は、候補がまだ何も無い新しい機械のために、ディスクの決まった場所（\EFI\BOOT\BOOTX64.EFI）を動かす項目である。この練習機は工場出荷時の最初の起動をここから行い、その起動の途中で、ubuntu の BOOTX64.CSV（候補の控え）をもとに Ubuntu の候補（0002）が作られて、BootOrder の先頭に入った。練習機を一度でも再起動した人の画面では、BootCurrent が 0002 になっている（再起動のあとは、Ubuntu の候補で起動する）。

ESP の種類 EFI System は、UEFI の決まりが定めた「この区画が ESP だ」という印である。OS のインストーラや、ESP を探して更新する道具は、この印で ESP を見分ける。だから ESP を作るときは、必ずこの種類にする。

たとえ: ファームウェアは建物の守衛、NVRAM の候補は守衛の来客名簿に近い。名簿には「15 番の部屋（区画の番号と PARTUUID）の、この人（ファイルのパス）を呼べ」と書いてあり、守衛は名簿の順に、それだけを見て呼び出す。名簿がまだ無い新しい建物では、決まった部屋の決まった人（\EFI\BOOT\BOOTX64.EFI）を呼び、その人が名簿を書く。
ただし崩れる点: 守衛なら建物の中の事情（どの部屋をいま誰が使っているか）も聞けるが、ファームウェアは Linux の設定（どこにマウントしているか）を一切読まない。Linux が動き出す前に仕事を終えるからである。

用途ごとに区画を分ける

この節で分かること: 新しいサーバのディスクを、何のためにどう区切るか。

練習機の vda は、/ と、起動に要る2つ（ESP と /boot）しか分けていない。クラウドのサーバは1台を1つの用途に使い、足りなくなれば作り直すことが多いので、小さく単純にしてある。区画を分けるのは必須ではないが、分けておくと、ある区画が溢れたり壊れたりしたときの被害が、その区画の中で止まる。何を分けるかは「いっぱいになったら何が困るか」「作り直すときに何を残したいか」で決める。

区画入るもの分ける理由
ESPブートローダ（FAT）UEFI で起動するなら必須。種類を EFI System にする
/bootカーネルと、起動の途中で使うファイル/ を複雑な形（第9章の LVM や暗号化）にしても、ブートローダが読める単純な形で残す
スワップメモリから書き出した中身メモリが足りないときの逃げ場（ファイルシステムではなく、専用の領域にする）
/OS とプログラムほかが溢れても、これが溢れなければシステムは動く
/varログ・メールの待ち行列・データベースなど、増え続けるものログが溢れても / を道連れにしない
/home利用者のファイルOS を入れ直しても残す。利用者が溢れさせても OS に響かない

この割り当てを vdb に作る。大きさは、ESP 100M・/boot 300M・スワップ 256M・/ 600M・/var 400M・/home 残り全部とする。

たとえ: 引っ越し先の部屋割りに近い。台所（/var）が散らかっても寝室（/）に物が溢れないよう、壁で仕切っておく。
ただし崩れる点: 部屋なら隣が空いていれば物を一時的に置けるが、区画は隣の区画に空きがあっても使えない。仕切りを動かす（区画の大きさを変える）のは手間がかかるので、後から広げたい区画は LVM（第9章）に載せておくのが今のふつうのやり方である。

gdisk で GPT を作る

この節で分かること: gdisk で GPT の表を作り直し、種類を4文字のコードで付ける流れ。

gdisk は GPT のための区切る道具で、使い方は fdisk とほぼ同じ（1文字のキーで操作し、w で書く）である。いまの vdb の MBR の表を、o（空の GPT にし直す）で捨ててから、n で6つ作る。n では4つ聞かれる: 番号（Enter で次の番号）・始まり（Enter で空きの先頭）・終わり（+100M のように大きさで）・種類（4文字のコード。ef00 = EFI System、8300 = Linux filesystem、8200 = Linux swap。L で一覧）。最後の区画は、終わりも Enter（残り全部）にする。

$ sudo gdisk /dev/vdb

最初に出た Found invalid GPT and valid MBR; converting MBR to GPT format in memory. は「GPT は無く MBR がある。メモリの上で GPT に変換した」で、w を打たなければディスクは変わらない。o は、すべての区画を消して空の GPT（と、古い道具に「このディスクは使用中」と見せるための保護用の MBR）を作る。p の表の Code の列に、付けた種類のコードが並んでいる。w を打つと、上書きしてよいかをもう一度聞いてくる。

$ lsblk -o NAME,SIZE,FSTYPE,PARTTYPENAME /dev/vdb

vdb1 の FSTYPE が ext4 になっている。種類は EFI System なのに、第2章で作った ext4 の印が残っている。いまの vdb1 も第2章の vdb1 も 2048 番目のセクタから始まるので、表を作り直しても、同じ場所にある印はそのまま見える（第3章と同じ）。ただし、その ext4 は 200MiB の区画に作ったもので、100MiB しかない今の vdb1 には収まらないため、このままではマウントできない（ext4 が自分の大きさと区画の大きさの食い違いに気づいて断る）。ESP の中身（FAT）は次の章で作る。

もう1つの道具 parted でも読む。parted は MBR と GPT の両方を扱う区切る道具で、print で表を出す。

$ sudo parted /dev/vdb print

parted は大きさを MB（1000×1000 バイト）で表示する（fdisk・gdisk の MiB とは単位が違うので、数字が少し大きく見える）。Flags の列には、種類が boot, esp（ESP）や swap という旗の形で出る。Name の列は GPT の区画に付けられる名前で、gdisk は種類の名前をそのまま付けた。

parted で消してから、quit で抜けると？

この節で分かること: parted で区画を消して quit で抜けると、表はどうなっているか。

parted はディスクの名前だけを渡すと、(parted) という問いを出す対話の画面になる。

ふつうこう考える

fdisk も gdisk も、w を打つまではディスクを変えなかった。parted でも、試しに区画を消してから quit で抜ければ、何も変わらないはずだ。

$ sudo parted /dev/vdb
$ sudo parted /dev/vdb print
だめな理由: 6番が表から消えている。parted は、コマンドを打った瞬間にディスクに書く。w に当たる「最後にまとめて書く」段階が無く、rm 6 と打った時点で消えていた。quit の後に出た Information: You may need to update /etc/fstab. は「区画が変わったので、起動のときにマウントする表（第7章）も直す必要があるかもしれない」という一般的な注意で、変更を取り消したという意味ではない。

消したのは表の1行だけなので、同じ位置に作り直せば元に戻る（第3章と同じ）。parted は引数に続けて書くと、対話の画面にならずに1つのコマンドだけを実行する。mkpart は区画を作るコマンドで、GPT では「区画の名前・ファイルシステムの種類（種類の印を選ぶための手がかり）・始まり・終わり」を渡す。始まりは、消す前の print に出ていた 1737MB、終わりの 100% はディスクの最後までである。

$ sudo parted /dev/vdb mkpart home ext4 1737MB 100%
$ sudo parted /dev/vdb print

6番が同じ 1737MB〜2146MB に戻った。Name は今度付けた home になっている。parted は始まりと終わりを 1MiB の切れ目に合わせて丸めるので、MB で渡しても gdisk で作ったときと同じセクタになる。

fdiskgdiskparted
扱える表（いまの版）MBR と GPT（o で空の MBR、g で空の GPT を作る ※）GPT（MBR は変換して読む）MBR（msdos と表示）と GPT（gpt）
ディスクに書くときw を打ったときw を打ったときコマンドを打った瞬間
使い方対話（1文字のキー）。-l で表示だけ対話（1文字のキー）。-l で表示だけ ※。sgdisk は一括版 ※対話でも、引数に続けて書いても使える（print・mkpart・rm）。-l で全部のディスクの表を出す ※
大きさの単位セクタ。+200M で MiBセクタ。+100M で MiBMB・GB（unit で変えられる ※）

※ はこの章では打たない（試験で名前が出るので、表にだけ載せた）。

版による違い: fdisk が GPT を扱えるようになったのは util-linux 2.23（2013年。当時は実験的な対応）からで、それより前の fdisk は MBR だけを扱った。
たとえ: fdisk と gdisk は第2章の下書きと清書、parted はペンで直接書く書き方に近い。ペンは書いた瞬間に残る。
ただし崩れる点: ペンで書いた字は消せないが、parted で消した区画も、中身はディスクに残っている。消えたのは表の1行だけで、同じ位置に作り直せば元に戻る（いま戻したとおり）。
手を動かす: 実践編の演習03は、この章で作った6つの区画を GPT に作る課題である（道具は gdisk・parted・fdisk のどれでもよい）。 判定は表を読み、種類と大きさを1行ずつ比べる。この章のとおりに打った人は、もう達成している。
確認

UEFI のファームウェアが起動のときに ESP を見つける手がかりは何か。/boot/efi というマウント先は手がかりになるか。

答え

NVRAM に覚えている起動の候補（efibootmgr で見られる）に書かれた、GPT の区画の番号と PARTUUID と、ファイルのパス（\EFI\ubuntu\shimx64.efi）。候補がまだ無い新しい機械では、ディスクの決まった場所（\EFI\BOOT\BOOTX64.EFI）を動かす。マウント先は手がかりにならない。ファームウェアは Linux より先に動くので、Linux の設定を読めない。ESP の中は FAT で、種類は EFI System にする。

確認

/var を / と別のパーティションにすると、どんな事故を防げるか。

答え

ログやメールの待ち行列などが増え続けて区画がいっぱいになっても、/ まではいっぱいにならない。/ が溢れると、ほかのプログラムが一時ファイルを書けなくなるなど、システム全体が困る。

確認

parted の対話の画面で rm 3 と打ってから quit で抜けた。3番の区画はどうなっているか。fdisk で d を打ってから q で抜けた場合はどうか。

答え

parted は打った瞬間に書くので、3番はもう表から消えている（中身はディスクに残っている）。fdisk は w を打つまで書かないので、q で抜ければ何も変わっていない。

この章で分かったこと

持ち帰ってほしいこと

  • GPT は MBR の後の表の形式。区画はふつう 128 個まで同じ扱いで、2TiB の制限が無く、表を先頭と末尾の2か所に持ち、種類を GUID で表す
  • ESP は UEFI のファームウェアがブートローダを読む FAT の区画で、種類は EFI System（gdisk のコード EF00）。ファームウェアは NVRAM の候補（区画の番号・PARTUUID・ファイルのパス）で読みに行き（候補が無ければ \EFI\BOOT\BOOTX64.EFI）、マウント先は知らない。/boot/efi のマウントは、Linux がブートローダを更新するため
  • 区画は「溢れたら困るもの」「残したいもの」で分ける: ESP・/boot・スワップ・/・/var・/home。分けるのは必須ではない
  • gdisk は GPT 用の fdisk（o で空の GPT、種類は4文字のコード、w で書く）。表を作り直しても中身は残る
  • parted は MBR と GPT の両方を扱い、打った瞬間に書く（print・rm・mkpart）
