6. ログアウトしても動かし続けるのは、systemd の仕事

rootless の podman のコンテナは、student の systemd（user@1000.service）の下で動いている（第1章）。その systemd は、student がログインしている間だけ動く。 だから ログアウトすると、コンテナも止まる。動かし続けるには、student の systemd をログインと関係なく動かし（linger）、 コンテナを systemd のサービスとして書く（quadlet）。落ちたコンテナの起動し直し（--restart）は podman にもあるが、 練習機の起動のときにコンテナを立ち上げ直す常駐の係（docker なら dockerd）が podman にはいないので、その仕事を systemd に任せる。

前提: 第1章（conmon と user@1000.service）所要 27分影響度 B最終検証 2026-10-14

この章のゴール

  • ログアウトで rootless のコンテナが止まることを、ログインし直して確かめられる
  • loginctl enable-linger が何を変えるかを、ログアウトの後のコンテナの状態で示せる
  • quadlet の .container ファイルから、systemd のサービスが作られる仕組みを、作られた unit から読める
ここで覚えなくていいこと: quadlet の全項目（.volume・.network・.kube）、podman generate systemd（古いやり方）、 podman auto-update、root の quadlet（/etc/containers/systemd）。

ログアウトすると、コンテナはどうなるか

この節で分かること: student の systemd とコンテナの寿命の関係。

ふつうこう考える

podman run -d で裏で動かしたコンテナは、端末を閉じてもログアウトしても動き続ける（docker の -d と同じで、そのためのオプションだ）。

@@ loginctl show-user student -p Linger
@@ podman run -d --name p6 alpine:3.24.2 sleep 3600
@@ podman ps --format '{{.Names}}: {{.Status}}'
@@ exit

外に出て15秒待ってから入り直す（student の systemd は、最後のログインが終わってから10秒で止まる）。

@@ sleep 15
@@ ssh linuc  ## elide
@@ podman ps -a --format '{{.Names}}: {{.Status}}'
だめな理由: 動いていた p6 は、ログインし直すと Created（作られただけ）になっていた。 最後のログインが終わると、logind は student の systemd（user@1000.service）を止め、その下のかごにいた conmon とコンテナのプロセスも止められた。 実行中の記録（/run/user/1000 の下）もそのとき消えたので、podman にはディスクの記録（作ったこと）しか残っていない。 -d は端末から切り離すだけで、student の systemd が止まれば、その下のコンテナも止まる。 docker のコンテナは root の containerd の下にいるので、ログインと関係なく動き続ける。
@@ podman rm p6

linger — ログインが無くても systemd を動かしておく

この節で分かること: loginctl enable-linger で、コンテナの寿命がどう変わるか。

linger は「ログインしていなくても、そのユーザの systemd を動かしておく」という logind の設定である。自分の分は自分で入れられる。

@@ loginctl enable-linger
@@ loginctl show-user student -p Linger
@@ podman run -d --name p6 alpine:3.24.2 sleep 3600
@@ exit
@@ sleep 15
@@ ssh linuc  ## elide
@@ podman ps -a --format '{{.Names}}: {{.Status}}'
@@ podman rm -f -t 0 p6

linger を入れると、ログアウトして15秒たっても p6 は動き続けていた。linger のユーザの systemd は、練習機の起動と一緒に立ち上がり、ログアウトしても止まらない。

たとえ: student の systemd は、student が在室している間だけ開いている事務所に近い。rootless のコンテナは、その事務所の中で動く仕事である。 最後の人が帰ると、事務所は電気を消して閉まり、中の仕事も止まる。linger は「人がいなくても事務所を開けておく」という届けである。
ただし崩れる点: 事務所なら閉まっても机の上の書きかけは残るが、systemd が止まると /run/user/1000 の下の実行中の記録は消える。 戻ってきたとき、仕事は「途中で止まった」ではなく「作っただけ」に見える。

quadlet — コンテナを systemd のサービスとして書く

この節で分かること: quadlet のファイルから、どんな systemd のサービスが作られるか。

linger だけでは、練習機を起動し直したときにコンテナを起動する人がいない。podman にはデーモンがいないので、機械の起動のときに立ち上がって「動いていたコンテナ」を起動し直す係もいない。 落ちたときの起動し直しなら、podman にも docker と同じ --restart がある。終了コードが 0 以外なら2回まで起動し直す（on-failure:2）コンテナで確かめる。

@@ podman run -d --name rs --restart=on-failure:2 alpine:3.24.2 sh -c 'exit 3'
@@ sleep 15
@@ podman inspect rs --format '{{.RestartCount}} {{.State.Status}} {{.State.ExitCode}}'
@@ podman rm rs

systemd のサービスにしていないのに、rs は2回起動し直され（RestartCount が 2）、3回目に終わったところで止まった（exited、終了コード 3）。 コンテナが終わると conmon が podman（podman container cleanup）を呼び、そこで方針を見て起動し直している。 podman に無いのは「機械の起動のときに立ち上げ直す」常駐の係のほうで、それを systemd に任せる（podman の podman-restart.service か、次の quadlet）。 systemd の下で動かすなら、--restart ではなく systemd の Restart= を使うのが podman の勧めである。

podman は、決まった場所の .container ファイルを読んでサービスの定義（unit）を作る仕組み、quadlet を持っている。

@@ mkdir -p ~/.config/containers/systemd

このディレクトリに、動かしたいコンテナを書いたファイルを置く。中身は [Container] に podman run の材料（イメージ・コマンド・公開するポート）、[Service] と [Install] に systemd への頼みを書く（httpd は既定の 80 番で待ち受ける）。

@@ cat > ~/.config/containers/systemd/web.container <<'EOF'
@@> [Unit]
@@> Description=busybox httpd (quadlet)
@@> [Container]
@@> Image=docker.io/library/busybox:1.38.0
@@> Exec=httpd -f -h /etc
@@> PublishPort=127.0.0.1:8082:80
@@> [Service]
@@> Restart=always
@@> [Install]
@@> WantedBy=default.target
@@> EOF
@@ systemctl --user daemon-reload
@@ systemctl --user cat web.service | grep -E '^(ExecStart|Restart|WantedBy)='
@@ ls /run/user/1000/systemd/generator/default.target.wants/

systemctl --user daemon-reload のときに、quadlet（systemd の generator として動く）が web.container を読み、web.service という unit を作った。 中身を見ると、ExecStart= は podman run の1行で、.container に書いた項目がそのままオプションになっている（--name=systemd-%N の %N はサービスの名前 web）。 [Install] の WantedBy=default.target は、generator が default.target.wants/ に置いたリンクになった。student の systemd が起動するたびに（linger なら練習機の起動のたびに）、web.service も起動する。

@@ systemctl --user start web.service
@@ systemctl --user is-active web.service
@@ curl -s http://127.0.0.1:8082/hostname
@@ podman ps --format '{{.Names}}  {{.Ports}}'

コンテナの名前は systemd-web だった。落ちたらどうなるかを、外から KILL を送って確かめる（podman kill の既定は KILL）。

@@ podman kill systemd-web
@@ sleep 5
@@ systemctl --user show -p NRestarts -p ActiveState web.service
@@ curl -s http://127.0.0.1:8082/hostname

systemd は止まったことに気づき（コンテナの終わりを conmon から知らされる）、Restart=always に従って起動し直した（NRestarts=1）。 返ってきたホスト名が前と違うのは、起動し直したのが新しいコンテナだからである（podman run --rm --replace で作り直している）。

たとえ: quadlet は、手書きの作業メモを、事務所の正式な業務手順書に清書してくれる係に近い。メモ（.container）には「何を動かすか」だけを書けば、 清書（unit）には「いつ始めるか・止まったらどうするか・誰の業務か」が systemd の書式で入る。
ただし崩れる点: 清書係は一度書いたら終わりだが、quadlet は daemon-reload のたびに書き直す。作られた unit を手で直しても次の reload で消えるので、直すのはいつもメモ（.container）のほうである。
たとえ: Restart=always は、倒れた看板を立て直す警備員に近い。看板（コンテナ）が倒れる（終わる）たびに、すぐに立て直す。
ただし崩れる点: 警備員は同じ看板を立て直すが、quadlet の unit は --rm --replace で毎回新しいコンテナを作るので、立て直した看板は別物になる（ID もホスト名も変わる）。看板に書いたもの（コンテナの書き込み用の層）は残らない。

片付ける。サービスを止め、メモを消して reload すると、unit も消える。linger も元に戻す。

@@ systemctl --user stop web.service
@@ rm ~/.config/containers/systemd/web.container
@@ systemctl --user daemon-reload
@@ loginctl disable-linger
@@ loginctl show-user student -p Linger
@@ podman ps -a
手を動かす: 実践編の演習06で、quadlet のファイルを書いて web サーバをサービスにし、ログアウトしても動き続けるようにする。
確認

rootless の podman で動かしていた web サーバが、ssh を切った後しばらくして止まった。docker で同じことをしたときは止まらなかった。なぜか。

答え

rootless のコンテナは student の systemd（user@1000.service）の下で動いていて、その systemd は最後のログインが終わると止まる（既定では10秒後）。 docker のコンテナは root の containerd の下にいるので、ログインと関係が無い。loginctl enable-linger で student の systemd を動かしておけば止まらない。

確認

~/.config/containers/systemd/web.container を書いたのに、systemctl --user start web.service が「unit が無い」と言った。何を忘れているか。

答え

systemctl --user daemon-reload。quadlet は systemd の generator として動き、reload のときに .container を読んで unit を作る。 書いただけでは unit はまだ無い（ファイルの書き間違いがあっても unit が作られない）。

この章で分かったこと

持ち帰ってほしいこと

  • rootless のコンテナは student の systemd の下で動く。最後のログインが終わると、その systemd ごと止まる
  • loginctl enable-linger は、ログインが無くても student の systemd を動かしておく（練習機の起動時にも立ち上がる）
  • 落ちたときの起動し直し（--restart）は podman 自身もできるが、練習機の起動のときに立ち上げ直す係はいない。quadlet は .container から、podman run を1行に書いた systemd の unit を作り、起動・停止・再起動を systemd に任せる
