2. コンテナの中の root は、外では student

rootless の podman のコンテナの中で id を打つと、root と答える。ところがその root が作ったファイルは、練習機の上では student の持ち物になっている。 コンテナはユーザ名前空間の中で動き、中の UID を外の別の UID に読み替える表（UID の対応表）を持っている。表の材料は /etc/subuid に書かれた、student が使ってよい UID の範囲（サブ UID）である。

前提: 第1章所要 22分影響度 B最終検証 2026-10-14

この章のゴール

  • コンテナの中の UID が、練習機の上でどの UID になるかを、UID の対応表から計算できる
  • /etc/subuid と newuidmap が、対応表を作るときに何をしているかを言える
  • podman unshare で、コンテナと同じ見え方の中に入って、持ち主の食い違いを直せる
ここで覚えなくていいこと: ユーザ名前空間の中のケーパビリティの細部、--userns=keep-id などの対応表の作り方の選択肢、 ファイルシステムの ID の読み替え（idmapped mount）、/etc/subgid のグループ側の細部（UID と同じ形）。

中の root が作ったファイルの、外での持ち主

この節で分かること: rootless のコンテナの root が、練習機の上で誰として振る舞うか。

student の持ち物のディレクトリをコンテナに見せ（バインドマウント）、中の root にファイルを作らせる。Docker 第7章と同じ実験である。

ふつうこう考える

コンテナの中で id が root と答えるなら、その root が作ったファイルは、docker のときと同じく練習機の上でも root（UID 0）の持ち物になるはずだ。

@@ mkdir ~/share
@@ podman run --rm -v "$HOME/share":/share alpine:3.24.2 sh -c 'id -u; touch /share/by-root; ls -ln /share'
@@ ls -ln ~/share
だめな理由: コンテナの中では持ち主が 0（root）に見えるファイルが、練習機の上では 1000（student）の持ち物だった。 rootless のコンテナの中の UID 0 は、練習機の上では student（UID 1000）である。同じファイルを、中と外で別の番号で見ている。 docker（ユーザ名前空間を区切らない）では、中の root は練習機の root そのものだった。

UID の対応表

この節で分かること: 中の UID を外の UID に読み替える表の読み方と、その表がどこから来たか。
@@ cat /proc/self/uid_map
@@ podman unshare cat /proc/self/uid_map
@@ grep student /etc/subuid /etc/subgid

/proc/self/uid_map は「名前空間の中の UID・外の UID・個数」の3列の表である。練習機の上のシェルは、全部の UID がそのまま（0 から 4294967295 個）。 podman unshare は、podman がコンテナに使うのと同じユーザ名前空間の中でコマンドを動かす。その中の表は2行だった。

中の UID外の UID個数意味
010001中の root は、外の student 自身
1〜65536100000〜16553565536/etc/subuid の student:100000:65536（student が使ってよい UID の範囲）を、中の 1 から順に割り当てる

だから中の UID 1000 は、外では 100000 + (1000 − 1) = 100999 になる。/etc/subuid の範囲の UID は練習機に人として登録されていない番号で、 外から見れば「誰でもない」持ち主である。

ただし、一般ユーザの student が自分で「外の 100000 番」を名乗る表を書くことは、カーネルが許さない。書くのは、root の権限を持たされた小さなプログラムである。

@@ ls -l /usr/bin/newuidmap /usr/bin/newgidmap

この練習機（Ubuntu）の newuidmap と newgidmap は持ち主が root で、s の印（setuid）が付いている（Fedora や Arch などは setuid ではなく、ファイルのケーパビリティ（newuidmap は cap_setuid、newgidmap は cap_setgid）で必要な権限だけを持たせる）。 呼び出した人が /etc/subuid（/etc/subgid）で許された範囲だけを、その権限で対応表に書く。rootless の podman で root の権限を使うのは、この表を書くところだけである。

たとえ: ユーザ名前空間は劇団の役名の表に近い。舞台の上（コンテナの中）では「王様」（UID 0）でも、劇場の外の名簿（練習機）では student 本人である。 家来の役（UID 1 以上）は、劇場が student に貸し出した背番号（100000 番から）の人が演じる。
ただし崩れる点: 劇団なら役者が勝手に背番号を決められるが、対応表は student が自分では書けず、劇場の事務所（root の権限を持つ newuidmap）が /etc/subuid の貸し出し簿を見て書く。 借りていない背番号は、舞台の上でも名乗れない。

中の UID 1000 は、外では 100999

この節で分かること: 中で root 以外の UID が書くとき、外の持ち主が食い違う問題と、その直し方。
@@ podman run --rm --user 1000:1000 -v "$HOME/share":/share alpine:3.24.2 touch /share/by-1000
@@ podman run --rm -v "$HOME/share":/share alpine:3.24.2 ls -lnd /share

中の UID 1000 は書けなかった。~/share は外では student（1000）の持ち物だが、中から見ると UID 0 の持ち物で、中の 1000（外の 100999）には書く権限が無い。 コンテナの中で root 以外のユーザとして動くアプリ（多くのサーバがそうする）に、外のディレクトリを渡すときによく起きる。

直すには、ディレクトリの持ち主を「中の 1000」にする。外の番号（100999）に chown するのは、student には許されていない。podman unshare の中なら、student は root なので、中の番号で chown できる。

@@ podman unshare chown 1000:1000 ~/share
@@ ls -lnd ~/share
@@ podman run --rm --user 1000:1000 -v "$HOME/share":/share alpine:3.24.2 touch /share/by-1000
@@ ls -ln ~/share
@@ podman unshare ls -ln ~/share

外から見ると ~/share の持ち主は 100999 になり、中の UID 1000 が書けるようになった。podman unshare ls で中から見ると、同じものが 0 と 1000 に見える。 同じファイルを、外と中で別の番号で見ているのが rootless の仕組みである。

片付けるとき、ここで1つ詰まる。

@@ rm -rf ~/share
@@ podman unshare rm -rf ~/share
@@ ls -d ~/share

自分のホームの中なのに、student は ~/share を消せなかった。~/share の持ち主は外では 100999 で、student ではないからだ。 podman unshare の中（student が root として振る舞える名前空間）で消すと、消えた。

たとえ: podman unshare は、舞台の上に上がって作業することに近い。客席（練習機）からは手の届かない大道具（100999 の持ち物）も、舞台に上がって王様（中の root）として振る舞えば動かせる。
ただし崩れる点: 舞台の王様でも、劇場が貸し出していない物（student の範囲の外の UID の持ち物、たとえば練習機の root のファイル）には触れない。 中の root にできるのは、自分の範囲（1000 と 100000〜165535）の持ち物だけである。
たとえ: 100999 の持ち物は、自分の部屋に置いてある、会社名義の荷物に近い。部屋（~/share の置き場所）は自分のものでも、名義が会社（100999）の荷物は、個人（student）の判断では捨てられない。会社の担当者として振る舞えば（podman unshare）処分できる。
ただし崩れる点: 会社名義の荷物なら会社に引き取ってもらえるが、100999 は練習機の誰の名前でもない番号で、外から見ると持ち主のいない荷物になる。引き取り手は、同じ表を使う student の名前空間の中にしかいない。
手を動かす: 実践編の演習02で、コンテナの中の UID 1000 が書けるディレクトリを、podman unshare を使って用意する。
確認

/etc/subuid が student:100000:65536 のとき、rootless のコンテナの中で UID 33（www-data）が作ったファイルは、練習機の上で何番の持ち物になるか。

答え

100032。中の 1 が外の 100000 に当たるので、中の 33 は 100000 + (33 − 1) = 100032。中の 0（root）だけは外の 1000（student）になる。

確認

練習機の上で ls -ln すると、持ち主が 100999 のファイルがあり、student は消せなかった。このファイルについて何が言えるか。どう消すか。

答え

student の rootless のコンテナの中で、UID 1000 のプロセスが作ったファイル（または中で 1000 に chown したもの）である。 外の student は持ち主ではないので消せない。podman unshare rm … で、中の root として消す。

確認

rootless のコンテナの中の root が、練習機の root だけが読めるファイル（たとえば /root の中のもの）を読めないのはなぜか。対応表から説明せよ。

答え

中の root は外では student（1000）で、練習機の root（外の UID 0）は対応表のどこにも出てこない。中から見ると、表に無い外の持ち主のファイルは「誰でもない」（nobody）の持ち物に見え、 中の root の特権（ファイルの権限を越えて読む CAP_DAC_OVERRIDE など）は、持ち主が対応表に無いファイルには効かない。だから student に読めない練習機の root のファイルは、中の root にも読めない。 逆に、持ち主が対応表にある番号（1000 と 100000〜165535）のファイルには中の root の特権が効くので、student 本人には読めない・消せないものでも読める・消せる（この章で、student が消せない ~/share を podman unshare rm で消せたのはこれ）。

この章で分かったこと

持ち帰ってほしいこと

  • rootless のコンテナはユーザ名前空間の中で動き、中の UID 0 は外の student（1000）、中の 1〜65536 は /etc/subuid で借りた 100000〜165535 になる
  • 対応表は /proc/PID/uid_map で読める。書くのは root の権限を持つ newuidmap / newgidmap（この練習機では setuid root）で、借りた範囲しか書けない
  • 中の root 以外の UID が書くディレクトリは、podman unshare chown で中の番号の持ち主にする。外からは 100999 などの持ち主に見える
