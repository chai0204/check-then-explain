1. podman には、頼む相手のデーモンがいない

docker コマンドは root で動く dockerd に頼むだけだった。podman コマンドは、頼む相手を持たない。 自分でコンテナを作り、見張り役の小さなプロセス（conmon）を1つ残して、すぐに終わる。 コンテナの一覧も、デーモンに尋ねるのではなく、ディスクに書いた記録を自分で読んでいる。

前提: 実践編の入口で練習機に入れた（ssh linuc）。Docker 第1章を読んでいると比べやすい所要 18分影響度 B最終検証 2026-10-14

この章のゴール

  • podman でコンテナを動かしている間、podman のプロセスが残っていないことを ps で示せる
  • コンテナのプロセスの親が conmon で、conmon が OCI ランタイム（crun）を呼んだことを、引数から読める
  • デーモンが無いので、コンテナの状態がどこに書かれ、誰の systemd の下で動いているかを言える
ここで覚えなくていいこと: conmon の全オプション、podman の状態のデータベースの中身、 crun と runc の実装の違い、podman system service（docker 互換の API。第7章で少しだけ使う）。

docker のデーモンは止まっている

この節で分かること: この練習機では、docker のデーモンが動いていないこと。

この記事の練習機は Docker の記事と同じディスクで、docker も入っている。ただし初回の準備で、docker のデーモンは止めてある。 この記事の端末は、すべて練習機の中（プロンプトが student@linuc）で打つ。

@@ systemctl is-active docker.service containerd.service
@@ docker ps

dockerd も containerd も止まっていて、docker コマンドは頼む相手がいないので何もできない。

podman でコンテナを動かし、プロセスを並べる

この節で分かること: podman のコンテナが動いている間に、何のプロセスが残っているか。

ふつうこう考える

podman も docker と同じだ。podman run -d は裏で動いているデーモンに頼んでいて、コンテナはそのデーモンの子として動いているはずだ。

@@ podman run -d --name p1 alpine:3.24.2 sleep 1000
@@ podman ps
@@ ps -o pid,ppid,user,comm -C podman,conmon,sleep,catatonit,dockerd
だめな理由: コンテナは動いているのに、podman という名前のプロセスはどこにもいない。dockerd もいない。 sleep 1000 の親は conmon で、conmon の親は PID 1（練習機の systemd）である（シェルから起動したとき。第6章の quadlet で起動すると、conmon の親は student の systemd になる）。 podman run -d はコンテナを作り、見張り役の conmon を残して、自分は終わった。頼む相手のデーモンは最初からいない。 catatonit は、student のユーザ名前空間（第2章）を保っておくための、何もしないプロセスである。
たとえ: podman run -d は、料理を届けたら帰る出前の配達員に近い。料理（コンテナ）は客の家に残り、配達員（podman コマンド）は店に戻る。お皿を下げる係（conmon）だけが、食べ終わるのを待っている。
ただし崩れる点: 配達員は二度と関わらないが、podman は、お皿を下げる係（conmon）から呼び戻される（--exit-command）。後始末と記録は、もう一度起動した podman がする。

conmon は、何を見張っているか

この節で分かること: conmon の役目と、コンテナを作った OCI ランタイム。
@@ ps -o args= -C conmon | tr ' ' '\n' | grep -A1 -E '^-(c|r|b|n|l)$|^--exit-command$'
@@ podman info --format '{{.Host.OCIRuntime.Name}} / {{.Host.Conmon.Version}}'

conmon の引数を1つ1行に分け、意味のあるものだけを、その次の行の値と一緒に抜き出した（-- の行は、grep が抜き出した組の区切りに入れたもの）。-c はコンテナの ID、-n は名前、-r /usr/bin/crun はコンテナを作る OCI ランタイム、 -b はコンテナの設定の置き場所（バンドル）、-l journald はコンテナの出力の送り先、--exit-command はコンテナが終わったときに呼ぶもの（/usr/bin/podman）である。

docker（Docker 第1章）podman役目
docker CLI → dockerd → containerdpodman（コマンドそのもの）頼みを受けて、コンテナを作る準備をする。podman は自分でやる
containerd-shimconmonコンテナ1つに1つ付き添い、プロセスの親になり、終了の記録を残す
runccrun名前空間と cgroup を設定してプロセスを作り、すぐ終わる（どちらも OCI ランタイム仕様を満たす）

conmon が残るのは、コンテナのプロセスの親になって、その終わり（終了コード）を受け取るためである。デーモンがいないので、 受け取った終了コードはファイルに書き、--exit-command で podman をもう一度呼んで、後始末と記録を頼む。

たとえ: docker は常駐の管理人がいる駐車場、podman はコインパーキングに近い。管理人（dockerd）がいれば、車の出し入れは全部管理人に頼む。 コインパーキングでは、利用者（podman コマンド）が自分で車を停め、車ごとに付いた精算機（conmon）が出庫を見張って記録する。
ただし崩れる点: 精算機は出庫したら料金を計算して終わるが、conmon はコンテナが終わると podman を呼び直して後始末を頼む。 見張り役から利用者の道具が呼ばれる、という逆向きの呼び出しがある。

デーモンがいないのに、一覧はどこから来るか

この節で分かること: podman ps が読んでいる記録と、コンテナが入っている cgroup の場所。
@@ ls ~/.local/share/containers/storage
@@ ls -l ~/.local/share/containers/storage/db.sql
@@ cat /proc/$(podman inspect -f '{{.State.Pid}}' p1)/cgroup

podman ps は、student のホームの下の記録（db.sql という SQLite のデータベースと、/run/user/1000/ の下の実行時の記録）を、毎回自分で読んでいる。 コンテナのプロセスは、練習機の system.slice（root のサービスの置き場所）ではなく、 student の systemd（user@1000.service）の下のかごに入っている。student のログインに結びついたこの systemd が、第6章の主役になる。

たとえ: デーモンのいない podman の一覧は、共有の台帳ノートに近い。誰か（podman コマンド）が車を停めるたびにノートに書き、一覧が要るときはノートを開いて読む。
ただし崩れる点: ノートは書いた人がいなくても残るが、podman の記録の一部（/run/user/1000/ の下）は、student の systemd が止まると消える。 ノートの半分が鉛筆書きで、ログアウトすると消えるようなものだ（第6章で実際に消える）。

最後に片付ける。-t 0 は「止まるまで待つ時間を 0 秒に」で、sleep が TERM を受け取らない（PID 1 の決まり。Docker 第2章）ので、待たずに KILL する。

@@ podman rm -f -t 0 p1
@@ podman ps -a
手を動かす: 実践編の演習01で、podman のコンテナを起動し、その親の conmon の PID を自分で突き止める。
確認

podman run -d の後、ps -C podman に何も出なかった。それでもコンテナが動き続けているのはなぜか。

答え

コンテナのプロセスの親は conmon で、podman コマンドではないから。podman はコンテナを作って conmon を残し、自分は終わる。 conmon は（シェルから起動したなら PID 1 の）systemd の子として動き続け、コンテナの終了を見届ける。

確認

docker で dockerd を止めると docker ps は何も答えられないが、podman ではそういうことが起きない。なぜか。

答え

podman には頼む相手のデーモンがいないから。podman ps はディスクの上の記録（~/.local/share/containers/storage/db.sql など）を自分で読む。 止めて困るような常駐のプロセスが無い。

確認

コンテナのプロセスの cgroup が /user.slice/user-1000.slice/user@1000.service/… だった。docker のコンテナ（/system.slice/docker-….scope）と比べて、何が違うと言えるか。

答え

docker のコンテナは root の systemd のサービスの置き場所（system.slice）に入り、podman の rootless のコンテナは student 自身の systemd（user@1000.service）の下に入る。 コンテナが student の持ち物として扱われていて、student の systemd が止まれば一緒に止まりうる（第6章）。

この章で分かったこと

持ち帰ってほしいこと

  • podman には頼む相手のデーモンがいない。podman コマンドがコンテナを作り、conmon を残して終わる
  • conmon はコンテナ1つに1つ付き添い、プロセスの親になって終了を見届ける（docker の shim にあたる）。作るのは crun（docker の runc にあたる）
  • 一覧や状態は、ディスク（~/.local/share/containers/storage）と /run/user/1000 の記録を、podman が毎回読む
  • rootless のコンテナは、student の systemd（user@1000.service）の下のかごで動く
