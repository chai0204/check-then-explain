4. rootless のネットワークは、カーネルの外で中継される

docker はポートを公開するとき、練習機の iptables に宛先の書き換え（DNAT）を書き、veth で練習機のブリッジにつないだ。 rootless の podman は student の権限しか持たないので、練習機のネットワークの設定を1つも変えられない。 代わりに、ユーザの権限で動くプログラムが、パケットを受け取って中へ運ぶ（slirp4netns と rootlessport、または pasta）。 だから 1024 番未満のポートは開けず、コンテナは QEMU の練習機と同じ形の網（10.0.2.0/24）に置かれる。

前提: 第2章。Docker 第5章を読んでいると比べやすい所要 22分影響度 B最終検証 2026-10-14

この章のゴール

  • rootless の podman が 80 番を公開できない理由を、練習機の設定の値で説明できる
  • ポートの公開を、iptables ではなく rootlessport というプロセスが受けていることを示せる
  • slirp4netns と pasta で、コンテナから見えるアドレスがどう違うかを示せる
ここで覚えなくていいこと: slirp4netns と pasta のオプション、netavark のブリッジ（root の podman の既定の網。rootless でも podman network create で作った網で使う）、 aardvark-dns による名前解決、IPv6。

80 番を公開する

この節で分かること: 一般ユーザのコンテナが、公開できないポートがあること。

ふつうこう考える

ポートの公開は -p を付けるだけだ。コンテナの中の 80 番を、練習機の 80 番で公開すればよい（docker では -p のホスト側に何番を書いても通った）。

@@ podman run -d --name web -p 127.0.0.1:80:80 busybox:1.38.0 httpd -f -h /etc
@@ sysctl net.ipv4.ip_unprivileged_port_start
@@ podman ps -a --format '{{.Names}}: {{.Status}}'
だめな理由: rootlessport cannot expose privileged port 80 と断られた。 練習機のカーネルは、1024 番（net.ipv4.ip_unprivileged_port_start）未満のポートで待ち受けることを、特権（CAP_NET_BIND_SERVICE）を持つプロセスにしか許さない。 rootless の podman では、練習機の側で待ち受けるのは student のプロセス（rootlessport）なので、この決まりがそのまま効く。 docker では、待ち受けるのも宛先を書き換えるのも root の dockerd とカーネルだった。コンテナは作られたまま起動しなかった（Created）。

作られただけのコンテナを消し、1024 番以上で公開し直す。

@@ podman rm web
@@ podman run -d --name web -p 127.0.0.1:8080:80 busybox:1.38.0 httpd -f -h /etc
@@ curl -s http://127.0.0.1:8080/hostname
たとえ: 1024 番未満のポートは、建物の正面玄関の受付席に近い。一般の入居者（一般ユーザ）は座れず、管理会社の人（特権を持つプロセス）だけが座れる。rootless の podman で受付に座るのは、入居者の代理人（rootlessport）なので、正面玄関には座れない。
ただし崩れる点: 本物の建物の決まりは変えにくいが、この線は練習機の設定 net.ipv4.ip_unprivileged_port_start の1つの値で、root なら引き直せる。ただし引き直すと、すべての入居者が座れるようになる。

誰がパケットを運んでいるか

この節で分かること: rootless のポートの公開とコンテナの外への通信を、どのプロセスが受け持っているか。
@@ ps -o pid,ppid,user,comm -C rootlessport,exe,slirp4netns,conmon,httpd
@@ ss -ltnp | grep 8080
@@ sudo iptables -t nat -S | grep -c 8080

練習機の 127.0.0.1:8080 で待ち受けているのは、student の rootlessport だった（pid= と fd= の番号は起動のたびに変わるので、あなたの画面では本文と違う）。iptables の nat 表には 8080 の規則が1つも無い（数えると 0）。 届いた接続は親の rootlessport が受け取る。子のプロセス（exe と表示される rootlessport-child）はコンテナの網の中で 80 番につなぎ、そのつながりを親に手渡すだけで、 両側のデータを写し続けるのは親の rootlessport である（rootlesskit の port の作り）。 コンテナの外への通信を運ぶのは slirp4netns で、どれも student のプロセスである。練習機のカーネルの網の設定は何も変わっていない。

コンテナの中から、自分のアドレスを見る。

@@ podman exec web ip -4 addr show tap0
@@ podman exec web ip route
@@ podman exec web cat /etc/resolv.conf
@@ ip -br addr show enp0s16

コンテナのアドレスは 10.0.2.100、出口（ゲートウェイ）は 10.0.2.2、DNS は 10.0.2.3 だった。そして練習機自身の NIC も 10.0.2.15 である。 偶然ではない。slirp4netns は、QEMU が練習機に見せているユーザモードの網（QEMU の記事の 10.0.2.x）と同じ部品（libslirp）を使っていて、 「NIC に見えるものの裏で、ユーザの権限で TCP/IP を話して外とつなぐ」という同じ仕組みを、コンテナに対して使っている。 libslirp 自体は番号を決めず、呼ぶ側が渡す。slirp4netns は、番号の初期値を QEMU に合わせて自分で決めている（網 10.0.2.0/24・出口 .2・DNS .3）。 ただし、自分に割り当てる番号は QEMU の練習機の .15 ではなく .100 である。

たとえ: rootless のネットワークは、建物に配管工事をさせてもらえない借家人が、窓の外に自分で中継の受付を置くことに近い。 docker（root）は建物の配管（iptables・ブリッジ）を引き直して直結できたが、借家人（student）は自分の部屋の中のこと（ユーザ名前空間の中の網）しか変えられないので、 受付（rootlessport）が荷物を受け取って中へ運ぶ。
ただし崩れる点: 本物の受付は人が運ぶので遅く見えるが、運び役は同じ計算機の中のプロセスで、手渡しの手間は小さい。 それでも、カーネルが直接書き換える docker の経路より、コピーが1回ずつ多くなる。
たとえ: slirp4netns と QEMU が同じ 10.0.2.x を使うのは、後から出た家庭用ルータが、先に広まった機種と同じ初期設定の番号を、わざと名乗ることに近い。中の部品（libslirp）は同じだが、番号の初期値は slirp4netns が QEMU に合わせて決めている。
ただし崩れる点: 同じ番号のルータを1つの家に2台つなげばぶつかるが、こちらの 10.0.2.x は、それぞれ練習機の中・コンテナの網の名前空間の中だけで使う番号で、互いに見えないのでぶつからない。

pasta — 練習機のアドレスをそのまま見せる

この節で分かること: もう1つの rootless の網（pasta）で、コンテナから見えるものがどう違うか。

この練習機の podman（4.9.3）の既定は slirp4netns で、podman 5 からは pasta（passt という道具の一部）が既定になった。--network pasta で選べる。

@@ podman run --rm --network pasta alpine:3.24.2 ip -4 addr show
@@ podman run --rm alpine:3.24.2 ip -4 addr show

pasta のコンテナには、練習機と同じ名前（enp0s16）・同じアドレス（10.0.2.15）の NIC が見えた。pasta は練習機のアドレスを写したように見せ、 コンテナの通信を練習機の通信として運び直す。slirp4netns（既定）のコンテナは、自分の tap0（10.0.2.100）を持っていた。 どちらも student の権限で動き、練習機の網の設定は変えない。

片付ける。httpd も PID 1 で TERM を受け取らないので、-t 0 で待たずに止める。

@@ podman rm -f -t 0 web
手を動かす: 実践編の演習04で、rootless のまま、練習機の 8080 番で web サーバを公開する。
確認

rootless の podman で -p 127.0.0.1:443:443 が断られた。直す方法を2つ挙げよ。それぞれ何を変えることになるか。

答え

(1) 1024 番以上（例: 8443）で公開する。練習機の側は何も変えない。(2) 練習機の net.ipv4.ip_unprivileged_port_start を 443 以下に下げる。 root の作業で、値は「ここから上を許す」という1つの境目なので、443 にすれば 443〜1023 の全部のポートでの待ち受けを、練習機の全部の一般ユーザに許すことになる。

確認

rootless の podman でポートを公開しているのに、sudo iptables -t nat -S にそのポートの規則が無い。どうやって届いているのか。

答え

練習機の側で待ち受けているのは student の rootlessport（または pasta）で、受け取った接続と、コンテナの網の中でつないだ接続の間で、ユーザの権限でデータを写している。 カーネルの宛先の書き換え（DNAT）は使っていない。ss -ltnp で、そのポートの持ち主のプロセスが分かる。

この章で分かったこと

持ち帰ってほしいこと

  • rootless の podman は練習機の網の設定を変えられないので、ユーザのプロセス（slirp4netns・rootlessport、または pasta）がパケットを運ぶ
  • だから 1024 番未満のポートは公開できない（net.ipv4.ip_unprivileged_port_start の決まりがそのまま効く）
  • slirp4netns のコンテナは 10.0.2.100 を持つ。QEMU のユーザモードの網と同じ部品（libslirp）を使い、網の番号の初期値も QEMU に合わせてある（出口 .2・DNS .3）
  • pasta は練習機の NIC とアドレスをそのまま写して見せる（podman 5 の既定）
