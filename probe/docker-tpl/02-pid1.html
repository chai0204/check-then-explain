2. コンテナの PID 1 は、合図を無視する

sleep は TERM の合図で終わるプログラムである。ところが sleep だけのコンテナに docker stop を打つと、 止まるまでにきっかり10秒かかる。コンテナの中で最初に起動したプロセスは、その名前空間の PID 1 になり、カーネルは PID 1 を特別に扱う。 後から docker exec で足したプロセスも、PID 1 の子ではない。

前提: 第1章所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • docker stop が10秒かかって終了コード 137 で終わる理由を、PID 1 とシグナルで説明できる
  • --stop-timeout と --init が、それぞれ何を変えるかを時間で示せる
  • docker exec で動かしたプロセスの TERM と umask が、どこから来るかを言える
ここで覚えなくていいこと: シグナルの全種類と番号（使うのは TERM 15・KILL 9 だけ）、 tini の作りの細部、systemd のドロップインの書式の全項目、Dockerfile の STOPSIGNAL。

docker stop は、なぜ10秒かかるのか

この節で分かること: 同じ sleep が、練習機の上とコンテナの中で、TERM に違う反応をすること。

まず練習機の上で、sleep に TERM（kill の既定の合図）を送る。 $! は直前に & で起動したプロセスの PID、wait はその終了コードを受け取る。

ふつうこう考える

練習機の上の sleep は TERM で終わった（終了コード 143 = 128 + 15。15 は TERM の番号。sh が標準エラーに出す Terminated の知らせは、出るときと出ないときがあるので 2>/dev/null で捨てている）。 docker stop も TERM を送るのだから、sleep だけのコンテナはすぐに止まるはずだ。

@@ sh -c 'sleep 1000 & sleep 1; kill $!; wait $!; echo "exit=$?"' 2>/dev/null
@@ docker run -d --name c3 alpine:3.24.2 sleep 1000
@@ time docker stop c3
@@ docker ps -a --format '{{.Names}}: {{.Status}}'
だめな理由: docker stop は10秒あまりかかり、コンテナの終了コードは 137（128 + 9。9 は KILL の番号）だった。 TERM では止まらず、10秒待った docker が KILL で止めたのである。 コンテナの中の sleep は PID 1 で、カーネルは PID 1 に、自分で受け取る準備をしていない合図を届けない。 docker stop は「止める合図を送り、決まった秒数（既定 10秒）待ち、まだ動いていれば KILL を送る」という手順で、 止める合図はイメージに STOPSIGNAL の指定が無ければ TERM である（alpine には指定が無い）。TERM を無視されれば、待ち時間をまるごと使い切る。

PID 1 に、外から合図を送る

この節で分かること: PID 1 が TERM を無視するのは docker のせいではなく、カーネルの決まりであること。

止まったコンテナは docker start で同じコンテナのまま起動し直せる（中のプロセスは新しく起動するので PID は変わる）。 今度は docker を通さず、練習機の root として直接 TERM を送る。

@@ docker start c3
@@ pid=$(docker inspect -f '{{.State.Pid}}' c3)
@@ sudo kill $pid
@@ docker ps --format '{{.Names}}: {{.Status}}'
@@ grep SigCgt /proc/$pid/status
@@ sudo kill -KILL $pid
@@ docker ps -a --format '{{.Names}}: {{.Status}}'

練習機の root が送った TERM でも、コンテナは Up のままだった。SigCgt（自分で受け取ると登録した合図の一覧）は全部 0 で、 この sleep は TERM の受け取り方を何も決めていない。普通のプロセスなら、決めていない合図は「既定の動作」（TERM なら終了）になる。 ところが名前空間の PID 1 には既定の動作が働かない。PID 1 が不意に死ぬと名前空間の全プロセスが道連れになるので、カーネルが守っている（Linux の pid_namespaces の決まり）。 例外は KILL と STOP で、これは外（親の名前空間）から送れば必ず届く。sudo kill -KILL で、コンテナはすぐに Exited (137) になった。

PID 1 が合図を受け取る準備には2通りある。1つは受け取り方（ハンドラ）を登録すること（SigCgt に出る）、もう1つは合図をブロックしておき、届いたものを後から取り出すこと。 ブロックしている合図は、PID 1 でも捨てられずに保留される（Linux の kernel/signal.c の決まり）。どちらもしていない合図だけが、黙って捨てられる。

たとえ: 名前空間の PID 1 は、船の船長に近い。船長が倒れると船全体が止まるので、乗客の「降りてくれ」（TERM）は、船長が聞く準備をしていない限り届かない。 港の当局が出す強制命令（KILL）だけは、船長の意思に関係なく実行される。
ただし崩れる点: 本物の船長は命令の中身を読んで判断するが、PID 1 は判断していない。受け取る準備（ハンドラの登録かブロック）をしていない合図は、カーネルが黙って捨てているだけである。 受け取り方を登録したプログラム（多くのサーバ）なら、PID 1 でも TERM で正常に終わる。

待ち時間を変える、合図を中継させる

この節で分かること: --stop-timeout と --init の効き方の違い。
@@ docker rm c3
@@ docker run -d --name c4 --stop-timeout 3 alpine:3.24.2 sleep 1000
@@ time docker stop c4
@@ docker run -d --name c5 --init alpine:3.24.2 sleep 1000
@@ docker exec c5 ps
@@ docker exec c5 grep SigCgt /proc/1/status
@@ time docker stop c5
@@ docker ps -a --format '{{.Names}}: {{.Status}}'
@@ docker rm c4 c5
起動のしかたPID 1docker stop にかかった時間終わり方
そのままsleep10秒あまりTERM は無視され、10秒後の KILL で 137
--stop-timeout 3sleep3秒あまり待ち時間が3秒になっただけ。やはり KILL で 137
--init/sbin/docker-init1秒ほどPID 1 の docker-init が TERM を受け取って sleep に中継し、sleep が TERM で終わる。docker-init はそれを 143（128 + 15）で報告する

--init を付けると、docker は小さな init（docker-init。tini というプログラム）を PID 1 に置き、頼んだコマンドをその子にする。 ところが docker-init の SigCgt も 0 だった。tini はハンドラを登録せず、合図をブロックしておき、届いたものを sigtimedwait という呼び出しで取り出して子に中継する（tini のソース）。 ブロックしている合図は PID 1 でも捨てられないので、SigCgt が 0 でも TERM を受け取れた。SigCgt で分かるのはハンドラの有無だけで、受け取れるかどうかは、何が PID 1 かと合わせて見る。 tini は子が終わったら後始末（終わったプロセスの回収）もする。

このサイトの仮想マシン型の檻は、--init の代わりにイメージ自身が tini を PID 1 に置き（イメージの ENTRYPOINT。LinuC 1.01 の第3章の ps -p 1）、 起動コマンドに --stop-timeout 30 を付けている。docker stop の TERM を tini が子の起動スクリプト（lab-vm-init）に中継し、 起動スクリプトは TERM を受け取ると練習機を正常に止めてから終わる。正常停止にかかる時間は、練習機の中で何が動いているかで変わる。 著者の記録（logs/docker-stop.log）では、練習機の中で何も動いていなければ 4.4 秒だったが、TERM を受け取らない PID 1 のコンテナ（この章の sleep のようなもの）を3つ残していると、 練習機の中の docker がそれぞれ10秒待ってから KILL するので 16.0 秒かかった（起動し直すと、3つとも Exited (137) だった）。 既定の10秒では間に合わないことがあるので、入口の docker run には --stop-timeout 30 が付いている（起動スクリプトは、25秒待っても練習機が止まらなければ電源を切る）。

たとえ: --stop-timeout は閉店時刻の「閉店まで○分」の放送の長さを変えるだけで、--init は入口に受付係を置くことに近い。 放送を長くしても、聞く気の無い客はやはり最後に追い出される。受付係がいれば、閉店の知らせを一人ひとりに伝えてくれる。
ただし崩れる点: 受付係（docker-init）が伝えても、客（子のプロセス）が TERM の受け取りを無視するように作られていれば、やはり出ていかない。 --init は伝える経路を作るだけで、子に TERM を聞かせる力は無い。

docker exec で足したプロセスは、誰の子か

この節で分かること: docker exec と docker run -it で、端末の種類（TERM）と umask が違って見える理由。

コンテナにもう1つプロセスを足すのが docker exec である。同じ問い（TERM・umask・端末があるか）を、入り方を変えて投げる。

@@ docker run -d --name c6 alpine:3.24.2 sleep 1000
@@ docker exec c6 sh -c 'echo "TERM=$TERM"; umask; tty'
@@ docker exec -it c6 sh -c 'echo "TERM=$TERM"; umask; tty'
@@ docker run --rm -it alpine:3.24.2 sh -c 'echo "TERM=$TERM"; umask; tty'
@@ echo "TERM=$TERM"; umask; tty

-t（端末を割り当てる）を付けたときだけ TERM=xterm になり、付けなければ TERM は空で、tty は not a tty と答えた。 TERM はコンテナの中の設定ではなく、docker が -t を見て渡している。このサイトの記録で踏んだのはこれで、端末なしの docker exec で取った記録と、 docker run -it の読者の画面とで、TERM が違った（TERM が違うと ls の色付けの有無などで表示が変わる）。

umask はどれも 0022 で、練習機の student のシェル（0002）とは違った。umask は親から子へ受け継がれる値である。では docker exec のプロセスの親は誰か。

@@ docker exec -d c6 sleep 2000
@@ ps -o pid,ppid,user,cmd -C sleep
@@ ps -o pid,ppid,comm -C containerd-shim
@@ grep Umask /proc/$(pgrep -x containerd)/status /proc/$(pgrep -x containerd-shim)/status

後から足した sleep 2000 の親は、PID 1 の sleep 1000 ではなく、shim だった（2つの PPID が同じ）。 shim の umask は、shim を起動した containerd と同じ 0022 である。docker exec のプロセスは shim の子で、umask を shim から受け継ぐのではないか。 containerd の umask を変えて確かめる。containerd は systemd のサービスなので、systemd の設定の追加分（ドロップイン）で UMask= を足し、containerd を再起動する。

@@ sudo mkdir -p /etc/systemd/system/containerd.service.d
@@ printf '[Service]\nUMask=0077\n' | sudo tee /etc/systemd/system/containerd.service.d/umask.conf
@@ sudo systemctl daemon-reload
@@ sudo systemctl restart containerd

containerd を再起動しても、c6 は動いたままか。そのうえで、新しいコンテナ c7 を起動し、3通りの umask を比べる。

@@ docker ps --format '{{.Names}}: {{.Status}}'
@@ docker run -d --name c7 alpine:3.24.2 sleep 1000
@@ docker exec c7 sh -c umask
@@ docker exec c6 sh -c umask
@@ docker run --rm alpine:3.24.2 sh -c umask

3つの答えがそろって説明できる。

プロセスumaskどこから来たか
containerd を再起動した後に起動した c7 への docker exec0077c7 の shim は新しい containerd（0077）から起動し、exec のプロセスはその shim から受け継いだ
再起動の前からある c6 への docker exec0022c6 の shim は古い containerd（0022）から起動したまま生きている（再起動しても c6 は Up のままだった）
docker run の PID 10022runc がコンテナの最初のプロセスに 0022 を明示的に設定する。親の値に左右されない

著者の PC（NixOS の docker 29.8.0）では、containerd が umask 0000 で動いていて、docker exec で取った記録だけが umask 0000 になった （ファイルが誰でも書ける権限で作られる）。原因はコンテナの中ではなく、コンテナの外の containerd の umaskだった。 docker run -it で入る読者の PID 1 のシェルは、runc が決めた 0022 になる（runc を使う docker なら、PC に依らない）。

設定を元に戻し、この章のコンテナを消す。

@@ sudo rm /etc/systemd/system/containerd.service.d/umask.conf
@@ sudo rmdir /etc/systemd/system/containerd.service.d
@@ sudo systemctl daemon-reload
@@ sudo systemctl restart containerd
@@ docker rm -f c6 c7
たとえ: docker run で生まれる PID 1 と、docker exec で足すプロセスは、同じ家に住む、本人と後から来た客に近い。 本人の生活習慣（umask）は家を建てた大工（runc）が決めて置いたが、客は送ってきた付き添い（shim）の習慣をそのまま持ち込む。
ただし崩れる点: 本物の客は家に入れば家の決まりに合わせるが、プロセスは入った名前空間に合わせて umask を変えたりしない。 受け継いだ値のまま、何もしなければ最後までその値で動く。
手を動かす: 実践編の演習02で、docker stop がすぐに終わるコンテナと、 待ち時間を使い切るコンテナを起動し、それぞれの止まり方を確かめる。
確認

docker ps -a の STATUS が Exited (137) だった。このコンテナは、どう終わったと言えるか。Exited (143) ならどうか。

答え

137 = 128 + 9 で、KILL で殺された。docker stop の待ち時間切れか、docker kill・docker rm -f・外からの kill -KILL などである。 143 = 128 + 15 は「TERM で終わった」という報告で、多いのは --init の docker-init が、子が TERM で終わったことをこの値で報告した場合（この章の c5）。プログラムが自分で 143 を選んで終わることもある。 ハンドラを登録した PID 1 が TERM を受けて自分で終わるときは、そのプログラムが決めた終了コード（0 が多い）になるので、TERM で止まったコンテナがいつも 143 になるとは限らない。

確認

あるサーバのコンテナが、docker stop のたびにちょうど10秒かかる。原因として何が考えられ、どう確かめればよいか。

答え

PID 1 が TERM を受け取っていない（受け取り方を登録していない、またはシェルが PID 1 でサーバがその子になっていて TERM が伝わらない）。 docker exec … ps で PID 1 が何かを見る。練習機（ホスト）から grep SigCgt /proc/PID/status でハンドラの登録を見る （0 でも、docker-init のように合図をブロックして待つ作りなら受け取れるので、何が PID 1 かと合わせて判断する）。 直し方は、サーバ自身を PID 1 にする（シェルを挟まない）、--init を付ける、などである。

確認

docker exec で作ったファイルの権限が、docker run -it で作ったものと違った。コンテナの中のどの設定を見ても umask は書かれていない。どこを調べればよいか。

答え

コンテナの外。docker exec のプロセスは shim の子で、umask を shim から受け継ぐ（shim の値は、shim を起動したときの containerd の値）ので、 ホストで grep Umask /proc/$(pgrep -x containerd)/status や shim の値を見る。containerd を起動した仕組み（systemd の UMask= など）が決めている。

この章で分かったこと

持ち帰ってほしいこと

  • コンテナの最初のプロセスは、その名前空間の PID 1 になる。PID 1 は、受け取る準備（ハンドラの登録か、ブロックして待つ）をしていない合図（TERM を含む）を受け取らない。KILL と STOP だけは外から届く
  • docker stop は止める合図（STOPSIGNAL が無ければ TERM）→ 待つ（既定 10秒）→ KILL。--stop-timeout は待ち時間を、--init は合図を中継する init を足す
  • docker exec のプロセスは shim の子で、umask を shim から受け継ぐ。PID 1 の umask は runc が 0022 に決める
  • TERM は -t を付けたときだけ docker が渡す。端末の有無で表示が変わるコマンドがある
