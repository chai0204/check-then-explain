1. コンテナは、練習機の上で動く1つのプロセス

docker run を打つと、小さな計算機が1台立ち上がったように見える。 ところが練習機の ps には、そのコンテナが普通のプロセスとして1行で並んでいる。 カーネルは練習機のもので、コンテナが自分で持っているのは「見え方の区切り」と「使える量の区切り」だけである。

この章のゴールと前提所要 20分
前提: 実践編の入口で練習機に入れた（ssh linuc）所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • コンテナが練習機の上の1つのプロセスであることを、ps と /proc の値で示せる
  • 名前空間と cgroup が、それぞれ何を区切っているかを言える
  • docker コマンドからコンテナのプロセスができるまでの経路（dockerd → containerd → shim → runc）を、動いているプロセスで示せる
ここで覚えなくていいこと: 名前空間の全種類の細部（ipc・time・cgroup 名前空間）、cgroup v1 と v2 の違い、 containerd の内部（スナップショッタやプラグインの構成）、OCI ランタイム仕様の項目の一覧。名前が出てくるだけで先に進める。

Alpine のコンテナを1つ起動する

この節で分かること: コンテナの中で最初に動いているもの（PID 1）と、カーネルの持ち主。

この記事の端末は、すべて練習機の中（プロンプトが student@linuc）で打つ。練習機には docker と、 小さなイメージ2つ（alpine:3.24.2 と busybox:1.38.0）が最初から入っている。

ふつうこう考える

コンテナは小さな仮想マシンだ。docker run alpine は Alpine Linux を起動する。 だから中では Alpine のカーネルが動き、最初に init（PID 1）が起動して、その上で頼んだコマンドが動いているはずだ。

@@ docker run -d --name c1 alpine:3.24.2 sleep 1000
@@ docker exec c1 ps
@@ docker exec c1 uname -r
@@ uname -r
だめな理由: コンテナの中の PID 1 は、頼んだコマンドの sleep 1000 そのものだった。 起動したカーネルも init も無い。uname -r は練習機と同じ 6.8.0-142-generic を返した。 コンテナは自分のカーネルを持たない。練習機のカーネルの上で、sleep というプロセスが1つ動いているだけである。 docker run -d が出した長い16進数は、コンテナに付いた ID（名前とは別の、機械が使う番号）で、起動のたびに変わる（あなたの画面では本文と違う）。

では「Alpine」はどこにあるのか。ファイルである。

@@ docker exec c1 grep PRETTY_NAME /etc/os-release
@@ grep PRETTY_NAME /etc/os-release

コンテナの中から見える /etc/os-release は Alpine のもので、練習機のものは Ubuntu のものである。 コンテナが Alpine なのは見えているファイル（ユーザランド）だけで、そのファイルはイメージから来ている（第3章・第4章）。

たとえ: コンテナは、劇場の舞台の上の役者に近い。役者（プロセス）は本物の人間で、劇場（カーネル）も本物である。 舞台装置（名前空間）のおかげで、役者からは客席が見えず、舞台の上の世界だけが見えている。
ただし崩れる点: 本物の舞台装置は板と布でできているが、名前空間はカーネルが「見せるもの」を絞っているだけで、壁は無い。 劇場の側（練習機）からは、舞台の上の役者がいつでも全部見えている（次の節）。

外から見ると、ただのプロセス

この節で分かること: 同じプロセスが、中と外で別の番号を持っていること。
@@ docker ps
@@ pid=$(docker inspect -f '{{.State.Pid}}' c1)
@@ echo $pid  ## id=pid
@@ ps -o pid,ppid,user,cmd -p $pid  ## id=ps1

docker inspect -f は、コンテナの情報から1つの項目だけを取り出す（{{.State.Pid}} は「練習機から見た PID」）。 その番号で練習機の ps を引くと、sleep 1000 が root のプロセスとして1行で出た。 コンテナの中では PID 1、練習機からは PID {{pid:^(\d+)$}}。同じ1つのプロセスに、番号が2つ付いている。 番号の付け方を分けているのが、次の名前空間である（あなたの画面の PID は本文と違ってよい。以下では変数 $pid で指す）。

見え方の区切り — 名前空間

この節で分かること: 名前空間が何を区切るのかと、区切られていないものがあること。

プロセスがどの名前空間に入っているかは、/proc/PID/ns/ の下のリンクの先の番号で分かる。 $$ は、いま打っているシェル自身の PID である。コンテナのプロセスは root のものなので、読むのに sudo が要る。

@@ readlink /proc/$$/ns/pid /proc/$$/ns/uts /proc/$$/ns/mnt /proc/$$/ns/net /proc/$$/ns/user
@@ sudo readlink /proc/$pid/ns/pid /proc/$pid/ns/uts /proc/$pid/ns/mnt /proc/$pid/ns/net /proc/$pid/ns/user
@@ docker exec c1 hostname
@@ hostname

pid・uts・mnt・net の4つは番号が違う。番号が違えば、別の名前空間にいる。ところが最後の user だけは同じ番号だった。

名前空間区切るものこの章で見えたこと
pidプロセスの番号の付け方中では PID 1、外では別の番号
utsホスト名中のホスト名はコンテナ ID の先頭12文字、外は linuc
mntマウントの一覧（見えるファイル）中の /etc/os-release は Alpine のもの
netNIC・IP アドレス・ポートコンテナは自分の NIC を持つ（第5章）
userユーザ ID の対応区切られていない。中の root（UID 0）は、練習機の root（UID 0）と同じ（第7章）

docker は、ユーザ名前空間を既定では使わない。だからコンテナの中で root のプロセスは、練習機から見ても root である（上の ps の USER 列）。 ここが Podman の rootless との大きな違いになる（Podman 第2章）。

使える量の区切り — cgroup

この節で分かること: cgroup がプロセスをどこにまとめ、どこで量を絞っているか。
@@ cat /proc/$pid/cgroup
@@ docker run -d --name c2 --memory 64m alpine:3.24.2 sleep 1000
@@ docker exec c2 cat /sys/fs/cgroup/memory.max
@@ systemctl show --property=MemoryMax docker-$(docker inspect -f '{{.Id}}' c2).scope
@@ cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' c2).scope/memory.max

cgroup は、プロセスを入れる「かご」と、かごごとに使える量（メモリ・CPU・プロセス数）を決める仕組みである。 /proc/$pid/cgroup は、そのプロセスが入っているかごのパスで、コンテナ1つが system.slice/docker-ID.scope という1つのかごになっている。 --memory 64m を付けて起動した c2 のかごには、上限 67108864（64×1024×1024 バイト）が書き込まれた。

同じ値が2か所から見えた。コンテナの中からは /sys/fs/cgroup/memory.max（かごのいちばん上に見える）、 練習機からは /sys/fs/cgroup/system.slice/docker-…scope/memory.max である。 練習機の systemd も、このかごを docker-….scope という名前の単位として知っている（MemoryMax=）。 この docker は、かごの作成を systemd に頼む設定（cgroup ドライバ systemd）で動いている。

たとえ: cgroup は、部屋ごとのブレーカー（契約アンペア）に近い。どの部屋の電気が建物のどの回路を通るかを決め、部屋ごとに上限を付けられる。
ただし崩れる点: ブレーカーは上限を超えると部屋全体の電気を落とすが、メモリの上限を超えたコンテナでは、カーネルがかごの中のプロセスを選んで止める（OOM killer）。 CPU の上限なら止めずに遅くするだけで、量の種類ごとに超えたときの振る舞いが違う。

docker コマンドは頼むだけ — dockerd → containerd → shim → runc

この節で分かること: docker run を打ってからプロセスができるまでに、誰が何をしているか。

docker コマンド（CLI）は、自分ではコンテナを作らない。ソケットを通して、root で動いている dockerd（docker のデーモン）に頼む。

@@ ls -l /run/docker.sock
@@ id
@@ docker version --format 'client {{.Client.Version}} / server {{.Server.Version}}'

/run/docker.sock は root と docker グループだけが読み書きできるソケットで、student は docker グループに入っているので、sudo なしで dockerd に頼める （それが何を意味するかは第7章）。docker version が版を2つ出したのは、頼む側（client）と頼まれる側（server）が別のプログラムだからである。

頼まれた dockerd も、自分ではプロセスを作らない。練習機の中で、関係するプロセスを並べる。

@@ ps -o pid,ppid,user,comm -C dockerd,containerd,containerd-shim,sleep
@@ runc --version
@@ ps -C runc
@@ sudo runc --root /run/docker/runtime-runc/moby state $(docker inspect -f '{{.Id}}' c1) | jq '{id, pid, status}'

並び方を読むと、役割が分かる。

プログラム役目上の出力で見えたこと
dockerddocker の API を受け付ける。イメージの名前・ネットワーク・ボリュームを管理し、コンテナの実行は containerd に頼むPPID 1（systemd が起動した）
containerdコンテナとイメージの実体を管理する。コンテナ1つごとに shim を起動するPPID 1。dockerd の子ではなく、別のサービス
containerd-shim-runc-v2コンテナ1つに1つ付き添う。中のプロセスの親になり、終了を見届けるコンテナが2つなので2つ。sleep の PPID は shim（ps の名前は15文字で切れて containerd-shim）
runc名前空間と cgroup を設定してプロセスを起動し、すぐに終わる動いている runc は無い（ps -C runc は見出しだけ）。それでも起動したコンテナの状態は覚えている（state）

runc が「コンテナを作る」部分の本体で、その作り方は OCI ランタイム仕様という公開の仕様で決まっている。 同じ仕様を満たす別のプログラム（例えば crun）に差し替えても、同じイメージが動く（Podman は既定で crun を使う。Podman 第1章）。

たとえ: この経路はレストランに近い。docker CLI は客の注文票、dockerd はホールで注文を受ける店員、containerd は厨房の責任者、 shim はテーブルごとに付く給仕、runc は料理を作って皿に盛ったら厨房に戻る料理人である。
ただし崩れる点: 本物の厨房では責任者が抜けると料理が止まるが、containerd を再起動しても、給仕（shim）が付いているコンテナは動き続ける（第2章で実際に再起動する）。 逆に客（CLI）は、店員（dockerd）がいなければ何も頼めない。

最後に、この章で起動した2つを消す。docker rm -f は、動いていれば止めて（KILL を送って）から消す。

@@ docker rm -f c1 c2
@@ docker ps -a
手を動かす: 実践編の演習01で、メモリの上限を付けたコンテナを起動し、 その上限が練習機のどのファイルに書かれたかを自分で探す。
確認

docker exec c1 ps では sleep 1000 が PID 1 で、練習機の ps では同じ sleep 1000 が別の番号の PID だった。 この2つの出力から、コンテナの中のプロセスについて何が言えるか。

答え

同じ1つのプロセスに、中と外で別の番号が付いている。コンテナは pid 名前空間で番号の付け方を分けているだけで、 プロセスそのものは練習機のカーネルの上の1つのプロセスである。外からは全部見えるが、中からは外が見えない。

確認

コンテナの中で uname -r が 6.8.0-142-generic を返した。Alpine 3.24 のイメージに、このカーネルが入っているからか。

答え

違う。イメージにカーネルは入っていない。uname はカーネルに版を尋ねるシステムコールで、答えたのは練習機のカーネルである。 あなたの PC の docker で同じことをすれば、あなたの PC のカーネルの版が出る（Docker Desktop なら、その中の Linux の版）。

確認

名前空間の番号を並べたとき、user だけが練習機と同じだった。このことから、コンテナの中の root について何が予想できるか。

答え

ユーザの対応が区切られていないので、コンテナの中の UID 0 は練習機の UID 0 そのものだと予想できる（ps の USER 列も root だった）。 できることを絞っているのは別の仕組み（ケーパビリティなど）で、それを第7章で測る。

この章で分かったこと

持ち帰ってほしいこと

  • コンテナは練習機のカーネルの上の1つのプロセスである。PID 1 は頼んだコマンドそのもので、カーネルも init も起動しない
  • 名前空間は「見え方」を区切る（pid・uts・mnt・net）。docker は既定ではユーザ（user）を区切らない
  • cgroup は「使える量」を区切る。コンテナ1つが1つのかご（docker-ID.scope）になり、上限はそのかごのファイルに書かれる
  • docker CLI → dockerd → containerd → shim → runc の順に頼み、runc はプロセスを作ったら終わる。プロセスの親として残るのは shim である
