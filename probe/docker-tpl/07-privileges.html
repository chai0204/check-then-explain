7. 渡したものだけが、コンテナの力になる

docker のコンテナの中の root は、練習機の root と同じ UID 0 である。それでも中から何でもできるわけではないのは、 カーネルの特権が細かい単位（ケーパビリティ）に分けられ、そのうち一部だけが渡されているからだ。 --cap-add・--device・--privileged・--user は、どれも「何を渡すか」を変えるオプションで、渡した分は数字で測れる。

前提: 第1章（user の名前空間は区切られていない）・第4章（バインドマウント）所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • コンテナの中の root が練習機の UID 0 であることを、ファイルの持ち主で示せる
  • ケーパビリティの集合（CapEff）を読み、--cap-add・--user で何が増減するかを数字で示し、--privileged が何を何に変えるかを練習機の root と比べて言える
  • --device が渡すものと、それだけでは足りないもの（ファイルの権限）を区別できる
  • この記事の檻の起動コマンドが、なぜこれらを1つも使わないのかと、このサイトの例外の2つが何を渡しているかを説明できる
ここで覚えなくていいこと: ケーパビリティ約40個の全部の意味、seccomp と AppArmor の規則の中身、 ユーザ名前空間を使う docker の設定（userns-remap・rootless docker）。名前と「何を渡すかを変える」という役目だけで先に進める。

コンテナの中の root は、練習機の上で誰か

この節で分かること: コンテナの中の root が書いたファイルの、練習機の上での持ち主。

student の持ち物のディレクトリを1つ作り、コンテナにバインドマウントで見せて、中の root にファイルを1つ作らせる。

ふつうこう考える

コンテナの中の root は、コンテナの中だけの root だ。練習機から見れば、どこかの一般ユーザか、名前の無い誰かにすぎないはずだ。

@@ mkdir ~/share
@@ docker run --rm -v "$HOME/share":/share alpine:3.24.2 sh -c 'id; touch /share/made-by-container'
@@ ls -ln ~/share
だめな理由: コンテナの中の root が作ったファイルは、練習機の上でも持ち主が 0（root）だった。 第1章で見たとおり、docker は既定でユーザの名前空間を区切らないので、中の UID 0 は練習機の UID 0 そのものである。 コンテナの中の root ができることを絞っているのは「別人にすること」ではなく、次の節のケーパビリティと、seccomp・AppArmor という別の仕組みである。

これが、docker グループに入ることの意味にもつながる。student は docker グループに入っているので、sudo なしで root の dockerd に頼める（第1章の /run/docker.sock）。 dockerd は頼まれれば、練習機のどのディレクトリでもバインドマウントでコンテナに見せ、中の UID 0 にそこを触らせる。 docker の公式の文書も「docker グループは root と同等の権限を与える」と書いている。人を docker グループに入れるのは、その人に root を渡すのと同じだと考える。

たとえ: docker グループは、合鍵を作れる鍵屋への紹介状に近い。紹介状そのものは扉を開けないが、持っていれば鍵屋（root の dockerd）が言われたとおりの鍵を作ってくれる。
ただし崩れる点: 本物の鍵屋なら依頼人の身元や用途を確かめるが、dockerd はソケットに書けた依頼を区別しない。 誰の依頼かで断る仕組みは、docker 自身には無い（だから紹介状を渡す相手を絞るしかない）。

中の root に渡されている特権を、数える

この節で分かること: ケーパビリティの集合の読み方と、docker の既定の集合。

Linux は root の特権を、ネットワークの設定（CAP_NET_ADMIN）・ファイルの持ち主の変更（CAP_CHOWN）などのケーパビリティに分けている。 プロセスが今使える集合は、/proc/self/status の CapEff に16進数のビットの並びで出る。

@@ grep CapEff /proc/self/status
@@ sudo grep CapEff /proc/self/status
@@ docker run --rm alpine:3.24.2 grep CapEff /proc/self/status
@@ capsh --decode=00000000a80425fb

一般ユーザの student は 0（何も無い）、練習機の root は 000001ffffffffff（全部）、コンテナの中の root は 00000000a80425fb で、 capsh --decode で読むと14個だった。ファイルの持ち主の変更や、1024番未満のポートで待ち受けること（cap_net_bind_service）はできるが、 ネットワークの設定（cap_net_admin）や、ファイルシステムのマウント（cap_sys_admin）は入っていない。

@@ docker run --rm alpine:3.24.2 ip link add lab0 type dummy
@@ docker run --rm --cap-add NET_ADMIN alpine:3.24.2 sh -c 'grep CapEff /proc/self/status; ip link add lab0 type dummy; ip link show lab0'
@@ capsh --decode=00000000a80435fb

既定では、仮想の NIC を足す操作が Operation not permitted で断られた。--cap-add NET_ADMIN を付けると CapEff のビットが1つ増え （a80425fb → a80435fb）、同じ操作が通った。足した NIC は、そのコンテナの net の名前空間の中だけにある（コンテナが消えると一緒に消える）。 --cap-add は、渡す特権を1つずつ足す。何が増えたかは CapEff の差で確かめられる。

たとえ: ケーパビリティは、ホテルのカードキーに書き込む「入れる場所」の一覧に近い。同じ「宿泊客」（UID 0）でも、 カードに書き込まれた場所（ジム・ラウンジ）にしか入れない。--cap-add は、フロントで1か所ずつ書き足してもらうことである。
ただし崩れる点: ホテルの場所は互いに独立しているが、ケーパビリティには1つで多くを許すもの（CAP_SYS_ADMIN はマウントをはじめ非常に広い）がある。 1つ足すだけでも、どれを足すかで渡すものの大きさがまるで違う。

デバイスを渡す — --device

この節で分かること: --device が渡すものと、それとは別に要るもの。

練習機には、仮想化の装置 /dev/kvm がある（QEMU の完全エミュレーションの中でも、CPU の仮想化支援機能を真似ているため。KVM の記事）。 コンテナに見えるデバイスは、既定ではごく少ない。

@@ docker run --rm alpine:3.24.2 ls /dev
@@ ls -l /dev/kvm
@@ docker run --rm --device /dev/kvm alpine:3.24.2 sh -c 'ls -l /dev/kvm; grep CapEff /proc/self/status'
@@ docker run --rm --device /dev/kvm --user 1000:1000 alpine:3.24.2 sh -c 'id; head -c0 /dev/kvm 2>&1 && echo opened'
@@ docker run --rm --device /dev/kvm --user 1000:1000 --group-add $(stat -c %g /dev/kvm) alpine:3.24.2 sh -c 'id; head -c0 /dev/kvm && echo opened'

--device /dev/kvm を付けると、コンテナの /dev に同じ装置（主番号・副番号 10, 232）ができ、cgroup の「使ってよい装置」の一覧にもこの1つが足される。 渡すのはその装置1つだけで、CapEff は既定のまま（a80425fb）だった。ただし装置のファイルの権限（crw-rw----、持ち主 root・グループ kvm）はそのまま効くので、 --user 1000:1000 で動く一般ユーザは開けなかった（Permission denied。2>&1 は、エラーの行を id の出力と同じ流れに入れて、表示の順が入れ替わらないようにしている）。 練習機の kvm グループの番号（stat -c %g）を --group-add で足すと、開けた。コンテナの中には kvm という名前のグループが無いので、番号のまま見えている。 装置を渡す（--device）ことと、その装置を開ける権限（グループ）は別で、両方そろって初めて使える。

このサイトの KVM の記事は、読者の PC の /dev/kvm をこの2つ（--device /dev/kvm と --group-add）だけで檻に渡す。ほかの特権は渡さない。

全部を渡す — --privileged

この節で分かること: --privileged が、上の2つと比べてどれだけ多くを、何から何へ変えるか。

--privileged は、上の2つのように1つずつではなく、まとめて全部を渡すオプションである。 このサイトの本文は、練習機の中であっても --privileged を打たない（本文の1行が読者の PC でそのまま打たれても、PC の特権を渡さないようにするため）。 代わりに、--privileged が変える4つの項目を、既定のコンテナと練習機の root で並べて測る。 /proc/self/attr/current は、そのプロセスに当たっている AppArmor の規則の名前である。

@@ docker info --format '{{.SecurityOptions}}'
@@ docker run --rm alpine:3.24.2 sh -c 'grep -E "^(CapEff|Seccomp):" /proc/self/status; cat /proc/self/attr/current; ls /dev | wc -l'
@@ sudo sh -c 'grep -E "^(CapEff|Seccomp):" /proc/self/status; cat /proc/self/attr/current; ls /dev | wc -l'

dockerd は既定で、どのコンテナにも AppArmor と seccomp を当てる（name=apparmor・name=seccomp,profile=builtin）。 既定のコンテナは、ケーパビリティが14個（a80425fb）、Seccomp が 2（呼べるシステムコールを一覧で絞られている）、 AppArmor の規則 docker-default が強制（enforce）で当たっていて、/dev の項目は 15 個だった。 練習機の root は、ケーパビリティが全部（000001ffffffffff）、Seccomp が 0（絞られていない）、AppArmor は unconfined（規則なし）で、/dev は 191 個。

docker の文書によれば、--privileged を付けたコンテナは、ケーパビリティが全部になり、既定の seccomp の一覧と AppArmor の規則が外れ、ホスト（ここでは練習機）の装置を全部使えるようになる （ほかに /sys と cgroup のマウントが書き込み可になる）。つまり上の4項目が、既定のコンテナの値から、練習機の root の値へほぼ丸ごと変わる。 名前空間で見え方は分かれていても、練習機の root とほぼ同じ力を渡すオプションで、何を渡したかを1つずつ数えられない。

逆の向きに、渡すものを減らすオプションもある。--user は、コンテナの最初のプロセスを root 以外で起動する。

@@ docker run --rm --user 1000:1000 alpine:3.24.2 sh -c 'id; grep CapEff /proc/self/status'
@@ docker run --rm --user 1000:1000 alpine:3.24.2 sh -c 'cat /proc/sys/net/ipv4/ping_group_range; ping -c1 -q 127.0.0.1 >/dev/null && echo ping-ok'

UID 1000 の一般ユーザとして起動し、CapEff は 0 になった（練習機の student と同じ）。それでも ping は通った（ping-ok）。 docker はコンテナの net.ipv4.ping_group_range を 0 2147483647（全部のグループ）にしていて、どのユーザでも、特権の要らない ping 専用のソケット（ICMP のソケット）が使える。 ping に cap_net_raw は要らない（Podman の記事の第7章で、この値が違う podman と比べる）。

オプションCapEff増えるもの
（なし）00000000a80425fb（14個。実測）—（docker の既定）
--cap-add NET_ADMIN00000000a80435fb（15個。実測）指定したケーパビリティ1つ
--device /dev/kvm変わらない（実測）指定した装置1つ（使うにはファイルの権限も要る）
--privileged000001ffffffffff（全部。練習機の root で測った値。docker の文書では、コンテナがこれと同じになる）全部のケーパビリティ・装置の全部・seccomp と AppArmor の解除
--user 1000:10000000000000000000（実測）減る（root でなくなる）
たとえ: --privileged は、カードキーではなく建物のマスターキーと警備室の鍵を一緒に渡すことに近い。部屋割り（名前空間）はそのままでも、どこへでも入れて、見張りも切れる。
ただし崩れる点: マスターキーは返してもらえば済むが、--privileged のコンテナが練習機の装置やカーネルの設定に加えた変更は、コンテナを消しても練習機に残る。 渡した瞬間から、コンテナの外を変えられる。

このサイトの檻の起動コマンドを読む

この節で分かること: このサイトの実践編の docker run が、何を渡していて、何を渡していないか。

このサイトの起動コマンドは、2つの型がある（オプションごとの意味と、確かめた章は理論編の目次に表にした）。

docker run --rm -it --name lab-… --hostname linuc \
  -v lab-…-work:/home/lab/work -v lab-…-state:/home/lab/.lab \
  ghcr.io/chai0204/lab-linuc:…-1.0.1@sha256:…            # コンテナ型

docker run -d --name lab-… --hostname host --stop-timeout 30 \
  -v lab-…-vm:/home/lab/vm -v lab-…-state:/home/lab/.lab \
  ghcr.io/chai0204/lab:…-1.0.0@sha256:…                  # 仮想マシン型（この記事の檻）

どちらにも --privileged・--cap-add・--device・バインドマウントが無い。この章で測った「渡すもの」が1つも無いということで、 檻の中の root（いれば）は docker の既定の14個のケーパビリティしか持たず、読者の PC のファイルは1つも見えない。 コンテナの中で docker を動かしたり（dockerd は --privileged を要る）、ブートやディスクを触ったりしたい記事が仮想マシン型を選んでいるのは、 仮想マシンなら、中の root が何をしても読者の PC の特権を1つも借りずに済むからである。

ただし、このサイトには例外が2つある。どちらも、渡すものを1つずつ書き、何が増えるかをそのページで測って見せている。

実践編足すもの何のためか
LinuC 1.09（時刻・ログ・メール）--cap-add SYS_ADMIN（CapEff が a80425fb から a82425fb へ、1ビット）檻の中で systemd を PID 1 として動かすため（docker が読むだけでマウントする /sys/fs/cgroup を、書けるようにする）
KVM--device /dev/kvm と --group-add（この章の --device の節と同じ形）読者の PC の KVM を、檻の中の QEMU に使わせるため

この章で作ったディレクトリを片付ける（中のファイルは root の持ち物なので sudo が要る）。

@@ sudo rm -r ~/share
手を動かす: 実践編の演習07で、--privileged を使わずに、仮想の NIC を作れるコンテナを起動する。 判定は、コンテナに渡した特権の一覧と、実際に NIC を作れるかを見る。
確認

あるコンテナの中で grep CapEff /proc/self/status を打つと 000001ffffffffff だった。起動のしかたについて何が言えるか。

答え

全部のケーパビリティを持っているので、--privileged で起動されたか、--cap-add ALL のように全部を足されたと考えられる。 docker の既定なら 00000000a80425fb（14個）で、一般ユーザ（--user）なら 0 になる。

確認

--device /dev/kvm を付けたのに、コンテナの中の一般ユーザが /dev/kvm を開けない。何が足りないか。

答え

装置のファイルの権限。/dev/kvm は root と kvm グループにしか開けない（crw-rw----）ので、ホストの kvm グループの番号を --group-add で足す。 --device が渡すのは「装置そのもの（と cgroup の許可）」で、ファイルの権限は変えない。

確認

チームの人に「sudo を渡したくないので、docker グループに入れておいた」と言われた。何が問題か。

答え

docker グループに入った人は、root で動く dockerd に何でも頼める。dockerd はホストのどのディレクトリでもコンテナに見せ、中の UID 0（ホストの root と同じ）に触らせるので、 実質的に root を渡したのと同じである（docker の公式の文書もそう書いている）。root を渡したくないなら、ユーザごとに分かれた rootless の仕組み（Podman の rootless など）を使う。

この章で分かったこと

持ち帰ってほしいこと

  • docker のコンテナの中の root は、練習機（ホスト）の UID 0 である。できることを絞っているのはケーパビリティ・seccomp・AppArmor
  • 既定のケーパビリティは14個（CapEff=00000000a80425fb）。--cap-add は1つずつ足し、--privileged は全部と装置と制限の解除を渡し（練習機の root の値になる）、--user は root でなくする
  • --device は装置1つと cgroup の許可を渡すだけで、開ける権限（グループ）は別に要る
  • docker グループに入れることは、root を渡すことと同じ。この記事の檻は、ここで測った「渡すもの」を1つも使わない（このサイトの例外は、--cap-add SYS_ADMIN の LinuC 1.09 と、--device /dev/kvm の KVM の2つ）
