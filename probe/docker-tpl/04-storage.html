4. コンテナの書き込みは、イメージの上の1枚に入る

コンテナの中でファイルを消しても、同じイメージから起動した次のコンテナには、そのファイルがある。 コンテナのファイルの木は、読むだけのイメージの層の上に、コンテナ専用の書き込み用の層を1枚重ねたもの（overlay）で、 消したことも「消した印」として上の1枚に書かれるだけである。上の1枚はコンテナと一緒に消えるので、残したいデータはコンテナの外（ボリューム）に置く。

前提: 第3章（イメージは層でできている）所要 27分影響度 B最終検証 2026-10-14

この章のゴール

  • コンテナの変更が overlay の upperdir に書かれ、イメージの層（lowerdir）は変わらないことを示せる
  • ファイルを消すと upperdir に「消した印」（whiteout）が残ることを、練習機の上のファイルで示せる
  • 名前付きボリュームとバインドマウントの違い（最初の中身・持ち主・置き場所）を、出力で説明できる
ここで覚えなくていいこと: overlay の workdir の役目の細部、opaque ディレクトリ、ストレージドライバの種類（overlay2・btrfs・zfs など）の違い、 ボリュームのドライバ（NFS など）、docker commit。

コンテナの中で消したファイル

この節で分かること: コンテナの中の変更が、イメージに届かないこと。

ふつうこう考える

コンテナはイメージから作った。だからコンテナの中で /etc/motd を消せば、元のイメージからも消える。 同じイメージから次に起動するコンテナにも、もう /etc/motd は無いはずだ。

@@ docker run -d --name w1 alpine:3.24.2 sleep 1000
@@ docker exec w1 rm /etc/motd
@@ docker exec w1 sh -c 'echo hello > /root/note.txt'
@@ docker diff w1 | sort -k2
@@ docker run --rm alpine:3.24.2 cat /etc/motd
だめな理由: docker diff は、w1 がイメージから変わったところを、足した（A）・変えた（C）・消した（D）で並べた（行の順は毎回同じとは限らないので、sort -k2 で2列目のパスの順に並べ替えている）。 ところが同じイメージから起動した新しいコンテナには、/etc/motd がそのまま残っていた。 コンテナの変更はイメージには書かれない。イメージの層は読むだけで、コンテナごとに、変更を受け止める書き込み用の層が1枚ずつ上に重ねてある。

重ね方を、練習機の上で見る

この節で分かること: 読むだけの層（lowerdir）と書き込み用の層（upperdir）が、練習機のどこにあるか。

コンテナのファイルの木は、Linux の overlay ファイルシステムでマウントされている。コンテナのプロセスから見た / のマウントを、findmnt -N（そのプロセスのマウントの名前空間で見る）で読む。-o FSTYPE はファイルシステムの種類、-o OPTIONS はマウントの指定で、指定は , 区切りの長い1行なので tr で1項目1行に直している。

@@ pid=$(docker inspect -f '{{.State.Pid}}' w1)
@@ sudo findmnt -N $pid -n -o FSTYPE /
@@ sudo findmnt -N $pid -n -o OPTIONS / | tr ',' '\n' | grep dir=

overlay は、下の層（lowerdir。: で区切って上から順に複数）の上に、上の層（upperdir）を1枚重ねて、1つの木に見せる。 下の層は読むだけで、書き込みは全部、上の層に入る（workdir は overlay が作業に使う場所）。 この docker では、層の実体は containerd の置き場所（/var/lib/containerd/…overlayfs/snapshots/番号/fs）にある。 下の層は2枚で、いちばん下が Alpine の層、その上の1枚は docker が足した小さな層（/etc/hosts などの差し込み口）である。

@@ up=$(sudo findmnt -N $pid -n -o OPTIONS / | tr ',' '\n' | sed -n 's/^upperdir=//p')
@@ low=$(sudo findmnt -N $pid -n -o OPTIONS / | tr ',' '\n' | sed -n 's/^lowerdir=//p' | tr ':' '\n' | tail -1)
@@ sudo ls -lR $up
@@ sudo ls -l $low/etc/motd

上の層には、/root/note.txt（足したファイル）があり、/etc/motd は種類が c（文字デバイス）で番号が 0, 0 の特別なファイルになっていた。 これが overlay の消した印（whiteout）で、「下の層の同じ名前のものを見せない」という意味である。下の層（Alpine の層）の /etc/motd は、そのまま残っている。 ファイルを書き換えたときも同じで、下の層のファイルを上の層に写してから書き換える（copy-up）。下の層には一切書かない。

たとえ: overlay は、印刷した地図の上に重ねた透明なシートに近い。書き込みはシートの上にだけして、地図（イメージの層）は汚さない。 地名を消したいときは、シートの上にその場所を塗りつぶす紙を貼る（whiteout）。シートを剥がせば、地図は元のままである。
ただし崩れる点: 透明シートなら下の地図が透けて見えるが、overlay で上の層に写したファイルは、下の同じファイルを完全に隠す（透けて混ざることはない）。 また、何枚も重ねたシートでも、見るときにはファイル1つごとに「いちばん上にあるもの」だけが選ばれる。

コンテナを消すと、上の層ごと消える。

たとえ: コンテナの書き込み用の層は、ホテルの部屋に置かれたメモ帳に近い。泊まっている間は好きに書けるが、チェックアウトする（コンテナを消す）と部屋ごと片付けられる。 次の客（同じイメージから作った別のコンテナ）は、まっさらなメモ帳から始める。
ただし崩れる点: ホテルなら一時的に外出しても（止めても）部屋は片付けられないのと同じく、docker stop では上の層は消えない。消えるのは docker rm したときで、止めただけなら docker start で書いたものが戻ってくる。
@@ docker rm -f w1
@@ sudo ls $up

残したいものは、外に置く — ボリューム

この節で分かること: 名前付きボリュームが、練習機のどこにあり、コンテナと別に生き残ること。

上の層はコンテナと一緒に消えるので、データベースのファイルのように残したいものは、コンテナの外の場所をマウントして、そこに書く。 docker が管理する場所を名前で呼ぶのが名前付きボリュームである。

@@ docker volume create notes
@@ docker run --rm -v notes:/data alpine:3.24.2 sh -c 'echo kept > /data/note.txt'
@@ docker run --rm -v notes:/data alpine:3.24.2 cat /data/note.txt
@@ docker volume inspect --format '{{.Mountpoint}}' notes
@@ sudo cat /var/lib/docker/volumes/notes/_data/note.txt

--rm を付けたので、書いたコンテナは終わると同時に消えた。それでも次のコンテナから読めた。 ボリュームの実体は練習機の /var/lib/docker/volumes/notes/_data というただのディレクトリで、コンテナはそこを /data にマウントして使っていただけである。

名前付きボリュームとバインドマウントは、最初の中身が違う

この節で分かること: -v 名前:パス と -v /パス:パス の違いと、このサイトの檻が名前付きボリュームを使う理由。

-v の左側が名前なら名前付きボリューム、/ から始まるパスなら、練習機（ホスト）のそのディレクトリをそのまま見せるバインドマウントになる。 中身がすでにあるディレクトリ（/etc/apk）に、両方をかぶせてみる。

@@ docker run --rm alpine:3.24.2 ls /etc/apk
@@ docker run --rm -v apkvol:/etc/apk alpine:3.24.2 ls /etc/apk
@@ docker run --rm -v "$HOME/apkdir":/etc/apk alpine:3.24.2 ls /etc/apk
@@ ls -ld ~/apkdir
@@ docker run --rm --mount type=bind,source="$HOME/nodir",target=/etc/apk alpine:3.24.2 ls /etc/apk
書き方マウントした直後の中身練習機の側
-v apkvol:/etc/apk（名前付きボリューム）イメージの /etc/apk の中身（コンテナを作るときにボリュームが空なら、イメージの中身が写される）/var/lib/docker/volumes/apkvol/_data（docker が管理）
-v "$HOME/apkdir":/etc/apk（バインドマウント）空。イメージの中身は隠れて見えない無かったディレクトリを docker が root の持ち物として作った
--mount type=bind,source=…（バインドマウント）—無いパスは作らずに止まる（bind source path does not exist）

名前付きボリュームに写されるのは、中身だけでなく、マウント先のディレクトリ自体の持ち主と権限もである。中身の無いディレクトリでも、持ち主と権限は写る。 alpine の /tmp（中身は空で、誰でも書ける drwxrwxrwt）で比べる。

@@ docker run --rm -v tmpvol:/tmp alpine:3.24.2 ls -ld /tmp
@@ docker run --rm -v "$HOME/tmpdir":/tmp alpine:3.24.2 ls -ld /tmp

名前付きボリュームの /tmp は、中身が空でもイメージと同じ drwxrwxrwt になった。バインドマウントの ~/tmpdir は、docker が作ったときの drwxr-xr-x の root の持ち物のままで、イメージの権限は写らない。

写すかどうかは、コンテナを作るときにボリュームが空かどうかだけで決まる。新しいかどうか、何回目かは見ない。apkvol を空にしてから、もう一度使う。

@@ sudo find /var/lib/docker/volumes/apkvol/_data -mindepth 1 -delete
@@ sudo ls -A /var/lib/docker/volumes/apkvol/_data | wc -l
@@ docker run --rm -v apkvol:/etc/apk alpine:3.24.2 ls /etc/apk

中身を 0 個にした apkvol に、また /etc/apk の中身が写った。逆に、何か1つでも入っていれば写さない（次のたとえの「崩れる点」）。

このサイトの仮想マシン型の檻の起動コマンドは -v lab-…-vm:/home/lab/vm と、名前付きボリュームを使っている。 イメージの中で /home/lab/vm は lab の持ち物の空のディレクトリとして作ってあるので、空のボリュームにはその持ち主と権限が写され、檻の中の lab が書ける。 バインドマウントにすると、持ち主は読者の PC のディレクトリのものになり、中の lab が書けないことがある（そして読者の PC のファイルを檻に直接見せることになる）。 名前付きボリュームは、イメージが用意した形を引き継ぎ、読者の PC のディレクトリに触れないので、このサイトは名前付きボリュームだけを使っている。

たとえ: 名前付きボリュームは倉庫会社に預けた箱、バインドマウントは自宅の物置の扉をそのまま窓口にすることに近い。 空の箱を使うとき、倉庫会社は棚にあった見本（イメージの中身）を箱に詰め、箱の名札（持ち主と権限）も棚に合わせて渡してくれる。自宅の物置をつなげば、中は物置にあるものだけで、棚の見本は扉の向こうに隠れる。
ただし崩れる点: 倉庫会社は、箱が空かどうかだけを見る。空ならいつでも詰め直すが、1つでも何か入っていれば何もしない。 だからイメージを新しくしても、空でない箱の中身は古いままになる（このサイトの檻で、新しい版のイメージに替えても進捗や練習機のディスクが残るのはこのため）。

この章で作ったボリュームとディレクトリを片付ける（~/apkdir と ~/tmpdir は docker が root の持ち物として作ったので、消すのに sudo が要る）。

@@ docker volume rm notes apkvol tmpvol
@@ sudo rmdir ~/apkdir ~/tmpdir
手を動かす: 実践編の演習04で、コンテナを消しても残るデータを名前付きボリュームに置き、残っていることを練習機の上のファイルで確かめる。
確認

upperdir を ls -l すると、c--------- … 0, 0 … motd という行があった。これは何を意味するか。

答え

overlay の「消した印」（whiteout）である。コンテナの中で /etc/motd が消されたので、下の層の /etc/motd を見せないための印が上の層に置かれた。 下の層（イメージ）の /etc/motd は消えていない。

確認

docker run -v "$HOME/conf":/etc/myapp … で起動したら、イメージに入っていたはずの設定ファイルが見えず、アプリが起動しなかった。何が起きたか。

答え

バインドマウントは、ホストのディレクトリをそのままかぶせる。~/conf が空（または無くて docker が空で作った）なので、イメージの /etc/myapp の中身は隠れた。 名前付きボリュームなら、コンテナを作るときに空であればイメージの中身が写されるが、バインドマウントでは写されない。

確認

イメージを新しい版に替えて同じ名前付きボリュームで起動したら、ボリュームの中のファイルが古い版のままだった。なぜか。

答え

イメージの中身がボリュームに写されるのは、コンテナを作るときにボリュームが空だった場合だけだから。前の版の中身が入っているボリュームには、新しい版の中身は写されず、前回のものがそのまま見える。 入れ替えたいなら、ボリュームを消して作り直す（か空にする）か、中身を自分で更新する。

この章で分かったこと

持ち帰ってほしいこと

  • コンテナのファイルの木は overlay で、読むだけのイメージの層（lowerdir）の上に、コンテナ専用の書き込み用の層（upperdir）が1枚重なっている
  • 変更は全部 upperdir に入り、消したファイルは whiteout（0, 0 の文字デバイス）になる。イメージの層は変わらない
  • upperdir はコンテナと一緒に消える。残したいものはボリュームに置く。名前付きボリュームの実体は /var/lib/docker/volumes/名前/_data
  • 名前付きボリュームは、コンテナを作るときに空なら、イメージの中身とマウント先のディレクトリの持ち主・権限が写される（何か入っていれば写さない）。バインドマウントはホストのディレクトリをそのままかぶせ、無ければ -v は root の持ち物で作り、--mount は止まる
