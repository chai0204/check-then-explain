3. QEMU は、頼まれたときだけ KVM を使う

/dev/kvm を開ける檻で、何も付けずに QEMU を起動すると、練習機は TCG で動く（起動し終わるまで 秒）。 QEMU が /dev/kvm を開くのは、-accel kvm（古い書き方は -enable-kvm）と頼まれたときだけである。 そのとき QEMU のプロセスは、カーネルの中に作ってもらった仮想マシンと仮想の CPU を、ファイルとして持っている。

この章のゴールと前提所要 20分
前提: 第2章まで読了（この檻で /dev/kvm を開ける）所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • QEMU の既定のアクセラレータが TCG であることを、/dev/kvm を開ける檻で示せる
  • -accel kvm・-enable-kvm で起動した QEMU が、/dev/kvm と kvm-vm・kvm-vcpu を開いていることを /proc で示せる
  • 既定の CPU で出る svm の警告と、-cpu host が KVM のときだけ使える理由を説明できる
ここで覚えなくていいこと: KVM に頼むときの命令（ioctl）の名前と引数、QEMU の他のアクセラレータ（macOS の HVF・Windows の WHPX・Xen）、 libvirt が組み立てるコマンド行（第6章と QEMU の記事の第7章）、TCG が命令を翻訳する仕組みの中身（QEMU の記事の第4章）。

何も言わなければ、TCG

この節で分かること: /dev/kvm があることと、QEMU が KVM を使うことの関係。

この檻では、lab が /dev/kvm を読み書きで開ける（第2章）。QEMU が KVM を使えるものはそろっている。

ふつうこう考える

KVM が使えるなら、QEMU は使う。わざわざ遅い方式を選ぶ理由は無いので、/dev/kvm を開ける檻で起動すれば、何も指定しなくても KVM で速く動くはずだ。

だめな理由: 速くならなかった。QEMU のプロセスが開いているファイルに、KVM のものが1つも無い（grep が何も出さない）。練習機自身も qemu（TCG）と答えた。 この檻の qemu-system-x86_64 は、アクセラレータを指定されなければ TCG を使う。/dev/kvm があっても、それを開くかどうかは QEMU に渡すオプションで決まり、 TCG で動けるかぎり、QEMU が自分で KVM に乗り換えることはしない（名前が kvm で終わる作りの QEMU、たとえば qemu-kvm は、反対に KVM を先に試す）。

readlink /proc/PID/fd/* は、プロセスが開いているファイル（ファイル記述子）がそれぞれ何を指しているかを出す。$(pgrep qemu) は QEMU のプロセスの番号に置き換わる。 この QEMU に組み込まれているアクセラレータは、QEMU 自身に尋ねられる（組み込まれていても、/dev/kvm を開けなければ kvm は使えない。--device なしの檻でも同じ2行が出る）。

たとえ: アクセラレータの指定は、タクシーに「高速道路を使って」と言うことに近い。高速道路（KVM）がすぐそこにあっても、言わなければ下の道（TCG）を走る。
ただし崩れる点: 運転手は気を利かせて高速道路を勧めてくることがあるが、QEMU は何も勧めない。黙って下の道を走り、着くのが遅くても理由を言わない。

KVM の仮想マシンは、カーネルの中にある

この節で分かること: KVM で動くとき、QEMU とカーネルがそれぞれ何を持っているか。

同じ練習機を、-accel kvm を付けて起動し直す。

秒数はあなたの PC で変わる。kvm-vcpu-stats の行は、仮想の CPU ごとの統計を読むためのもので、Linux 5.14 より古いカーネルの PC では出ない。 AMD の PC では、kvm_amd の nested が 1（既定）なら svm の警告は出ない（0 なら Intel と同じ警告が出る。理由は第5章）。

QEMU は /dev/kvm を開いて、カーネルに「仮想マシンを1つ作って」と頼んだ。カーネルは KVM の中に仮想マシンを作り、それをファイル記述子として QEMU に返す。 それが anon_inode:kvm-vm である（anon_inode は、ディスクの上に名前を持たないファイルという意味）。続けて「仮想の CPU を作って」と2回頼み、kvm-vcpu:0 と kvm-vcpu:1 を受け取った。 QEMU の中では、仮想の CPU ごとのスレッドが、自分の kvm-vcpu に「実行して」と頼み続ける。すると本物の CPU が、仮想化支援機能を使って練習機の命令をそのまま実行する。 練習機が装置に読み書きしようとしたときなど、本物の CPU だけでは済まない場面になると、CPU は KVM に戻り、KVM は必要なら QEMU に「この装置の処理をして」と渡す。 ディスクやネットワークの装置は、KVM で動くときも QEMU がソフトで真似している（割り込みの装置など一部は、KVM がカーネルの中で受け持つ）。

たとえ: KVM で動く QEMU は、劇場の舞台監督に近い。役者（練習機の命令）は舞台（本物の CPU）で自分で演じ、監督は袖で待っていて、小道具（装置）が要る場面になると呼ばれて手渡す。 TCG の QEMU は、役者の台詞を1つずつ自分で読み上げる朗読者である。
ただし崩れる点: 舞台監督は劇場を持っていないが、KVM で動く QEMU は劇場（カーネルの中の仮想マシン）をファイルとして手に持っている。QEMU のプロセスが終われば、ファイルが閉じられ、劇場ごと消える。

svm の警告は、第1章の答えの続きである。何も指定しないときの CPU（qemu64）は AMD-V（svm）を持つと名乗る型だった。 TCG なら QEMU がソフトで真似できたが、KVM では練習機の命令を本物の CPU が実行するので、本物の CPU が持っていない機能は練習機に渡せない。 Intel の CPU に svm は無いので、QEMU は「その印は付けられない」と警告し、印を外して起動した（仮想の CPU が2個なので2行出る）。中から見て何が変わったかは、第5章で見る。

-enable-kvm は、同じ頼み方の古い書き方

この節で分かること: KVM を頼む書き方の違いと、KVM が無いと使えないオプション。

-enable-kvm でも、QEMU は同じように /dev/kvm を開き、仮想マシンと仮想の CPU を受け取った。古い資料や設定には、-enable-kvm や -machine accel=kvm と書かれていることがある。 意味は -accel kvm と同じで、いまの QEMU の書き方は -accel である。

反対に、KVM でなければ使えないオプションがある。-cpu host は「この PC の本物の CPU を、そのまま練習機に見せる」という指定で、TCG では断られる。

TCG では、練習機の命令を実行しているのは QEMU のソフトで、そもそも「そのまま見せる」本物の CPU がいない。HVF は macOS の、KVM と同じ役目の仕組みである。 -cpu host で練習機の中がどう見えるかは、第5章で確かめる。

書き方意味QEMU が開くもの
（何も書かない）TCG（この QEMU の場合）KVM のものは何も開かない
-accel tcgTCG（命令を翻訳して実行）同上
-accel kvmKVM（本物の CPU に直接実行させる）/dev/kvm・kvm-vm・kvm-vcpu:N
-enable-kvm / -machine accel=kvm-accel kvm の古い書き方同上
-machine accel=kvm:tcg / -accel kvm -accel tcgKVM を試し、/dev/kvm を開けなければ TCG（起動のときに falling back to tcg と警告する）開ければ KVM のときと同じ。開けなければ何も開かない

最後の行は、本文の記録ではなく、演習の判定を確かめたときの記録で確かめた（/dev/kvm を開ける檻では KVM を使い、--device なしの檻では警告を出して TCG で起動した）。 -accel kvm:tcg とは書けない（invalid accelerator kvm:tcg で起動しない）。

たとえ: -cpu host は、本人の身分証をそのまま見せることに近い。KVM なら練習機の命令は本人（本物の CPU）が実行しているので、本人の身分証を出せる。 TCG で頼むのは、代読している朗読者に「作者本人の身分証を出して」と言うようなもので、持っていない。
ただし崩れる点: 身分証は本人がそのまま出すものだが、-cpu host でも KVM は本物の CPU の機能のうち、自分が練習機に渡せるものだけを見せる。まったくの素通しではない（第5章で、自分で印を消すこともする）。
手を動かす: 実践編の演習03で、同じ練習機を KVM で起動し直す。判定は、QEMU のプロセスが anon_inode:kvm-vm を開いているかを見る（練習機の答えも表示するが、名乗りは消せるので合否には使わない。第5章）。 何も付けずに起動しても合格しない。
確認

同僚が「/dev/kvm はあるのに、QEMU の仮想マシンが遅い」と言っている。QEMU のプロセスの番号は 4242 だった。KVM を使っているかどうかを、どう確かめるか。

答え

readlink /proc/4242/fd/* | grep kvm で、anon_inode:kvm-vm があるかを見る。無ければ TCG で動いている。 理由は、アクセラレータを指定していない、TCG をはっきり指定している（-accel tcg。libvirt なら <domain type='qemu'>。第6章）、 「KVM が駄目なら TCG」と頼んでいて（-machine accel=kvm:tcg や -accel kvm -accel tcg）、/dev/kvm を開けずに TCG に切り替わった（起動のときに falling back to tcg と出る）、のどれかである。 仮想マシンの中の systemd-detect-virt の答えは、決め手にならない。もとになる名前は QEMU が CPUID に書く名乗りで、KVM で動いていても消せる（第5章）。外の /proc/PID/fd を見る。

確認

Intel の CPU の PC で、-accel kvm を付けて QEMU を起動すると warning: host doesn't support requested feature: CPUID.80000001H:ECX.svm [bit 2] が出た。何が起きているか。

答え

CPU の型を指定していないので、QEMU は既定の型（qemu64）を使い、それは AMD-V（svm）を持つと名乗る。KVM では本物の CPU が持っていない機能は練習機に渡せないので、 QEMU が svm を外して起動した、という知らせである。起動は続く。

確認

qemu-system-x86_64 -accel tcg -cpu host … が CPU model 'host' requires KVM or HVF で起動しなかった。なぜ TCG では host を使えないのか。

答え

host は「練習機の命令を実行している本物の CPU を、そのまま見せる」型で、TCG では命令を実行しているのが QEMU のソフトだから、見せる本物の CPU がいない。 KVM（Linux）や HVF（macOS）のように本物の CPU に直接実行させる方式でだけ使える。

  • KVM では本物の CPU が命令を実行するので、本物が持たない機能は渡せない（svm の警告）。-cpu host は KVM のときだけ使える
