4. 速くなるのは、CPU が命令を実行する部分だけ

同じ練習機（同じディスク）を TCG と KVM で起動すると、起動し終わるまで 秒と 秒だった。ところが段階ごとに分けると、 OS が起動していく部分（ユーザ空間）は 倍速いのに、カーネルの最初の表示まで（おおむねファームウェアと GRUB）は 倍にしかならない。 GRUB がメニューを出して待つ 3 秒は、何で動かしても 3 秒である。KVM が速くするのは、CPU が命令を実行している時間だけだ。

前提: 第3章まで読了所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • 外（qemu-linuc の時間・ps）と中（systemd-analyze・journal）の両方で、起動の時間を段階に分けて測れる
  • 段階ごとに速くなる割合が違うことを、自分の測った数字で示せる
  • KVM が速くするもの（CPU が命令を実行する時間）と、速くしないもの（待ち時間・QEMU が真似している装置）を言える
ここで覚えなくていいこと: ベンチマークの取り方（何回測って平均するか、ばらつきの扱い）、仮想マシンが KVM に戻る回数や理由の数え方（perf kvm stat など）、 メモリのアドレスの変換を CPU に任せる仕組み（Intel の EPT・AMD の NPT）の細部、ディスクやネットワークの速さの比べ方。

同じディスクを、2通りで起動して測る

この節で分かること: 起動の時間を、外と中からどう区切って測るか。

第3章の終わりで練習機は止まっている。まず TCG で起動し、起動し終わったところで、中から OS の記録を、外から QEMU のプロセスを見る。

qemu-linuc は2つの時間を出す。練習機が起動し終わるまで（練習機の systemd が「起動し終わった」と答えるまで）と、練習機のシリアルの画面にカーネルの最初の行（Linux version …）が出るまでである。 最初の行より前は、おおむねファームウェア（UEFI）と GRUB の時間である（最初の行は、カーネルが動き出してシリアルの画面を使えるようになってから出るので、動き出した瞬間より少し後になる）。 systemd-analyze は練習機の OS 自身の記録で、カーネルが動き出してから systemd に渡すまで（kernel。initramfs の仕事も入る）と、systemd が起動し終わるまで（userspace）に分けて出す。 ps の ELAPSED はプロセスが起動してからの秒数、TIME はそのあいだに使った CPU の時間（秒）で、起動し終わった直後に測っている。

止めて、同じディスクを KVM で起動し、同じものを見る。

ここの時間は、どれもあなたの PC で変わる（CPU の速さ、ほかに動いているもの）。比べるのは、同じ PC の TCG と KVM の間だけにしてほしい。

ふつうこう考える

起動し終わるまでが 秒から 秒になった。KVM で約 倍速くなったということで、練習機の中のどの部分も、だいたい同じ割合で速くなっているはずだ。

測ったもの（著者の PC）TCGKVMKVM で
QEMU を起動してから、カーネルの最初の表示まで（おおむねファームウェアと GRUB） 秒 秒 倍
カーネル（systemd-analyze の kernel。initramfs も入る） 秒 秒 倍
ユーザ空間（systemd-analyze の userspace） 秒 秒 倍
QEMU を起動してから、起動し終わるまで（qemu-linuc） 秒 秒 倍
起動し終わった直後までに QEMU が使った CPU の時間（ps の TIME） 秒 秒 倍
だめな理由: 段階によって、 倍から 倍までばらばらだった。ユーザ空間（たくさんのプログラムが起動していく部分）は CPU が命令を実行し続ける時間なので、 本物の CPU に直接実行させる KVM でいちばん速くなる。カーネルの最初の表示までには、待っている時間が入っている（GRUB の待ちの 3 秒。KVM では 秒のうちの 3 秒、TCG でも 秒のうちの 3 秒）。 GRUB はメニューを出して、決まった秒数だけキーが押されるのを待つ。待ち時間は、命令をどれだけ速く実行しても縮まない。 全体の 倍は、よく縮む部分と縮まない部分を足したもので、どの部分の速さも表していない。

表の上の3行を足すと、ほぼ4行目になる（ずれは、カーネルの最初の行が少し遅れて出ることと、起動し終わったかを確かめる時間の分）。

GRUB が何秒待つかは、練習機の中の設定にある。

Ubuntu のクラウドイメージは待たない設定（0）だが、このサイトの練習機は GRUB のメニューを見せるために 3 秒にしてある（LinuC 1.01 の記事で、メニューからカーネルに引数を渡す練習をするため）。 KVM の 秒のうち 3 秒はこの待ち時間で、残りの約 秒がファームウェアと GRUB の仕事（とカーネルの最初の一歩）である。TCG では、その仕事に約 秒かかっていた（ 秒のうちの 3 秒が待ち時間）。

たとえ: 起動は、引っ越しの一日に近い。荷物を運ぶ（命令を実行する）作業は、人手を増やせば（KVM）何倍も速くなる。 でも、鍵の受け渡しの約束の時刻（GRUB の待ち時間）は、人手を増やしても早まらない。一日の長さが何倍縮んだかは、作業と待ちの割合で決まる。
ただし崩れる点: 引っ越しの人手は増やした分だけ費用がかかるが、KVM は費用が増えるどころか、使う CPU の時間がかえって減る（ 秒から 秒）。TCG は命令を翻訳する手間に CPU を使っていた。

TCG は、翻訳に CPU を使う

この節で分かること: 速さの差が、CPU の使い方の差でもあること。

TCG の QEMU は、経過 秒のあいだに CPU を 秒使った。経過時間より長いのは、CPU を2個（-smp 2）持つ練習機の命令を、QEMU が2本のスレッドで同時に翻訳して実行しているからである。 練習機のカーネルが「仕事が無い」と CPU を休ませる命令（HLT）を出している間は、QEMU のスレッドも休む。だから TCG の 秒は、練習機の命令を翻訳して実行するために使った時間である（装置を真似する QEMU の仕事も入っている）。

KVM の QEMU は経過 秒・CPU 秒だった。本物の CPU が練習機の命令をそのまま実行した時間も、QEMU のスレッドの CPU の時間として数えられるので、0 にはならない（CPU が2個あるので、経過時間より長くもなりうる）。 それでも、命令を翻訳する手間が無いぶん、同じ起動に使った CPU の時間は TCG のほうが 倍多かった（どちらも起動し終わった直後に測った。測るまでの数秒の待ちも入るので、倍率はおおよそである）。

たとえ: TCG は、外国語の本を声に出して訳しながら読むことに近い。読むのにも訳すのにも頭を使い、2冊を2人で同時に訳せば、その分の手間がかかる。 KVM は、その言葉が分かる人がそのまま黙読する。
ただし崩れる点: 黙読は本の中身によらず速いが、KVM でも練習機が装置に触る場面（ディスクを読む、ネットワークに送る）は、本物の CPU から KVM と QEMU に戻って、QEMU がソフトで装置を真似する。 そこは黙読にならず、TCG のときと同じ QEMU の仕事が残る。

同じディスクに、すべての起動の記録が残っている

この節で分かること: 練習機の OS 自身が、どの起動をどのアクセラレータで迎えたかを記録していること。

練習機の中のログ（journal）には、起動のたびに systemd が書いた2行が残っている。どの仮想化の上で起動したか（Detected virtualization）と、起動にかかった時間（Startup finished）である。 第1章から、同じディスクを何度も起動してきた。

同じディスク・同じ OS で、起動にかかった時間が TCG の3回はどれも 20 秒台、KVM の3回はどれも数秒だった。同じ方式どうしのばらつき（ほかに動いているものの影響）より、アクセラレータの違いのほうがずっと大きい。 練習機の中の OS は、自分が何の上で起動したかを毎回自分で調べて書いている（どう調べているかは第5章）。

たとえ: この journal は、同じ車の運転日誌に近い。日によって道（TCG か KVM か）が違い、日誌には「今日はどの道を通ったか」と「何分かかったか」が並んでいる。
ただし崩れる点: 運転日誌は運転手が書くが、この記録は車自身（練習機の systemd）が、道を自分で調べて書いている。運転手（あなた）が何を頼んだかは、日誌には書かれない。
手を動かす: 実践編の演習03の判定は、この journal から、いまの起動と、それより前に練習機が qemu と記録した最後の起動を探し、2つの Startup finished を並べて出す（いま KVM で動いているかは、QEMU のプロセスのファイルで決める）。 あなたの PC での倍率は、それを見て計算できる。
確認

ある人が「KVM にしたら仮想マシンの起動が 3 倍速くなった。だから CPU を使う処理も 3 倍速くなる」と言った。この推論のどこがおかしいか。

答え

起動の時間には、CPU が命令を実行する時間と、待ち時間（GRUB のメニュー、ネットワークの応答など）が混ざっている。待ち時間は KVM でも縮まないので、全体の倍率は 命令を実行する部分の倍率より小さく出る。著者の PC では、全体が 倍でも、CPU が働き続けるユーザ空間は 倍だった。CPU を使う処理の倍率は、起動の時間からは言えない。

確認

TCG の QEMU で、ps -o etimes,times が と を出した。経過時間より CPU の時間が長いのはなぜか。

答え

練習機に CPU が2個あり、QEMU が2本のスレッドで同時に命令を翻訳・実行していたから。CPU の時間は、使ったスレッドの分を足し合わせて数える。

確認

KVM の練習機で、カーネルの最初の表示までにかかった 秒のうち、3 秒はどの設定から来ているか。それを 0 にすると、TCG と KVM のどちらの起動がより大きな割合で縮むか。

答え

/etc/default/grub.d/99-lab.cfg の GRUB_TIMEOUT=3（GRUB のメニューで待つ秒数）。0 にすると、どちらも同じ 3 秒だけ縮むが、全体が短い KVM のほうが割合では大きく縮む（ 秒 → 約 秒と、 秒 → 約 秒）。

この章で分かったこと

持ち帰ってほしいこと

  • 起動の時間は、外（起動し終わるまで・カーネルの最初の表示まで・ps）と中（systemd-analyze）で段階に分けて測れる
  • KVM で縮むのは CPU が命令を実行する時間。ユーザ空間は 倍、カーネルの最初の表示までは 倍（GRUB の 3 秒の待ちは縮まない）
  • TCG は命令の翻訳に CPU を使う。同じ起動で、QEMU が使った CPU の時間は 秒と 秒
  • 装置（ディスク・ネットワーク）は KVM でも QEMU がソフトで真似している。全体の倍率は、どの部分の速さも表さない
