理論編 — KVM

このサイトの実践編は、読者に docker で「檻」を起動させ、その中で QEMU の練習機（Ubuntu 24.04 の仮想マシン）を動かしている。 その練習機は、KVM を使わない完全エミュレーション（TCG）で動く。この記事では、同じ練習機を TCG と KVM の両方で起動して、 KVM が何で、どこにあり、何を速くし、何を変えるのかを、あなたの PC の上で確かめる。全6章・約2時間。

ただし、この記事はあなたの PC の CPU と KVM そのものを見るので、CPU の名前・/dev/kvm の権限・時間など、PC ごとに違って当然の行がある。そういう行には、ブロックの直後に注記を置いた。

この6章を貫いている1つの事実

KVM の正体は、CPU の仮想化支援機能を使って仮想マシンを動かすカーネルの部品で、使う側には /dev/kvm というファイル1つで配られている。QEMU はそれを開いたときだけ速くなり、練習機の中から見える CPU も変わる。 開けるかどうかは、CPU の印・カーネル・ファイルの権限・コンテナの許可の4つで決まる。

「KVM を使う」という言い方は、何か大きな仕組みを有効にするように聞こえる。実際に起きているのは、QEMU が /dev/kvm を開き、 カーネルに仮想マシンと仮想の CPU を作ってもらって、それをファイルとして持つことだけである。 だから、使えるかどうかは「そのファイルを開けるか」で決まり（第1・2章）、使うかどうかは QEMU に頼むかで決まり（第3章）、 使ったときに変わるのは、本物の CPU が命令を実行する部分の速さと、練習機から見える CPU の姿である（第4・5章）。 このサイトの練習機は、全員が開けるわけではないことと、開くと画面が変わることを理由に、開かないことを選んでいる（第6章）。

ここで覚えなくていいこと: KVM に頼むときの命令（ioctl）の一覧、VT-x と AMD-V の命令の違い、メモリのアドレスの変換を CPU に任せる仕組み（EPT・NPT）の細部、 入れ子の仮想化の速さ、QEMU の装置・ディスク・ファームウェアの選び方（QEMU の記事）、libvirt の定義の書き方。

この記事で扱うこと・扱わないこと
扱うことどこで
CPU の仮想化支援機能（VT-x / AMD-V）と、/proc/cpuinfo の vmx / svm。印が CPUID の答え（自己申告）であること1
KVM はカーネルのモジュール（kvm と kvm_intel / kvm_amd）で、/dev/kvm（10, 232）を出す2
コンテナに /dev/kvm を渡すとは何を渡すことか（device cgroup・ファイルの権限・--group-add・特権は増えない）。0666 と 0660 の両方の PC2
QEMU は KVM をアクセラレータとして使う（-accel kvm・-enable-kvm・-cpu host）。既定は TCG3
同じ練習機を TCG と KVM で起動して、段階ごとの時間と CPU の時間を測って比べる4
練習機の中から見た違い（systemd-detect-virt・hypervisor の印・CPUID の名前・dmesg）と、入れ子の仮想化（nested）。中から見える名前は QEMU が書いた名乗りで、消せる（kvm=off）5
このサイトの仮想マシン型の檻が KVM を使わない理由（定義が type='qemu'・全員に同じ画面・権限ゼロ）と、その代償6
扱わないことどこで扱うか・なぜ扱わないか
QEMU そのもの（マシンの型・装置・ディスクイメージ・ファームウェア・シリアル・モニタ・ネットワーク）QEMU の記事。この記事では、練習機を起動するコマンド行の最後の行（-accel と -cpu）だけを変える
libvirt と virsh の使い方LinuC 1.01 の第1章。この記事では、定義の type だけを見る
コンテナの仕組み（名前空間・cgroup の全体・イメージ）Docker の記事。この記事では、デバイスを渡す部分（device cgroup）だけを見る
Xen・VMware・Hyper-V などの他のハイパーバイザー、macOS の HVF の使い方この記事の檻では動かせない。名前が出るだけ
KVM の性能の調整（CPU の固定・大きなページ・vhost）速さは第4章の起動の時間だけを測る。調整は読者の PC で結果が大きく変わり、同じ画面を約束できない

このサイトの他の記事の檻は、これをどう使っているか

この記事を読みに来た理由は、たぶん実践編の docker run にある。このサイトの檻は、KVM との関係で3種類に分かれる。

檻の種類どの記事KVM との関係
コンテナ型（コンテナの中で直接打つ）LinuC 1.02・1.03・1.04・1.06・1.09、SQLite など仮想マシンを動かさないので、KVM は関係ない。カーネルはあなたの PC のもの（LinuC 1.01 の第3章）
仮想マシン型（コンテナの中で libvirt が QEMU の練習機を動かす）LinuC 1.01・1.05・1.07・1.08・1.10 など練習機の定義が type='qemu' なので TCG で動く。--device /dev/kvm を渡しても KVM は使わない（第6章で確かめた）
この記事の檻（コンテナの中で QEMU を直接打つ）この記事--device /dev/kvm と --group-add を渡したときだけ、-accel kvm で KVM を使える

仮想マシン型の檻の起動コマンドに --privileged も --cap-add も --device も無いのは、TCG がホストの特権も装置も1つも借りないからである。 練習機の中の lscpu が全員に同じ QEMU TCG CPU version 2.5+ を出すのも、TCG だからである（定義が cpu mode='maximum'、つまり -cpu max なのでこの名前になる。この記事の練習機は既定の qemu64 なので QEMU Virtual CPU version 2.5+。max は KVM では読む人の CPU の名前になる。第5章）。 この記事の檻だけが、比べるために /dev/kvm を受け取る。それでも渡すのはファイル1つとグループ1つで、特権は増えない（持てる特権の上限 CapBnd が docker の既定のまま。第2章）。

TCG の練習機の中は、どの PC でも同じ画面になる（第1章の AuthenticAMD・svm など）。

章

  1. 仮想化支援機能は、CPU の自己申告 — Intel の PC の上の TCG の練習機が、AMD の CPU と AMD-V を名乗り、KVM まで用意した。その KVM で仮想マシンも動く（25分）
  2. KVM の入口は /dev/kvm ひとつ — 同じ番号のファイルを root で作っても開けない。関門は3つで、エラーの文言で見分けられる（25分）
  3. QEMU は、頼まれたときだけ KVM を使う — /dev/kvm を開ける檻でも、何も付けなければ TCG。KVM の仮想マシンはファイルとして見える（20分）
  4. 速くなるのは、CPU が命令を実行する部分だけ — 全体は 倍、ユーザ空間は 倍、GRUB の待ちは縮まない（20分）
  5. 中から見える CPU は、アクセラレータで変わる — 同じ型でも KVM では Intel を名乗る。-cpu host で入れ子の仮想化の入口が開く。中から見える名前は QEMU が書いていて、消せる（25分）
  6. このサイトの練習機が KVM を使わない理由 — /dev/kvm を渡しても -accel tcg。ここで6章が1本になる（15分）

檻で再現できないもの

ことなぜ再現できないか代わりにしたこと
/dev/kvm が 0660 の PC著者の PC は 0666 で、--group-add が無くても開けてしまう第2章で、Ubuntu 24.04（検証用の仮想マシン。入れ子の KVM・docker.io 29.1.3）で同じ檻を起動した記録を載せた
AMD の CPU の PC著者の PC は Intel だけ出力が変わる行に注記を置いた（AuthenticAMD・svm・kvm_amd・nested が 1）。記録は無い
ファームウェアで仮想化支援を切った PC、nested が N の PCあなたの PC のファームウェアやカーネルの設定を変えることになり、檻の外に影響する第1・5章で、何が起きるかを説明した。印が無い CPU は、第5章で -cpu host,-vmx を使って練習機の中に作って確かめた。 nested が N の KVM は、検証用の仮想マシン（Ubuntu 24.04）で kvm_intel を nested=0 で読み込み直し、演習05 の判定が「前提不足」になることを記録した
rootless の podman で起動した檻本文の記録は docker で取った。rootless の podman では --group-add の番号が檻の中の番号になり、0660 の /dev/kvm は開けなかった Ubuntu 24.04 の podman 4.9.3 と、著者の PC の podman 5.8.6 で試した結果と、代わりの書き方（--group-add keep-groups・crun）を実践編に書いた
macOS・Windows の Docker Desktop著者は試していない。/dev/kvm が渡せるかも、檻が起動するかも確かめていない（この檻のイメージは amd64 用だけ）docker が動くカーネルに KVM が無いときを、検証用の仮想マシン（Ubuntu 24.04）で KVM の部品を外して記録した（第2章）。--device /dev/kvm は docker の時点で失敗し、--device なしの檻では KVM が要る演習を lab check が「前提不足」と理由を出して終える

実務のどこで効くか

場面ここで効く理由見落としやすい点関連する章
仮想マシンが遅いQEMU のプロセスが anon_inode:kvm-vm を持っているかで、KVM を使っているかが分かる/dev/kvm があっても、qemu-system-x86_64 はアクセラレータを指定しなければ TCG。TCG をはっきり指定している（-accel tcg・libvirt の type='qemu'）ことも、 「KVM が駄目なら TCG」（-machine accel=kvm:tcg・-accel kvm -accel tcg）で KVM を開けずに TCG に切り替わっている（起動のときに falling back to tcg と出る）こともある。仮想マシンの中の systemd-detect-virt は決め手にならない3・5・6
コンテナや CI で KVM を使いたい渡すのは --device /dev/kvm と、0660 ならグループ。特権は要らない--privileged で済ませると、要らない特権を全部渡すことになる2
仮想マシンの中で仮想マシンを動かしたい外の nested と、中に見せる CPU の型（vmx / svm）で決まる中の OS の設定をいくら見ても、外が印を渡していなければ使えない5
仮想マシンの中の画面や挙動を、人や環境の間でそろえたいKVM では CPU のメーカーや機能が外の PC に引きずられる。型を決めても、メーカーの名前と、外の CPU が持たない機能は引きずられる。完全にそろえるなら TCG速さの違いだけでなく、/proc/cpuinfo などの画面も変わる5・6
