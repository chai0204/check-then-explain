5. 中から見える CPU は、アクセラレータで変わる

TCG の練習機は AMD の CPU を名乗った（第1章）。同じ CPU の型（既定の qemu64）のまま KVM で起動すると、練習機は GenuineIntel を名乗り、svm は消え、 Hypervisor vendor: KVM が出る。-cpu host にすれば、あなたの PC の CPU の名前と印をそのまま名乗り、練習機の中にも /dev/kvm ができる（入れ子の仮想化）。 練習機から見える CPU は、QEMU の型と、命令を実行しているもの（QEMU のソフトか、本物の CPU か）の両方で決まる。 「どのハイパーバイザーか」の名前も QEMU が書いていて、消すこともできる。

この章のゴールと前提所要 25分
前提: 第4章まで読了（練習機が KVM で動いている）所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • 同じ CPU の型でも、TCG と KVM で練習機の CPU の名乗り（メーカー・印）が変わることを、出力で示せる
  • 練習機の中から、どのハイパーバイザーの上にいるかを尋ねる方法を3つ言え（systemd-detect-virt・lscpu の Hypervisor vendor・CPUID の名前）、その答えが QEMU の書いた名乗りで、消せることを示せる
  • -cpu host と、印を消す書き方（-cpu host,-vmx）で、入れ子の仮想化の入口を出し入れできる
ここで覚えなくていいこと: CPUID の他の番号の中身、kvm-clock などの準仮想化の仕組みの中身、CPU の型の一覧（Skylake-Client など）の各項目、 入れ子の仮想化の速さと、その中で動く仮想マシンの作り方。

同じ型でも、KVM では Intel を名乗る

この節で分かること: アクセラレータを変えると、練習機の中の何が変わるか。

第4章の最後で、練習機は -accel kvm（CPU の型は指定していないので既定の qemu64）で動いている。中に入る。

ふつうこう考える

練習機の CPU は、QEMU の -cpu の型で決まる。型は第1章と同じ qemu64 のままなのだから、TCG でも KVM でも、中から見える CPU は同じはずだ。 違うのは速さだけで、AMD の CPU を名乗り、AMD-V（svm）を持つと答えるだろう。

だめな理由: 型は同じでも、練習機は Intel の CPU を名乗り、svm は消えていた。 KVM でも、練習機が CPUID を実行すると本物の CPU はいったん KVM に戻り、KVM が QEMU の用意した答えの表から答える（だから型の名前は QEMU のまま）。 ただし KVM では練習機の命令を本物の CPU が実行するので、表に載せられるのは本物の CPU と KVM が持っている機能だけである。 Intel の CPU に AMD-V は無いので svm は外された（第3章の警告）。メーカーの名前は、QEMU が KVM のときは既定で本物の CPU のもの（GenuineIntel）に置き換える（-cpu qemu64,vendor=… で変えることはできる）。 型の名前（QEMU Virtual CPU version 2.5+）だけが同じで、中身は「命令を誰が実行しているか」で変わった。 AMD の PC で同じことをすると、メーカーは AuthenticAMD のままで、svm も（kvm_amd の nested が 1 なら）残る。KVM の練習機の中の画面は、読む人の PC で変わる。

hypervisor は、CPU が「自分は仮想マシンの CPU だ」と知らせる印で、TCG のときにもあった（第1章）。では、どのハイパーバイザーか。第1章と同じ場所の CPUID を読む。

CPU の答えの同じ場所に、今度は KVMKVMKVM と書いてある。書いたのは KVM ではなく QEMU で、KVM で動かすときの答えの表を作るときに、既定でこの名前を入れる（TCG の TCGTCGTCGTCG も QEMU が書いていた）。 Linux のカーネルはこの名前を知っているので、起動のときに Hypervisor detected: KVM と記録し、 KVM と協力して動く仕組み（時計の読み方など。準仮想化）を使った。それが Booting paravirtualized kernel on KVM の行である。 TCG の TCGTCGTCGTCG はカーネルも lscpu も知らない名前なので、TCG の練習機は、仮想マシンだとは分かっている（hypervisor の印がある）のに準仮想化を使わず、実機と同じやり方で起動し（on bare hardware）、Hypervisor vendor の行も出なかった。 systemd-detect-virt は TCG の名前も知っているので、第3章で qemu と答えた。

たとえ: CPU の型（qemu64）は、舞台の配役表に近い。役名は同じでも、TCG では代役（QEMU）が演じ、KVM では本人（本物の CPU）が演じる。 本人が演じれば、特技（使える機能）は本人ができるものに限られ、名乗る声（メーカー）も本人のものにそろえるのが QEMU の決まりである。
ただし崩れる点: 舞台では代役も本人も役名どおりに振る舞おうとするが、KVM の本人は、自分に無い特技（svm）を演じることがそもそもできない。役を寄せるのではなく、役のほうが削られる。
たとえ: CPUID の 0x40000000 番は、建物の管理人室の表札に近い。住人（練習機の OS）が見に行くと、管理会社の名前（KVMKVMKVM）が書いてある。 知っている会社なら、その会社のやり方（準仮想化）に合わせて暮らす。
ただし崩れる点: 表札は誰でも読める字で書かれているが、住人が「知っている会社」かどうかは住人の側の知識で決まる。同じ TCGTCGTCGTCG を、カーネルは知らず、systemd-detect-virt は知っていた。 それに、この表札を掛けているのは管理会社（KVM）ではなく、建物を建てた側（QEMU）である（この章の最後の節）。

-cpu host は、あなたの PC の CPU をそのまま見せる

この節で分かること: -cpu host が練習機に見せるものと、入れ子の仮想化の条件。

練習機から出て、QEMU が用意している CPU の型を見る。

この出力はあなたの PC の CPU で変わる。AMD の PC なら AuthenticAMD・AMD-V・kvm_amd になる。

-cpu host では、練習機は本物の CPU の名前を名乗り、仮想化支援機能 VT-x（vmx）まで持っていると答えた。練習機のカーネルはそれを見て kvm_intel を読み込み、 練習機の中にも /dev/kvm ができた。練習機の中で、さらに仮想マシンを KVM で動かせる状態である。これを入れ子の仮想化（nested virtualization）という。

練習機に vmx を渡すかどうかは、あなたの PC の KVM の設定で決まっている。外（この檻はあなたの PC のカーネルを見ている）で見る。

AMD の PC ではファイルが /sys/module/kvm_amd/parameters/nested になり、許していれば 1 と出る。

N（AMD は 0）なら、KVM は vmx を練習機に渡さず、-cpu host でも練習機の中に /dev/kvm はできない。 クラウドの仮想マシンや、仮想マシンの中の Linux で「この中で KVM が使えない」ときは、外側の KVM（やハイパーバイザー）がこの印を渡していないことを、まず疑う。

たとえ: 入れ子の仮想化は、貸し会議室の中に、さらに貸し会議室を作ることに近い。建物のオーナー（あなたの PC の KVM）が又貸しを許していれば（nested=Y）、借り手（練習機）も自分で部屋を貸せる。
ただし崩れる点: 又貸しの許可は書類で確かめられるが、練習機には「許されているか」を尋ねる窓口が無い。練習機は CPU の答えに vmx があるかだけを見て、あれば KVM を用意する。

印を消すと、入れ子の入口も消える

この節で分かること: CPU の型から機能を1つ消す書き方と、その効き目。

-cpu の値には、型の名前の後ろに「+機能」「-機能」を並べて、機能を1つずつ足したり消したりできる。vmx だけを消して起動する。

grep は何も出さず（vmx も svm も無い）、練習機の中に /dev/kvm は無い。CPU の名前は本物のまま、仮想化支援の印だけが消えた。 第1章で見たとおり、練習機のカーネルは CPU の答え（CPUID）を見て KVM を用意するかどうかを決めるので、印を消せば入れ子の仮想化はできなくなる。

手を動かす: 実践編の演習04で -cpu host の練習機を起動し、中の CPU があなたの PC の CPU と同じ名前になることを確かめる（KVM が要る）。 演習05は、印を消して練習機の中の /dev/kvm を無くす課題で、TCG（-cpu qemu64,-svm）でも KVM でもできる。

名前を消しても、KVM は KVM

この節で分かること: 練習機の中から見える「どのハイパーバイザーか」の名前が、何の証拠になり、何の証拠にならないか。

この章の最初で、練習機の CPUID の 0x40000000 番には KVMKVMKVM と書いてあった。KVM で動かすときも、CPU の答えの表を作るのは QEMU で（KVM はその表から答える）、名前も QEMU が表に入れている。 -cpu の値には、機能の印のほかに、こうした QEMU の決まりごとも書ける。kvm=off は「KVM の名前を書かない」という指定である。 -snapshot は、この起動で練習機のディスクに書いたものを、QEMU が終わるときに捨てる指定で、この起動を練習機の起動の記録に残さないために付ける（理由はこの節の最後）。

この出力の Model name などはあなたの PC の CPU で変わる。od の行も変わることがある。名前を書かないと 0x40000000 番の答えが無くなり、 Intel を名乗る練習機には、KVM は Intel の CPU と同じく「いちばん大きい基本の番号」の答えを返す。著者の PC ではその答えが 0 なので \0 が並んだが、 基本の番号が 0xD までの古い Intel の CPU では、0 でない字が並ぶ（著者の PC で、-cpu host,kvm=off,level=13 として確かめた）。どちらでも KVMKVMKVM は無い。

QEMU のプロセスは KVM の仮想マシン（anon_inode:kvm-vm）を持っていて、練習機は KVM で動いている。それなのに練習機の中では、CPUID の 0x40000000 番に名前が無く、lscpu に Hypervisor vendor の行が出ず、 カーネルは準仮想化を使わずに実機と同じやり方で起動した（on bare hardware）。systemd-detect-virt は kvm ではなく qemu と答えた。 CPUID に名前が無いので、ファームウェアが書いた機種の情報（/sys/class/dmi/id/sys_vendor の QEMU）から答えたのである。

練習機の中から見える名前は、QEMU の名乗りで、KVM を使っているかどうかの証拠ではない。確かめるなら、外で QEMU のプロセスが開いているファイルを見る（第3章）。 -snapshot を付けたのは、最後に見た journalctl の行のためである。練習機の systemd は、起動するたびに何の上で起動したと思ったかを記録に残し、演習03 はその記録（練習機の名乗り）で起動を分けて、時間を並べる。 この起動は KVM なのに qemu と記録されたので、ディスクに残すと、演習03 が TCG の起動として並べる時間に、この KVM の起動が混ざる。-snapshot なので、QEMU が終わればこの記録も消える。

たとえ: kvm=off は、管理人室の表札を外すことに近い。管理会社（KVM）は変わらず建物を管理しているが、住人（練習機の OS）は表札を見ても会社が分からないので、その会社のやり方（準仮想化）を使わずに暮らす。
ただし崩れる点: 表札を外しても、建物の登記（ファームウェアの機種の情報）には建てた会社の名前（QEMU）が残っていて、そちらを見る住人（systemd-detect-virt）は、仮想マシンの中だとは気づく。それでも、管理しているのが KVM かどうかは、建物の中からは分からない。
確認

仮想マシンの中で lscpu を打つと Hypervisor vendor: KVM と出た。また、sudo dmesg に Booting paravirtualized kernel on KVM があった。この2つから何が言えるか。

答え

CPU の答え（CPUID の 0x40000000 番）に KVM の名前（KVMKVMKVM）が書かれていて、カーネルがそれを知っている名前として受け取り、KVM と協力する仕組み（準仮想化）で起動した、ということ。 ただし名前は QEMU が CPUID に書いた名乗りなので、命令を本物の CPU が実行していることまでは、この2つだけでは言えない。反対に、kvm=off で名前を消せば、KVM で動いていてもこの2つは出ない（この章の最後の節）。 確かめるなら、外から QEMU のプロセスの /proc/PID/fd を見る（第3章）。

確認

Intel の PC で、同じ練習機を TCG と KVM（どちらも -cpu を指定しない）で起動し、中で lscpu の Vendor ID を見た。それぞれ何が出るか。理由も述べよ。

答え

TCG は AuthenticAMD、KVM は GenuineIntel。TCG では CPU の答えを QEMU が作るので、既定の型の答え（AMD）がそのまま出る。 KVM では、QEMU が既定でメーカーの名前を本物の CPU（Intel）のものに置き換える（型の名前は QEMU のまま）。

確認

KVM の上の仮想マシンの中で、さらに KVM を使いたい。外の PC の /sys/module/kvm_intel/parameters/nested は Y だった。QEMU にどう頼めばよいか。反対に、使わせたくないときは。

答え

-accel kvm -cpu host で起動すれば、vmx が仮想マシンに渡り、中のカーネルが kvm_intel を読み込んで /dev/kvm を作る。 使わせたくなければ -cpu host,-vmx のように印を消す（外の nested を N にしても渡らなくなる）。

この章で分かったこと

持ち帰ってほしいこと

  • KVM では練習機の命令を本物の CPU が実行するので、同じ型でも、本物が持たない機能は消える。メーカーの名前も、QEMU の既定で本物のものになる
  • CPUID の 0x40000000 番の名前（KVMKVMKVM・TCGTCGTCGTCG）は、どちらも QEMU が書いている。lscpu・dmesg・systemd-detect-virt はそれを読む
  • -cpu …,kvm=off で名前を消すと、KVM で動いていても中からは名乗らない（systemd-detect-virt は qemu）。KVM かどうかの決め手は、外の /proc/PID/fd
  • -cpu host は本物の CPU の名前と印をそのまま見せる。vmx / svm が渡ると練習機の中にも /dev/kvm ができる（入れ子の仮想化。外の nested が許しているとき）
  • -cpu 型,-機能 で印を消せる。印が無ければ、中のカーネルは KVM を用意しない
