8. 関数は、子ではない

名前に番号を振るスクリプトで、番号が 1 の次に 21 へ飛んだ。区切り線を引く関数が、中の for で同じ名前の変数 i を使っていたからである。スクリプトは子のプロセスで動くが、関数は呼んだシェルの中で動く。だから変数を共有し、exit すれば全体が終わる。bash -x は、その書き換わりを1行ずつ見せる道具である。最後に、8章が1つの事実から出ていたことをまとめる。

前提: 第7章まで読了所要 20分影響度 A出題範囲 1.06.2（重要度6）最終検証 2026-10-13

この章のゴール

  • 名前() { … } と function 名前 { … } で関数を作れ、その違い（dash で使えるか）を言える
  • local・return・exit が関数の中で何をするかを、記録で説明できる
  • bash -x と bash -v の出力の違いを言い、原因の見当を付けるのに使える
  • 8章の結果を「子が受け取ったもの・親に返せたもの」の表で説明できる
ここで覚えなくていいこと: export -f（関数を子に渡す bash 独自の機能）、FUNCNAME・BASH_SOURCE、PS4 による -x の表示の変更、再帰。デバッグは bash -x・bash -v・set -x・set +x の4つで足りる。

関数は、いまのシェルの中で動く

この節で分かること: 関数の2つの書き方と、子に渡らないこと。

この章も ~/try で作業する。何度も使う一連のコマンドに名前を付けたものが関数である。

$ mkdir -p ~/try && cd ~/try
$ wave() { echo "やあ、$1"; }
$ wave alice
やあ、alice
$ type wave
wave is a function
wave () 
{ 
    echo "やあ、$1"
}
$ function bye { echo "またね、$1"; }
$ bye bob
またね、bob
$ bash -c 'wave alice'; echo "終了ステータス $?"
bash: line 1: wave: command not found
終了ステータス 127

書き方は2つある。名前() { …; } は sh の規格にある書き方で、dash でも動く。function 名前 { …; } は bash の書き方で、第4章のとおり dash では動かない。type は、その名前が関数であることと中身を見せた。

関数は子のシェルに渡らない。bash -c で起動した子からは wave が見えず、127（見つからない）になった。第2章の alias と同じで、関数は環境変数ではないからである。

名前だけで打ったコマンドは、alias の次に関数が調べられ、組み込みコマンドと PATH はその後になる（第2章のサーチパスの順）。だから既存のコマンドと同じ名前の関数を作ると、そちらが先に動く。

$ date() { echo "関数の date が先に動いた"; }
$ date
関数の date が先に動いた
$ type date
date is a function
date () 
{ 
    echo "関数の date が先に動いた"
}
$ unset -f date
$ type date
date is /usr/bin/date

unset -f で関数を消すと、PATH の /usr/bin/date に戻った。

たとえ: 関数は、自分の手帳に書いた「いつもの手順」の名前に近い。「朝の点検」と書けば、自分がその場で手順を順にこなす。誰かに頼む（子のプロセスを起動する）わけではない。
ただし崩れる点: 手帳の手順は他人に見せれば使ってもらえるが、関数は子のシェルには見えない。使わせたいなら、子の側で定義し直すか、スクリプトにして置く（第4章）。

local・return・exit

この節で分かること: 関数の中の変数・戻り値・終わり方。
$ cat > fn.sh <<'END'
> #!/bin/bash
> greet() {
>     local who=$1
>     echo "こんにちは、$who（関数の中で \$0 = $0、\$# = $#）"
>     return 3
> }
> greet alice bob
> echo "greet の終了ステータス = $?"
> echo "関数の外で who = [$who]"
> END
$ bash fn.sh
こんにちは、alice（関数の中で $0 = fn.sh、$# = 2）
greet の終了ステータス = 3
関数の外で who = []

関数の中の $1・$# は、関数に渡した引数のものになる（スクリプトの引数とは別）。$0 だけはスクリプトの名前のままである。local who と書いた変数は関数の中だけのもの（ローカル変数）で、外からは空に見えた。return 3 は関数を終わらせ、3 を終了ステータスとして呼んだ側の $? に渡した。

$ cat > ex.sh <<'END'
> #!/bin/bash
> stop() { echo "関数の中で exit します"; exit 5; }
> stop
> echo "ここは表示されない"
> END
$ bash ex.sh; echo "終了ステータス $?"
関数の中で exit します
終了ステータス 5

関数の中の exit は、関数ではなくスクリプト全体を終わらせた。関数は別のプロセスではないので、「関数だけを終わらせる」には return を使う。

関数の中で書くと呼んだ側から見ると
return 数関数だけを終わらせるその数が $? になる（0〜255）
exit 数スクリプト全体を終わらせるスクリプトの終了ステータスになる
local 変数関数の中だけの変数を作る見えない・変わらない
（local なしの代入）呼んだ側の同じ名前の変数を書き換える書き換わる（次の節）

local を付けない変数は、呼んだ側と同じもの

この節で分かること: 関数が子ではないことの、いちばん困る帰結。

名前に番号を振り、名前ごとに区切り線を引くスクリプトを書く。区切り線は関数 line に任せる。

ふつうこう考える

関数 line の中の for で使う i は、関数の中の作業用の数である。外のループの i とは別の場所にあり、i=$((i + 1)) で 1 ずつ増える番号には影響しないはずだ。

$ cat > number.sh <<'END'
> #!/bin/bash
> line() {
>     for ((i = 0; i < 20; i++)); do printf '-'; done
>     printf '\n'
> }
> i=1
> for name in "$@"; do
>     echo "$i: $name"
>     line
>     i=$((i + 1))
> done
> END
$ bash number.sh alice bob carol
1: alice
--------------------
21: bob
--------------------
21: carol
--------------------
だめな理由: 番号が 1 の次に 21 へ飛んだ。関数は呼んだシェルの中で動き、local を付けない変数は呼んだ側の同じ名前の変数そのものである。 line の for が i を 0 から 20 まで進め、戻ったところで i=$((i + 1)) が 21 にした。 スクリプト（子のプロセス）なら親の変数を書き換えられないが、関数は子ではないので書き換えられる。第2章〜第7章で見てきた「コピーだから戻らない」が、関数には当てはまらない。
たとえ: スクリプトを呼ぶのはコピーした書類を別の人に渡すこと、関数を呼ぶのは同じ机の上で、自分がもう1つの作業を始めることに近い。同じ机なので、メモ用紙（変数）も同じものを使う。
ただし崩れる点: 人なら「このメモは作業用」と区別して使うが、bash は名前が同じなら同じメモ用紙に書く。作業用だと宣言する（local）まで区別しない。

bash -x は、展開した後の形を1行ずつ見せる

この節で分かること: bash -x・bash -v・set -x の違いと使いどころ。

bash -x は、実行する直前のコマンドを、変数を展開した後の形で + を付けて出す。この出力をトレースと呼ぶ。出力は標準エラーに出るので、2>&1 で標準出力にまとめてから読む。

$ bash -x number.sh alice bob 2>&1 | head -12
+ i=1
+ for name in "$@"
+ echo '1: alice'
1: alice
+ line
+ (( i = 0 ))
+ (( i < 20 ))
+ printf -
-+ (( i++ ))
+ (( i < 20 ))
+ printf -
-+ (( i++ ))

(( i = 0 ))・(( i < 20 )) と、関数の中で i が動いているのが見える（printf - の出力の - が、次の + の行の頭にくっついている）。長いので、i への代入と echo だけを抜き出す。

$ bash -x number.sh alice bob 2>&1 | grep -E '^\+ (i=|echo)'
+ i=1
+ echo '1: alice'
+ i=21
+ echo '21: bob'
+ i=21

+ i=1 の次の代入が + i=21 である。原因の行がここで分かる。bash -v は、展開する前の行を読んだとおりに出す。

$ bash -v number.sh alice 2>&1 | head -14
#!/bin/bash
line() {
    for ((i = 0; i < 20; i++)); do printf '-'; done
    printf '\n'
}
i=1
for name in "$@"; do
    echo "$i: $name"
    line
    i=$((i + 1))
done
1: alice
--------------------

-v では変数は $i のままで、値は分からない。ここまで読まれた、ということを確かめるのに向く。関数の中の i を local にすると直る。

$ sed -i '/^line() {/a\    local i' number.sh; sed -n '2,6p' number.sh
line() {
    local i
    for ((i = 0; i < 20; i++)); do printf '-'; done
    printf '\n'
}
$ bash number.sh alice bob carol
1: alice
--------------------
2: bob
--------------------
3: carol
--------------------

スクリプト全体ではなく一部だけを見たいときは、その範囲を set -x と set +x で挟む。対話シェルでもそのまま使える。

$ set -x; echo "$HOME"; set +x
+ echo /home/lab
/home/lab
+ set +x
書き方出すもの向いている場面
bash -x x.sh実行する直前の行。変数は展開した後の値で、行頭に +どこで値がおかしくなったか
bash -v x.sh読み込んだ行をそのまま（展開する前）どこまで読まれたか・文法エラーの位置
set -x … set +x挟んだ範囲だけ -x と同じもの長いスクリプトの一部だけ見る
手を動かす: 実践編の演習08は、この章と同じ症状のスクリプトを bash -x で調べて直す課題である。 判定は bash number.sh alice bob carol を実行し、番号と区切り線の6行を期待の出力と比べる。

8章が1つの事実から出ていた

この節で分かること: 主題1.06 の出題範囲が、なぜこの並びになっているのか。

この教材で記録したことを並べる。

章起動されたもの受け取ったもの親に返せたもの記録で見たこと
1ログインシェル・子のシェル起動のしかた（ログインか・対話か）—読むファイルが変わる。~/.bash_profile を作ると ~/.profile と ~/.bashrc が読まれない
2bash ファイルexport した環境変数のコピー終了ステータスだけbash ~/.bashrc では alias が残らない。source が要る
3$( )・( )同上標準出力の文字と終了ステータス中で x=2 にしても外は 1。|| は直前の数しか見ない
4スクリプト（./x.sh）実行した人の PATH のコピー終了ステータスalice の ~/bin/date が動いた。先頭で PATH を決めると止まる
5スクリプト呼んだ側が切った引数の並び—"my file.txt" は1つで届き、$* で割れる
6スクリプト—0〜255 の数1つexit 256 が 0 になる
7パイプの右側の while変数のコピー終了ステータス中で数えた合計が 0 になる
8関数（子ではない）同じ変数そのものreturn の数。変数は共有i が 21 になる

1〜7章は同じ形をしている。

新しく起動したシェルやスクリプトは、親の環境変数のコピーを受け取って始まる。
終わるときに親へ返せるのは、0〜255 の終了ステータス1つだけである。

そして8章の関数だけが、この形の外にある（子ではないので、コピーではなく本物を触る）。だから local という言葉が要る。

出題範囲 1.06 の「詳細」欄に並ぶ語は、ほとんどがこの事実の言い換えである。source と . は「子を作らずに読む」ため、~/.profile と ~/.bashrc の書き分けは「環境変数は子に渡り、alias は渡らない」ため、$? と exit は「返せる唯一のもの」、"$@" は「受け取った区切りを保つ」ため、スクリプトの中の PATH は「受け取ったコピーを信用しない」ためにある。

だから、シェルで何かが思いどおりに動かないときに確かめる順番は決まる。

1. いま、どのシェルの中か      echo $0 / shopt login_shell / echo $-
2. 何を受け取ったか            declare -p 変数 / echo "$PATH" / for a in "$@"
3. 何を返したか                echo $?
4. どこで値が変わったか        bash -x / set -x … set +x
たとえ: 8章はどれも、出張に出る部下の話だった。出発のときに書類のコピー（環境変数）と指示（引数）を持たされ、帰ってきて報告できるのは「うまくいったか」の番号札1枚（終了ステータス）だけ。出張先で何を書き込んでも、本社の原本は変わらない。関数だけは出張ではなく、本社の中で別の机に移るだけだった。
ただし崩れる点: 人の部下なら帰ってから口頭で補足できるが、シェルの子には札1枚以外の帰り道が無い。伝えたいことがあるなら、ファイルに書くか、標準出力に出してコマンド置換で受け取るしかない。
確認

関数の中で使う変数を、その関数の中だけのものにするには、何というキーワードで宣言するか。

答え

local。付けないと、呼んだ側の同じ名前の変数を書き換える（記録では番号が 21 に飛んだ）。

確認

関数の中に exit 5 と書いた。その関数を呼んだスクリプトはどうなるか。return 5 と書いた場合はどうか。

答え

exit 5 ではスクリプト全体がそこで終わり、終了ステータスは 5 になる（記録では「ここは表示されない」が出なかった）。 return 5 では関数だけが終わり、呼んだ直後の $? が 5 になって、スクリプトは続く。

確認

シェルスクリプトを、実行するコマンドを1行ずつ（変数を展開した後の形で）表示しながら実行するオプションはどれか。
(A) bash -v　(B) bash -x　(C) bash -n　(D) bash -e

答え

(B)。(A) bash -v は読み込んだ行を展開する前のまま表示する（変数は $i のまま）。 -n と -e はこの章では扱っていない。

確認

#!/bin/sh で始まるスクリプトで関数を定義したい。Ubuntu で動く書き方はどちらか。
(A) function backup { …; }　(B) backup() { …; }

答え

(B)。/bin/sh は dash で、function キーワードを知らない（第4章の記録: function: not found のあと文法エラー）。 bash で動かすなら（先頭行が #!/bin/bash）どちらでもよい。

この章で分かったこと

持ち帰ってほしいこと

  • 関数は 名前() { …; } か function 名前 { …; }（bash のみ）。子のシェルには渡らない
  • 関数は呼んだシェルの中で動く。local を付けない変数は共有され、exit はスクリプト全体を終わらせる。関数だけ終えるのは return
  • bash -x は展開後の形に + を付けて、bash -v は読んだままを出す。一部だけなら set -x … set +x
  • 子は親の環境変数のコピーを受け取り、返せるのは 0〜255 の終了ステータス1つだけ。主題1.06 の語はほとんどがこの言い換え
  • 動かないときは「どのシェルか → 何を受け取ったか → 何を返したか → どこで変わったか」の順に確かめる
