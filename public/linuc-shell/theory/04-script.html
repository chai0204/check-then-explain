4. 先頭行を読むのはカーネルで、bash ではない

#!/bin/sh で始まるスクリプトを bash hello.sh で動かすと動く。chmod +x して ./hello.sh で動かすと、同じファイルが文法エラーになる。先頭行の #! を読むのは「直接実行された」ときのカーネルだけで、bash hello.sh のときはただのコメントだからである。スクリプトを他の人に使わせるときは、この先頭行に、権限・所有者・置き場所・PATH の4つが加わる。

前提: 第3章まで読了所要 22分影響度 B出題範囲 1.06.2（重要度6）最終検証 2026-10-13

この章のゴール

  • ./x.sh・bash x.sh・. x.sh のそれぞれで、何がファイルを読むのか、どんな権限が要るのかを言える
  • 先頭行 #! が何を決めるか、Ubuntu の /bin/sh が dash であることが何を引き起こすかを説明できる
  • chmod と chown でスクリプトを全員が使える形にでき、スクリプトには r と x の両方が要る理由を言える
  • 使う人の PATH に左右されないスクリプトの書き方を言える
ここで覚えなくていいこと: SUID・SGID・スティッキービット（主題1.02 で扱う）、ACL、install コマンド、#!/usr/bin/env bash と #!/bin/bash の使い分けの細部。chmod の数字は 755・644・700・711 が読めれば足りる。

同じファイルを、3つの書き方で動かす

この節で分かること: ./x.sh と bash x.sh の違い。先頭行がいつ使われるか。

~/try に、関数を1つ持つ小さなスクリプトを書く。先頭行は #!/bin/sh にしておく。

$ mkdir -p ~/try && cd ~/try
$ cat > hello.sh <<'END'
> #!/bin/sh
> function say {
>     echo "こんにちは、$1"
> }
> say "$(id -un)"
> echo "\$0 は $0"
> END
$ ls -l hello.sh
-rw-r--r-- 1 lab lab 93 Oct 13 11:44 hello.sh
$ ./hello.sh; echo "終了ステータス $?"
bash: ./hello.sh: Permission denied
終了ステータス 126
$ bash hello.sh; echo "終了ステータス $?"
こんにちは、lab
$0 は hello.sh
終了ステータス 0

作ったばかりのファイルは -rw-r--r-- で、x（実行権）が無い。./hello.sh は「このファイルを実行せよ」とカーネルに頼むので、x が無いと Permission denied（終了ステータス 126）になる。bash hello.sh は動いた。実行されたのは bash という実行ファイルのほうで、hello.sh は bash に読まれただけだからである。読むのに要るのは r（読み）だけでよい。

では x を付けて、直接実行する。

ふつうこう考える

bash hello.sh で正しく動くことは確かめた。足りなかったのは実行権だけなのだから、chmod +x すれば ./hello.sh でも同じように動くはずだ。

$ chmod +x hello.sh; ls -l hello.sh
-rwxr-xr-x 1 lab lab 93 Oct 13 11:44 hello.sh
$ ./hello.sh; echo "終了ステータス $?"
./hello.sh: 2: function: not found
こんにちは、
./hello.sh: 4: Syntax error: "}" unexpected
終了ステータス 2
だめな理由: 直接実行すると、カーネルはファイルの先頭2文字が #!（シバン、shebang とも呼ぶ）かを見て、その行に書かれたプログラム（ここでは /bin/sh）を起動し、ファイルを読ませる。 Ubuntu の /bin/sh は bash ではなく dash である。dash は function というキーワードを知らない。 function say { の1行を1つのコマンドとして読み、function をコマンド名だと思って探し（function: not found。say と { はその引数になった）、次の行の echo を単独のコマンドとしてその場で実行し（だから引数の無い「こんにちは、」が出た）、対になる { の無い } で文法エラーになった。 bash hello.sh のときは、先頭行は # で始まるただのコメントとして読み飛ばされていた。先頭行を読むのは bash ではなく、直接実行されたときのカーネルである。
$ head -1 hello.sh; ls -l /bin/sh
#!/bin/sh
lrwxrwxrwx 1 root root 4 Mar 31  2024 /bin/sh -> dash
$ sh hello.sh; echo "終了ステータス $?"
hello.sh: 2: function: not found
こんにちは、
hello.sh: 4: Syntax error: "}" unexpected
終了ステータス 2

sh hello.sh も同じ結果になる。こちらは「dash に読ませる」なので、先頭行はやはりコメントである。

dash が function に何を渡したかは、function という名前のコマンドを仮に作って PATH の先頭に置くと見える。

$ mkdir -p fbin
$ printf '#!/bin/sh\necho "function が受け取った引数: $# 個: $*"\n' > fbin/function; chmod +x fbin/function
$ PATH="$HOME/try/fbin:$PATH" sh hello.sh
function が受け取った引数: 2 個: say {
こんにちは、
hello.sh: 4: Syntax error: "}" unexpected

受け取った引数は say と { の2つだった。{ は「まとまりの始まり」としてではなく、ただの文字として渡されている。だから最後の } には対になる相手がいない。先頭行を bash に直す。

$ sed -i '1s|.*|#!/bin/bash|' hello.sh; head -1 hello.sh
#!/bin/bash
$ ./hello.sh
こんにちは、lab
$0 は ./hello.sh
$ sh hello.sh; echo "終了ステータス $?"
hello.sh: 2: function: not found
こんにちは、
hello.sh: 4: Syntax error: "}" unexpected
終了ステータス 2

./hello.sh は動くようになり、sh hello.sh は相変わらず失敗する。先頭行を直しても、読ませるプログラムを自分で指定した起動のしかたには効かない。

3つ目の書き方は第2章の .（source）で、子を作らず、いまのシェルに読ませる。

$ . ./hello.sh
こんにちは、lab
$0 は /bin/bash
$ type say
say is a function
say () 
{ 
    echo "こんにちは、$1"
}

$0 がスクリプトの名前ではなく、いまのシェル自身の $0（/bin/bash）になった。スクリプトの中で定義した関数 say も、いまのシェルに残っている。

先頭行が無いスクリプトを直接実行すると、起動した側のシェルが自分で読む。

$ printf 'echo "BASH_VERSION=[$BASH_VERSION]"\n' > noshebang.sh; chmod +x noshebang.sh
$ ./noshebang.sh
BASH_VERSION=[5.2.21(1)-release]
$ sh noshebang.sh
BASH_VERSION=[]
書き方読むプログラム先頭行要る権限$0どこで動くか
./hello.sh#! の行のプログラム（無ければ起動した側のシェル）使われるr と x./hello.sh子のプロセス
bash hello.shbashコメントrhello.sh子のプロセス
sh hello.shdash（Ubuntu の /bin/sh）コメントrhello.sh子のプロセス
. ./hello.sh / source ./hello.shいまのシェルコメントrシェル自身の $0いまのシェル
たとえ: 先頭行は封筒に書いた「担当: ○○課」に近い。郵便受け（カーネル）に投げ込めば、封筒の指定どおりの課に回る。 自分で「この書類を△△課に読んでもらって」と手渡せば（bash hello.sh・sh hello.sh）、封筒の指定は見られない。
ただし崩れる点: 人の課なら指定違いに気づいて回し直してくれるが、dash は自分宛てでない書類も黙って読み始め、読めないところで止まる。しかも止まる前に、読めた部分（「こんにちは、」）は実行してしまう。

chmod: スクリプトには r と x の両方が要る

この節で分かること: 権限の書き方と、スクリプトと実行ファイルの違い。
$ chmod 700 hello.sh; ls -l hello.sh
-rwx------ 1 lab lab 95 Oct 13 11:44 hello.sh
$ chmod u=rwx,go=rx hello.sh; ls -l hello.sh
-rwxr-xr-x 1 lab lab 95 Oct 13 11:44 hello.sh
$ chmod go-x hello.sh; ls -l hello.sh
-rwxr--r-- 1 lab lab 95 Oct 13 11:44 hello.sh
$ chmod 755 hello.sh

chmod は数字でも記号でも書ける。数字は r=4・w=2・x=1 の足し算を、所有者・グループ・その他の順に3桁並べたものである。

書き方結果意味
chmod 755 / chmod u=rwx,go=rxrwxr-xr-x所有者は全部、他の人は読んで実行できる（全員が使うスクリプトの形）
chmod 700rwx------所有者だけ
chmod 644rw-r--r--実行権なし（作ったばかりのファイルの形）
chmod +x / chmod go-x—今の権限に足す・から引く。+x のように誰に（u・g・o・a）を省くと、umask が隠しているビットには付けない（umask が 022 なら全員に付く）。必ず全員に付けるなら a+x

umask を 077 にした中で試すと、違いが見える。

$ (umask 077; chmod 644 hello.sh; chmod +x hello.sh; ls -l hello.sh)
-rwxr--r-- 1 lab lab 95 Oct 13 11:43 hello.sh
$ (umask 077; chmod 644 hello.sh; chmod a+x hello.sh; ls -l hello.sh)
-rwxr-xr-x 1 lab lab 95 Oct 13 11:43 hello.sh

次に、全員が使える場所へ置く。カレントディレクトリは PATH に入っていないので、名前だけでは動かない（第2章）。/usr/local/bin は管理者が自分でコマンドを置くための場所で、全員の PATH に最初から入っている。

$ hello.sh
bash: hello.sh: command not found
$ sudo cp hello.sh /usr/local/bin/hello
$ ls -l /usr/local/bin/hello
-rwxr-xr-x 1 root root 95 Oct 13 11:45 /usr/local/bin/hello
$ hello
こんにちは、lab
$0 は /usr/local/bin/hello
$ sudo -u alice hello
こんにちは、alice
$0 は /usr/local/bin/hello

alice も名前だけで使えた。ここで、その他（alice）から r を外して x だけにしてみる。比べるために、機械語の実行ファイル（id のコピー）も同じ 711 にする。

$ sudo chmod 711 /usr/local/bin/hello; ls -l /usr/local/bin/hello
-rwx--x--x 1 root root 95 Oct 13 11:45 /usr/local/bin/hello
$ sudo -u alice hello; echo "終了ステータス $?"
/bin/bash: /usr/local/bin/hello: Permission denied
終了ステータス 126
$ sudo cp /usr/bin/id /usr/local/bin/myid; sudo chmod 711 /usr/local/bin/myid; ls -l /usr/local/bin/myid
-rwx--x--x 1 root root 39432 Oct 13 11:45 /usr/local/bin/myid
$ sudo -u alice myid -un
alice

機械語の myid は x だけで動き、スクリプトの hello は /bin/bash: … Permission denied になった。エラーを出したのが /bin/bash であることに注目する。カーネルは x を見て /bin/bash を起動するところまではやった。そこから先、alice の権限で動く bash が、スクリプトを読めなかった。スクリプトは読まれてはじめて動くので、使う人に r が要る。

たとえ: 機械語の実行ファイルはオルゴール、スクリプトは楽譜に近い。オルゴールはゼンマイを巻く権利（x）さえあれば鳴る。楽譜は演奏者（bash）が読めなければ1音も出ない。
ただし崩れる点: 楽譜なら誰か別の人に読んでもらえばよいが、演奏者はスクリプトを実行した本人の権限で動く。alice が読めないものは、alice の演奏者にも読めない。

chown: 置いたファイルを、誰のものにするか

この節で分かること: 所有者を変えるコマンドと、全員が使うものを root の持ち物にする理由。
$ sudo chmod 755 /usr/local/bin/hello
$ chown lab /usr/local/bin/hello
chown: changing ownership of '/usr/local/bin/hello': Operation not permitted
$ sudo chown alice:alice /usr/local/bin/hello; ls -l /usr/local/bin/hello
-rwxr-xr-x 1 alice alice 95 Oct 13 11:45 /usr/local/bin/hello
$ sudo chown root:root /usr/local/bin/hello; ls -l /usr/local/bin/hello
-rwxr-xr-x 1 root root 95 Oct 13 11:45 /usr/local/bin/hello

所有者を変えられるのは root だけで、lab が自分に変えようとすると Operation not permitted になった。chown 所有者:グループ ファイル の形で、両方を一度に変えられる。

グループだけなら事情が違う。ファイルの所有者は、自分が属しているグループへなら root でなくても変えられる（chgrp グループ ファイル か chown :グループ ファイル）。alice を staff グループに入れて試す。

$ sudo usermod -aG staff alice; id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice),50(staff)
$ sudo -u alice bash -c umask
0002
$ sudo -u alice bash -c 'cd /tmp && touch g.txt && chgrp staff g.txt && ls -l g.txt'
-rw-rw-r-- 1 alice staff 0 Oct 13 11:43 g.txt
$ sudo -u alice bash -c 'cd /tmp && chown :alice g.txt && ls -l g.txt'
-rw-rw-r-- 1 alice alice 0 Oct 13 11:43 g.txt
$ sudo -u alice bash -c 'cd /tmp && chgrp lab g.txt'
chgrp: changing group of 'g.txt': Operation not permitted
$ sudo -u alice bash -c 'cd /tmp && chown lab g.txt'
chown: changing ownership of 'g.txt': Operation not permitted

alice が属している staff と alice へは変えられ、属していない lab へは変えられなかった。所有者を lab にすることもできない。ファイルが -rw-rw-r-- なのは、sudo -u alice で動いたシェルの umask が 0002 だったからで、ここではグループの列だけを見ればよい。

全員が使うスクリプトの所有者を root にするのは、書き換えられる人を減らすためである。alice の持ち物のままだと、alice はいつでも中身を書き換えられ、次に lab が hello と打ったときには alice が書いたものが lab の権限で動く。rwxr-xr-x root root なら、書き換えられるのは root だけになる。

使う人の PATH に、左右されない

この節で分かること: 同じスクリプトが、実行した人によって違う動きをする理由と、その止め方。

今日の日付を出すだけのスクリプトを全員用に置く。一方で alice は、自分用の date を ~/bin に作っていた（ここでは、いつも同じ日付を出す偽物にしておく）。

$ cat > report.sh <<'END'
> #!/bin/bash
> echo "作成日: $(date +%F)"
> END
$ sudo cp report.sh /usr/local/bin/report; sudo chmod 755 /usr/local/bin/report
$ sudo -u alice mkdir /home/alice/bin
$ printf '#!/bin/sh\necho "1999-12-31"\n' | sudo -u alice tee /home/alice/bin/date
#!/bin/sh
echo "1999-12-31"
$ sudo chmod 755 /home/alice/bin/date
$ report
作成日: 2026-10-13
$ sudo -u alice report
作成日: 2026-10-13
$ sudo -iu alice report
作成日: 1999-12-31
$ sudo -iu alice bash -c 'echo $PATH'
/home/alice/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin

同じ /usr/local/bin/report なのに、alice がログインして使うと別の日付が出た。スクリプトは起動した人の環境変数のコピーを受け取って動き、PATH もその1つである。alice のログインシェルでは、Ubuntu の ~/.profile が ~/bin を PATH の先頭に足すので（第2章）、スクリプトの中の date は alice の ~/bin/date になる。ログインしない sudo -u alice では ~/.profile が読まれず、本物が動いた。

同じ alice でも、入り方で PATH そのものが違う。

$ su - alice
Password: 
（略）   ← 入口の案内
alice@linuc:~$ echo $PATH
/home/alice/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
alice@linuc:~$ type date
date is /home/alice/bin/date
alice@linuc:~$ report
作成日: 1999-12-31
alice@linuc:~$ exit
logout

su - の PATH には /usr/games などが入っていて、sudo -i のときと並びが違う（入り方ごとに別の仕組みが PATH を作っている）。スクリプトの書き手は、使う人がどの入り方をしたかを選べない。だからスクリプトの先頭で PATH を決めてしまう。

$ sed -i '1a PATH=/usr/bin:/bin' report.sh; head -2 report.sh
#!/bin/bash
PATH=/usr/bin:/bin
$ sudo cp report.sh /usr/local/bin/report
$ sudo -iu alice report
作成日: 2026-10-13

先頭で PATH=/usr/bin:/bin と代入すると、このスクリプトの中のコマンドは、使う人の PATH ではなくこの並びで探される。代入はスクリプト（子のプロセス）の中だけで効き、使う人の PATH は変わらない。/usr/bin/date のように1つずつ絶対パスで書いても同じ効果になる。

たとえ: 出張先で「近くの文房具屋で買ってきて」と頼むのに近い。どの店に行くかは、頼まれた人がいる場所（PATH）で決まる。同じ指示でも、行く人によって違う店の違う品が届く。
ただし崩れる点: 人なら店の違いに気づいて確かめるが、スクリプトは見つかった最初の date を黙って使う。店の住所（PATH）を指示書の側に書いておくしかない。
手を動かす: 実践編の演習03は、#!/bin/sh のまま function を使っているスクリプトを直して /usr/local/bin に置き、alice が名前だけで使えるようにする課題である。 判定は所有者と権限を読み、alice として2回実行する。2回目は date と id の偽物を PATH の先頭に置いた状態で動かす。
確認

権限が rw-r--r-- のスクリプト x.sh がある。chmod を使わずに実行できる方法をすべて選べ。
(A) ./x.sh　(B) bash x.sh　(C) source x.sh　(D) . x.sh

答え

(B)・(C)・(D)。どれも、実行されるのは bash（またはいまのシェル）で、x.sh は読まれるだけなので r があれば足りる。 (A) はファイルそのものを実行するので x が要る（記録では Permission denied・終了ステータス 126）。

確認

スクリプトの1行目 #!/bin/bash が使われるのは、次のうちどの起動のしかたか。
(A) ./x.sh　(B) bash x.sh　(C) sh x.sh　(D) . x.sh

答え

(A) だけ。直接実行されたときに、カーネルが #! を見て /bin/bash を起動する。 (B)(C)(D) では、読むプログラムが先に決まっているので、1行目は # で始まるコメントとして読み飛ばされる。

確認

全員が使うスクリプトを /usr/local/bin/tool に置いた。所有者を root、グループを root にし、所有者だけが書き換えられ、全員が実行できる状態にするコマンドを2つ書け。

答え

chown root:root /usr/local/bin/tool と chmod 755 /usr/local/bin/tool（どちらも root で実行する。一般ユーザが所有者を変えようとすると Operation not permitted になる。グループだけなら、所有者が自分の属するグループへ変えられる）。 chmod 711 にするとスクリプトは他のユーザから読めなくなり、Permission denied で動かない。

確認

スクリプトの2行目に PATH=/usr/bin:/bin と書く理由を説明せよ。

答え

スクリプトは実行した人の環境変数のコピーを受け取るので、中のコマンドは実行した人の PATH で探される。 使う人が PATH の先頭に同じ名前の別物を置いていれば、そちらが動く。先頭で PATH を決めれば、誰がどの入り方で実行しても同じコマンドが使われる。 代入はスクリプトの中だけで効き、実行した人の PATH は変わらない。

この章で分かったこと

持ち帰ってほしいこと

  • ./x.sh はカーネルが #! の行のプログラムを起動する。bash x.sh・sh x.sh は読むプログラムを自分で決めるので、先頭行はただのコメント
  • Ubuntu の /bin/sh は dash。function などの bash の書き方は #!/bin/sh では動かない
  • ./x.sh には r と x、bash x.sh と . x.sh には r だけが要る。他人に使わせるスクリプトには、その人に r と x の両方が要る
  • 全員用のスクリプトは /usr/local/bin に置き、chown root:root・chmod 755。所有者を変えるのは root だけ。グループは、所有者が自分の属するグループへなら chgrp や chown :グループ で変えられる
  • スクリプトは実行した人の PATH のコピーで動く。先頭で PATH=/usr/bin:/bin と決めると、使う人に左右されない
