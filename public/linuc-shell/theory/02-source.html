2. 子のシェルは、親を書き換えられない

~/.bashrc に alias を1行足し、bash ~/.bashrc で読み直そうとした。エラーが出て、alias も増えない。bash ファイル は「新しい bash を起動してファイルを読ませ、終わらせる」コマンドだからである。新しい bash は親の環境変数のコピーを受け取って始まり、終わるときに何も書き戻さない。いまのシェル自身に読ませるのが source（.）である。

前提: 第1章まで読了所要 18分影響度 A出題範囲 1.06.1（重要度4）最終検証 2026-10-13

この章のゴール

  • source ファイル・. ファイル・bash ファイル の違いを、どのシェルが読むかで説明できる
  • シェル変数と環境変数を export で作り分け、どちらが子に渡るかを言える
  • PATH の足し方と、足した PATH が効く範囲を言える
  • alias が子のシェルに渡らず、bash のスクリプトでは既定で展開されない理由と、だから ~/.bashrc に書くことを説明できる
ここで覚えなくていいこと: declare の全オプション、set と env が出す一覧の中身、hash（コマンドの在りかの記憶）、readonly、export -f（関数を子に渡す bash 独自の機能）。覚えるのは source・.・export・alias・unalias・PATH の6つでよい。

~/.bashrc を直しても、いまのシェルは変わらない

この節で分かること: 設定ファイルを書き換えたあと、なぜ読み直しが要り、なぜ bash では読み直せないのか。

この章は ~/try で作業する。

$ mkdir -p ~/try && cd ~/try

alias を1つ ~/.bashrc の末尾に足す。alias 名前='コマンド' は「この名前を打ったら、このコマンドに置き換える」という定義である。

ふつうこう考える

ファイルに書いただけではまだ効かない。~/.bashrc はシェルが起動するときに読むファイルなのだから、bash にもう一度読ませれば効くはずだ。

$ echo "alias hi='echo やあ'" >> ~/.bashrc
$ tail -1 ~/.bashrc
alias hi='echo やあ'
$ hi
bash: hi: command not found
$ bash ~/.bashrc
/home/lab/.bashrc: line 8: return: can only `return' from a function or sourced script
$ hi
bash: hi: command not found
だめな理由: bash ~/.bashrc は「新しい bash（子のプロセス）を起動し、そのファイルを読ませる」コマンドである。 いまのシェルは何も読んでいない。読んだのは子で、子は読み終わるとすぐ終わる。 この子は対話シェルではないので、~/.bashrc の8行目（第1章で見た「対話でなければ戻る」の return）を実行する。 関数の外の return なのでエラーを出すが、bash はそこで止まらずに最後まで読む。末尾の alias hi も子の中では定義されたが、子が終わると一緒に消えた。 読み直しは、いまのシェル自身にさせる必要がある。

子が最後まで読んだことは、~/.bashrc の写しの末尾に alias hi（定義を表示するコマンド）を足して読ませると確かめられる。

$ cp ~/.bashrc /tmp/bashrc.copy; echo 'alias hi' >> /tmp/bashrc.copy
$ bash /tmp/bashrc.copy; echo "終了ステータス $?"
/tmp/bashrc.copy: line 8: return: can only `return' from a function or sourced script
alias hi='echo やあ'
終了ステータス 0
$ hi
bash: hi: command not found

エラーの行の後に hi の定義が表示された。子は8行目を越えて末尾まで読み、alias を定義していた。それでも、子が終わった後のあなたのシェルに hi は無い。

いまのシェルに読ませるのが source である。

$ source ~/.bashrc
$ hi
やあ
$ type hi
hi is aliased to `echo やあ'
たとえ: 料理の手順書を書き直したあと、新人に読ませて帰らせるのが bash ~/.bashrc、自分で読むのが source ~/.bashrc である。 新人がどれだけ正しく覚えても、帰った時点でその記憶は店に残らない。
ただし崩れる点: 新人なら帰る前に口頭で伝えてくれるかもしれないが、子のシェルが親に返せるのは終了ステータスという数1つだけで、覚えた alias や変数を伝える手段そのものが無い。

子が受け取るのはコピー。それも export したものだけ

この節で分かること: シェル変数と環境変数の違いと、子に渡る範囲。

変数で確かめる。bash -c '…' は、引用符の中を新しい bash（子）に実行させる。

$ x=1
$ bash -c 'echo "子から見た x=[$x]"'
子から見た x=[]
$ export x
$ bash -c 'echo "子から見た x=[$x]"'
子から見た x=[1]
$ bash -c 'x=2; echo "子の中で x=$x"'; echo "親の x=$x"
子の中で x=2
親の x=1
$ declare -p x PATH
declare -x x="1"
declare -x PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
$ y=2; declare -p y
declare -- y="2"
$ env | grep -E '^(x|y)='
x=1

x=1 と書いただけの変数は、子からは見えない。export x したあとは見える。子の中で x=2 にしても、親の x は 1 のままである。

declare -p は変数の性質を見せる。-x が付いていれば環境変数（子にコピーが渡る）、-- ならシェル変数（このシェルの中だけ）である。env は環境変数だけを一覧するので、y は出てこない。

作り方子のシェル・スクリプトから確かめ方
シェル変数y=2見えないdeclare -p y が declare --
環境変数export x（export x=1 でもよい）コピーが見える。子が変えても親は変わらないdeclare -p x が declare -x・env に出る

export 名前=値 と書けば、作るのと印を付けるのを一度にできる。

$ export z=3; bash -c 'echo "z=[$z]"'
z=[3]

PATH は最初から declare -x、つまり環境変数である。だから PATH=… と値を変えるだけで子に渡り、改めて export する必要はない。

スクリプトの中でディレクトリを移ったり環境変数を作ったりしても、同じことが起きる。

$ cat > go.sh <<'END'
> cd /tmp
> export GREETING=やあ
> END
$ bash go.sh; pwd; echo "GREETING=[$GREETING]"
/home/lab/try
GREETING=[]
$ . ./go.sh; pwd; echo "GREETING=[$GREETING]"
/tmp
GREETING=[やあ]
$ cd ~/try

bash go.sh では、cd も export も子の中で起きて消えた。. ./go.sh では、いまのシェルが読んだので両方が残った。第1章で ~/.bash_profile の中に . ~/.profile と書いたのは、このためである。読み込まれたファイルが作った PATH を、ログインシェル自身に残す必要があった。

そして、ログインシェルで一度作った環境変数は、そこから起動されるすべての子にコピーされていく。PATH を ~/.profile（ログインのときに1回だけ読まれる）に書けば足りるのはこのためである。第1章で sudo -iu alice の案内に lab-base と出たのは逆の例で、sudo -i はコピーを渡す前に環境変数をほぼ空にするので、あなたの LAB_THEME が alice に届かなかった。

たとえ: 親が子に書類のコピーを持たせて送り出すのに近い。 export は「この書類はコピーして持たせる」という印で、印の無い書類（シェル変数）は親の机に残る。子はコピーに書き込めるが、親の原本は変わらない。
ただし崩れる点: 書類なら後から追加で送れるが、環境変数のコピーは子が起動する瞬間に1回作られるだけである。子が動き出した後に親が export しても、その子には届かない。

source と . は同じもの。sh で使えるのは . だけ

この節で分かること: 2つの書き方の違い。
$ type source .
source is a shell builtin
. is a shell builtin
$ sh -c '. ./go.sh; pwd'
/tmp
$ sh -c 'source ./go.sh'
sh: 1: source: not found

source と . は、どちらも組み込みコマンド（bash 自身が持っている命令）で、bash では同じ働きをする。ただし . は sh の規格にある書き方で、source は bash が足した別名である。Ubuntu の sh（dash）は . しか知らない。#!/bin/sh で書くスクリプトの中では . を使う。

alias は、コピーすらされない

この節で分かること: alias を ~/.bashrc に書く理由。
$ alias yo='echo よう'
$ yo
よう
$ bash -ic yo
bash: yo: command not found
$ bash -ic hi
やあ
$ printf '#!/bin/bash\nhi\n' > usehi.sh
$ bash usehi.sh; echo "終了ステータス $?"
usehi.sh: line 2: hi: command not found
終了ステータス 127
$ alias ll
alias ll='ls -alF'
$ type ll
ll is aliased to `ls -alF'
$ unalias yo
$ yo
bash: yo: command not found

プロンプトで定義した yo は、bash -ic（対話シェルとして子を起動する）からは見えない。エイリアスは環境変数ではないので、子にコピーされない。一方 hi は見えている。子が自分で ~/.bashrc を読み直して、自分で定義したからである。

スクリプトの中では、~/.bashrc に書いた hi すら使えない。スクリプトを読む bash は対話シェルではないので ~/.bashrc を読まず、しかも既定では alias の置き換えをしない。終了ステータス 127 は「コマンドが見つからない」である（第6章）。置き換えをするかどうかは shopt の expand_aliases が決めていて、bash では対話シェルのときだけ on になっている。

$ bash -c 'shopt expand_aliases'
expand_aliases 	off
$ bash -ic 'shopt expand_aliases'
expand_aliases 	on

「既定では」と書いたのは、変えられるからである。スクリプトの中で定義した alias を、bash は既定どおり置き換えないが、先に shopt -s expand_aliases と書けば置き換える。sh（dash）や bash --posix は、非対話でも置き換える。

$ printf 'alias hi3="echo alias が展開された"\nhi3\n' > a.sh
$ bash a.sh; echo "終了ステータス $?"
a.sh: line 2: hi3: command not found
終了ステータス 127
$ printf 'shopt -s expand_aliases\nalias hi3="echo alias が展開された"\nhi3\n' > a2.sh
$ bash a2.sh
alias が展開された
$ sh a.sh
alias が展開された
$ bash --posix a.sh
alias が展開された

どの場合も、スクリプトの外（あなたの ~/.bashrc やプロンプト）で定義した alias はスクリプトに届かない。届かないこと（子に渡らない）と置き換えないこと（expand_aliases）は、別々の理由である。

alias を消さずに、そのときだけ元のコマンドを使うには、名前の前に \ を付ける。前に command を付けても、フルパスで書いても alias は使われない。unalias は定義そのものを消す。

$ alias ls='ls -l'
$ ls -d /etc
drwxr-xr-x 1 root root 4096 Oct 13 19:18 /etc
$ \ls -d /etc
/etc
$ command ls -d /etc
/etc
$ /usr/bin/ls -d /etc
/etc
$ unalias ls
$ alias ls
bash: alias: ls: not found

alias ls='ls -l' は、Ubuntu の ~/.bashrc が作っていた ls --color=auto の定義を上書きし、unalias ls はその定義を消した。どちらも新しく開いた対話シェルでは ~/.bashrc から元に戻る。

alias も変数の代入も、= の前後に空白を入れない。反対に [ ] の中で比べる = には空白が要る（第6章）。

$ alias ll = 'ls -l'; echo "終了ステータス $?"
alias ll='ls -alF'
bash: alias: =: not found
bash: alias: ls -l: not found
終了ステータス 1
$ x = 1
bash: x: command not found
$ x=no; [ "$x"="yes" ] && echo "空白が無いと、いつも真"
空白が無いと、いつも真
$ [ "$x" = "yes" ] || echo "空白があれば、正しく偽"
空白があれば、正しく偽
書き方= の前後逆にすると
alias ll='ls -l'空白を入れないalias ll = 'ls -l' は ll・=・ls -l の3つを別々に調べ、= と ls -l は not found（終了ステータス 1）
x=1（代入）空白を入れないx = 1 は x という名前のコマンドを探して command not found
[ "$x" = "yes" ]（比べる）空白を入れる[ "$x"="yes" ] は1つの長い文字列になり、空でないのでいつも真

ここで第1章の2つのファイルの役割がつながる。

書くもの子に渡るか書く場所理由
環境変数（PATH・EDITOR など）コピーが渡る~/.profile（ログイン時に1回）1回作れば、以後のすべての子に渡る
alias・シェル変数・シェルの設定渡らない~/.bashrc（対話シェルごと）渡らないので、対話シェルが起動するたびに作り直す

alias は ~/.bashrc 以外にも書ける。/etc/profile に書けば、ログインシェルで定義される。ただしログインしない子のシェルには渡らないので、全員の対話シェルで使わせたいなら、どの対話シェルも読む /etc/bash.bashrc（Debian 系）に書くのがふつうである。

$ echo "alias zz='echo /etc/profile で定義した alias'" | sudo tee -a /etc/profile
alias zz='echo /etc/profile で定義した alias'
$ bash -l -c 'alias zz'
alias zz='echo /etc/profile で定義した alias'
$ bash -c 'alias zz'
bash: line 1: alias: zz: not found
$ sudo sed -i '/^alias zz=/d' /etc/profile; tail -1 /etc/profile
fi

試験の例題の解説に「/etc/profile には alias を書けない」とあることがあるが、記録のとおり書ける。問われているのは「どのシェルで定義されるか」で、ログインシェルなら定義され、ログインしないシェルでは定義されない。

~/.bashrc に書くものは alias だけではない。プロンプトの形を決める PS1 や、覚えておく履歴の件数を決める HISTSIZE のようなシェル変数も、Ubuntu ではここで決めている（履歴の仕組みそのものは主題1.03 の第2章で扱う）。試験に出るのは HISTSIZE=0 と書いたときで、履歴を1件も覚えず、終わるときに履歴ファイルにも何も書かない。

HISTSIZE=0 の子のシェルでは history が何も出さず、抜けた後も履歴ファイルが作られていない。その行を消してから開いた子のシェルでは、打った2行がファイルに残った。HISTFILE=… は、この実験のために履歴ファイルの置き場所だけを変える指定である。

たとえ: alias は自分の手帳に書いた略語表に近い。「ll と書いたら ls -alF のこと」と自分だけが知っている。 同じ部屋の別の人（子のシェル）は、同じ手帳を自分で持ってこない限り読めない。
ただし崩れる点: 人なら略語を見て意味を推測できるが、bash は手帳に無い略語を一切推測しない。command not found で止まる。

PATH は、左から順に探す棚の並び

この節で分かること: コマンドサーチパスの足し方と、足した PATH が効く範囲。
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ type ls cd
ls is aliased to `ls --color=auto'
cd is a shell builtin

名前だけで打ったコマンドは、まず alias が置き換えられ、次に関数（第8章）、組み込みコマンドの順に調べられる。どれでもなければ PATH に : 区切りで並んだディレクトリを左から順に探す。これがコマンドサーチパスで、最初に見つかったものが実行される。type を使うと、どれに当たったかが分かる（ls は Ubuntu の ~/.bashrc が作った alias だった）。関数 → 組み込み → PATH の順は、man にこう書いてある（alias はそれより前に置き換えられる）。

$ MANWIDTH=80 man bash | grep -A10 'If the command name contains no slashes'

       a match is found, that builtin is invoked.

type -a は、当たる候補を探す順に全部出す。echo は組み込みが先なので、/usr/bin/echo は使われない。

$ type -a echo

カレントディレクトリは PATH に入っていない。

~/bin を作っただけでは見つからない。~/.profile の判定はログインしたその瞬間に1回行われただけで、そのとき ~/bin はまだ無かった。. ~/.profile で読み直させると、先頭に /home/lab/bin が付いた。

手で足すなら、こう書く。

$ PATH="$PATH:$HOME/try"; echo $PATH
/home/lab/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/home/lab/try
書き方意味

こうして手で足した PATH は、このシェルと、ここから起動する子にしか効かない。次のログインでは消える。ずっと効かせるには、ログインのときに読まれるファイル（Ubuntu なら ~/.profile）に書く。第1章のとおり、~/.bash_profile を新しく作ると ~/.profile が読まれなくなる点に注意する。

たとえ: 倉庫の棚を端から順に見ていく係に近い。棚の並び順（PATH）が係に渡された唯一の地図で、同じ名前の箱が2つの棚にあれば、先に見た棚のものを持ってくる。
ただし崩れる点: 人の係は「この棚、さっき増えたよね」と気づくことがあるが、シェルは地図を書き換えてもらわない限り、新しく作った棚（~/bin）を見に行かない。

(A) history は打ったコマンドを表示する　(B) history は何も表示せず、終わったあと履歴ファイルにも書かれない　(C) history は何も表示しないが、履歴ファイルには書かれる

答え

(B)。HISTSIZE は覚えておく件数で、0 なら1件も覚えない。覚えていないものは、終わるときにファイルへ書く分も無い（記録では履歴ファイルが作られなかった）。

確認

set.sh の中身は export GREETING=hello の1行だけである。bash set.sh を実行した直後に、元のシェルで echo "[$GREETING]" と打つと何が出るか。

答え

[]（空）。export は子のシェルの中で起き、子が終わると消えた。export は「自分の子へコピーを渡す」印であって、親へ送り返す手段ではない。 . set.sh か source set.sh で実行すれば [hello] になる。

確認

コマンドサーチパスの末尾に /opt/tools/bin を追加する書き方として正しいものはどれか。
(A) PATH=/opt/tools/bin　(B) PATH="$PATH:/opt/tools/bin"　(C) PATH="$PATH;/opt/tools/bin"　(D) $PATH=$PATH:/opt/tools/bin

答え

(B)。export PATH="$PATH:/opt/tools/bin" と書いても同じ意味になる。 (A) は既存のディレクトリを全部消してしまう。(C) は区切りが ; なので、最後の要素が /bin;/opt/tools/bin という1つの（存在しない）ディレクトリ名になる。 (D) は左辺の $PATH が先に展開されて、代入ではなく長い名前のコマンドを実行しようとする。

$ (PATH="/usr/bin;/opt/tools/bin"; echo "$PATH"; ls /)
/usr/bin;/opt/tools/bin
bash: ls: command not found
$ $PATH=$PATH:/opt/tools/bin
bash: /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/opt/tools/bin: No such file or directory
確認

#!/bin/sh で始まるスクリプトの中で、別のファイル conf.sh の変数定義を読み込みたい。Ubuntu で確実に動く書き方はどれか。
(A) source conf.sh　(B) . ./conf.sh　(C) bash conf.sh

答え

(B)。Ubuntu の /bin/sh は dash で、source を持たない（記録: sh: 1: source: not found）。 (C) は子のプロセスが読むだけなので、変数は呼んだ側に残らない。

この章で分かったこと

持ち帰ってほしいこと

  • bash ファイル は子のプロセスに読ませる。source ファイル・. ファイル はいまのシェルに読ませる。設定の読み直しは後者
  • 子に渡るのは export した環境変数のコピーだけ。子が変えても親は変わらない
  • declare -p 名前 の -x が環境変数の印。env は環境変数だけを出す
  • alias は子に渡らない。bash のスクリプトでは既定で展開されない（shopt -s expand_aliases で有効になる。sh（dash）は展開する）。だから対話シェルごとに読まれる ~/.bashrc に書く
  • alias をそのときだけ避けるのは \ls・command ls・フルパス。unalias は定義ごと消す。alias ll='ls -l' も x=1 も = の前後に空白を入れない
  • ~/.bashrc の HISTSIZE=0 は、履歴を覚えずファイルにも書かない。プロンプトは PS1
  • PATH は : 区切りで左から探す。先頭に足すと優先、末尾に足すと後回し。手で足した PATH は次のログインで消える
  • source は bash の別名。sh（dash）で使えるのは . だけ
