理論編 — Docker

このサイトの実践編では、docker run … を打って檻を起動してもらっています。 その1行が何をしているのかを、練習機（仮想マシン）の中に入れた本物の docker で確かめる7章。 コンテナのプロセスを練習機の ps で見つけ、イメージを tar に書き出して指紋を計算し、公開したポートの宛先の書き換えを iptables の数えで見ます。

このページのコマンドは、あなたの画面に本文と同じ文字を出します。 出なければ教材のバグとして直します。 AI の回答は毎回違い、公式ドキュメントはあなたの環境を知りません。 ここにあるのは、誰かが実際に一度通した記録です。

この7章を貫いている1つの事実

docker は自分では何も閉じ込めない。練習機のカーネルに頼んで、1つのプロセスに「見え方の区切り」（名前空間）・「使える量の区切り」（cgroup）・ 「重ねたファイルの木」（overlay）を付けているだけで、コンテナの中身も力も、起動するときに渡したもの（ダイジェスト・ボリューム・ポート・特権）で決まる。

だから、コンテナを止めるのはプロセスへの合図で（第2章）、中身を決めるのはファイルの指紋で（第3章）、書き込みは重ねた1枚に入り（第4章）、 ポートの公開はカーネルの宛先の書き換えで（第5章）、コンテナの力は渡したケーパビリティと装置の分だけになる（第7章）。 docker run のオプションの多くは、この「何を渡すか」を決めるためにあります。

ここで覚えなくていいこと: docker の全サブコマンドとオプションの一覧、Compose・Swarm・Kubernetes、イメージのレジストリの運用（push・認証・署名）、 Docker Desktop の内部（Mac や Windows の上の Linux の仮想マシン）、Windows コンテナ。必要になったら、この7章の仕組みの上に足せます。

このサイトの檻は、docker をどう使っているか

実践編の起動コマンドのオプションを、1つずつこの記事の章で確かめられます。2つの型があります。

docker run --rm -it --name lab-… --hostname linuc \
  -v lab-…-work:/home/lab/work \
  -v lab-…-state:/home/lab/.lab \
  ghcr.io/chai0204/lab-linuc:…@sha256:…                 # コンテナ型（檻そのものがコンテナ）

docker run -d --name lab-… --hostname host --stop-timeout 30 \
  -v lab-…-vm:/home/lab/vm \
  -v lab-…-state:/home/lab/.lab \
  ghcr.io/chai0204/lab:…@sha256:…                       # 仮想マシン型（コンテナの中で QEMU が練習機を動かす）
docker exec -it lab-… bash -l
オプション意味なぜこのサイトはそう書くか確かめる章
--rmコンテナが終わったら、コンテナ（書き込み用の層）を消すコンテナ型は終わるたびに作り直してよい。残したいもの（作業・進捗）はボリュームに置いてある4
-it-i 標準入力をつなぐ・-t 端末を割り当てる（TERM も渡る）コンテナ型は PID 1 のシェルにそのまま入る。端末があると TERM=xterm になり、本文と同じ表示になる2
-d と docker exec -it … bash -l裏で動かし、後から別のプロセスとして入る仮想マシン型は練習機を動かし続ける。入るシェルは exec で足す（PID 1 の子ではなく shim の子）1・2
--name lab-…コンテナに名前を付ける本文の docker exec・stop で同じ名前を使えるように1
--hostname linuc / hostuts の名前空間のホスト名を決める（付けないとコンテナ ID の先頭12文字）プロンプトと出力に出るホスト名を、全員でそろえる1
--stop-timeout 30docker stop が TERM の後 KILL まで待つ秒数（既定 10）TERM を受けた起動スクリプト（PID 1 の tini の子。--init の代わりにイメージが tini を PID 1 に置いている）が、練習機を正常に止めるのに十数秒かかる。10秒では電源を抜くのと同じになる2
-v lab-…:/home/lab/…名前付きボリューム（コンテナを作るときに空なら、イメージの中身とディレクトリの持ち主・権限が写される）イメージが用意した持ち主（lab）のまま書け、読者の PC のディレクトリに触れない。バインドマウントは使わない4
…@sha256:…名前とダイジェストの両方で指す（取るのはダイジェストのほう）半年後も、全員が同じ中身を取る3
（この2つの型が書かないもの）--privileged・--cap-add・--device・-p・バインドマウント特権・装置・ポート・ホストのファイルを渡す読者の PC に何も渡させない。仮想マシン型なら、中の root が何をしても読者の PC の特権を借りない。 例外は2つで、LinuC 1.09 は --cap-add SYS_ADMIN、KVM の記事は --device /dev/kvm と --group-add を渡し、どちらも何を渡したかを測って見せる5・7

この記事の檻も仮想マシン型で、練習機の中で dockerd を動かしています。コンテナの中で dockerd を動かすには --privileged が要りますが、 練習機（QEMU の完全エミュレーション）の中なら要りません。檻の作りは QEMU の記事、KVM を使わない理由は KVM の記事にあります。

章

  1. コンテナは、練習機の上で動く1つのプロセス — 中の PID 1 は sleep そのもので、カーネルは練習機のもの。docker CLI → dockerd → containerd → shim → runc（20分）
  2. コンテナの PID 1 は、合図を無視する — docker stop が10秒かかって 137 で終わる。docker exec の umask は containerd から来る（20分）
  3. イメージを決めるのは、名前ではなくダイジェスト — docker tag 1回で alpine:3.24.2 が BusyBox を起動する。ファイル名は中身の SHA-256（25分）
  4. コンテナの書き込みは、イメージの上の1枚に入る — 消したファイルは upperdir の whiteout になる。ボリュームには、空のときだけ中身が写る（27分）
  5. ポートの公開は、宛先の書き換え — INPUT で塞いでも外から届く。DNAT の後は INPUT を通らない（22分）
  6. ビルドのキャッシュは、変えた段から後ろを全部作り直す — スクリプトを1行直すと、関係の無い RUN まで作り直される（20分）
  7. 渡したものだけが、コンテナの力になる — 中の root は練習機の UID 0。CapEff で、渡した特権を数える（25分）

檻で再現できないもの

ものなぜ再現できないか代わりにしたこと
レジストリからの取得（docker pull）と送り出し（push） 取得の結果は読者のネットワークとレジストリの状態で変わる（取得の回数の制限もある）。練習機は Docker Hub に届かないようにしてあり（ほかのレジストリには届くが、本文では使わない）、使うイメージ2つはディスクに入れてある 第3章で、取りに行く操作が全員に同じ失敗を出すことと、取った中身の正体（指紋の束）を docker save で確かめた
Docker Desktop（Mac・Windows）の中の仮想マシン Docker Desktop は Linux の仮想マシンを1台隠し持ち、その中で dockerd を動かしている。中身は製品と版で違う この記事の練習機が、その「隠れた仮想マシン」の役を見える形でしている。第1章の uname -r の説明
あなたの PC の docker と同じ版・同じ設定 docker の版で既定値が変わる（イメージの置き場所が containerd か overlay2 か、docker images の表示、.NetworkSettings.IPAddress の有無）。containerd の umask も環境で違う 本文で、版によって変わる行にはそう書いた（第2・3・5章）。練習機の docker は Ubuntu の docker.io 29.1.3
