3. イメージを決めるのは、名前ではなくダイジェスト

alpine:3.24.2 という名前は、1コマンドで別のイメージに付け替えられる。名前を付け替えると、同じ docker run alpine:3.24.2 が 別の中身を起動する。イメージの正体は、中身から計算した指紋（ダイジェスト）で、イメージそのものは、その指紋を名前にした JSON と tar の束である。

前提: 第1章所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • タグ（alpine:3.24.2）とダイジェスト（sha256:…）の違いを、付け替えた結果で説明できる
  • イメージを docker save で書き出し、目録（index）→ 設計図（manifest）→ 設定（config）と層（layer）をたどれる
  • ファイル名の16進数が、そのファイルの中身の SHA-256 であることを、自分で計算して確かめられる
ここで覚えなくていいこと: OCI イメージ仕様の各項目、メディアタイプの一覧、来歴（attestation）の中身、 レジストリの API。この章で使うのは「中身の指紋をファイル名にして、指紋で次のファイルを指す」という1つの形だけである。

名前を付け替える

この節で分かること: 名前:タグ は中身ではなく、中身を指す札であること。

練習機に入っているイメージを、ダイジェスト付きで並べる。

$ docker images --digests
REPOSITORY   TAG       DIGEST                                                                    IMAGE ID       CREATED        SIZE
alpine       3.24.2    sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6   294b683cb724   3 weeks ago    13MB
busybox      1.38.0    sha256:fd7dc98638c8e305f4dc34e979f1c0fdfdcaeb0fbf8fcff77ae834b6da3d7e6e   fd7dc98638c8   5 months ago   6.81MB

行ごとに、名前（REPOSITORY と TAG）・ダイジェスト（DIGEST）・ID（IMAGE ID）がある。この docker（29.1.3。イメージの置き場所が containerd）では、 ID はダイジェストそのもので、一覧では先頭12文字に縮めて表示している。

ふつうこう考える

alpine:3.24.2 と書けば、中身は Alpine 3.24.2 に決まっている。バージョン番号まで書いたのだから、誰がいつ起動しても同じものが動くはずだ。

$ docker run --rm alpine:3.24.2 cat /etc/alpine-release
3.24.2
$ docker tag busybox:1.38.0 alpine:3.24.2
$ docker run --rm alpine:3.24.2 cat /etc/alpine-release
cat: can't open '/etc/alpine-release': No such file or directory
$ docker images --digests alpine
REPOSITORY   TAG       DIGEST                                                                    IMAGE ID       CREATED        SIZE
alpine       3.24.2    sha256:fd7dc98638c8e305f4dc34e979f1c0fdfdcaeb0fbf8fcff77ae834b6da3d7e6e   fd7dc98638c8   5 months ago   6.81MB
だめな理由: docker tag を1回打っただけで、同じ docker run --rm alpine:3.24.2 が BusyBox の中身を起動し、 /etc/alpine-release が無いと言われた。alpine:3.24.2 の行の DIGEST と IMAGE ID は、節の最初の一覧の busybox の行と同じ（sha256:fd7dc986… と fd7dc98638c8）になった（docker images の後ろに名前を書くと、その名前の行だけが出る）。 タグは中身を指す札にすぎず、いつでも別の中身に付け替えられる。手元で誰かが付け替えなくても、レジストリの上でも同じことが起きる （alpine:3.24 は 3.24.3 が出れば付け替えられる。3.24.2 のような細かい番号のタグでも、付け替えないという約束は無い。変わらないと約束されているのはダイジェストだけである）。

では元の Alpine はどこへ行ったか。消えてはいない。名前が付いていないだけである。

$ docker images -a
                                                            i Info →   U  In Use
IMAGE            ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:3.24.2    fd7dc98638c8       6.81MB         2.23MB
busybox:1.38.0   fd7dc98638c8       6.81MB         2.23MB
<untagged>       294b683cb724         13MB         3.94MB
$ docker run --rm alpine@sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6 cat /etc/alpine-release

$ docker run --rm 294b683cb724 cat /etc/alpine-release
3.24.2

-a を付けると、名前の無いイメージ（<untagged>）として ID 294b683cb724 が見えた。 ダイジェストで alpine@sha256:294b… と指すと、docker は手元に「その名前（alpine）でそのダイジェスト」のものが無いので取りに行こうとし、失敗した （この練習機は Docker Hub に届かないようにしてある。あなたの PC なら、Docker Hub からこのダイジェストの目録を取り、そこから自分の CPU の種類の中身をたどる。 CPU の種類が同じ（この練習機と同じ amd64）なら、取れれば必ず同じ中身になる。目録は CPU の種類ごとの設計図の一覧なので、arm64 の PC は同じ 294b… から別の中身をたどる。次の節で中を見る）。 ID で指せば、手元の名前の無いイメージがそのまま動いた。元に戻す。

たとえ: 名前を付け替えられたイメージは、ラベルを別の瓶に貼り替えられた保存瓶に近い。「梅干し」のラベルが別の瓶に移っても、元の瓶の中身は棚に残っている。 ラベルの無い瓶は、棚の番号（ID）で呼べば取り出せる。
ただし崩れる点: 保存瓶なら中身を見れば梅干しだと分かるが、docker は中身を見て名前を推し量ったりしない。この docker では、ラベル（タグ）を剥がされたイメージは、ID で指さない限りたどれない（ダイジェスト付きの名前 alpine@sha256:… でも、手元では見つからなかった。 この docker は、手元のイメージを「その名前（alpine）が付いた記録」の中からしか探さない）。
$ docker tag 294b683cb724 alpine:3.24.2
$ docker images --digests
REPOSITORY   TAG       DIGEST                                                                    IMAGE ID       CREATED        SIZE
alpine       3.24.2    sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6   294b683cb724   3 weeks ago    13MB
busybox      1.38.0    sha256:fd7dc98638c8e305f4dc34e979f1c0fdfdcaeb0fbf8fcff77ae834b6da3d7e6e   fd7dc98638c8   5 months ago   6.81MB

このサイトの実践編の起動コマンドが、イメージを ghcr.io/chai0204/lab:…-1.0.0@sha256:… と名前とダイジェストの両方で書いているのはこのためである。 名前は人が読むため、ダイジェストは中身を1つに決めるため。両方書くと、docker はダイジェストのほうで取る（名前のタグは無視する）。

たとえ: タグは本棚の見出し札、ダイジェストは本の ISBN と中身全体の指紋を合わせたものに近い。 見出し札「3.24.2」は、誰かが別の本の前に差し替えれば、その本を指す。指紋は本の中身から計算するので、中身が1文字でも違えば変わる。
ただし崩れる点: ISBN は出版社が割り当てる番号だが、ダイジェストは誰も割り当てない。中身から誰でも同じ計算で出せる値で、 だから手元で計算し直して確かめられる（次の節でやる）。

この節で分かること: イメージが「JSON のファイルと tar のファイルの束」であること。

amd64 の設計図（manifest）は、設定（config）1つと層（layers）1つを、大きさとダイジェストで指している。 設定（config）には、起動するコマンド（Cmd）と、層の一覧が書かれている。Alpine のイメージは層が1枚だけである。

ファイル名は、中身の指紋

この節で分かること: ダイジェストを自分で計算して確かめる方法と、層の指紋が2種類あること。
$ sha256sum blobs/sha256/e2de*
e2de96513ba9eb53b431787ec8a65cdde380ac4772a3e4c4b714dcfde2a102b5  blobs/sha256/e2de96513ba9eb53b431787ec8a65cdde380ac4772a3e4c4b714dcfde2a102b5
$ file blobs/sha256/e2de*
blobs/sha256/e2de96513ba9eb53b431787ec8a65cdde380ac4772a3e4c4b714dcfde2a102b5: gzip compressed data, original size modulo 2^32 8704000
$ gunzip -c blobs/sha256/e2de* | sha256sum
74d97c428c51a828f9051a7a40a53ff1fc99e54fc30323ce36760701b0b7f711  -
$ tar tzf blobs/sha256/e2de* | head -5
bin/
bin/arch
bin/ash
bin/base64
bin/bbconfig
$ docker image inspect alpine:3.24.2 --format '{{json .RootFS.Layers}}'
["sha256:74d97c428c51a828f9051a7a40a53ff1fc99e54fc30323ce36760701b0b7f711"]

層のファイルの SHA-256 を計算すると、ファイル名と同じ値が出た。名前が中身の指紋なので、受け取った側は計算し直すだけで、途中で1バイトも変わっていないことを確かめられる。 docker もレジストリから取るたびに同じ計算をしている。設計図が層をこの値で指し、目録が設計図を、タグを付ける前の名前（@sha256:）が目録を指すので、 いちばん上のダイジェスト1つが決まれば、CPU の種類ごとに、下のファイルは全部1つに決まる。

層には指紋が2つある。gzip で圧縮したファイルの指紋（ブロブの名前 e2de9651…。転送と保存に使う）と、 展開した tar の指紋（74d97c42…。設定の diff_ids と docker image inspect の Layers に出るもの。ファイルの並びの正体を表す）である。 展開すると、中身は Alpine のディレクトリの木（bin/・etc/…）を入れた、普通の tar だった。

たとえ: イメージの束は、中身の指紋を背表紙に書いた本の、目次の目次に近い。目録が設計図の背表紙を、設計図が設定と層の背表紙を書いている。 いちばん外の目録の指紋を1つ控えておけば、届いた本が全部本物かを、背表紙と中身を見比べるだけで確かめられる。
ただし崩れる点: 本なら背表紙の文字を書き換えれば偽物を作れるが、指紋は中身から計算し直せるので、背表紙（ファイル名）を書き換えても計算が合わなくなって見破られる。 守れないのは、いちばん外の指紋を最初にどこから知ったか（書いてある場所が信用できるか）だけである。

作業用のディレクトリを片付ける。tar tvf の一覧のとおり、ブロブは読むだけの権限（-r--r--r--）で書き出されるので、 rm -r だけだと1つずつ「書き込み禁止のファイルを消してよいか」と聞かれる。-f を付けて、聞かずに消す。

$ cd
$ rm -rf ~/img
手を動かす: 実践編の演習03で、別の中身に付け替えられた名前を、ダイジェストを手がかりに元の中身へ戻す。
確認

docker images --digests alpine で、alpine の行の DIGEST と IMAGE ID が、busybox の行と同じだった。この出力から何が言えるか。

答え

その名前（alpine:3.24.2）は、busybox と同じ中身に付いた札である。ダイジェストは中身から計算した指紋なので、ダイジェストが同じなら中身は1つしかない。 名前が alpine でも、中で動くのは BusyBox である。名前と中身の対応は手元でいくらでも変わるので、中身を確かめるには名前ではなくダイジェストを見る。

確認

同じ alpine:3.24.2 を起動したのに、Aさんと Bさんで動きが違った。中身が同じかどうかを、どのコマンドの何で確かめればよいか。

答え

docker images --digests の DIGEST と、CPU の種類（docker image inspect alpine:3.24.2 --format '{{.Os}}/{{.Architecture}}'）を比べる。 目録のダイジェストと CPU の種類が両方同じなら中身は同じで、違いは起動のしかた（環境・ボリューム・オプション）にある。 ID（.Id）は、docker の版とイメージの置き場所の設定で、目録のダイジェストだったり設定の指紋だったりするので、PC の間で比べる値には使わない。 ダイジェストが違えば、名前が別の中身に付いている。それ以降は alpine:3.24.2@sha256:… のようにダイジェストまで書いて起動すれば、中身が1つに決まる。

確認

層のブロブのファイル名と sha256sum の結果は一致したが、docker image inspect の Layers の値とは違った。どちらかが壊れているのか。

答え

壊れていない。ファイル名は圧縮した tar の指紋、Layers（diff_ids）は展開した tar の指紋で、同じ層を別の形で測っている。 gunzip -c … | sha256sum が diff_ids と一致したことで、両方が同じ層を指していると確かめられた。

この章で分かったこと

持ち帰ってほしいこと

  • 名前:タグ は中身を指す札で、手元でもレジストリでも付け替えられる。中身を1つに決めるのはダイジェスト（目録のダイジェストなら、CPU の種類ごとに1つ）
  • イメージは、中身の SHA-256 を名前にした JSON と tar の束である。目録 → 設計図 → 設定と層、とダイジェストでたどれる
  • ダイジェストは誰でも計算し直せるので、受け取った中身が変わっていないことを確かめられる
  • 層には、圧縮したものの指紋（転送・保存用）と、展開した tar の指紋（diff_ids）の2つがある
