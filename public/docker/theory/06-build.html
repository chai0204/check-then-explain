6. ビルドのキャッシュは、変えた段から後ろを全部作り直す

Dockerfile の1行は、イメージの層1枚（か設定1項目）になる。docker build は段ごとに「前と同じ材料か」を調べ、同じなら前回の層を使う（キャッシュ）。 材料にはそれより前の段が作った層も入るので、1つの段が変わると、そこから後ろの段は命令が同じでも全部作り直しになる。

前提: 第3章（イメージは層でできている）所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • Dockerfile の各行が、イメージの層や設定になることを docker history で示せる
  • キャッシュが効かなくなる条件を、作り直された段で説明できる
  • よく変わるものを後ろに置く並べ方で、ビルドの時間が変わることを示せる
ここで覚えなくていいこと: Dockerfile の全命令（ARG・ENTRYPOINT・HEALTHCHECK など）、マルチステージビルド、 BuildKit のキャッシュの持ち出し（--cache-to）、来歴（attestation）の中身、.dockerignore の書き方。

Dockerfile を書いて、ビルドする

この節で分かること: docker build が Dockerfile を段ごとに実行していること。

作業用のディレクトリに、起動すると1行出す小さなスクリプトと、Dockerfile を置く。Dockerfile は cat とヒアドキュメント（<<'EOF' から EOF まで）で書く。 RUN の段の sleep 10 は、パッケージのインストールのような「時間のかかる準備」の代わりである。

$ mkdir ~/app
$ cd ~/app
$ echo 'echo "app v1"' > app.sh
$ cat > Dockerfile <<'EOF'
> FROM alpine:3.24.2
> COPY app.sh /app/app.sh
> RUN sleep 10 && echo "dependencies installed" > /app/deps.txt
> CMD ["sh", "/app/app.sh"]
> EOF
$ time docker build --progress=plain -t app:1 .
...
#6 [2/3] COPY app.sh /app/app.sh
#6 DONE 0.2s
...
#7 [3/3] RUN sleep 10 && echo "dependencies installed" > /app/deps.txt
#7 DONE 11.6s
...
real	0m18.832s
...
$ docker run --rm app:1
app v1

--progress=plain は、進み具合を1行ずつ書き足す表示にする指定である（付けないと、端末の上で同じ行を書き換えながら進む表示になる。中身は同じ）。 出力は長いので、本文では COPY と RUN の段の見出し（[2/3]・[3/3]）と、その段の終わりの行（実行したら DONE と秒数、前回のものを使ったら CACHED）、全体にかかった時間（real）の行だけを抜き出している（#6 などは段の通し番号）。 3つの段（FROM・COPY・RUN）が順に実行され、RUN の段で10秒あまりかかった。もう一度、何も変えずにビルドする。

$ time docker build --progress=plain -t app:1 .
...
#6 [2/3] COPY app.sh /app/app.sh
#6 CACHED
...
#7 [3/3] RUN sleep 10 && echo "dependencies installed" > /app/deps.txt
#7 CACHED
...
real	0m3.692s
...

今度は COPY も RUN も CACHED で、すぐに終わった。材料が前回と同じなので、前回できた層をそのまま使ったのである。

たとえ: ビルドのキャッシュは、料理の作り置きに近い。同じレシピの同じ手順を、同じ下ごしらえの上でもう一度やるなら、冷蔵庫の作り置きを出せば済む。
ただし崩れる点: 人なら作り置きの味見をして「まだ使える」と判断するが、docker は中身を確かめない。命令の文字と、前の段の層と、COPY するファイルの中身の指紋が同じかどうかだけで決める。 RUN がネットから取ってくる内容が変わっていても、命令の文字が同じなら作り置き（古い結果）を出してくる。

1行直すと、どこまで作り直すか

この節で分かること: キャッシュが効かなくなる範囲。

ふつうこう考える

app.sh を1行直しただけだ。変わったのは app.sh を写す COPY の段だけなので、作り直すのはその段だけで、 app.sh と関係の無い RUN の段（10秒かかる準備）は前回のものが使われるはずだ。

$ echo 'echo "app v2"' > app.sh
$ time docker build --progress=plain -t app:2 .
...
#6 [2/3] COPY app.sh /app/app.sh
#6 DONE 0.2s
...
#7 [3/3] RUN sleep 10 && echo "dependencies installed" > /app/deps.txt
#7 DONE 11.6s
...
real	0m15.827s
...
だめな理由: COPY だけでなく RUN も作り直され、また10秒あまりかかった。 ある段のキャッシュの材料には、その段の命令と、それより前の段が作った層の中身が入る。COPY の層が変われば、その上で実行する RUN は 「違う土台の上での実行」になるので、命令が同じでもキャッシュは使えない。1つの段が変わると、そこから後ろ（Dockerfile の下の行）は全部作り直しになる。
たとえ: Dockerfile の段は積み木の塔に近い。下の1段を差し替えたら、その上の段は同じ形の積み木でも、一度下ろして積み直すしかない。
ただし崩れる点: 積み木なら上の段をそのまま持ち上げて載せ替えられるが、ビルドの段は「下の段の上で実行した結果」なので載せ替えられない。 RUN の結果は、下の層の中身によって変わりうるからである（docker は中身を見て判断せず、下が変わったら必ず作り直す）。

よく変わるものを、後ろに置く

この節で分かること: 段の並べ方で、キャッシュの効く範囲が変わること。

時間のかかる準備（RUN）を先に、よく直すもの（COPY app.sh）を後ろに並べ替える。RUN の段が /app を先に作るように mkdir /app を足す。

$ cat > Dockerfile <<'EOF'
> FROM alpine:3.24.2
> RUN mkdir /app && sleep 10 && echo "dependencies installed" > /app/deps.txt
> COPY app.sh /app/app.sh
> CMD ["sh", "/app/app.sh"]
> EOF
$ time docker build --progress=plain -t app:3 .
...
#6 [2/3] RUN mkdir /app && sleep 10 && echo "dependencies installed" > /app/deps.txt
#6 DONE 11.5s
...
#7 [3/3] COPY app.sh /app/app.sh
#7 DONE 0.3s
...
real	0m16.080s
...
$ echo 'echo "app v3"' > app.sh
$ time docker build --progress=plain -t app:4 .
...
#6 [2/3] RUN mkdir /app && sleep 10 && echo "dependencies installed" > /app/deps.txt
#6 CACHED
...
#7 [3/3] COPY app.sh /app/app.sh
#7 DONE 0.2s
...
real	0m3.958s
...
$ docker run --rm app:4
app v3

並べ替えた直後の1回（app:3）は、RUN の段の命令が変わったので作り直しになった。 その後で app.sh を直したビルド（app:4）では、RUN の段は CACHED で、作り直したのは後ろの COPY だけだった。 変わりやすいものを Dockerfile の後ろに置くと、変わらない準備の層を毎回使い回せる。

出来上がったイメージの層は、docker history で上（新しい段）から順に見られる。

$ docker history app:4
IMAGE          CREATED          CREATED BY                                      SIZE      COMMENT
c6435a09ce04   6 seconds ago    CMD ["sh" "/app/app.sh"]                        0B        buildkit.dockerfile.v0
<missing>      6 seconds ago    COPY app.sh /app/app.sh # buildkit              12.3kB    buildkit.dockerfile.v0
<missing>      12 seconds ago   RUN /bin/sh -c mkdir /app && sleep 10 && ech…   12.3kB    buildkit.dockerfile.v0
<missing>      3 weeks ago      CMD ["/bin/sh"]                                 0B        buildkit.dockerfile.v0
<missing>      3 weeks ago      ADD alpine-minirootfs-3.24.2-x86_64.tar.gz /…   9.08MB    buildkit.dockerfile.v0

上の3行が Dockerfile の CMD・COPY・RUN で、その下の2行は FROM で土台にした Alpine のイメージが作られたときの記録である。 CMD の行は大きさ 0B で、ファイルの層ではなく設定（第3章の config）に書かれる項目である。<missing> は「この段だけの ID は手元に無い」という意味で、層が欠けているわけではない。

たとえ: よく変わるものを後ろに置くのは、引っ越しの荷造りで、毎日使う物をいちばん上に詰めることに近い。 毎日の出し入れで、下の段ボールまで開け直さずに済む。
ただし崩れる点: 段ボールは中身を見れば上下を入れ替えられるが、Dockerfile では後ろの段が前の段の結果に頼ることがある（RUN が COPY したファイルを使う、など）。 その場合は並べ替えられないので、写すファイルを「準備に要る分」と「よく変わる分」に分けて、2回に分けて COPY する。

作業用のディレクトリとイメージを片付ける。

$ cd
$ rm -r ~/app
$ docker rmi app:1 app:2 app:3 app:4
Untagged: app:1
...
Untagged: app:2
...
Untagged: app:3
...
Untagged: app:4
...
手を動かす: 実践編の演習06で、渡された Dockerfile を並べ替えて、スクリプトを直しても時間のかかる段が作り直されないようにする。 判定は、実際にスクリプトを書き換えてビルドし、その段が CACHED になるかを見る。
確認

COPY . /src の次に RUN npm install を置いた Dockerfile がある。README を1文字直しただけで、npm install が毎回走る。なぜか。どう並べ替えればよいか。

答え

COPY . /src はディレクトリ全体を写すので、README が変わるとその段の層が変わり、上に積む RUN npm install のキャッシュも使えなくなる。 依存の一覧（package.json など）だけを先に COPY して RUN npm install、その後で残りを COPY すれば、依存の一覧が変わらない限り npm install の層を使い回せる。

確認

docker history で CMD の行の SIZE が 0B だった。この段はイメージの何を変えたのか。

答え

ファイルの層は作らず、イメージの設定（config）の Cmd の項目を変えた。起動するコマンドは、ファイルではなく設定の JSON に書かれている（第3章で jq で読んだ項目）。

この章で分かったこと

持ち帰ってほしいこと

  • Dockerfile の1行は、層1枚か設定1項目になる。docker history で上から順に見られる
  • 段のキャッシュは「命令」と「その下の層」が前回と同じときだけ使われる。1つの段が変わると、そこから後ろは全部作り直し
  • 時間のかかる準備を前に、よく変わるものを後ろに並べると、作り直しの範囲が小さくなる
