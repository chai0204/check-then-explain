9. LVM で、2台のディスクを1つにまとめる

第8章までで、区画を切り（第2〜4章）、ファイルシステムを作り（第5章）、マウントし（第6・7章）、スワップにも使った（第8章）。区画の大きさは、切ったときに決まったままだった。この章では、ディスクとファイルシステムのあいだに LVM という段を1つはさみ、空のディスク vdc と sda をまとめて1台より大きな箱を作り、使いながら広げる。

前提: 第8章まで読了前提: 練習機の中にいる所要 24分影響度 B出題範囲 1.05.2（重要度4）最終検証 2026-10-20

この章のゴール

  • 物理ボリューム・ボリュームグループ・論理ボリュームの関係を、作る順番（pvcreate → vgcreate → lvcreate）と一緒に説明できる
  • 論理ボリュームを広げたり縮めたりしたとき、中のファイルシステムがどうなるかを確かめ、必要な操作を言える（ext4 と XFS の違いも）
  • スナップショットを元より小さく作って使い、それが何を残しているのかを確かめる
ここで覚えなくていいこと: シンプロビジョニング（使った分だけ割り当てる LVM の使い方）は扱わない。複数のディスクに同じ中身を書いて壊れに備える論理ボリューム（RAID。--type raid1 など）と、pvmove によるデータの引っ越しも扱わない。LVM が自分の管理情報をどこにどう書くかも扱わない。

材料・池・箱の3段

この節で分かること: LVM を作る3つのコマンドと、それぞれが何を作るか。

LVM（Logical Volume Manager）は、ディスクとファイルシステムのあいだに1段はさむ仕組みである。材料にするのは、まだ使っていない vdc と sda（どちらも 1G）。

$ lsblk /dev/vdc /dev/sda
NAME
    MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS
sda   8:0    0   1G  0 disk
vdc 253:32   0   1G  0 disk
$ sudo pvcreate /dev/vdc /dev/sda
  Physical volume "/dev/vdc" successfully created.
  Physical volume "/dev/sda" successfully created.
$ sudo pvs
  PV         VG Fmt  Attr PSize PFree
  /dev/sda      lvm2 ---  1.00g 1.00g
  /dev/vdc      lvm2 ---  1.00g 1.00g

pvcreate は、ディスク（や区画）を LVM の材料にするコマンドで、材料になったものを物理ボリューム（PV）と呼ぶ。pvs は物理ボリュームの一覧で、PSize が大きさ、PFree が空きである。区画を切らずに、ディスク全体を材料にした。2つを1つにまとめる。

$ sudo vgcreate vg0 /dev/vdc /dev/sda
  Volume group "vg0" successfully created
$ sudo vgs
  VG  #PV #LV #SN Attr   VSize VFree
  vg0   2   0   0 wz--n- 1.99g 1.99g
$ sudo vgdisplay vg0
  --- Volume group ---
  VG Name               vg0
  System ID
  Format                lvm2
  Metadata Areas        2
  Metadata Sequence No  1
  VG Access             read/write
  VG Status             resizable
  MAX LV                0
  Cur LV                0
  Open LV               0
  Max PV                0
  Cur PV                2
  Act PV                2
  VG Size               1.99 GiB   ← 池の大きさ
  PE Size               4.00 MiB   ← 区切り1つの大きさ
  Total PE              510   ← 区切りの数
  Alloc PE / Size       0 / 0
  Free  PE / Size       510 / 1.99 GiB
  VG UUID               d70UwX-3E7x-2y4u-w6wo-pK9n-avfB-ccKd6b   ← 作るたびに変わる番号（あなたの画面では違う）

vgcreate は、物理ボリュームをまとめてボリュームグループ（VG）にするコマンドで、ここでは vg0 という名前にした。1G の2台で 1.99GiB の池ができている（管理情報の分だけ少し小さい）。vgdisplay は詳しい表示で、池の中は 4MiB ごとの区切り（物理エクステント、PE）で管理されていると分かる。池から論理ボリューム（LV）を切り出す。論理ボリュームは、パーティションの代わりに使う箱である。

$ sudo lvcreate -L 600M -n data vg0
  Logical volume "data" created.
$ sudo lvs
  LV   VG  Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  data vg0 -wi-a----- 600.00m
$ ls -l /dev/vg0/data /dev/mapper/vg0-data
lrwxrwxrwx 1 root root 7 Oct 20 21:02 /dev/mapper/vg0-data -> ../dm-0
lrwxrwxrwx 1 root root 7 Oct 20 21:02 /dev/vg0/data -> ../dm-0

lvcreate の -L は大きさ、-n は名前である。lvs は論理ボリュームの一覧で、LSize が大きさ。/dev/vg0/data と /dev/mapper/vg0-data は、どちらも /dev/dm-0 という同じ装置を指す別名（シンボリックリンク）である（dm は device mapper。LVM が論理ボリュームのために作る仮の装置）。論理ボリュームは、区画と同じように mkfs してマウントできる。

$ sudo mkfs.ext4 -q /dev/vg0/data
$ sudo mkdir /srv/data
$ sudo mount /dev/vg0/data /srv/data
$ df -h /srv/data
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/vg0-data  574M   24K  532M   1% /srv/data
/dev/vdc（1GiB）─┐                         ┌─ vg0/data（600MiB）─ ext4 ─ /srv/data
                 ├─ vg0（1.99GiB の池） ──┤
/dev/sda（1GiB）─┘   4MiB ごとの PE       └─ （空き）
  pvcreate             vgcreate              lvcreate          mkfs     mount
  物理ボリューム        ボリュームグループ      論理ボリューム
たとえ: バケツの水を池に空けて、そこから容器に汲み分けるのに近い。バケツ（ディスク）が何杯でも、池（VG）では区別せずに使え、容器（LV）は後から大きいものに替えられる。
ただし崩れる点: 池の水は混ざれば区別できないが、LVM は「どの LV が、どのディスクのどこを使っているか」を覚えている。だからディスクが1台壊れると、そこを使っていた LV は壊れる。LVM は、壊れに備えて写しを持つ仕組みではない。

箱を広げる

この節で分かること: 論理ボリュームを広げたら、中のファイルシステムで使える量はどうなるか。

lvextend は、論理ボリュームを広げるコマンドである。-L +800M は「いまより 800MiB 大きく」。

ふつうこう考える

LVM の売りは、使いながら容量を足せることだ。lvextend で 800MiB 足せば、/srv/data で使える量もその分増えるはずだ。

$ sudo lvextend -L +800M vg0/data
  Size of logical volume vg0/data changed from 600.00 MiB (150 extents) to <1.37 GiB (350 extents).
  Logical volume vg0/data successfully resized.
$ sudo lvs vg0/data
  LV   VG  Attr       LSize  Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  data vg0 -wi-ao---- <1.37g
$ df -h /srv/data
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/vg0-data  574M   24K  532M   1% /srv/data   ← 574M のまま
だめな理由: 論理ボリュームは 1.37GiB になったのに、df は 574M のままである。 lvextend が広げたのは箱（論理ボリューム）だけで、中の ext4 は、作ったときの大きさを自分の管理情報に書いている。 その数を書き換えるまで、ext4 は外側に空きが増えたことを使わない。ファイルシステムを広げるのは、別の道具である。
$ sudo resize2fs /dev/vg0/data
resize2fs 1.47.0 (5-Feb-2023)
Filesystem at /dev/vg0/data is mounted on /srv/data; on-line resizing required
old_desc_blocks = 1, new_desc_blocks = 1
The filesystem on /dev/vg0/data is now 358400 (4k) blocks long.
$ df -h /srv/data
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/vg0-data  1.4G   24K  1.3G   1% /srv/data

resize2fs は ext2・ext3・ext4 の大きさを変えるコマンドで、広げるだけならマウントしたままでよい（on-line resizing）。XFS では xfs_growfs を使う。lvextend に -r（--resizefs）を付けると、箱と中身を続けて広げる。

$ sudo lvs -o lv_name,lv_size,devices vg0
  LV   LSize  Devices
  data <1.37g /dev/vdc(0)
  data <1.37g /dev/sda(0)
$ sudo lvextend -r -L +200M vg0/data
  Size of logical volume vg0/data changed from <1.37 GiB (350 extents) to 1.56 GiB (400 extents).
  Logical volume vg0/data successfully resized.
resize2fs 1.47.0 (5-Feb-2023)
Filesystem at /dev/mapper/vg0-data is mounted on /srv/data; on-line resizing required
old_desc_blocks = 1, new_desc_blocks = 1
The filesystem on /dev/mapper/vg0-data is now 409600 (4k) blocks long.
$ df -h /srv/data
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/vg0-data  1.6G   24K  1.5G   1% /srv/data

lvs -o で列を選び、devices（使っている物理ボリューム）を出した。data は vdc と sda の2台にまたがっている。1台は 1GiB しかないのに、1.37GiB の箱ができている。ディスク1台より大きな箱を作れるのも LVM の特徴である。

たとえ: 本棚を大きいものに買い替えたのに、本の並べ方の目録（ファイルシステム）が前の棚の段数のままになっている状態に近い。棚は広いのに、目録に載っていない段には本を置かない。
ただし崩れる点: 人なら棚が広がったことに見れば気づくが、ファイルシステムは自分から外側を測り直さない。resize2fs で「棚はここまである」と書き直してもらう必要がある。

箱を縮める

この節で分かること: 縮めるときの順番と、縮められないファイルシステムがあること。

縮めるときは順番が逆になる。先に中身（ファイルシステム）を縮め、そのあとで箱を縮める。逆にすると、箱からはみ出した中身が壊れる。lvreduce（論理ボリュームを縮めるコマンド）に -r を付けると、この順番でやる。ext4 はマウントしたままでは縮められないので、先に外す。

$ sudo umount /srv/data
$ sudo lvreduce -r -L 1.2G vg0/data
  Rounding size to boundary between physical extents: 1.20 GiB.
fsck from util-linux 2.39.3
/dev/mapper/vg0-data: 11/99840 files (0.0% non-contiguous), 10824/409600 blocks
resize2fs 1.47.0 (5-Feb-2023)
Resizing the filesystem on /dev/mapper/vg0-data to 315392 (4k) blocks.
The filesystem on /dev/mapper/vg0-data is now 315392 (4k) blocks long.

  Size of logical volume vg0/data changed from 1.56 GiB (400 extents) to 1.20 GiB (308 extents).
  Logical volume vg0/data successfully resized.
$ sudo mount /dev/vg0/data /srv/data
$ df -h /srv/data
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/vg0-data  1.2G   24K  1.2G   1% /srv/data

出力の順に、fsck（第7章。ここでは ext4 の検査をする e2fsck が走った）→ resize2fs（中身を縮める）→ 箱を縮める、と動いている。XFS で同じことをしてみる。

$ sudo lvcreate -L 300M -n logs vg0
  Logical volume "logs" created.
$ sudo mkfs.xfs -q /dev/vg0/logs
$ sudo mkdir /srv/logs
$ sudo mount /dev/vg0/logs /srv/logs
$ sudo lvreduce -r -L 200M vg0/logs
fsadm: Xfs filesystem shrinking is unsupported.
  /usr/sbin/fsadm failed: 1
  Filesystem resize failed.
$ sudo umount /srv/logs
$ sudo lvremove -y vg0/logs
  Logical volume "logs" successfully removed.
$ sudo rmdir /srv/logs

XFS は縮められない（Xfs filesystem shrinking is unsupported）。箱を縮める前に止まったので、データは無事である。XFS を小さくしたいときは、別の場所に退避して作り直すしかない。lvremove は論理ボリュームを消すコマンドで、-y は確認の問いに「はい」と答えておくオプションである。

ファイルシステム広げる縮めるこの章の記録
ext4マウントしたまま（resize2fs）外してから（resize2fs）マウントしたまま広げ、外して 1.2G に縮めた
XFSマウントしたまま（xfs_growfs）できないlvreduce -r が止めた

スナップショットで、消したファイルを取り戻す

この節で分かること: スナップショットの大きさが何で決まるか。

スナップショットは、論理ボリュームのある瞬間の姿を残したものである。ファイルを1つ置いてから、data のスナップショットを 100MiB で作る（lvcreate の -s）。元は 1.2GiB あるが、それより小さくてよい。

$ echo "スナップショットの前" | sudo tee /srv/data/note.txt
スナップショットの前
$ sudo lvcreate -s -L 100M -n snap vg0/data
  Logical volume "snap" created.
$ sudo lvs vg0
  LV   VG  Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  data vg0 owi-aos---   1.20g
  snap vg0 swi-a-s--- 100.00m      data   0.01

元の側でファイルを消し、40MiB 書き込む（/dev/urandom はでたらめなバイトを返す装置のファイル。sync は、メモリに溜めた書き込みをディスクに書き出させるコマンド）。

$ sudo rm /srv/data/note.txt
$ sudo dd if=/dev/urandom of=/srv/data/big bs=1M count=40 status=none; sync
$ sudo lvs vg0
  LV   VG  Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
  data vg0 owi-aos---   1.20g
  snap vg0 swi-a-s--- 100.00m      data   40.22   ← 100MiB のうち 40% を使った

スナップショットの Data% が 0.01 から 40 に増えた。スナップショットは中身を丸ごと写すのではなく、元が書き換えられる直前に、書き換えられる前のブロックだけを自分の領域に退避する（コピーオンライト）。40MiB 書いたので 40MiB 分を退避した。だから大きさは「この先どれだけ変わるか」で決めればよく、100% に達するとスナップショットは使えなくなる。

スナップショットは、作った瞬間の姿のまま読める。消したファイルを取り戻す。

$ sudo mkdir /mnt/snap
$ sudo mount -o ro /dev/vg0/snap /mnt/snap
$ ls /srv/data /mnt/snap
/mnt/snap:
lost+found  note.txt

/srv/data:
big  lost+found
$ cat /mnt/snap/note.txt
スナップショットの前
$ sudo cp /mnt/snap/note.txt /srv/data/
$ sudo umount /mnt/snap
$ sudo lvremove -y vg0/snap
  Logical volume "snap" successfully removed.
$ sudo rm /srv/data/big
$ sudo rmdir /mnt/snap
たとえ: 書類を直すたびに、直す前のページだけを抜いて保管しておく運用に近い。変更の無いページは元の書類を見ればよいので、保管庫は小さくて済む。
ただし崩れる点: 保管庫がいっぱいになっても、書類の修正は止まらない。止まるのはスナップショットのほうで、そこで写しとしての価値を失う。大きく変わる作業の前に作るなら、変わる量より大きくしておく。

最後の状態を見ておく。

$ sudo pvs
  PV         VG  Fmt  Attr PSize    PFree
  /dev/sda   vg0 lvm2 a--  1020.00m 808.00m
  /dev/vdc   vg0 lvm2 a--  1020.00m      0
$ sudo lvs -o lv_name,lv_size,devices vg0
  LV   LSize Devices
  data 1.20g /dev/vdc(0)
  data 1.20g /dev/sda(0)
LVM の利点LVM の欠点
使っている途中で箱を広げられる（動的拡張）。ext4 なら縮めることもできるディスクとファイルシステムのあいだに段が1つ増え、壊れたときの調べ方が難しくなる
複数のディスクをまとめて、1台より大きな箱を作れるまとめたディスクの1台が壊れると、そこを使っていた論理ボリュームは壊れる（写しを持つ仕組みではない）
スナップショットで、ある瞬間の姿を小さな容量で残せるスナップショットがある間は、書き込みのたびに退避が起きて遅くなる
手を動かす: 実践編の演習08は、vdc と sda をまとめた vg0 に、1台より大きな vg0/data を作り、中の ext4 も箱いっぱいに広げる課題である。 判定は箱の大きさと中身の大きさを別々に読んで比べる。この章のとおりに打った人は、もう達成している。
確認

lvextend -L +1G vg0/data を実行したが、df -h で見るとファイルシステムの大きさが変わっていない。中身は ext4 である。何をすればよいか。XFS ならどうか。

答え

resize2fs /dev/vg0/data でファイルシステムを広げる（マウントしたままでよい）。XFS なら xfs_growfs。最初から lvextend -r を使えば、箱と中身を続けて広げる。

確認

LVM で論理ボリュームを作ってマウントするまでのコマンドを、順に並べよ。

答え

pvcreate（ディスクを物理ボリュームにする）→ vgcreate（ボリュームグループにまとめる）→ lvcreate（論理ボリュームを切り出す）→ mkfs（ファイルシステムを作る）→ mount。一覧はそれぞれ pvs・vgs・lvs（ボリュームグループの詳しい表示は vgdisplay）。

確認

1.2GiB の論理ボリュームに、100MiB のスナップショットを作れたのはなぜか。100MiB を使い切るとどうなるか。

答え

スナップショットは元の中身を丸ごと写さず、元が書き換えられるブロックの「書き換える前」だけを退避するので、要る大きさは作ってから変わる量で決まる。使い切るとスナップショットは使えなくなり、作った時点の姿を読めなくなる（元の論理ボリュームは影響を受けない）。

この章で分かったこと

持ち帰ってほしいこと

  • LVM は3段: 物理ボリューム（pvcreate）→ ボリュームグループ（vgcreate）→ 論理ボリューム（lvcreate）。ファイルシステムは論理ボリュームの中に作る
  • 論理ボリュームは複数のディスクにまたがれるので、1台より大きな箱を作れる。ただし1台壊れれば道連れになる
  • lvextend が広げるのは箱だけ。中身は resize2fs（ext4）・xfs_growfs（XFS）で広げるか、lvextend -r で続けて広げる
  • 縮めるのは中身が先、箱が後（lvreduce -r）。ext4 は外してから縮められ、XFS は縮められない
  • スナップショットは書き換えられる前のブロックだけを退避するので、大きさは「変わる量」で決まる。Data% が 100% になると使えなくなる
