4. 起動の入口は、マウントしなくても見つかる

練習機の /etc/fstab から /boot/efi の行を消して再起動しても、練習機はふつうに起動する。ESP の種類の印を書き換えて再起動しても、まだ起動する。UEFI のファームウェアは Linux より先に動き、NVRAM の名簿に書かれた「どの区画（PARTUUID）の、どのファイルか」を頼りに、自分で中の FAT を読むからだ。マウントは、Linux が中身を書き換えるときの都合にすぎない。

前提: 第3章まで読了前提: 練習機が起動している所要 24分影響度 B出題範囲 1.05.2（重要度4）最終検証 2026-10-13

この章のゴール

  • UEFI が起動のときに何をどの順に読むか（NVRAM → GPT → ESP）を言え、ESP の種類の印（EF00）が何のためにあるかを説明できる
  • /・/boot・/var・/home・スワップを別々のパーティションにする理由を、用途で説明できる
  • gdisk で GPT の表を作り、種類（EF00・8200・8300）を割り当てられる
ここで覚えなくていいこと: Secure Boot と shim の署名の検証、GRUB の設定ファイルの書き方、BIOS（レガシー）での起動の流れの細部は扱わない。起動の流れそのものは主題1.01 のコースで扱う。ここで要るのは「ファームウェアは何を手がかりに ESP を見つけるか」だけである。

練習機（Ubuntu 24.04 のクラウドイメージ）は、ディスクを4つに分けている。

/var と /home は分けていない。スワップも無い（Swap: 0B）。クラウドのサーバは1台を1つの用途に使い捨てることが多く、小さく作っておいて足りなくなれば作り直すからである。LinuC の公式セミナーの資料には「少なくとも / とスワップの2つ」という形が出てくるが、スワップが無くても Linux は動く（この練習機がそう。スワップは後からファイルでも足せる。第7章）。分ける理由は、この章の後半で表にする。

ESP の中身と、ファームウェアの名簿

この節で分かること: ファームウェアが「どこの何を」起動するかを、何で指しているか。

ESP（EFI System Partition）は、UEFI で起動するための FAT の区画である。中を見る。/boot/efi は umask=0077 でマウントされているので、root でないと中が読めない。

$ ls /boot/efi
ls: cannot open directory '/boot/efi': Permission denied
$ sudo ls -R /boot/efi/EFI
/boot/efi/EFI:
BOOT  ubuntu

/boot/efi/EFI/BOOT:
BOOTX64.EFI  fbx64.efi	mmx64.efi

/boot/efi/EFI/ubuntu:
BOOTX64.CSV  grub.cfg  grubx64.efi  mmx64.efi  shimx64.efi

次に、ファームウェア（UEFI）が覚えている起動の候補を見る。これはディスクではなく、マザーボードの不揮発メモリ（NVRAM）にある。

$ sudo efibootmgr
BootCurrent: 0001   ← 今回はどの候補で起動したか
Timeout: 0 seconds
BootOrder: 0002,0001,0000   ← 試す順番
Boot0000* UiApp	FvVol(7cb8bdc9-f8eb-4f34-aaea-3ee4af6516a1)/FvFile(462caa21-7614-4503-836e-8ab6f4662331)
Boot0001* UEFI Misc Device	PciRoot(0x0)/Pci(0x1,0x2)/Pci(0x0,0x0){auto_created_boot_option}
Boot0002* Ubuntu	HD(15,GPT,9606bc98-2904-4577-9584-a8310313a04c,0x2800,0x35000)/File(\EFI\ubuntu\shimx64.efi)   ← Ubuntu の候補
$ sudo blkid /dev/vda15 /dev/vda16
/dev/vda15: LABEL_FATBOOT="UEFI" LABEL="UEFI" UUID="B792-27AD" BLOCK_SIZE="512" TYPE="vfat" PARTUUID="9606bc98-2904-4577-9584-a8310313a04c"
/dev/vda16: LABEL="BOOT" UUID="a5eecc38-8587-4601-9295-c92dabc20612" BLOCK_SIZE="4096" TYPE="ext4" PARTUUID="ce13a6f1-b3f2-4c7a-b3db-6d75505ad739"

Boot0002 の中身は HD(15,GPT,9606bc98-…,…)/File(\EFI\ubuntu\shimx64.efi) で、「GPT の 15 番目、固有の番号（PARTUUID）が 9606bc98-… の区画の中の、このファイル」と読む。blkid の vda15 の PARTUUID と一致している。ファームウェアの名簿は、/dev/vda15 という名前も /boot/efi というマウント先も知らない。知っているのは表の上の位置と番号だけである。

ESP の中の GRUB の設定は、さらに /boot の区画を UUID で探しに行く。

$ sudo cat /boot/efi/EFI/ubuntu/grub.cfg
search.fs_uuid a5eecc38-8587-4601-9295-c92dabc20612 root 
set prefix=($root)'/grub'
configfile $prefix/grub.cfg
$ sudo iconv -f UTF-16 -t UTF-8 /boot/efi/EFI/ubuntu/BOOTX64.CSV
shimx64.efi,Ubuntu,,This is the boot entry for Ubuntu

search.fs_uuid a5eecc38-… は vda16（/boot）の UUID である。起動の流れは、ファームウェア → ESP の shim → GRUB → /boot のカーネル、となる。どの段も、次の段を番号（GUID・UUID）で探している。

もう1つ、efibootmgr の1行目に注目する。BootCurrent: 0001、つまり今回の起動は Ubuntu（0002）ではなく、ファームウェアがディスクを見て自分で作った候補 UEFI Misc Device から始まっている。練習機の NVRAM は最初の起動のときに空の雛形から作られるので、Ubuntu の候補はまだ無かった。名簿に使える候補が無いとき、ファームウェアはディスクの FAT を探して、決まった場所（\EFI\BOOT\BOOTX64.EFI）のファイルを起動する。今回もそうして起動し、その途中で shim の fallback が BOOTX64.CSV（「shimx64.efi を Ubuntu という名前で登録せよ」）を読んで Boot0002 を足した。次の起動からは 0002 になるはずで、この章の再起動のあとで確かめる（ここまでにコンテナを止めて起動し直した人は、この時点ですでに 0002 になっている）。

たとえ: 建物の守衛と来客名簿に近い。守衛（ファームウェア）は名簿（NVRAM）に書かれた部屋番号（PARTUUID）と担当者の名前（ファイルのパス）で、担当者（ブートローダ）を呼び出す。名簿に無ければ、決まった受付（\EFI\BOOT\）に行く。
ただし崩れる点: 守衛なら建物の中の事情（どの部屋を誰が使っているか）も聞けるが、ファームウェアは Linux の設定（/etc/fstab やマウント）を一切読まない。読むのは NVRAM と、表と、ESP の中身だけである。

マウントを外すと、起動できなくなる？

この節で分かること: /boot/efi のマウントが起動のどこで使われているか。

/etc/fstab の ESP の行を、先頭に # を付けて止める。元に戻せるように控えを取っておく。

$ sudo cp /etc/fstab /etc/fstab.bak
$ sudo sed -i 's|^LABEL=UEFI|#&|' /etc/fstab
$ grep UEFI /etc/fstab
#LABEL=UEFI	/boot/efi	vfat	umask=0077	0 1

ふつうこう考える

ESP は起動に使う区画で、Linux はそれを /boot/efi にマウントしている。 起動するときにマウントされていなければ、ブートローダが読めず、練習機は起動できなくなるはずだ。

$ sudo reboot
Broadcast message from root@linuc on pts/1 (Tue 2026-10-13 19:28:51 JST):

The system will reboot now!

ssh が切れて外に戻る。少し待ってから、外で起動を待つ（vm start は、動いている練習機なら起動し終わるまで待つだけ）。

$ vm start
練習機はもう動いています
  起動中… 10秒（KVM なしの完全エミュレーションなので 40〜90 秒かかります）
  起動中… 20秒（KVM なしの完全エミュレーションなので 40〜90 秒かかります）
練習機が起動しました（26秒）
  入るには:  ssh linuc   （抜けるときは exit）
$ findmnt -o TARGET,SOURCE,FSTYPE /boot/efi
$ ls -la /boot/efi
total 8
drwxr-xr-x 2 root root 4096 Sep  5 20:22 .
drwxr-xr-x 5 root root 4096 Oct 13 10:06 ..
$ systemctl is-system-running
running
$ sudo efibootmgr | head -3
BootCurrent: 0002   ← Ubuntu の候補（0002）で起動した
Timeout: 0 seconds
BootOrder: 0002,0001,0000
だめな理由: ふつうに起動し、running（不具合なし）になった。/boot/efi は空のディレクトリのままである。 ファームウェアは Linux が動き出す前に、NVRAM の候補が指す区画を GPT の表から PARTUUID で見つけ、中の FAT を自分で読んで shim を起動している。 /etc/fstab とマウントは、そのあとで Linux が使うものなので、起動には関わらない。 /boot/efi にマウントするのは、パッケージの更新で GRUB や shim を書き換えるときのためである。 そして今回の起動は BootCurrent: 0002、前の起動で shim が登録した Ubuntu の候補からだった。

戻しておく。/etc/fstab は起動のたびに読み直される（systemd が起動の初めに fstab からマウントの手順を作り直す）ので、次の起動には何もしなくても効く。ただし、いま動いている systemd は書き換えを知らないままなので、daemon-reload で読み直させておく（しないと、mount が「fstab が変わった」と注意を出す。第8章）。

$ sudo cp /etc/fstab.bak /etc/fstab
$ sudo systemctl daemon-reload
$ sudo mount /boot/efi
$ findmnt -o TARGET,SOURCE,FSTYPE /boot/efi
TARGET    SOURCE     FSTYPE
/boot/efi /dev/vda15 vfat
たとえ: 店の搬入口に近い。棚の商品（ブートローダ）を入れ替えるときは搬入口（マウント）を使うが、客（ファームウェア）は正面玄関から入ってきて棚の商品を手に取る。搬入口を閉めても、店は開いている。
ただし崩れる点: 搬入口を閉めたままだと、商品の入れ替え（GRUB や shim の更新）が失敗する。起動には要らないが、外したまま運用してよいわけではない。

種類の印は、誰のためか

この節で分かること: ESP の種類の印（EF00）を、起動のときに誰が見ているか。

ESP の種類 EFI System（gdisk のコードで EF00）は、UEFI の仕様が決めた「ここが ESP」という印である。ではファームウェアは、起動のときにこの印を見ているのか。vda15 の種類を Linux filesystem（8300）に書き換えて、再起動してみる（あとで戻す）。

sgdisk -i の Partition unique GUID が PARTUUID で、名簿の Boot0002 に書かれた 9606bc98-… と同じである。種類を書き換えたときの Warning は「動いているカーネルは、まだ前の表を使っている」という意味で、区画の位置は変えていないので、ここでは困らない。そして起動した。種類は Linux filesystem のまま、候補は同じ 0002 で、/boot/efi も（/etc/fstab はラベルで指しているので）マウントされている。この練習機のファームウェア（OVMF）は、名簿の候補が指す PARTUUID とファイルのパスで読みに行き、区画の種類は確かめなかった。種類の印を頼りにするのは、OS のインストーラや、ESP を探して更新する道具のほうである。だから ESP を作るときは、仕様どおり EF00 を付ける。戻しておく。

$ sudo sgdisk -t 15:ef00 /dev/vda
Warning: The kernel is still using the old partition table.
The new table will be used at the next reboot or after you
run partprobe(8) or kpartx(8)
The operation has completed successfully.
$ lsblk -o NAME,PARTTYPENAME /dev/vda
NAME    PARTTYPENAME
vda     
├─vda1  Linux filesystem
├─vda14 BIOS boot
├─vda15 EFI System
└─vda16 Linux extended boot
たとえ: 建物の通用口の札に近い。扉に「通用口」の札を貼っておくのが決まりで、新しく来た工事業者（インストーラ）はその札で扉を探す。
ただし崩れる点: 毎朝来る守衛（ファームウェア）は、名簿に書いた扉の番号で入るので、札を剥がしても入ってくる。札が要らないわけではなく、札を見る相手が違う。

/・/boot・/var・/home・スワップを分ける理由

この節で分かること: 用途に合わせてパーティションを割り当てる考え方と、gdisk での作り方。

分けるのは必須ではない。/ 1つ（UEFI で起動するならそれに ESP）でも Linux は動く。分けておくと、溢れたり壊れたりしたときの被害がその区画で止まり、fsck などの修復も区画ごとに短く済む。新しいサーバのディスクを設計するとき、区画をどう分けるかは「いっぱいになったら何が困るか」「作り直すとき何を残したいか」で決める。

区画入るもの分ける理由
ESPブートローダ（FAT）UEFI で起動するなら必須。種類に EF00（EFI System）の印を付ける。ファームウェアは NVRAM の候補（PARTUUID とファイルのパス）で読みに行く
/bootカーネル・initramfs・GRUB の設定/ を LVM や暗号化にしたとき、GRUB が読める単純な形で残すため
スワップメモリから追い出したページメモリが足りないときの逃げ場。休止（ハイバネート）するならメモリ以上の大きさが要る（第7章）
/OS とプログラムほかが溢れても、これが溢れなければシステムは動く
/varログ・メールの待ち行列・データベースなど、増え続けるものログが溢れても / を道連れにしない
/home利用者のファイルOS を入れ直しても残す。利用者が溢れさせても OS に響かない

この割り当てを、第3章で使った vdb に作る。GPT は gdisk で切る。まず o で空の GPT にし直し、n で6つ作る。種類は4文字のコードで答える（ef00 = EFI System、8200 = Linux swap、8300 = Linux filesystem。L で一覧）。

vdb1 の FSTYPE が ext4 になっている。種類は EFI System なのに、中身は第3章で作った ext4 のままである。表を作り直しても、中身には触れていない（第3章と同じ）。ESP の中身（FAT）は第6章で作る。parted は、種類を boot, esp や swap という旗（Flags）で表示する。

たとえ: 引っ越し先の部屋割りに近い。台所（/var）が散らかっても寝室（/）に物が溢れないよう、壁で仕切っておく。
ただし崩れる点: 部屋の壁は後から動かしにくいが、ディスクの仕切りも同じで、一度データを入れると広げ直すのが大変である。後から広げたい区画は、第5章の LVM に載せておくのが今のふつうのやり方である。
手を動かす: 実践編の演習04は、この6つの区画を GPT に作る課題である（道具は gdisk・parted・fdisk のどれでもよい）。 判定は表を読み、種類と大きさを1行ずつ比べる。この章のとおりに打った人は、もう達成している。
確認

UEFI のファームウェアが起動のときに ESP を見つける手がかりは何か。ESP の中のファイルシステムは何か。

答え

ふつうは NVRAM の起動の候補（efibootmgr の Boot0002 など）に書かれた、区画の PARTUUID とファイルのパス（\EFI\ubuntu\shimx64.efi）。候補が無ければ、ディスクの FAT を探して決まった場所（\EFI\BOOT\BOOTX64.EFI）を起動する。中は FAT（ふつう FAT32）。GPT の種類 EF00（EFI System）は仕様が決めた ESP の印で、作るときには付けるが、この練習機のファームウェアは起動のときに種類を確かめなかった。/etc/fstab やマウント先（/boot/efi）は手がかりにならない。ファームウェアは Linux より先に動くので、それらを読めない。

確認

/var を / と別のパーティションにすると、どんな事故を防げるか。

答え

ログやメールの待ち行列などが増え続けて区画がいっぱいになっても、/ まではいっぱいにならない。/ が溢れると、ほかのプログラムが一時ファイルを書けなくなったり、ログインに必要なファイルが書けなくなったりする。

確認

efibootmgr の出力の BootOrder と BootCurrent は何を表すか。

答え

BootOrder は、ファームウェアが起動の候補を試す順番で、NVRAM に書かれていて電源を切っても残る。BootCurrent は、今回の起動で実際に使われた候補で、起動のたびにファームウェアが設定する（残しておく値ではない）。どちらもディスクの上には無い。練習機の最初の起動では、BootOrder の先頭は 0002 なのに BootCurrent は 0001 だった（起動の途中で 0002 が登録されたため）。

この章で分かったこと

持ち帰ってほしいこと

  • UEFI のファームウェアは NVRAM の候補（efibootmgr）に書かれた PARTUUID とファイルのパスで、ESP の中の FAT を自分で読んでブートローダを起動する。候補が無ければ \EFI\BOOT\BOOTX64.EFI を探す
  • ESP の種類 EF00（EFI System）は仕様が決めた印で、作るときは付ける。ただしこの練習機のファームウェアは、起動のときに種類を確かめなかった（書き換えても起動した）
  • 候補は区画を「GPT の何番目・PARTUUID」で指す。/dev/vda15 という名前も /boot/efi というマウント先も知らない
  • /boot/efi のマウントを外しても起動する。マウントは、Linux がブートローダを書き換えるときのため
  • 分けるのは必須ではない（/ 1つと、UEFI なら ESP でも動く）。/・/boot・/var・/home・スワップは「溢れたら困るもの」「残したいもの」で分け、被害と修復をその区画で止める
  • GPT は gdisk で切り、種類を4文字のコードで付ける（EF00・8200・8300）。表を作り直しても、中身は前のまま残る
