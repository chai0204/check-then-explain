理論編 — Podman

このサイトの実践編の起動コマンドは、docker を podman に読み替えても動きます。 その podman が docker とどこまで同じで、どこから違うのかを、練習機（仮想マシン）の中に入れた本物の podman（rootless）で確かめる7章。 デーモンのいない作り、一般ユーザのままのコンテナ（rootless）、ユーザの systemd に任せる動かし方を、プロセスと UID の番号で見ます。

このページのコマンドは、あなたの画面に本文と同じ文字を出します。 出なければ教材のバグとして直します。 AI の回答は毎回違い、公式ドキュメントはあなたの環境を知りません。 ここにあるのは、誰かが実際に一度通した記録です。

この7章を貫いている1つの事実

podman には頼む相手のデーモンがいない。打った人の権限のまま、打った人の置き場所に、打った人の systemd の下でコンテナを作る。

だから、コンテナの親は付き添いの conmon で（第1章）、中の root は外では本人で（第2章）、イメージはユーザごとに別の置き場所にあり（第3章）、 網はユーザのプロセスが運び（第4章）、ログアウトすれば本人の systemd と一緒に止まる（第6章）。 docker と同じコマンドの形は、その上に重ねた互換の層で、既定値や API の版までは同じではない（第7章）。

ここで覚えなくていいこと: podman の全サブコマンド、netavark のブリッジ（root の podman の既定の網。rootless でも podman network create で作った網で使う）、podman kube play と Kubernetes、 Podman Desktop や macOS・Windows の podman machine、buildah・skopeo。必要になったら、この7章の仕組みの上に足せます。

この記事の檻（lab-podman:1.0.0）は、docker を podman に読み替えた同じオプション（名前付きボリュームも同じ）で、rootless の podman（5.8.6）でも起動することを確かめてあります （logs/podman-rootless.log。起動から ssh まで35秒、podman exec の umask は 0022、podman stop は5秒で終了コード 0）。 Docker の記事の檻（lab-docker:1.0.0）も、同じ方法で確かめてあります（logs/docker-rootless.log）。

起動コマンドの部分rootless の podman では章
特権を求めない（--privileged・--cap-add・--device が無い。このサイトの例外は、--cap-add SYS_ADMIN の LinuC 1.09 と --device /dev/kvm の KVM の記事で、rootless の podman での動きはこの記事では確かめていない）rootless で渡せないものを、最初から頼んでいない。檻の中の lab は一般ユーザなので、既定のケーパビリティの差（docker 14個・podman 11個）にも触れない7
-v 名前:/home/lab/…名前付きボリュームは、檻を起動した人の rootless の置き場所（~/.local/share/containers/storage/volumes）に作られ、ユーザ名前空間の中でイメージの持ち主（lab）がそのまま写される。バインドマウントだと、外の持ち主と中の持ち主の食い違い（100999 問題）が起きうる2・3
-p が無い1024 番未満の公開の制限も、rootlessport の中継も関係しない4
--stop-timeout 30・--hostname host・-d・exec -itpodman にも同じオプションがあり、同じ意味で効く7
（ログアウトしたら）rootless の podman のコンテナは、本人の systemd が止まると一緒に止まる。檻を動かしたままログアウトするなら loginctl enable-linger6

docker の側からの見方（同じ起動コマンドの各オプションの意味）は、Docker の記事の理論編の表にあります。

章

  1. podman には、頼む相手のデーモンがいない — コンテナが動いている間、podman のプロセスはいない。親は conmon（18分）
  2. コンテナの中の root は、外では student — 中の root が作ったファイルが、外では student の持ち物。中の 1000 は外の 100999（22分）
  3. イメージの置き場所は、ユーザごとに別 — sudo podman images が空。運ぶと ID は同じで DIGEST が変わる（18分）
  4. rootless のネットワークは、カーネルの外で中継される — 80 番は公開できない。コンテナは QEMU と同じ形の 10.0.2.x の網に置かれる（22分）
  5. pod は、ネットワークを分け合うコンテナの組 — 別のコンテナの httpd に 127.0.0.1 で届き、ホスト名は pod の名前（20分）
  6. ログアウトしても動かし続けるのは、systemd の仕事 — ログアウトするとコンテナが止まる。linger と quadlet で systemd に任せる（27分）
  7. 同じコマンドで、違う仕組み — 既定の特権は11個で、ping を許すグループも違う。docker の CLI から podman を使え、CLI の側の版の決まりで既定の一覧など一部が断られる（25分）

檻で再現できないもの

ものなぜ再現できないか代わりにしたこと
podman 5 の既定（pasta が rootless の網の既定 など） 練習機の podman は Ubuntu 24.04 の 4.9.3。podman 5 は Ubuntu 24.04 の apt に無い 第4章で、4.9.3 でも --network pasta で pasta を選んで確かめた。違いは本文に版を書いた
macOS・Windows の podman（podman machine） podman machine は Linux の仮想マシンを1台隠し持ち、その中で podman を動かす。中身は製品と版で違う この記事の練習機が、その「隠れた仮想マシン」の役を見える形でしている
レジストリからの取得（podman pull） 結果が読者のネットワークとレジストリの状態で変わる。練習機は Docker Hub に届かないようにしてある（ほかのレジストリには届くが、本文と演習では使わない） 第3章で、置き場所から置き場所へ運ぶ方法（save と load）を確かめた
練習機の再起動をまたいだ quadlet のサービスの自動起動 練習機の再起動（KVM なしで1分前後）を本文の流れに入れると、読者の待ち時間が長くなる 第6章で、起動のときに読まれるリンク（default.target.wants/）が作られることと、linger を確かめた
