3. イメージの置き場所は、ユーザごとに別

docker のイメージは、練習機に1か所（root の dockerd の置き場所）しかない。podman のイメージは、使うユーザごとに別の置き場所にある。 student の podman に入っているイメージは、同じ練習機の sudo podman（root の podman）からは見えない。 置き場所から置き場所へは、イメージを書き出して読み込めば運べるが、運び方によって変わるものと変わらないものがある。

前提: 第2章所要 18分影響度 B最終検証 2026-10-14

この章のゴール

  • rootless と root の podman が、別の置き場所（~/.local/share/containers/storage と /var/lib/containers/storage）を使うことを示せる
  • イメージを podman save と podman load で別の置き場所へ運べる
  • 運んだ後に、イメージの ID（設定の指紋）は変わらず、ダイジェスト（設計図の指紋）が変わりうる理由を言える
ここで覚えなくていいこと: storage.conf の全項目、ストレージドライバ（overlay と vfs）の選び方、podman image scp、 追加の読み取り専用の置き場所（additional image stores）。

student と root は、別のイメージを見ている

この節で分かること: 同じ練習機の podman が、ユーザによって違う一覧を出すこと。

ふつうこう考える

イメージは練習機に入っているのだから、student の podman でも、root の sudo podman でも、同じイメージが見えるはずだ（docker なら、誰が打っても同じ一覧が出る）。

$ podman images
REPOSITORY                 TAG         IMAGE ID      CREATED       SIZE
docker.io/library/alpine   3.24.2      320994c3b997  3 weeks ago   8.72 MB
docker.io/library/busybox  1.38.0      aaef90e06523  5 months ago  4.69 MB
$ sudo podman images
REPOSITORY  TAG         IMAGE ID    CREATED     SIZE
だめな理由: student の podman には2つのイメージがあるのに、sudo podman の一覧は空だった。 podman はデーモンを持たず、打った人の置き場所を直接読むので、student と root は別の置き場所を使っている。 docker は誰が打っても1つの dockerd に頼むので、置き場所も1つだった（Docker 第3章）。
$ podman info --format '{{.Store.GraphRoot}}'
/home/student/.local/share/containers/storage
$ sudo podman info --format '{{.Store.GraphRoot}}'
/var/lib/containers/storage
$ du -sh ~/.local/share/containers/storage
14M	/home/student/.local/share/containers/storage

student の置き場所はホームの下の ~/.local/share/containers/storage、root の置き場所は /var/lib/containers/storage である。 student のイメージの層は、第2章のユーザ名前空間の中で展開されている（イメージの中の root の持ち物は、外では student の持ち物として置かれる）。

たとえ: podman の置き場所は、社員ごとの机の引き出しに近い。docker は総務の共有の倉庫（root の dockerd）で、誰が頼んでも同じ棚から出てくる。 引き出しの中身は、本人が開けたときにしか見えない。
ただし崩れる点: 引き出しは物として分かれているが、podman の置き場所はディレクトリが違うだけで、練習機の root ならどの引き出しの中も読める。 分かれているのは「podman が、打った人の置き場所だけを読む」という決まりのほうである。

別の置き場所へ運ぶ

この節で分かること: イメージを運んだとき、変わるものと変わらないもの。

podman save はイメージを tar にして標準出力に書き、podman load は標準入力から読み込む。パイプでつなげば、student の置き場所から root の置き場所へ運べる。

$ podman images --digests alpine
REPOSITORY                TAG         DIGEST                                                                   IMAGE ID      CREATED      SIZE
docker.io/library/alpine  3.24.2      sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6  320994c3b997  3 weeks ago  8.72 MB
$ podman save alpine:3.24.2 | sudo podman load
Getting image source signatures
Copying blob 74d97c428c51 done   |
Copying config 320994c3b9 done   |
Writing manifest to image destination
Loaded image: docker.io/library/alpine:3.24.2
$ sudo podman images --digests alpine
REPOSITORY                TAG         DIGEST                                                                   IMAGE ID      CREATED      SIZE
docker.io/library/alpine  3.24.2      sha256:4d5cf6fa4d69da5c2b2a04a7ac06083e9d567e768c4f44c4333bb335a0226b06  320994c3b997  3 weeks ago  8.71 MB

運んだ後も、IMAGE ID（320994c3b997）は同じだった。ところが DIGEST は 294b683c… から別の値に変わった。

値何の指紋か運んで変わったか理由
IMAGE ID設定（config）の JSON変わらない設定の中身（起動するコマンド、層の diff_ids）は運んでも同じ
DIGEST取ってきたときの目録・設計図変わったpodman save は既定で昔の docker の形（docker-archive）で書き出し、読み込んだ側で設計図を作り直す。層も圧縮しない形で入れ直すので、設計図に書かれる層の指紋が変わる

読み込むときの Copying blob 74d97c428c51 は、Docker 第3章で計算した「展開した tar の指紋」（diff_ids）と同じ値である。 運び方を変えれば DIGEST はまた変わるが、層の中身（diff_ids）と設定（ID）は変わらない。中身を確かめたいときは、どの指紋を比べているのかを意識する。 レジストリから取った 294b683c… と同じであることを保証したいなら、運ぶ途中で作り直さない方法（同じレジストリから同じダイジェストで取る）を使う。

docker と podman でも、同じイメージに別の ID が付く。Docker 第3章の docker（29.1.3。イメージの置き場所が containerd）は目録のダイジェストを ID にしていた（294b683cb724）が、podman は設定の指紋を ID にしている（320994c3b997）。 docker でも、古い置き場所（overlay2）のまま 29 に上げたものは podman と同じく設定の指紋を ID にする（containerd の置き場所は、29 を新しく入れたときの既定）。

たとえ: イメージを運ぶのは、書類一式をコピーして別の部署に送ることに近い。中身の書類（設定と層）は同じでも、送り状（設計図）は送る側が作り直すので、送り状の通し番号（DIGEST）は変わる。
ただし崩れる点: 書類のコピーなら紙が変わっても中身は同じと言えるが、イメージの層は「圧縮したかどうか」で指紋が変わるので、どの形で比べているかを決めないと「同じ」と言えない。
たとえ: docker と podman の ID の違いは、同じ本に、図書館ごとに別の請求記号が付くことに近い。docker は目録の指紋を、podman は設定の指紋を、その本の番号として棚に貼る。
ただし崩れる点: 請求記号は図書館が勝手に決める番号だが、ここではどちらも中身の指紋の一部で、計算し直せば同じ値が出る。違うのは「どの部分の指紋を ID と呼ぶか」という決め方だけである。

root の置き場所に運んだものを消す。

$ sudo podman rmi alpine:3.24.2
Untagged: docker.io/library/alpine:3.24.2
Deleted: 320994c3b997e2ec6433f717f153e108023c5bec8fefa8d76b83451d16d05ea8
$ sudo podman images
REPOSITORY  TAG         IMAGE ID    CREATED     SIZE
手を動かす: 実践編の演習03で、student の置き場所の busybox を root の置き場所へ運び、root の podman で動かす。
確認

student で podman pull したイメージが、sudo podman run では「取ってこようとして」失敗した。なぜか。

答え

student の podman と root の podman は別の置き場所を使うので、root の置き場所にはそのイメージが無い。root は自分の置き場所に無い名前をレジストリへ取りに行った （この練習機は Docker Hub に届かないので失敗する）。podman save | sudo podman load で運ぶか、root でも取ってくる。

確認

運んだ後のイメージで、IMAGE ID は同じなのに DIGEST が違った。中身は同じと言ってよいか。

答え

設定（ID）と層の中身（diff_ids）が同じなので、コンテナとして動く中身は同じである。違うのは、運ぶときに作り直した設計図（DIGEST）の指紋だけ。 ただし「レジストリの @sha256:294b… と同じもの」を名指しする用途（起動コマンドへのダイジェストの記入）には、作り直した後の DIGEST は使えない。

この章で分かったこと

持ち帰ってほしいこと

  • podman のイメージの置き場所はユーザごとに別。rootless は ~/.local/share/containers/storage、root は /var/lib/containers/storage
  • podman save | sudo podman load で運べる。ID（設定の指紋）と diff_ids は変わらず、DIGEST（設計図の指紋）は運び方で変わる
  • docker と podman は、同じイメージに別の ID を付けることがある（containerd の置き場所の docker 29 は目録のダイジェスト、podman は設定の指紋）
