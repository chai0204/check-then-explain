5. pod は、ネットワークを分け合うコンテナの組

pod は、いくつかのコンテナを1つの組にしたものである。同じ pod のコンテナは、同じ net の名前空間（と uts の名前空間）を使うので、 互いに 127.0.0.1 で話せて、ホスト名も同じになる。名前空間を持ち続け、pod の網の寿命の区切りになるのは、何もしない小さなコンテナ（infra。中身は pause）で、 アプリのコンテナはそこに相乗りしている。Kubernetes の Pod と同じ考え方を、podman は1台の上で真似ている。

前提: 第4章所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • 同じ pod のコンテナが、127.0.0.1 で互いに届くことを示せる
  • どの名前空間が共有されていて、どれが別かを、/proc/PID/ns の番号で示せる
  • infra のコンテナと pause のイメージが何のためにあるかを言える
ここで覚えなくていいこと: podman kube play（Kubernetes の YAML から pod を作る）、pod の cgroup の上限、 共有する名前空間の選び方（--share）、Kubernetes の Pod の細部。

pod を作り、2つのコンテナを入れる

この節で分かること: 同じ pod のコンテナ同士が、どう話せるか。

ポートの公開は、pod を作るときに pod に付ける（pod の中のコンテナは、pod の網を使うので）。

$ podman pod create --name pod1 -p 127.0.0.1:8081:80
0d91cc9297d6841515bf91698b253ea54f04464f92a15fb898eb4334c4ea68f7
$ podman ps -a --pod --format '{{.Names}}  {{.Image}}  {{.PodName}}'
0d91cc9297d6-infra  localhost/podman-pause:4.9.3-0  pod1
$ podman images
REPOSITORY                 TAG         IMAGE ID      CREATED        SIZE
localhost/podman-pause     4.9.3-0     99250d27d870  3 seconds ago  835 kB
docker.io/library/alpine   3.24.2      320994c3b997  3 weeks ago    8.72 MB
docker.io/library/busybox  1.38.0      aaef90e06523  5 months ago   4.69 MB

空の pod を作っただけで、コンテナが1つ（…-infra）できている。中身は localhost/podman-pause という、この練習機で今作られたばかりのイメージである （podman は、何もしないで眠り続けるだけの小さなプログラム catatonit から、最初の pod のときに作る。だから CREATED が新しい）。

たとえ: infra のコンテナは、会議室の予約だけを持ち続ける人に近い。会議の出席者（アプリのコンテナ）が入れ替わっても、予約（網とホスト名の名前空間）が切れないので、同じ部屋（同じアドレス・同じ公開）をずっと使える。
ただし崩れる点: 予約者は会議に出なくても予約は残るが、infra のコンテナは実際に動いているプロセス（pause）で、これを止めると、部屋の外線と受付（外とのつなぎと公開）が外される。部屋そのもの（名前空間）は、中に人（アプリ）がいる間は残り、内線（127.0.0.1）だけが使える。

ふつうこう考える

pod は、関係するコンテナをまとめて起動・停止するための名前の束だ。コンテナ同士は、普段と同じくそれぞれ別のネットワークにいるので、相手に届くにはアドレスか名前を調べて指定する必要があるはずだ。

$ podman run -d --pod pod1 --name pod1-web busybox:1.38.0 httpd -f -h /etc
ce23304a52d7285f465143594f277f2568e4fbbba26eeb351d33dd772b2ba0f5
$ podman run --rm --pod pod1 alpine:3.24.2 wget -qO- http://127.0.0.1/hostname
pod1
$ curl -s http://127.0.0.1:8081/hostname
pod1
だめな理由: 2つ目のコンテナ（alpine）から 127.0.0.1、つまり「自分自身」の 80 番に接続すると、別のコンテナの httpd が答えた。 しかも返ってきたホスト名は、どちらのコンテナの名前でもなく pod1 だった。 同じ pod のコンテナは、同じ net の名前空間（NIC・アドレス・ポートの一覧）と同じ uts の名前空間（ホスト名）を使っている。だから相手のアドレスを調べる必要が無い。 練習機からの curl は、pod に付けた公開（8081 番）から、同じ網の 80 番に届いた。

何を分け合い、何を分けているか

この節で分かること: pod の中で共有される名前空間と、共有されない名前空間。
$ a=$(podman inspect --format '{{.State.Pid}}' pod1-web)
$ b=$(podman inspect --format '{{.State.Pid}}' $(podman pod inspect --format '{{.InfraContainerID}}' pod1))
$ readlink /proc/$a/ns/net /proc/$a/ns/uts /proc/$a/ns/ipc /proc/$a/ns/pid /proc/$a/ns/mnt
net:[4026532351]
uts:[4026532413]
ipc:[4026532414]
pid:[4026532418]
mnt:[4026532417]
$ readlink /proc/$b/ns/net /proc/$b/ns/uts /proc/$b/ns/ipc /proc/$b/ns/pid /proc/$b/ns/mnt
net:[4026532351]
uts:[4026532413]
ipc:[4026532414]
pid:[4026532415]
mnt:[4026532411]
$ podman inspect --format '{{.HostConfig.NetworkMode}}' pod1-web
container:d643cea34b8dfa85a29b70a50af18421bceead71626d2c9fcd0e3b8fea4aa386

httpd（$a）と infra（$b）で、net・uts・ipc の番号は同じ、pid（プロセスの番号）と mnt（ファイルの見え方）は別だった。 NetworkMode は container: の後に infra のコンテナの ID を書いていて、「網は infra のものを使う」という意味である。 ファイルの木は別々なので、2つのコンテナは別のイメージ（busybox と alpine）から作れる。

名前空間同じ pod のコンテナ同士だから
net共有127.0.0.1 で互いに届く。同じポートを2つのコンテナで待ち受けることはできない
uts共有ホスト名が同じ（pod の名前）
ipc共有（podman の既定）共有メモリなどで話せる
mnt別コンテナごとに別のイメージのファイルの木
pid別（podman の既定）互いのプロセスは見えない

infra のコンテナは、pod の名前空間を持ち続ける係である。アプリのコンテナが落ちても、何もしない infra が uts・ipc の名前空間を持ち続け、 pod の網も infra が動いている間は保たれる（rootless の podman は、網の名前空間を /run/user/1000/netns/ の下のファイルで固定している）。 だから、起動し直したアプリは同じアドレス・同じ公開のまま戻れる。逆に、infra を止めると何が起きるかを確かめる。

$ ls /run/user/1000/netns/ | wc -l
1
$ readlink /proc/$a/ns/net
net:[4026532351]
$ podman stop $(podman pod inspect --format '{{.InfraContainerID}}' pod1)
d643cea34b8dfa85a29b70a50af18421bceead71626d2c9fcd0e3b8fea4aa386
$ podman ps -a --pod --format '{{.Names}}  {{.Status}}'
0d91cc9297d6-infra  Exited (0) 2 seconds ago
pod1-web  Up 15 seconds
$ curl -s -m 5 http://127.0.0.1:8081/hostname; echo "exit=$?"
exit=7
$ ls /run/user/1000/netns/ | wc -l
0
$ readlink /proc/$a/ns/net
net:[4026532351]
$ podman exec pod1-web ip -o -4 addr
1: lo    inet 127.0.0.1/8 scope host lo\       valid_lft forever preferred_lft forever

infra を止めると、アプリの pod1-web は Up のままなのに、pod に付けた公開（8081 番）には届かなくなった（curl の終了コード 7 は「つながらなかった」）。 網を固定していたファイルも 1 個から 0 個になり、pod1-web の中の網には lo（127.0.0.1）だけが残った（10.0.2.100 の tap0 が消えた）。 ただし pod1-web の網の名前空間の番号は、止める前と同じだった。podman が片付けたのは外とのつなぎ（tap0 を持つ slirp4netns・公開を受けていた rootlessport・網を固定していたファイル）で、 名前空間そのものは、入っているアプリがいる間は残る。pod の外とのつなぎと公開の寿命は、infra のコンテナの寿命に結び付いている。

たとえ: pod はシェアハウスに近い。住人（コンテナ）は自分の部屋（mnt・pid）を持つが、玄関と住所と電話（net・uts）は1つを分け合う。 大家（infra）は何もしないで住み続け、住人が入れ替わっても住所が変わらないようにしている。
ただし崩れる点: シェアハウスの住人は互いの声が聞こえるが、pod のコンテナは既定では互いのプロセスが見えない（pid は別）。 分け合うのは網とホスト名で、生活そのものではない。
たとえ: pod の中の 127.0.0.1 は、相部屋で1台の電話機を共用することに近い。同じ部屋の人に内線（127.0.0.1）でかければ、相部屋の誰かが出る。
ただし崩れる点: 電話なら誰が出ても話せるが、ポートは早い者勝ちで、同じ番号（80 番）で2つのコンテナが待ち受けることはできない。電話機は1台でも、受話器を取れるのは1人だけである。

pod ごと消す。-f は動いているコンテナも止めて消し、-t 0 は止まるのを待たない。

$ podman pod rm -f -t 0 pod1
0d91cc9297d6841515bf91698b253ea54f04464f92a15fb898eb4334c4ea68f7
$ podman ps -a
CONTAINER ID  IMAGE       COMMAND     CREATED     STATUS      PORTS       NAMES
手を動かす: 実践編の演習05で、web サーバと、それを 127.0.0.1 で確かめるコンテナを、1つの pod に入れる。
確認

同じ pod の中で、2つのコンテナがどちらも 80 番で待ち受けようとした。どうなるか。この章の名前空間の表から予想せよ。

答え

後から待ち受けようとしたほうが失敗する（アドレスがすでに使われている）。同じ pod のコンテナは net の名前空間を共有しているので、ポートの一覧も1つしか無い。 別々のコンテナなら、それぞれ自分の網を持つので同じ番号で待ち受けられる。

確認

pod を作っただけなのに、podman ps -a にコンテナが1つ増え、podman images に localhost/podman-pause が増えた。何のためか。

答え

pod の名前空間を持ち続け、pod の外とのつなぎと公開の寿命の区切りになる infra のコンテナと、その中身（何もしないで眠るだけのプログラム）である。 アプリのコンテナが入れ替わっても、infra が動いている限り pod の網と公開は消えない（infra を止めると、podman が外とのつなぎと公開を片付ける）。

この章で分かったこと

持ち帰ってほしいこと

  • pod のコンテナは net と uts（podman の既定では ipc も）の名前空間を分け合う。127.0.0.1 で互いに届き、ホスト名は pod の名前になる
  • mnt と pid は別なので、別のイメージから作ったコンテナを1つの pod に入れられる
  • pod の名前空間と網を保つのは infra のコンテナ（podman-pause のイメージ）。infra を止めると、アプリが動いていても外とのつなぎ（tap0）と公開は片付けられ、名前空間には lo だけが残る。ポートの公開は pod に付ける
