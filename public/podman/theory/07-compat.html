7. 同じコマンドで、違う仕組み

podman のコマンドの形は docker とほぼ同じで、このサイトの檻も docker を podman に読み替えるだけで起動する。 podman は docker の API の真似もでき、docker の CLI から podman にコンテナを作らせることさえできる。 けれども、中で渡している特権・置いている印・止め方・API の版は、docker と同じではない。同じ画面を期待してよいところと、いけないところを数字で分ける。

前提: 第1〜6章。Docker 第7章を読んでいると比べやすい所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • podman と docker で、既定のケーパビリティ・ping の許し方・コンテナの中の印のファイル・exec の umask の決まり方が、どう同じでどう違うかを示せる
  • docker の CLI を podman の API につないで使え、そのときに起きる版の食い違いを説明できる
  • このサイトの檻が、docker でも rootless の podman でも同じオプションで動く理由を言える
ここで覚えなくていいこと: podman-docker パッケージ（docker という名前で podman を呼ぶ）、docker compose と podman compose の違い、 API の各版で何が変わったかの一覧、Docker Desktop と Podman Desktop。

同じ形のコマンド、違う中身

この節で分かること: 同じ run でも、コンテナに渡る特権と、中に置かれる印が違うこと。

ふつうこう考える

podman は docker と同じコマンドが打てる「docker の別名」だ。同じ run を打てば、コンテナの中は docker と同じになるはずだ。

$ podman run --rm alpine:3.24.2 grep CapEff /proc/self/status
CapEff:	00000000800405fb
$ capsh --decode=00000000800405fb
0x00000000800405fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_sys_chroot,cap_setfcap
$ podman run --rm alpine:3.24.2 ls /run/.containerenv
/run/.containerenv
$ podman run --rm alpine:3.24.2 ls /.dockerenv
ls: /.dockerenv: No such file or directory
だめな理由: コンテナの中の root のケーパビリティは 00000000800405fb の11個で、docker の既定（00000000a80425fb の14個。Docker 第7章）より cap_net_raw（ping などの生のパケット）・cap_mknod（装置のファイルを作る）・cap_audit_write の3つが少ない。 コンテナの中の印も違い、podman は /run/.containerenv を置き、docker の /.dockerenv は無い。 コマンドの形が同じでも、既定値は別々の人が別々に決めている。このサイトの lab env は、この2つの印のファイルでランタイムを見分けている。

cap_net_raw が無いなら、podman のコンテナでは ping が打てないのか。中の root と、UID 1000 で比べる。

$ podman run --rm alpine:3.24.2 sh -c 'cat /proc/sys/net/ipv4/ping_group_range; ping -c1 -q 127.0.0.1 >/dev/null 2>&1 && echo ping-ok || echo ping-ng'
0	0
ping-ok
$ podman run --rm --user 1000:1000 alpine:3.24.2 sh -c 'ping -c1 -q 127.0.0.1 >/dev/null 2>&1 && echo ping-ok || echo ping-ng'
ping-ng
$ podman run --rm --user 1000:1000 --cap-add NET_RAW alpine:3.24.2 sh -c 'ping -c1 -q 127.0.0.1 >/dev/null 2>&1 && echo ping-ok || echo ping-ng'
ping-ok

中の root の ping は、cap_net_raw が無くても通った。podman はコンテナの net.ipv4.ping_group_range を 0 0（グループ 0 だけ）にしていて、 グループ 0 の root は、特権の要らない ping 専用のソケット（ICMP のソケット）で ping できる。UID 1000 にすると断られ、--cap-add NET_RAW を足すと通った。 docker はこの値を 0 2147483647（全部のグループ）にしているので、一般ユーザでも通る（Docker 第7章の --user の節）。 差は、ケーパビリティよりも ping_group_range の値にある。

たとえ: podman と docker は、ボタンの配置が同じ、別のメーカーのリモコンに近い。押し方（コマンドの形）は同じでも、中の初期設定（既定のケーパビリティ・印のファイル）はメーカーがそれぞれ決めている。
ただし崩れる点: リモコンなら同じボタンで同じテレビが動くが、podman と docker は動かす相手からして違う（デーモンの有無・ユーザ名前空間・置き場所）。ボタンが同じでも、押した先で起きることの仕組みは別物である。

止め方と、exec の umask

この節で分かること: stop と exec で、docker と同じところと違うところ。
$ podman run -d --name p7 alpine:3.24.2 sleep 1000
d95eb7a1070c4f02d479eb7944d984fb7698d6758f34b94301c5feda4aeb5587
$ podman exec p7 sh -c 'umask; echo "TERM=$TERM"'
0022
TERM=
$ umask
0002
$ grep Umask /proc/$(pgrep -x conmon)/status
Umask:	0022

exec の umask は 0022、端末なしでは TERM が空、という点は docker と同じだった（Docker 第2章）。 conmon はいま打った podman から生まれたのに、打ったシェルの umask（0002）ではなく 0022 で動いていた。では、exec のプロセスは誰の子で、umask はどこから来るのか。

$ podman exec -d p7 sleep 2000
e14797d80b7a18ef6ab2a645225963bc5e5631eca95ee2d310830273934e8485
$ ps -o pid,ppid,comm -C sleep,conmon
    PID    PPID COMMAND
   2352       1 conmon
   2354    2352 sleep
   2389       1 conmon
   2392    2389 sleep

後から足した sleep 2000 の親（PPID）は、PID 1 の sleep 1000 の親とは別の conmon だった。 podman は exec のたびに、その exec のためだけの conmon を起動する（docker の exec のプロセスは、コンテナの shim の子だった）。 次に、コンテナの umask の設定（--umask）を変えたコンテナと比べる。exec で足したプロセス（$s）と、その親（$p。この exec のための conmon）の umask を並べる。

$ podman run -d --name p7u --umask 0077 alpine:3.24.2 sleep 1000
51e8326e7d0027f691de94e2010695fe74659c1f9d511a75448593c4c5071e37
$ podman exec p7u sh -c umask
0077
$ podman exec -d p7u sleep 3000
295af872711cce39662744bfa3db1aa0df81a5e139821be6e65fffe24f804de5
$ s=$(pgrep -x -f 'sleep 3000'); p=$(ps -o ppid= -p $s | tr -d ' ')
$ grep Umask /proc/$s/status /proc/$p/status
/proc/2449/status:Umask:	0077
/proc/2446/status:Umask:	0022
$ ps -o pid,comm -p $p
    PID COMMAND
   2446 conmon
$ podman inspect p7 p7u --format '{{.Name}} {{.Config.Umask}}'
p7 0022
p7u 0077
$ podman rm -f -t 0 p7u
p7u

--umask 0077 で作った p7u への exec は 0077 になった。exec -d で足した sleep 3000 も 0077 だが、その親の conmon は 0022 のままだった。 podman の exec の umask は、conmon から受け継ぐのではなく、コンテナの umask の設定（--umask。既定 0022）を、podman が exec のたびに crun へ渡して決めている。 docker の exec が shim から受け継いだのと、値は同じ 0022 でも決まり方が違う。最後に p7 を止める。

$ time podman stop p7
WARN[0010] StopSignal SIGTERM failed to stop container p7 in 10 seconds, resorting to SIGKILL
p7

real	0m11.189s
user	0m0.870s
sys	0m0.949s
$ podman rm p7
p7

stop は docker と同じく TERM → 10秒待つ → KILL で、PID 1 の sleep は TERM を受け取らないので10秒あまりかかった。 違うのは、podman が KILL に切り替えたことを警告で知らせることである（docker は黙って KILL する）。

docker の CLI から、podman に頼む

この節で分かること: podman が docker の API を真似られることと、その限界。

podman は、頼まれたときだけ起動する docker 互換の API の受け口（ソケット）を、student の systemd のサービスとして持っている。 この練習機には docker の CLI も入っているので、DOCKER_HOST でつなぐ先を podman のソケットに変えると、docker の CLI が podman に頼むようになる。

$ systemctl --user start podman.socket
$ ls -l /run/user/1000/podman/podman.sock
srw-rw---- 1 student student 0 Oct 14 05:12 /run/user/1000/podman/podman.sock
$ export DOCKER_HOST=unix:///run/user/1000/podman/podman.sock
$ docker version --format '{{.Server.Version}} / API {{.Server.APIVersion}}'
4.9.3 / API 1.41
$ docker run --rm alpine:3.24.2 cat /etc/alpine-release
3.24.2
$ docker images
API version 1.41 is not supported by this client: the minimum supported API version is 1.44
$ docker images --format '{{.Repository}}:{{.Tag}}'
alpine:3.24.2
busybox:1.38.0
localhost/podman-pause:4.9.3-0
$ DOCKER_API_VERSION=1.41 docker images
                                                            i Info →   U  In Use
IMAGE                           ID             DISK USAGE   CONTENT SIZE   EXTRA
docker.io/library/alpine:3.24.2
                                320994c3b997       8.72MB             0B
docker.io/library/busybox:1.38.0
                                aaef90e06523       4.69MB             0B
localhost/podman-pause:4.9.3-0
                                99250d27d870        835kB             0B
$ unset DOCKER_HOST
$ systemctl --user stop podman.socket podman.service

dockerd は止まっているのに、docker の CLI で run が動いた。答えたのは podman 4.9.3 で、docker の API の 1.41 版として振る舞っている。 ところが docker images は「この CLI は 1.44 版より古い API を使えない」と断った。断ったのは podman ではなく、docker の CLI（29.1.3）のほうである。 この CLI は、1.44 版より古いサーバとの版合わせを断る決まりを持っている。ほとんどのコマンド（run など）は、その断りを無視して、CLI 自身の版（1.52）の番号を付けたまま頼む。 podman 4.9.3 の受け口は、頼みに付いた版の番号を咎めず、1.41 版として答えるので動く（著者の記録 logs/podman-api.log: 受け口に届いた頼みは /v1.52/containers/json などだった）。 既定の docker images（木の形の一覧）だけは版合わせをやり直して、頼みを送る前に断りを出す（ほかに、--platform を付けた image inspect などの一部も同じ断りを出す）。--format を付けた一覧は出た。 使う版を DOCKER_API_VERSION=1.41 で決め打ちすると、版合わせ自体をしないので、同じ木の形の一覧が出た（IMAGE ID は podman の値の 320994c3b997。第3章）。 新しい表示が 1.44 版の機能を要るのではない。互換は「API の何版として振る舞うか」の範囲までで、相手の版をどう扱うかはクライアントの側の決まりでも変わる。

たとえ: podman の docker 互換の API は、通訳つきの窓口に近い。docker の CLI（客）は、いつもの言葉（docker の API）で話しかければ用が足りる。
ただし崩れる点: 窓口の通訳が「1.41 版の世代です」と名乗ると、客（docker の CLI 29）のほうが「1.44 版より古い通訳は相手にしない」という決まりを持っている。 それでも、たいていの用事は構わず自分の世代の言葉で話しかけ、通訳もそれを咎めずに答えるので通じてしまう。一覧（既定の images）など一部を頼むときだけ、客がその決まりを持ち出して断る。断っているのは窓口ではなく客である。

このサイトの檻は、なぜ podman でもそのまま動くのか

この節で分かること: このサイトの起動コマンドが、docker と rootless の podman の両方で同じ画面になる条件。

この記事の檻（lab-podman:1.0.0）は、docker を podman に読み替えた同じオプション（-d --name … --hostname host --stop-timeout 30 -v 名前:/home/lab/vm -v 名前:/home/lab/.lab）で、 rootless の podman（5.8.6）でも起動することを確かめてある（著者の記録 logs/podman-rootless.log: 起動から ssh まで35秒、lab env のランタイムは podman、 exec の umask 0022、CapBnd は podman の既定の 00000000800405fb、podman stop は5秒で終了コード 0）。そのまま動く理由は、この記事で見たことで説明できる。

起動コマンドの部分podman rootless で関係する章
特権を1つも求めない（--privileged・--cap-add・--device が無い。このサイトの例外は、--cap-add SYS_ADMIN の LinuC 1.09 と --device /dev/kvm の KVM の記事で、rootless の podman での動きはこの記事では確かめていない）rootless で渡せないものを、最初から頼んでいない。中の lab は一般ユーザなので、既定のケーパビリティの差（14個と11個）にも触れない第2章・この章
-v 名前:/home/lab/vm（名前付きボリューム）檻を起動した人の rootless の置き場所（~/.local/share/containers/storage/volumes）に作られ、ユーザ名前空間の中でイメージの持ち主（lab）がそのまま写される（記録の ls -ld /home/lab/vm）第2章・第3章
-p が無い1024 番未満の公開の制限も、rootlessport の中継も関係しない。練習機への ssh は檻の中で閉じている第4章
--stop-timeout 30・--hostname hostpodman にも同じオプションがあり、同じ意味で効くこの章
練習機は QEMU の完全エミュレーション（TCG）/dev/kvm も特権も要らないので、rootless でも動き方が変わらない—

逆に言うと、-p 80:80 を使う檻なら rootless の podman では起動できず（1024 番未満）、--device を使う檻は、読者の PC の装置と権限しだいで動き方が変わる。 読者に何も渡させない作りは、安全のためだけでなく、docker と podman のどちらでも同じ画面を出すためでもある。

たとえ: 読者に何も渡させない檻は、電池でもコンセントでも動く電化製品に近い。特別な部品（特権・装置・小さい番号のポート）を要求しないので、どちらの電源（docker・podman rootless）でも同じに動く。
ただし崩れる点: 電化製品なら電源で動き方は変わらないが、rootless の podman で動かした檻は、ログアウトで止まりうる（第6章）。電源の種類による違いが、1つだけ残る。
手を動かす: 実践編の演習07で、docker の CLI を podman のソケットにつなぎ、docker のコマンドで podman のコンテナを動かす。
確認

docker では動いていた、コンテナの中の一般ユーザ（--user 1000）の ping が、rootless の podman では「許可されていない」と失敗した。何が違うと考えられるか。どう確かめるか。

答え

net.ipv4.ping_group_range の値が違う。docker は 0 2147483647（全部のグループが特権なしの ICMP のソケットを使える）、podman は 0 0（グループ 0 だけ）にしている。 コンテナの中で cat /proc/sys/net/ipv4/ping_group_range を打てば分かる。一般ユーザの CapEff はどちらも 0 なので、ケーパビリティを比べても差は出ない。 podman で通すなら --cap-add NET_RAW を足す（この章で確かめた）。

確認

docker の CLI を podman のソケットにつないだら、docker run は動くのに docker images だけが API の版の誤りで止まった。この出力から何が言えるか。

答え

podman は docker の API を 1.41 版として真似ていて、docker の CLI（29.1.3）は 1.44 版より古いサーバとの版合わせを断る決まりを持っている。 ほとんどのコマンドはその断りを無視して、CLI 自身の版（1.52）の番号のまま頼み、podman はそれを咎めずに答えるので動く。既定の images の表示（と、--platform を付けた一部のコマンド）が断りを出す。断っているのは CLI の側で、podman が足りないのではない。 DOCKER_API_VERSION=1.41 で使う版を決め打ちするか、--format を付けると出る。

この章で分かったこと

持ち帰ってほしいこと

  • podman のコマンドの形は docker とほぼ同じだが、既定値は別（ケーパビリティ 11個と14個、ping_group_range の 0 0 と 0 2147483647、/run/.containerenv と /.dockerenv）
  • exec の umask は、docker は shim から受け継ぎ、podman はコンテナの --umask（既定 0022）を渡して決める。値は同じ 0022 でも決まり方が違う。TERM の決まりと stop の TERM → 10秒 → KILL は docker と同じで、podman は KILL に切り替えたことを警告する
  • podman は docker の API を（1.41 版として）真似られ、docker の CLI から使える。ただし docker の CLI 29 は古い版のサーバとの版合わせを断る決まりを持ち、既定の images の表示など一部が断られる（ほかのコマンドは CLI の版の番号のまま頼み、podman が咎めないので動く）
  • この記事の檻は読者に何も渡させないので、docker でも rootless の podman でも同じオプション・同じ画面で動く
