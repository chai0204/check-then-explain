3. 特殊なビットは「誰として動くか」と「誰が消せるか」を変える

root が持ち主で SUID を付けたシェルスクリプトを動かすと、名乗るのは root ではなく lab のままだった。同じ印を付けた id の複製は euid=0(root) と名乗る。特殊なビットは中身（inode）に付いた印にすぎず、その印をどう扱うかはカーネルが決めている。

この章のゴールと前提所要 20分
前提: 第2章まで読了前提: sudo が打てる所要 20分影響度 B出題範囲 1.02.1（重要度3）最終検証 2026-10-14

この章のゴール

  • SUID・SGID・スティッキービットを、ls -l の表示と chmod の先頭の桁（4桁で書いたときの左端）の両方で読み書きできる
  • 3つの特殊なビットが、ファイルとディレクトリでそれぞれ何を変えるかを言える
  • chown と chgrp を誰がどこまで使えるかを、実測の結果から説明できる
ここで覚えなくていいこと: ケーパビリティ（setcap）、nosuid マウント、SUID のプログラムを安全に書く方法、newgrp や sg でグループを切り替える方法は扱わない。ユーザやグループの作り方（useradd・groupadd）は主題1.08 の範囲なので、この檻では alice・bob・carol とグループ devs を最初から用意してある。

SUID — 誰として動くか

この節で分かること: SUID が付いたプログラムが、誰の権限で動くか。

この章は ~/work/ch3 で作業する。まず、一般ユーザが自分のパスワードを変えられる仕組みを見る。

$ mkdir -p ~/work/ch3
$ cd ~/work/ch3
$ ls -l /usr/bin/passwd /etc/shadow
-rw-r----- 1 root shadow   578 Oct 13 09:43 /etc/shadow
-rwsr-xr-x 1 root root   64152 May 30  2024 /usr/bin/passwd

パスワードが入っている /etc/shadow は、root しか書けない。それでも一般ユーザが passwd を打てば書き換わるのは、passwd の所有者の x の位置が s になっているからである。これが SUID（set-user-ID）で、付いているプログラムは打った人ではなく、ファイルの所有者として動く。

同じことを自分で作って確かめる。

ふつうこう考える

root が持ち主のファイルに SUID を付ければ、それは root として動く。 passwd がそうなのだから、自分で書いたスクリプトでも同じはずだ。

$ printf '#!/bin/bash\nid -un\n' > whoami.sh
$ sudo chown root:root whoami.sh
$ sudo chmod 4755 whoami.sh
$ ls -l whoami.sh
-rwsr-xr-x 1 root root 19 Oct 13 11:43 whoami.sh
$ ./whoami.sh
lab
だめな理由: 表示は passwd と同じ -rwsr-xr-x root root なのに、名乗ったのは lab だった。 Linux のカーネルは、#! で始まるスクリプトの SUID を無視する。 スクリプトは中身を別のプログラム（/bin/bash）が読んで動かすので、 読み込むまでの間にすり替えられる隙があり、root の権限を渡すと危ないからである。 SUID が効くのは、カーネルが直接実行する機械語のプログラムだけである。
$ sudo cp /usr/bin/id ./myid
$ sudo chmod 4755 myid
$ ls -l myid
-rwsr-xr-x 1 root root 39432 Oct 13 11:43 myid
$ ./myid
uid=1000(lab) gid=1000(lab) euid=0(root) groups=1000(lab)
$ id
uid=1000(lab) gid=1000(lab) groups=1000(lab)
$ file whoami.sh myid
whoami.sh: setuid Bourne-Again shell script, ASCII text executable
myid:      setuid ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=26e732a61e6fabef4bafe3165cb7b9fa31438cd2, for GNU/Linux 3.2.0, stripped

機械語（ELF）の id の複製は euid=0(root) を名乗った。uid は打った人（lab）のまま残り、権限の判定に使われる実効ユーザ ID（euid）だけが所有者に変わる。file は2つとも「setuid」と報告するので、印そのものは両方に付いている。違うのは、カーネルが印を見るかどうかである。

たとえ: 社長の印鑑を押した委任状に近い。 窓口（カーネル）は委任状を持ってきた人を、その用件に限って社長として扱う。passwd は「パスワードの変更」という用件だけを持った委任状である。
ただし崩れる点: 人間の窓口は書類の種類で扱いを変えないが、カーネルは変える。 同じ印鑑でも、中身を別の人（インタプリタ）が読み上げる形の書類（スクリプト）は、委任状として受け付けない。

s・S・t・T の読み方

この節で分かること: chmod の先頭の桁と、ls -l に出る文字の対応。

特殊なビットは3つあり、chmod の数値では先頭にもう1桁足して書く。表示は x の位置に重ねて出る。

$ touch s.txt
$ chmod 4755 s.txt; ls -l s.txt
-rwsr-xr-x 1 lab lab 0 Oct 13 11:43 s.txt
$ chmod 4644 s.txt; ls -l s.txt
-rwSr--r-- 1 lab lab 0 Oct 13 11:43 s.txt
$ chmod 2755 s.txt; ls -l s.txt
-rwxr-sr-x 1 lab lab 0 Oct 13 11:43 s.txt
$ chmod 2644 s.txt; ls -l s.txt
-rw-r-Sr-- 1 lab lab 0 Oct 13 11:43 s.txt
$ mkdir t
$ chmod 1777 t; ls -ld t
drwxrwxrwt 2 lab lab 4096 Oct 13 11:43 t
$ chmod 1770 t; ls -ld t
drwxrwx--T 2 lab lab 4096 Oct 13 11:43 t

小文字は「印 ＋ x あり」、大文字は「印はあるが x が無い」である。ファイルの -rwSr--r-- は、印は付いているのに実行できないので、SUID が働く場面が無い。一方、ディレクトリの S（SGID）と T（スティッキービット）は、x が無くても効く。演習03 の模範解答 drwxrws--T では、T のおかげで bob は alice のファイルを消せなかった（判定の記録）。記号でも付けられる。

$ chmod 755 s.txt; chmod u+s s.txt; ls -l s.txt
-rwsr-xr-x 1 lab lab 0 Oct 13 11:43 s.txt
$ chmod g+s,o+t t; ls -ld t
drwxrws--T 2 lab lab 4096 Oct 13 11:43 t
$ stat -c "%a %A %n" s.txt t
4755 -rwsr-xr-x s.txt
3770 drwxrws--T t
ビット先頭の桁記号表示の位置ファイルに付けるとディレクトリに付けると
SUID4u+s所有者の x → s / S所有者として動く（機械語のみ）（Linux では意味を持たない）
SGID2g+sグループの x → s / Sグループの権限で動く中に作ったものがディレクトリのグループを受け継ぐ
スティッキービット1o+tその他の x → t / T（いまの Linux では意味を持たない）中のファイルを消せるのは、その持ち主・ディレクトリの持ち主・root だけ

先頭の桁は足し算で組み合わせる。3770 は SGID（2）とスティッキービット（1）の両方で、stat の %a もそう報告した。

/tmp のスティッキービット — 誰が消せるか

この節で分かること: 誰でも書けるディレクトリで、他人のファイルが消えない仕組み。
$ ls -ld /tmp
drwxrwxrwt 1 root root 4096 Oct 13 11:43 /tmp
$ sudo -u alice touch /tmp/alice.txt
$ ls -l /tmp/alice.txt
-rw-rw-r-- 1 alice alice 0 Oct 13 11:43 /tmp/alice.txt
$ sudo -u bob rm -f /tmp/alice.txt
rm: cannot remove '/tmp/alice.txt': Operation not permitted
$ rm -f /tmp/alice.txt
rm: cannot remove '/tmp/alice.txt': Operation not permitted
$ sudo rm /tmp/alice.txt
$ ls -l /tmp/alice.txt
ls: cannot access '/tmp/alice.txt': No such file or directory

/tmp は rwxrwxrwt で、誰でも名前を作れる。第1章の規則なら、w を持つ全員が他人の名前も消せるはずだが、bob も lab も -f（確認を聞かない）を付けて断られた。最後の t がスティッキービットで、「消す・名前を変える」をファイルの持ち主（とディレクトリの持ち主・root）だけに絞る。root は消せた。

たとえ: 誰でも貼れる共用の掲示板に近い。 貼るのは自由だが、はがせるのは貼った本人と掲示板の管理者だけ、という決まりが付いている。
ただし崩れる点: 掲示板の決まりは「はがす」だけを縛るが、スティッキービットは「名前を変える」も縛る。

スティッキービットが縛るのは「消す」と「名前を変える」で、試験はこれで答える。他人のファイルの中身を書き換えられるかは、基本的にはそのファイル自身の権限で決まる。ただし Linux には fs.protected_regular という保護もあり、有効だと /tmp のような誰でも書けるスティッキーなディレクトリでは、他人のファイルへの > や >> が、ファイルが rw-rw-rw- でも Permission denied になる。値はコンテナを動かしているホストの設定で決まり（cat /proc/sys/fs/protected_regular）、この檻を記録したホストでは 1、Ubuntu 24.04 の実機の既定は 2 である（2 ではグループで書けるスティッキーなディレクトリにも及ぶ）。

chown と chgrp — 所有者を変えられるのは root だけ

この節で分かること: 一般ユーザが所有者とグループをどこまで変えられるか。
$ touch g.txt
$ ls -l g.txt
-rw-r--r-- 1 lab lab 0 Oct 13 11:43 g.txt
$ chgrp devs g.txt
chgrp: changing group of 'g.txt': Operation not permitted
$ chown alice g.txt
chown: changing ownership of 'g.txt': Operation not permitted
$ chgrp lab g.txt; echo "exit=$?"
exit=0

自分のファイルでも、所有者を他人に変えることはできない。chgrp は、自分が属しているグループへなら変えられる（lab は devs に入っていない）。他人に押し付けたり、入っていないグループの名義を名乗ったりできないようにしているのである。root はどちらもできる。

$ sudo chgrp devs g.txt; ls -l g.txt
-rw-r--r-- 1 lab devs 0 Oct 13 11:43 g.txt
$ sudo chown alice:devs g.txt; ls -l g.txt
-rw-r--r-- 1 alice devs 0 Oct 13 11:43 g.txt
$ sudo chown bob g.txt; ls -l g.txt
-rw-r--r-- 1 bob devs 0 Oct 13 11:43 g.txt
$ sudo chown :lab g.txt; ls -l g.txt
-rw-r--r-- 1 bob lab 0 Oct 13 11:43 g.txt
$ sudo chown carol: g.txt; ls -l g.txt
-rw-r--r-- 1 carol carol 0 Oct 13 11:43 g.txt
$ sudo chown bob:lab g.txt; ls -l g.txt
-rw-r--r-- 1 bob lab 0 Oct 13 11:43 g.txt
$ sudo chown carol. g.txt; ls -l g.txt
chown: warning: '.' should be ':': ‘carol.’
-rw-r--r-- 1 carol carol 0 Oct 13 11:43 g.txt
書き方変わるもの
chown alice file所有者だけ
chown alice:devs file所有者とグループ
chown :lab fileグループだけ（chgrp lab file と同じ）
chown carol: file所有者を carol に、グループを carol の主グループに
chown -R alice dirディレクトリの下全部（chgrp -R も同じ）

carol: のようにグループを空けると、グループはそのユーザの主グループになる。区切りに . を使う古い書き方（carol.）も同じ結果になるが、警告が出る。ユーザ名に . を含められるようになったため、区切りは : に一本化されつつある。試験で . 区切りが出ても、意味は : と同じと読めばよい。

SGID のディレクトリ — グループを受け継ぐ

この節で分かること: グループで共有するディレクトリに、SGID が必要な理由。
$ getent group devs
devs:x:1001:alice,bob
$ sudo mkdir /srv/team
$ sudo chgrp devs /srv/team
$ sudo chmod 2775 /srv/team
$ ls -ld /srv/team
drwxrwsr-x 2 root devs 4096 Oct 13 11:43 /srv/team
$ sudo -u alice touch /srv/team/plan.txt
$ sudo -u alice mkdir /srv/team/docs
$ ls -l /srv/team
total 4
drwxrwsr-x 2 alice devs 4096 Oct 13 11:43 docs
-rw-rw-r-- 1 alice devs    0 Oct 13 11:43 plan.txt
$ sudo -u alice touch /tmp/plan.txt
$ ls -l /tmp/plan.txt
-rw-rw-r-- 1 alice alice 0 Oct 13 11:43 /tmp/plan.txt

同じ alice が作ったのに、/srv/team の中ではグループが devs、/tmp では alice になった。SGID の付いたディレクトリの中で作ったものは、作った人の主グループではなく、ディレクトリのグループを受け継ぐ。中に作ったディレクトリ docs にも s が付いて、印そのものも下へ受け継がれている。

$ sudo -u bob sh -c "echo bob も書ける >> /srv/team/plan.txt"
$ cat /srv/team/plan.txt
bob も書ける
$ sudo -u bob rm /srv/team/plan.txt
$ ls -l /srv/team
total 4
drwxrwsr-x 2 alice devs 4096 Oct 13 11:43 docs

グループが devs で、権限が rw-rw-r-- なので、bob は alice のファイルに書き足せた。ところが bob は alice のファイルを消せてしまった。ディレクトリにグループの w があるからである（第1章）。共有ディレクトリで「仲間は書けるが、他人のファイルは消せない」にするには、/tmp の節で見たスティッキービットも要る。

やり直しで権限を数値で付け直すときに、1つ落とし穴がある。

$ mkdir sg
$ chmod 2775 sg; ls -ld sg
drwxrwsr-x 2 lab lab 4096 Oct 13 11:43 sg
$ chmod 755 sg; ls -ld sg
drwxr-sr-x 2 lab lab 4096 Oct 13 11:43 sg
$ stat -c "%a %n" sg
2755 sg
$ chmod 00755 sg; ls -ld sg
drwxr-xr-x 2 lab lab 4096 Oct 13 11:43 sg
$ chmod 2775 sg; chmod g-s sg; ls -ld sg
drwxrwxr-x 2 lab lab 4096 Oct 13 11:43 sg

chmod 755 と数値で書いたのに、s は残った（2755）。GNU の chmod は、ディレクトリの SUID と SGID を、3桁の数値の指定では外さない（man chmod）。共有ディレクトリの印をうっかり消さないための作りである。外すには g-s のように記号で書くか、00755 のように 0 を2つ付けた数値で書く（=755 でもよい）。通常ファイルにはこの例外は無い。

たとえ: 部署の共有キャビネットに入れた書類が、自動で部署の持ち物として登録される仕組みに近い。 誰が入れても「総務部」の札が付くので、部署の全員が手に取れる。
ただし崩れる点: 札（グループ）は自動で付くが、書き込めるかどうかは入れた人の umask が決める。 alice のファイルが rw-rw-r-- になったのは、sudo で動いた alice の umask が 0002 だったからで（第2章）、 umask が 022 の人が入れた書類は、札が付いても仲間は書き込めない。
手を動かす: 実践編の演習03は、SGID とスティッキービットを組み合わせて、 devs の共有ディレクトリ /srv/share を作る課題である。 判定は alice・bob・carol として実際にファイルを作り、消し、一覧しようとして確かめる。
確認

chmod 4755 /usr/local/bin/tool を実行した。ls -l の先頭10文字はどうなるか。

答え

-rwsr-xr-x。4 は SUID で、所有者の x の位置に s が出る。x が無い 4644 なら -rwSr--r-- と大文字になる。

確認

パーミッションが drwxrwxrwt のディレクトリで、一般ユーザ bob は alice のファイルを削除できるか。rm -f ならどうか。

答え

どちらもできない（Operation not permitted）。スティッキービット（t）が付いたディレクトリの中のファイルを消せるのは、 そのファイルの持ち主、ディレクトリの持ち主、root だけである。-f は確認を聞かないだけで、権限は変えない。

確認

ディレクトリに SGID を設定するコマンドと、その効果を答えよ。

答え

chmod g+s dir（または chmod 2775 dir のように、4桁で書いたときの先頭を 2 にする）。 中に新しく作ったファイルとディレクトリのグループが、作った人の主グループではなくディレクトリのグループになる。 中に作ったディレクトリにも SGID が付く。

確認

一般ユーザが、自分の所有するファイルに対してできることはどれか。2つ選べ。
a. chown で所有者を他のユーザにする
b. chgrp で、自分が属しているグループに変える
c. chgrp で、自分が属していないグループに変える
d. chmod でパーミッションを変える

答え

b と d。所有者を変えられるのは root だけで、chgrp は自分が属するグループへだけ変えられる （実測では chgrp devs も chown alice も Operation not permitted）。 chmod は所有者なら自由にできる。

この章で分かったこと

持ち帰ってほしいこと

  • SUID（4・u+s）は所有者として、SGID（2・g+s）はグループとして動かす印。/usr/bin/passwd は -rwsr-xr-x
  • Linux はスクリプトの SUID を無視する。効くのは機械語のプログラムだけ（実測: スクリプトは lab、id の複製は euid=0(root)）
  • スティッキービット（1・o+t）を付けたディレクトリでは、消せるのは持ち主・ディレクトリの持ち主・root だけ。/tmp は drwxrwxrwt
  • 小文字 s t は x あり、大文字 S T は x なし
  • SGID のディレクトリの中で作ったものは、ディレクトリのグループを受け継ぐ
  • 所有者を変えられるのは root だけ。一般ユーザの chgrp は、自分が属するグループへだけ
