1. 名前と中身は、別の場所にある

ディレクトリに r を残して x だけを外すと、ls には名前が並ぶのに、ls -l の残りの欄は全部 ? になり、ls 自身もファイルごとに「入れない」と言う。名前を持っているのはディレクトリで、権限も所有者も大きさも、名前の先にある別の場所が持っているからだ。この章は、その「別の場所」を見つけるところから始める。

前提: 檻が起動している前提: cd と ls が打てる所要 18分影響度 B出題範囲 1.02.1（重要度3）最終検証 2026-10-13

この章のゴール

  • ls -l の先頭10文字を、種類・所有者・グループ・その他に分けて読める
  • ディレクトリにとっての r・w・x が、それぞれ何を許すかを言える
  • 「消せるかどうか」をファイルではなくディレクトリの権限から判断できる
ここで覚えなくていいこと: ACL（getfacl / setfacl）、SELinux や AppArmor のような権限の外側にある仕組み、ケーパビリティの一覧は扱わない。ls -l の2列目（リンク数）は第7章で扱うので、ここでは「数字が1つある」と分かれば足りる。

ls -l の10文字

この節で分かること: ls -l の1行が、どの欄で何を表しているか。

この章は ~/work/ch1 で作業する。ファイルとディレクトリを1つずつ作って並べる。

$ mkdir -p ~/work/ch1
$ cd ~/work/ch1
$ echo "メモ" > memo.txt
$ mkdir box
$ ls -l memo.txt
-rw-r--r-- 1 lab lab 7 Oct 13 11:09 memo.txt
$ ls -ld box
drwxr-xr-x 2 lab lab 4096 Oct 13 11:09 box

先頭の10文字がパーミッション（と種類）である。1文字目が種類で、残りの9文字は3文字ずつ「所有者」「グループ」「その他」に分かれる。

-  rw-  r--  r--   1  lab  lab   7  Oct 13 10:11  memo.txt
^  ^^^  ^^^  ^^^   ^  ^^^  ^^^   ^  ^^^^^^^^^^^^  ^^^^^^^^
種類 所有者 グループ その他  リンク数 所有者 グループ 大きさ 更新時刻  名前
1文字目種類この檻で見られる例
-通常ファイルmemo.txt
dディレクトリbox
lシンボリックリンク/bin（第7章）
cキャラクタデバイス/dev/null（次の節）
bブロックデバイス無い（次の節）
p名前付きパイプmkfifo で作れる（次の節）
sソケット無い（プロセス同士の通信口。次の節で数える）

残りの9文字は、どれも r（読む）・w（書く）・x（実行する）の3つの並びで、無い権限は - になる。memo.txt は「所有者 lab は読み書きでき、グループ lab とその他は読むだけ」と読む。ファイルを作るときこの組み合わせが選ばれた理由は第2章で見る。

3つの欄のうち、使われるのは1つだけである。所有者なら所有者の欄、そうでなくグループの一員ならグループの欄、どちらでもなければその他の欄を見て、そこで決まる。足し合わせはしない。

$ echo "持ち主だけが読めない" > /tmp/owner.txt
$ chmod 044 /tmp/owner.txt
$ ls -l /tmp/owner.txt
----r--r-- 1 lab lab 31 Oct 13 11:09 /tmp/owner.txt
$ cat /tmp/owner.txt
cat: /tmp/owner.txt: Permission denied
$ sudo -u alice cat /tmp/owner.txt
持ち主だけが読めない

持ち主の lab は所有者の欄（---）で断られ、その他の欄（r--）は使われない。他人の alice には、その他の欄が使われて読めた。

大事なのは、この1行の中でファイル名だけが別の出どころを持つことである。これがこの章の結論なので、先に覚えておいてほしい。確かめるのは「ディレクトリの r と x は別の権限」の節である。

たとえ: 社員名簿と、本人が持つ社員証の関係に近い。 名簿には名前と社員番号だけが書いてあり、所属・権限・入社日は社員証のほうに書いてある。 ls -l は名簿で名前を引き、その番号の社員証を1枚ずつ見に行って、1行にまとめて見せている。
ただし崩れる点: 社員証は本人と一緒に動くが、ファイルの「社員証」は1か所に置かれたまま動かない。 名簿の側の名前を書き換えても、社員証は何も変わらない（第4章の mv）。

スペシャルファイル — 大きさの欄に数字が2つある

この節で分かること: /dev の下のファイルが何で、大きさの欄に何が入っているか。
$ ls -l /dev/null /dev/tty /dev/zero /dev/urandom
crw-rw-rw- 1 root root 1, 3 Oct 13 11:09 /dev/null
crw-rw-rw- 1 root root 5, 0 Oct 13 11:09 /dev/tty
crw-rw-rw- 1 root root 1, 9 Oct 13 11:09 /dev/urandom
crw-rw-rw- 1 root root 1, 5 Oct 13 11:09 /dev/zero
$ file /dev/null /dev/tty
/dev/null: character special (1/3)
/dev/tty:  character special (5/0)

種類が c で、大きさの欄に 1, 3 のような数字が2つ並ぶ。これは大きさではなく「どのドライバの何番か」を表すメジャー番号とマイナー番号である。こうした、中身の代わりに装置への入口を持つファイルをスペシャルファイル（デバイスファイル）と呼ぶ。読み書きはディスクではなく、カーネルのドライバに届く。

$ echo "どこにも残らない" > /dev/null
$ head -c 8 /dev/zero | od -c
0000000  \0  \0  \0  \0  \0  \0  \0  \0
0000010

/dev/null は書いたものを捨て、/dev/zero は読むたびに 0 のバイトを返し続ける。/dev/tty はいま使っている端末そのものである。どれも rw-rw-rw- で誰でも使える。

パイプ（|）に名前を付けてファイルとして置いたものが名前付きパイプ（FIFO）で、種類は p になる。

$ mkfifo pipe
$ ls -l pipe
prw-r--r-- 1 lab lab 0 Oct 13 11:09 pipe
$ file pipe
pipe: fifo (named pipe)

ディスクのようにブロック単位で読み書きする装置はブロックデバイス（種類 b）になる。実機なら /dev/sda や /dev/nvme0n1 がそうだが、この檻には1つも無い。

$ ls -l /dev | grep -c "^b"
0
$ find / -xdev -type s 2>/dev/null | wc -l
0

コンテナには、ディスクの装置そのものが渡されないからである。檻のファイルはホストの上に重ねたファイルシステムの中にあり、檻の中からディスクに直接触る経路は無い。ソケット（s）も、この檻のファイルシステムには1つも無かった。試験では b と s の意味と、/dev/sda のような例だけを覚えておけばよい。

ディレクトリの r と x は別の権限

この節で分かること: ディレクトリにとって r と x が、それぞれ何を許しているか。

box にファイルを2つ入れる。

$ echo "中身" > box/known.txt
$ echo "別の中身" > box/other.txt
$ ls -l box
total 8
-rw-r--r-- 1 lab lab  7 Oct 13 11:09 known.txt
-rw-r--r-- 1 lab lab 13 Oct 13 11:09 other.txt

ここから box の権限を1つずつ外していく。

ふつうこう考える

ディレクトリの r（読む）を残しておけば、中のファイルの一覧も、ls -l の詳しい情報も見られるはずだ。 x は「実行」の権限だから、プログラムではないディレクトリには関係ないだろう。

$ chmod u-x box
$ ls -ld box
drw-r-xr-x 2 lab lab 4096 Oct 13 11:09 box
$ ls box
ls: cannot access 'box/known.txt': Permission denied
ls: cannot access 'box/other.txt': Permission denied
known.txt  other.txt
$ ls -l box
ls: cannot access 'box/known.txt': Permission denied
ls: cannot access 'box/other.txt': Permission denied
total 0
-????????? ? ? ? ?            ? known.txt
-????????? ? ? ? ?            ? other.txt
$ cat box/known.txt
cat: box/known.txt: Permission denied
だめな理由: 名前は2つとも出た。しかし ls は名前ごとに Permission denied と言い、 ls -l の残りの欄は全部 ? で、中身も読めない。 ディレクトリの中に書かれているのは名前と、その実体の番号の対応表だけだからである。 r はこの表を読む権限で、名前が出るところまでしか届かない。 権限・所有者・大きさ・時刻は、番号の先にある実体（inode）の側に書いてあり、 そこへ進むには表を引いて先へ進む権限が要る。ディレクトリにとって、それが x である。 ls まで断られたのは、この檻の ls が ls --color=auto（~/.bashrc の設定）で、 色を決めるために名前の先の種類や権限を見に行ったからである。

逆に、x だけを残して r を外す。

$ chmod u=x box
$ ls -ld box
d--xr-xr-x 2 lab lab 4096 Oct 13 11:09 box
$ ls box
ls: cannot open directory 'box': Permission denied
$ cat box/known.txt
中身
$ cd box
$ pwd
/home/lab/work/ch1/box
$ cd ..
$ chmod 755 box

今度は一覧が出ないのに、名前を知っている known.txt は読める。cd もできる。表を読めなくても、名前を自分で知っていれば表を引いて先へ進めるからである。

権限通常ファイルに対してディレクトリに対して
r中身を読める名前の一覧を読める（ls）
w中身を書き換えられる名前を作る・消す・変える（x も一緒に要る）
xプログラムとして実行できる名前を引いて先へ進める（cd・cat dir/名前・ls -l の詳細）
たとえ: 鍵の掛かった部屋の前に貼られた名簿に近い。 r は「名簿を読める」、x は「名前を言えば中に通してもらえる」で、2つは別々に渡せる。 x だけの人は、名簿を見ることはできないが、会いたい人の名前を知っていれば会える。
ただし崩れる点: 部屋は1つだが、パスは何段にも重なる。/home/lab/work/ch1/box/known.txt を開くには、 途中のディレクトリ全部で「通してもらう」必要があり、1段でも x が欠けるとそこで止まる。

消せるかどうかは、ディレクトリが決める

この節で分かること: 書き込めないファイルが消せて、書き込めるファイルが消せない場合があること。

書き込み禁止のファイルを1つ作る。

$ echo "残す" > ro.txt
$ chmod 444 ro.txt
$ ls -l ro.txt
-r--r--r-- 1 lab lab 7 Oct 13 11:09 ro.txt
$ echo "追記" >> ro.txt
bash: ro.txt: Permission denied
$ rm ro.txt
rm: remove write-protected regular file 'ro.txt'? y
$ ls -l ro.txt
ls: cannot access 'ro.txt': No such file or directory

中身には1文字も足せないのに、rm は確認を1回聞いただけで消した（y は自分で打つ）。他人のファイルでも同じである。

$ sudo touch rootfile
$ ls -l rootfile
-rw-r--r-- 1 root root 0 Oct 13 11:09 rootfile
$ rm rootfile
rm: remove write-protected regular empty file 'rootfile'? y
$ ls -l rootfile
ls: cannot access 'rootfile': No such file or directory

root のファイルを、一般ユーザの lab が消せた。消すという操作は「ディレクトリの表から名前を1行消す」ことで、書き換わるのはファイルではなくディレクトリだからである。だから問われるのは、ディレクトリの w（と、中へ進むための x）になる。逆向きも確かめる。

$ chmod u-w box
$ ls -ld box
dr-xr-xr-x 2 lab lab 4096 Oct 13 11:09 box
$ rm box/other.txt
rm: cannot remove 'box/other.txt': Permission denied
$ ls -l box/other.txt
-rw-r--r-- 1 lab lab 13 Oct 13 11:09 box/other.txt
$ chmod u+w box

自分のファイルで、自分は書き込めるのに、消せない。表のほうに w が無いからである。rm が聞いてくる「write-protected」は親切な警告にすぎず、可否を決めているのはディレクトリの w と x である（第3章のスティッキービットが付いていれば、もう1つ条件が増える）。

たとえ: 図書館の蔵書目録から1行消す作業に近い。 本そのものに「貸出禁止」の札が付いていても、目録を編集する権限がある人は目録から行を消せる。 逆に、本の書き込みを許されていても、目録を触れない人は本を目録から外せない。
ただし崩れる点: 目録から消された本は棚に残るが、ファイルは名前が全部なくなった時点で実体も片づけられる。 名前がいくつあると片づけられないかは、第7章で数える。
手を動かす: 実践編の演習01は、ディレクトリの r と x を別々に渡して、 alice に「一覧は見せないが、1つのファイルだけは読ませる」状態を作る課題である。 判定は alice として実際に cat と ls を打って確かめる。

root はこの表をほとんど見ない

この節で分かること: root が r・w とディレクトリの x を無視し、ファイルの実行だけは x を見ること。
$ echo "ひみつ" > secret.txt
$ chmod 000 secret.txt
$ ls -l secret.txt
---------- 1 lab lab 10 Oct 13 11:09 secret.txt
$ cat secret.txt
cat: secret.txt: Permission denied
$ sudo cat secret.txt
ひみつ

---------- は所有者自身も読めないが、root には読める。root はパーミッションの表を見ずに読み書きを通すからである（コンテナの中の root も、この権限は持っている）。

ただし実行だけは違う。

$ printf "#!/bin/bash\necho 動いた\n" > run.sh
$ chmod 000 run.sh
$ sudo ./run.sh
sudo: ./run.sh: command not found
$ sudo bash -c ./run.sh
bash: line 1: ./run.sh: Permission denied
$ chmod 100 run.sh
$ ls -l run.sh
---x------ 1 lab lab 27 Oct 13 11:09 run.sh
$ ./run.sh
/bin/bash: ./run.sh: Permission denied
$ sudo ./run.sh
動いた
$ chmod 700 run.sh
$ ./run.sh
動いた

3つのことが同時に起きている。

  • x が1つも無いと、root でも実行しない。sudo ./run.sh の command not found は、sudo が自分で x の有無を見て出した文言で、 root のシェル（sudo bash -c）から打つと、カーネルが Permission denied で断る。誰かが実行してよいと示した印が無いものを、勝手にプログラムとして扱わないためである
  • x が1つでもあれば、root は r の有無に関係なく動かせる
  • 所有者は --x だけでは自分のスクリプトを動かせない。スクリプトは /bin/bash が中身を読んで実行するので、r も要る。行頭の /bin/bash: は、中身を読もうとして断られたインタプリタの名前である

ディレクトリの x は、root にとっては壁にならない。

$ chmod 000 box
$ ls -ld box
d--------- 2 lab lab 4096 Oct 13 11:09 box
$ ls box
ls: cannot open directory 'box': Permission denied
$ sudo ls box
known.txt  other.txt
$ sudo cat box/known.txt
中身
$ chmod 755 box

root は r も x も無いディレクトリを一覧し、通り抜けて中を読んだ。root が見るのは、通常ファイルを実行するときの x だけである。

たとえ: 合鍵を持った管理人に近い。 どの部屋の鍵も開けて中の書類を読めるし、書き込みもできる。
ただし崩れる点: 管理人でも、「実行してよい」と誰も印を付けていない書類を手順書として扱うことはしない。 合鍵は扉を開けるだけで、ファイルの性質（実行できるものかどうか）までは変えない。
確認

ls -l の出力が crw-rw-rw- 1 root root 1, 3 Oct 13 11:09 /dev/null だった。 このファイルの種類は何か。また 1, 3 は何を表すか。

答え

キャラクタデバイス（スペシャルファイル）。1, 3 は大きさではなく、メジャー番号とマイナー番号で、 どのドライバのどの装置かを表す。b ならブロックデバイス、p なら名前付きパイプ、l ならシンボリックリンク。

確認

所有者の権限が r-- のディレクトリ dir がある（x が無い）。所有者が ls dir と cat dir/a.txt を打つとどうなるか。

答え

ls dir は名前の一覧を出す（色付きの ls では、ファイルごとに Permission denied も出る。ls -l dir では名前以外が ? になる）。 cat dir/a.txt は Permission denied になる。名前の先へ進むにはディレクトリの x が要る。

確認

自分のディレクトリ（drwxr-xr-x）の中に、root が所有する -rw-r--r-- のファイルがある。 一般ユーザの自分は、このファイルを rm で消せるか。

答え

消せる（端末では「write-protected」と確認を聞かれる）。消すのはディレクトリの表から名前を外す操作なので、 見られるのはディレクトリの w と x である。ファイル自身の権限や所有者は関係ない。 他人のファイルを消せないようにする仕組みは第3章のスティッキービットである。

確認

パーミッションが ----------（000）のシェルスクリプトを、root で ./run.sh として実行できるか。

答え

できない。root は r と w（とディレクトリの x）を無視するが、通常ファイルの実行は x がどこかに1つ立っていないと許さない （実測では root のシェルから bash: line 1: ./run.sh: Permission denied。sudo ./run.sh なら sudo が先に command not found と言う）。 x が1つでもあれば、root は r が無くても実行できる。

この章で分かったこと

持ち帰ってほしいこと

  • ls -l の先頭10文字は「種類1文字 ＋ 所有者・グループ・その他の rwx」
  • 種類: - 通常 / d ディレクトリ / l シンボリックリンク / c キャラクタデバイス / b ブロックデバイス / p 名前付きパイプ / s ソケット
  • ディレクトリの中身は「名前 → 実体の番号」の表。r は表を読む、x は表を引いて先へ進む、w は表を書き換える
  • r だけのディレクトリでは名前しか見えず、ls -l の残りは ? になる。権限も大きさも名前の先（inode）にあるから
  • 3つの欄のうち使われるのは1つだけ（所有者 → グループ → その他の順に、最初に当てはまった欄）
  • ファイルを消せるかどうかはディレクトリの w と x が決める。ファイル自身の w ではない
  • root は r・w とディレクトリの x を無視するが、x が1つも無い通常ファイルは実行しない
