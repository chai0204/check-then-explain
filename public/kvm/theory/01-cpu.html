1. 仮想化支援機能は、CPU の自己申告

あなたの PC の CPU には、仮想マシンを速く動かすための仕組み（Intel は VT-x、AMD は AMD-V）があり、/proc/cpuinfo に vmx か svm という印で出る。 QEMU がソフトだけで作った CPU（TCG）で練習機を起動し、中で同じものを見ると、Intel の PC の上で AMD の CPU を名乗り、svm まで出す。 練習機のカーネルはそれを信じて、KVM まで用意した。CPU の印は、CPU が「持っている」と答えた内容でしかない （TCG の QEMU は、その AMD-V もソフトで真似していて、練習機の中の KVM で仮想マシンまで動いた）。

前提: 檻が起動している（実践編）所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • lscpu と /proc/cpuinfo で、CPU が仮想化支援機能（VT-x / AMD-V）を名乗っているかを確かめられる
  • 練習機（TCG）の CPU が何を名乗っているかを出力で示し、それを答えているのが QEMU だと説明できる
  • 「CPU が印を出している」と「KVM が使える」が別のことだと言える
  • TCG の練習機の中の KVM で、小さな仮想マシンが動くことを示せる（QEMU が AMD-V もソフトで真似している）
ここで覚えなくていいこと: CPUID 命令の細かい仕様（何番の問い合わせのどのビットか）、VT-x と AMD-V の命令の違い（VMLAUNCH・VMRUN など）、 /proc/cpuinfo の vmx flags の各項目の意味、ファームウェア（BIOS / UEFI）の設定画面で仮想化支援を有効にする手順。

あなたの PC の CPU は、仮想化支援を名乗っている

この節で分かること: vmx と svm が何の印で、どこに出るか。

檻に入ったら、外（lab@host）で CPU を見る。

$ lscpu | grep -E '^(Vendor ID|Model name|Virtualization|Hypervisor vendor):'
Vendor ID:                               GenuineIntel   ← CPU のメーカー
Model name:                              Intel(R) Core(TM) Ultra 9 285H
Virtualization:                          VT-x   ← 仮想化支援機能の名前

$ grep -m1 -o -w -E 'vmx|svm' /proc/cpuinfo
vmx

この2つの出力は、あなたの画面では本文と違って正常である。あなたの PC の CPU が出る（AMD の PC なら AuthenticAMD・AMD-V・svm）。 この檻はコンテナなので、/proc/cpuinfo を作っているのはあなたの PC のカーネルで、見えるのはあなたの PC の CPU そのものである（LinuC 1.01 の第3章）。

CPU は、仮想マシンの中の OS（ゲスト）の命令を、そのまま自分で実行できる仕組みを持っている。 ゲストが「ハードウェアを直接触る」ような命令を実行しようとした瞬間にだけ止まり、仮想マシンを動かしている側（ハイパーバイザー）に処理を戻す。 これが仮想化支援機能で、Intel のものを VT-x、AMD のものを AMD-V と呼ぶ。Linux は、CPU がこれを持っていると答えたとき、/proc/cpuinfo の flags の行に Intel なら vmx、AMD なら svm を並べる。lscpu の Virtualization の行は、それを名前で言い直したものである。

たとえ: 仮想化支援機能は、大きな工場に「来客用の作業場」が作り付けてあることに近い。来客（ゲスト）は自分の道具で自由に作業できるが、 危ない機械（ハードウェア）に手を伸ばした瞬間にブザーが鳴り、工場の係（ハイパーバイザー）が代わりに操作する。作業場が無ければ、係が来客の作業を1つずつ真似して代わりにやるしかない。
ただし崩れる点: 来客は自分が作業場にいると分かっているが、ゲストの OS は、ハイパーバイザーが知らせない限り、自分の命令が作業場の中で実行されていることを知らない（知らせ方は第5章）。ブザーが鳴っても、ゲストからは何も起きなかったように見える。

練習機の CPU は、AMD を名乗る

この節で分かること: QEMU がソフトで作った CPU（TCG）が、何を名乗るか。

練習機（Ubuntu 24.04 の仮想マシン）を起動する。qemu-linuc は、練習機を qemu-system-x86_64 で直接起動する、この檻の短縮のコマンドである。 後ろに書いたものはそのまま QEMU のオプションになり、実際に打ったコマンド行を ▶ で表示して、練習機が起動し終わるまで待つ。-accel tcg は、QEMU に「練習機の命令を翻訳して実行する方式（TCG）で動け」と頼むオプションである。

$ qemu-linuc -accel tcg
▶ qemu-img create -f qcow2 -b /var/lib/lab-vm/linuc-guest.qcow2 -F qcow2 /home/lab/vm/linuc.qcow2 20G   ← 最初の1回だけ。練習機のディスク（土台との差分）を作る
▶ qemu-system-x86_64 -machine q35 -m 1536 -smp 2 \
    -bios /usr/share/ovmf/OVMF.fd \
    -drive file=/home/lab/vm/linuc.qcow2,if=virtio \
    -netdev user,id=n0,hostfwd=tcp:127.0.0.1:2222-:22 \
    -device virtio-net-pci,netdev=n0,addr=0x10 \
    -display none -serial file:/home/lab/vm/serial.log \
    -daemonize -pidfile /home/lab/vm/qemu.pid \
    -accel tcg   ← あなたが足したオプション
練習機が起動し終わりました（QEMU を起動してから 31.0 秒。カーネルの最初の表示は 6.1 秒の時点）
ssh linuc で入れます

秒数は、あなたの PC の速さで変わる。▶ の固定の部分（メモリ・CPU の数・UEFI のファームウェア・ディスク・NIC・シリアル）が何をしているかは、QEMU の記事で1つずつ扱う。 この記事で変えるのは、最後の行（-accel と -cpu）だけである。

起動し終わったら、練習機に入って、外と同じコマンドを打つ。

$ ssh linuc

  LinuC 練習機（Ubuntu 24.04 / 仮想マシン）
  - 採点は外のコンテナが持っています。この中でも lab check NN で答え合わせできます
  - 管理用の NIC（enp0s16）を止めると ssh が切れます。そのときは外で vm console

案内の最後の行にある vm console は、libvirt に登録した練習機（第6章の vm start で起動するもの）のシリアルにつなぐコマンドである。 qemu-linuc で起動した練習機は libvirt に登録されておらず、シリアルはファイル（~/vm/serial.log）に書き出しているので、vm console ではつながらない。この記事では練習機の NIC を止めないので、使わない。

$ lscpu | grep -E '^(Vendor ID|Model name|Virtualization|Hypervisor vendor):'
Vendor ID:                               AuthenticAMD   ← Intel の PC の上で、AMD を名乗る
Model name:                              QEMU Virtual CPU version 2.5+   ← QEMU が作った CPU の名前
Virtualization:                          AMD-V

$ grep -o -w -E 'vmx|svm|hypervisor' /proc/cpuinfo | sort | uniq -c
      2 hypervisor   ← 「自分は仮想マシンだ」という印（第5章）
      2 svm   ← AMD-V の印。CPU 2個に1つずつ

あなたの PC の CPU が Intel でも AMD でも、練習機は同じ答えを返す（ここは全員が本文と同じ画面になる）。 メーカーは AuthenticAMD、名前は QEMU Virtual CPU version 2.5+。そして、仮想化支援機能 AMD-V を持っていると名乗る（練習機の CPU は2個なので、印も2つずつ出る）。Hypervisor vendor の行は出なかった（第5章で、KVM のときと比べる）。

ふつうこう考える

vmx や svm は、CPU の回路に作り付けられた機能の印だ。QEMU がソフトで作った CPU には回路が無いのだから、 この印は形だけで、練習機の中に KVM（仮想化支援機能を使って仮想マシンを動かす Linux の仕組み）が用意されることは無いはずだ。

$ ls -l /dev/kvm
crw-rw---- 1 root kvm 10, 232 Oct 14 03:35 /dev/kvm   ← 練習機の中にも KVM の入口がある

$ lsmod | grep kvm
kvm_amd               212992  0   ← AMD の仮想化支援機能を使う KVM の部品
ccp                   147456  1 kvm_amd
kvm                  1404928  1 kvm_amd
irqbypass              12288  1 kvm

$ sudo dmesg | grep -E 'Hypervisor detected|paravirtualized|kvm_amd|kvm_intel'
[    0.079844] Booting paravirtualized kernel on bare hardware
[   12.697535] kvm_amd: Nested Virtualization enabled   ← 設定（nested）の報告。この中で作る仮想マシンにも AMD-V を見せる
[   12.698007] kvm_amd: Nested Paging disabled
[   12.706095] kvm_amd: PMU virtualization is disabled
だめな理由: 練習機のカーネルは kvm_amd を読み込み、/dev/kvm（KVM の入口。第2章）まで作っていた。 OS が CPU の正体を知る主な方法は、CPUID という命令で CPU に尋ねることである（ほかに、MSR という CPU の設定を読むこともある）。答えに AMD-V があれば、カーネルは svm を並べ、kvm_amd を読み込む。 TCG の練習機では、その問いに答えているのは QEMU である。QEMU が何も指定されないときに作る CPU（qemu64 という型）は「AMD の CPU で、AMD-V を持っている」と答える。 kvm_amd が読み込まれるときに確かめるのも、この答え（AMD の CPU か、svm の印があるか）で、AMD-V を動かしてみるわけではない。 AMD-V を実際に使い始めるのは、仮想マシンを作るときである（練習機のカーネル 6.8 の場合。Linux 6.12 からは、既定で読み込んだときに使い始める。kvm の設定 enable_virt_at_load の既定が Y）。 だから kvm_amd は、AMD-V を試さないまま初期化を終え、/dev/kvm を作った。 （Nested Virtualization enabled は判断の結果ではなく、kvm_amd の設定 nested が有効だという報告で、この中で作る仮想マシンにも AMD-V を見せる、という意味である。） CPU の印は、回路の有無ではなく、CPU（ここでは QEMU）が「持っている」と答えた内容だった。 ただし、この印は形だけでもない。TCG の QEMU は AMD-V の仕組みもソフトで真似していて、この練習機の KVM で、さらに仮想マシンを動かすこともできる（次の節で確かめる）。 （Booting paravirtualized kernel on bare hardware の行は第5章で読む。）

CPU の答えは、練習機の中から直接読める。cpuid というカーネルの部品を読み込むと、/dev/cpu/0/cpuid というファイルから、CPUID の答えを番号ごとに読み出せる。 読む場所（-j で飛ばすバイト数）が CPUID の問いの番号で、0x40000000 は「あなたはどのハイパーバイザーか」を尋ねる番号である。

$ sudo modprobe cpuid

$ sudo od -A n -c -j $((0x40000000)) -N 16 /dev/cpu/0/cpuid
 001  \0  \0   @   T   C   G   T   C   G   T   C   G   T   C   G   ← QEMU の TCG が、CPU の答えに自分の名前を書いている

最初の4バイトの後ろに、TCGTCGTCGTCG と並んでいる。CPU の答えを書いているのが QEMU の TCG だということを、答えそのものが名乗っている。 同じものを KVM の練習機で読むと何が出るかは、第5章で見る。

$ exit
logout
Connection to 127.0.0.1 closed.

exit で練習機から出て、外に戻った。

たとえ: CPUID は、OS が CPU に渡す問診票に近い。「メーカーは」「何ができるか」の欄に CPU が自分で書き込み、OS はそれを読んで、どの部品（ドライバ）を使うか決める。 TCG では、問診票を書いているのは CPU ではなく、CPU の代わりをしている QEMU である。
ただし崩れる点: 病院は問診票の後に検査をして確かめるが、仮想マシンの中の OS は、答えを外から確かめる方法を持たない。MSR を読んでも、答えるのはやはりハイパーバイザーである。
見たもの外（あなたの PC の CPU。著者の場合）練習機の中（TCG・既定の CPU）
メーカー（Vendor ID）GenuineIntelAuthenticAMD
名前（Model name）Intel(R) Core(TM) Ultra 9 285HQEMU Virtual CPU version 2.5+
仮想化支援の印vmx（VT-x）svm（AMD-V）
答えているのは本物の CPUQEMU（ソフト）

その AMD-V で、練習機の中の KVM も動く

この節で分かること: QEMU が名乗った AMD-V を、練習機の中の KVM が本当に使えるか。

練習機の中の KVM で、仮想マシンを1つ動かしてみる。この檻には、そのための小さなプログラム tiny-vm.py を置いてある。 練習機の /dev/kvm に仮想マシンを作り、命令を6つ（2+2 を計算して、答えの文字を装置に書き、止まる）だけ実行させる。 仮想マシンを作る前と後には、CPU の AMD-V のスイッチ（EFER という CPU の設定の SVME）も読む。中身は次のとおり（読み飛ばしてよい。KVM に頼むこと（ioctl）が順に並んでいる）。

tiny-vm.py の中身 
$ cat /usr/local/share/lab-kvm/tiny-vm.py
"""練習機の中の KVM（入れ子の仮想化）に、小さな仮想マシンを1つ作って動かす（練習機の中の root で動かす）。
  檻（lab@host）から: ssh linuc sudo python3 - < /usr/local/share/lab-kvm/tiny-vm.py
仮想マシンのメモリに置く命令は6つだけ（実モード）:
  mov al,2 / add al,2 / add al,'0' / mov dx,0x3f8 / out dx,al / hlt
  2+2 を計算して、文字 '4' を装置の番号 0x3f8（シリアル）に書き、hlt で止まる。
  装置への書き込みと hlt では、KVM が仮想マシンを止めて、このプログラムに知らせる（KVM_EXIT_IO・KVM_EXIT_HLT）。
仮想マシンを作る前と後に、CPU 0 の AMD-V のスイッチ（EFER という設定の SVME。MSR 0xC0000080 の bit 12）も読む。
"""
import ctypes, fcntl, mmap, os, struct, subprocess


def svme():
    f = os.open("/dev/cpu/0/msr", os.O_RDONLY)
    v = int.from_bytes(os.pread(f, 8, 0xC0000080), "little")
    os.close(f)
    return (v >> 12) & 1


subprocess.run(["modprobe", "msr"], check=True)
print("AMD-V のスイッチ（EFER.SVME）:", svme())
kvm = os.open("/dev/kvm", os.O_RDWR)
vm = fcntl.ioctl(kvm, 0xAE01, 0)                                   # KVM_CREATE_VM
print("KVM_CREATE_VM → 仮想マシンを作った")
print("AMD-V のスイッチ（EFER.SVME）:", svme())
mem = mmap.mmap(-1, 0x10000)                                       # 仮想マシンのメモリ（64KiB）
code = bytes([0xB0, 0x02, 0x04, 0x02, 0x04, 0x30, 0xBA, 0xF8, 0x03, 0xEE, 0xF4])
mem[0x1000:0x1000 + len(code)] = code
addr = ctypes.addressof(ctypes.c_char.from_buffer(mem))
fcntl.ioctl(vm, 0x4020AE46, struct.pack("<IIQQQ", 0, 0, 0, 0x10000, addr))   # KVM_SET_USER_MEMORY_REGION
cpu = fcntl.ioctl(vm, 0xAE41, 0)                                   # KVM_CREATE_VCPU
run = mmap.mmap(cpu, fcntl.ioctl(kvm, 0xAE04, 0))                  # KVM_GET_VCPU_MMAP_SIZE
sregs = bytearray(312)
fcntl.ioctl(cpu, 0x8138AE83, sregs)                                # KVM_GET_SREGS
struct.pack_into("<Q", sregs, 0, 0)                                # cs の base を 0
struct.pack_into("<H", sregs, 12, 0)                               # cs の selector を 0
fcntl.ioctl(cpu, 0x4138AE84, bytes(sregs))                         # KVM_SET_SREGS
regs = bytearray(144)
struct.pack_into("<QQ", regs, 128, 0x1000, 0x2)                    # rip = 0x1000、rflags = 2
fcntl.ioctl(cpu, 0x4090AE82, bytes(regs))                          # KVM_SET_REGS
while True:
    fcntl.ioctl(cpu, 0xAE80, 0)                                    # KVM_RUN
    reason = struct.unpack_from("<I", run, 8)[0]
    if reason == 2:                                                # KVM_EXIT_IO
        size, port, off = run[33], struct.unpack_from("<H", run, 34)[0], struct.unpack_from("<Q", run, 40)[0]
        print(f"KVM_RUN → KVM_EXIT_IO（装置 {port:#x} に {run[off:off + size]!r} を書いた）")
    elif reason == 5:                                              # KVM_EXIT_HLT
        print("KVM_RUN → KVM_EXIT_HLT（hlt で止まった）")
        break
    else:
        print("KVM_RUN → 止まった理由", reason)
        break

ssh linuc sudo python3 - は、練習機の中の root で Python を動かし、プログラムを標準入力（< で渡した、この檻のファイル）から読ませる、という意味である。

$ ssh linuc sudo python3 - < /usr/local/share/lab-kvm/tiny-vm.py
AMD-V のスイッチ（EFER.SVME）: 0   ← 読み込んだだけの kvm_amd は、スイッチを入れていない
KVM_CREATE_VM → 仮想マシンを作った   ← 練習機の KVM に、仮想マシンを作った
AMD-V のスイッチ（EFER.SVME）: 1   ← 仮想マシンを作ると、スイッチが入った
KVM_RUN → KVM_EXIT_IO（装置 0x3f8 に b'4' を書いた）   ← 2+2 の答えを、装置に書いた
KVM_RUN → KVM_EXIT_HLT（hlt で止まった）   ← hlt で止まった

仮想マシンを作る前、AMD-V のスイッチは 0 だった。kvm_amd は、読み込まれたときに AMD-V を試していない（前の節）。仮想マシンを作ると 1 になり、 仮想マシンは 2+2 を計算して、文字 4 を装置（番号 0x3f8）に書き、hlt で止まった。KVM は、装置に触れたときと止まったときに仮想マシンを止めて、プログラムに知らせている。

この仮想マシンの命令を実行したのも、本物の CPU ではない。QEMU の TCG が、AMD-V の仕組み（仮想マシンに入る命令や、装置に触れたら止まる仕組み）までソフトで真似して、ひとまとまりずつ翻訳して実行した。 だから TCG の練習機の svm は、名乗りだけでなく、中身も QEMU が持っている。それでも kvm_amd が印を信じたのは、中身を確かめたからではない。

たとえ: TCG の練習機の中の KVM は、朗読劇の中の劇中劇に近い。TCG の QEMU は、役者の台詞を1つずつ読み上げる朗読者である（第3章）。 劇の中でさらに小さな劇（仮想マシン）が始まっても、その台詞も朗読者が読み上げ、「劇中劇が始まる」「ここで止まる」という合図（AMD-V の仕組み）まで朗読者が演じる。
ただし崩れる点: 朗読劇の観客は朗読者が読んでいると知っているが、練習機の中の KVM は、頼んだ AMD-V を本物の CPU が受け持っているのか、朗読者が真似しているのかを知らないし、知らなくても動く。

練習機を止める。qemu-linuc stop は、ssh で練習機に sudo poweroff を頼み、QEMU のプロセスが終わるまで待つ。

$ qemu-linuc stop
▶ ssh linuc sudo poweroff
止まりました（3.5 秒）

印があることと、使えることは別

この節で分かること: 印が「ある」ときと「無い」ときに、それぞれ何が言えるか。

印は CPU の申告なので、印が無ければ、その OS からは仮想化支援機能を使えない（カーネルは KVM の部品を読み込まない）。 ただし、印が無い理由は CPU が持っていないとは限らない。ファームウェア（BIOS / UEFI）の設定で仮想化支援機能が切られていると、Intel の CPU では Linux 5.6 以降、AMD の CPU では Linux 6.7 以降は、印を並べない（このときカーネルは、CPUID ではなく MSR を読んで、切られていることを知る）。 仮想マシンの中では、外のハイパーバイザーが印を見せていないこともある（第5章で、自分で消して確かめる）。

反対に、印があっても、KVM が使えるとは限らない。印は「CPU がそう答えた」というだけで、使うにはさらに、カーネルに KVM の部品があり、その入口のファイルを開けることが要る。 この檻の外（あなたの PC）は vmx を出していたが、この檻の中で KVM が使えるかどうかは、檻をどう起動したかで決まる。第2章で、その条件を1つずつ確かめる。

たとえ: 印は、運転免許証の「中型」の欄に丸があることに近い。丸が無ければ中型には乗れない。丸があっても、目の前の車の鍵を持っていなければ乗れない。
ただし崩れる点: 免許証は発行元が試験で確かめた記録だが、CPU の印は CPU（または CPU の代わりをしている QEMU）の自己申告で、誰も確かめていない。 練習機の svm は、本人ではなく代理人（QEMU）が書いた丸で、この代理人は実際に中型も運転できた（前の節）。それでも、丸が正しいかどうかを、カーネルは確かめずに信じている。
手を動かす: 実践編の演習01で、練習機を TCG で起動して、中から見える CPU を確かめる（KVM が使えない PC でもできる）。 演習05では反対に、練習機の CPU から仮想化支援の印を消して、練習機の中の /dev/kvm が消えることを確かめる。
確認

ある Linux の計算機で grep -m1 -o -w -E 'vmx|svm' /proc/cpuinfo を打つと svm と出た。この出力から言えることはどれか。

A. この計算機は AMD の CPU を積んだ実機である
B. この計算機の OS から見ると、CPU は AMD-V を持っていると答えている
C. この計算機では KVM が使える
D. この計算機は仮想マシンではない

答え

B。印は CPU（仮想マシンなら、CPU の代わりをしているハイパーバイザー）が CPUID で答えた内容である。 TCG の練習機は Intel の PC の上で svm を出したので、A も D も言えない。C は、カーネルの部品と /dev/kvm を開けるかどうか（第2章）を見ないと分からない。

確認

練習機（TCG）の中で lsmod | grep kvm に kvm_amd が出たのはなぜか。「誰が、何と答えたから」の形で説明せよ。

答え

QEMU が、CPUID の問いに「AMD の CPU で、AMD-V を持っている」と答えたから。練習機のカーネルはその答えを見て、AMD 用の KVM の部品 kvm_amd を読み込み、/dev/kvm を作った。 読み込みのときに AMD-V を試してはいないし、練習機のカーネルからは、その答えを外から確かめる方法も無い（その AMD-V は、QEMU がソフトで真似していて、実際に使えた）。

確認

VT-x を持っているはずの Intel の CPU の PC で、grep -c vmx /proc/cpuinfo が 0 を返した。まず何を疑うか。

答え

ファームウェア（BIOS / UEFI）の設定で仮想化支援機能が切られていること。Intel の CPU では、Linux 5.6 以降は切られていると vmx を並べない（AMD の CPU の svm も、Linux 6.7 以降は同じ）。 その PC 自体が仮想マシンなら、外のハイパーバイザーが印を見せていないこともある（第5章）。

この章で分かったこと

持ち帰ってほしいこと

  • 仮想化支援機能は、ゲストの命令を CPU に直接実行させ、危ない命令のときだけハイパーバイザーに戻す仕組み。Intel は VT-x（印は vmx）、AMD は AMD-V（svm）
  • lscpu の Virtualization と /proc/cpuinfo の flags で見る。コンテナの中ではあなたの PC の CPU が見える
  • OS は CPU の正体を主に CPUID の答えで知る。TCG の練習機では QEMU が答え、Intel の PC の上で AuthenticAMD と svm を名乗る
  • 練習機のカーネルはその答えを信じて kvm_amd を読み込み、/dev/kvm を作った（読み込みのときに AMD-V は試していない）。印は申告で、使えるかどうかは別に決まる（第2章）
  • TCG の QEMU は AMD-V の仕組みもソフトで真似しているので、練習機の中の KVM で仮想マシンも動いた。命令を実行したのは、ここでも QEMU のソフトである
