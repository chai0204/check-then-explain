6. このサイトの練習機が KVM を使わない理由

このサイトの仮想マシン型の檻（LinuC の記事の練習機）は、libvirt の定義に type='qemu' と書いてあり、/dev/kvm を渡しても TCG で動く。 KVM を使えば起動は数倍速いが、練習機の中の画面が読む人の PC で変わり、/dev/kvm を渡せない人は練習機を動かせず、渡せる人にも起動のオプションを増やすことになる。 この檻は、全員に同じ画面を出し、何の権限も求めないために、速さを払っている。

前提: 第5章まで読了所要 15分影響度 B最終検証 2026-10-14

この章のゴール

  • このサイトの仮想マシン型の檻が TCG で動くことを、定義（XML）と、動いている QEMU の両方で示せる
  • KVM にすると練習機の中の何が読む人ごとに変わるかを、この記事の記録から挙げられる
  • TCG を選んだ代わりに払っているもの（時間と CPU）を、数字で言える
ここで覚えなくていいこと: libvirt の定義（XML）の他の項目、virsh の使い方（LinuC 1.01 の第1章）、 定義を type='kvm' に書き換える手順、クラウドの仮想マシンで入れ子の仮想化を有効にする設定。

定義には type='qemu' と書いてある

この節で分かること: このサイトの仮想マシン型の檻が、何で練習機を動かしているか。

この記事の檻は、LinuC の仮想マシン型の檻と同じ土台（lab-linuc-machine）の上にあり、その檻が使う libvirt と練習機の定義も入っている。 LinuC の記事では、読者は vm start や virsh start で練習機を起動していた。vm は、中で virsh を打つ短縮のコマンドである。 qemu-linuc の練習機を止めてから、定義を見る。

$ qemu-linuc stop
▶ ssh linuc sudo poweroff
止まりました（3.5 秒）

$ grep -E '<domain|<cpu' /etc/lab-vm/domain.xml.in
<domain type='qemu' xmlns:qemu='http://libvirt.org/schemas/domain/qemu/1.0'>   ← TCG で動かす、という指定
  <cpu mode='maximum'/>   ← QEMU が真似できる機能を全部見せる

$ virsh capabilities | grep -o "<domain type='[a-z]*'" | sort | uniq -c
      2 <domain type='kvm'   ← この檻なら、libvirt は KVM の仮想マシンも作れる
      2 <domain type='qemu'

<domain type='qemu'> は libvirt に「QEMU の TCG で動かす」と言っている。KVM で動かすなら type='kvm' と書く。 virsh capabilities は、libvirt が作れる仮想マシンの種類を数えたもので、この檻（/dev/kvm を開ける）では kvm と qemu の両方がある （第2章の、--device なしの2つ目の檻では qemu だけだった。数の 2 は、libvirt が作れる練習機の種類の数で、64 ビットの x86_64 と 32 ビットの i686 の分）。

たとえ: virsh capabilities と定義の type の関係は、レストランのメニューと注文票に近い。メニューに「特急（kvm）」が載っていても、 注文票に「普通（qemu）」と書けば、普通のものが出てくる。
ただし崩れる点: レストランのメニューは店が決めて毎日同じだが、capabilities は檻の起動のしかた（/dev/kvm を渡したか）で変わる。 同じ注文票でも、メニューに特急が無い檻では、type='kvm' と書いた練習機はそもそも起動できない。

ふつうこう考える

LinuC の記事の仮想マシン型の檻も、起動のときに --device /dev/kvm（と --group-add）を足せば、libvirt は KVM が使えることに気づいて、練習機は数秒で起動するはずだ。 この檻は /dev/kvm を開けるので、その檻と同じ vm start で確かめられる。

$ vm start
▶ virsh start linuc
  起動中… 10秒（KVM なしの完全エミュレーションなので 40〜90 秒かかります）
  起動中… 20秒（KVM なしの完全エミュレーションなので 40〜90 秒かかります）
練習機が起動しました（28秒）   ← KVM（第3・4章）よりずっと長い
  入るには:  ssh linuc   （抜けるときは exit）

$ ps -o args= -p $(pgrep qemu) | grep -o -E -- '-(accel|cpu) [a-z]+'
-accel tcg   ← libvirt が QEMU に渡したのは TCG
-cpu max

$ readlink /proc/$(pgrep qemu)/fd/* | grep kvm

$ ssh linuc systemd-detect-virt
qemu   ← 練習機も TCG の上にいると答えた
だめな理由: TCG で起動していた。libvirt が組み立てた QEMU のコマンド行（組み立て方は QEMU の記事の第7章）は -accel tcg -cpu max で、QEMU は /dev/kvm を開いていない。 libvirt は、/dev/kvm が使えるかどうかではなく、定義に書かれた type のとおりに QEMU を起動する。定義が type='qemu' である限り、 /dev/kvm を渡しても TCG のままで、速くはならない。速くするには定義そのものを type='kvm' に書き換える必要があり、このサイトの檻はわざとそうしていない。 （「起動中…」の行の数は、待った時間で変わる。）
$ vm stop
▶ virsh shutdown linuc
止まりました（6秒）
たとえ: libvirt の定義は、工事の発注書に近い。発注書に「手作業で」（type='qemu'）と書いてあれば、現場に重機（/dev/kvm）が置いてあっても、業者は手作業で進める。
ただし崩れる点: 現場の業者は重機があれば「使いましょうか」と言うかもしれないが、libvirt は言わない。重機が置いてあることを知っていても（virsh capabilities）、発注書を勝手に書き換えない。

全員に同じ画面を出すために

この節で分かること: KVM にすると何が読む人ごとに変わり、TCG で何を払っているか。

このシリーズの約束は「本文のコマンドは、読者の画面に本文と同じ文字を出す」ことである。この記事で見てきたとおり、KVM にすると練習機の中の画面が読む人の PC で変わる。

練習機の中で見るものTCG（どの PC でも同じ）KVM（読む人の PC で変わる）章
CPU のメーカー・印（既定の型）AuthenticAMD・svmあなたの PC の CPU のメーカー。Intel なら svm は消える5
CPU の名前（-cpu host・libvirt の maximum）QEMU が作った名前あなたの PC の CPU の名前5
systemd-detect-virt・lscpu の Hypervisor vendorqemu・出ないkvm・KVM5
練習機の中の /dev/kvm（入れ子）既定の型ではある（kvm_amd）あなたの PC の KVM の nested と CPU の型で変わる1・5
起動にかかる時間遅い（著者の PC で 30.5 秒）速い（同じく 6.6 秒）4

LinuC の記事には、CPU の名前（lscpu）や systemd-detect-virt の答えを本文に載せている章がある（LinuC 1.01 の第3章）。 KVM の読者と TCG の読者でそこが違えば、約束が守れない。さらに、KVM を使うには /dev/kvm を開ける檻が要る（第2章）。docker が動くカーネルに KVM が無い読者は使えず、 使える読者にも --device と --group-add を足してもらうことになる。TCG なら、起動のオプションに権限を1つも足さずに、全員が同じ練習機を動かせる。

払っているものは、第4章で測った。

同じ練習機の起動（著者の PC）TCGKVM
QEMU を起動してから、起動し終わるまで30.5 秒6.6 秒
起動し終わった直後までに QEMU が使った CPU の時間52 秒8 秒
練習機の OS が数えたユーザ空間の時間22.258 秒1.713 秒

練習機の中で重い処理をしない LinuC の演習では、待つのは主に起動と停止の数十秒である。このサイトは、その時間を払って、画面と権限を全員にそろえた。

たとえ: このサイトの練習機は、全員に同じ教習車を用意する教習所に近い。自分の車（KVM）で来れば速く着くが、車種によってハンドルの位置やメーターの見え方が違い、教本の写真と合わなくなる。 同じ教習車なら遅くても、全員が教本と同じ景色を見られる。
ただし崩れる点: 教習車は教習所が持ち、乗るのに免許の種類を確かめるが、この練習機は読む人の PC の上で動き、乗るのに何の許可も要らない。そろえているのは車ではなく、車の動かし方（TCG）である。

この6章を貫いている1つの事実

この節で分かること: 6つの章が、1つの事実から出てくること。

KVM の正体は、CPU の仮想化支援機能を使って仮想マシンを動かすカーネルの部品で、使う側には /dev/kvm というファイル1つで配られている。QEMU はそれを開いたときだけ速くなり、練習機の中から見える CPU も変わる。 開けるかどうかは、CPU の印・カーネル・ファイルの権限・コンテナの許可の4つで決まる。

章この事実の、どの部分か
1最初の関門の CPU の印は、CPU（TCG では QEMU）の自己申告。練習機のカーネルは、その答えを見て KVM を用意した
2KVM の入口はファイル1つ。コンテナの許可（device cgroup）とファイルの権限で、開けるかが決まる。特権は要らない
3QEMU は頼まれたときだけ開く。開いた QEMU は、カーネルの中の仮想マシンと仮想の CPU をファイルとして持つ
4開いて速くなるのは、本物の CPU が命令を実行する部分だけ。待ち時間と装置は速くならない
5開くと、練習機の CPU は本物の CPU を名乗る。印を渡せば、練習機の中にも /dev/kvm ができる
6このサイトの練習機は、開かないことを選んだ。全員が開けるわけではなく、開くと画面が変わるから
手を動かす: 実践編の演習02を、--group-add を外して起動し直した檻でもう一度 lab check 02 してみてほしい。あなたの PC の /dev/kvm が 0660 なら未達になり、0666 なら合格のままになる。 どちらになるかで、あなたの PC の /dev/kvm の権限の数字（誰でもか、グループだけか）が分かる。
確認

LinuC の記事の仮想マシン型の檻を、--device /dev/kvm --group-add "$(stat -c %g /dev/kvm)" を足して起動した。練習機の起動は速くなるか。理由も述べよ。

答え

速くならない。練習機の定義が type='qemu' なので、libvirt は QEMU に -accel tcg を渡し、/dev/kvm を開かせない。 この檻で vm start した練習機は、/dev/kvm を開ける檻でも TCG で起動し、systemd-detect-virt は qemu と答えた。

確認

このサイトの練習機を KVM で動かすと、読者によって本文と違う画面になりうる。どんなコマンドの出力が変わるか、2つ挙げよ。

答え

例: lscpu の Vendor ID・Model name（読者の PC の CPU になる）、systemd-detect-virt（qemu が kvm になる）、 /proc/cpuinfo の仮想化支援の印、sudo dmesg の Hypervisor detected の行、起動にかかる時間。

この章で分かったこと

持ち帰ってほしいこと

  • このサイトの仮想マシン型の檻は、libvirt の定義が type='qemu'。/dev/kvm を渡しても -accel tcg で動く
  • libvirt は、使えるかどうか（virsh capabilities）ではなく、定義の type のとおりに動かす
  • KVM にすると、練習機の中の CPU・systemd-detect-virt・起動の時間が読む人の PC で変わり、/dev/kvm を渡せない人は使えない
  • TCG を選んで、全員に同じ画面と、権限ゼロの起動を約束した。代わりに、起動の時間（著者の PC で 30.5 秒と 6.6 秒）と CPU を払っている
