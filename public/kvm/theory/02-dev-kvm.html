2. KVM の入口は /dev/kvm ひとつ

KVM は Linux のカーネルの部品（kvm と kvm_intel / kvm_amd のモジュール）で、使う側に見えるのは /dev/kvm というファイル1つだけである。 コンテナに KVM を渡すとは、このファイルを置き、開くことを許すことだ。同じ番号のファイルを自分で作っても、root でも開けない。 開けるかどうかは、ファイルがあるか・ファイルの権限・コンテナの許可（device cgroup）の3つの関門で決まり、どこで止まったかはエラーの文言で分かる。

前提: 第1章まで読了前提: 端末をもう1つ開ける所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • KVM がカーネルのモジュールで、/dev/kvm（文字デバイス 10, 232）を出していることを示せる
  • コンテナの中で /dev/kvm を開くまでの3つの関門を、それぞれのエラー（No such file or directory・Operation not permitted・Permission denied）で示せる
  • --device /dev/kvm と --group-add が何を渡し、何を渡さないか（持てる特権の上限 CapBnd は docker の既定のまま）を測って言える
ここで覚えなくていいこと: KVM に何を頼むかの細かい種類（ioctl の名前）、cgroup v1 と v2 の違いや、デバイスの許可が中でどう実装されているか（BPF）、 /dev/kvm の権限を決めている udev の規則の書き方、podman の rootless で渡すときの細部。

KVM は、あなたの PC のカーネルの中にある

この節で分かること: KVM がどこにあり、使う側から何が見えるか。

外（lab@host）で、カーネルが読み込んでいる部品（モジュール）の一覧から、名前が kvm で始まるものを探す。

$ grep -o -E '^kvm[a-z_]*' /proc/modules
kvm_intel   ← Intel の VT-x を使う部分
kvm

$ ls -l /dev/kvm
crw-rw-rw- 1 root 302 10, 232 Oct 14 03:35 /dev/kvm   ← 文字デバイス。番号は 10, 232

この2つはあなたの PC で変わる。AMD の PC なら kvm_amd。/dev/kvm の権限とグループは、著者の PC は crw-rw-rw- と 302 だが、 Ubuntu などでは crw-rw---- と別の番号になる（この章の最後で、その場合を記録で見る）。日時は檻を起動した時刻になる。

/proc/modules はカーネルが自分で書いている一覧で、コンテナの中から見えるのはあなたの PC のカーネルの部品である。 KVM の本体は kvm、CPU のメーカーごとの部分が kvm_intel（VT-x）と kvm_amd（AMD-V）に分かれている。

KVM を使う側に見えるのは、/dev/kvm というデバイスファイル1つだけである。行の頭の c は文字デバイス、10, 232 はカーネルの中の窓口を指す番号（10 は小さな装置をまとめる misc、232 が KVM）。 ファイルの名前に意味は無く、カーネルはこの番号で、開いた人の頼みを KVM へ回す。QEMU はこのファイルを開いて「仮想マシンを作って」「この CPU を動かして」と頼む（第3章）。

たとえ: /dev/kvm は、役所の建物の中にある窓口の番号札（10 番の 232）に近い。仕事をしているのは奥の部署（カーネルの KVM）で、札は「どこに頼めばよいか」を示すだけである。
ただし崩れる点: 役所の窓口は札が無くても見つけられるが、プログラムは /dev/kvm というファイルが無いと、KVM に頼む方法を持たない。札を外されたら、部署があっても頼めない。

名前の無いグループ 302

この節で分かること: 起動のときに渡した --group-add が、この檻の中で何になっているか。

実践編の起動コマンドには --device /dev/kvm と --group-add "$(stat -c %g /dev/kvm)" がある。檻に入ったとき、最初の行にこう出ていた。

groups: cannot find name for group ID 302

302 は著者の PC の番号で、あなたの PC では別の番号のことがある。--group-add を付けずに起動したときは、この行は出ない。

自分が何者かを見る。

$ id
uid=1000(lab) gid=1000(lab) groups=1000(lab),302   ← 302 には名前が無い

$ getent group kvm 302

$ echo $?
2   ← kvm という名前も 302 という番号も、この檻の /etc/group に無い

$ grep -E '^(Groups|CapEff|CapBnd)' /proc/self/status
Groups:	302 1000
CapEff:	0000000000000000   ← いま効いている特権は無い（lab は root ではない）
CapBnd:	00000000a80425fb   ← 持てる特権の上限。docker の既定のまま

--group-add は、コンテナの中のプロセスに補助グループを番号で足す。$(stat -c %g /dev/kvm) は docker を打つ前にあなたの PC のシェルが展開し、 /dev/kvm の持ち主のグループの番号（著者の PC では 302）になる。カーネルが覚えているのは番号だけで、番号に名前を付けているのは各ファイルシステムの /etc/group である。 この檻の /etc/group には、kvm という名前のグループも 302 という番号も無い（getent は何も出さず、終了コード 2 は「見つからない」）。だから id は番号だけを出し、ログインのときに groups コマンド（Ubuntu の /etc/bash.bashrc が打っている）が「名前が見つからない」と言った。害は無い。

CapEff は、いま効いている特権（ケーパビリティ）の一覧で、全部 0 である。この lab のまま、第3章で QEMU は KVM の仮想マシンを作る。 KVM を使うのに特権は要らない。/dev/kvm を開けさえすれば、誰でもカーネルに仮想マシンを作ってもらえる。

ただし CapEff が 0 なのは、lab が root ではないからである。起動のときに特権を渡しすぎていないかは、CapEff では分からない（--privileged で起動しても、lab の CapEff は 0 のままだった）。 渡した特権が出るのは CapBnd（このコンテナのプロセスが持てる特権の上限）で、00000000a80425fb は docker の既定のままである。--privileged で起動すると 000001ffffffffff になった（どちらも、演習02 の判定を確かめたときの記録）。

たとえ: --group-add 302 は、番号だけが書かれた会員証を渡すことに近い。受付（カーネル）は番号で照らし合わせるので、名前が無くても通れる。
ただし崩れる点: 会員証の名前は本人が見て安心するためのものだが、ここで名前を引いているのは檻の中の /etc/group で、あなたの PC の /etc/group（302 は kvm）とは別のファイルである。同じ番号に、場所ごとに別の名前が付きうる。

ファイルを作っても、開けない

この節で分かること: --device が、ファイルを置くこと以外に何を渡しているか。

比べるために、--device を付けない檻をもう1つ起動する。あなたの PC で、端末をもう1つ開いて打つ（ボリュームは付けない。--rm なので抜けると消える）。

入ると、最初の行は 練習機 linuc: 止まっている / /dev/kvm: なし（この檻は --device /dev/kvm なしで起動した） になり、groups: の行は出ない。この2つ目の檻で打つ。

/dev/kvm は無いが、CPU は vmx を名乗り、カーネルには kvm_intel がある。KVM はすぐそこにあって、入口のファイルだけが無い。 （virsh capabilities は、このサイトの仮想マシン型の檻が使っている libvirt に「どんな仮想マシンを作れるか」を尋ねるコマンドで、第6章でもう一度使う。）

ふつうこう考える

/dev/kvm は番号 10, 232 のデバイスファイルにすぎない。番号さえ合えば中身は同じなのだから、無いなら作ればよい。 この檻の lab は sudo で root になれるので、自分で作って、誰でも読み書きできる権限にすれば使えるはずだ。

$ sudo mknod -m 666 /dev/kvm c 10 232

$ ls -l /dev/kvm
crw-rw-rw- 1 root root 10, 232 Oct 14 03:35 /dev/kvm   ← 同じ番号・誰でも読み書きできる権限

$ qemu-linuc -accel kvm
▶ qemu-system-x86_64 -machine q35 -m 1536 -smp 2 \
...
    -accel kvm
Could not access KVM kernel module: Operation not permitted   ← lab でも開けない
qemu-system-x86_64: -accel kvm: failed to initialize kvm: Operation not permitted

$ sudo sh -c 'exec 3<>/dev/kvm'
sh: 1: cannot create /dev/kvm: Operation not permitted   ← root（sudo）でも開けない（dash は読み書きで開くときもこう出す）
だめな理由: ファイルは作れた（mknod）が、lab でも root でも開けなかった。エラーは「権限が無い（Permission denied）」ではなく「その操作は許されていない（Operation not permitted）」である。 コンテナは cgroup という仕組みで、どの番号のデバイスを開いてよいかの一覧を持たされている（device cgroup）。docker の既定では、端末や /dev/null などの決まった番号だけが入っていて、10, 232 は入っていない。 カーネルはファイルを開くとき、ファイルの権限に加えてこの一覧も確かめるので、権限を誰でも読み書きできるようにしても、root でも開けない。 --device /dev/kvm は、ファイルを置くと同時に、この一覧に 10, 232 を足している。ファイルだけ真似しても、許しは付いてこない。

では、ファイルの権限も足りないときはどうなるか。作った /dev/kvm を、root だけが読み書きできる権限（600）にして、lab のまま開かせる。

$ sudo chmod 600 /dev/kvm

$ qemu-linuc -accel kvm
▶ qemu-system-x86_64 -machine q35 -m 1536 -smp 2 \
...
    -accel kvm
Could not access KVM kernel module: Permission denied   ← device cgroup の許しも無いままなのに、権限のエラーが出た
qemu-system-x86_64: -accel kvm: failed to initialize kvm: Permission denied

今度は Permission denied になった。device cgroup の許しが無いのは前と同じなのに、出たのはファイルの権限のエラーである。 カーネルはファイルを開くとき、まずファイルの権限を確かめ、次に device cgroup を確かめる。両方とも駄目なら、先に確かめた権限のほうで断られる。 Permission denied を直しても（グループを足しても）、次に Operation not permitted が出ることがある、ということでもある。

$ grep -E '^(Groups|CapEff|CapBnd)' /proc/self/status
Groups:	1000
CapEff:	0000000000000000
CapBnd:	00000000a80425fb

$ exit
logout

2つ目の檻を exit で抜けると、--rm なのでコンテナごと消え、作った /dev/kvm も残らない。ここからは、元の端末（1つ目の檻）に戻る。

たとえ: device cgroup は、ビルの入館証に書かれた「入ってよい部屋の番号」に近い。部屋のドアの合鍵（デバイスファイル）を自分で作っても、入館証に番号が無ければ警備（カーネル）に止められる。
ただし崩れる点: ビルの警備は人を見て止めるが、device cgroup は「どのグループ（cgroup）のプロセスか」で止める。同じ人（root）でも、所属するグループが違えば止められる。

0660 の PC では、グループが要る

この節で分かること: --group-add が要る PC と、要らない PC の違い。

著者の PC の /dev/kvm は crw-rw-rw-（0666）で、誰でも読み書きできる。だからこの PC では、--group-add を付けなくても開ける。 Ubuntu 24.04 などでは crw-rw----（0660）で、持ち主のグループ（kvm）に入っていないと開けない。その場合を、Ubuntu 24.04 の PC で同じ檻を起動して記録した （著者の PC の上の、検証用の仮想マシン。入れ子の仮想化で KVM が使える。docker は Ubuntu の docker.io 29.1.3）。

デスクトップの PC では、画面の前でログインしている人に、ファイルの権限とは別に ACL で /dev/kvm の読み書きが許されていることがある（ls -l の権限の後ろに + が付く）。 docker の --device は ACL を持ち込まないので、檻の中では --group-add が要ることに変わりはない。

この PC の student は kvm グループに入っていなかったが、檻の中では KVM が使えた。docker の本体（デーモン）は root で動いていて、デバイスを渡すかどうかは docker が決めるからである。 docker を使える人は、kvm グループに入っていなくても KVM を使える。

エラー（QEMU が出す）どの関門で止まったか渡すもの
No such file or directory入口のファイルが無い--device /dev/kvm（ファイルを置く）
Permission deniedファイルの権限（0660 など）で、持ち主のグループに入っていない--group-add "$(stat -c %g /dev/kvm)"
Operation not permittedファイルの権限は通ったが、コンテナの device cgroup が 10, 232 を許していない--device /dev/kvm（許しも足す）

2つ以上の関門で止まるときは、先に確かめられるほうのエラーが出る。ファイルが無ければ No such file、あれば次にファイルの権限（Permission denied）、最後に device cgroup（Operation not permitted）。

この3つより手前に、第1章の関門がある。CPU が仮想化支援を名乗り（vmx / svm）、カーネルに kvm の部品があること。 ここで言うカーネルは、docker が動いているカーネルである。Docker Desktop（macOS・Windows）は、docker を自分の中の Linux の仮想マシンで動かす作りなので、そのカーネルになる（著者は Docker Desktop を試していない）。 docker が動いているカーネルに KVM が無いときを、さきほどの Ubuntu 24.04 の PC で KVM の部品を外して記録した。

$ sudo modprobe -r kvm_intel kvm

$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory   ← KVM の部品を外したので、入口のファイルも無い

$ docker run --rm --device /dev/kvm lab-kvm:1.0.0 true
docker: Error response from daemon: error gathering device information while adding custom device "/dev/kvm": no such file or directory   ← 渡すファイルが無いので、docker の時点で失敗する

Run 'docker run --help' for more information

ここだけイメージの名前が lab-kvm:1.0.0 なのは、検証用の仮想マシンに読み込んだときの名前だからである。中身は実践編のイメージと同じ。

この檻は --device なしなら起動する。その檻で、KVM が要る演習の判定を打った。

$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory   ← この檻にも入口のファイルは無い

$ lab check 02
⚠ 02 この環境では判定できません
  判定 : 観測型（この檻の lab として /dev/kvm を読み書きで開き、自分の権限を /proc/self/status で見た）
  前提不足: docker が動いているカーネルに KVM が見当たりません（/sys/module/kvm が無いか、CPU が vmx・svm を名乗っていない）。   ← 判定できない理由を出して終わる（読者の失敗ではない）
            この演習は、本文の記録で読んでください
たとえ: 3つの関門は、建物の入口（ファイル）・部屋の鍵（ファイルの権限）・入館証（device cgroup）に近い。どれか1つでも欠ければ、部屋には入れない。
ただし崩れる点: 建物なら入口・フロア・部屋の順に止められ、止められた場所も目で見えるが、カーネルは部屋の鍵を先に確かめ、入館証を後で確かめる。 両方欠けていれば鍵のほうで断られ、どこで止まったかは QEMU が出すエラーの文言（No such file・denied・not permitted）でしか分からない。
手を動かす: 実践編の演習02は、この檻の lab が /dev/kvm を開けるように起動し直す課題である。判定は実際に /dev/kvm を読み書きで開き、特権が増えていないこと（CapBnd が docker の既定のままで、CapEff も 0）も確かめる。 --device なしの檻で lab check 02 を打つと、未達の理由として「この檻の /dev に kvm が無い」が出る。
確認

コンテナの中で QEMU を -accel kvm で起動すると、次のように出た。何が足りないか。

Could not access KVM kernel module: Permission denied
答え

ファイルの権限で断られている。/dev/kvm はコンテナの中にあるが（無ければ No such file）、0660 などで、コンテナの中のプロセスがその持ち主のグループに入っていない。 --group-add "$(stat -c %g /dev/kvm)" を付けて起動し直す。ただし、権限は device cgroup より先に確かめられるので、この文言からは device cgroup が許しているかまでは分からない。 --device で渡したファイルなら許されている（自分で mknod したファイルなら、権限を直しても次は Operation not permitted になる）。

確認

2つ目の檻で、root になって mknod で作った /dev/kvm（crw-rw-rw-）は、lab からも root（sudo）からも開けなかった。root でも開けない理由を、「誰が・何を見て」止めたのかで説明せよ。

答え

カーネルが、そのプロセスの属するコンテナの device cgroup（開いてよいデバイスの番号の一覧）を見て止めた。一覧に 10, 232 が無いので、ファイルの権限や root かどうかに関係なく、開くことが許されない（Operation not permitted）。 --device /dev/kvm は、ファイルを置くと同時にこの一覧へ 10, 232 を足す。

確認

この檻の CapEff は 0000000000000000 だった。それでも QEMU が KVM で仮想マシンを作れたのはなぜか。

KVM を使うのに特権（ケーパビリティ）は要らず、/dev/kvm を読み書きで開けることだけが条件だから。誰が KVM を使えるかは、ファイルの置き場（--device）と権限（グループ）で決まっている。

この章で分かったこと

持ち帰ってほしいこと

  • KVM はカーネルの部品（kvm と kvm_intel / kvm_amd）で、使う側に見えるのは /dev/kvm（文字デバイス 10, 232）1つだけ
  • コンテナで開くまでの関門は3つで、確かめられる順に: ファイルがあるか（No such file）、ファイルの権限（Permission denied）、device cgroup が許すか（Operation not permitted）
  • --device /dev/kvm はファイルと許しを、--group-add はグループの番号を渡す。名前は檻の /etc/group に無いことがある
  • 特権は1つも増えない（持てる特権の上限 CapBnd は docker の既定のまま。CapEff が 0 なのは lab が root でないからで、渡しすぎていない証拠にはならない）。KVM を使えるかどうかは、/dev/kvm を開けるかどうかだけで決まる
