4. 報告先は、ソフトの中に書いてある

bash --help の最後は「バグは bashbug で報告して」と言い、/etc/os-release は Launchpad の URL を指す。同じ bash に報告先が2つある。どちらに出すかは、壊れているのが誰の作った部分かで決まる。そして報告先も、許可の条件と同じく、ソフトと一緒に配られている。

前提: 第3章まで読了前提: 素の Ubuntu を起動できる（任意）所要 15分影響度 A出題範囲 1.11.2（重要度1）最終検証 2026-10-13

この章のゴール

  • 1つのパッケージに関わる層（上流・Debian・Ubuntu）を、手元の情報から読み取れる
  • コミュニティの場（メーリングリスト・掲示板・開発サイト）と開発体制を説明できる
  • 良いバグ報告に要る情報を挙げられ、エコシステムへの参加の形を言える
ここで覚えなくていいこと: 各プロジェクトの投稿の作法（英語の書き方、パッチの送り方）、Git や GitHub の操作、Launchpad や Debian のバグ管理システムの使い方、財団や団体の名前の一覧は扱わない。試験で問われるのは、どんな場があり、どう参加するかである。

報告先が、2つある

この節で分かること: 1つのソフトに、作った人と配った人が別にいること。

ふつうこう考える

Ubuntu に入っている bash の不具合を見つけたら、Ubuntu に報告すればよい。bash を配っているのは Ubuntu なのだから、窓口は1つのはずだ。

$ bash --help | tail -4
Use the `bashbug' command to report bugs.

bash home page: <http://www.gnu.org/software/bash>
General help using GNU software: <http://www.gnu.org/gethelp/>
$ grep URL /etc/os-release
HOME_URL="https://www.ubuntu.com/"
SUPPORT_URL="https://help.ubuntu.com/"
BUG_REPORT_URL="https://bugs.launchpad.net/ubuntu/"
PRIVACY_POLICY_URL="https://www.ubuntu.com/legal/terms-and-policies/privacy-policy"
だめな理由: bash 自身は「bashbug コマンドで報告して」と言い、ホームページとして GNU のサイトを挙げる。 OS のほうは BUG_REPORT_URL として Launchpad（Ubuntu のバグ管理の場）を指している。窓口は1つではない。 bash を作っているのは GNU プロジェクトで、Ubuntu はそれを受け取って配っている。どちらの窓口が正しいかは、不具合がどちらの手で入ったかで決まる。

1つのパッケージに関わる人は、パッケージの情報に並んでいる。

$ dpkg -s bash | grep -E '^(Version|Maintainer|Original-Maintainer|Homepage):'
Maintainer: Ubuntu Developers <ubuntu-devel-discuss@lists.ubuntu.com>
Version: 5.2.21-2ubuntu4
Homepage: http://tiswww.case.edu/php/chet/bash/bashtop.html
Original-Maintainer: Matthias Klose <doko@debian.org>
$ grep '^Upstream-Contact' /usr/share/doc/bash/copyright
Upstream-Contact: chet@po.cwru.edu

3つの層が見える。版番号 5.2.21-2ubuntu4 も、同じ3層を順に書いている。

上流（upstream）  5.2.21            作った人。Upstream-Contact: chet@po.cwru.edu
   ↓ 受け取って Debian 向けに整える
Debian           5.2.21-2          Original-Maintainer: Matthias Klose
   ↓ 受け取って Ubuntu 向けに整える
Ubuntu           5.2.21-2ubuntu4   Maintainer: Ubuntu Developers（メーリングリスト）

5.2.21 が上流（開発元）の版、-2 が Debian の付けた改訂番号（その上流版を Debian 向けにまとめた2回目）、ubuntu4 が Ubuntu での4回目の変更である。下流の層は、上流のソースに自分たちの修正（パッチ）を足して配ることがある。

だから不具合の出どころで窓口が変わる。上流の版でも起きる不具合なら上流へ、Ubuntu が足した部分や配り方の不具合なら Launchpad へ。どちらか分からないときは、OS が BUG_REPORT_URL で示す窓口から始めればよい。そこには配布元（Ubuntu）の担当者がいて、上流の問題であれば上流へつなげられる。

たとえ: 輸入食品の問い合わせ先に近い。中身の製法の問題は海外の製造元、ラベルや国内向けの包装の問題は輸入元、買った店にも窓口がある。 商品の裏を見ると、それぞれの連絡先が書いてある。
ただし崩れる点: 輸入元は製造元に代わって責任を負うことがあるが、オープンソースは無保証で（第1章）、どの層も直す義務を負わない。直すかどうかは、それぞれの層の判断である。

掲示板（Web のフォーラム）は、利用者どうしが質問し、答え合う場である。開発者へ直接届くメーリングリストやバグトラッカーと違い、「使い方が分からない」「自分の設定がおかしいのか」を確かめる段階で使う。/etc/os-release でも、利用者の手助け（SUPPORT_URL）とバグ報告（BUG_REPORT_URL）は別の欄になっていた。

場何をする所か素の Ubuntu で見えた例
メーリングリストメールで議論・告知・報告。購読者全員に届き、記録が残るutil-linux@vger.kernel.org、bug-grep@gnu.org
掲示板（フォーラム）利用者どうしの質問と回答SUPPORT_URL は利用者向けの手引きの入口として別に置かれている
開発サイトソースの保管、課題管理、変更の提案と審査github.com、kernel.org、sourceforge.net
バグ管理の場不具合の登録と追跡BUG_REPORT_URL（Launchpad）
たとえ: メーリングリストは、宛先が1つの回覧板に近い。1通出すと、名簿に載った全員のところへ届く。済んだ回覧は綴じて保管される。
ただし崩れる点: 回覧板は1軒ずつ順に回るが、メーリングリストは全員に同時に届く。また回覧板は町内の人しか読めないが、オープンソースのメーリングリストの多くは、誰でも購読でき、保管庫も誰でも読める。

開発体制 — 誰が決めて、誰が直すか

この節で分かること: プロジェクトによって決め方の形が違うこと、そして上流の出来事が下流まで流れること。

上の Upstream-Contact: の一覧には、決め方の違いがそのまま出ている。

形一覧に見えたもの
個人が中心（作者や1人のメンテナが決める）chet@po.cwru.edu（bash）、Theodore Ts'o（e2fsprogs など5パッケージ）
チームで運営するAPT Development Team、util-linux@vger.kernel.org
財団・団体が支えるcoreutils と bash の著作権者は Free Software Foundation（第1章）
企業が開発するberkeleydb-info_us@oracle.com、sgrubb@redhat.com

多くのプロジェクトには役割の区別がある。メンテナはそのソフト（またはパッケージ）に責任を持つ人、コミッタは本体に変更を取り込む権限を持つ人、コントリビュータは報告・修正・翻訳などで貢献する人である。誰がどの役割かを決めるのも、そのプロジェクト自身である。

$ zcat /usr/share/doc/bash/changelog.Debian.gz | head -3
bash (5.2.21-2ubuntu4) noble; urgency=medium

  * No-change rebuild for CVE-2024-3094

版番号 5.6.1+really5.4.5 は「番号は 5.6.1 より新しく、中身は本当は（really）5.4.5」という意味で、中身を前の版へ戻したことを示す。changelog には urgency=critical（緊急）と Non-maintainer upload by the Security Team（担当のメンテナではなく、セキュリティチームが出した）とある。CVE-2024-3094 は、xz の上流が配った 5.6.0 と 5.6.1 に不正なコードが仕込まれていた件の番号で、Ubuntu では bash も中身を変えずに作り直されていた（No-change rebuild）。

上流で起きたことが Debian のチームの判断で差し戻され、Ubuntu の作り直しまで流れていく。第1章で見た継続した開発は、この連なりが動き続けていることを指している。

たとえ: 開発体制は、楽団の形に近い。指揮者1人がすべて決める楽団もあれば、団員の合議で決める楽団も、企業が支える楽団もある。
ただし崩れる点: 楽団を抜けた人は、その楽団の楽譜を持ち出せない。オープンソースでは、方針に賛成できなければ、ソースコードごと持ち出して別のプロジェクトを始めてよい（フォーク）。それを許しているのが、第1章の「改変した版を配る自由」である。

良いバグ報告に要るもの

この節で分かること: バグ報告に何を書けば、開発者が動けるか。

bash の報告手段 bashbug が、答えを用意している。

$ bashbug --help
GNU bashbug, version 5.2.21-release
Usage: /usr/bin/bashbug [--help] [--version] [bug-report-email-address]

Bashbug is used to send mail to the Bash maintainers
for when Bash doesn't behave like you'd like, or expect.

Bashbug will start up your editor (as defined by the shell's
EDITOR environment variable) with a preformatted bug report
template for you to fill in. The report will be mailed to the
bug-bash mailing list by default. See the manual for details.

If you invoke bashbug by accident, just quit your editor without
saving any changes to the template, and no bug report will be sent.

エディタで報告の下書き（テンプレート）を開き、書き終えると bug-bash メーリングリストへメールで送る。ここではエディタの代わりに cat を渡して、下書きを画面に出すだけにする。件名を書き換えていないので bashbug は送る前に止まり、y（あきらめる）で終わる。何も送信されない。

$ echo y | EDITOR=cat bashbug
From: root
To: bug-bash@gnu.org
Subject: [50 character or so descriptive subject here (for reference)]

Configuration Information [Automatically generated, do not change]:
Machine: x86_64
OS: linux-gnu
Compiler: gcc
Compilation CFLAGS: -g -O2 -fno-omit-frame-pointer -mno-omit-leaf-frame-pointer -flto=auto -ffat-lto-objects -fstack-protector-strong -fstack-clash-protection -Wformat -Werror=format-security -fcf-protection -Wall
uname output: Linux linuc 7.2.6 #1-NixOS SMP PREEMPT_DYNAMIC Mon Sep 14 11:41:11 UTC 2026 x86_64 x86_64 x86_64 GNU/Linux   ← この行だけは手元のカーネルの情報になる
Machine Type: x86_64-pc-linux-gnu

Bash Version: 5.2

	[Detailed description of the problem, suggestion, or complaint.]

Repeat-By:
	[Describe the sequence of events that causes the problem
	to occur.]

	[Description of how to fix the problem.  If you don't know a
	fix for the problem, don't include this section.]

/usr/bin/bashbug: You have not changed the subject from the default.
/usr/bin/bashbug: Please use a more descriptive subject header.

/usr/bin/bashbug: type `n' to re-enter the editor.
/usr/bin/bashbug: Do you want to give up?

下書きの欄が、そのまま良いバグ報告の部品になっている。

要るものbashbug の欄無いと何が起きるか
具体的な件名Subject（50字ほど。書き換えないと bashbug が送らない）似た報告と区別できず、後から探せない
環境Configuration Information（自動で集める。変えない）開発者の手元で再現できない
版Bash Version / Patch Levelすでに直っている版の話かどうか判断できない
何が起きたか（期待した結果と実際の結果）Description不具合なのか仕様どおりなのか判断できない
再現の手順Repeat-By開発者が同じ現象を見られない
直し方（分かれば）Fix（分からなければ書かない）—

これに加えて、出す前に同じ報告が既に無いかを探す、1件の報告には1つの問題だけを書く、そのプロジェクトが決めた場（メーリングリストか、バグトラッカーか）に出す、の3つを守ると、報告が埋もれにくい。このサイトの「本文と違う出力が出たら」の手順（打ったコマンド・本文の出力・あなたの出力・環境）も、同じ形をしている。

たとえ: 病院の問診票に近い。いつから・どこが・どうなったか・飲んでいる薬は何かを、医師が聞く前に書かせる。
ただし崩れる点: 医師は目の前で診察できるが、開発者はあなたのマシンを見られない。報告に書かれたことだけが手がかりなので、問診票よりずっと細かく、手順を再現できる形で書く必要がある。
手を動かす: このコースには演習がない。素の Ubuntu で bash --help | tail -4 と grep URL /etc/os-release を打ち、報告先が2つあることを自分の画面で確かめる。 echo y | EDITOR=cat bashbug は下書きを表示するだけで、何も送信しない。起動のしかたは入口にある。

参加は、使うことから始まる

この節で分かること: オープンソースのエコシステムに、どういう形で加われるか。

出題範囲は、エコシステムへの参加として「使用、紹介、バグ報告」の3つを挙げている。

参加の形中身
使用使うこと自体が参加になる。使う人が多いほど不具合が見つかり、改善の理由になる
紹介ブログ・勉強会・職場などで広める。利用者と貢献者が増える
バグ報告前の節の形で、決められた場に報告する
そのほか翻訳、文書の改善、修正（パッチ）の提案、寄付

翻訳の窓口も、コマンドの中に書いてある。

$ ls --help | tail -3
Report any translation bugs to <https://translationproject.org/team/>
Full documentation <https://www.gnu.org/software/coreutils/ls>
or available locally via: info '(coreutils) ls invocation'

「翻訳の誤りは translationproject.org の各言語のチームへ」。コードを書かなくても、日本語のメッセージを直すことで上流に加われる。

4章が1つの事実から出ていた

この節で分かること: 主題1.11 の4章が、同じ1つの形をしていること。
章誰が（持ち主）何を書いたかどこに一緒に入っていたか
1FSF などの著作権者使ってよいという許可、無保証、写しを渡すこと--version、/usr/share/doc/*/copyright
2GPL のソフトの著作権者配るなら同じ条件で、ソースも渡すこと/usr/share/common-licenses/GPL-3
3MIT・BSD・Apache の著作権者（パブリックドメインは持ち主なし）表示を残すこと（パブリックドメインは条件なし）copyright の許諾文
4上流・Debian・Ubuntu の各層報告先と連絡先--help、/etc/os-release、Upstream-Contact:

4つとも同じ形をしている。

オープンソースは、権利を手放したソフトではない。
持ち主が条件を書いて出した許可で、その条件と連絡先はソフトと一緒に配られている。

だから主題1.11 は知識問題でありながら、答えの根拠が手元の1台に全部入っている。マニュアルを捨てた最小のイメージでさえ、copyright と changelog は捨てていなかった。試験の前に ls /usr/share/common-licenses/ を1回打っておくと、選択肢に並ぶ GPL・LGPL・MPL・BSD・Apache の名前が、実物のファイルと結びつく。

確認

オープンソースのコミュニティで、電子メールで議論や告知を行い、購読者全員に配信される仕組みはどれか。

  1. バグトラッカー
  2. メーリングリスト
  3. 掲示板
  4. リポジトリ
答え

B。copyright の Upstream-Contact: には util-linux@vger.kernel.org や bug-grep@gnu.org のようなメーリングリストのアドレスが並んでいた。 bashbug --help も、報告を bug-bash mailing list へ送ると書いている。

確認

バグ報告の書き方として、最も適切なものはどれか。

  1. 「動きません」とだけ書いて、できるだけ早く出す
  2. 版と環境、再現の手順、期待した結果と実際の結果を書く
  3. 関係のない複数の不具合を1件の報告にまとめる
  4. 既存の報告を確かめず、同じ内容を何度も出す
答え

B。bashbug の下書きも、環境（Configuration Information）、版（Bash Version / Patch Level）、 何が起きたか（Description）、再現の手順（Repeat-By）の欄を持っていた。

確認

Ubuntu のパッケージの版 5.2.21-2ubuntu4 のうち、上流（開発元）の版を表しているのはどの部分か。

答え

5.2.21。-2 は Debian の付けた改訂番号、ubuntu4 は Ubuntu での4回目の変更である。 dpkg -s bash でも、Original-Maintainer（Debian）と Maintainer（Ubuntu）が別に書かれていた。

確認

LinuC の出題範囲が「オープンソースエコシステムへの参加」として挙げているものを3つ答えよ。

答え

使用・紹介・バグ報告。使うこと自体も参加に数えられる。ほかに翻訳（ls --help が窓口を書いている）、文書の改善、修正の提案、寄付などの形もある。

この章で分かったこと

持ち帰ってほしいこと

  • 1つのパッケージには、上流（作った人）・Debian・Ubuntu の層がある。版番号 5.2.21-2ubuntu4 がその順に並んでいる
  • 報告先は1つではない。bash --help は上流（bashbug → bug-bash@gnu.org）を、/etc/os-release は Ubuntu（Launchpad）を指す。不具合の出どころで窓口を選ぶ
  • コミュニティの場は、メーリングリスト（メールで議論・報告）、掲示板（利用者どうしの質問と回答）、開発サイト（ソースの保管・課題管理・変更の提案）
  • 開発体制は、個人中心・チーム・財団・企業とプロジェクトごとに違う。役割としてメンテナ・コミッタ・コントリビュータがある。方針が合わなければフォークできる
  • 良いバグ報告は、具体的な件名・版・環境・再現の手順・期待と実際の結果。bashbug の下書きがその形をしている
  • エコシステムへの参加は、使用・紹介・バグ報告から。翻訳や文書、修正の提案もある
  • 4章すべてが「持ち主が条件を書いて出した許可で、その条件と連絡先はソフトと一緒に配られている」という1つの形だった
