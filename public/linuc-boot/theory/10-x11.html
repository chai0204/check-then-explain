10. X では、画面の側がサーバー

X Window System では、アプリが動いている計算機ではなく、画面とキーボードがある側を「X サーバー」と呼ぶ。 だから遠くの計算機の GUI を手元に出すとき、X サーバーは手元で動いていなければならない。 画面の無いこの檻で ssh -X を試すと、その順番どおりに、手元の側から断られる。

この章のゴール

  • X サーバーと X クライアントが、どちらの計算機で動くかを説明できる
  • ディスプレイマネージャ・ウィンドウマネージャ・統合デスクトップ環境・ターミナルの役割を区別できる
  • DISPLAY と xauth が何のためにあり、ssh -X で何が起きるかを言える
ここで覚えなくていいこと: X のプロトコルの中身、Xorg の設定ファイル（xorg.conf）、 Wayland の仕組みの細部、デスクトップ環境ごとの操作方法。 この章は GUI を再現できない檻で書いているので、手で確かめられるのは「X が無いこと」と ssh -X の失敗のしかただけである（理由は理論編の目次）。

練習機には X が無い

この節で分かること: GUI が無い計算機で、X の部品がどこにも無いことの確かめ方。

練習機の中で、X の部品があるかを確かめる。

$ echo "DISPLAY=[$DISPLAY]"
DISPLAY=[]
$ command -v startx Xorg xauth xterm; echo "終了コード $?"
終了コード 1
$ systemctl status display-manager.service
Unit display-manager.service could not be found.
$ sudo sshd -T | grep -i x11
x11displayoffset 10
x11forwarding yes
x11uselocalhost yes

DISPLAY は空で、startx も、X サーバー（Xorg）も、xauth も、xterm も入っていない（command -v は1つも見つけられず、終了コード 1）。 GUI のログイン画面を出すディスプレイマネージャ（display-manager.service）も無い。第4章で見たとおり、練習機はクラウド用の最小構成で、デスクトップのパッケージを入れていない。

それでも sshd は、X11 の転送を受け付ける設定（x11forwarding yes）になっている。受け付ける設定があることと、受け付けたものを処理する部品があることは、別のことである。次の節で、その差がそのまま断られ方に出る。

サーバーとクライアントの向き

この節で分かること: X の部品の名前と、それぞれがどこで動くか。
手元の PC（画面・キーボード・マウスがある）                 遠くのサーバ（画面が無い）
┌─────────────────────────────────┐            ┌────────────────────────┐
│ X サーバー（Xorg）……画面に描く・入力を受ける │ ←X の要求── │ X クライアント（アプリ） │
│ ウィンドウマネージャ……窓の枠・移動・重なり   │   DISPLAY   │  例: xterm、xeyes        │
│ ディスプレイマネージャ……GUI のログイン画面   │  を見て接続 │  DISPLAY=localhost:10.0  │
└─────────────────────────────────┘            └────────────────────────┘
部品役目例
X サーバー画面に描き、キーボードとマウスの入力を受ける。クライアントからの「描いて」という要求を待つ側Xorg
X クライアントX サーバーに描いてもらうアプリ。別の計算機で動いていてもよいxterm、firefox、xeyes
ウィンドウマネージャ窓の枠・移動・大きさ・重なりを受け持つ（これも X クライアントの1つ）mutter、kwin、xfwm4、twm
ディスプレイマネージャGUI のログイン画面を出し、ログインしたらデスクトップを起動するgdm3、lightdm、sddm、xdm
統合デスクトップ環境ウィンドウマネージャ・パネル・ファイル管理・設定を揃えた一式GNOME、KDE Plasma、Xfce
ターミナルX の上でシェルを動かす X クライアント（端末エミュレータ）xterm、gnome-terminal、konsole

ディスプレイマネージャが無い計算機では、ログインした後に startx を打って X を起動する。startx は xinit を呼び、 ~/.xinitrc に書いたもの（ウィンドウマネージャや最初のアプリ）を X クライアントとして起動する。

X クライアントがどの X サーバーに描いてもらうかは、環境変数 DISPLAY で決まる。書式は ホスト名:ディスプレイ番号.スクリーン番号。 手元の最初の画面は :0（ホスト名を省くと自分の計算機）、ssh -X が作る通り道は localhost:10.0 のような値になる。 誰でも画面に描けては困るので、X サーバーは合い言葉（MIT-MAGIC-COOKIE と呼ぶ乱数）を知っている相手だけを受け入れる。 その合い言葉を ~/.Xauthority に出し入れするのが xauth である。

たとえ: X サーバーは映画館の映写室に近い。フィルム（アプリ）がどこの配給会社から届いても、映すのは館の映写機で、客席（画面）があるのも館の側である。
ただし崩れる点: 映画館は大きな建物で、ふつうの感覚の「サーバ」（遠くの大きな機械）に近いが、X サーバーはあなたの手元の小さな PC で動く。 「サービスを受け付ける側」がサーバーという定義に忠実なだけで、ssh でいう「サーバ」とは向きが逆になる。

X サーバーが動いている計算機では、その様子を文字で尋ねるコマンドがある。どれも X クライアントで、DISPLAY の指す X サーバーに尋ねる。 練習機には X が無いので、この表は記録ではなく、試験のための一覧である。

コマンド何を出すか
xdpyinfoX サーバー（ディスプレイ）の情報。版・画面の大きさ・色深度（depth of root window: 24 planes のような行）
xwininfoウィンドウの情報。クリックした窓、または -root で画面全体（ルートウィンドウ）。色深度は Depth: の行
xlsclientsいま X サーバーにつながっている X クライアントの一覧
xwdウィンドウや画面を画像（XWD 形式）に書き出す
showrgb使える色の名前と、その RGB の値の一覧

ssh -X を試す

この節で分かること: リモートの GUI を手元に出すのに、どちらの計算機に何が要るか。

ふつうこう考える

ssh -X を付ければ、相手の計算機の GUI アプリを手元に出せる。相手（サーバー）の sshd が X11 の転送を許していれば、つながるはずだ。

$ echo "DISPLAY=[$DISPLAY]"
DISPLAY=[]
$ ssh -X linuc 'echo DISPLAY=[$DISPLAY]'
DISPLAY=[]
$ ssh -v -X linuc true 2>&1 | grep -iE 'x11|display'
debug1: Remote: /home/student/.ssh/authorized_keys:1: key options: agent-forwarding port-forwarding pty user-rc x11-forwarding
debug1: Remote: /home/student/.ssh/authorized_keys:1: key options: agent-forwarding port-forwarding pty user-rc x11-forwarding
debug1: X11 forwarding requested but DISPLAY not set
だめな理由: 練習機の sshd は X11 の転送を許している（前の節の x11forwarding yes）のに、相手の側に DISPLAY は作られなかった。 断ったのは手元の ssh で、-v の表示が「X11 の転送を頼まれたが、DISPLAY が無い」と言っている。 ssh -X は「相手のアプリの描画を、手元の X サーバーまで運ぶ通り道を作ってほしい」という頼みである。手元に X サーバーが無ければ（DISPLAY が空なら）、運ぶ先が無いので、頼み自体を出さない。

手元に X サーバーがある振りをして、DISPLAY=:0 を付けて打つ。

$ DISPLAY=:0 ssh -X linuc 'echo DISPLAY=[$DISPLAY]'
Warning: No xauth data; using fake authentication data for X11 forwarding.
X11 forwarding request failed on channel 0
DISPLAY=[]
$ DISPLAY=:0 ssh -v -X linuc true 2>&1 | grep -iE 'x11|xauth'
debug1: Remote: /home/student/.ssh/authorized_keys:1: key options: agent-forwarding port-forwarding pty user-rc x11-forwarding
debug1: Remote: /home/student/.ssh/authorized_keys:1: key options: agent-forwarding port-forwarding pty user-rc x11-forwarding
debug1: No xauth program.
Warning: No xauth data; using fake authentication data for X11 forwarding.
debug1: Requesting X11 forwarding with authentication spoofing.
debug1: Remote: No xauth program; cannot forward X11.
X11 forwarding request failed on channel 0

今度は手元の ssh が頼みを送り、相手の sshd が「xauth が無いので X11 を転送できない」と断った（Remote: で始まる行は、相手から届いた知らせ）。 手元の側にも xauth が無いので、ssh は本物の合い言葉の代わりに偽物（fake authentication data）を作って送っていた。

ssh -X が通るには、手元の X サーバー（DISPLAY）、手元と相手の xauth、相手の sshd の許可（X11Forwarding yes）が揃っている必要がある。 揃っていれば、相手の側に DISPLAY=localhost:10.0 のような値が作られ、そこに描いたものが ssh の中を通って手元の X サーバーに届く。どれか1つでも欠ければ、受け取った側が通り道を作らない。

たとえ: ssh -X は、遠くの工場（相手）に「できた製品（絵）は、うちの店（手元の X サーバー）に届けてくれ」と配送先を伝える頼みに近い。 店が無ければ届け先を書けないので、頼みを出せない（手元の ssh が断った）。伝票を書く道具（xauth）が工場に無ければ、工場が引き受けない（相手の sshd が断った）。
ただし崩れる点: 本物の配送なら、届け先の店が閉まっていても荷物は先に出せる。X の絵は、届け先の X サーバーとつながったまま1枚ずつやり取りして描くので、届け先が無いまま描き始めることはできない。

10章を1本にする

この節で分かること: 10章の「予想と違ったこと」が、1つの事実の言い換えだったこと。

10章で、送った側の期待と、受け取った側の振る舞いが食い違う場面を10回見た。並べる。

章送ったもの（合図）受け取った側受け取った側が決めたこと
1virsh shutdown（止まってほしいという頼み）中の OS（ゲストエージェント、いなければ ACPI の電源ボタンで受け取る。GRUB の間は誰もいない）受け取る者がいない間の頼みは消えた
2ssh の公開鍵相手の sshd と authorized_keys他人が書ける名簿の鍵は使わない
3docker stop（TERM）檻の起動スクリプト → 練習機練習機を正常に止めてから終わる（猶予の中で）
4インストール時の選択起動時の systemd（default.target）GUI が無くても graphical.target まで進む
5ブート順（BootOrder）起動された shim の fallback書き換えたブート順を元に戻した
6カーネル引数 singlesulogin（Ubuntu の改造版）パスワードの無い root を、聞かずに渡した
7haltカーネル（と、電源を切る ACPI）CPU は止めたが、電源は切らなかった
8kill（TERM）lab-hog無視した。KILL だけは断れなかった
9回線の切断（SIGHUP）シェルとそのジョブnohup・tmux の中のものは無視した
10ssh -X の要求手元の ssh と、相手の sshdX サーバーも xauth も無いので、通り道を作らなかった

停止の頼みも、シグナルも、ログインも、相手に送る「合図」でしかない。どう振る舞うかは、受け取った側が決める。

受け手に決めさせずに終わらせられるのは、電源を抜く virsh destroy と kill -9 だけで、どちらも後片付けの機会を奪う （一時停止なら virsh suspend と kill -STOP も断れないが、これは終わらせずに止めておくだけである）。 試験に shutdown halt poweroff reboot、kill pkill killall、nohup screen tmux と似たものが並ぶのは、 送る合図と、受け取る相手が違うからである。コマンドを覚えるときは「誰に、何を頼んでいるか」を一緒に覚えると、取り違えなくなる。

たとえ: この10章は、郵便を出すことに似ている。差出人は封筒（合図）を出せるが、開けるか、従うか、捨てるかは受取人が決める。
ただし崩れる点: 郵便には「受け取りを拒否できない」書留のような強制は無いが、コンピュータには、相手を終わらせる強制が2つだけある。電源を抜くことと、KILL である。 強制は確実だが、受取人に片付けの暇を与えない。だから最後の手段にする。
手を動かす: この章に対応する演習はありません（X を再現できないため）。代わりに、外の端末で本文の ssh -X の2つの試し方（DISPLAY なし・DISPLAY=:0）を打ち、 同じ断られ方をするか確かめてください。-v を付けると、どちらの側が断ったかが分かります。
確認

X Window System の説明として正しいものはどれか。

A. X サーバーは、アプリケーションが動いているリモートの計算機で動く
B. X サーバーは、ディスプレイやキーボードを持つ手元の計算機で動く
C. X クライアントは、必ず X サーバーと同じ計算機で動く
D. ウィンドウマネージャは X サーバーの一部である

答え

B。X サーバーは画面に描いて入力を受け取る側で、手元で動く。X クライアントは別の計算機で動いてもよく（ネットワーク越しに描いてもらえる）、 ウィンドウマネージャも X クライアントの1つである。

確認

環境変数 DISPLAY に remotehost:0.0 と設定した。何を意味するか。

答え

X クライアントは、remotehost で動いている X サーバーの、ディスプレイ番号 0・スクリーン番号 0 に描きに行く。 ホスト名を省いた :0 は自分の計算機の最初の画面。

確認

X サーバーへの接続を許可するための認証情報（MIT-MAGIC-COOKIE）を表示・追加するコマンドはどれか。

A. xhost　B. xauth　C. startx　D. xinit

答え

B。xauth は ~/.Xauthority の中の合い言葉を扱う（xauth list で表示）。 実測では、練習機に xauth が無いので sshd が「No xauth program; cannot forward X11」と断った。 A の xhost は、ホスト単位で接続を許すかを X サーバーに伝える別の仕組み。

この章で分かったこと

持ち帰ってほしいこと

  • X サーバーは画面・キーボードのある手元で動き、X クライアント（アプリ）の要求を受けて描く。向きは ssh の「サーバ」と逆
  • ディスプレイマネージャはログイン画面、ウィンドウマネージャは窓の管理、統合デスクトップ環境はその一式、ターミナルはシェルを動かす X クライアント
  • ディスプレイマネージャが無ければ startx（~/.xinitrc）で X を起動する
  • DISPLAY は描きに行く先（ホスト:ディスプレイ.スクリーン）、xauth は接続の合い言葉を扱う
  • ssh -X には、手元の X サーバー（DISPLAY）と、相手の xauth の両方が要る。どちらかが無ければ、受け取る側が通り道を作らない
