5. ファームウェアが必ず読めるのは、FAT の中のファイルだけ

Linux のカーネルは /boot の中にある。ところが電源を入れて最初に動く UEFI ファームウェアは、/boot（ext4）を1バイトも読めない。 読めるのは ESP という FAT の小さな区画の中のファイルだけで、そこから先は「起動された側が、次に起動するものを自分で探しに行く」リレーになっている。 ブート順を書き換えても、起動された側がそれを書き戻すことさえある。

前提: 第4章まで読了前提: 端末を2つ開いている所要 20分影響度 B出題範囲 1.01.3（重要度4）出題範囲 1.01.1（重要度4）最終検証 2026-10-13

この章のゴール

  • ファームウェア（UEFI / BIOS）→ ブートローダ（GRUB）→ カーネル → initramfs → systemd の順番と、それぞれが何を読むかを言える
  • UEFI と BIOS で、ファームウェアが最初に読む場所の違い（ESP と MBR）を説明できる
  • ブートメディアの優先順位を、ファームウェアの設定画面と efibootmgr で確かめ、変えられる
ここで覚えなくていいこと: Secure Boot の署名を検証する仕組み（shim と MOK）、 grub.cfg の文法と GRUB のコマンド、カーネルが起動時に出す1行1行の意味、systemd-analyze の細かい使い方。

ブートローダは GRUB で、ここで止めればカーネルに渡す引数を書き換えられる（第6章）。 カーネルは自分だけではルートのディスクを開けない構成もあるので、ブートローダが一緒に渡した小さなファイルシステム initramfs に最初の仕事を任せる。 Begin: で始まる行は、その initramfs の中のスクリプトが出している。 なお error: prohibited by secure boot policy. の2行は、Secure Boot が有効なときに GRUB が出すもので、この練習機の起動には影響していない（毎回出る）。

たとえ: 起動はリレーに近い。各走者は、次の走者がどこに立っているかを自分の資料（NVRAM・grub.cfg・カーネル引数・default.target）で知っていて、バトンを渡したら退場する。
ただし崩れる点: リレーのバトンは同じ1本だが、起動では渡すものが毎回変わる（ファイルの場所 → カーネルとその引数 → ルートのファイルシステム → 目標のターゲット）。 しかも後の走者ほど読める範囲が広い。最初の走者（ファームウェア）は FAT しか読めない。

ファームウェアが読めるもの

この節で分かること: UEFI のファームウェアがディスクの何を読み、なぜ /boot/efi という区画があるのか。

ふつうこう考える

電源を入れると、UEFI（昔なら BIOS）が /boot にあるカーネル（vmlinuz）を読み込んで起動する。ブート順の設定に書いてあるのは「どのディスクのカーネルか」だろう。

$ sudo efibootmgr

Timeout: 0 seconds

Boot0002* Ubuntu	HD(15,GPT,9606bc98-2904-4577-9584-a8310313a04c,0x2800,0x35000)/File(\EFI\ubuntu\shimx64.efi)

vda

だめな理由: ブート順の先頭 Boot0002 に書いてあるのは、カーネルではなく 「15番目の区画（HD(15,GPT,…)）の \EFI\ubuntu\shimx64.efi というファイル」だった。 15番目の区画 vda15 は FAT（vfat）で、/boot/efi にマウントされている。カーネルのある /boot は別の区画 vda16 で、ext4 である。 UEFI の仕様がファームウェアに必ず読めるよう求めているファイルシステムは FAT だけで（ほかのファイルシステムを読めるファームウェアもあるが、当てにはできない）、ext4 の /boot はファームウェアからは中身の分からない領域でしかない。 だから FAT の区画（ESP: EFI システムパーティション）にブートローダを置き、そこから先の ext4 を読む仕事はブートローダ（GRUB）に任せている。

/sys/firmware/efi があることが、この Linux が UEFI で起動したことの証拠になる（BIOS で起動していれば無い）。ESP の中を見る。

$ findmnt -n -o TARGET,FSTYPE,OPTIONS /boot/efi
/boot/efi vfat   rw,relatime,fmask=0077,dmask=0077,codepage=437,iocharset=iso8859-1,shortname=mixed,errors=remount-ro
$ sudo blkid -p -o export /dev/vda15 | grep -E '^(TYPE|VERSION)='
VERSION=FAT32
TYPE=vfat
$ ls /boot/efi
ls: cannot open directory '/boot/efi': Permission denied
$ sudo ls -l /boot/efi/EFI/ubuntu
total 4380
-rwx------ 1 root root     108 Oct 13 09:58 BOOTX64.CSV
-rwx------ 1 root root     112 Oct 13 09:58 grub.cfg
-rwx------ 1 root root 2660232 Oct 13 09:58 grubx64.efi
-rwx------ 1 root root  856280 Oct 13 09:58 mmx64.efi
-rwx------ 1 root root  966664 Oct 13 09:58 shimx64.efi
$ sudo cat /boot/efi/EFI/ubuntu/grub.cfg
search.fs_uuid a5eecc38-8587-4601-9295-c92dabc20612 root
set prefix=($root)'/grub'
configfile $prefix/grub.cfg

ESP は FAT（blkid -p で区画そのものを調べると、版は FAT32）で、root 以外には中を見せない設定（fmask=0077,dmask=0077）でマウントされている。だから一般ユーザの ls は断られた。 中にあるのは、ファームウェアが最初に起動する shimx64.efi、そこから起動される GRUB 本体の grubx64.efi、そして3行しかない grub.cfg である。 3行の中身は「この UUID の区画を探し、その中の /grub/grub.cfg を読め」で、ESP の中に本当の設定は無い。UUID の a5eecc38-… は、上の lsblk で BOOT の区画（vda16）である。 GRUB は ext4 を読めるので、ここで初めて /boot（vda16）の中に手が届く。

たとえ: ESP は建物の受付カウンターに近い。受付（ファームウェア）が手を伸ばせるのはカウンターの上だけで、 そこに置いてある案内係（shim と GRUB）を呼び、奥の部屋（ext4 の /boot）へは案内係に行ってもらう。カウンターの上のメモ（3行の grub.cfg）には「奥の何号室へ」としか書いていない。
ただし崩れる点: 受付は奥の部屋の存在を知っているが、ファームウェアは ext4 の区画の中身を何も知らない。知っているのは、カウンターに置かれたファイルの名前だけである。

ブートメディアの優先順位は、NVRAM にある

この節で分かること: 起動する順番がどこに書かれ、どうやって変えるか。変えた順番が守られるとは限らないこと。

efibootmgr の BootOrder: 0002,0001,0000 が、ファームウェアが試す順番である。 0002（Ubuntu）、0001（UEFI Misc Device。ディスクの決まった場所 \EFI\BOOT\BOOTX64.EFI を試す汎用の候補）、0000（UiApp。ファームウェアの設定画面）の順になっている。 この順番はディスクではなく、ファームウェアの記憶領域（NVRAM）に入っている（練習機では外の ~/vm/linuc_VARS.fd がその中身）。

今回の起動は 0001 から（BootCurrent: 0001）なのに、BootOrder は 0002（Ubuntu）が先頭に戻っていた。 0001 が起動するのはディスクの決まった場所 \EFI\BOOT\BOOTX64.EFI で、その大きさ（966664 バイト）は shimx64.efi と同じ、つまり中身は shim である。 shim はこの場所から起動されると、隣の fbx64.efi（fallback）を動かす。fallback は BOOTX64.CSV（「shimx64.efi を Ubuntu という名前で登録せよ」）を読んで、 Ubuntu の候補を NVRAM に登録し直し、先頭に置く。ブート順を決めるのはファームウェアの設定のはずが、起動された側がそれを書き戻した。 （第1章で練習機を初めて起動したとき、コンソールに Boot0001 "UEFI Misc Device" と出ていたのも同じ仕組みで、そのとき Ubuntu の候補が作られた。）

たとえ: BootOrder は、受付に貼られた呼び出しの順番表に近い。管理人（あなた）が順番表を書き換えると、受付はその順に呼ぶ。
ただし崩れる点: 順番表を書き換えられるのは管理人だけのはずが、ここでは呼ばれた案内係（shim の fallback）が自分で順番表を書き直した。 NVRAM は「ファームウェアの設定」でも、OS や起動されたプログラムから書ける場所である。

カーネルが受け取った引数は /proc/cmdline にそのまま残っている。root=UUID=… がルートの区画、ro は「まず読み取り専用でマウントせよ」、console= は表示の行き先である。

その引数の出どころは、/etc/default/grub と /etc/default/grub.d/*.cfg である。同じ設定がファイルの順に何度も上書きされ（タイムアウトは 0 → 0 → 3 → 10）、 最後に読んだものが勝つ。これを update-grub（中身は grub-mkconfig -o /boot/grub/grub.cfg）が /boot/grub/grub.cfg に書き出し、 GRUB は起動のたびにそれを読む。grub.cfg を手で直しても、次に update-grub が走ると消えるので、毎回の設定は /etc/default/grub の側に書く。 1回だけ変えたいときは、GRUB のメニューで書き換える（第6章）。

ここで見ているのは GRUB 2（いまの GRUB）である。古い GRUB Legacy は、設定ファイル（/boot/grub/menu.lst、RHEL 系では grub.conf）を人が直接書き、生成する仕組みは無かった。 RHEL 系の GRUB 2 では、update-grub に当たるのが grub2-mkconfig -o /boot/grub2/grub.cfg で（UEFI の機械では出力先が変わる版もある）、 initramfs を作り直すコマンドも Ubuntu の update-initramfs に対して dracut である。

systemd-analyze は、カーネルと initramfs の段（kernel）と、systemd が既定のターゲットに着くまで（userspace）の時間を分けて出す。この練習機は KVM を使わないので、合わせて 31 秒ほどかかった。

確認

UEFI で起動するシステムで、ブートローダ（GRUB など）のファイルが置かれる区画は何か。また、そのファイルシステムは何か。

答え

EFI システムパーティション（ESP）。ファイルシステムは FAT（実測では、マウントの種類が vfat、blkid -p で調べた版が FAT32）で、Linux では /boot/efi にマウントされる。 UEFI の仕様がファームウェアに必ず読めるよう求めているのは FAT だけなので、ext4 の /boot には置けない。

確認

次のうち、Linux の起動の順番として正しいものはどれか。

A. カーネル → ブートローダ → UEFI → systemd
B. UEFI → ブートローダ → カーネル → initramfs → systemd
C. UEFI → カーネル → ブートローダ → systemd
D. ブートローダ → UEFI → initramfs → カーネル

答え

B。コンソールの表示の順（BdsDxe → GRUB のメニュー → Linux version → Run /init と Begin: の行 → Welcome to Ubuntu）と一致する。

確認

UEFI のブート順を Linux から変更するコマンドと、次回の1回だけ起動するものを指定するオプションは何か。

答え

efibootmgr。順番は -o（例: efibootmgr -o 0001,0002,0000）、次回の1回だけは -n（例: efibootmgr -n 0000）。 どちらも root の権限が要る。ファームウェアの設定画面（Boot Maintenance Manager → Change Boot Order）からも変えられる。

確認

BIOS で起動するとき、ファームウェアが最初に読み込むのはディスクのどこか。

答え

ディスクの先頭 512 バイト（MBR）。そのうち先頭の 446 バイトが起動コードで、そこからブートローダの続きを読み込む。 UEFI はこれと違い、ESP の中のファイルを名前で読む。

この章で分かったこと

持ち帰ってほしいこと

  • 起動はリレー: ファームウェア（UEFI / BIOS）→ ブートローダ（GRUB）→ カーネル → initramfs → systemd
  • UEFI のファームウェアが必ず読めるのは FAT の ESP（/boot/efi）だけ。カーネルのある ext4 の /boot は、ブートローダが読む
  • BIOS はディスクの先頭（MBR）の起動コードを読む。UEFI は ESP の .efi ファイルを読む。/sys/firmware/efi があれば UEFI で起動している
  • ブートメディアの優先順位は NVRAM の BootOrder。efibootmgr -o で順番、-n で次の1回。設定画面からも変えられる
  • 変えた順番は、起動された側（shim の fallback）が書き戻すことがある。決めるのは最後に受け取った側
  • カーネルに渡った引数は /proc/cmdline。毎回の引数は /etc/default/grub（と grub.d/）に書いて update-grub で grub.cfg に反映する
