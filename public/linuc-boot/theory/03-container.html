3. コンテナの中のカーネルは、ホストのもの

外側のコンテナで /etc/os-release を読むと Ubuntu 24.04.5 LTS と出る。同じコンテナで uname -r を打つと 7.2.6 と出る。 Ubuntu 24.04 にそんな版のカーネルは無い。それは著者の PC（ホスト）のカーネルである。 コンテナは計算機を持たず、ホストのカーネルを借りている。仮想マシンは自分のカーネルを持っている。

前提: 第2章まで読了（鍵で ssh linuc できる）所要 15分影響度 B出題範囲 1.01.2（重要度4）最終検証 2026-10-13

この章のゴール

  • コンテナと仮想マシンの違いを、同じコマンドを両方で打った出力で示せる
  • ハイパーバイザーの2つの型と、仮想化支援機能（VT-x / AMD-V）が何をするかを説明できる
  • docker stop / docker start が、コンテナの中の仮想マシンに何を起こすかを言える
ここで覚えなくていいこと: Docker のイメージの層の仕組み、Dockerfile の書き方、Kubernetes などのオーケストレーション、 仮想マシンの中でさらに仮想マシンを動かす入れ子の仮想化、QEMU が命令を翻訳する仕組みの細部。

同じ質問を、外と中に投げる

この節で分かること: コンテナと仮想マシンが、それぞれ誰のカーネルで動いているか。

ふつうこう考える

コンテナも「Ubuntu 24.04 のイメージ」から作った小さな計算機だ。/etc/os-release が Ubuntu 24.04 なら、 中では Ubuntu 24.04 のカーネルが動いているはずだ。

$ uname -r
7.2.6
$ uname -v
#1-NixOS SMP PREEMPT_DYNAMIC Mon Sep 14 11:41:11 UTC 2026
$ grep PRETTY_NAME /etc/os-release
PRETTY_NAME="Ubuntu 24.04.5 LTS"
だめな理由: /etc/os-release は Ubuntu なのに、カーネルは 7.2.6、ビルドの印は NixOS だった。 これは著者の PC で動いているホストOS（コンテナや仮想マシンを動かしている側の OS）のカーネルである。コンテナが Ubuntu なのはファイル（ユーザランド）だけで、カーネルはホストのものを借りている。 だからこの2行は、あなたの画面では本文と違う（あなたの PC のカーネルが出る。Docker Desktop なら linuxkit、WSL2 なら microsoft-standard-WSL2 などが付く）。 違うことが、この節の答えである。

同じ質問を、練習機の中に投げる。

$ uname -r
6.8.0-142-generic
$ uname -v
#142-Ubuntu SMP PREEMPT_DYNAMIC Wed Sep  2 14:24:27 UTC 2026
$ grep PRETTY_NAME /etc/os-release
PRETTY_NAME="Ubuntu 24.04.5 LTS"

練習機のカーネルは Ubuntu が配っている 6.8.0-142-generic で、ビルドの印も Ubuntu である。 仮想マシンは自分のカーネルを持ち、自分で起動した（第1章でコンソールに Linux version 6.8.0-142-generic と出たのはこれ）。こちらは読者全員が同じ画面になる。

もっと並べる。

$ ps -p 1 -o pid,comm
    PID COMMAND
      1 tini
$ nproc
16
$ free -m | head -2
               total        used        free      shared  buff/cache   available
Mem:           96068       18544       18632        3692       63627       77523
$ ps -p 1 -o pid,comm
    PID COMMAND
      1 systemd
$ nproc
2
$ free -m | head -2
               total        used        free      shared  buff/cache   available
Mem:            1424         231        1157           0         169        1193
見たもの外（コンテナ）練習機（仮想マシン）なぜ
カーネル（uname -r）ホストのもの自分のものコンテナはカーネルを持たない
PID 1tinisystemdコンテナは自分のプロセスの番号付けだけを持つ。1番は最初に起動したプログラム
CPU の数16（ホストの全部）2（定義どおり）コンテナは制限しなければホストの CPU がそのまま見える
メモリ約 94GB（ホストの全部）約 1.4GB（定義の 1.5GB からカーネルの分を引いた残り）仮想マシンには定義した分しか無い

コンテナは、ホストのカーネルの上で「プロセスの番号・ホスト名・ファイルの見え方」などを分けてもらったプロセスの集まりである（分ける仕組みを名前空間、使える量を絞る仕組みを cgroup という）。 外側のプロンプトのホスト名が host で PID 1 が tini なのは、この分け方のおかげで、カーネルそのものは共有している。

たとえ: コンテナはアパートの1部屋、仮想マシンは敷地の中に建てた別棟に近い。 部屋の住人は自分の表札（ホスト名）と郵便受け（PID）を持つが、水道と電気（カーネル）は建物のものを使う。別棟は配管も電気も自前で引いている。
ただし崩れる点: 本物の別棟は大家の建物と無関係に建っているが、この檻の練習機（別棟）は、アパートの1部屋（コンテナ）の中で動く QEMU というプロセスである。 部屋を解約すると（docker rm）、別棟も一緒に消える。

練習機の CPU は、ハイパーバイザーが見せている

この節で分かること: ハイパーバイザーと仮想化支援機能の関係。この檻がどちらの型か。
$ lscpu | grep -E '^(Model name|Virtualization|Hypervisor vendor):'
Model name:                              Intel(R) Core(TM) Ultra 9 285H
Virtualization:                          VT-x
$ grep -o -w -E 'vmx|svm' /proc/cpuinfo | sort | uniq -c
     32 vmx
$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory
$ lscpu | grep -E '^(Model name|Virtualization|Hypervisor vendor):'
Model name:                              QEMU TCG CPU version 2.5+
Virtualization:                          AMD-V
$ grep -o -w -E 'vmx|svm' /proc/cpuinfo | sort | uniq -c
      2 svm
$ systemd-detect-virt
qemu

外から見える CPU は本物（Intel Core Ultra 9 285H）で、Intel の仮想化支援機能 VT-x を表す vmx が flags に並んでいる（CPU 16個 × 2行ずつ）。 ところが練習機の中から見える CPU は QEMU TCG CPU で、しかも AMD の仮想化支援機能 AMD-V（svm）を名乗っている。 練習機の CPU は、ハイパーバイザー（QEMU）がソフトで作って見せているものだからだ。 外に /dev/kvm が無いので、QEMU は CPU の仮想化支援機能を使わず、ゲストの命令を1つずつ翻訳して実行している（TCG、完全エミュレーション）。 起動に 30 秒以上かかるのはこのためで、代わりにあなたの PC の特権を1つも借りずに済んでいる。

$ virsh capabilities | grep -o "<domain type='[a-z]*'" | sort | uniq -c
      2 <domain type='qemu'
$ virsh version | grep -i hypervisor
Running hypervisor: QEMU 8.2.2
$ ps -o pid,user,etime,comm -C qemu-system-x86_64
    PID USER         ELAPSED COMMAND
   2665 lab            01:59 qemu-system-x86

libvirt が使える仮想マシンの種類は qemu（TCG）だけで、kvm は無い。ハイパーバイザーは QEMU 8.2.2 である。 そして練習機は、外のコンテナの中で一般ユーザ lab が動かしている1つのプロセス（qemu-system-x86_64。名前は 15 文字で切れて見える。第8章）である。

ハイパーバイザーの型どこで動くか例
ネイティブ型（ハイパーバイザー型・ベアメタル型・Type 1）ハードウェアの上で直接動き、その上に OS が乗るVMware ESXi、Xen、Microsoft Hyper-V、Linux の KVM（カーネルの一部として動く）
ホスト型（Type 2）ホスト OS の上でアプリとして動くVirtualBox、VMware Workstation、この檻の QEMU（TCG）
たとえ: 仮想化支援機能は、国際会議の同時通訳ブースに近い。ブースがあれば、話者（ゲスト OS）の言葉はほぼそのまま聞き手（CPU）に届く。 無ければ逐次通訳（TCG）で、1文ずつ訳すので時間がかかる。
ただし崩れる点: 通訳は話の中身を変えないが、TCG は CPU そのものを作り替えて見せる。Intel の PC の上の練習機が AMD-V を名乗るのは、通訳が話者の国籍まで変えてしまうようなものだ。

コンテナを止めると、中の練習機はどうなるか

この節で分かること: docker stop / docker start の合図が、練習機にどう伝わるか。

練習機を外から見ている「外側のコンテナ」も、あなたの PC から見れば1つのコンテナである。止めて、また起動する。 この2行は、あなたの PC の端末（コンテナの外）で打つ。

docker stop lab-linuc-boot
docker start lab-linuc-boot
docker exec -it lab-linuc-boot bash -l

著者の環境では docker stop に 12.4 秒かかり、終了コードは 0 だった。 docker stop はコンテナの PID 1（tini）に TERM という合図（シグナル、第8章）を送るだけで、 受け取った檻の起動スクリプトが「練習機を virsh shutdown で正常に止めてから終わる」と決めている。 docker は待つが、無限には待たない。猶予（既定 10 秒）を過ぎると KILL で打ち切る。練習機の正常停止には十数秒かかる（第1章では約 12 秒）ので、 起動コマンドに --stop-timeout 30 を付けて猶予を延ばしてある。

起動し直した直後に外で一覧を見る。

$ virsh list
 Id   Name    State
-----------------------
 1    linuc   running

誰も virsh start を打っていないのに、練習機が動いている。第1章で付けた自動起動の印（virsh autostart）が効いた。 練習機の側から見ると、こうなっている。

$ last -x reboot shutdown | head -4
reboot   system boot  6.8.0-142-generi Tue Oct 13 20:47   still running
shutdown system down  6.8.0-142-generi Tue Oct 13 20:47 - 20:47  (00:00)
reboot   system boot  6.8.0-142-generi Tue Oct 13 20:45 - 20:47  (00:02)
reboot   system boot  6.8.0-142-generi Tue Oct 13 20:44 - 20:47  (00:03)
$ journalctl --list-boots --no-pager | tail -3
 -2 7e1c965c0c824c11a432a91f5cb34d8d Tue 2026-10-13 20:44:07 JST Tue 2026-10-13 20:44:30 JST
 -1 a63712b96ef14e4fbde4511c2ae11087 Tue 2026-10-13 20:45:08 JST Tue 2026-10-13 20:47:09 JST
  0 70f480a3ca08412e9fa9842cc2ba3c59 Tue 2026-10-13 20:47:40 JST Tue 2026-10-13 20:48:02 JST
$ journalctl -b -1 -n 4 --no-pager
Oct 13 20:47:09 linuc systemd-shutdown[1]: Syncing filesystems and block devices.
Oct 13 20:47:09 linuc systemd-shutdown[1]: Sending SIGTERM to remaining processes...
Oct 13 20:47:09 linuc systemd-journald[221]: Received SIGTERM from PID 1 (systemd-shutdow).
Oct 13 20:47:09 linuc systemd-journald[221]: Journal stopped

last -x は、起動（reboot）と停止（shutdown）の記録を新しい順に出す。いちばん上が今の起動で、その下に、前の起動が正常に終わった印（shutdown system down）がある。 journalctl --list-boots は、起動ごとに最初と最後の記録の時刻を出し、-b -1 は1つ前の起動の記録を指す。前の起動の最後の4行は、ディスクへの書き残しを同期して（Syncing filesystems）から記録を閉じている（Journal stopped）。 docker stop の合図は、檻の起動スクリプト → virsh shutdown → 練習機の OS と、受け取る側を順に渡っていき、最後の受け手が正常に止まると決めた。

比べると、その下の2つの reboot の行の間には shutdown の行が無い。第1章で virsh destroy（電源を抜く）をした起動である。 --list-boots の -2 がその起動である。電源を抜かれた起動の記録がどう残るかは、第7章で確かめる。 猶予が足りずに途中で KILL されると、練習機は電源を抜かれたのと同じになる。そのとき何が起きるかは第7章で見る。

たとえ: docker stop は、閉館時刻に流す館内放送に近い。放送を聞いた警備員（檻の起動スクリプト）が、各部屋（練習機）に戸締まりを頼んで回る。
ただし崩れる点: 館内放送は戸締まりが終わるまで待ってくれるが、docker stop は猶予の秒数が来たら、戸締まりの途中でも建物の電源を落とす（KILL）。 だから猶予を何秒にするかは、受け取る側の仕事の長さに合わせて、送る側が決めておく必要がある。

確認

コンテナと仮想マシンの違いについて、正しいものはどれか。

A. コンテナはそれぞれ自分のカーネルを起動する
B. 仮想マシンはホスト OS のカーネルを共有する
C. コンテナはホスト OS のカーネルを共有し、仮想マシンは自分のカーネルを持つ
D. どちらもハイパーバイザーの上で動く

答え

C。実測で、Ubuntu のコンテナの uname -r はホストの 7.2.6 を、練習機は Ubuntu の 6.8.0-142-generic を答えた。 D は誤り。コンテナはハイパーバイザーを使わず、ホストのカーネルの機能（名前空間・cgroup）で分けられている。

確認

CPU が仮想化支援機能を持っているかを /proc/cpuinfo で確かめたい。Intel と AMD で、それぞれ何というフラグを探すか。

答え

Intel（VT-x）は vmx、AMD（AMD-V）は svm。例: grep -E -c 'vmx|svm' /proc/cpuinfo。 ファームウェアの設定で無効にされていると、フラグが出ないことが多い（Intel で Linux 5.6 以降のカーネルの場合。AMD の svm や古いカーネルでは、無効でも出ることがある）。

確認

ハードウェアの上で直接動くハイパーバイザー（ハイパーバイザー型）の例を挙げよ。また、VirtualBox はどちらの型か。

答え

VMware ESXi、Xen、Hyper-V（Linux の KVM もカーネルに組み込まれてこの型として働く）。 VirtualBox はホスト OS の上でアプリとして動くホスト型。

この章で分かったこと

持ち帰ってほしいこと

  • コンテナはホストのカーネルを共有する。/etc/os-release が何であっても、uname -r はホストのカーネルを答える
  • 仮想マシンは自分のカーネルを起動する。CPU・メモリはハイパーバイザーが見せたものだけが見える
  • ハイパーバイザーには、ハードウェアの上で直接動く型と、ホスト OS の上で動く型がある
  • 仮想化支援機能は Intel が vmx（VT-x）、AMD が svm（AMD-V）。無ければ QEMU は TCG で翻訳して動かす（遅いが特権が要らない）
  • docker stop は PID 1 に TERM を送り、猶予の後に KILL する。中の練習機を正常に止められるかは、猶予と、受け取った側の作り次第
