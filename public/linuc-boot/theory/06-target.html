6. Ubuntu では、root にパスワードが無いとシングルユーザモードは何も聞かずに root を渡す

この練習機の root にはパスワードが無い（第4章で L＝ロックと確かめた）。だから root では誰も入れない——はずである。 ところが GRUB でカーネル引数に single と1語足して起動し、Enter を1回押すと、パスワードを1文字も打たずに root のシェルが出る。 シングルユーザモードを頼んだのはカーネル引数だが、root を渡すと決めたのは、それを受け取ったプログラムだった。

試験との関係: root にパスワードを設定してある計算機では、同じプログラム（sulogin）が root のパスワードを聞く。 試験の「シングルユーザモードでは root のパスワードを求められる」は、その場合の説明で、誤りではない。 また、root がロックされているときに聞かずに通すのは Ubuntu の改造で、本家の sulogin（RHEL 系など）はシェルを渡さずに止まる（この章の後半で比べる）。この章は、root がロックされている Ubuntu で何が起きるかを確かめる。
前提: 第5章まで読了前提: 端末を2つ開いている所要 18分影響度 B出題範囲 1.01.3（重要度4）最終検証 2026-10-13

この章のゴール

  • ブートターゲットとランレベルの対応を言え、get-default / set-default / isolate を使い分けられる
  • GRUB でカーネル引数を足し、その1回だけシングルユーザモード（rescue.target）で起動できる
  • シングルユーザモードで root を渡すかどうかを、誰が決めているかを説明できる
ここで覚えなくていいこと: ユニットファイル（.target や .service）の書き方、ターゲット同士の依存関係の細部（Wants と Requires の違い）、 systemd.unit= 以外の systemd 向けのカーネル引数、GRUB の設定ファイルの文法。

ターゲットとランレベル

昔の SysV init のランレベル（0〜6 の数字）は、systemd では同じ名前のターゲットへのシンボリックリンクとして残っている。 いま active なターゲットは 20 以上あり、graphical.target も multi-user.target も basic.target も同時に active である。 ブートターゲットは1本の目標ではなく、「ここまで来た」という到達点の重なりで、既定のもの（default.target）が一番上にある。

ランレベルターゲット意味
0poweroff.target停止
1（single）rescue.targetシングルユーザモード（保守用）
2・3・4multi-user.targetマルチユーザ・CUI（ネットワークあり）
5graphical.targetマルチユーザ・GUI のログイン
6reboot.target再起動
—emergency.targetrescue よりさらに最小（ほかのファイルシステムもサービスも起動しない）
たとえ: ターゲットは、ビルの階に近い。ランレベルの数字は、古い建物の階数表示が新しい建物でも案内板として残っているようなものである。
ただし崩れる点: ビルでは同時に2つの階にはいられないが、systemd では5階（graphical）にいる間も4階（multi-user）や1階（basic）が「到達済み」のまま active である。 だから「いま何階か」は1つに決まらず、runlevel は到達している一番上のターゲットを数字に読み替えて出している。

いまを変える isolate、次からを変える set-default

この節で分かること: 「いまの状態」と「次の起動」を、別々のコマンドで変えること。
$ sudo systemctl isolate multi-user.target
$ systemctl is-active graphical.target multi-user.target
inactive
active
$ runlevel
5 3
$ sudo systemctl default
$ runlevel
3 5

isolate は「指定したターゲットに要るものだけを残し、要らないものを止める」。multi-user.target に isolate すると graphical.target が inactive になり、 runlevel は「前回 5、いま 3」と答えた。systemctl default（既定のターゲットに isolate する）で戻すと「前回 3、いま 5」。isolate はいまの状態だけを変え、次の起動には何も残さない。

$ sudo systemctl set-default multi-user.target
Created symlink /etc/systemd/system/default.target → /usr/lib/systemd/system/multi-user.target.
$ ls -l /etc/systemd/system/default.target
lrwxrwxrwx 1 root root 41 Oct 13 20:53 /etc/systemd/system/default.target -> /usr/lib/systemd/system/multi-user.target
$ systemctl get-default
multi-user.target
$ systemctl is-active graphical.target
active
$ sudo systemctl set-default graphical.target
Removed "/etc/systemd/system/default.target".
Created symlink /etc/systemd/system/default.target → /usr/lib/systemd/system/graphical.target.
$ ls -l /etc/systemd/system/default.target
lrwxrwxrwx 1 root root 40 Oct 13 20:54 /etc/systemd/system/default.target -> /usr/lib/systemd/system/graphical.target

set-default がしたのは、/etc/systemd/system/default.target というリンクを作ることだけで、いまの状態（graphical.target が active）は変わらなかった。 効くのは次の起動からである。元に戻すと、リンクは消えずに graphical.target を指すリンクとして作り直された。

変えたいものやり方いまの状態次の起動
いまだけsystemctl isolate 〇〇.target（systemctl rescue、既定に戻す systemctl default なども）変わる既定に戻る
次の起動からsystemctl set-default 〇〇.target変わらない変わる
次の1回だけGRUB でカーネル引数に足す（systemd.unit=〇〇.target、single、3 など）—その1回だけ変わる

ふつうこう考える

シングルユーザモードは root だけが入れる保守用の状態だ。この練習機の root はロックされていて、パスワードが無い（第4章で L）。 だからシングルユーザモードで起動しても、root のパスワードを聞かれて止まる——少なくとも、パスワード無しで root になれることは無いはずだ。

[  OK  ] Reached target rescue.target - Rescue Mode.
（略）

system logs, "systemctl reboot" to reboot, or "exit"
to continue bootup.
Press Enter for maintenance
(or press Control-D to continue):
root@linuc:~# id; tty; systemctl is-active rescue.target
uid=0(root) gid=0(root) groups=0(root)
/dev/ttyS0
active
だめな理由: パスワードは聞かれなかった。「Press Enter for maintenance」に Enter を1回押しただけで、uid=0(root) のシェルが出た。 single が頼んだのは「rescue.target で起動せよ」だけで、root のシェルを渡すかどうかは、rescue.target が起動する sulogin（シングルユーザ用のログイン）が決めている。 Ubuntu の sulogin は、root のパスワード欄が *（ロック）だと「確かめようがない」として、パスワードを聞かずに通す。 これは Ubuntu が sulogin に入れている改造で（本家の sulogin は止まる。後で比べる）、root をロックした Ubuntu が、壊れたときに誰も直せなくならないようにしている。 コンソールに触れられる人は root になれる。守るのは GRUB のパスワード（引数の書き換えを禁じる）、ディスクの暗号化、機械に触らせないことである。

root のシェルを exit で抜けると、systemd は既定のターゲットへの起動を続ける。

rescue.target には入らず、いつもどおり graphical.target まで起動して、ログインを待っている。崩れた語はどのプログラムにも通じないので、黙って無視された。 同じ操作で崩れずに渡り、rescue.target に入った回もあった（著者の別の記録）。崩れるかどうかは、毎回同じではない。 長い語を足したら、起動した後に cat /proc/cmdline で本当に渡ったかを確かめる。この本の演習で短い語（single・3）を使うのはそのためである。

本家の sulogin と比べる: root がロックされていても聞かずに通すのは、Ubuntu が sulogin（util-linux）に入れている改造である。 本家の sulogin は、root がロックされているとシェルを渡さずに止まる。AlmaLinux 9.7 のコンテナで、root がロックされた状態（*）の sulogin を起動した記録を載せる。

$ grep '^root:' /etc/shadow | cut -d: -f1,2
root:*
$ script -qec sulogin /dev/null < /dev/null

Cannot open access to console, the root account is locked.
See sulogin(8) man page for more details.

Press Enter to continue.

本家の sulogin でも、root にパスワードがあれば、それを聞いて確かめる。root がロックされたままシェルを渡させるには、--force（systemd では環境変数 SYSTEMD_SULOGIN_FORCE=1）が要る。 「パスワードを聞かずに root を渡す」のは、root がロックされた Ubuntu だけの振る舞いと覚えておく。

たとえ: sulogin は、夜間に保守の人を通す通用口の守衛に近い。合い言葉（root のパスワード）があれば、それを聞いて確かめる。
ただし崩れる点: ふつうの守衛は合い言葉が決まっていなければ誰も通さないが、Ubuntu の sulogin は合い言葉が無いときに全員を通す。 通用口（コンソール）にたどり着けた時点で、中に入れてしまう。

init=/bin/bash: systemd を飛ばす

この節で分かること: PID 1 を差し替えると何が動き、何が動かないか。

もう1つ、試験によく出るカーネル引数がある。init= で、カーネルが最初に起動するプログラム（PID 1）そのものを差し替える。もう一度 GRUB で linux の行末に足す。

initramfs の仕事（Begin: Running /scripts/init-bottom）の後、systemd の代わりに bash が PID 1 として起動し、いきなり root のシェルになった。sulogin すら通っていない。 ホスト名も決まっておらず（(none)）、ジョブ制御も使えない。

systemctl get-default は動いた。リンクを読むだけだからである。一方 systemctl is-system-running は offline（終了コード 1）と答えた。 systemd が PID 1 として動いていないので、頼む相手がいない。/ は読み取り専用（ro）で、何かを直すなら mount -o remount,rw / が要る。 root のパスワードを忘れたときに、ここで passwd を打って付け直すのが、昔からの直し方である。

root@(none):/# exec /sbin/init
（略）
Welcome to Ubuntu 24.04.5 LTS!
（略）
[  OK  ] Reached target graphical.target - Graphical Interface.
（略）

exec /sbin/init で、PID 1 の bash を systemd に置き換えると、そこから普通の起動が始まる（exit すると PID 1 がいなくなり、カーネルが止まってしまう）。

たとえ: init= は、開演前に舞台監督を差し替えることに近い。いつもの監督（systemd）なら台本どおりに照明も音響も立ち上げるが、 代役（bash）は何も立ち上げず、舞台の上にあなた1人を立たせる。
ただし崩れる点: 代役は途中で本来の監督を呼べないのが普通だが、ここでは exec /sbin/init で代役が監督に変身でき、そこから上演が普通に始まる。
手を動かす: 実践編の演習03は、この章と同じ手順で、1回だけ multi-user.target で起動する課題である（足す語は 3）。 演習04は set-default で既定を変え、再起動しても CUI で起動することを確かめる。
確認

カーネルパラメータでシングルユーザモード（rescue.target）を指定して起動したい。GRUB で linux の行に足すものとして正しいものをすべて選べ。

A. single　B. 1　C. systemd.unit=rescue.target　D. runlevel=rescue

答え

A・B・C。systemd は single や 1 を rescue.target と読み替える。D のような引数は無い。 （A は本文で実測した。C は、この練習機の 80 桁のコンソールでは、打った文字が崩れて効かなかった回と、効いた回があった。B は試していない。）

確認

いま動いているシステムを、再起動せずにマルチユーザ（CUI）の状態に切り替えるコマンドはどれか。また、それは次の起動にも残るか。

A. systemctl set-default multi-user.target　B. systemctl isolate multi-user.target　C. systemctl enable multi-user.target

答え

B。isolate は指定したターゲットに要らないものを止めて、いまの状態を切り替える。次の起動には残らない（既定はそのまま）。 次の起動から変えるのは A の set-default で、こちらはいまの状態を変えない。

確認

ランレベル 1・3・5 は、systemd ではそれぞれどのターゲットに当たるか。

答え

1 → rescue.target、3 → multi-user.target、5 → graphical.target。 実測では /usr/lib/systemd/system/runlevel1.target などがそれぞれのターゲットへのシンボリックリンクになっていた（0 → poweroff.target、6 → reboot.target）。

確認

root のパスワードがロックされた Ubuntu を、GRUB で single を足して起動した。何が起きるか。また、それを防ぐにはどうするか。

答え

「Press Enter for maintenance」と出て、Enter を押すとパスワード無しで root のシェルが出る（実測）。 Ubuntu の sulogin が「root にパスワードが無いなら確かめようがない」として通すためである（Ubuntu の改造。本家の sulogin や RHEL 系では「Cannot open access to console, the root account is locked.」と出て、シェルは渡らない）。 防ぐには GRUB にパスワードを掛けて引数の書き換えを禁じる、ディスクを暗号化する、コンソールに物理的に触れさせない、のいずれかが要る。

この章で分かったこと

持ち帰ってほしいこと

  • ランレベルはターゲットに読み替えられる（0 poweroff・1 rescue・3 multi-user・5 graphical・6 reboot）。runlevel は「前回 いま」を出す
  • isolate はいまだけ、set-default は次の起動から（/etc/systemd/system/default.target のリンクを書く）、カーネル引数はその1回だけ
  • GRUB のメニューで e を押し、linux の行の末尾に single（または 1、systemd.unit=rescue.target）を足し、Ctrl+X で起動する
  • シングルユーザモードで root を渡すかは sulogin が決める。Ubuntu では root がロックされているとき、パスワードを聞かずに通す
  • init=/bin/bash は systemd を飛ばして bash を PID 1 にする。ルートは読み取り専用で、systemd に頼むコマンドは動かない
  • コンソールに触れられる人は root になれる。守るのは GRUB のパスワード・暗号化・物理的な管理
