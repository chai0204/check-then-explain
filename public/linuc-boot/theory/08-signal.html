8. kill は止めない。合図を送るだけ

kill という名前のコマンドは、プロセスを殺さない。番号の付いた合図（シグナル）を送るだけで、どう振る舞うかは受け取ったプロセスが決める。 練習機には、その合図を無視するプロセスが1つ動いている。kill を打っても、消えない。

前提: 第7章まで読了所要 16分影響度 B出題範囲 1.01.4（重要度3）最終検証 2026-10-13

この章のゴール

  • ps・top・pstree・uptime・pgrep で、動いているプロセスと負荷を読める
  • kill・pkill・killall の違い（何で相手を指定するか）と、既定のシグナルを言える
  • 無視できるシグナルと、無視できないシグナル（KILL・STOP）を区別できる
ここで覚えなくていいこと: ps と top の全オプション・全列、シグナルの番号の全部（覚えるのは 1・2・9・15・18・19・20 で足りる）、 /proc/PID/status の他の行、プロセスの優先度（nice・renice。Version 10.0 の出題範囲から外れた）。

プロセスを見る

この節で分かること: 動いているものを、一覧・木・刻々の3つの見方で見る。

まず、練習機がどれくらい忙しいかを1行で見る。

$ uptime
 19:28:07 up 0 min,  1 user,  load average: 1.58, 0.41, 0.14
$ cat /proc/loadavg
1.58 0.41 0.14 1/129 689

uptime は、いまの時刻・起動してからの時間・ログイン中のユーザ数・ロードアベレージを1行で出す。 ロードアベレージは、実行中か実行の順番を待っている（またはディスクの読み書きを待っている）プロセスの数を、直近1分・5分・15分で平均したものである。 同じ3つの数は /proc/loadavg にもあり、uptime も top もここを読んでいる。

練習機は第7章の最後で再起動したばかりで（up 0 min）、1分の値（1.58）だけが高く、15分の値（0.14）はまだ低い。起動の作業が直前の1分に集まっていたからである。 練習機の CPU は2個（第1章の virsh dominfo）で、ロードアベレージは CPU の数と比べて読む。1分の値（1.58）でも 2 に届いていないので、起動の直後でも CPU の順番待ちは続いていなかった。 3つの数は「いまの値」ではなく平均なので、1分と15分を比べると、忙しさが増えているのか収まりつつあるのかが読める。

次に、プロセスの一覧を見る。ps は、打った瞬間のプロセスを一覧にする。

$ ps aux | head -4
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root           1 15.1  0.8  21692 12932 ?        Ss   19:27   0:05 /sbin/init
root           2  0.1  0.0      0     0 ?        S    19:27   0:00 [kthreadd]
root           3  0.0  0.0      0     0 ?        S    19:27   0:00 [pool_workqueue_release]
$ ps -ef | head -4
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0 14 19:27 ?        00:00:05 /sbin/init
root           2       0  0 19:27 ?        00:00:00 [kthreadd]
root           3       2  0 19:27 ?        00:00:00 [pool_workqueue_release]

ps のオプションには書き方が2系統ある。aux（ハイフンなし。BSD 系）と -ef（ハイフンあり。System V 系）で、どちらも「全員のプロセスを」の意味だが、出る列が違う。 aux は CPU とメモリの使用率（%CPU %MEM）と状態（STAT）を、-ef は親の PID（PPID）を出す。試験にはどちらも出る。

STAT の文字意味
R実行中か、実行の順番を待っている
S眠って待っている（何かが起きれば起きる）
T止められている（Ctrl+Z など。第9章）
Z終わったが、親がまだ後始末をしていない（ゾンビ）
2文字目の sセッションの先頭（ログインシェルやデーモンの親）

オプションの1文字の違いで、出るものが大きく変わる組がある。

$ ps -f
UID          PID    PPID  C STIME TTY          TIME CMD
student      963     962  3 19:30 pts/1    00:00:00 -bash
student      991     963 99 19:30 pts/1    00:00:00 ps -f
$ ps f
    PID TTY      STAT   TIME COMMAND
    963 pts/1    Ss     0:00 -bash
    992 pts/1    R+     0:00  \_ ps f
    889 pts/3    Ss+    0:00 /bin/bash
    672 pts/0    Ss+    0:00 -bash
$ ps -A | wc -l; ps -e | wc -l
131
131
$ ps e -o args= -p $$ | cut -c1-100
-bash LANG=C.UTF-8 USER=student LOGNAME=student HOME=/home/student PATH=/usr/local/sbin:/usr/local/b

-f（ハイフンあり）は列を増やすだけで（フル形式。UID・PPID・C・STIME が付く）、親子の木は出さない。 木を出すのはハイフンなしの f（--forest と同じ）で、\_ の線で子を字下げする。 選ばれるプロセスの範囲も違う。ハイフンありの書き方はこの端末（pts/1）のものだけを、ハイフンなしの書き方は自分の、端末を持つプロセスすべてを出した（この記録は第10章まで進めた後に撮ったので、第9章で残す screen の中のシェル（pts/3）と、別の端末のシェル（pts/0）も写っている。順に進めてきた画面では、そのとき開いている端末の分だけが並ぶ）。 -A は -e と同じ「全部」で、数えると同じ数になった。ハイフンなしの e は、コマンドの後ろに環境変数を並べる（上の最後の出力は $$、つまりこのシェル自身の分を 100 文字で切ったもの）。

親子の関係は pstree が木で出す。-p で PID を添え、ユーザ名を付けるとそのユーザのプロセスだけを出す。

$ pstree -p student
lab-hog(504)───sleep(686)

sshd(671)───bash(672)───pstree(694)

systemd(654)───(sd-pam)(655)

lab-hog が子として sleep を動かしていること、いま打った pstree 自身が sshd → bash の子であることが分かる。

top は一覧を数秒ごとに描き直し続ける（終えるのは q）。ここでは記録に残すため、-b（描き直さずに文字で出す）と -n 1（1回だけ）を付けた。

    695 student   20   0    9380   5328   3200 R  14.3   0.4   0:00.13 top

      3 root      20   0       0      0      0 S   0.0   0.0   0:00.00 pool_wo+

1行目は uptime と同じ。2行目はプロセスの数を状態ごとに、3行目は CPU の使われ方、4〜5行目はメモリを出す。表は CPU を多く使っている順に並び、いちばん上は top 自身だった。

特定のプロセスを探すのは pgrep である。条件に合うプロセスの PID だけを出すので、ほかのコマンドに埋め込める。

$ pgrep -a lab-hog
504 /bin/bash /usr/local/bin/lab-hog
$ pgrep -l -u student
504 lab-hog
654 systemd
655 (sd-pam)
671 sshd
672 bash
696 sleep
$ ps -o pid,ppid,user,stat,etime,cmd -p $(pgrep -x lab-hog)
    PID    PPID USER     STAT     ELAPSED CMD
    504       1 student  Ss         00:24 /bin/bash /usr/local/bin/lab-hog

-a は引数まで、-l は名前を添えて出し、-u はユーザで、-x は名前の完全一致で絞る。 $(pgrep -x lab-hog) のように埋め込めば、PID を目で写し間違えずに済む。lab-hog の親（PPID）は 1、つまり systemd が起動したサービスである。

たとえ: ps は集合写真、top は防犯カメラの映像、pstree は家系図に近い。同じ人たちを、その瞬間・刻々・親子の向きで見ている。
ただし崩れる点: 集合写真は全員を同じ瞬間に写すが、ps はプロセスを1つずつ順に見て回る。見て回る間に生まれたものや消えたものは、写ったり写らなかったりする。 ps や pgrep の結果は「打った頃の様子」であって、次の行を打つときにも同じとは限らない。

kill を打っても消えない

この節で分かること: kill が実際に何をしているか。受け手がそれをどう扱えるか。

ふつうこう考える

kill はプロセスを殺すコマンドだ。PID を渡せば、そのプロセスは消える。

$ kill $(pgrep -x lab-hog)
$ ps -o pid,stat,comm -p $(pgrep -x lab-hog)
    PID STAT COMMAND
    504 Ss   lab-hog
だめな理由: lab-hog は残っていて、状態も Ss（眠って待っている）のまま変わらない。 kill は、プロセスにシグナルという番号付きの合図を送るだけのコマンドである。番号を付けなければ 15番の TERM（終了してください）を送る。 受け取ったプロセスは、そのまま終わるか、自分で後片付けをしてから終わるか、無視するかを、自分で決めておける。lab-hog は、起動したときに TERM を無視すると決めていた。

どのシグナルを無視しているかは、/proc/PID/status の SigIgn（無視する）と SigCgt（捕まえて自分で処理する）に、ビットの並びで出ている。

$ grep -E "^Sig(Ign|Cgt)" /proc/$(pgrep -x lab-hog)/status
SigIgn:	0000000000005007
SigCgt:	0000000000010000

16進数の 5007 を2進数にすると 0101 0000 0000 0111 で、右端を1番として 1・2・3・13・15 番目が立っている。HUP（1）・INT（2）・QUIT（3）・PIPE（13）・TERM（15）を無視している。 lab-hog が自分で無視を決めたのは TERM・INT・HUP の3つで（trap '' TERM INT HUP）、QUIT は bash がいつも無視するもの、PIPE は systemd がサービスを起動するときに無視させるもの（IgnoreSIGPIPE=yes が既定）である。 SigCgt の 10000 は 17番の CHLD（子が終わった知らせ）で、bash は子の sleep が終わったことを知るためにこれを捕まえている。

シグナルの番号と名前の一覧は kill -l で出る。

番号名前いつ送られるか受け手が無視できるか
1HUP端末（回線）が切れたとき（第9章）。デーモンには「設定を読み直して」の意味で送ることが多いできる

無視も捕捉もできないのは、KILL と STOP の2つだけである。この2つはプロセスに渡されず、カーネルがその場で処理する。

$ kill -KILL $(pgrep -x lab-hog)
$ pgrep -a lab-hog; echo "終了コード $?"
終了コード 1
$ systemctl status lab-hog --no-pager | head -6
× lab-hog.service - linuc-boot exercise 06: a process that ignores SIGTERM
     Loaded: loaded (/etc/systemd/system/lab-hog.service; enabled; preset: enabled)
     Active: failed (Result: signal) since Tue 2026-10-13 19:28:22 JST; 187ms ago
   Duration: 29.566s
    Process: 504 ExecStart=/usr/local/bin/lab-hog (code=killed, signal=KILL)
   Main PID: 504 (code=killed, signal=KILL)

pgrep は何も見つけられず、終了コード 1 を返した。systemd は lab-hog の終わり方を「シグナル KILL で殺された（code=killed, signal=KILL）」と記録している。 kill -9 PID と kill -KILL PID は同じ意味である（9番が KILL）。

シグナルの指定のしかたは、ほかにもある。-SIG を付けた名前と、-s の後ろに名前か番号を書く形である。

$ sleep 801 &
[1] 1000
$ kill -s 15 $!
$ sleep 802 &
[2] 1001
[1]   Terminated              sleep 801
$ kill -SIGKILL $!
$ jobs
[2]+  Killed                  sleep 802

kill -s 15 は TERM（Terminated）、kill -SIGKILL は KILL（Killed）を送った。$! は、直前に & で起動したプロセスの PID である。 つまり KILL は、kill -9・kill -KILL・kill -SIGKILL・kill -s KILL・kill -s 9 のどれで書いてもよい。

たとえ: TERM は「閉店です、お帰りください」という館内放送で、KILL は警備員が腕をつかんで外へ出すことに近い。放送は聞き流せるが、警備員は断れない。
ただし崩れる点: 連れ出された客でも、自分の足で歩き、荷物くらいは持って出られる。KILL されたプロセスは何もしないまま消える。 開いていたファイルを閉じる、一時ファイルを消す、書きかけを保存する、といった後片付けは一切されない。だから KILL は、TERM で止まらないときの最後の手段にする。

名前で送る: pkill と killall

この節で分かること: PID を調べずに、名前や条件でシグナルを送る方法と、その落とし穴。

PID を調べずに、名前や条件で選んで送るコマンドが2つある。sleep を3つ動かして試す（& は第9章で扱う。後ろで動かす印）。

$ sleep 601 &
[1] 716
$ sleep 602 &
[2] 717
$ sleep 603 &
[3] 718
$ jobs
[1]   Running                 sleep 601 &
[2]-  Running                 sleep 602 &
[3]+  Running                 sleep 603 &

pkill は pgrep と同じ条件で選んで、シグナルを送る（既定は TERM）。-f を付けると、名前ではなく引数まで含めたコマンド行で照合するので、sleep 601 の1つだけを選べた。 killall は名前の完全一致で選ぶので、sleep という名前の残り2つが両方止まった。pkill の名前は正規表現で、名前の一部に一致すれば当たる。killall は名前全体が一致したものにだけ送る。

名前で選ぶときには落とし穴が1つある。

$ cp /usr/bin/sleep /tmp/very-long-process-name
$ /tmp/very-long-process-name 300 &
[1] 727
$ pgrep very-long-process-name; echo "終了コード $?"
pgrep: pattern that searches for process name longer than 15 characters will result in zero matches
Try `pgrep -f' option to match against the complete command line.
終了コード 1
$ pgrep -f very-long-process-name
727
$ ps -o pid,comm,args -p $!
    PID COMMAND         COMMAND
    727 very-long-proce /tmp/very-long-process-name 300
$ pkill -f very-long-process-name
[1]+  Terminated              /tmp/very-long-process-name 300
$ jobs

プロセスの名前（ps の COMMAND 列の短いほう。comm と呼ぶ）は、カーネルの中に 15 文字までしか持っていない。 very-long-process-name（22文字）は very-long-proce として記録され、それより長い名前で探すと pgrep は何も見つけられない（pgrep 自身がそう注意してくる）。 長い名前のプロセスは、-f を付けてコマンド行全体で探す。

killall は、この点が逆になる。

$ cp /usr/bin/sleep /tmp/very-long-process-name
$ /tmp/very-long-process-name 300 &
[1] 1004
$ pgrep -l very-long-proce
1004 very-long-proce
$ killall very-long-proce; echo "終了コード $?"
very-long-proce: no process found
終了コード 1
$ killall very-long-process-name; echo "終了コード $?"
[1]+  Terminated              /tmp/very-long-process-name 300
終了コード 0
$ jobs

pgrep は 15 文字に切られた名前（very-long-proce）で見つけたが、killall はその名前では「無い」と答え、元の長い名前で止めた。 killall は、名前がちょうど 15 文字で切れているプロセスについては、コマンド行のほうの名前と比べるからである。 短い名前で探すなら pgrep・pkill、長い名前のまま探すなら killall か -f と覚えると取り違えない。

たとえ: プロセスの名前は、名前の欄が15文字しかない名札に近い。長い名前は途中で切れて書かれている。
ただし崩れる点: 人なら、切れた名札でも「たぶんあの人だ」と見当をつけて呼べる。pgrep は切れた名札と探す名前を文字どおり比べるので、長い名前で探すと誰も返事をしない。 見当をつけてくれる係はいないので、-f でコマンド行という別の札を見に行く。
手を動かす: 実践編の演習06は、TERM を無視する lab-hog を止める課題である。 判定は、systemd が記録した lab-hog の終わり方（何番のシグナルで終わったか）を確かめる。
確認

kill 1234 のようにシグナルを指定せずに実行したとき、送られるシグナルはどれか。

A. SIGHUP（1）　B. SIGINT（2）　C. SIGKILL（9）　D. SIGTERM（15）

答え

D。kill の既定は TERM（終了してください、という頼み）。受け手は無視も後片付けもできる。 実測で、TERM を無視する lab-hog は kill の後も S（眠って待っている）のまま残った。

確認

受け取ったプロセスが無視も捕捉もできないシグナルを2つ挙げよ。

答え

SIGKILL（9）と SIGSTOP（19）。この2つはプロセスに届く前にカーネルが処理する。 kill -9 PID（= kill -KILL PID）は相手に後片付けをさせずに終わらせるので、最後の手段にする。

確認

プロセス名 httpd のプロセスすべてに TERM を送りたい。使えるコマンドを2つ挙げよ。また、2つの違いは何か。

答え

pkill httpd と killall httpd。pkill は pgrep と同じ条件（名前の一部・正規表現・-f で引数まで・-u でユーザ）で選ぶ。 killall は名前の完全一致で選ぶ。pgrep と pkill は、15 文字で切られた名前（comm）と比べる点に注意（実測）。

確認

uptime の出力の末尾にある load average: の3つの数は何を表すか。

答え

直近1分・5分・15分の平均の負荷（実行中か、実行を待っているプロセスの数の平均）。CPU の数と比べて読む。 CPU が2個の練習機なら、2 を超え続けていれば待ちが出ている。

この章で分かったこと

持ち帰ってほしいこと

  • ps aux / ps -ef は一覧、pstree は親子の木、top は刻々（-b -n 1 で1回だけ）、uptime は稼働時間と負荷
  • pgrep は条件で PID を探す（-a 引数まで表示・-l 名前を表示・-u ユーザ・-f 引数まで含めて照合）
  • kill はシグナルを送るだけ。既定は TERM（15）で、受け手は無視できる。無視の印は /proc/PID/status の SigIgn
  • KILL（9）と STOP（19）は無視できない。kill -l で一覧が出る
  • kill は PID で、pkill は条件で、killall は名前で送る。pgrep・pkill が見る名前は 15 文字で切られる（killall は長い名前も完全一致で探せる）
