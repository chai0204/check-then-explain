2. 入れるかどうかは、受け取る側のファイルが決める

初めて ssh linuc を打つと、パスワードより先に「この相手を信じるか」と聞かれる。 鍵を使うようにすると、今度は練習機の側が、こちらを入れるかどうかを自分のファイルで決める。 ssh の信用は、どちらの向きも、受け取る側に置いたファイルに書いてある。

前提: 第1章まで読了前提: 練習機が起動している所要 20分影響度 B出題範囲 1.01.1（重要度4）最終検証 2026-10-13

この章のゴール

  • ssh-keygen で鍵ペアを作り、ssh-copy-id で相手に登録して、パスワードなしで入れる
  • ~/.ssh/id_rsa・id_rsa.pub・authorized_keys・known_hosts が、どちらの計算機に置かれ、誰が読むかを言える
  • logout・exit・Ctrl+D の違いを、出力で説明できる
ここで覚えなくていいこと: ~/.ssh/config に書ける項目の細部（この章で使う Host HostName Port User 以外。主題1.10.3 の範囲なので、linuc-security のコースで扱う）、 known_hosts をハッシュにする設定の名前、鍵の数学的な仕組み。 なお、鍵の種類（rsa・ecdsa・ed25519）の違い・ssh-agent・ポート転送は出題範囲（主題1.10.3）に入っているので、そちらのコースで手を動かす。

初めての接続: 相手を信じるかを聞かれる

この節で分かること: 接続する側が、相手を何で覚えるか。

外（lab@host）には、まだ鍵が1つも無い。あるのは接続先の設定だけである。

$ ls -la ~/.ssh
total 12
drwx------ 1 lab lab 4096 Oct 13 10:51 .
drwxr-x--- 1 lab lab 4096 Oct 13 20:40 ..
-rw-r--r-- 1 lab lab  502 Oct 13 10:11 config
$ cat ~/.ssh/config
（略）
Host linuc
    HostName 127.0.0.1
    Port 2222
    User student
    ServerAliveInterval 15

ssh linuc と打つと、ssh はこの設定を見て student@127.0.0.1 の 2222 番に接続する（QEMU が練習機の 22 番に転送している）。打つ。

$ ssh linuc

  - 採点は外のコンテナが持っています。この中でも lab check NN で答え合わせできます

student@linuc:~$ exit

パスワードより先に、相手（練習機の sshd）が出したホスト鍵の指紋（fingerprint）を見せて、信じるかを聞いてきた。 yes と答えると、その鍵が ~/.ssh/known_hosts に書かれる（Permanently added）。次からは聞かれない。 もし次に接続したとき相手の鍵が違っていたら、ssh は接続を止めて警告する。途中で誰かが相手になりすましているかもしれないからだ。

$ cut -c1-60 ~/.ssh/known_hosts
|1|8BliHPcGMVBoZAF2cTfzCnwXP2w=|AO1eScacB70ijbpgRh9HRQV2EVw=
|1|8Yyd3mWGtszczAPO/GWlcKi6AwU=|y/wH05bfLIleit7QtDp85ZnyZXU=
|1|2Ml1lNiPxSWc4VP0A5tYcCgVo6A=|3InIktgKL6NULQrxuAyKgY+5NMA=
$ ssh-keygen -F '[127.0.0.1]:2222' | cut -c1-60
# Host [127.0.0.1]:2222 found: line 1
|1|8BliHPcGMVBoZAF2cTfzCnwXP2w=|AO1eScacB70ijbpgRh9HRQV2EVw=
# Host [127.0.0.1]:2222 found: line 2
|1|8Yyd3mWGtszczAPO/GWlcKi6AwU=|y/wH05bfLIleit7QtDp85ZnyZXU=
# Host [127.0.0.1]:2222 found: line 3
|1|2Ml1lNiPxSWc4VP0A5tYcCgVo6A=|3InIktgKL6NULQrxuAyKgY+5NMA=
$ ssh-keygen -F linuc; echo "終了コード $?"
終了コード 1

known_hosts を開いても、相手の名前はどこにも書いていない。Ubuntu の ssh は名前を伏せて（ハッシュにして）記録するからだ。 記録のキーは linuc ではなく実際の接続先 [127.0.0.1]:2222 で、ssh-keygen -F に渡して初めて「1〜3行目がそれだ」と分かる。 3行あるのは、ログインした後に相手が持っている他の種類のホスト鍵も教えてもらって、まとめて覚えたからである。

たとえ: 初めて訪ねる家の表札を写真に撮っておくのに近い。次に来たとき、表札が違えば「別の家かもしれない」と気づける。
ただし崩れる点: 写真は見れば誰の家か分かるが、known_hosts は宛名を伏せて保存している。 ファイルを盗み見られても、どこに接続したことがあるかは分からない。代わりに、自分で読むときも ssh-keygen -F が要る。

鍵を作る

この節で分かること: 鍵の名前と種類が何で決まるか。試験の名前（id_rsa）との関係。

ふつうこう考える

出題範囲には ~/.ssh/id_rsa と id_rsa.pub が名指しされている。だから ssh-keygen を何も付けずに打てば、この2つができるはずだ。

$ ssh-keygen
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/lab/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/lab/.ssh/id_ed25519
Your public key has been saved in /home/lab/.ssh/id_ed25519.pub
（略）
$ ls -l ~/.ssh
total 20
-rw-r--r-- 1 lab lab 502 Oct 13 10:11 config
-rw------- 1 lab lab 399 Oct 13 20:45 id_ed25519
-rw-r--r-- 1 lab lab  90 Oct 13 20:45 id_ed25519.pub
-rw------- 1 lab lab 978 Oct 13 20:45 known_hosts
-rw-r--r-- 1 lab lab 142 Oct 13 20:45 known_hosts.old
だめな理由: できたのは id_ed25519 だった。鍵の種類の既定は OpenSSH 9.5 で RSA から Ed25519 に変わり、 Ubuntu 24.04 の OpenSSH（9.6）はそれに従っている。ファイル名は種類で決まるので、種類が変われば名前も変わる。 試験の id_rsa は RSA の鍵の名前で、今は -t rsa と頼まないと作られない。 （3つの問い——保存先・パスフレーズ・その確認——には Enter だけで答えた。パスフレーズを空にすると、鍵のファイルを盗まれたら終わりになる。練習機だから空にしている。）
試験との関係: 試験の例題は、ssh-keygen で id_rsa と id_rsa.pub ができる（RSA が既定だった頃の説明）として書かれていることがある。 問われたら、その前提で答えてよい。手元の新しい OpenSSH（9.5 以降）で同じものを作るには -t rsa を付ける。

種類を指定して、もう1組作る。

$ ssh-keygen -t rsa
Generating public/private rsa key pair.
Enter file in which to save the key (/home/lab/.ssh/id_rsa):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/lab/.ssh/id_rsa
Your public key has been saved in /home/lab/.ssh/id_rsa.pub
（略）
$ ls -l ~/.ssh
total 28
-rw-r--r-- 1 lab lab  502 Oct 13 10:11 config
-rw------- 1 lab lab  399 Oct 13 20:45 id_ed25519
-rw-r--r-- 1 lab lab   90 Oct 13 20:45 id_ed25519.pub
-rw------- 1 lab lab 2590 Oct 13 20:45 id_rsa
-rw-r--r-- 1 lab lab  562 Oct 13 20:45 id_rsa.pub
-rw------- 1 lab lab  978 Oct 13 20:45 known_hosts
-rw-r--r-- 1 lab lab  142 Oct 13 20:45 known_hosts.old
$ ssh-keygen -lf ~/.ssh/id_rsa.pub
3072 SHA256:ZbSNblQ4MACaLhP0nO7H5HStxlCHSMGfY3tw0Wc9aS0 lab@host (RSA)

秘密鍵（拡張子なし）は -rw-------（本人だけが読める）、公開鍵（.pub）は -rw-r--r--（誰が読んでもよい）で作られた。 RSA の鍵は 3072 ビットが既定である。

ファイル置く場所中身誰が読むか
~/.ssh/id_rsa接続する側（外）秘密鍵。手元から出さない自分の ssh
~/.ssh/id_rsa.pub接続する側（外）公開鍵。相手に渡してよい相手に写されて、相手の sshd
~/.ssh/authorized_keys接続される側（練習機）入ってよい公開鍵の一覧相手の sshd
~/.ssh/known_hosts接続する側（外）信じると決めた相手のホスト鍵自分の ssh

公開鍵を渡すと、受け取る側の名簿に1行増える

この節で分かること: パスワードなしで入れるようになったとき、どこに何が増えたか。
$ ssh-copy-id -i ~/.ssh/id_rsa.pub linuc

/usr/bin/ssh-copy-id: INFO: attempting to log in with the new key(s), to filter out any that are already installed

パスワードを聞かれるのは、この1回だけである（まだ鍵が登録されていないから）。もう一度入る。今度は何も聞かれない。

$ ssh linuc
$ ls -la ~/.ssh
total 12
drwx------ 2 student student 4096 Oct 13 09:46 .
drwxr-x--- 4 student student 4096 Oct 13 20:41 ..

練習機の ~/.ssh/authorized_keys に、外の id_rsa.pub と同じ1行（ssh-rsa AAAA…）が入った。 ssh-copy-id がしたのは、これを書き足すことだけである。手で cat id_rsa.pub >> ~/.ssh/authorized_keys しても同じになる。

外の ssh が、どの鍵をどの順で見せたかを確かめる。

$ ssh -v linuc true 2>&1 | grep -E 'identity file /home/lab/.ssh/id_[a-z0-9_]+ type|Offering|Authenticated'
debug1: identity file /home/lab/.ssh/id_rsa type 0
debug1: identity file /home/lab/.ssh/id_ecdsa type -1
debug1: identity file /home/lab/.ssh/id_ecdsa_sk type -1
debug1: identity file /home/lab/.ssh/id_ed25519 type 3

debug1: identity file /home/lab/.ssh/id_xmss type -1
debug1: identity file /home/lab/.ssh/id_dsa type -1

Authenticated to 127.0.0.1 ([127.0.0.1]:2222) using "publickey".

ssh は決まった名前（id_rsa → id_ecdsa → … → id_ed25519）を順に探し、ある鍵（type が -1 でないもの）を見せる。 最初に見せた id_rsa を、練習機の sshd が名簿と照らして受け入れた。鍵は「見せる」だけで、通すかどうかは受け取る側が決めている。

たとえ: authorized_keys は、受付が持っている入館者名簿に近い。来た人は名簿に載っている名前を名乗り、本人である証拠（秘密鍵で作った署名）を見せる。
ただし崩れる点: 名簿には顔写真（秘密鍵）は載っていない。載っているのは公開鍵だけで、名簿が漏れても、それだけでは誰も入れない。 入るには、手元にしかない秘密鍵が要る。

ここまで ssh linuc の1語で済んでいたのは、外の ~/.ssh/config に、つなぎ先・ポート・ユーザが書いてあるからである。同じことをオプションで書くと、こうなる。

$ cat ~/.ssh/config
# 外側（lab@host）から練習機（student@linuc）に入るときの設定。`ssh linuc` で入れる。
# 実体は 127.0.0.1:2222（QEMU が練習機の 22 番に転送している）。
#
# 鍵のファイル（IdentityFile）はわざと書いていない。書かなければ ssh は既定の名前
# （~/.ssh/id_rsa, id_ecdsa, id_ed25519 …）を順に探す。第2章でそれを確かめる。
Host linuc
    HostName 127.0.0.1
    Port 2222
    User student
    ServerAliveInterval 15
$ ssh -i ~/.ssh/id_rsa -p 2222 -l student 127.0.0.1 hostname
linuc
$ ssh -i ~/.ssh/id_rsa -p 2222 student@127.0.0.1 hostname
linuc
$ ssh -v -i ~/.ssh/id_rsa -p 2222 -l student 127.0.0.1 true 2>&1 | grep -E 'Connecting to|Offering public key|Authenticated to'
debug1: Connecting to 127.0.0.1 [127.0.0.1] port 2222.
debug1: Offering public key: /home/lab/.ssh/id_rsa RSA SHA256:ZbSNblQ4MACaLhP0nO7H5HStxlCHSMGfY3tw0Wc9aS0 explicit
Authenticated to 127.0.0.1 ([127.0.0.1]:2222) using "publickey".
$ ssh -l student 127.0.0.1 hostname
ssh: connect to host 127.0.0.1 port 22: Connection refused
オプション意味~/.ssh/config での書き方
-i ファイル使う秘密鍵を指定する（-v の Offering public key の行末の explicit は「指定された鍵」の印）IdentityFile
-p ポート接続先のポート。省くと 22 番（上の最後の行は 22 番に断られた）Port
-l ユーザログインするユーザ。ユーザ@ホスト と書いても同じUser

紛らわしいのは -i である。どちらも「鍵の組（identity）」を指す文字で、ssh -i には秘密鍵のファイルを渡す。 ssh-copy-id -i には、この章では id_rsa.pub を渡したが、.pub を付けずに渡してもよい。

$ ssh-copy-id -i ~/.ssh/id_rsa linuc
/usr/bin/ssh-copy-id: INFO: Source of key(s) to be installed: "/home/lab/.ssh/id_rsa.pub"
/usr/bin/ssh-copy-id: INFO: attempting to log in with the new key(s), to filter out any that are already installed

/usr/bin/ssh-copy-id: WARNING: All keys were skipped because they already exist on the remote system.
		(if you think this is a mistake, you may want to use -f option)

名前が .pub で終わっていなければ .pub を足して読むので、相手に送られるのは常に公開鍵である（Source of key(s) の行）。 ここでは同じ鍵が既に名簿にあったので、何も足さなかった。

名簿を他人が書き換えられるなら、名簿ごと使わない

この節で分かること: 鍵を登録したのにパスワードを聞かれるとき、何を疑うか。

鍵を登録したのに、ある日パスワードを聞かれるようになった——実務でよく起きる。練習機で、名簿（authorized_keys）の権限を緩めてみる。

$ ssh linuc 'id; chmod 664 ~/.ssh/authorized_keys; ls -l ~/.ssh/authorized_keys'
uid=1000(student) gid=1000(student) groups=1000(student),4(adm),27(sudo)
-rw-rw-r-- 1 student student 562 Oct 13 20:45 /home/student/.ssh/authorized_keys
$ ssh linuc 'echo 鍵で入れた; getent group student'
鍵で入れた
student:x:1000:

group に書ける（664）ようにしても、鍵で入れた。student グループのメンバー欄は空で、書けるのは本人だけである。 ただし、これを許すのは Debian / Ubuntu の sshd の改造で、練習機の man ssh にも「本人だけのグループなら group に書けてもよい」という但し書きがある。

$ ssh linuc "man ssh | grep -B2 -A2 'group-writable'"
troff:<standard input>:970: warning [p 8, 8.8i]: cannot adjust line
               of  the potential for abuse, this file must have strict permis‐
               sions: read/write for the user, and not writable by others.  It
               may be group-writable provided that the group in question  con‐
               tains only the user.

（troff: で始まる行は、端末を持たない ssh の中で man が文章を整形したときの警告で、中身とは関係ない。）本家の OpenSSH にはこの改造が無く、グループが本人だけでも、group に書けるだけで断る。比べるために、AlmaLinux 9.7 のコンテナで同じことをした記録を載せる。

$ chmod 664 /home/alice/.ssh/authorized_keys; ls -l /home/alice/.ssh/authorized_keys; getent group alice
-rw-rw-r-- 1 alice alice 100 Oct 13 11:33 /home/alice/.ssh/authorized_keys
alice:x:1000:
$ su - alice -c 'ssh -o StrictHostKeyChecking=accept-new -o BatchMode=yes localhost true'; echo "終了コード $?"
Warning: Permanently added 'localhost' (ED25519) to the list of known hosts.
alice@localhost: Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
終了コード 255
$ grep 'Authentication refused' /tmp/sshd.log
Authentication refused: bad ownership or modes for file /home/alice/.ssh/authorized_keys
$ chmod 600 /home/alice/.ssh/authorized_keys
$ su - alice -c 'ssh -o BatchMode=yes localhost echo 鍵で入れた'
鍵で入れた

試験では「authorized_keys は group にも other にも書けてはいけない（600 にする）」と答える。

次は他人（other）にも書けるようにする。

$ ssh linuc 'chmod 666 ~/.ssh/authorized_keys; ls -l ~/.ssh/authorized_keys'
-rw-rw-rw- 1 student student 562 Oct 13 20:45 /home/student/.ssh/authorized_keys
$ ssh linuc
student@127.0.0.1's password:

パスワードを聞かれた。外の ssh は何も教えてくれない。理由は、受け取った側のログにだけ残る。パスワードで入って読む。

$ sudo journalctl -u ssh --no-pager -n 30 | grep -E 'refused|Accepted'
（略）
Oct 13 20:46:18 linuc sshd[802]: Authentication refused: bad ownership or modes for file /home/student/.ssh/authorized_keys
Oct 13 20:46:18 linuc sshd[802]: Authentication refused: bad ownership or modes for file /home/student/.ssh/authorized_keys
Oct 13 20:46:18 linuc sshd[802]: Accepted password for student from 10.0.2.2 port 60122 ssh2
$ chmod 600 ~/.ssh/authorized_keys
$ exit
logout
Connection to 127.0.0.1 closed.

sshd は「名簿の権限がおかしい」と鍵の照合を断り（Authentication refused）、残ったパスワード認証で通した。 他人が書き換えられる名簿は、誰かが自分の鍵を書き足せる名簿なので、sshd はそれを信用しない（sshd_config の StrictModes yes。既定）。 chmod 600 に戻せば、また鍵で入れる。

たとえ: 受付の入館者名簿が廊下の掲示板に貼り出されていて、誰でも書き込める状態に近い。そんな名簿に載っていても、受付は通さない。
ただし崩れる点: 受付なら「名簿が信用できないので」と一言説明してくれるが、sshd は接続してきた側に理由を言わない。 黙ってパスワードを聞くだけで、理由は自分のログにしか書かない。断られた側は、相手のログを読める人に頼むしかない。

抜け方: logout・exit・Ctrl+D

この節で分かること: 3つの抜け方が、どのシェルで何をするか。
$ ssh linuc
$ shopt login_shell
login_shell    	on
$ bash
student@linuc:~$ shopt login_shell
login_shell    	off
student@linuc:~$ logout
bash: logout: not login shell: use `exit'
student@linuc:~$ exit
exit
$
logout
Connection to 127.0.0.1 closed.

ssh で入って最初に動くシェルはログインシェル（login_shell on）である。その中で bash を打つと子のシェルが動き、こちらは off になる。 logout はログインシェルでしか使えず、子のシェルでは「exit を使え」と断られた。exit はどちらのシェルでも抜けられる。

最後の logout の表示は、Ctrl+D を押したときに出たものである。Ctrl+D は「入力の終わり」を送るキーで、シェルは入力が尽きたら終わる。 ログインシェルなので logout と表示して抜け、ssh の接続が閉じた（Connection to 127.0.0.1 closed.）。

コマンドを付けて ssh すると、ログインシェルは起動せず、そのコマンドだけを打って帰ってくる。

$ ssh linuc 'hostname; shopt login_shell'
linuc
login_shell    	off
抜け方ログインシェル子のシェル
logout抜ける使えない（not login shell）
exit抜ける抜ける（親のシェルに戻る）
Ctrl+D抜ける（logout と表示）抜ける（exit と表示）
手を動かす: 実践編の演習02は、試験の名前どおりの id_rsa を作り、練習機に登録してパスワードなしで入れるようにする課題である。 判定は、パスワードでの認証を禁じた ssh を実際に1回打って確かめる。
確認

ssh で初めて接続したサーバのホスト鍵は、接続した側のどのファイルに保存されるか。

A. ~/.ssh/authorized_keys　B. ~/.ssh/known_hosts　C. ~/.ssh/id_rsa.pub　D. /etc/ssh/ssh_host_rsa_key

答え

B。実測では yes と答えた直後に Permanently added … to the list of known hosts と出た。 A は接続される側に置く公開鍵の一覧、C は自分の公開鍵、D はサーバ自身が持っているホスト鍵の秘密鍵である。

確認

公開鍵認証でログインできるようにするため、クライアントで作った公開鍵をサーバ側のどのファイルに追記するか。また、それを1コマンドで行うものは何か。

答え

サーバ側のログインするユーザの ~/.ssh/authorized_keys。1コマンドで行うのは ssh-copy-id（-i で公開鍵を指定する）。 -i を省くと、ssh-agent に鍵が登録されていればその鍵が、無ければ ~/.ssh の中で一番新しい公開鍵が送られる。

確認

ssh-keygen -t rsa を既定のまま実行したとき、作られる秘密鍵と公開鍵のファイル名は何か。また、-t を付けずに実行するとどうなるか（OpenSSH 9.6）。

答え

~/.ssh/id_rsa（秘密鍵）と ~/.ssh/id_rsa.pub（公開鍵）。-t を付けないと Ed25519 になり、id_ed25519 と id_ed25519.pub ができる（実測）。

確認

シェルで logout と打ったら bash: logout: not login shell: use `exit' と表示された。何が起きているか。

答え

いま動いているのはログインシェルではなく、その中で起動した子のシェルである。logout はログインシェルでしか使えない。 exit（または Ctrl+D）で子のシェルを抜けると、親のログインシェルに戻る。

この章で分かったこと

持ち帰ってほしいこと

  • 初回の接続で相手のホスト鍵を確かめ、~/.ssh/known_hosts に覚える。違えば ssh が止める
  • ssh-keygen の既定は Ed25519（id_ed25519）。試験の id_rsa / id_rsa.pub は -t rsa で作る
  • 秘密鍵は手元から出さない（600）。渡すのは公開鍵だけで、相手の ~/.ssh/authorized_keys に1行足せば入れる（ssh-copy-id）
  • 鍵は見せるだけ。通すかは受け取る側の sshd が名簿と権限を見て決める。断った理由は相手のログにしか出ない
  • logout はログインシェルでだけ。exit はどこでも。Ctrl+D は入力の終わり
