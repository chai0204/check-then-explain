3. 時刻合わせは、基準を渡されるまで始まらない

この檻では時刻合わせのデーモンが動いている。systemctl is-active chrony は active を返す。それでも Reference ID は 00000000 で、Leap status は Not synchronised のままである。動いていることと、合わせていることは別のことだ。

前提: 第2章まで読了前提: 檻が起動している所要 15分影響度 B出題範囲 1.09.1（重要度2）最終検証 2026-10-12

この章のゴール

  • NTP クライアントが「基準」を設定で渡されるまで何もしないことを、出力で示せる
  • chronyc sources と chronyc tracking の読み分けができる
  • chronyd と ntpd が同時に入らない理由をパッケージの宣言から言える
ここで覚えなくていいこと: NTP のパケット形式、うるう秒の扱い、NTS（暗号化）、stratum の階層をどこまで深く追えるかは扱わない。ハードウェアタイムスタンプや PTP も外す。ここで覚えるのは「どのファイルに何を書くと、どのコマンドの出力がどう変わるか」だけである。

動いているのに、合っていない

この節で分かること: デーモンの稼働と、時刻が合っていることが別だという事実。
$ systemctl is-active chrony
active
$ chronyc sources
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
$ chronyc tracking
Reference ID    : 00000000 ()
Stratum         : 0
Ref time (UTC)  : Thu Jan 01 00:00:00 1970
System time     : 0.000000000 seconds fast of NTP time
Last offset     : +0.000000000 seconds
RMS offset      : 0.000000000 seconds
Frequency       : 0.000 ppm slow
Residual freq   : +0.000 ppm
Skew            : 0.000 ppm
Root delay      : 1.000000000 seconds
Root dispersion : 1.000000000 seconds
Update interval : 0.0 seconds
Leap status     : Not synchronised

chronyc sources は見出しだけを出して、行が1本も無い。Ref time が 1970-01-01 なのは「一度も基準と話していない」印である。

ふつうこう考える

デーモンが動いていないのではないか。あるいは起動に失敗しているのではないか。 サービスの状態とログを見れば原因が出るはずだ。

$ systemctl is-active chrony
active
$ chronyc activity
200 OK
0 sources online
0 sources offline
0 sources doing burst (return to online)
0 sources doing burst (return to offline)
0 sources with unknown address
だめな理由: 失敗していない。200 OK が返り、 chronyd は問い合わせにきちんと答えている。答えの内容が 「online が 0、offline が 0、unknown も 0」＝基準の候補を1つも持っていないというだけである。 エラーを探すと何も見つからない。探す先は設定ファイルで、そこに「どこを基準にするか」が 1行も書かれていない。

設定を見る。

$ grep -vE '^\s*#|^\s*$' /etc/chrony/chrony.conf
confdir /etc/chrony/conf.d
sourcedir /run/chrony-dhcp
sourcedir /etc/chrony/sources.d
keyfile /etc/chrony/chrony.keys
driftfile /var/lib/chrony/chrony.drift
ntsdumpdir /var/lib/chrony
logdir /var/log/chrony
maxupdateskew 100.0
rtcsync
makestep 1 3
leapsectz right/UTC

置き場所（driftfile、logdir）と振る舞い（makestep）は書いてあるが、server も pool も無い。

（この教材では既定の pool ntp.ubuntu.com を外してある。インターネットに出られる読者と出られない読者で出力が完全に変わり、「本文と同じ画面が出る」が壊れるため。著者の環境ではこの行を残したまま測ると、外部のサーバに stratum 3 で同期してしまい、誰にも再現できない出力になった。）

たとえ: 検針員を雇ったが、どの家を回るかのリストを渡していない状態に近い。 出勤はしているし、呼べば返事もする。回る先が0軒なので報告できる数字が無い。
ただし崩れる点: 検針員はリストが空なら「仕事がない」と言うが、 chronyd は何も言わない。chronyc で聞いたときだけ 0 を返す。 黙っていることを「正常」と読み違えないために、聞きに行く必要がある。

基準を1行与える

この節で分かること: 設定1行で出力がどこまで変わるか。

この檻の中には、基準として使えるサーバがもう1台立っている。

$ systemctl is-active lab-ntp-server
active
$ grep -vE '^\s*#|^\s*$' /etc/chrony/lab-ntp-server.conf
local stratum 8
allow 127.0.0.1
bindaddress 127.0.0.1
driftfile /var/lib/chrony/lab-server.drift
pidfile /run/chrony-lab-server.pid
cmdport 0
$ ss -lun | grep -E ':(123|323)'
UNCONN 0      0          127.0.0.1:123       0.0.0.0:*
UNCONN 0      0          127.0.0.1:323       0.0.0.0:*
UNCONN 0      0              [::1]:323          [::]:*

123/udp が NTP の待ち受けである（試験範囲のポート番号表にある）。323/udp は chronyc が使う管理用で、NTP ではない。

クライアント側に1行足して読み直させる。

$ echo 'server 127.0.0.1 iburst' >> /etc/chrony/chrony.conf
$ systemctl restart chrony
$ sleep 8
$ chronyc sources -v

  .-- Source mode  '^' = server, '=' = peer, '#' = local clock.
 / .- Source state '*' = current best, '+' = combined, '-' = not combined,
| /             'x' = may be in error, '~' = too variable, '?' = unusable.
||                                                 .- xxxx [ yyyy ] +/- zzzz
||      Reachability register (octal) -.           |  xxxx = adjusted offset,
||      Log2(Polling interval) --.      |          |  yyyy = measured offset,
||                                \     |          |  zzzz = estimated error.
||                                 |    |           \
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
^* localhost                     8   6    17     2    +49ns[ +289ns] +/- 3392ns

-v を付けると記号の意味が先頭に出る。覚えなくてよい。読み方は毎回ここから引ける。

^   … 相手はサーバ（peer なら =、ローカル時計なら #）
*   … いま選ばれている基準
17  … Reach は8進数。直近8回の到達を1ビットずつ記録したもの
$ chronyc tracking
Reference ID    : 7F000001 (localhost)
Stratum         : 9
Ref time (UTC)  : Mon Oct 12 12:46:18 2026
System time     : 0.000002802 seconds fast of NTP time
Last offset     : +0.000000240 seconds
RMS offset      : 0.000000240 seconds
Frequency       : 0.069 ppm slow
Residual freq   : +0.001 ppm
Skew            : 1.484 ppm
Root delay      : 0.000006719 seconds
Root dispersion : 0.000004577 seconds
Update interval : 2.0 seconds
Leap status     : Normal

Reference ID が 7F000001 になった。これは 127.0.0.1 を16進で書いたもの（7F=127, 00=0, 00=0, 01=1）である。Stratum が 9 なのは、基準側が local stratum 8 だから1段深くなった結果である。

（ナノ秒の数値・時刻・Skew はあなたの環境で変わる。一致を見るのは Reference ID、Stratum、Leap status の3行だけ。）

timedatectl の側も変わる。第1章で見た行が、ここに繋がる。

$ timedatectl | tail -3
System clock synchronized: yes
              NTP service: active
          RTC in local TZ: no

2つのコマンドの役割を分ける。

コマンド答えることntpd 系での対応
chronyc sources候補が何本あって、どれが選ばれているかntpq -p
chronyc trackingいま何を基準にして、どれだけずれているかntpq -c rv
chronyc sourcestats各候補の測定のばらつき—
ntpdate -q <host>1回問い合わせるだけ（時計は動かさない）同じ
$ ntpdate -q 127.0.0.1
2026-10-12 21:46:20.424878 (+0900) +0.000001 +/- 0.000048 127.0.0.1 s8 no-leap

s8 が相手の stratum、+0.000001 がずれである。-q は問い合わせだけなので、権限が無くても通る。次の節でそれが効く。

たとえ: 時報に電話をかけて、自分の時計との差をメモする作業に近い。 sources は「どの番号に何回繋がったか」の記録で、tracking は 「いまどの番号を信じていて、何秒ずれているか」のまとめである。
ただし崩れる点: 人は時報を聞いたらその場で針を合わせるが、 chronyd は差を測ることと針を動かすことを分けている。次の節で、測るだけで止まる場合を見る。

測るのと、動かすのは別の権限

この節で分かること: ずれを測れることと、時計を直せることが別だという切り分け。

同期状態になった。では時計を動かしてみる。

$ chronyc makestep
500 Failure
$ date -s "2020-01-01 00:00:00"
date: cannot set date: Operation not permitted
Wed Jan  1 00:00:00 JST 2020

date -s の出力に注意する。エラーを出したあとに、設定しようとした時刻を表示している。表示だけ見ると成功したように見えるが、直前の行が Operation not permitted である。date を打ち直せば元の時刻が返る。

権限が無いのは、この檻に CAP_SYS_TIME というケーパビリティが無いからである。第1章で RTC のデバイスが無かったのと同じ理由で、コンテナに時計を動かす力は既定で渡されない。

だからこの檻の chronyd は、最初から「時計を触らない」指定で起動している。

$ cat /etc/default/chrony
DAEMON_OPTS="-F -1 -x"

-x が「システムクロックを制御しない」である。それでも Leap status : Normal になった。つまり chronyd の仕事は2つに分かれている。

測る   … 基準と話して、ずれと揺らぎを求める     ← 権限は要らない
直す   … 求めたずれをシステムクロックに反映する ← CAP_SYS_TIME が要る

そしてこの失敗は、ログに残っている。第4章でこの行をもう一度見る。

$ tail -3 /var/log/syslog
2026-10-12T12:46:16.625635+00:00 a7c1d43cae23 chronyd[327]: Selected source 127.0.0.1
2026-10-12T12:46:20.383363+00:00 a7c1d43cae23 chronyd[327]: Could not step system clock
2026-10-12T12:46:20.434153+00:00 a7c1d43cae23 root: はじめての logger

Could not step system clock が、いま打った makestep の結果である。コマンドの手元には 500 Failure という4文字しか返らなかったが、理由はログに書かれていた。これがこの教材を通して繰り返す形になる。

たとえ: 時刻のずれを測る計測員と、時計の針を回す鍵を持つ管理人が 別人になっている状態に近い。計測員は「3分遅れています」と正しく報告できるが、針には触れない。
ただし崩れる点: 人なら管理人を呼べるが、コンテナには呼ぶ相手がいない。 権限は起動のときに決まり、あとから足せない。足すには起動コマンドを変える。
手を動かす: 実践編の演習02で、Not synchronised から Reference ID : 7F000001 までを自分で通す。判定は chronyd 自身の報告だけを見る。

ntpd と chronyd は同時に入らない

この節で分かること: 試験範囲に2つ並ぶのに、実機には片方しか無い理由。

試験範囲 1.09.1 には ntpd・ntp.conf・ntpq と、chronyd・chrony.conf・chronyc が並んで出てくる。両方入れて見比べればよさそうだが、できない。パッケージがそう宣言している。

$ apt-cache show chrony | grep -E '^(Provides|Conflicts):'
Provides: time-daemon
Conflicts: time-daemon
$ apt-cache show ntpsec | grep -E '^(Provides|Conflicts):'
Provides: time-daemon
Conflicts: time-daemon

どちらも time-daemon を提供し、同時に time-daemon と衝突すると書いてある。自分と同じ役を名乗る相手を排除する書き方である。結果として、1台のマシンには時刻デーモンが1つしか入らない。

理由は 123/udp を2つのプロセスが取り合うからで、片方が先に bind すると他方は起動に失敗する。パッケージの段階で防いでいる。

だから覚え方はこうなる。コマンド名を別々に覚えるのではなく、対応表で覚える。

やることchrony（現行の既定）ntpd / ntpsec
設定ファイル/etc/chrony/chrony.conf/etc/ntp.conf
デーモンchronydntpd
候補の一覧chronyc sourcesntpq -p
基準の指定server / poolserver / pool
1回だけ問い合わせchronyd -qntpdate -q
公開サーバ群の名前pool.ntp.org（どちらも同じものを使う）

この檻には ntpdate だけ別パッケージ（ntpsec-ntpdate）として入っている。これは time-daemon を名乗らないので chrony と共存できる。逆に ntpq は ntpsec 本体に入っているため、この檻には無い。

確認

systemctl is-active chrony が active を返しているのに、 chronyc tracking の Leap status が Not synchronised だった。 最初に見るべきものは何か。

答え

基準の候補が何本あるか（chronyc sources / chronyc activity）。 0本なら設定に server も pool も無い。 サービスのログを探してもエラーは出ていない。「動いている」と「仕事がある」は別である。

確認

chronyc tracking の Stratum が 9 になった。 基準にしたサーバの Stratum はいくつか。

答え

8。stratum は基準から何段離れているかを数えるので、 基準にした相手より必ず1大きくなる。実測でも、基準側の設定は local stratum 8 で、こちらは 9 になった。

この章で分かったこと

持ち帰ってほしいこと

  • デーモンが active でも、基準を渡されていなければ時刻は合わない（Reference ID : 00000000 / Not synchronised）
  • 基準は設定の server か pool で渡す。1行足して読み直させるだけで Reference ID : 7F000001 / Stratum : 9 になった
  • sources は候補の一覧、tracking はいまの基準とずれ。読み分ける
  • ずれを測るのに権限は要らないが、時計を動かすには CAP_SYS_TIME が要る。makestep は 500 Failure、date -s は Operation not permitted
  • 手元に返るのは 500 Failure の4文字でも、理由（Could not step system clock）はログに書かれている
  • chrony と ntpsec はどちらも Provides: time-daemon かつ Conflicts: time-daemon。だから実機には片方しか無い
