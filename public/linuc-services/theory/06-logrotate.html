6. 捨てる判断も、受け手側にある

ログを書くプログラムは、自分のログを切らない。切るのは別のプログラムで、いつ切るかは設定ファイルが決める。そして logrotate は、設定ファイルの権限が気に入らないと、エラーを出しながら終了コード 0 で正常終了する。

前提: 第5章まで読了前提: 演習03 を終えている所要 16分影響度 B出題範囲 1.09.2（重要度5）最終検証 2026-10-12

この章のゴール

  • /etc/logrotate.conf と /etc/logrotate.d/ の関係を説明できる
  • logrotate が設定を拒否する2つの条件を、出力から特定できる
  • ログを切る判断が「いつ」「何世代」「圧縮するか」のどこに書かれているかを言える
ここで覚えなくていいこと: dateext による命名、sharedscripts と prerotate の細かい使い分け、mail ディレクティブ、copytruncate が要る場面の見極めは扱わない。journald の捨て方は第5章で済んでいる（logrotate の対象外）。

設定は2段ある

この節で分かること: 全体の既定と、対象ごとの設定の関係。
$ grep -vE '^\s*#|^\s*$' /etc/logrotate.conf
weekly
su root adm
rotate 4
create
include /etc/logrotate.d
$ ls /etc/logrotate.d/
alternatives
apt
btmp
chrony
dpkg
rsyslog
wtmp

/etc/logrotate.conf に全体の既定が5行あり、最後の include でディレクトリを取り込んでいる。ディレクトリの中は対象ごとのファイルで、そちらが優先する。

第3章で触った chrony のログも、ここに設定が置かれている。

$ cat /etc/logrotate.d/rsyslog
/var/log/syslog
/var/log/mail.log
/var/log/kern.log
/var/log/auth.log
/var/log/user.log
/var/log/cron.log
{
	rotate 4
	weekly
	missingok
	notifempty
	compress
	delaycompress
	sharedscripts
	postrotate
		/usr/lib/rsyslog/rsyslog-rotate
	endscript
}

第4章で見た /var/log/syslog と /var/log/mail.log が、ここに対象として並んでいる。rsyslog が「どこへ書くか」を決め、logrotate が「いつ捨てるか」を決める。2つは別のプログラムで、設定ファイルも別である。

主なディレクティブを押さえる。

書き方意味
daily / weekly / monthly期間で切る
size 1kサイズで切る（期間指定と排他）
rotate 33世代残す。4世代目は消える
compress切ったものを gzip する
delaycompress圧縮を1世代遅らせる（まだ書き込み中のプロセスがある場合に使う）
missingok対象が無くてもエラーにしない
notifempty空のファイルは切らない
create 0640 syslog adm切った後、この権限で新しいファイルを作る
su root admどのユーザ・グループとして作業するか
postrotate … endscript切った後に走らせるコマンド

postrotate が要る理由は、書いている側がファイルを開いたままだからである。mv しても rsyslog は古い実体に書き続ける。だから「開き直せ」と伝える必要がある（rsyslog なら HUP シグナル）。

たとえ: ノートを書く人と、古いノートを倉庫に移す人が別にいる職場に近い。 移す人は「何冊たまったら」「何冊まで残すか」の規定表を持っていて、書く人はそれを知らない。
ただし崩れる点: 人なら新しいノートに自分で書き始めるが、プログラムは移されたことに気づかない。 だから「新しいノートに切り替えて」と声をかける手順（postrotate）が要る。

エラーを出して、正常終了する

この節で分かること: logrotate が設定を拒否する2つの条件と、その見つけ方。

第4章で作った /var/log/lab-app.log を切る設定を書く。

ふつうこう考える

設定ファイルを置いて、そのファイルを指定して logrotate を打てば切れるはずだ。 うまくいかなければ終了コードかエラーで分かるだろう。

$ printf '/var/log/lab-app.log {\n    size 1k\n    rotate 3\n    compress\n}\n' > /etc/logrotate.d/lab-app
$ logrotate -v /etc/logrotate.d/lab-app
warning: Potentially dangerous mode on /etc/logrotate.d/lab-app: 0666
error: Ignoring /etc/logrotate.d/lab-app because it is writable by group or others.
Creating stub state file: /var/lib/logrotate/status
acquired lock on state file /var/lib/logrotate/statusReading state from file: /var/lib/logrotate/status
Allocating hash table for state file, size 64 entries

Handling 0 logs
$ echo $?
0
だめな理由: error: と書かれた行が出ているのに、 終了コードは 0 である。最後の行は Handling 0 logs ＝「対象0件」で、 これも正常終了として扱われる。スクリプトで $? だけ見ていると成功に見える。 原因は 0666 という権限で、このコンテナの root は umask が 0000 なので printf > で作ったファイルが誰でも書ける状態になった。 logrotate は設定に書かれたコマンドを root で実行するので、 他人が書き換えられる設定ファイルを読まない。著者はこれで3回空振りした。

権限を直す。

$ chmod 644 /etc/logrotate.d/lab-app
$ for i in $(seq 1 60); do logger -p local3.info "かさ増し $i"; done
$ ls -l /var/log/lab-app.log
-rw-r----- 1 syslog adm 4210 Oct 12 22:00 /var/log/lab-app.log

4210 バイトで、size 1k の条件は満たしている。もう一度打つ。

$ logrotate -v /etc/logrotate.d/lab-app
Handling 1 logs

rotating pattern: /var/log/lab-app.log  1024 bytes (3 rotations)
empty log files are not rotated, old logs are removed
considering log /var/log/lab-app.log
error: skipping "/var/log/lab-app.log" because parent directory has insecure permissions (It's world writable or writable by group which is not "root") Set "su" directive in config file to tell logrotate which user/group should be used for rotation.
Creating new state

まだ切れない。2段目の条件は、ログの親ディレクトリの権限である。

$ ls -ld /var/log
drwxrwxr-x 1 root syslog 4096 Oct 12 22:00 /var/log

/var/log は syslog グループが書ける。rsyslog が自分でログファイルを作れるようにそうなっている。logrotate はこれを危険と見て飛ばす。メッセージが解決策を名指ししている — Set "su" directive。この su ディレクティブは、すでにどこかに書かれている。

$ grep -n su /etc/logrotate.conf
2:su root adm

全体設定の2行目にある。つまり渡すべきファイルが違った。

$ logrotate -v /etc/logrotate.conf
...
rotating log /var/log/lab-app.log, log->rotateCount is 3
renaming /var/log/lab-app.log to /var/log/lab-app.log.1
creating new /var/log/lab-app.log mode = 0640 uid = 101 gid = 4
running postrotate script
compressing log with: /bin/gzip
$ ls -l /var/log/lab-app.log*
-rw-r----- 1 syslog adm   0 Oct 12 22:01 /var/log/lab-app.log
-rw-r----- 1 syslog adm 513 Oct 12 22:01 /var/log/lab-app.log.1.gz

切れた。.log が 0 バイトで作り直され、前の内容は .log.1.gz になっている。

Ubuntu 標準の /etc/logrotate.d/rsyslog に su が書かれていないのに動くのは、単体で実行される前提になっていないからである。logrotate.conf から include され、そこにある su root adm を受け継いで動いている。設定の階層は「どのファイルを渡して実行したか」で変わる。

自分の設定に書いても通る。どちらでもよい。

/var/log/lab-app.log {
    su root adm          ← ブロックの中に書く
    size 1k
    ...
}
たとえ: 立ち入りの許可証を持たずに現場へ来た作業員に近い。 現場（/var/log）は複数の業者が出入りできる場所なので、 誰の権限で作業するかを明示した書類（su）が無いと作業を始めない。 書類は事務所（logrotate.conf）に用意されているが、 現場へ直行すると持っていない状態になる。
ただし崩れる点: 作業員は口頭で確認できるが、logrotate は尋ねない。 メッセージを出して黙って飛ばし、終了コードは 0 を返す。
手を動かす: 実践編の演習05が、この2つの罠をどちらも踏む構成になっている。 -d（何もせずに判断だけ出す）と -v（やったことを出す）を使い分けること。

前回いつ切ったかは、ファイルに残る

この節で分かること: logrotate が状態を持っていること、そして誰が呼ぶのか。
$ cat /var/lib/logrotate/status
logrotate state -- version 2
"/var/log/lab-app.log" 2026-10-12-22:0:0

対象ごとに「前回切った時刻」を持っている。だから weekly の設定で1日に何度打っても1回しか切らない。条件を無視させたいときだけ -f を使う。

$ logrotate -f /etc/logrotate.conf

世代の上限が効いていることも確かめられる。4回切ると最古が消える。

$ for r in 1 2 3 4; do
>   for i in $(seq 1 60); do logger -p local3.info "回 $r 行 $i"; done
>   logrotate -f /etc/logrotate.conf
> done
$ ls -l /var/log/lab-app.log*
-rw-r----- 1 syslog adm   0 Oct 12 22:01 /var/log/lab-app.log
-rw-r----- 1 syslog adm 473 Oct 12 22:01 /var/log/lab-app.log.1.gz
-rw-r----- 1 syslog adm 472 Oct 12 22:01 /var/log/lab-app.log.2.gz
-rw-r----- 1 syslog adm 476 Oct 12 22:01 /var/log/lab-app.log.3.gz

rotate 3 なので .4.gz は作られず、捨てられている。

では誰が logrotate を呼ぶのか。常駐していない。

$ systemctl list-timers logrotate.timer --no-pager
NEXT                            LEFT LAST PASSED UNIT            ACTIVATES
Tue 2026-10-13 00:00:00 JST 2h 13min -         - logrotate.timer logrotate.service

1 timers listed.
$ systemctl cat logrotate.timer | head -12
# /usr/lib/systemd/system/logrotate.timer
[Unit]
Description=Daily rotation of log files
Documentation=man:logrotate(8) man:logrotate.conf(5)

[Timer]
OnCalendar=daily
AccuracySec=1h
Persistent=true

[Install]
WantedBy=timers.target

systemd のタイマーが1日1回呼ぶ。Persistent=true は「止まっていた間に来るべきだった分を、起動後に実行する」指定である。ノート PC のように電源を切る機械でも切り忘れが起きない。

試験範囲では、同じ仕事を cron 側で持つ形も出る（/etc/cron.daily/logrotate）。どちらも「logrotate 自身は時刻を知らない」という点では同じで、呼ぶ人が systemd か cron かの違いである。

たとえ: 月末だけ来る清掃業者に近い。 来る日を決めているのはカレンダー（タイマー）で、業者は作業の規定表しか持っていない。 前回いつ来たかは受付の台帳（status）に書いてある。
ただし崩れる点: 業者は来れば必ず何かするが、 logrotate は条件を満たさなければ何もせずに帰る。来たことすら分かりにくい。 だから台帳とタイマーの両方を見る。
確認

logrotate -v /etc/logrotate.d/myapp を打ったら Handling 0 logs と出て終了コードは 0 だった。何を疑うか。

答え

設定ファイルが読まれていない。まず権限を見る （ls -l。group か other に書き込みがあると丸ごと無視される）。 次に、対象ファイルの親ディレクトリの権限と su ディレクティブを見る。 終了コードは両方の場合で 0 になるので、$? では判別できない。 -d を付けて判断の過程を読む。

確認

rotate 3 と compress を設定して4回切った。 残っているファイルを列挙せよ。

答え

lab-app.log（新しい空ファイル）、.1.gz、.2.gz、.3.gz の4つ。 .4.gz は作られずに捨てられる。 delaycompress を付けていれば .1 が非圧縮のまま残り、 .2.gz 以降が圧縮される。

この章で分かったこと

持ち帰ってほしいこと

  • 書く側（rsyslog）と捨てる側（logrotate）は別のプログラムで、設定ファイルも別
  • logrotate は設定ファイルが group/other に書けると丸ごと無視する。しかも終了コードは 0
  • ログの親ディレクトリが group 書き込み可だと、su ディレクティブが無い限り飛ばす
  • /etc/logrotate.d/<名前> を直接渡すと /etc/logrotate.conf の既定（su root adm など）が効かない。渡すのは logrotate.conf
  • 前回切った時刻は /var/lib/logrotate/status にある。無視させるのは -f
  • logrotate は常駐しない。logrotate.timer（OnCalendar=daily / Persistent=true）が呼ぶ
