4. ログの宛先は、受け手の表が決める

logger -p local3.info と打つと、行は /var/log/syslog に入る。local3 という名前のファイルはどこにも無い。送り手は宛先を1文字も指定していない。決めたのは受け手の設定表である。

前提: 第3章まで読了前提: 檻が起動している所要 22分影響度 B出題範囲 1.09.2（重要度5）最終検証 2026-10-13

この章のゴール

  • facility.priority のセレクタを読み書きできる
  • 同じ1行が複数のファイルに同時に入る理由を、設定の構造から説明できる
  • logger が何を渡し、何を渡していないかを列挙できる
  • ログを別のマシン（ログサーバー）へ送る行と、受け取る側で有効にする行を書ける
ここで覚えなくていいこと: rsyslog の RainerScript の書き方（action() 形式。受信を有効にする module と input の行は、コメントを外すところだけ扱う）、TLS による暗号化、テンプレートによる書式変更、キューの設計はここでは扱わない。imklog や imfile などの入力モジュールも、名前を見たとき「入力の口」と分かれば足りる。覚えるのはセレクタの文法と既定の宛先だけでよい。

投げた先と、入った先が違う

この節で分かること: ログの宛先を決めているのが送り手ではないこと。
$ logger "はじめての logger"
$ tail -3 /var/log/syslog
2026-10-13T02:42:04.442509+00:00 linuc chronyd[413]: Selected source 127.0.0.1
2026-10-13T02:42:08.216251+00:00 linuc chronyd[413]: Could not step system clock
2026-10-13T02:42:16.335989+00:00 linuc root: はじめての logger

自分が投げた行が、第3章で見た chronyd の行の隣に並んだ。デーモンのログと、手で打った1行が同じファイルに入っている。

では宛先を指定して投げてみる。-p で facility.priority を渡せる。

ふつうこう考える

local3 という宛先を指定して投げたのだから、local3 向けの場所に入るはずだ。 少なくとも、指定しなかったとき（/var/log/syslog）とは別の場所に行くだろう。

$ logger -p local3.info "local3 に投げる"
$ grep local3 /var/log/syslog
2026-10-13T02:42:17.346742+00:00 linuc root: local3 に投げる
だめな理由: 同じ /var/log/syslog に入っている。 しかも行の中に local3 という文字は残っていない（grep が当たったのは本文のほうである）。 local3 は宛先ではなくラベルで、そのラベルをどう扱うかは受け手が決める。 この環境の受け手は「どんなラベルでも /var/log/syslog に入れる」という設定になっていた。 次の節でその1行を見る。

受け手の設定を読む。rsyslog は本体の最後で、ディレクトリの中身を取り込んでいる。

$ grep IncludeConfig /etc/rsyslog.conf
$IncludeConfig /etc/rsyslog.d/*.conf
$ ls /etc/rsyslog.d/
50-default.conf
postfix.conf
$ grep -vE '^\s*#|^\s*$' /etc/rsyslog.d/50-default.conf
auth,authpriv.*			/var/log/auth.log
*.*;auth,authpriv.none		-/var/log/syslog
kern.*				-/var/log/kern.log
mail.*				-/var/log/mail.log
mail.err			/var/log/mail.err
*.emerg				:omusrmsg:*

2行目が答えである。*.* は「どの facility の、どの priority も」という意味で、;auth,authpriv.none が「ただし auth と authpriv は除く」を付け足している。local3.info はこれに当てはまるので /var/log/syslog に入った。

行頭の記号も読む。

-/var/log/syslog     先頭の - は「書くたびに同期（fsync）しない」の印（速いが、落ちると最後の数行が消えうる）
 /var/log/auth.log   - が無いのは、従来の syslog では「書くたびに同期する」の意味（認証ログは落としたくない）
:omusrmsg:*          ファイルではなく「ログイン中の全ユーザの端末」へ送る出力モジュール

ただし、いまの rsyslog は既定で書くたびの同期をしない（man 5 rsyslog.conf の言葉では By default, files are not synced after each write）。 同期させるには $ActionFileEnableSync on を書く必要があり、この檻の設定には無い。だから auth.log も実際には書くたびには同期されていない。 試験で - の意味を問われたら「書くたびに同期しない（書き込みを速くする）」と答えればよい。

たとえ: 郵便物に「至急」と赤いスタンプを押して出す動作に近い。 スタンプは宛先ではない。配達の優先度をどう扱うかは、受け取った郵便局の処理表が決める。
ただし崩れる点: 郵便物には宛先住所も書いてあるが、 logger が渡す情報には宛先が1つも無い。ラベルと本文だけである。

セレクタは facility と priority の2語でできている

この節で分かること: 設定の1行がどう組み立てられていて、どこまで絞れるか。

設定の1行は、左がセレクタ、右がアクション（当てはまった行をどうするか。ここでは書き込む先のファイル＝宛先）である。

local3.*          /var/log/lab-app.log
^^^^^^^^          ^^^^^^^^^^^^^^^^^^^^
セレクタ           アクション（宛先）

local3  .  *
facility   priority

facility（ファシリティ）は「どの種類の機能から出たか」を表す決まった名前の集合で、priority（優先度。プライオリティとも呼ぶ）は「どれだけ重いか」の段である。出題範囲の詳細にも「標準的なファシリティ、優先度、およびアクションを理解する」とあり、試験ではこの日本語で出る。ファシリティと優先度は、どちらも logger の man に一覧がある。

priority（重い順）別名意味の目安
emergpanicシステムが使えない
alert—すぐ対応が要る
crit—致命的
errerrorエラー
warningwarn警告
notice—通常だが注意に値する
info—情報
debug—開発用

facility は auth、authpriv、cron、daemon、ftp、kern、lpr、mail、news、syslog、user、uucp、そして local0 から local7 である。local0〜local7 は用途が決まっていないので、自分のアプリに割り当てて使う。だから演習で使うのもここである。

priority の書き方は3通りあり、意味が違う。実際に投げて確かめる。

$ echo 'local4.warning  /var/log/lab-warn.log' > /etc/rsyslog.d/61-lab.conf
$ systemctl restart rsyslog
$ logger -p local4.debug   "debug なので入らない"
$ logger -p local4.info    "info なので入らない"
$ logger -p local4.warning "warning だから入る"
$ logger -p local4.err     "err だから入る"
$ cat /var/log/lab-warn.log
2026-10-13T11:42:19.416733+09:00 linuc root: warning だから入る
2026-10-13T11:42:19.418365+09:00 linuc root: err だから入る

local4.warning と書くと warning 以上が入る。4つ投げて2つしか入っていない。= を付けるとその段だけになる。

（行頭の時刻が、ここから +09:00 になっている。それまでの行は +00:00 だった。rsyslog は起動したときのタイムゾーンを使い続けるので、第2章で /etc/localtime を Asia/Tokyo に変えたあと、ここで再起動して初めて日本時間で書くようになった。）

$ echo 'local5.=notice  /var/log/lab-notice.log' > /etc/rsyslog.d/62-lab.conf
$ systemctl restart rsyslog
$ logger -p local5.notice "notice"
$ logger -p local5.err    "err"
$ cat /var/log/lab-notice.log
2026-10-13T11:42:21.472220+09:00 linuc root: notice

err は notice より重いのに入らない。これが = の効果である。

書き方入るもの
local4.warningwarning と、それより重いもの全部
local4.=warningwarning だけ
local4.*全部
local4.noneこの facility を除外する（*.*;local4.none のように使う）
local3,local4.errfacility を複数並べる（カンマ区切り）
local3.err;local4.*セレクタを複数並べる（セミコロン区切り）
たとえ: 「課長以上を集めてください」という指示に近い。 課長だけでなく部長も社長も来る。「課長だけ」と言いたいときは別の書き方が要る。
ただし崩れる点: 役職は上下1列だが、facility には上下が無い。 mail と local3 はどちらが上でもない。 2つの語のうち片方（priority）だけに順序があることが、この文法の読みにくさの原因である。

同じ1行が、2つのファイルに入る

この節で分かること: 受け手が宛先を1つに決めるわけではないこと。

受け皿を1つ足す。既定の設定は消さない。

$ echo 'local3.*  /var/log/lab-app.log' > /etc/rsyslog.d/60-lab.conf
$ systemctl restart rsyslog
$ logger -p local3.info "受け皿ができた後"
$ cat /var/log/lab-app.log
2026-10-13T11:42:23.529517+09:00 linuc root: 受け皿ができた後
$ grep "受け皿ができた後" /var/log/syslog
2026-10-13T11:42:23.529517+09:00 linuc root: 受け皿ができた後

同じ行が両方にある。rsyslog はセレクタに当てはまった行を、当てはまったすべての宛先に書く。最初に見つかったところで止まらない。

*.*;auth,authpriv.none   -/var/log/syslog        ← 既定。ほぼ全部を拾う
local3.*                  /var/log/lab-app.log   ← 足したもの
                          どちらも local3.info に当てはまる → 2回書かれる

ここが「移す」と「増やす」の違いである。/var/log/lab-app.log だけに入れたいなら、既定の行のほうに local3.none を足して除外する必要がある。送り手側では何も変えられない。

そして第3章で見た行をもう一度見る。

chronyd[413]: Could not step system clock

この行も chronyd が facility と priority を付けて投げただけで、/var/log/syslog に入ったのは *.* の行があったからである。第3章で「結果も理由もログに書かれていた」と言ったのは、この設定表がそう決めていたからに過ぎない。設定を変えれば、その行は別のファイルに行くか、/var/log/syslog からは消える（journald の側には残る。第5章）。

たとえ: 回覧板を「関係する部署すべて」に同時に回す運用に近い。 1枚の紙が複数の部署の棚に写しとして置かれる。どこか1つに届いたら終わりではない。
ただし崩れる点: 回覧板は1枚を回すので同時に2箇所には置けないが、 rsyslog は同じ内容をいくつでも複製する。コストはディスクだけである。
手を動かす: 実践編の演習03は、この「1行が2箇所に入る状態」を作る課題である。 判定は実際に1行投げて、両方のファイルを grep して確かめる。

宛先は別のマシンでもよい — ログサーバーへ送る

この節で分かること: 1行を別のマシン（ログサーバー）へ送る書き方と、受け取る側で開ける口。

アクション（右側）には、ファイルの代わりに別のマシンを書ける。何台ものマシンのログを1台に集めておくのがログサーバー（中央のログサーバー）で、出題範囲 1.09.2 の概要にも「ログ出力を中央のログサーバーに送信する」「中央のログサーバーとして受け入れる」とある。送る側の書き方はこうなる。

*.*   @logserver.example.com          ← UDP で送る（宛先のポートは既定で 514）
*.*   @@logserver.example.com         ← TCP で送る（同じく 514）
*.*   @@logserver.example.com:10514   ← ポートを変えるときは :番号

@ が1つなら UDP、2つなら TCP である（man 5 rsyslog.conf）。UDP は届いたかどうかを確かめないので、途中で落ちても送り手は気づかない。左側はこれまでと同じセレクタなので、authpriv.* @@logserver.example.com のように一部だけを送ることもできる。

受け取る側は、ネットワークから受け取る入力の口を開ける。Ubuntu の /etc/rsyslog.conf には、その行がコメントにして用意してある。

$ grep -n -E 'imudp|imtcp' /etc/rsyslog.conf
17:#module(load="imudp")
18:#input(type="imudp" port="514")
21:#module(load="imtcp")
22:#input(type="imtcp" port="514")

この4行の先頭の # を外して、読み直させる（vi で外してよい。記録では sed で同じことをした）。

$ sed -i -e '17s/^#//' -e '18s/^#//' -e '21s/^#//' -e '22s/^#//' /etc/rsyslog.conf
$ grep -n -E 'imudp|imtcp' /etc/rsyslog.conf
17:module(load="imudp")
18:input(type="imudp" port="514")
21:module(load="imtcp")
22:input(type="imtcp" port="514")
$ systemctl restart rsyslog
$ ss -lnu | grep ':514'
UNCONN 0      0            0.0.0.0:514       0.0.0.0:*
UNCONN 0      0               [::]:514          [::]:*
$ ss -lnt | grep ':514'
LISTEN 0      25           0.0.0.0:514       0.0.0.0:*
LISTEN 0      25              [::]:514          [::]:*

UDP と TCP の 514 番で待ち受け始めた。module(load="imudp") が「UDP で受け取る入力モジュールを読み込む」、input(type="imudp" port="514") が「514 番で受け取る」で、TCP は imtcp が受け持つ。

この檻には送ってくる別のマシンが無いので、logger に外から送る役をさせる。-n で送り先、-P でポート、-d で UDP、-T で TCP を選ぶ（-T の既定のポートは 601 なので、-P 514 を付ける）。

$ logger -n 127.0.0.1 -P 514 -d "UDP で届いた"
$ logger -n 127.0.0.1 -P 514 -T "TCP で届いた"
$ grep "で届いた" /var/log/syslog
2026-10-13T11:42:25.611155+09:00 linuc root UDP で届いた
2026-10-13T11:42:25.612490+09:00 linuc root TCP で届いた
$ journalctl | grep -c "で届いた"
0

どちらも /var/log/syslog に入った。ネットワークから来た行も、同じセレクタの表（*.*）で振り分けられる。そして journalctl には1行も入っていない（0）。ネットワークから来た行は rsyslog が直接受け取るので、journald を通らない。第5章で、この入口の違いをもう一度見る。

（送る側の @ / @@ の行は、この檻では書き方だけにとどめる。送り先になる別のログサーバーが無いからである。）

たとえ: 各支店の日誌の写しを、本社の文書係へ毎日送る運用に近い。支店は「どの種類の日誌を送るか」だけを決め、本社は受付の窓口を開けておく。
ただし崩れる点: 郵便は届かなければ戻ってくるが、UDP で送ったログは途中で落ちても誰にも知らされない。取りこぼしを減らしたいときに TCP（@@）を選ぶのはそのためである。

logger が渡しているものを数える

この節で分かること: 送り手が持っている情報の少なさ。

logger が渡せるものは少ない。

$ logger -p local3.err -t myapp "タグも付けられる"
$ tail -1 /var/log/lab-app.log
2026-10-13T11:42:26.621744+09:00 linuc myapp: タグも付けられる
渡すもの指定行のどこに出るか
facility-p local3.出ない（宛先の判断にだけ使われる）
priority-p .err出ない（同じ）
タグ-t myappmyapp:
本文引数末尾
時刻・ホスト名指定しない受け手が付ける

facility と priority は行の中に残らない。分類に使われて消える。タグを省略するとユーザ名（root:）が入る。行の先頭の時刻とホスト名は rsyslog が付けたものである（時刻はマイクロ秒まである。logger も秒までの時刻を添えて送っているが、この行には使われていない。第5章で確かめる）。

だから「このログの priority は何だったか」を後から /var/log/syslog から知ることはできない。知りたければ、priority ごとに別のファイルへ分けておくしかない。ログ設計が設定ファイルの仕事になっているのはこのためである。

第5章で見る journald は、ここが違う。同じ1行を構造ごと保存している。

確認

logger -p local3.info "test" と打った行を /var/log/syslog で見つけた。 この行の facility を出力から特定できるか。

答え

できない。facility と priority は宛先を選ぶために使われたあと、行には書かれない。 実測の行は root: local3 に投げる で、local3 という語は本文に書いた文字列が 残っているだけだった。知りたければ facility ごとに別ファイルへ分ける設定を先に作る。

確認

/etc/rsyslog.d/60-lab.conf に local3.* /var/log/lab-app.log を書いた。 local3 のログを /var/log/syslog には入れたくない。どこを直すか。

答え

/etc/rsyslog.d/50-default.conf の *.*;auth,authpriv.none -/var/log/syslog に local3.none を足して *.*;auth,authpriv.none;local3.none にする。 自分が足したファイルを直しても /var/log/syslog への経路は消えない。 別の行が独立して拾っているからである。

確認

rsyslog で、すべてのログを TCP で 192.168.0.10 のログサーバーへ送る設定行を書け。また、受け取る側では何を有効にするか。

答え

送る側は *.* @@192.168.0.10（TCP。宛先のポートは既定で 514）。@ が1つなら UDP になる。 受け取る側は /etc/rsyslog.conf の module(load="imtcp") と input(type="imtcp" port="514") を有効にして（UDP なら imudp）、rsyslog を再起動する。

この章で分かったこと

持ち帰ってほしいこと

  • logger が渡すのは facility・priority・タグ・本文（と秒までの時刻）だけ。宛先は1文字も渡していない
  • 宛先を決めるのは /etc/rsyslog.conf と /etc/rsyslog.d/*.conf のセレクタ表
  • Debian 系の既定は *.*;auth,authpriv.none -/var/log/syslog という catch-all。だから何を投げても /var/log/syslog に入る
  • local4.warning は warning 以上、local4.=warning は warning だけ、local4.none は除外
  • 当てはまった宛先すべてに書かれる。だから設定を足すと「移る」のではなく「増える」
  • facility と priority は行に残らない。後から知りたければ、分けて保存する設定を先に作る
  • アクションには別のマシン（ログサーバー）も書ける。@ は UDP、@@ は TCP で、宛先のポートは既定で 514。受け取る側は imudp / imtcp の module と input を有効にする。ネットワークから来た行は journald を通らない
