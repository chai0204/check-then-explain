1. 時計は2つある

この檻で hwclock を打つと、時刻は1行も返らない。ところが /proc/driver/rtc には時刻が入っていて、しかも date が返す時刻と33秒ずれている。片方だけ見ていると気づかないが、1台のマシンの中で別々に進む時計が2つある。

前提: コマンドを打てる前提: 檻が起動している所要 17分影響度 B出題範囲 1.09.1（重要度2）最終検証 2026-10-13

この章のゴール

  • date と timedatectl と hwclock が、それぞれ何を読んでいるかを区別して言える
  • ハードウェアクロック（RTC）とシステムクロックの役割を分けて説明できる
  • コンテナで hwclock が失敗する理由を、コマンドの有無ではなくデバイスの有無から説明できる
  • date で時刻を設定する書式（年は最後）と、touch -t の書式（年が先頭）を取り違えずに書ける
  • timedatectl のサブコマンドを、無いもの（set-clock）と区別して挙げられる
ここで覚えなくていいこと: NTP による時刻合わせは第3章で扱う。うるう秒、tzdata の更新手順、hwclock --systohc で RTC に書き戻す操作はここでは扱わない（書き戻しには RTC デバイスが要るので、この檻では試せない。出る出力は後で示す）。clock_gettime の精度やクロックソースの選択も、合格に要らないので外す。

時計を2つ見つける

この節で分かること: 同じマシンの中に、別々に進む時計が2つあること。

まず2つ並べて打つ。どちらも時刻を出すコマンドだが、出てくる内容が違う。

$ date
Tue Oct 13 21:05:43 JST 2026
$ date -u
Tue Oct 13 12:05:44 UTC 2026
$ timedatectl
               Local time: Tue 2026-10-13 12:05:44 UTC
           Universal time: Tue 2026-10-13 12:05:44 UTC
                 RTC time: n/a
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: yes
              NTP service: active
          RTC in local TZ: no

timedatectl は4行で4つの別のことを言っている。Local time と Universal time は同じ瞬間の別表記で、ここは第2章の話。いまここで見たいのは3行目の RTC time で、値が n/a になっている。つまり timedatectl は「RTC という別の時計があるはずだが、読めない」と言っている。

ふつうこう考える

RTC が読めないと言うなら、RTC を読む専用のコマンドで読めばいい。 試験範囲にもハードウェアクロックを読むコマンドとして hwclock が並んでいる。打ってみる。

$ hwclock
hwclock: Cannot access the Hardware Clock via any known method.
hwclock: Use the --verbose option to see the details of our search for an access method.
$ hwclock --show
hwclock: Cannot access the Hardware Clock via any known method.
hwclock: Use the --verbose option to see the details of our search for an access method.
だめな理由: コマンドは存在している（command -v hwclock は /usr/sbin/hwclock を返す）。失敗しているのは探索のほうで、メッセージは any known method ＝「知っているどの経路でも触れない」と言っている。 つまり足りないのはコマンドではなく読む先である。 そして「読む先が無い」ことは「RTC が存在しない」ことと同じではない。次でそれを確かめる。

RTC が本当に存在しないのかを、別の経路から見る。カーネルは /proc の下に、自分が把握しているデバイスの状態をテキストで出している。

$ cat /proc/driver/rtc
rtc_time	: 12:05:13
rtc_date	: 2026-10-13
alrm_time	: 13:32:01
alrm_date	: 2026-10-11
alarm_IRQ	: no
alrm_pending	: no
update IRQ enabled	: no
periodic IRQ enabled	: no
periodic IRQ frequency	: 1
max user IRQ frequency	: 64
24hr		: yes

RTC は在る。時刻も入っている。2つの時計を比べるには、同じ瞬間に読む必要がある。上の date -u と cat は打った時刻がずれている（手で打てば数秒から数十秒）ので、その間の分が差に混ざる。1行で続けて読み直す。

$ date -u +%T; grep rtc_time /proc/driver/rtc
12:05:47
rtc_time	: 12:05:14

ここで2つの数字を並べる。

date -u +%T        → 12:05:47   ← システムクロック
rtc_time           → 12:05:14   ← RTC
                     差 33秒

同じマシンの、同じ瞬間に読んだ2つの時計が33秒ずれている。どちらかが壊れているのではない。2つは別々に進んでいて、合わせる仕組みが別にある。その仕組みが第3章の NTP である。

（秒数と日付はあなたの環境で変わる。見るのは「2つの値が一致しない」ことだけ。一致していたら、直前に合わせた直後だったということになる。）

たとえ: 壁掛け時計と腕時計を両方持っている状態に近い。 腕時計（システムクロック）は普段見る側で、動かすのも簡単。壁掛け時計（RTC）は電池で勝手に動き続け、 部屋の電気を落としても止まらない。朝起きたら2つがずれているので、どちらかに合わせ直す。
ただし崩れる点: 壁掛け時計はいつでも見られるが、RTC は普段見ない。 OS が起動した瞬間に1回読んで、そのあとはシステムクロックだけを見て動く。 「常に2つを見比べている」わけではない。

hwclock が失敗したのは、デバイスが無いから

この節で分かること: コマンドが無いのではなく、読む経路が無いという失敗の形。

hwclock が探していた「読む先」を見る。

$ ls -l /dev/rtc*
ls: cannot access '/dev/rtc*': No such file or directory

hwclock は /dev/rtc0 のようなデバイスファイルを開いて、そこに ioctl で問い合わせる。このコンテナにはそのデバイスファイルが無い。一方 /proc/driver/rtc はカーネルが文字列で出している読み取り専用の情報なので、デバイスファイルを開かずに読める。同じ RTC を、別の経路で見ていたというだけの話である。

なぜコンテナにデバイスが無いのか。コンテナはホストのカーネルをそのまま使う普通のプロセスで、見えるデバイスはコンテナランタイムが渡したものに限られる。時計を進めたり書き換えたりできるデバイスは既定で渡さない。だからこの失敗はコンテナの設計どおりの結果であって、読者の操作ミスではない。

実機や仮想マシンなら次が通る。この檻では試せないので、出る形だけ書いておく。

# 実機・VM での例（この檻では実行できない）
hwclock --show            # RTC を読む
hwclock --systohc         # システムクロック → RTC に書き戻す
hwclock --hctosys         # RTC → システムクロックに読み込む

試験では hwclock が「ハードウェアクロックを扱うコマンド」として問われる。方向が2つある（--systohc と --hctosys）ことと、RTC は UTC で持つのが既定であること（timedatectl の RTC in local TZ: no）が要点になる。

短い形もある。どれがどれかは --help に並んでいる（表示するだけなのでデバイスは要らない）。

$ hwclock --help | grep -E -- '--(show|hctosys|systohc|adjust) '
 -r, --show                      display the RTC time
 -s, --hctosys                   set the system time from the RTC
 -w, --systohc                   set the RTC from the system time
 -a, --adjust                    adjust the RTC to account for systematic drift

-r が --show（RTC を読む）、-w が --systohc（システムクロック → RTC）、-s が --hctosys（RTC → システムクロック）である。 覚え方の一例: -w は RTC に書く（write）、-s はシステムの時刻を合わせる（system）。 -a（--adjust）は、RTC が一定の割合で進む・遅れる癖（systematic drift）の分を、前回合わせてから経った時間に応じて足し引きする（man 8 hwclock）。

たとえ: 建物の中に金庫があることは館内図（/proc/driver/rtc）で分かるが、 金庫室の扉（/dev/rtc0）の鍵を渡されていない状態に近い。 中身の一部は館内図に書き写されているので読めるが、開け閉めはできない。
ただし崩れる点: 館内図は人が書いたコピーなので古くなるが、 /proc/driver/rtc は読むたびにカーネルが実物から取ってくる。写し間違いは起きない。
手を動かす: 実践編の演習01で、この2つの時計の表示を実際に揃える。 その前に檻の中で lab env を打つと、いま何が動いているかが1画面で出る。

「正しい時刻」を決めているのは時計ではない

この節で分かること: 同期しているかどうかを誰が判断して、どこに書いてあるか。

timedatectl は人間向けの整形だが、機械向けの出力もある。

$ timedatectl show
Timezone=Etc/UTC
LocalRTC=no
CanNTP=yes
NTP=yes
NTPSynchronized=yes
TimeUSec=Tue 2026-10-13 21:05:49 JST

NTPSynchronized=yes と出ている。RTC は読めないままである。つまり「同期している」という判断は RTC とは無関係に下されている。判断の材料は、カーネルが持っている時計の状態である（timedatectl は systemd を通してカーネルに問い合わせている）。そしてコンテナはホストのカーネルをそのまま使うので、ここに出ているのはホスト側の時刻合わせの結果である。第3章で見るとおり、檻の中の時刻合わせのデーモンは、この時点ではまだ何とも同期していない。

整理すると、時刻に関わる登場人物はこうなる。

名前何か電源を切ると読むコマンド
RTC（ハードウェアクロック）基板上の電池で動く時計動き続けるhwclock / /proc/driver/rtc
システムクロックカーネルが持つ時刻。起動時に RTC から受け取る消えるdate / timedatectl
NTP デーモン外の基準と比べてずれを測り、システムクロックを合わせる（この檻の chronyd は測るだけ。第3章）止まるchronyc / ntpq

この章の時点で押さえるのは、システムクロックは起動のときに RTC から値を受け取るが、そのあとは別々に進むという点である。システムクロックの値を RTC へ書き戻す仕組み（hwclock --systohc や、chrony.conf の rtcsync のような同期の機能）が働かなければ、2つのずれは開いていく。さきほどの33秒がどういう経緯で生じたかまでは、この檻の中からは確かめられない（RTC はホストのものである）。

たとえ: 出社したときに壁の時計を見て自分の腕時計を合わせ、 そのあとは腕時計だけを見て1日働く、という動き方に近い。合わせるのは朝の1回だけで、 日中に腕時計が遅れても壁の時計は教えてくれない。
ただし崩れる点: 人は気になれば壁を見られるが、システムクロックは RTC を定期的に見ない。 ずれを見つける役は RTC ではなく、外の基準と話す NTP デーモンが担っている。

時刻を設定する書式 — date は年が最後、touch -t は年が先

この節で分かること: date に日時を渡す書式と、よく似た touch -t の書式の違い。timedatectl のサブコマンドの全体。

date は表示するだけでなく、システムクロックを設定することもできる。引数に数字の並びを1つ渡すと設定になる。書式は --help にある。

$ date --help | grep MMDDhhmm
  or:  date [-u|--utc|--universal] [MMDDhhmm[[CC]YY][.ss]]
With -s, or with [MMDDhhmm[[CC]YY][.ss]], set the date and time.

月・日・時・分（MMDDhhmm）が先に来て、年（CC が西暦の上2桁、YY が下2桁。どちらも省ける）はその後ろ、秒は最後に .ss で付ける。2022年2月14日 9時0分なら 021409002022 である。打ってみる。

$ date 021409002022
date: cannot set date: Operation not permitted
Mon Feb 14 09:00:00 JST 2022
$ echo $?
1

設定は失敗した（終了コード 1）。この檻には時計を動かす権限（CAP_SYS_TIME）が無いからで、第3章でもう一度見る。それでも date は、解釈した日時を表示してから終わる。 Mon Feb 14 09:00:00 JST 2022 と読まれたので、末尾の4桁が年だったと分かる。実機で root が打てば、この時刻に設定される（date -s "2022-02-14 09:00" のように、文字列で渡す書き方もある）。

ファイルの時刻を変える touch -t も数字の並びを取るが、年の位置が逆である。

$ touch --help | grep STAMP
  -t STAMP               use [[CC]YY]MMDDhhmm[.ss] instead of current time
$ touch -t 202202140900 /tmp/stamp
$ date -r /tmp/stamp
Mon Feb 14 09:00:00 JST 2022

touch -t の書式は [[CC]YY]MMDDhhmm[.ss] で、年が先頭に来る。date -r ファイル はファイルの更新時刻を表示するので、date に渡したのと同じ瞬間になったと分かる。

コマンド書式2022年2月14日 9:00 を渡す
date（設定）MMDDhhmm[[CC]YY][.ss] — 年は最後date 021409002022
date -s日時の文字列date -s "2022-02-14 09:00"
touch -t[[CC]YY]MMDDhhmm[.ss] — 年は先頭touch -t 202202140900 ファイル
timedatectl set-time"YYYY-MM-DD hh:mm:ss"timedatectl set-time "2022-02-14 09:00:00"

timedatectl にも時刻を設定するサブコマンドがある。サブコマンドは全部で7つで、--help に並んでいる。

$ timedatectl --help | sed -n '/^Commands:/,/^$/p'
Commands:
  status                   Show current time settings
  show                     Show properties of systemd-timedated
  set-time TIME            Set system time
  set-timezone ZONE        Set system time zone
  list-timezones           Show known time zones
  set-local-rtc BOOL       Control whether RTC is in local time
  set-ntp BOOL             Enable or disable network time synchronization
サブコマンドすること
statusいまの状態を人間向けに出す。サブコマンドを省いたときはこれになる（この章の最初の表示）
show同じ内容を キー=値 の形で出す（機械向け）
set-timeシステムクロックを設定する。NTP による時刻合わせが有効な間は拒否される
set-timezoneタイムゾーンを設定する（/etc/localtime を張り替える。第2章）
list-timezones指定できるゾーン名の一覧（第2章）
set-local-rtcRTC を地方時で持つかどうか（既定は no ＝ UTC。RTC in local TZ の行）
set-ntpNTP による時刻合わせを有効・無効にする（NTP service の行）

似た名前で間違えやすいものを打ってみる。

$ timedatectl set-clock 2022-02-14
Unknown command verb 'set-clock', did you mean 'set-time'?
$ timedatectl set-time "2022-02-14 09:00:00"
Failed to set time: Automatic time synchronization is enabled

set-clock というサブコマンドは無い（did you mean 'set-time'? と返る）。時刻を設定するのは set-time である。こちらは日時の書き方は通ったが、NTP による時刻合わせが有効なので断られた（Automatic time synchronization is enabled）。手で合わせたいときは、先に set-ntp false で自動の時刻合わせを止める。

たとえ: 同じ日付を、月を先に書く国と年を先に書く国の書き方で書き分けるのに近い。date は「月日時分年」、touch -t は「年月日時分」で書く。
ただし崩れる点: 人は 2022 を見れば年だと分かるので、並びが違っても読み取れる。コマンドは位置だけで読む。date に年を先頭にした 202202140900 を渡すと、先頭の 20 を月として読もうとして invalid date で止まる（別の檻で実測）。
確認

hwclock が Cannot access the Hardware Clock を返した。 このマシンに RTC が無いと結論できるか。

答え

できない。結論できるのは「hwclock が使う経路（/dev/rtc* などの デバイスファイル）では触れない」ことだけである。実際このコンテナでは /proc/driver/rtc に RTC の時刻が入っていた。 「コマンドが失敗した」から「対象が存在しない」を導かないこと。

確認

timedatectl が System clock synchronized: yes と出している。 このとき RTC も正しい時刻になっていると言えるか。

答え

言えない。この行はシステムクロックが基準と合っているかを示すだけで、RTC には触れていない。 実際この檻では RTC time: n/a のまま synchronized: yes になっていた。 RTC にシステムクロックを書き戻すのは別の操作（hwclock --systohc、 あるいは chrony.conf の rtcsync）である。

確認

root が date 101309302026 と打った（時刻を設定できる環境とする）。何年何月何日の何時何分に設定されるか。また、同じ日時をファイルに付ける touch -t の引数はどう書くか。

答え

2026年10月13日 9時30分。date の書式は MMDDhhmm[[CC]YY] で、10 が月、13 が日、0930 が時と分、末尾の 2026 が年である。 touch -t は年が先頭の [[CC]YY]MMDDhhmm なので、touch -t 202610130930 ファイル になる。

この章で分かったこと

持ち帰ってほしいこと

  • 1台のマシンに時計は2つある。RTC は電池で動き続け、システムクロックはカーネルが持ち、電源で消える
  • システムクロックは起動時に RTC から値を受け取り、そのあとは別々に進む。書き戻す仕組みが働かなければずれる（この檻では33秒ずれていた）
  • hwclock の失敗は「コマンドが無い」ではなく「/dev/rtc* が無い」。同じ RTC は /proc/driver/rtc から読めた
  • コンテナにデバイスを渡さないのは設計どおり。だからこの章の失敗は読者の操作ミスではない
  • hwclock の短い形は -r（--show）・-w（--systohc、システム → RTC）・-s（--hctosys、RTC → システム）。-a（--adjust）は進み・遅れの癖を補正する
  • 時刻の設定は date MMDDhhmm[[CC]YY][.ss]（年は最後。例 date 021409002022）か date -s "文字列"。touch -t は [[CC]YY]MMDDhhmm[.ss] で年が先頭。この檻では CAP_SYS_TIME が無いので設定は失敗するが、date は解釈した日時を表示する
  • timedatectl のサブコマンドは status（省略時）・show・set-time・set-timezone・list-timezones・set-local-rtc・set-ntp の7つ。set-clock は無い。set-time は NTP が有効な間は拒否される
  • System clock synchronized はシステムクロックの話であって、RTC が合っているとは言っていない。しかもこの檻では、その判断もホストのカーネルの状態から来ている
