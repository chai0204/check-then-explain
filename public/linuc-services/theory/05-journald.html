5. journald は隣にある別の箱

logger で1行投げると、/var/log/lab-app.log と journalctl の両方に出る。どちらも1件ずつで、合計2件保存されている。保存は別々で、別々の規則で捨てる。ただし入口は1本で、logger の1行はまず journald が受け取り、journald がそれを rsyslog に回している。

前提: 第4章まで読了前提: 檻が起動している所要 20分影響度 B出題範囲 1.09.2（重要度5）最終検証 2026-10-13

この章のゴール

  • journald と rsyslog が同じ1行を二重に持つことを、数えて確かめられる
  • logger の1行が journald を通ってから rsyslog に届くことを、転送を止めて確かめられる
  • Storage= の既定（auto）がディレクトリの有無で決まることを説明できる
  • journalctl の絞り込みを、ユニット・優先度・時刻・タグで書ける
ここで覚えなくていいこと: journal のバイナリ形式、--merge やリモートの journal（journal-remote）、systemd-journal-gatewayd は扱わない。Seal=（改ざん検知）も外す。ForwardToSyslog= は、rsyslog への入口になっていることを確かめるところだけ扱う。覚えるのは保存先が2つあることと、絞り込みの書き方だけでよい。

同じ1行が、2つの箱に入っている

この節で分かること: rsyslog と journald が、同じ1行を別々に保存していること。

第4章の受け皿がある状態で、1行投げて両方で数える。

$ logger -p local3.info "二重に入るか"
$ grep -c "二重に入るか" /var/log/lab-app.log
1
$ journalctl | grep -c "二重に入るか"
1

どちらも1件である。同じ1行が2つの箱に保存されている。保存先は別々なので、片方を消してももう片方は残る。ただし2つの箱は、入口でつながっている（次の節で確かめる）。

ふつうこう考える

journalctl はログを見るための便利なコマンドなのだから、 /var/log/syslog を読んで整形して出しているのだろう。 だとすれば /var/log/syslog を消せば journalctl からも消えるはずだ。

$ journalctl --disk-usage
Archived and active journals take up 8.0M in the file system.
$ journalctl --no-pager -t myapp -o verbose
Tue 2026-10-13 11:42:26.621586 JST [s=7862faf881244922895fff133ab494fc;i=b6;b=e5d039e944a940f79a88cd842c8332fd;m=1f2700944f;t=65dafc3d7c4d9;x=70a9b30e12212940]
    _UID=0
    _GID=0
    _BOOT_ID=e5d039e944a940f79a88cd842c8332fd
    _MACHINE_ID=f5295b64ae1a49b9a1af1c892764514b
    _HOSTNAME=linuc
    _RUNTIME_SCOPE=system
    _TRANSPORT=syslog
    PRIORITY=3
    SYSLOG_FACILITY=19
    SYSLOG_IDENTIFIER=myapp
    SYSLOG_TIMESTAMP=Oct 13 11:42:26
    MESSAGE=タグも付けられる
    _PID=664
    _SOURCE_REALTIME_TIMESTAMP=1791859346621586
だめな理由: journalctl --disk-usage が自分の占有量を 8.0M と答えている。 テキストファイルを読んでいるだけなら、自分の占有量という概念が無い。 第4章で logger が投げた1行を -o verbose で出すと、_PID・_UID・_HOSTNAME・_BOOT_ID といった項目が並び、PRIORITY=3（err）と SYSLOG_FACILITY=19（local3）まで残っている。 第4章で見たとおり、/var/log/syslog の1行には facility も priority も残っていなかった。 logger が添えた秒までの時刻も、SYSLOG_TIMESTAMP として別に持っている。 journald は独自のバイナリ形式で、項目ごとに分けて保存している。 /var/log/syslog を消しても journal は減らない。

2つの箱の違いを整理する。

rsyslogjournald
入口journald から回してもらう（ForwardToSyslog）。ネットワーク（imudp・imtcp）からは直接/dev/log（logger）・systemd-cat
保存の形テキスト1行バイナリ・項目ごと
置き場所/var/log/*.log/var/log/journal/ か /run/log/journal/
設定/etc/rsyslog.conf・/etc/rsyslog.d//etc/systemd/journald.conf・journald.conf.d/
捨て方logrotate（別のプログラム）自分で上限管理（SystemMaxUse=）
読み方cat / grep / tailjournalctl だけ
ユニット単位の絞り込みできないできる（-u）

捨て方の列が重要である。journald は logrotate の対象ではない。第6章で logrotate を扱うが、journal はそこに出てこない。自分で上限を持っている。

たとえ: 同じ会議の記録を、議事録係が文章で書き、 もう1人が項目を埋める用紙で記録している状態に近い。内容は同じでも、 後から「発言者だけ抜き出す」ができるのは用紙のほうである。
ただし崩れる点: 人が2人書けば労力は2倍だが、 ログの二重化で増えるのはディスクだけで、投げる側の手間は変わらない。 送り手は1回投げただけである。

保存は別々、入口は1本

この節で分かること: logger の1行が、journald を通ってから rsyslog に届いていること。

logger が書き込む /dev/log が、どこにつながっているかを見る。

$ ls -l /dev/log
lrwxrwxrwx 1 root root 28 Oct 13 11:41 /dev/log -> /run/systemd/journal/dev-log
$ cat /usr/lib/systemd/journald.conf.d/syslog.conf
# Undo upstream commit 46b131574fdd7d77 for now. For details see
#  http://lists.freedesktop.org/archives/systemd-devel/2014-November/025550.html

[Journal]
ForwardToSyslog=yes

/dev/log は journald のソケット（/run/systemd/journal/dev-log）へのリンクである。logger の1行を最初に受け取るのは journald で、rsyslog に届くのは、journald が ForwardToSyslog=yes で回した分である。この設定は Ubuntu（Debian）が /usr/lib/systemd/journald.conf.d/syslog.conf に置いている。

確かめるには、回すのを止めればよい。/usr/lib の下の設定ファイルは、/etc の同じ場所に同じ名前のファイルを置くと差し替えられる。

$ mkdir -p /etc/systemd/journald.conf.d
$ printf '[Journal]\nForwardToSyslog=no\n' > /etc/systemd/journald.conf.d/syslog.conf
$ systemctl restart systemd-journald
$ logger -p local3.info "転送を止めた後"
$ grep -c "転送を止めた後" /var/log/syslog
0
$ journalctl | grep -c "転送を止めた後"
1

/var/log/syslog に 0 件、journal に 1 件。rsyslog の設定には何も触っていないのに、rsyslog に届かなくなった。置いたファイルを消して、もとに戻す。

$ rm /etc/systemd/journald.conf.d/syslog.conf
$ systemctl restart systemd-journald
$ logger -p local3.info "戻した後"
$ grep -c "戻した後" /var/log/syslog
1

戻すとまた届く。2つの箱は横に並んでいるのではなく、入口で直列につながっている。

logger → /dev/log（journald が受け取る）→ /var/log/journal に保存
                          └→ ForwardToSyslog=yes → rsyslog → /var/log/syslog などに保存

保存先と捨て方は別々だが、入口は1本である。だから journald の設定を変えると、rsyslog に届くものが変わる。逆に、第4章でネットワークから受け取った行は rsyslog に直接入り、journald には入らなかった。

（差し替えるファイルを 99-noforward.conf のような名前にすると効かない。設定は名前の順に読まれ、後に読まれる syslog.conf の ForwardToSyslog=yes が勝つからである。別の檻で実測した。）

たとえ: 会社に届いた郵便を受付がまず全部受け取って自分の台帳に記録し、写しを文書係へ回している状態に近い。文書係（rsyslog）は、受付から回ってきたものしか見ていない。受付が回すのをやめれば、文書係の棚には何も増えない。
ただし崩れる点: 文書係には裏口（ネットワークの 514 番）もあり、そこから来たものは受付を通らないので、受付の台帳（journal）には載らない。

保存先は2つあり、ディレクトリの有無で決まる

この節で分かること: 設定値を書いていないのに保存先が決まっている仕組み。

設定ファイルはほぼ空である。

$ grep -vE '^\s*#|^\s*$' /etc/systemd/journald.conf
[Journal]

セクション名だけで、キーが1つも無い。それでも保存先は決まっている。

$ ls -d /var/log/journal/*
/var/log/journal/f5295b64ae1a49b9a1af1c892764514b
$ ls -d /run/log/journal/* 2>&1
ls: cannot access '/run/log/journal/*': No such file or directory
$ journalctl --disk-usage
Archived and active journals take up 8.0M in the file system.

Storage= の既定値は auto で、その意味はこうである。

Storage=保存先再起動すると
persistent/var/log/journal/（無ければ作る）残る
volatile/run/log/journal/消える
auto（既定）/var/log/journal/ が在ればそこ、無ければ /run/log/journal/場合による
none保存しない（転送のみ）—

ディレクトリが在るかどうかが設定値の役割をしている。この檻は起動した時点で /var/log/journal/ の下に machine-id の名前のディレクトリが在り（上の ls）、もう永続化されている。 /var/log/journal が無い環境で永続化するときの手順はこうなる。

# /var/log/journal が無い環境での手順（この檻では済んでいる）
mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal
systemctl restart systemd-journald        # マシンの再起動でもよい

（別の新しい檻で /var/log/journal を消してから試すと、mkdir のあと journalctl --flush だけでは /run/log/journal に書き続け、 journald を再起動して初めて /var/log/journal/<machine-id> に移った。journalctl -t systemd-journald の行も Runtime Journal から System Journal に変わった。）

ディレクトリの名前は machine-id である。

$ cat /etc/machine-id
f5295b64ae1a49b9a1af1c892764514b

（machine-id は本来1台ごとに違う値である。この檻ではイメージを作ったときの値が焼き込まれているので、誰が起動しても f5295b64ae1a49b9a1af1c892764514b になる。見るのは、ディレクトリの名前が machine-id と同じであることである。）

たとえ: 郵便受けを設置したかどうかで、配達員が 投函するか持ち帰るかを決める運用に近い。「投函してください」と書面で頼むのではなく、 受け箱を置くことが依頼になっている。
ただし崩れる点: 郵便受けは置くだけで機能するが、 /var/log/journal は作ったあとに journald に読み直させないと使われない。 設置と開始が別の操作である。

journald は自分の上限をログに書く

この節で分かること: 設定が効いたかどうかを推測せずに確かめる方法。

上限は SystemMaxUse= で決める。本体を書き換えずに、差分だけ置ける。

$ mkdir -p /etc/systemd/journald.conf.d
$ printf '[Journal]\nSystemMaxUse=8M\n' > /etc/systemd/journald.conf.d/10-lab.conf
$ systemctl restart systemd-journald
$ journalctl -t systemd-journald --no-pager | tail -1
Oct 13 11:42:32 linuc systemd-journald[728]: System Journal (/var/log/journal/f5295b64ae1a49b9a1af1c892764514b) is 8.0M, max 8.0M, 0B free.

journald は起動のたびに、自分がどの上限で動くかをログに書く。だから設定が効いたかどうかを推測しなくてよい。第3章の chronyc tracking と同じで、当人に聞けば答える。

名前は System と Runtime の2系統あり、保存先に対応している。

SystemMaxUse=    /var/log/journal  の上限
RuntimeMaxUse=   /run/log/journal  の上限
SystemKeepFree=  ディスクに残す空き
MaxRetentionSec= この期間より古いものを捨てる

すぐ減らしたいときは、上限とは別に明示的に捨てられる。

$ journalctl --vacuum-size=1M
Vacuuming done, freed 0B of archived journals from /var/log/journal.
Vacuuming done, freed 0B of archived journals from /run/log/journal.
Vacuuming done, freed 0B of archived journals from /var/log/journal/f5295b64ae1a49b9a1af1c892764514b.
$ journalctl --vacuum-time=2d
Vacuuming done, freed 0B of archived journals from /var/log/journal.
Vacuuming done, freed 0B of archived journals from /var/log/journal/f5295b64ae1a49b9a1af1c892764514b.
Vacuuming done, freed 0B of archived journals from /run/log/journal.

freed 0B なのは、捨てられるのがアーカイブ済みのファイルだけで、いま書いている分（system.journal）は対象外だからである。この檻にはまだアーカイブ済みのファイルが1つも無いので、何も減らない。これは失敗ではない。

手を動かす: 実践編の演習04は、上限を 8M にして journald 自身に max 8.0M と言わせる課題である。 設定を書くだけでは通らない。読み直させるところまでやって初めて判定が通る。

journalctl の絞り込み

この節で分かること: テキストの grep では書けない絞り方。

journald は項目ごとに保存しているので、項目で絞れる。

$ journalctl --no-pager -u rsyslog -n 3
Oct 13 11:42:24 linuc rsyslogd[636]: rsyslogd's groupid changed to 102
Oct 13 11:42:24 linuc rsyslogd[636]: rsyslogd's userid changed to 101
Oct 13 11:42:24 linuc rsyslogd[636]: [origin software="rsyslogd" swVersion="8.2312.0" x-pid="636" x-info="https://www.rsyslog.com"] start
$ journalctl --no-pager -p err -n 3
Oct 13 11:42:24 linuc rsyslogd[636]: imklog: cannot open kernel log (/proc/kmsg): Operation not permitted.
Oct 13 11:42:24 linuc rsyslogd[636]: activation of module imklog failed [v8.2312.0 try https://www.rsyslog.com/e/2145 ]
Oct 13 11:42:26 linuc myapp[664]: タグも付けられる

-p err が効いている。第4章で local3.err として投げたmyapp の行が入り、info で投げた行は入っていない。rsyslog では行に残らなかった priority が、journald では絞り込みに使える。

書き方意味
journalctl -u rsyslogそのユニットのログだけ
journalctl -t myappそのタグ（SYSLOG_IDENTIFIER）だけ
journalctl -p errerr 以上（rsyslog のセレクタと同じ考え方）
journalctl --since "5 min ago"相対時刻で絞る
journalctl --since "2026-10-13 10:00"絶対時刻で絞る
journalctl -b今回の起動分だけ
journalctl -f追尾する（tail -f 相当）
journalctl -kカーネルのメッセージだけ（dmesg 相当）
journalctl -o verbose項目を1行に1つずつ、すべて出す
journalctl -o json項目をすべて JSON の1行で出す

起動ごとの区切りも持っている。

$ journalctl --list-boots
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
  0 e5d039e944a940f79a88cd842c8332fd Tue 2026-10-13 11:41:58 JST Tue 2026-10-13 11:42:32 JST
$ cat /proc/sys/kernel/random/boot_id
e5d039e9-44a9-40f7-9a88-cd842c8332fd

1件しか出ない。BOOT ID はカーネルが起動のたびに作る値で（/proc/sys/kernel/random/boot_id と同じもの）、コンテナはホストのカーネルをそのまま使っている。だからこの檻の BOOT ID はホストの起動 ID で、コンテナを作り直しても再起動しても、ホストを再起動しない限り増えない。実機では起動のたびに新しい ID が付いて過去の起動が並び、journalctl -b -1 で前回分を読める。これは永続化していないとできない。保存先の話がここに繋がる。

自分でも journal に書ける。

$ systemd-cat -t lab-cat echo "systemd-cat から1行"
$ journalctl --no-pager -t lab-cat
Oct 13 11:42:33 linuc lab-cat[746]: systemd-cat から1行

logger は /dev/log（journald のソケット）へ syslog の形で、systemd-cat はコマンドの標準出力を journald へつないで渡す。どちらも受け取るのは journald である。違いはラベルで、facility と priority のうち systemd-cat が付けられるのは priority（-p）だけである。

$ journalctl --no-pager -t lab-cat -o verbose
Tue 2026-10-13 11:42:33.839485 JST [s=7862faf881244922895fff133ab494fc;i=c3;b=e5d039e944a940f79a88cd842c8332fd;m=1f276eb6f3;t=65dafc445e77d;x=1df38eae81e1ecbd]
    PRIORITY=6
    _UID=0
    _GID=0
    _BOOT_ID=e5d039e944a940f79a88cd842c8332fd
    _MACHINE_ID=f5295b64ae1a49b9a1af1c892764514b
    _HOSTNAME=linuc
    _RUNTIME_SCOPE=system
    _TRANSPORT=stdout
    _STREAM_ID=93a8b21478fc4b57841463e8ffa82c56
    SYSLOG_IDENTIFIER=lab-cat
    MESSAGE=systemd-cat から1行
    _PID=746

PRIORITY=6（info）はあるが、SYSLOG_FACILITY の項目が無い（logger の1行には SYSLOG_FACILITY=19 があった）。_TRANSPORT=stdout が「標準出力から来た」という印である。どちらも宛先は1文字も渡していない。

たとえ: 自由記述の日誌と、項目が決まった記録簿の違いに近い。 日誌からは「先週の月曜の天気」を探すのに読み返すしかないが、記録簿は天気の欄だけ見れば済む。
ただし崩れる点: 記録簿は欄が決まっているので欄外のことは書けないが、 journald は本文も丸ごと持っている。項目が増えただけで、情報は減っていない。
確認

/var/log/syslog を削除した。journalctl で過去のログは見られるか。

答え

見られる。2つは保存先が別の箱で、journald は /var/log/journal/ か /run/log/journal/ に自分の形式で持っている。 逆に journalctl --vacuum-size で journal を削っても /var/log/syslog は減らない。

確認

/etc/systemd/journald.conf に Storage= を1行も書いていない。 journal はどこに保存されているか。

答え

既定は auto なので、/var/log/journal/ というディレクトリが 存在すればそこ、存在しなければ /run/log/journal/。 確かめるには ls -d /var/log/journal/* /run/log/journal/* で machine-id のディレクトリがどちらに在るかを見るか、 journalctl -t systemd-journald に出る行が System Journal（/var）か Runtime Journal（/run）かを見る。 journalctl --disk-usage は合計しか出さないので、どちらかは分からない。設定ファイルを読んでも分からない、という点が要点である。

この章で分かったこと

持ち帰ってほしいこと

  • 同じ1行が rsyslog と journald の両方に入る（どちらも1件）。保存は別々だが入口は1本で、logger → journald →（ForwardToSyslog）→ rsyslog の順に通る。転送を止めると /var/log/syslog には0件になった
  • journald はテキストではなくバイナリで、項目ごとに保存する（-o verbose で _PID・_BOOT_ID・PRIORITY などが見える）
  • Storage=auto（既定）は /var/log/journal の有無で保存先が決まる。設定ファイルを読んでも分からない
  • journald は起動のたびに自分の上限をログに書く。max 8.0M を見れば設定が効いたか確かめられる
  • journal は logrotate の対象ではない。自分で SystemMaxUse= を持ち、--vacuum-size で捨てる
  • rsyslog では行に残らない priority が、journald では -p で絞り込みに使える
