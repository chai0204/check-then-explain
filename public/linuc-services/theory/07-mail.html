7. 宛先に書いた名前は、希望にすぎない

alice 宛に送ったメールが root のメールボックスに入る。途中で2回書き換えられている。そして途中の経路（bob を経由したこと）は、届いたメールを見ても分からない。設定とログを読んで追う。この章で、主題1.09 の3つ（時刻・ログ・メール）が1本に繋がる。

前提: 第6章まで読了前提: 檻が起動している所要 25分影響度 B出題範囲 1.09.3（重要度2）最終検証 2026-10-13

この章のゴール

  • /etc/aliases と ~/.forward の役割と優先順を説明できる
  • newaliases が必要な理由を、ファイルの形から説明できる
  • 配送の経路を orig_to と to の2つでログから追える
  • mail のオプション（-s・-c・-b・-r）と、MTA が1台に1つしか入らない理由を言える
ここで覚えなくていいこと: SMTP のやりとり、main.cf の各パラメータ、外部へのリレー・認証・TLS・DKIM は扱わない（レベル1の範囲外）。exim の設定方法も外す。試験で問われるのは「MTA が2つあって、どちらも sendmail 互換のコマンドを持つ」ことまでである（章の後半の対応表で扱う）。

宛先が書き換わる

この節で分かること: 送り手が書いた名前と、実際に配送された先が違いうること。

まず素直に1通送る。

$ echo "本文です" | mail -s "最初の1通" alice
$ ls -l /var/mail/
total 4
-rw------- 1 alice mail 505 Oct 13 21:08 alice
$ cat /var/mail/alice
From root@lab.local  Tue Oct 13 21:08:39 2026
Return-Path: <root@lab.local>
X-Original-To: alice
Delivered-To: alice@lab.local
Received: by lab.local (Postfix, from userid 0)
	id BE8D01185579; Tue, 13 Oct 2026 12:08:39 +0000 (UTC)
To: alice@lab.local
Subject: 最初の1通
MIME-Version: 1.0
Content-Type: text/plain; charset="UTF-8"
Content-Transfer-Encoding: 8bit
Message-Id: <20261013120839.BE8D01185579@lab.local>
Date: Tue, 13 Oct 2026 12:08:39 +0000 (UTC)
From: root <root@lab.local>

本文です

ここで第2章が効く。Date: と Received: は +0000 (UTC) で書かれているが、ls -l の時刻は 21:08（JST）である。同じ瞬間を、2つのゾーンで表示している。メールのヘッダはオフセット付きで書くので、受け取った側がどのゾーンで読んでも同じ瞬間を指せる。

mail の書き方を押さえておく。宛先は最後に並べ、本文は標準入力から渡す（上では echo の出力をパイプで渡した）。オプションは宛先より前に置く。

書き方意味
-s 件名件名（Subject:）。空白を含むなら引用符で囲む
-c 宛先Cc。ヘッダの Cc: に載る
-b 宛先Bcc。届くが、どのヘッダにも載らない
-r 送信元From: と差出人（エンベロープ）を変える。届かなかったときの差し戻しも、ここへ戻る
宛先最後に並べる（複数可）
本文標準入力から（echo 本文 | mail …、mail … < ファイル）

（別の新しい檻で mail -s "オプションの確認" -c alice -b bob -r noreply@lab.local lab と送ると、3人とも1通ずつ受け取り、どの1通のヘッダにも Bcc: は無く、From: と Return-Path: は noreply@lab.local になった。-r lab@lab.local を付けて届かない宛先へ送ると、差し戻しは lab のメールボックスに入った。）

Red Hat 系の mail（mailx）は、-S 変数=値 で設定を渡せる。試験に出る -S smtp=サーバー は「sendmail を呼ばずに、このサーバーへ SMTP で直接送る」という指定である（AlmaLinux 8.10 の mailx 12.5 の man）。 AlmaLinux 9.8 の mailx（s-nail）でも同じ書き方で送ろうとするが、smtp は古い書き方だという警告が出て、-S mta=smtp://サーバー を使うよう勧められる。 Ubuntu の mail（bsd-mailx）には、この -S が無い（mail: invalid option -- 'S'）。どれも lab の podman と別の檻で実測した。

次に宛先を曲げる。表は postconf が答える。

$ postconf -n | grep alias
alias_database = hash:/etc/aliases
alias_maps = hash:/etc/aliases
$ cat /etc/aliases
postmaster: root

ふつうこう考える

/etc/aliases はテキストファイルなのだから、1行書き足せば効くはずだ。

$ echo 'alice: bob' >> /etc/aliases
$ cat /etc/aliases
postmaster: root
alice: bob
$ echo "曲がったか" | mail -s "aliases 経由" alice
$ ls -l /var/mail/
total 4
-rw------- 1 alice mail 1014 Oct 13 21:08 alice
だめな理由: alice に届いたままで、bob のメールボックスは作られていない。 postconf -n の出力をもう一度読むと hash:/etc/aliases と書いてある。 hash: は「このテキストから作ったハッシュ形式のデータベースを読む」という指定で、 postfix が実際に開くのは隣にある /etc/aliases.db である。 テキストを書き換えても .db は古いままなので、効かない。
$ ls -l /etc/aliases /etc/aliases.db
-rw-r--r-- 1 root root    28 Oct 13 21:08 /etc/aliases
-rw-r--r-- 1 root root 12288 Oct 12 21:58 /etc/aliases.db
$ newaliases
$ ls -l /etc/aliases.db
-rw-r--r-- 1 root root 12288 Oct 13 21:08 /etc/aliases.db
$ echo "曲がったか" | mail -s "aliases 経由" alice
$ ls -l /var/mail/
total 8
-rw------- 1 alice mail 1014 Oct 13 21:08 alice
-rw------- 1 bob   mail  509 Oct 13 21:08 bob

bob のメールボックスができた。newaliases がテキストから .db を作り直したので効いた。

この「テキストを直して、作り直す」形は試験で繰り返し出る。newaliases は sendmail 互換のコマンドで、sendmail -bi と同じものである（/usr/bin/newaliases は sendmail へのリンク）。postfix の newaliases は、中で postalias を走らせて .db を作り直す（man 1 sendmail）。

/etc/aliases の右側には、カンマで区切って複数の宛先を書ける（man 5 aliases の書式は name: value1, value2, ...）。 support: alice, bob と書いて newaliases を打てば、support 宛の1通が alice と bob に1通ずつ届く（別の新しい檻で実測）。

たとえ: 転居届を出す動作に近い。 郵便物の表書きは変えないまま、郵便局側の台帳で配達先を差し替える。
ただし崩れる点: 転居届は本人が出すが、/etc/aliases は システム管理者が書く。本人の意思とは無関係に宛先を曲げられる。 本人が自分で曲げる手段は次の節の ~/.forward である。

本人も曲げられる。ただし権限を見られる

この節で分かること: 2段目の書き換えと、それが黙って無効になる条件。

bob 宛をさらに root へ曲げる。1段目のエイリアスは管理者が書く表だったが、2段目は本人のホームに置く .forward というファイルで、本人が書く。

$ printf 'root\n' > /home/bob/.forward
$ chown bob:bob /home/bob/.forward
$ ls -l /home/bob/.forward
-rw-rw-rw- 1 bob bob 5 Oct 13 21:09 /home/bob/.forward
$ echo "2回曲がる" | mail -s "forward 経由" alice
$ grep -c "2回曲がる" /var/mail/root
grep: /var/mail/root: No such file or directory
$ grep -c "2回曲がる" /var/mail/bob
1

曲がっていない。bob のメールボックスに入って終わっている。エラーは1つも出ていない。理由はログにだけ書かれている。

$ journalctl -t postfix/local --no-pager | tail -3
Oct 13 21:08:56 linuc postfix/local[1020]: 15DC111855B1: to=<bob@lab.local>, orig_to=<alice>, relay=local, delay=0.02, delays=0.02/0/0/0, dsn=2.0.0, status=sent (delivered to mailbox)
Oct 13 21:09:03 linuc postfix/local[1020]: warning: file /home/bob/.forward is world writable
Oct 13 21:09:03 linuc postfix/local[1020]: 1DF801185007: to=<bob@lab.local>, orig_to=<alice>, relay=local, delay=0.02, delays=0.01/0/0/0, dsn=2.0.0, status=sent (delivered to mailbox)

world writable である。.forward を書ける人は他人のメールを自分に転送できるので、postfix は誰でも書けるファイルを読まない。第6章の logrotate と同じ形の拒否である。ただし条件は少し違う。logrotate は group か other が書けると拒否したが、postfix が拒否するのは other（world）が書けるときだけで、group だけが書ける 664 の .forward は読まれて転送された（別の檻で実測）。

同じ警告は /var/log/mail.log にも入っている。postfix が facility mail で投げ、journald から回された rsyslog が振り分けた先である（第4章・第5章）。

$ grep "world writable" /var/log/mail.log
2026-10-13T21:09:03.125978+09:00 linuc postfix/local[1020]: warning: file /home/bob/.forward is world writable

どちらにしても、警告はログに出るだけで、送り手には何も返らない。

（podman で入った場合は、シェルの umask が 0022 なので .forward は 0644 で作られ、この拒否は起きずに1回目から root まで曲がる。podman 5.8.6 rootless で実測。）

$ chmod 644 /home/bob/.forward
$ echo "2回曲がる" | mail -s "forward 経由" alice
$ grep -c "2回曲がる" /var/mail/root
1
$ journalctl -t postfix/local --no-pager -n 2
Oct 13 21:09:10 linuc postfix/local[1020]: B99261185008: to=<alice@lab.local>, orig_to=<alice>, relay=local, delay=0.02, delays=0.02/0/0/0, dsn=2.0.0, status=sent (forwarded as BAB251185002)
Oct 13 21:09:10 linuc postfix/local[1020]: BAB251185002: to=<root@lab.local>, orig_to=<alice>, relay=local, delay=0.01, delays=0/0/0/0, dsn=2.0.0, status=sent (delivered to mailbox)

2行に分かれている。1行目では to はまだ alice のままで、結果は forwarded as BAB251185002（別の1通として送り直した）である。2行目で、その新しい1通（BAB251185002）の to が root になり、delivered to mailbox で終わっている。orig_to はどちらも alice で、送り手が書いた名前は最後まで残る。to を順に追えば、どこへ曲がったかが分かる。

途中の bob はこの2行には出てこない。/etc/aliases で bob へ、~bob/.forward で root へ、という2回の書き換えは、どちらも配送を受け持つ postfix/local の中で済んでいる（1段目だけだったときは、さきほどのログのように to=<bob@lab.local>, orig_to=<alice> と出ていた）。

届いたメールのヘッダにも、跡は一部残る。

$ grep -E '^(X-Original-To|Delivered-To):' /var/mail/root
X-Original-To: alice
Delivered-To: root@lab.local
Delivered-To: alice@lab.local

X-Original-To が送り手の書いた名前、Delivered-To は配送の段ごとに付く宛先で、root と alice が並んでいる。しかし途中で bob を経由したことは、ヘッダにも、最後の2行のログにも出てこない。どこで曲がったかを確かめるには、/etc/aliases と ~bob/.forward を読み、ログを順に追う。

~/.forward には、転送先を1行に1つずつ書く（各行は /etc/aliases の右側と同じ書き方なので、カンマで並べても通る）。転送しながら自分の手元にも残したいときは、自分の名前に \ を付けた行を足す。

\bob
root

\ は「この名前をそれ以上展開しない（.forward をもう一度読みに行かない）」という印である。別の新しい檻でこの2行を ~bob/.forward に置くと、bob 宛の1通が bob のメールボックスと root の両方に1通ずつ入った。 なお postfix は、\ が無くても、自分自身の名前を見つけたらメールボックスに入れる（man 8postfix local: When a user is listed in the user's own ~/.forward file, delivery is made to the user's mailbox instead.）。試験では \自分の名前 の形で問われる。

2つの曲げ方を並べる。

/etc/aliases~/.forward
書く人管理者本人
適用範囲システム全体そのユーザ宛だけ
書き換えた後newaliases が必要不要（テキストをそのまま読む）
権限の制約root 所有other（world）書き込み不可（group だけなら読まれる）
適用の順先（alias を展開してから）後（展開先のユーザについて見る）
宛先を複数書く右側にカンマで並べる（support: alice, bob）1行に1つ。手元にも残すなら \自分の名前 の行を足す

newaliases が .forward に要らないのは、.forward が hash: ではなくテキストとして直接読まれるからである。「作り直しが要るかどうか」は、設定の形式で決まる。

たとえ: 会社の受付が持つ配布先リスト（/etc/aliases）と、 各自が自席に貼る「不在時はこの人へ」のメモ（~/.forward）の違いに近い。 受付のリストが先に引かれ、届いた席でメモが見られる。
ただし崩れる点: 自席のメモは誰が書いても読まれるが、 .forward は権限が緩いと読まれない。しかも読まなかったことを本人に伝えない。
手を動かす: 実践編の演習06で、この2段の書き換えを自分で作る。 判定は実際に1通送って、どのメールボックスに入ったかだけを見る。

届かないメールは、キューではなく root に戻る

この節で分かること: 「キューが空だから問題なし」が成り立たない理由。

存在しない宛先に送る。

$ echo x | mail -s "届かない宛先" nosuchuser@invalid.example
$ mailq
Mail queue is empty
$ postqueue -p
Mail queue is empty

キューは空である。しかし送れていない。どこへ行ったか。

$ journalctl -t postfix/smtp -t postfix/bounce -t postfix/local --no-pager -n 3
Oct 13 21:09:17 linuc postfix/smtp[1045]: 2E9FC118500D: to=<nosuchuser@invalid.example>, relay=none, delay=0.03, delays=0.02/0/0.01/0, dsn=5.4.4, status=bounced (Host or domain name not found. Name service error for name=invalid.example type=A: Host not found)
Oct 13 21:09:17 linuc postfix/bounce[1046]: 2E9FC118500D: sender non-delivery notification: 343631185090
Oct 13 21:09:17 linuc postfix/local[1020]: 343631185090: to=<root@lab.local>, relay=local, delay=0.01, delays=0/0/0/0, dsn=2.0.0, status=sent (delivered to mailbox)
$ ls -l /var/mail/root
-rw------- 1 root mail 3088 Oct 13 21:09 /var/mail/root

3行で1つの話になっている。1行目で、配送を試みた smtp が宛先のドメインを引けず、status=bounced で諦めた（dsn の先頭の 5 は恒久的な失敗を表し、再試行しない）。2行目で postfix/bounce が差し戻しを作った。sender non-delivery notification、つまり送り手への不達通知で、新しい1通（343631185090）になっている。3行目で、その1通が root のメールボックスに入った。送り手が root だったからである。元の1通はこの時点でキューから消えている。

サーバの上でメールを出すのは、多くが root として動くプログラムである。だから届かなかった通知も root に戻る。管理者宛ての予約された名前 postmaster も、/etc/aliases の1行目で root に向いている。

$ head -1 /etc/aliases
postmaster: root

つまり「mailq が空なら問題なし」ではない。処理の結果は root のメールボックスに溜まる。実機でサーバを預かったとき、最初に見るのは /var/mail/root である。

コマンド見るもの
mailq / postqueue -pまだ送れていないメール（これから再試行する分）
postqueue -fキューの再試行を今すぐ走らせる
/var/mail/root差し戻しと、システムからの通知
/var/log/mail.log / journalctl -t postfix/local1通ごとの配送結果

/var/log/mail.log が在るのは、第4章で見た設定の4行目があるからである。

mail.*				-/var/log/mail.log
mail.err			/var/log/mail.err

postfix は facility mail で投げているだけで、/var/log/mail.log という名前を知らない。決めたのは /etc/rsyslog.d/50-default.conf である。第4章の話が、そのままここに戻ってくる。

たとえ: 宛先不明の郵便が「あて所に尋ねあたりません」の付箋付きで 差出人に戻ってくる運用に近い。窓口（キュー）には何も残らないので、 窓口だけ見ていると全部送れたように見える。
ただし崩れる点: 郵便の差出人は人ごとに違うが、サーバの上でメールを出すプログラムの多くは root として動いている。だから戻ってきた封筒は1つの箱（/var/mail/root）に集まる。 管理者宛ての postmaster も、/etc/aliases で同じ箱に向けてある。

MTA は1台に1つ — postfix と exim

この節で分かること: 出題範囲に並ぶ MTA の名前と、1台に1つしか入らない理由。

この檻の MTA（メールを配送するプログラム）は postfix である。試験範囲にはもう1つ exim が並んでいる。第3章の chrony と ntpsec と同じく、パッケージの宣言を見る（exim は入っていないので、第3章で apt-get update を通した檻でだけ読める）。

$ dpkg -s postfix | grep -E '^(Provides|Conflicts):'
Provides: default-mta, mail-transport-agent
Conflicts: mail-transport-agent, smail
$ apt-cache show --no-all-versions exim4-daemon-light | grep -E '^(Provides|Conflicts):'
Provides: exim4-localscanapi-6.0, mail-transport-agent
Conflicts: mail-transport-agent
$ ls -l /usr/sbin/sendmail /usr/bin/mailq /usr/bin/newaliases
lrwxrwxrwx 1 root root    16 May  6 00:47 /usr/bin/mailq -> ../sbin/sendmail
lrwxrwxrwx 1 root root    16 May  6 00:47 /usr/bin/newaliases -> ../sbin/sendmail
-rwxr-xr-x 1 root root 31184 May  6 00:47 /usr/sbin/sendmail

どちらも mail-transport-agent を提供し、同時にそれと衝突する。だから1台に MTA は1つしか入らない（sendmail のパッケージ sendmail-bin も同じ宣言をしている。別の檻で実測）。

そして postfix は sendmail という名前のコマンドを持ち、mailq と newaliases はそこへのリンクになっている。exim も同じ名前のコマンドを用意している（Ubuntu の exim4 では /usr/sbin/sendmail・/usr/bin/mailq・/usr/bin/newaliases が exim4 へのリンク。別の檻でパッケージの中身を見て確かめた）。 どの MTA が入っていても、sendmail・mailq・newaliases という名前のコマンドは打てるように作られている（名前が同じでも、中で動くのはそれぞれの MTA である）。

postfixeximsendmail
Ubuntu のパッケージpostfixexim4（本体は exim4-daemon-light など）sendmail-bin
sendmail・mailq・newaliases の名前のコマンドある（この檻）ある（exim4 へのリンク）本家（互換コマンドの名前の由来）
同時に入るか入らない。どれも mail-transport-agent を提供し、それと衝突する

7章が1つの事実から出ていた

この節で分かること: 主題1.09 のファイルパス群が、なぜ出題範囲に並んでいるのか。

この教材で触ったものを並べる。

章送り手が渡したもの宛先を決めた受け手の表
1RTC が持つ時刻起動時にシステムクロックへ読み込む設定
2エポック秒（1つ）TZ / /etc/localtime / /etc/timezone
3基準とのずれ（測った値）chrony.conf と起動の指定（この檻は -x）。反映するかは別の判断
4facility・priority・本文/etc/rsyslog.conf・/etc/rsyslog.d/
5同じ1行journald.conf（保存先と上限）
6書き続けられるログ/etc/logrotate.conf・/etc/logrotate.d/
7To: に書いた名前/etc/aliases・~/.forward

7つとも同じ形をしている。

送り手は、中身とラベルだけを渡す。
宛先を決めているのは、受け手側にある設定ファイルである。

だから出題範囲 1.09 の「詳細」欄に、コマンドよりファイルパスが多く並んでいる。判断がそこに置かれているからである。/etc/localtime・/etc/timezone・chrony.conf・rsyslog.conf・journald.conf・logrotate.conf・/etc/aliases・~/.forward — どれも「受け取ったものをどう扱うか」が書かれた表である。

そしてこの構造が、同じ形の失敗を3回起こした。

章書いたのに効かなかった理由
2timedatectl set-timezone は /etc/timezone を更新しない（担当が違う）
6設定ファイルが 0666 だと logrotate が丸ごと無視する（終了コードは 0）
7~/.forward が world writable だと postfix が読まない（警告はログだけ）

受け手が表を読むのだから、受け手がその表を信用できるかどうかを先に判断する。信用できなければ黙って従わない。そして「従わなかった」という事実は、ほとんどの場合ログにしか残らない。

だから実機でこの主題の作業をするときの順番は決まる。

1. 設定を書く
2. 読み直させる（restart / newaliases / HUP）
3. 当人に聞く（chronyc tracking / journalctl -t systemd-journald / postconf -n）
4. ログを読む（journalctl / /var/log/mail.log）

2 を飛ばすと第3章と第5章で止まり、4 を飛ばすと第6章と第7章で止まる。推測で埋めずに、当人に聞いてログを読む。それがこの主題の実技である。

たとえ: どの章も「申請書を出す側」と「受け付けて処理する側」に分かれていた。 出す側は申請書の様式と中身しか決められず、処理の仕方は受付の規定集が決める。 規定集が複数の棚（/etc の各ファイル）に分かれて置かれている。
ただし崩れる点: 役所なら不受理のときに通知が来るが、 ここでは通知が来ないことが多い。ログを自分で見に行く必要がある。
確認

/etc/aliases に alice: bob を書いた。newaliases は打っていない。 alice 宛のメールはどこに届くか。

答え

alice に届く。postfix が読むのは alias_maps = hash:/etc/aliases の hash: が示す /etc/aliases.db で、テキストを書き換えただけでは .db は古いまま。newaliases（sendmail -bi と同じ。postfix では中で postalias が作り直す）で作り直す。 一方 ~/.forward はテキストを直接読むので作り直しは要らない。

確認

mailq が Mail queue is empty を返した。 全部のメールが正しく配送されたと言えるか。

答え

言えない。配送できなかったメールは、送り手への差し戻し（不達通知）が作られ、 元の1通はキューから消える。この檻では送り手が root なので、通知は /var/mail/root に入った。 確かめるのは送り手のメールボックスと /var/log/mail.log （または journalctl -t postfix/smtp -t postfix/bounce）である。

確認

この主題で触った設定を書き換えたあと、必ずやることは何か。章をまたいで答えよ。

答え

読み直させること。chrony.conf と rsyslog.d/*.conf と journald.conf は systemctl restart、 /etc/aliases は newaliases、 rsyslog に開き直させるのは HUP シグナル。~/.forward と logrotate の設定は例外で、 使うたびに読まれるので何も要らない（logrotate は常駐しない）。 そして読み直させたあと、効いたかどうかを当人に聞く（chronyc tracking、 journalctl -t systemd-journald、postconf -n）。

確認

bob が、自分宛のメールを alice へ転送しつつ、自分のメールボックスにも残したい。~bob/.forward に何を書くか。

答え

alice と \bob の2行。\ は「この名前をそれ以上展開しない」印で、\bob の分は bob のメールボックスに入る。 alice の1行だけだと、転送されて bob の手元には残らない。ファイルは other（world）が書けない権限にしておく（書けると postfix は読まない）。

この章で分かったこと

持ち帰ってほしいこと

  • To: に書いた名前は希望でしかない。/etc/aliases と ~/.forward で2回書き換わった
  • alias_maps = hash:/etc/aliases なので、テキストを直したら newaliases で .db を作り直す。~/.forward は不要
  • /etc/aliases の右側はカンマで複数（support: alice, bob）。~/.forward は1行に1宛先で、手元にも残すなら \自分の名前 の行を足す
  • mail -s 件名 [-c Cc] [-b Bcc] [-r 送信元] 宛先…。本文は標準入力から。-S smtp=… は Red Hat 系の mailx の書き方で、Ubuntu の mail には無い
  • ~/.forward が world writable（other が書ける）だと postfix は読まない（group だけなら読む）。警告はログ（journal と /var/log/mail.log）に出るだけで、送り手には返らない
  • 配送の経路はログの orig_to（送り手の名前）と to（実際の配送先）で追う
  • mailq が空でも成功とは言えない。差し戻しは送り手（この檻では root）のメールボックスへ行き、元の1通はキューから消える
  • MTA は1台に1つ。postfix・exim・sendmail はどれも mail-transport-agent を提供し、それと衝突する。どれも sendmail・mailq・newaliases の名前のコマンドを持つ
  • 7章すべてが「送り手はラベルだけを渡し、宛先は受け手の表が決める」という1つの形だった。だから出題範囲にファイルパスが並ぶ
  • 書いたら読み直させ、当人に聞き、ログを読む。この3手を飛ばすと必ず止まる
