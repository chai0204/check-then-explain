5. バイナリを読む

41バイトの .wasm を開けても、そこには4つの塊しか入っていない。 その4つを読むだけで、モジュールが何を外に見せているか、そして外に何を要求しているかが実行前に分かる。

前提: 第1〜4章前提: wabt（wasm-objdump, wasm2wat）所要 18分影響度 A最終検証 2026-09-30

この章のゴール

  • wasm-objdump でセクション構成を読み、どの export がどの関数かを対応づけられる
  • 手元の .wasm が何を import しているかを、実行する前に調べられる
ここで覚えなくていいこと: セクション種類番号の全一覧は覚えない。この章で出てくる4種類＋3種類を、出力と突き合わせて読めれば足りる。 custom section（規格が中身を決めていない、道具ごとの任意領域）の仕様も不要。 DWARF デバッグ情報も不要で、この章の2つの道具はデバッグ情報が1バイトも無いファイルに対して動いている。

セクションという単位

この節で分かること: 41バイトのファイルが4つの塊に分かれていること、その境界がどのバイトで宣言されているか。

結論から言う。.wasm は「種類番号1バイト」「長さ1バイト（この41バイトの範囲では）」「その長さぶんの中身」の繰り返しでできている。 先頭8バイトだけが例外で、そこには識別子と版が入る。

ふつうこう考える

バイナリの中身を見たいのだから、まず xxd で開く。41バイトなら目で全部追える。

$ xxd add.wasm
00000000: 0061 736d 0100 0000 0107 0160 027f 7f01  .asm.......`....
00000010: 7f03 0201 0007 0701 0361 6464 0000 0a09  .........add....
00000020: 0107 0020 0020 016a 0b                   ... . .j.

右の列に .asm と add が見えるので、手応えはある。

だめな理由: 16進が並んでいることは分かるが、どこからどこまでが1つのまとまりかがどこにも書いていない。 add という名前が見えても、それが「0番の関数の名前」なのか「1番の関数の名前」なのかは、この画面からは決まらない。 41バイトなら根気で読めるが、判断の根拠が「なんとなくこの辺が区切りだろう」になっている。 必要なのは境界の位置であって、バイトの列そのものではない。

境界だけを出す道具がある。

$ wasm-objdump -h add.wasm

add.wasm:	file format wasm 0x1

Sections:

     Type start=0x0000000a end=0x00000011 (size=0x00000007) count: 1
 Function start=0x00000013 end=0x00000015 (size=0x00000002) count: 1
   Export start=0x00000017 end=0x0000001e (size=0x00000007) count: 1
     Code start=0x00000020 end=0x00000029 (size=0x00000009) count: 1

この出力は中身を一切解釈していない。名前と、始まりと、終わりと、件数だけである。 そして xxd の側と重ねると、境界の直前2バイトに規則性が現れる。 下の表のバイトは、上の xxd の出力を切り出し直したものである。

オフセットバイト読み
0x00–0x070061 736d 0100 0000識別子と版。右の ASCII 列に .asm が出る。-h の1行目が file format wasm 0x1 と言う 0x1 は、0x04 の 01 にあたると読める
0x0801種類番号。-h はこのあとの塊を Type と呼んだ
0x0907長さ 7
0x0a–0x1001 60 02 7f 7f 01 7fType の中身。start=0x0000000a end=0x00000011 (size=0x00000007) と一致する
0x1103種類番号。-h は Function と呼んだ
0x1202長さ 2
0x13–0x1401 00Function の中身。start=0x00000013 end=0x00000015 と一致
0x1507種類番号。-h は Export と呼んだ
0x1607長さ 7
0x17–0x1d01 03 61 64 64 00 00Export の中身。61 64 64 が xxd の右列の add
0x1e0a種類番号。-h は Code と呼んだ
0x1f09長さ 9
0x20–0x2801 07 00 20 00 20 01 6a 0bCode の中身。end=0x00000029 = 41 でファイルが尽きる

ファイル順の種類番号は 01, 03, 07, 0a で、-h はそれぞれを Type, Function, Export, Code と呼んだ。 種類番号の対応表は、この2つの出力を並べれば自分で作れる。仕様書を開く前に、手元の .wasm と -h の出力で確かめられる部分がここまである。

長さが中身より先に置かれているので、読み手は種類番号を知らなくても 09 バイト読み飛ばして次へ進める。 -h が中身を1バイトも解釈せずに境界だけを出せるのは、この形のおかげである。

たとえ: -h の出力は目次で、xxd の出力は本文。ページ番号（start / end）があるから、どこを読めばいいかが決まる。
ただし崩れる点: 本の目次は著者が本文とは別に作るが、この目次は本文そのものの中に埋まっている。0x08 の 01 と 0x09 の 07 がそのまま1行分の目次になっている。目次だけを差し替えることはできない。

確認問題

  1. -h の最初の start は 0x0a である。ファイル先頭の 10 バイトはどのセクションにも属していない。この 10 バイトは何か。
  2. Code セクションの end=0x00000029 は 41 で、xxd の最後のバイトの次にあたる。ここから、-h の一覧に出てこないセクションについて何が言えるか。
答え

1. 先頭8バイトが識別子と版（0061 736d 0100 0000）、続く 0x08 と 0x09 の2バイトが最初のセクションの種類番号と長さ。-h が報告する start はセクションの中身の先頭なので、種類番号と長さの2バイトは範囲の外に出る。だから 8 + 2 = 10 バイトが余る。

2. 4つのセクションでファイルが尽きている。つまり一覧に無いセクションは「-h が省略した」のではなく、ファイルに存在しない。この性質が、あとで import を調べるときの根拠になる。

名前と番号の対応

この節で分かること: export の名前が、どの関数の本体に結びついているか。

境界だけでなく中身まで出すのが -x である。第3章で使った mem.wasm に通す。

$ wasm-objdump -x mem.wasm

mem.wasm:	file format wasm 0x1

Section Details:

Type[1]:
 - type[0] () -> i32
Function[2]:
 - func[0] sig=0 <ptr>
 - func[1] sig=0 <len>
Memory[1]:
 - memory[0] pages: initial=1
Export[3]:
 - memory[0] -> "mem"
 - func[0] <ptr> -> "ptr"
 - func[1] <len> -> "len"
Code[2]:
 - func[0] size=4 <ptr>
 - func[1] size=4 <len>
Data[1]:
 - segment[0] memory=0 size=10 - init i32=0
  - 0000000: 6865 6c6c 6f20 7761 736d                 hello wasm

ここで見るべきは Export[3] の3行である。左が内部の番号、右が外から呼ぶときの名前で、 func[0] <ptr> -> "ptr" は「0番の関数を "ptr" という名前で外に出す」と読む。

Code[2] は本体を func[0], func[1] の順に並べている。 つまりホストが "len" を呼んだときに走るのは func[1] size=4 の本体である。 名前から本体へたどる経路は、Export の行が示す番号を Code の並びに当てるところにしかない。

たとえ: Export セクションは内線表である。外から掛ける人は "len" という名前しか知らず、交換台がそれを func[1] という番号に置き換える。
ただし崩れる点: 会社の内線表は席替えのたびに番号を付け替えれば済むが、ここでの番号は Code セクションの並び順そのものである。表の番号だけ書き換えると、別の本体が呼ばれる。

add.wasm でも同じことが起きている。Export の中身は 01 03 61 64 64 00 00 の7バイトで、 先頭の 01 が件数、03 が名前の長さ、61 64 64 が add、残りが 00 00 の2バイトである。 同じ場所を wasm2wat は (export "add" (func 0)) と書き出す（次の節）。 func という種別と 0 という番号の2つが、この2バイトに収まっていると読める。 どちらが先かは add.wasm だけでは決められない。両方 00 だからである。1つの標本で決まらないことは、決まらないままにしておく。

Memory と Data

Memory[1] の pages: initial=1 が、第3章でホスト側から 65536 バイトとして見えたものの宣言である。 Data[1] はそのメモリの初期値で、segment[0] memory=0 size=10 - init i32=0 は 「0番のメモリのオフセット 0 に 10 バイト置く」と読む。置かれる 10 バイトは 6865 6c6c 6f20 7761 736d で、 右端に hello wasm と添えられている。

たとえ: Data セグメントは入居前に部屋へ運び込んでおく荷物である。モジュールが動き出す前に、線形メモリの決まった位置に決まったバイト列が置かれる。
ただし崩れる点: 荷物を運び込むのは住人ではなくホスト側のランタイムである。しかも置かれるのは「文字列」ではなく 10 バイトの数値の並びで、それを hello wasm として読むかどうかは外側の解釈にすぎない（第3章で ptr と len から組み立てたのがその解釈である）。

確認問題

  1. ホストが "len" という名前で呼んだとき、Code[2] のどちらの本体が走るか。何を根拠にそう言えるか。
  2. Type[1] は type[0] () -> i32 の1件しかないのに、関数は2つある。矛盾していないのはなぜか。
答え

1. func[1] size=4 の本体。根拠は Export の func[1] <len> -> "len" が名前 "len" を番号 1 に結びつけており、Code セクションが本体を同じ番号順に並べていること。名前は Export 側にしか無く、本体側は番号しか持っていない。

2. Function[2] の2行がどちらも sig=0 で、同じ型を指しているから。ptr も len も「引数なしで i32 を1つ返す」形をしているので、型は1件で足りる。型は関数ごとに複製されず、番号で共有される。

構造は戻る、名前は戻らない

この節で分かること: バイナリから WAT を戻したときに、何が戻って何が戻らないか。

wasm2wat はバイナリを WAT の表記に戻す。翻訳ではなく、同じものの別表記である。

$ wasm2wat add.wasm
(module
  (type (;0;) (func (param i32 i32) (result i32)))
  (func (;0;) (type 0) (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add)
  (export "add" (func 0)))

ここに出てくる (;0;) は番号であって名前ではない。 この出力の中で名前として残っているのは "add" だけで、それは Export セクションに書かれている文字列である。 関数も型も、番号でしか指されていない。

(param i32 i32) (result i32) という形は、前の節で見た Type の中身 01 60 02 7f 7f 01 7f に対応する。 7f が3回出るのが引数2つと戻り値1つで、並ぶのは型1つ1つの番号だけである。 第1章で (result string) が wat2wasm に受け付けられなかったのは、この列に文字列の型を置く場所が無いからだと読める。

1〜4章で見たものは、どこにあったか

この節で分かること: これまで画面に出たものが、バイナリのどの部分に対応するか。
章画面で見たことバイナリのどこ
1add を外から名前で呼べたExport セクション（add.wasm の 0x17–0x1d）。名前 add はここにしか無い
1(result string) が書けなかったType セクション（01 60 02 7f 7f 01 7f）。7f のような型の番号しか並ばない
2env::log が無いと起動しなかったImport セクション。add.wasm と mem.wasm にはこの塊が無い
3ホストから見えた線形メモリMemory セクション（pages: initial=1）と、それを外に見せている Export の memory[0] -> "mem"
3hello wasm の実体Data セクション（segment[0] memory=0 size=10 - init i32=0 と続く 10 バイト）
4同じ .wasm がホストによって動く／動かないImport セクション。ファイルに書いてあるのは要求の名前だけで、それを満たせるかはホスト側の事情

表の6行のうち2行が Import セクションを指している。そしてこれまで見てきた2つのファイルには、そのセクションが無い。

実行する前に、要求を読む

この節で分かること: 実行せずに、そのモジュールが何を要求しているかを読む手順。

配布された .wasm を wasm-objdump -x に通すと、Import の行が出るか出ないかが分かる。 Import に並んだ名前が、そのモジュールの能力の上限である。外の世界に触る手段は、ホストが手渡したものしか無い。

上で見た2つの出力には Import の行が1つも無い。 -h add.wasm は Type / Function / Export / Code の4つを挙げ、それで 41 バイトが尽きた。 -x mem.wasm は Type / Function / Memory / Export / Code / Data を挙げ、Import はその中にいない。 つまりこの2つは外へ出る口を1つも持っていない。できるのは、数値を受け取って数値を返すことと、自分の線形メモリを触ることだけである。

逆向きの証拠は第2章にある。imp.wasm を wasmtime に読み込ませた時点で、 unknown import: `env::log` has not been defined という趣旨のメッセージ（文言は環境で変わる）で止まった。 関数が1行も走っていない段階で、wasmtime は env::log という名前を言い当てている。 その文字列がファイルの中に書いてあるからである。読めば分かるものを、実行して確かめる必要はない。

たとえ: Import セクションは買い物リストである。中身を開ける前にリストを読めば、その部品が何を要求するかが分かる。リストに無いものは要求できない。
ただし崩れる点: 買い物リストは買い忘れても後から買い足せるが、import は読み込みの時点で全部揃っていないと起動しない。第2章で1つ欠けただけで止まったのがそれで、あとから足す経路が無い。

読む順番

  1. wasm-objdump -x を通す。
  2. Import の行を読む。無ければ、そのモジュールは外に出られない。第1章の add のように、数値を受け取って数値を返すだけである。
  3. Export の行を読む。ここは向きが逆で、ホスト側がモジュールの中を覗ける範囲である。mem.wasm に memory[0] -> "mem" があったから、第3章でホストは線形メモリを丸ごと読めた。この行が無ければホストは中を見られない。
  4. Memory と Data を読む。ただしここに何が置かれていても、それはモジュールの内側の話である。外に出る経路は Import、外から覗く経路は Export で、この2つ以外に境界を越える口は無い。

「動かしてエラーを読む」のも調べることではある。ただし順番が逆で、調べたい相手をホストに読み込ませる側が、何を渡すかを先に決めていなければならない。 -x はファイルを読むだけなので、読み込ませる前に決める材料になる。

対応する演習は lab start 05。判定は lab check 05。 第2章の imp.wasm に wasm-objdump -x を通し、Import の行を自分の画面に出す。 そのうえで、add.wasm と mem.wasm には出ないことを確かめる。

確認問題

  1. 配布された .wasm がファイルを読み書きしないことを、実行せずに確かめるには何を見るか。
  2. ある .wasm の Export に memory[0] -> "mem" があった。これはそのモジュールが外のメモリを読めることを意味するか。
答え

1. wasm-objdump -x の Import の行。ファイルを読み書きする手段はホストから渡された関数しか無いので、Import に何も無ければその手段を持っていない。Code セクションが大きくても、Memory や Data に何が書かれていても、外へ出る口の有無とは関係がない。

2. 意味しない。向きが逆で、ホストがそのモジュールの線形メモリを読めるという意味である。第3章でホスト側が hello wasm を組み立てられたのはこの Export があったからで、モジュールが外に出るには Import が要る。

この章で分かったこと

持ち帰ってほしいこと

  • .wasm は「種類番号・長さ・中身」の繰り返し。wasm-objdump -h の start / end を xxd に重ねれば、種類番号の対応は自分で確かめられる。
  • 名前は Export セクションにしか無い。名前から本体へは、Export が示す番号を Code の並び順に当ててたどる。
  • wasm2wat で戻るのは構造だけで、番号は番号のまま出てくる。名前として残るのは Export に書かれた文字列だけ。
  • Import の行を読めば、そのモジュールが何を要求しているかが実行前に分かる。行が無ければ外に出る口が無い。
  • Export は「中を覗かせる窓」で、能力を増やす口ではない。できることの上限は Import が決めている。
