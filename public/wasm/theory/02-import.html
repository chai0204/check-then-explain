2. 能力は import でしか増えない

1本の同じ .wasm が、渡す相手と渡すものを変えるだけで3通りに終わる。 その3つを並べると、できることがモジュールの中ではなく渡す側にあることが見える。

前提: 第1章を読み終えている前提: wat2wasm でビルドできる前提: node が打てる所要 14分影響度 Alab-wasm:1.0.0最終検証 2026-09-30

この章のゴール

  • import した関数をホストから受け取って呼び出せる
  • import が足りないときに何が起きるかを、wasmtime と Node の2つのホストで見分けられる
ここで覚えなくていいこと: WASI にどんな API が並んでいるかは1つも覚えなくていい。この章で扱うホストの能力は、自分で名前を決めた関数1つだけである。 コンポーネントモデルという上位の仕組みも出てこない。import の型が一致するかどうかの判定規則も、条文として覚える必要はない。 この章で必要なのは「名前と形が合っていなければ繋がらない」という事実1つで、規則の全文はここでは使わない。

注文票だけを持つモジュール

この節で分かること: モジュールが自分で「これが無いと動けない」と宣言する書き方と、その宣言が誰にも解決されないまま .wasm になること。

第1章の add は外を一切必要としなかった。引数を2つ受けて足して返すだけで、話し相手がいない。 今回のモジュールは、そこに1行だけ足したものである。

$ cat imp.wat
(module
  (import "env" "log" (func $log (param i32)))
  (func (export "run")
    i32.const 42
    call $log))

足したのは import の行である。ここには3つの情報しかない。 二段の名前 "env" と "log"、受け取る形 (param i32)、そしてモジュール内部で呼ぶためのラベル $log。 この行は定義ではなく要求である。log の中身はどこにも書かれていない。

もう一方の run は、42 を積んで $log を呼ぶ。それで終わりである。 画面に出す命令も、書き出す命令も、1つも無い。42 がこのあとどうなるかは $log の中身次第で、その中身はこのファイルの外にある。

たとえ: import の行は注文票である。「env 売り場の log という品を、i32 を1つ受ける形で1つ」と書いてある。渡す側はこの票を見て品を揃える。
ただし崩れる点: 注文票は品名と形までしか書かない。log が実際に何をするか（画面に出すのか、数えるのか、捨てるのか）はどこにも書いていない。log という語は人間向けのラベルにすぎず、形が合う関数なら何を渡してもよい。
$ wat2wasm imp.wat -o imp.wasm

何も言わずに通る。log の中身が無いままでも .wasm になる。 モジュール単体で見れば矛盾がないからである。要求が書いてあり、その要求に沿った呼び出しが書いてある。それで筋は通っている。

たとえ: プラグの付いた家電に近い。コンセントに差さなくても製品としては完成していて、箱に入って出荷できる。差した瞬間に、その部屋に合う口があるかどうかが決まる。
ただし崩れる点: 家電はプラグの形が合えばだいたい動くが、import は名前と形の両方が一致しないと繋がらない。形が合っていても名前が違えば繋がらない。

同じ1本の .wasm が3通りに終わる

この節で分かること: 1本の imp.wasm を3つの条件に渡した実測。結末が分かれた原因がモジュール側に1つも無いこと。

これから渡すのは3回とも同じ imp.wasm である。作り直さない。変えるのは渡す相手と、一緒に渡すものだけである。

(a) wasmtime に渡す

ふつうこう考える

42 を扱うモジュールを書いてビルドまで通ったのだから、wasmtime に渡せば 42 が出るはずだ。WASM は速い実行環境なのだから、数を1つ出すくらいのことは自前でできる。

$ wasmtime run --invoke run imp.wasm
Error: failed to run main module `imp.wasm`

Caused by:
    0: failed to instantiate "imp.wasm"
    1: unknown import: `env::log` has not been defined
だめな理由: 42 を出す手段がモジュールの中に1つも無い。i32.const 42 は値を積むだけで、積んだ値を外に見せる命令ではない。見せる仕事は $log に任されていて、その $log は要求されただけで供給されていない。 しかもメッセージが止まっている場所は failed to instantiate である。run の途中で困ったのではなく、組み立ての段階で諦めている。42 を積む命令は1度も実行されていない。 wasmtime は env::log という名前の関数を持っていないので、揃えられない品がある時点で先に進まなかった。

手元では unknown import: `env::log` has not been defined という趣旨のメッセージが出る（文言は環境で変わる）。 読むべきは文言そのものではなく、止まった段階と、名前の二段目までが指名されている事実である。

(b) Node に import を渡す

同じ imp.wasm を Node に渡す。違うのは、インスタンス化のときに env という入れ物を用意し、その中に log という関数を1つ入れて一緒に渡したことだけである。 渡した関数の中身は、受け取った数をそのまま表示するだけのものにした。

$ node host_ok.mjs
ホストが受け取った値: 42

42 が出た。ただし、この文字を画面に出したのはモジュールではない。 ホスト側で用意した関数が、引数として受け取った 42 を表示している。モジュールがしたのは 42 を積んで $log を呼ぶところまでで、呼んだ先で何が起きたかをモジュールは知らない。

(c) Node で入れ物だけ渡す

3回目は、env という入れ物は渡すが、中の log を入れないでおく。

$ node host_ng.mjs
LinkError: WebAssembly.instantiate(): Import #0 module="env" function="log" error: function import requires a callable

書式も語彙も (a) とはまったく違う。言っていることは同じ位置の同じ欠品である。 Import #0 が0番目の import、module="env" function="log" が二段の名前、function import requires a callable が「呼べるものが来ていない」。 env そのものは届いているので、「入れ物が無い」ではなく「中身が呼べない」という言い方になっている。

渡した相手一緒に渡したもの結末観測した文字列
wasmtime何も渡していない組み立ての段階で停止unknown import: `env::log` has not been defined
Nodeenv の中に log を1つrun が動き、42 がホスト側の関数に届くホストが受け取った値: 42
Nodeenv は渡すが log は入れない組み立ての段階で停止function import requires a callable

確認問題

  1. wat2wasm imp.wat -o imp.wasm は何も言わずに通ったのに、wasmtime では動かなかった。ビルドが失敗していたということか。
  2. 3回のうち 42 が画面に出たのは1回だけだった。その 42 を画面に出したのは誰か。
答え

1. 失敗していない。妥当かどうかはモジュール単体で決まり、要求した名前が実在するかどうかはそこでは見ない。見るのは渡す相手が決まってからである。wasmtime のメッセージが failed to instantiate で止まっているのがその証拠で、翻訳ではなく組み立ての段で落ちている。

2. ホスト側で用意した関数である。モジュールは 42 を積んで $log を呼んだだけで、表示する命令を1つも持っていない。同じ呼び出しでも、渡す関数を差し替えれば結果は変わる。

2つのホストのメッセージを、同じものとして読む

この節で分かること: 文言の違いに惑わされず、import の欠品を同じ手順で特定する読み方。

(a) と (c) のメッセージは、書式も語彙も共通点が少ない。それでも取り出すべきものは3つで、どちらからも同じように取り出せる。

  1. 止まった段階 — failed to instantiate と WebAssembly.instantiate()。どちらも組み立ての段である。関数の中で落ちたのではない。ここが読めれば、モジュールの命令列を疑う手を止められる。
  2. 二段の名前 — env::log と module="env" function="log"。区切りが :: か module= / function= かの違いだけで、指している品は同一である。
  3. 欠け方 — has not been defined は「その名前で揃うものが無い」、requires a callable は「来てはいるが呼べるものではない」。前者と後者では、次に見る場所が変わる。

手元の文言が上のどれとも一致しないときに、まず文言で検索しても遠回りになる。 突き合わせる相手は文言ではなく二段の名前である。モジュール側の二段名は WAT の (import "env" "log" (func $log (param i32))) の行にそのまま書いてあり、ホスト側で用意した名前と1文字ずつ照らせる。 照らす対象が2つに絞れているので、読む量は文言の長さとは関係なく一定になる。

たとえ: 同じ欠品を、和文の納品書と英文のインボイスで受け取ったようなものである。書式も語彙も違うが、欠けている品番は同一である。
ただし崩れる点: 納品書の書式は取引先が決めたら当面変わらないが、エラー文言は実装とバージョンの都合で変わる。だから覚えるのは文言ではなく、二段名を突き合わせるという手順のほうである。
対応する演習は lab start 02。判定は lab check 02。 1本の imp.wasm を作り、渡す相手と渡すものだけを変えて、この章の3通りの結末をコンテナの中で自分の手で出す。

確認問題

  1. 手元で module="env" function="log" error: function import requires a callable と出た。ホスト側で何を確認するか。
  2. unknown import と LinkError は、別々の不具合なのか。
答え

1. env という入れ物は届いている。届いていないのは env の中の log で、そこに入っている値が呼べるものになっていない。確認するのは、env のキーに log があるか、そしてその値が関数かどうかである。入れ忘れ、別のキーに入っている、関数以外を入れた、のいずれかに当たる。

2. 同じ不具合の2通りの言い方である。どちらも組み立ての段で、モジュールが出した要求とホストが出した提供を突き合わせた結果として出ている。名前が同じ表記でないので別物に見えるだけである。

能力はここでしか増えない

この節で分かること: この教材が最後まで回収する1文と、それがこの章の実測のどこに現れていたか。

この教材はこの1文を最後まで回収していく。

WASM は外の世界を一切知らない。できることは全部、ホストが import として手渡したものだけである。

この章の3回は、その1文が実物として見える最小の形である。imp.wasm は3回とも同じファイルだった。 変わったのは渡す相手と、一緒に渡した import だけである。それなのに結末は、停止・成功・停止の3通りに分かれた。 分かれた原因はモジュールの中に1つも無い。

そして揃える作業は、組み立ての1回で終わる。(a) と (c) はどちらもそこで止まり、モジュールの命令は1行も動いていない。 足りないものを実行中に取りに行く経路は、この章で観測した範囲には無い。 だから「この .wasm は何ができるのか」を調べる場所は、.wasm ではなくホスト側のコードになる。

たとえ: 持ち物検査を通って手ぶらで作業室に入る職人に近い。使えるのは入室時に渡された工具だけで、部屋の中に道具箱は置かれていない。
ただし崩れる点: 職人は作業中に「ドライバーをください」と頼める。モジュールは頼めない。渡すものは入室の瞬間に全部決まり、足りなければ入室そのものが成立しない。

確認問題

  1. 「この .wasm はファイルを読めますか」と聞かれた。.wasm だけを見て答えられるか。
  2. この章の観測の範囲で、実行が始まったあとにモジュールが新しい能力を要求する経路はあったか。
答え

1. 答えられない。読めるかどうかは、ホストがそれに当たる関数を import として渡すかどうかで決まる。.wasm から分かるのは「何を要求しているか」までで、要求が通るかどうかは渡す側の話である。

2. 無かった。足りない import は組み立ての段で突き合わされ、足りなければ組み立て自体が成立しなかった。実行が始まった (b) では、必要なものが最初から全部揃っていた。

この章で分かったこと

持ち帰ってほしいこと

  • .wasm 単体が妥当であることと、ホストに繋がることは別物である。突き合わせは組み立ての段で起きる
  • import の欠品は「止まった段階・二段の名前・欠け方」の3点で読む。文言は実装とバージョンで変わる
  • モジュールが同じでも、渡す import が違えば結末は変わる。能力を調べる場所はホスト側である
