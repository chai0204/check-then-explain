1. 41バイトの計算機

テキスト5行を wat2wasm に通すと、41 バイトの .wasm ができる。 その 41 バイトを1バイトずつ指して、中に何が入っているか、そして何が入っていないかを確かめる。

前提: シェルが打てる・16進ダンプを見たことがある所要 20分影響度 A最終検証 2026-09-30

この章のゴール

  • WAT を手で書いて .wasm にコンパイルし、関数を呼び出せる
  • 41 バイトのバイナリの各バイトが何であるかを xxd の出力上で指せる
  • WASM の値型に文字列が無いことを、コンパイルエラーで示せる
ここで覚えなくていいこと: オペコードの一覧は覚えない。この章に出てくるのは3つだけで、残りは必要になった時に引けばよい。 セクション ID の番号も暗記しない。番号と名前の対応は wasm-objdump が出力に書いてくれる。 バイナリ中の数の符号化規則（LEB128）には触らない。この章に現れる数はすべて1バイトに収まっていて、規則を知らなくても読める。 Rust や C から .wasm を作る話も出さない。生成物が数十 KB になると、中身を指で追う練習にならない。

WAT を書いて 41 バイトにする

この節で分かること: .wasm は言語処理系を用意しなくても、テキスト5行から作れる。

WASM のバイナリを作るのに、コンパイラ一式は要らない。WAT というテキスト表記があり、 それを wat2wasm に通せばバイナリになる。まず入力を見る。

$ cat add.wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))

読み方は上から順に、module が入れ物、func が関数1つ、 (export "add") が外から呼ぶときの名前、(param i32 i32) (result i32) が型。 残る3行が本体で、これはスタックに対する命令列である。 local.get 0 で1つめの引数を積み、local.get 1 で2つめを積み、 i32.add が上2つを降ろして和を積む。最後に積まれている1個が戻り値になる。

たとえ: WAT と .wasm の関係は、アセンブリとオブジェクトファイルの関係に近い。 人が読める表記と、機械が読む表記が1対1で並んでいる。
ただし崩れる点: オブジェクトファイルはリンクすれば OS の上で単独に走り出せるが、 .wasm には走り出す先が無い。誰かが呼ばない限り1命令も動かない。

変換する。wat2wasm は成功すると何も言わない。

$ wat2wasm add.wat -o add.wasm
$ ls -l add.wasm
-rw-r--r-- 1 lab lab 41 Sep 30 19:11 add.wasm

41 バイト。この中に型情報と関数の本体と add という名前が全部入っている。 呼び出してみる。

$ wasmtime run --invoke add add.wasm 3 4
warning: using `--invoke` with a function that takes arguments is experimental and may break in the future
warning: using `--invoke` with a function that returns values is experimental and may break in the future
7

warning が2行出るのは正常で、隠す理由が無いのでそのまま載せている。 --invoke は wasmtime が experimental と明示している機能で、 引数や戻り値のある関数を名指しで叩くという使い方は将来変わりうる。 この教材では「関数1つだけを外から突く」のに都合がいいので使い続ける。

対応する演習は lab start 01。判定は lab check 01。

41 バイトを指で追う

この節で分かること: 41 バイトの内訳と、そこに外の世界の話が1バイトも無いこと。

ダンプを取る。3行で終わる。

$ xxd add.wasm
00000000: 0061 736d 0100 0000 0107 0160 027f 7f01  .asm.......`....
00000010: 7f03 0201 0007 0701 0361 6464 0000 0a09  .........add....
00000020: 0107 0020 0020 016a 0b                   ... . .j.

右端の ASCII 欄に手がかりが2つ見えている。1行目の .asm は先頭4バイト 0061 736d、つまり先頭がヌルバイトで続く3文字が asm のマジックナンバーで、 その直後の 0100 0000 がバージョン 1。 2行目の add は 0361 6464 の後ろ3バイトで、 export 名がバイナリの中に平文で入っている。

残りの内訳を知るには、まずどこからどこまでが何のセクションかを絞る。 wasm-objdump がそれを出す。

$ wasm-objdump -h add.wasm

add.wasm:	file format wasm 0x1

Sections:

     Type start=0x0000000a end=0x00000011 (size=0x00000007) count: 1
 Function start=0x00000013 end=0x00000015 (size=0x00000002) count: 1
   Export start=0x00000017 end=0x0000001e (size=0x00000007) count: 1
     Code start=0x00000020 end=0x00000029 (size=0x00000009) count: 1

ここで出ている start はセクションの本体の先頭である。 Type は 0x0a から始まると書いてあるが、ダンプの 0x0a の 2つ手前、0x08 と 0x09 には 01 07 がある。 この 07 は objdump の size=0x00000007 と一致し、 01 がセクションの種類を表す番号である。 同じ関係が他の3つでも成立する。Function の本体は 0x13 からで、 手前の 0x11 0x12 は 03 02。Export は 0x17 からで手前が 07 07。 Code は 0x20 からで手前が 0a 09。 つまり各セクションが「番号・自分の長さ・本体」の3点セットで並んでいる。

たとえ: 41 バイトは、章立てが決まった薄い冊子である。 先頭8バイトが表紙（マジックとバージョン）で、そのあとに型の章・関数の章・輸出の章・本体の章が続く。
ただし崩れる点: 冊子なら先頭に全体の目次があるが、ここには無い。 各章が自分の長さを自分で名乗っていて、読む側は先頭から長さ分だけ進んで次の章に着く。 上の start と end が隙間なく繋がっているのはそのため。

ここまで分かれば全バイトが埋まる。xxd は2バイトずつまとめて印字するので、 下の表の1行が印字の1かたまりと揃わないことがある。オフセットで数える。

オフセットバイト意味
0x0000 61 73 6dマジック。ASCII 欄に .asm と出ている
0x0401 00 00 00バージョン 1
0x0801セクション番号 1。objdump が Type と呼んだもの
0x0907本体 7 バイト（objdump の size と一致）
0x0a01型は1つ（objdump の count: 1 と一致）
0x0b60これは関数の型である
0x0c02 7f 7f引数2個、どちらも i32
0x0f01 7f戻り値1個、i32
0x1103 02セクション番号 3（Function）、本体 2 バイト
0x1301 00関数は1つ。その型は 0 番
0x1507 07セクション番号 7（Export）、本体 7 バイト
0x1701輸出は1つ
0x1803 61 64 64名前の長さ 3、続けて add
0x1c00 00種別は関数、その番号は 0
0x1e0a 09セクション番号 10（Code）、本体 9 バイト
0x2001 07関数本体は1つ、その長さ 7 バイト
0x2200ローカル変数の宣言なし
0x2320 00local.get 0
0x2520 01local.get 1

0x280bend。関数の終わり

ダンプ3行目の ASCII 欄が ... . .j. になっていて、途中に空白が2つ見える。 これは 0x20 というバイトが ASCII の空白と同じ値だからで、 その2つがちょうど local.get の2回に対応する。 6a が j と表示されているのも同じ理由である。

たとえ: 0x18 からの add は荷札である。 外の誰かがこの箱を名前で指名できるように、読める文字で貼ってある。
ただし崩れる点: 荷札は普通は中身を示すが、これは示さない。 Export セクションがしているのは名前と関数番号 0 を結ぶことだけで、 add と書いてあることは中の命令が足し算である保証にならない。

ここで、埋まらなかった欄を数える。画面に文字を出す記述は無い。ファイルを開く記述も、 時計を読む記述も、乱数をもらう記述も無い。あるのは型1つ、関数1つ、名前1つ、命令4つだけである。 それでも先ほど端末には 7 が出た。 3 と 4 を用意したのも、返ってきた 7 を印字したのも、41 バイトの外側にいた wasmtime である。 WASM は外の世界を一切知らない。次章はここを起点に、外の世界に触れる機能をどう足すのかを扱う。

確認問題

  1. wasm-objdump -h が Export セクションを start=0x17 と報告した。 このセクションが「番号 7・長さ 7 バイト」であることを、objdump を使わずにダンプだけから言うにはどこを見るか。
  2. この 41 バイトのどこにも「画面に出力する」という記述が無いのに、端末に 7 が表示された。誰が表示したか。
答え

1. 本体の先頭 0x17 の2つ手前を見る。0x15 と 0x16 が 07 07 で、前が番号、後ろが本体の長さ。各セクションが「番号・自分の長さ・本体」で並んでいるので、 本体の開始位置が分かれば手前2バイトが読める。

2. wasmtime。--invoke に渡した 3 と 4 を引数として関数に入れ、 戻ってきた値を標準出力に書いたのは wasmtime 側の仕事である。 41 バイトの側には印字する手段が1バイトも入っていない。

値型に文字列は無い

この節で分かること: 文字列を返す関数は書けず、実行前のコンパイルで止まる。

ここまで出てきた型名は i32 だけだった。これは例が単純だったからではない。 (result …) に書ける語は決まっていて、その中に文字列は無い。

ふつうこう考える

足し算が動いたなら、次は挨拶を返す関数だろう。(result i32) の i32 を string に替えて、greet という名前で export すればよさそうに見える。 実際にそう書いて wat2wasm に通すと、こうなる。

$ wat2wasm str.wat -o str.wasm
str.wat:2:34: error: unexpected token string, expected ).
  (func (export "greet") (result string)
                                 ^^^^^^

unexpected token string, expected ). という趣旨のメッセージ（文言は wabt のバージョンで変わる）が出て、 wat2wasm は終了コード 1 で落ちる。str.wasm は作られない。

だめな理由: エラーが出ているのは型の意味を検査する段階ではなく、 その手前の、字面を読む段階である。expected ) は「ここで括弧が閉じるはずだった」という意味で、 つまり wat2wasm は string を型名として認識すらしていない。 知らない語が来たので、(result) の中身は終わったものと解釈して括弧を探した。 型が合わないのではなく、語彙に無い。だから実行時ではなくコンパイル時に止まる。

キャレット ^^^^^^ が string の6文字をちょうど指し、 行頭の str.wat:2:34 が2行目34桁目を示している。 どの語が原因かをエラーが自分で名指ししているので、ここは推測が要らない。

たとえ: WASM の値型は電卓のボタンである。数と演算のボタンはあるが、 文字を打つボタンは最初から付いていない。
ただし崩れる点: 電卓は文字を扱えないまま完結しているが、WASM の上では文字を扱うプログラムが現に動いている。 無いのは型であって、文字を扱えないという意味ではない。この差をどう埋めるかは後の章で扱う。

確認問題

  1. (result string) の誤りは、実行してみるまで分からないか。分かるとすれば何段目で分かるか。
  2. エラーの expected ). という部分は、何を期待していたと言っているか。
答え

1. 実行の前に分かる。wat2wasm がテキストを読む段階で落ちるので、 .wasm ファイル自体が作られない。実行する対象が存在しないところまで手前で止まっている。

2. (result の中身がもう終わって括弧が閉じること。 string を型名の候補として突き合わせたのではなく、型名が並ぶ場所に未知の語が来たので、 リストの終端を探した結果である。

バイナリからテキストへ戻す

この節で分かること: WAT は入力専用の補助表記ではなく、バイナリから復元できる正式な表現である。

逆変換がある。wasm2wat にバイナリを渡すとテキストが返る。

$ wasm2wat add.wasm
(module
  (type (;0;) (func (param i32 i32) (result i32)))
  (func (;0;) (type 0) (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add)
  (export "add" (func 0)))

命令列は元の add.wat と同じ3行が同じ順で出ている。型も (param i32 i32) (result i32) のまま。 一方で、書き方は3か所変わった。(type (;0;) …) という宣言が独立して現れ、 関数は (type 0) でそれを番号で指し、export は関数の内側から外へ出て (export "add" (func 0)) になっている。(;0;) は WAT のコメント記法で、 何番目かを人間向けに添えたものである。

この変化は前節の表がそのまま説明する。バイナリには Type セクションと Function セクションと Export セクションが別々にあり、それぞれ番号で結ばれていた。 元のテキストは型を関数の中にまとめて書く省略形を使っていたが、 バイナリはその省略を持たないので、戻すときも省略できない。

たとえ: 和文を英訳して、また和訳し戻したときの往復に似ている。 戻ってきた文は元の文と一字一句同じにはならない。
ただし崩れる点: 翻訳では意味が削れることがあるが、ここで変わったのは書き方だけである。 型も命令も並び順も、上の出力と add.wat を見比べれば残っていることが確かめられる。

往復できるということは、テキスト側が説明のための飾りではないことを意味する。 その結果、手元の見知らぬ .wasm は必ず読める。分からない1バイトに当たったときの順序はこうなる。

  1. wasm2wat でテキストに戻し、同じ位置に何があるかを見る。名前の付いたものが見えれば、だいたいそこで済む
  2. 済まなければ wasm-objdump -h で、そのオフセットがどのセクションの本体に入るかを絞る
  3. そのうえで仕様のバイナリフォーマットの章を、絞ったセクション名で引く

順序を逆にすると、仕様の全体を先に読むことになって量に飲まれる。 先に objdump にセクション名を言わせてから引くのが、一次情報を最短で使う手順である。

確認問題

  1. wasm2wat の出力に、元の add.wat には無かった (type (;0;) …) が現れた。 情報が増えたのか。
  2. 見知らぬ .wasm の 0x1a 番目のバイトが何か知りたい。最初に打つのはどちらのコマンドか。
答え

1. 増えていない。元のテキストは型を関数の宣言の中に書く省略形を使っており、 バイナリではそれが Type セクションとして独立して置かれていた。 wasm2wat はバイナリにある形をそのまま書いているだけで、 省略形に戻すという判断をしていない。

2. wasm2wat。テキストに戻して読めればそれで終わる。 読めなかったときに wasm-objdump -h でセクションを絞り、それでも足りなければ仕様を引く。 逆順にすると、名前が付いていて済む話に仕様を持ち出すことになる。

この章で分かったこと

持ち帰ってほしいこと

  • WAT を5行書いて wat2wasm に通せば .wasm になり、wasmtime run --invoke で関数を名指しで呼べる
  • 41 バイトの内訳は「マジック4・バージョン4」＋「番号・長さ・本体」を4組。オフセットから手前2バイトを見ればセクションの番号と長さが読める
  • export 名は平文でバイナリに入っているが、名前と関数番号を結んでいるだけで、中身の保証にはならない
  • 値型に文字列は無い。(result string) はコンパイルの字面を読む段階で落ち、.wasm は生成されない
  • バイナリはテキストに戻せる。読めない1バイトは wasm2wat → wasm-objdump -h → 仕様の順で詰める
  • 41 バイトの中に、外の世界に触れる記述は1バイトも無い。引数を用意し結果を印字したのは外側の wasmtime である
