4. 同じ .wasm が、ホストが違うと動かない

1つの .wasm ファイルを2つのホストに渡す。片方は標準出力に文字を出し、もう片方は命令を1つも実行しないまま止まる。 「どこでも動く」の どこ を決めているのはファイルではない。

前提: 第3章を読んだ前提: wasmtime が動く前提: node が動く所要 14分影響度 A最終検証 2026-09-30

この章のゴール

  • WASI を使った .wasm が動くホストと動かないホストを区別できる
  • 「どこでも動く」の どこ が何で決まるかを言える
ここで覚えなくていいこと: WASI Preview 2 と Preview 1 の差分は追わない。この章で要るのは「名前にバージョンが埋まっている」という一点だけ。 iovec のフィールドも、先頭位置と長さの2つ以外は扱わない。残りが要る場面はこの章のゴールの外。 Node で WASI を動かす experimental フラグの詳細も不要。ここでは素の Node が WASI を持たないことだけを使う。

同じバイト列を2つのホストに渡す

この節で分かること: 同じ .wasm が、片方のホストでは文字を出し、もう片方では命令を1つも実行せずに止まる。

結論から言う。.wasm は「どこでも動く」ファイルではない。動くかどうかを決めているのはファイルの中身ではなくホストである。これを1つのファイルで確かめる。

使うのは wasi.wat を組み立てた wasi.wasm。標準出力への書き込みを1回だけ行う手書きのモジュールで、演習 04 の作業ディレクトリに置いてある。まず wasmtime に渡す。

実測 wasmtime に渡す
$ wat2wasm wasi.wat -o wasi.wasm
[exit 0]
$ wasmtime run wasi.wasm
hello from wasi
[exit 0]

端末に hello from wasi が出た。次に、同じ wasi.wasm を素の Node に渡す。ブラウザが持っている WebAssembly API とほぼ同じもので、import を何も渡さずに結び付けを試みる。

実測 素の Node に渡す
$ node wasi_browser.mjs
TypeError: WebAssembly.instantiate(): Import #0 module="wasi_snapshot_preview1" error: module is not an object or function
[exit 0]

module is not an object or function という趣旨のメッセージ（文言は環境で変わる）で止まる。なおこの行はスクリプトが例外を捕まえて印字したものなので、プロセスの終了コードは 0 になっている。終了コードは何も教えていない。

2回の実行で、渡したバイト列は同じである。命令もデータも1ビットも違わない。変わったのはホストだけで、結果は「文字が出る」と「結び付けに失敗する」に分かれた。

たとえ: 同じ電源プラグを、国の違うコンセントに差すのに近い。形が合う国では通電し、合わない国では何も起きない。プラグ側は自分が何国製かを知らない。
ただし崩れる点: プラグは変換アダプタで物理的に橋渡しできる。import は名前の一致しか見ないので、似た機能の別名では代替されない。逆に、ホスト側で同じ名前の関数を自分で書けば通る。決めているのは形ではなく名前である。

確認問題

  1. wasmtime では動き、素の Node では失敗した。2回の実行で違っていたものを挙げてください。
  2. 素の Node での失敗は、モジュールの中の命令を実行している途中で起きましたか。
答え

1. ホストだけ。wasi.wasm のバイト列は2回とも同一のファイルである。

2. いいえ。Import #0 と出ているのは import を解決している段階で止まったという意味で、モジュールの命令は1つも実行されていない。失敗は実行中ではなく結び付けの前に起きる。

端末に文字を出したのは誰か

この節で分かること: hello from wasi の文字は .wasm の中にある。だが端末に書いたのは wasmtime である。

失敗したほうのメッセージが、モジュールが何を要求していたかを教えている。module="wasi_snapshot_preview1" — これが要求している名前空間の名前で、Import #0 なのでこれが最初の import である。要求している関数は fd_write ひとつ。

モジュール本体がやることは、第3章の ptr と len の約束そのままである。書き出したい文字列は線形メモリの中に置いてある。モジュールはその先頭位置と長さという2つの数値を、決められた場所に並べる（WASI はこの2つ組を iovec と呼ぶ）。そのうえで、書き込み先の番号 1、並べた場所、並べた個数、書けたバイト数を書き戻す場所 — 全部ただの数値 — を渡して fd_write を呼ぶ。

つまりモジュールは「1 番の出口へ、ここから何バイト」と番号で言っただけである。1 番が標準出力だと決めているのも、そこへ実際に書くのも wasmtime 側。.wasm には端末という概念が無い。だから hello from wasi は wasm が出力したのではなく、wasmtime が出力した。

たとえ: 声を出したのは通訳である。.wasm は原稿を机に置き「そこから16バイトを読み上げてくれ」と場所を番号で指しただけで、自分の口を持っていない。
ただし崩れる点: 人間の通訳は原稿が1文字ずれていても意味で補う。ホストは指された範囲のバイトをそのまま扱うので、置き場所を1バイト間違えれば間違ったものがそのまま出る。

沈黙は成功ではない

この節で分かること: 逆向き（ブラウザ用の .wasm を wasmtime に渡す）はエラーにならず、何も起きずに正常終了する。

ふつうこう考える

ホストが約束を満たしているかは、走らせてエラーが出るかどうかで確かめればよい。それなら逆向きも試せる。第3章で作った mem.wasm — ブラウザから使う前提で、import を1つも持たないモジュール — を wasmtime に渡してみる。

実測 ブラウザ用の .wasm を wasmtime に渡す
$ wasmtime run mem.wasm
[exit 0]
だめな理由: 出力が無く、エラーも無く、終了コードは 0。読者はここで「動いた」と読む。だが何も実行されていない。 mem.wasm が export しているのは mem / ptr / len の3つで、wasmtime run が引数なしで呼べる入口が無い。第3章では --invoke で ptr や len を名指ししていた。名指しが無ければ wasmtime は呼ぶ先を持たない。一方 wasi.wasm は _start を export しているので、名指しなしで走った。 そのうえ mem.wasm は import が0個なので、ホストが何も渡さなくても結び付けは成立する。結び付けは成功し、呼ぶものが無い。だから正常に終わる。 エラーの有無では「ホストが約束を満たしたか」は判定できない。

失敗の形が2つあることになる。片方は騒がしく、片方は静かである。前節の Node は Import #0 で止まり、何が足りないかを名前で言った。ここでの wasmtime は何も言わない。言うことが無いからである。要求が0個のモジュールに対して、ホストは満たすべき約束を持たない。

たとえ: 入口の無い建物に近い。壁も部屋も中にあり、工事は完了しているので誰も異常を報告しない。だが外から入る扉が無いので、誰も中で何もしない。
ただし崩れる点: 建物なら「扉が無い」ことが外から一目で分かる。.wasm は渡して走らせただけでは分からず、成功と同じ終了コードが返る。
対応する演習は lab start 04。判定は lab check 04。同じ .wasm を2つのホストに渡す往復を、自分の手元で通す。

確認問題

  1. wasmtime run mem.wasm が終了コード 0 で何も出さなかった。ここから「wasmtime は mem.wasm を実行できる」と言えますか。
  2. mem.wasm は import を1つも持たない。このモジュールがホストを選ばないのはなぜですか。
答え

1. 言えません。呼ぶ入口が無いので結び付けまでで終わっており、中の命令は実行されていない。「実行できる」ことも「実行できない」ことも、この1回からは分からない。

2. ホストに何も要求していないからです。動くために必要なものが全部モジュールの中に閉じているので、渡し先のホストが何を持っていようと結び付けは成立する。ただし成立するだけで、呼ばれるとは限らない。

「どこでも動く」の どこ

この節で分かること: 動くホストの範囲を決めているのは、モジュールが要求する import 名の集合である。

この章と第3章で観測した4通りを並べる。

渡した .wasmホスト観測何が決めたか
wasi.wasmwasmtime runhello from wasi が出たwasmtime が wasi_snapshot_preview1 を定義している
wasi.wasm素の Node（import を渡さない）Import #0 で停止その名前空間を誰も渡していない
mem.wasm（第3章）wasmtime run何も出ず終了コード 0要求が0個なので拒否されず、入口が無いので呼ばれない
mem.wasm（第3章）Node線形メモリを読んで文字列が組み立てられた要求が0個。ホストは何も約束しなくてよい

4行から読み取れることは1つである。移植性は .wasm の性質ではない。同じファイルが動く範囲は、そのファイルが要求する import 名をホストが全部定義しているかどうかで決まる。要求が0個のモジュールはどこでも結び付く。wasi_snapshot_preview1 を要求するモジュールは、その名前空間を渡してくれるホストの中でしか動かない。wasmtime はそれを渡し、素の Node は渡さない。この差はホスト側の実装の差であって、ファイルの側にはどこにも書かれていない。

たとえ: .wasm が持っているのは鍵の刻みで、ホストが持っているのは錠である。刻みが合う錠なら回る。刻みは鍵の側に固定されていて、どの錠の前でも同じ形をしている。
ただし崩れる点: 鍵は1本で1つの錠を開ける。import は複数あり、1つ欠けただけで全部が回らない。半分の能力で半分動く状態は無い。

エラーの1行から何を読むか

結び付けに失敗したメッセージは、次に何を調べればいいかをそのまま書いている。前節で出た1行を分解する。

断片読み取れること
Import #0何番目の import で止まったか。0 番なので最初の1つ。以降は検査されていない
module="wasi_snapshot_preview1"欠けている名前空間の名前。ホストを選ぶ基準であり、そのまま調べるときの語になる
module is not an object or function名前空間そのものが渡されていない。個別の関数が足りないのとは別の段階の失敗

ここで効いてくるのが名前の形である。wasi_snapshot_preview1 には preview1 が入っている。約束のバージョンが名前そのものに埋まっているので、ホストの説明に「WASI 対応」と書いてあるだけでは判断できない。モジュールが要求している文字列と一致するかを見る。

そしてこの文字列が、一次情報を引くときの入口になる。WASI の仕様は名前空間ごとに関数を並べた表であり、fd_write の引数が何番目に何を意味するか、iovec をどう並べるかは、全部この1つの名前空間の取り決めの中に書かれている。関数名を単体で検索すると別の実装の話に混ざるので、名前空間名と関数名を組で引く。

確認問題

  1. 知らない .wasm を渡されました。手元のホストで動くかどうかを、走らせる前に判断するには何を見ますか。
  2. ホストの説明に「WASI 対応」と書いてありました。これで足りますか。
答え

1. そのモジュールが要求している import の名前空間と関数名の一覧と、ホストがそれを全部定義しているか。1つ欠ければ結び付け自体が失敗するので、部分的に動く可能性を考える必要はない。要求を .wasm から取り出す手立ては第5章で扱う。

2. 足りません。wasi_snapshot_preview1 のように名前にバージョンが埋まっているので、モジュールが要求している文字列と一致するかを見る必要がある。

この章で分かったこと

持ち帰ってほしいこと

  • 同じ .wasm が動くホストと動かないホストを分けているのは、モジュールが要求する import の名前空間である。wasi.wasm は wasi_snapshot_preview1 を要求し、wasmtime はそれを定義し、素の Node は定義しない
  • 結び付けの失敗は実行前に起きる。Import #0 と出ていれば、モジュールの命令は1つも動いていない
  • 標準出力に文字を出したのはホストである。モジュールは線形メモリ上の場所を数値で指し、数値で fd_write を呼んだだけ
  • エラーが出ないことは動いた証拠にならない。入口の無いモジュールは終了コード 0 で黙って終わる
  • 「どこでも動く」の どこ は、ホストが名前で約束を満たす範囲。移植性はファイル側の性質ではない
