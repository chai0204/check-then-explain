3. 境界を越えられるのは数値だけ

この章で扱うモジュールには hello wasm がそのまま入っている。それでも関数から返ってくるのは 0 と 10 という数値2つだけで、文字列の形に戻す作業はホスト側にしか残っていない。

前提: 第2章まで読了前提: wat2wasm が動く前提: node が動く所要 14分影響度 A最終検証 2026-09-30

この章のゴール

  • 線形メモリに置いた文字列を、ポインタと長さの2つの数値だけでホストに渡せる
  • 線形メモリの実体が1枚の ArrayBuffer であることを確かめられる
ここで覚えなくていいこと: メモリを後から広げる操作（grow）は扱わない。1ページのまま最後まで進む。 何バイト境界に値を置くか（アラインメント）も扱わない。0 番地から詰めるだけで足りる。 1つのモジュールが複数のメモリを持つ提案と、GC 提案の参照型も、この章の外に置く。読まなくても最後まで詰まらない。

返るのは数値だけ

この節で分かること: 文字列を持っているモジュールの関数を呼ぶと、実際に手元に来るもの。

まず、この章で最後まで使うモジュールを見る。5行しかない。

$ cat mem.wat
(module
  (memory (export "mem") 1)
  (data (i32.const 0) "hello wasm")
  (func (export "ptr") (result i32) i32.const 0)
  (func (export "len") (result i32) i32.const 10))
$ wat2wasm mem.wat -o mem.wasm

hello wasm という文字列がソースに書かれていて、外向きの入口が ptr と len の2つある。この状態で関数を呼ぶと何が来るか。

ふつうこう考える

モジュールが hello wasm を持っていて、関数を2つ export しているなら、どちらかを呼べば文字列が返ってくるはずだ。そういう入口として ptr か len のどちらかが用意されているように見える。両方呼んでみれば分かる。

$ wasmtime run --invoke ptr mem.wasm
warning: using `--invoke` with a function that returns values is experimental and may break in the future
0
$ wasmtime run --invoke len mem.wasm
warning: using `--invoke` with a function that returns values is experimental and may break in the future
10
だめな理由: 返ってきたのは 0 と 10 である。0 は「線形メモリの 0 バイト目」、10 は「そこから 10 バイト分」を指すつもりの数値だが、その「つもり」は戻り値のどこにも入っていない。関数の型は () -> i32 で、この i32 が位置なのか個数なのかを書く欄がそもそも無い。文字列に戻す作業は、2つの数値を受け取った側にしか残らない。
たとえ: 窓口が「3番の棚、10冊分」としか言わない図書館の受け渡し口に近い。棚の番号と冊数だけが口頭で渡り、本そのものは自分で棚まで行って取る。
ただし崩れる点: 図書館の職員は棚に何が並んでいるかを知っているが、このモジュールは 0 と 10 が何を指しているかを知らない。数を2つ出しただけで、指し先を確かめる手段を持っていない。

線形メモリは区切りのないバイト列

この節で分かること: (memory ...) と (data ...) の2行が作っているもの。

先の 5 行を1行ずつ読むと、文字列がどこに置かれたかが分かる。

mem.wat の行作っているもの
(memory (export "mem") 1)1ページ分のメモリ領域。mem という名前で外に出している
(data (i32.const 0) "hello wasm")そのメモリの 0 番地から hello wasm のバイト列を置く指示
(func (export "ptr") (result i32) i32.const 0)定数 0 を返すだけの関数
(func (export "len") (result i32) i32.const 10)定数 10 を返すだけの関数

置き場所を決めているのは (data (i32.const 0) ...) の 0 で、長さを 10 と返しているのは人間が数えて書いた定数である。メモリ側には「ここからここまでが1つの文字列」という印が一切付かない。番地が 0 から順に振られたバイトが並んでいるだけで、境界の情報は外に出す数値のほうに持たせている。

たとえ: 罫線のない長いレシート用紙に文字を詰めて書いた状態に近い。先頭から何文字目かを数えれば位置は指せるが、紙の上に区切りは無い。
ただし崩れる点: レシートなら人が見て「ここが文の終わり」と判断できる。線形メモリを持っている側には読み手がいないので、どこで切るかを判断する主体が中に存在しない。

確認問題

  1. ptr が返した 0 は、何を 0 と言っているのか。
  2. len が返す 10 を書いたのは誰か。
答え

1. 線形メモリの先頭から数えた 0 バイト目、という位置である。ただし戻り値そのものは () -> i32 の i32 でしかなく、「メモリの番地である」という情報は付いていない。受け取った側がそう解釈することで初めて位置になる。

2. モジュールを書いた人間である。(func (export "len") (result i32) i32.const 10) は定数 10 を返すだけの関数で、hello wasm を数えた結果ではない。文字列を書き換えて 10 を直し忘れれば、長さは合わなくなる。

ホスト側で組み立てる

この節で分かること: 2つの数値から hello wasm に戻すまでに、誰が何をしているか。

ホスト側を Node にして、ptr と len を呼んでから文字列に組み立てる。

$ node readstr.mjs
ptr = 0  len = 10
組み立てた文字列 = hello wasm
線形メモリの実体 = ArrayBuffer 65536 バイト

3行が別々の出どころを持っている。1行目の ptr = 0 len = 10 は、関数を呼んだ結果をそのまま表示したものである。第1章で見た add と同じ、数値が返るだけの呼び出しにすぎない。

2行目の 組み立てた文字列 = hello wasm は、ホスト側の作業の結果である。export された mem から mem.buffer を取り、そこに Uint8Array をかぶせて 0 番地から 10 バイトを切り出し、TextDecoder に通している。切り出す位置と長さに使ったのが 1 行目の 2 つの数値で、バイト列をどの文字コードとして読むかを決めているのはデコーダ側である。その情報はモジュールから渡されていない。

3行目の ArrayBuffer 65536 バイト が、この章のゴールの後半にあたる。線形メモリは特別な入れ物ではなく、mem.buffer を見れば 65536 バイトの ArrayBuffer が1枚あるだけだと分かる。(memory ... 1) と書いた 1 がこの 65536 の由来で、1ページ = 64KB である。ホストから見れば、ふつうのバイト配列として端から端まで読める。

たとえ: 金庫の中身ではなく「上から何段目、そこから何センチ分」というメモだけを受け取る受け渡しに近い。金庫を開けて測るのは受け取った側の仕事になる。
ただし崩れる点: 現実の受け渡しなら、取り出したものを見れば書類か現金かは分かる。ここで取り出せるのはバイトの並びだけで、それを文字として読むという判断は、メモにも金庫にも書かれていない。
対応する演習は lab start 03。判定は lab check 03。

確認問題

  1. node readstr.mjs の出力3行のうち、WASM の関数を呼ぶだけで得られたのはどれか。
  2. 線形メモリが 65536 バイトだと分かったのは、モジュールのどの記述の結果か。
答え

1. 1行目の ptr = 0 len = 10 だけである。2行目は mem.buffer から Uint8Array を作って TextDecoder でデコードした結果、3行目は mem.buffer 自体を調べた結果で、どちらもホスト側の作業から出ている。

2. (memory (export "mem") 1) の 1 である。1ページが 64KB なので 65536 バイトになる。export していなければホストは mem.buffer に触れず、この行も出ない。

バイナリの中では平文のバイト列

この節で分かること: hello wasm がファイルのどこに、どんな姿で入っているか。

mem.wasm の中身を一覧させると、文字列が隠されていないことが見える。

$ wasm-objdump -x mem.wasm

mem.wasm:	file format wasm 0x1

Section Details:

Type[1]:
 - type[0] () -> i32
Function[2]:
 - func[0] sig=0 <ptr>
 - func[1] sig=0 <len>
Memory[1]:
 - memory[0] pages: initial=1
Export[3]:
 - memory[0] -> "mem"
 - func[0] <ptr> -> "ptr"
 - func[1] <len> -> "len"
Code[2]:
 - func[0] size=4 <ptr>
 - func[1] size=4 <len>
Data[1]:
 - segment[0] memory=0 size=10 - init i32=0
  - 0000000: 6865 6c6c 6f20 7761 736d                 hello wasm

見るのは最後の Data の2行である。segment[0] memory=0 size=10 - init i32=0 が「0 番の メモリの、i32 の 0 番地から、10 バイトを置け」という指示で、その次の行が置かれるバイトそのもの。6865 6c6c 6f20 7761 736d の10バイトが、右側に hello wasm として並んで見えている。暗号化も圧縮もされておらず、バイナリの中にそのまま並んでいる。

ここで注意する点が1つある。この Data セグメントに型は無い。「10バイトを 0 番地から置け」だけが書かれていて、それが文字なのか数値の列なのかはどこにも書かれていない。wasm-objdump の右側に hello wasm と出ているのは、印字できるバイトを文字として表示する wasm-objdump の親切であって、モジュールの中にその判断は入っていない。

セクションの一覧そのものの読み方は第5章で扱う。ここでは Data の2行だけ見れば足りる。

たとえ: 箱に貼られたラベルではなく、箱の中に入れた砂に近い。hello wasm はある位置に並んだ10バイトで、「これは文字である」という札は付いていない。
ただし崩れる点: 砂は手に取れば砂だと分かる。バイト列は見ただけでは文字なのか数値なのか判別できず、判別の手続きを持っているのは読む側だけである。

ptr と len は言語ではなく約束

この節で分かること: この受け渡しを成立させているものが、WASM の機能ではないこと。

上の wasm-objdump の出力が、そのまま証拠になっている。Type[1] は型が1種類しか無いことを示し、func[0] sig=0 <ptr> と func[1] sig=0 <len> は2つの関数がどちらも同じ sig=0、つまり () -> i32 であることを示している。型のレベルでは、位置を返す関数と長さを返す関数が区別されていない。

区別を作っているのは Export[3] の "ptr" と "len" という名前の文字列だけである。そしてこの名前を「前者が位置、後者が長さ」と読むのは、ホスト側のコードがそう書かれているからにすぎない。順序を逆に読むホストを書けば、同じ mem.wasm から別の結果が出る。

文字列という概念は、この受け渡しのどちら側にあるか。モジュール側には、番地と、バイトと、i32 を返す関数しか無い。ArrayBuffer を Uint8Array で覗き、10バイトを切り出し、文字コードを決めてデコードする——この一連の判断は全部ホスト側にある。(ptr, len) の組は WASM の型でも命令でもなく、ホストとモジュールが事前に合わせた取り決めである。第2章で import として能力を手渡したのと同じ構図が、データの受け渡しにも出ている。

たとえ: 同じ番号札を使う2つの店に近い。片方は「番号札は棚の位置」、もう片方は「番号札は受付順」と決めている。札そのものはどちらでも同じ紙である。
ただし崩れる点: 店の番号札は人間が見て意味を取り違えれば気づける。() -> i32 が2つ並んでいる状態では、取り違えを教えてくれる仕組みがどこにも無い。

確認問題

  1. wasm-objdump -x の出力のどこを見れば、ptr と len が型で区別されていないと言えるか。
  2. Data セグメントに hello wasm が見えている。このモジュールは自分が文字列を持っていることを知っているか。
答え

1. Function[2] の func[0] sig=0 と func[1] sig=0 が同じ sig=0 を指していて、Type[1] にはその 0 番として () -> i32 が1つしか無い。2つの関数の型は同一である。区別は Export の名前の文字列にしか無い。

2. 知らない。Data セグメントは「0 番地から10バイトを置け」という指示で、型を持たない。wasm-objdump が右側に hello wasm と印字するのはツールの表示であって、モジュールの中に「これは文字列だ」という記述は無い。文字列という概念はホスト側にしかない。

この章で分かったこと

持ち帰ってほしいこと

  • 境界を越えるのは数値だけである。ptr は 0、len は 10 を返し、それ以上のものは返らない
  • 線形メモリの実体は1枚の ArrayBuffer。(memory ... 1) の 1 が ArrayBuffer 65536 バイト になる
  • hello wasm はバイナリの Data セグメントに 6865 6c6c 6f20 7761 736d として平文で入っている。型は付いていない
  • ptr と len は型が同じ () -> i32 で、区別しているのは export の名前とホスト側のコードだけ。(ptr, len) は言語機能ではなく約束である
  • 文字列に組み立てる判断はすべてホスト側にある。モジュールは番地とバイトしか持っていない
