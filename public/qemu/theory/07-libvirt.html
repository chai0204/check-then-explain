7. libvirt は、コマンド行を組み立てているだけ

このサイトの仮想マシン型の檻で読者が打つ virsh start linuc。その後ろで動いているのは、この記事で自分の手で打ってきたのと同じ qemu-system-x86_64 だった。 libvirt は、定義の XML を読んで 100 個近い引数を組み立て、QEMU を1つ起動し、QMP のソケットで話しかけているだけである。 その証拠に、libvirt のデーモンを止めても、練習機（QEMU のプロセス）は動き続け、デーモンを起こし直すと、動いている QEMU につなぎ直す。

前提: 第6章までを同じ端末で終えている（後ろで動いている QEMU が無い）所要 20分影響度 B最終検証 2026-10-14

この章のゴール

  • libvirt の練習機の定義（XML）を読み、それが QEMU のどの引数になるかを、動いている QEMU のプロセスの引数（/proc/PID/cmdline）と並べて言える
  • libvirt のデーモンと QEMU のプロセスが別物で、デーモンが QMP で QEMU を操作していることを、デーモンを止めて確かめられる
  • このサイトの仮想マシン型の檻の作り（TCG・UEFI・差分ディスク・ユーザモードネットワーク・pty のシリアル）を、この記事の各章と結び付けて説明できる
ここで覚えなくていいこと: libvirt の XML の全項目、-blockdev の JSON の書式、-sandbox（QEMU 自身にかける制限）や -overcommit の意味、 libvirt の session と system の違いの細部、ゲストエージェント（qemu-guest-agent）の命令。

libvirt の定義を読む

この節で分かること: このサイトの仮想マシン型の檻が、練習機をどう定義しているか。

このサイトの仮想マシン型の檻は、この定義をもとに練習機を作っている（ネットワークの基礎やハードウェアとディスクの記事のように、これに NIC やディスクを足した定義に置き換えている檻もある）。この檻にも、この土台の定義が入っている。

$ sed -n '/<domain/,$p' /etc/lab-vm/domain.xml.in
<domain type='qemu' xmlns:qemu='http://libvirt.org/schemas/domain/qemu/1.0'>
  <name>linuc</name>
  <title>LinuC 練習機</title>
  <memory unit='MiB'>1536</memory>
  <vcpu>2</vcpu>
  <os firmware='efi'>
    <type arch='x86_64' machine='q35'>hvm</type>
    <nvram>@VMDIR@/linuc_VARS.fd</nvram>
  </os>
  <features><acpi/></features>
  <cpu mode='maximum'/>
  <clock offset='utc'/>
  <on_poweroff>destroy</on_poweroff>
  <on_reboot>restart</on_reboot>
  <devices>
    <disk type='file' device='disk'>
      <driver name='qemu' type='qcow2' discard='unmap'/>
      <source file='@VMDIR@/linuc.qcow2'/>
      <target dev='vda' bus='virtio'/>
    </disk>
    <serial type='pty'/>
    <console type='pty'/>
    <channel type='unix'>
      <target type='virtio' name='org.qemu.guest_agent.0'/>
    </channel>
    <rng model='virtio'><backend model='random'>/dev/urandom</backend></rng>
  </devices>
  <qemu:commandline>
    <qemu:arg value='-netdev'/>
    <qemu:arg value='user,id=lab0,hostfwd=tcp:127.0.0.1:2222-:22'/>
    <qemu:arg value='-device'/>
    <qemu:arg value='virtio-net-pci,netdev=lab0,mac=52:54:00:12:34:56,addr=0x10'/>
  </qemu:commandline>
</domain>

この記事で見てきた言葉が並んでいる。type='qemu'（KVM ではなく TCG。第4章）、machine='q35'（第1章・第5章）、firmware='efi' と nvram（UEFI と NVRAM のファイル。第6章）、 qcow2 のディスク（第3章）、serial type='pty'（シリアルの行き先。第2章）。最後の qemu:commandline は、XML の書き方を通さずに QEMU へそのまま渡す引数で、 第5章で自分で書いた -netdev user,…,hostfwd=… と addr=0x10 の NIC がそのまま書いてある。libvirt 10 の XML でも、<interface type='user'/> と書けば同じ QEMU の内蔵のユーザモードネットワーク（slirp）の NIC になる。ただし XML でポート転送（<portForward>）を書けるのは、代わりの仕組みの passt を選んだときだけで、passt は docker の中では起動できなかった。だから hostfwd 付きの NIC を、QEMU の書き方のまま渡している。

たとえ: 定義の XML は、レストランの注文票に近い。「q35 で、メモリ 1.5GB、UEFI で」と料理の名前を書けば、厨房（libvirt）が調理の手順（QEMU の引数）に書き直してくれる。
ただし崩れる点: 注文票には書いていない手順も、厨房は勝手に足す（次の節で見る -nodefaults や -S）。 逆に、注文票の書き方では頼めないものは、<qemu:commandline> に調理の手順をそのまま書いて渡すしかない。注文票は便利な書き方であって、QEMU にできることの全部ではない。

@VMDIR@ を置き換えて登録し、差分ディスクを作り、電源を入れる。仮想マシン型の檻の vm start がしているのも、この3つである。

$ qemu-img create -q -f qcow2 -b /var/lib/lab-vm/linuc-guest.qcow2 -F qcow2 ~/vm/linuc.qcow2
$ sed "s|@VMDIR@|$HOME/vm|g" /etc/lab-vm/domain.xml.in > ~/vm/linuc.xml
$ virsh define ~/vm/linuc.xml
Domain 'linuc' defined from /home/lab/vm/linuc.xml
$ virsh start linuc
Domain 'linuc' started

virsh start が起動したもの

この節で分かること: 電源を入れた後に動いているプロセスと、その引数。

ふつうこう考える

virsh で動かす仮想マシンは、libvirt という仮想化のソフトが動かしている。libvirt のデーモン（libvirtd）の中で仮想マシンが動いていて、 デーモンを止めれば、仮想マシンも一緒に止まるはずだ。

$ ps -o pid,ppid,comm -C qemu-system-x86,libvirtd,virtlogd
    PID    PPID COMMAND
    488       1 libvirtd
    520       1 virtlogd
    524       1 qemu-system-x86
$ virsh qemu-monitor-command linuc --hmp 'info status'
VM status: running
$ virsh qemu-monitor-command linuc '{"execute":"query-status"}'
{"return":{"status":"running","singlestep":false,"running":true},"id":"libvirt-451"}
$ pkill -x libvirtd
$ ps -o pid,ppid,comm -C qemu-system-x86,libvirtd,virtlogd
    PID    PPID COMMAND
    520       1 virtlogd
    524       1 qemu-system-x86
$ virsh list
 Id   Name    State
-----------------------
 1    linuc   running
$ ps -o pid,ppid,comm -C qemu-system-x86,libvirtd,virtlogd
    PID    PPID COMMAND
    520       1 virtlogd
    524       1 qemu-system-x86
    548       1 libvirtd

PID の数字は毎回違う。

だめな理由: 練習機は qemu-system-x86（qemu-system-x86_64 の名前の頭 15 文字）という独立したプロセスで、親（PPID）は libvirtd ではなく PID 1 だった。 libvirt は QEMU を起動したあと、自分の子として抱えず切り離している。pkill -x libvirtd でデーモンを止めても、QEMU（PID 524）はそのまま動き続けた。 次の virsh list で新しい libvirtd（PID 548）が自動で起き、まだ動いている QEMU を見つけてつなぎ直し、running と答えた。 仮想マシンを動かしているのは QEMU のプロセスで、libvirt はその起動と操作を代わりにしている係である。 virsh qemu-monitor-command は、libvirt が持っている QEMU のモニタに命令を素通しする。HMP の info status も、QMP の query-status も、第2章と同じ答えが返った。 QMP の返事の "id":"libvirt-451" は、libvirt が自分の命令に付けている通し番号で、電源を入れてからここまでに、libvirt はこの QEMU に 450 回ほど QMP で話しかけていた。

<qemu:commandline>-netdev user,id=lab0,hostfwd=… と -device virtio-net-pci,…,addr=0x10（そのまま）同じもの5

違いもある。libvirt は -S（CPU を止めたまま起動する）で QEMU を起動し、準備がすべて済んでから QMP で動かし始める。 -no-shutdown は、練習機が電源を切っても QEMU のプロセスを終わらせずに残し、libvirt が後始末をする。 UEFI は Secure Boot 用の組（プログラムの OVMF_CODE_4M.ms.fd と、Microsoft の鍵を入れた NVRAM のひな形 OVMF_VARS_4M.ms.fd）を選び、ディスクは土台まで自分で開いて読み取り専用にしている。 どれも QEMU の引数で、libvirt にしかできないことではない。

たとえ: libvirt は、劇場の舞台監督に近い。台本（XML）を読んで役者（QEMU）に出番の段取り（引数）を渡し、本番中はインカム（QMP）で指示を出す。
ただし崩れる点: 舞台監督がいなくなっても劇は続く。役者は自分で演じていて、監督は指示を出していただけだからである。 新しい監督が来れば、いま演じている役者のインカムに入り直す（virsh list の後の新しい libvirtd）。

止めて、片付ける

この節で分かること: virsh destroy と undefine が何を消すか。
$ virsh destroy linuc
Domain 'linuc' destroyed
$ virsh undefine --nvram linuc
Domain 'linuc' has been undefined
$ rm ~/vm/linuc.qcow2 ~/vm/linuc.xml

virsh destroy は QEMU のプロセスを終わらせる（第2章の quit と同じく、電源を抜く）。virsh undefine --nvram は定義と、libvirt が作った NVRAM のファイル（linuc_VARS.fd）を消す。 差分ディスクと XML は自分で作ったので、自分で消す。このサイトの仮想マシン型の檻の vm reset --yes も、同じものを消して作り直している。

たとえ: virsh destroy は電源コードを抜くこと、virsh undefine は備品の台帳から名前を消すことに近い。
ただし崩れる点: 台帳から名前を消しても、倉庫の中身（差分ディスク）は残る。libvirt が消すのは自分が作ったもの（定義と、--nvram を付けたときの NVRAM のファイル）だけで、 ディスクは libvirt の持ち物ではなく、QEMU に渡したただのファイルだからである。
手を動かす: 実践編の演習05と演習06で組んだ QEMU の引数を、この章の libvirt の引数と並べてみてほしい。 演習05 の判定は、127.0.0.1:2222 で待っている QEMU の引数に -name guest=linuc（libvirt が付ける印）があると、「自分の qemu-system-x86_64 で起動していない」と言う。
確認

ps で、qemu-system-x86 の親（PPID）が 1 だった。ここから、libvirt と QEMU の関係について何が言えるか。

答え

QEMU は libvirtd の子として動いているのではなく、独立したプロセスとして切り離されている。だから libvirtd を止めても QEMU は止まらない。 libvirtd は QMP のソケットで QEMU に話しかける側で、起動し直せば動いている QEMU につなぎ直す（virsh list で確かめた）。

確認

libvirt の定義に <serial type='pty'/> と書くと、QEMU の引数に何が現れるか。それは第2章のどの指定と同じ仕組みか。

答え

-chardev pty,id=charserial0 と -device isa-serial,…,"chardev":"charserial0"。シリアルポートの行き先（キャラクタデバイス）を疑似端末（pty）にしたもので、 第2章の -serial mon:stdio（行き先を端末に）や -serial file:（行き先をファイルに）と同じく、線の先を付け替えているだけである。virsh console は、この pty にあなたの端末をつなぐ。

確認

このサイトの仮想マシン型の檻の定義では、NIC だけが <qemu:commandline> に書かれていた。そこに書くと、何が違うか。

答え

libvirt はその引数を読み解かず、QEMU のコマンド行の終わりのほう（-sandbox と -msg の手前）に、書いたとおりに並べる（引数の一覧で、XML に書いたとおりの -netdev と -device がそこにあった）。 XML でポート転送を書けるのは passt を選んだときだけで、passt は docker の中で起動できないので、第5章と同じ QEMU のユーザモードネットワークを、hostfwd ごと QEMU の書き方のまま渡している。

確認

virsh qemu-monitor-command linuc '{"execute":"query-status"}' の返事に "id":"libvirt-451" が付いていた。これは何を表しているか。

答え

libvirt が QEMU に送った QMP の命令の通し番号。libvirt は電源を入れるとき（-S で止めたまま起動し、準備をしてから動かす）や状態を見るたびに、QMP で QEMU に命令を送っている。 virsh の操作の多くは、QMP の命令に置き換えられて QEMU に届く。

この章で分かったこと — 7章を貫いていたもの

持ち帰ってほしいこと

仮想マシンは、QEMU という1つのプロセスである。CPU もディスクも NIC もシリアルポートも、そのプロセスの中のソフトウェアが演じていて、何を演じるかは起動のときのコマンド行が決める（動いている間も、QMP で部品を足せる）。libvirt も、そのコマンド行を組み立てているだけだ。

  • 何も渡さなくても、既定の部品で PC が1台組み上がった（第1章）。libvirt は -nodefaults で既定を断り、要る部品を全部自分で書く
  • シリアルポートの先は、QEMU のプロセスの標準入出力・ファイル・ソケット・pty のどれか（第2章）。libvirt は pty につなぎ、virsh console がそこに端末をつなぐ
  • ディスクは QEMU が開くファイルで、qcow2 は書いたところだけを持ち、土台を重ねる（第3章）。libvirt も土台と差分の2つを開いている
  • CPU は QEMU が命令を翻訳して動かしている（第4章）。type='qemu' は -accel tcg
  • ネットワークも QEMU の中で演じられ、ssh の入口で待つのは QEMU（第5章）。libvirt の定義にも同じ指定がそのまま入っている
  • ファームウェアも QEMU が読むファイルで、NVRAM はファイルとして書き換わる（第6章）
  • libvirt は QEMU を起動し、QMP で話しかけ続ける係で、いなくなっても仮想マシンは止まらない（この章）
