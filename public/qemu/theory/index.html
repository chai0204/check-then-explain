理論編 — QEMU

このサイトの仮想マシン型の檻は、コンテナの中で QEMU が練習機を1台動かしている。 その QEMU を、libvirt（virsh）を通さずに qemu-system-x86_64 と qemu-img で直接打って、 仮想マシンが何でできているかを確かめる7章。部品の組み立て・シリアルとモニタ・ディスク・CPU の翻訳・ネットワーク・ファームウェアを順に見て、 最後に libvirt が組み立てているコマンド行を読む。

この7章を貫いている1つの事実
この節で分かること: 7章の挙動が、どれも1つの事実から出てくること

仮想マシンは、QEMU という1つのプロセスである。CPU もディスクも NIC もシリアルポートも、そのプロセスの中のソフトウェアが演じていて、何を演じるかは起動のときのコマンド行が決める（動いている間も、QMP で部品を足せる）。

何も渡さずに起動すると、既定値で PC が1台組み上がる（第1章）。シリアルポートの先は QEMU のプロセスの標準入出力、つまりあなたの端末で（第2章）、 ディスクは QEMU が開いているファイル（第3章）、CPU は QEMU が命令を翻訳して動かすプログラム（第4章）、 ネットワークのルータも DHCP も QEMU のプロセスの中にある（第5章）。ファームウェアも QEMU が読み込むファイルで（第6章）、 libvirt は、そのコマンド行を組み立てて QEMU を起動し、モニタで話しかけているだけだった（第7章）。

ここで覚えなくていいこと: QEMU のオプションの全部、マシン型の版の違い、QMP の命令の一覧、qcow2 のファイルの中の表の形、 TCG が作る中間の命令（TCG ops）、UEFI の Secure Boot の鍵のしくみ。どれも本文では名前が出るだけです。

x86 以外の CPU の仮想マシン（qemu-system-aarch64 など）と、1つのプログラムだけを翻訳して動かす qemu-x86_64（ユーザモードのエミュレーション）この檻に入っていない。仕組み（TCG の翻訳）は第4章と同じで、翻訳元の CPU が違うだけ

このサイトの他の記事の檻は、QEMU をどう使っているか
この節で分かること: 実践編で打っている docker run の各オプションが、QEMU の何に当たるか

このサイトの LinuC の5つの記事（起動・仮想化・プロセス・ハードウェアとディスク・ネットワークの基礎・アカウント・ジョブ・ロケール・セキュリティ）は、 仮想マシン型の檻で練習機を動かしています。読者が打つのは次の2行でした。

docker run -d --name lab-linuc-boot --hostname host --stop-timeout 30 \
  -v lab-linuc-boot-vm:/home/lab/vm \
  -v lab-linuc-boot-state:/home/lab/.lab \
  ghcr.io/chai0204/lab-linuc:boot-1.0.1@sha256:…

docker exec -it lab-linuc-boot bash -l

コンテナの中では libvirt（session モード）が練習機の定義から QEMU を1つ起動していて、その QEMU に何を渡しているかは第7章で1行ずつ読みます。 docker run の各オプションと、その先の QEMU の関係は次のとおりです。

オプションQEMU から見た意味章
（--privileged も --device /dev/kvm も無い） QEMU は TCG で命令を翻訳して動くので、ホストの特権も /dev/kvm も要らない。その代わり起動に 30〜90 秒かかる4
-v lab-…-vm:/home/lab/vm 練習機のディスク（読み取り専用の土台に重ねた qcow2 の差分 linuc.qcow2）と、UEFI の NVRAM（linuc_VARS.fd）の置き場所。ボリュームにあるので、コンテナを作り直しても練習機は続きから動き、vm reset --yes はこの2つを消して工場出荷時に戻す3 6
--stop-timeout 30 docker stop を受けたコンテナは、libvirt を通して練習機に止まるよう頼み（中のゲストエージェントがつながっていればエージェントに、いなければ ACPI の電源ボタンで。電源ボタンは第2章の system_powerdown と同じもの）、練習機が自分で止まるのを待つ。かかる時間は練習機の中の様子で変わり（linuc-boot の記事の記録で 12.4 秒）、docker の既定の猶予 10 秒を超えると QEMU ごと終わらされる（quit と同じく電源を抜いたことになる）2
ssh linuc コンテナの 127.0.0.1:2222 で待っているのは QEMU のプロセス（ユーザモードネットワークの hostfwd）。練習機の中では 10.0.2.15 の enp0s16 に届く5
練習機の中の lab check 練習機から 10.0.2.2:7777 へつなぐと、QEMU がコンテナの 127.0.0.1:7777 に渡す（ユーザモードネットワークは 10.0.2.2 を外のループバックにつなぐ）5
vm console（virsh console） 練習機のシリアルポートは疑似端末（pty）につながっていて、virsh console がその先にあなたの端末をつなぐ。抜けるのは Ctrl+]（libvirt の約束）で、-nographic の Ctrl-a x（QEMU の約束）とは別物2 7

コンテナ型の檻（ファイルとパーミッションや SQLite など）は QEMU を使いません。 コンテナの中のプログラムはホストのカーネルの上で直接動くので、翻訳も起動の待ち時間もありません。 仮想マシン型にしているのは、ブート・ディスクの分割・カーネルモジュール・NIC の設定のように、自分のカーネルが要る題材の記事だけです。 この記事の檻は、その仮想マシン型の檻と同じ土台（同じ QEMU と同じ練習機のディスク）から、コンテナの起動のときに libvirt で練習機を用意する係を外したものです（練習機は、あなたが打つまで1台も動いていません）。

章

  1. 何も渡さなくても、PC が1台組み上がる — 何も渡さずに起動すると、BIOS がディスク・フロッピー・CD を探し、最後はネットワークから起動しようとして DHCP で 10.0.2.15 をもらう（15分）
  2. シリアルの先は、あなたの端末そのもの — QEMU を終えた後、端末の長い行が 80 桁で切れる。止めたのは仮想マシンの中の BIOS が送った数バイト（20分）
  3. ディスクは、書いたところだけを持つファイル — 20GiB のディスクのファイルが 192KiB。-snapshot は何も保存しない。savevm はメモリごと入れる（30分）
  4. CPU は、命令を翻訳して動いている — 同じループが練習機の中では外の 20 倍ほどかかる。翻訳の跡を info jit と -d in_asm で見る（18分）
  5. ネットワークも、QEMU のプロセスの中にある — NIC を足してもアドレスが付かない。名前は差した位置で決まる。ssh の入口で待つのは QEMU（25分）
  6. ファームウェアは、差し替えられるファイル — UEFI 用に作った練習機が BIOS でも起動していた。NVRAM はファイルで、初回の起動で書き換わる（25分）
  7. libvirt は、コマンド行を組み立てているだけ — virsh start が起動したのは同じ qemu-system-x86_64。デーモンを止めても練習機は止まらない。ここで7章が1本になる（20分）

檻で再現できないもの

この節で分かること: 打てないものと、その理由と、代わりにしたこと
題材なぜ再現できないか代わりにしたこと
KVM で動かす（-accel kvm） 檻に /dev/kvm を渡していない（読者に権限を求めない）。macOS や入れ子の仮想化が無い環境では、渡すことすらできない 第4章で、断られるときの出力と /dev/kvm が無いことを見る。続きは KVM の記事
仮想マシンの画面（VNC・GTK の窓） VNC はコンテナの中の ::1:5900 で待ち受けるだけで、読者の手元から見る経路が無い。見る絵も読者ごとに違う 第1章で VNC の待ち受けまで見て、画面はシリアル（第2章）で代える
tap・ブリッジのネットワーク /dev/net/tun と CAP_NET_ADMIN が要る 第5章のユーザモードネットワークで、特権の要らない作りを見る
passt（libvirt 9.0 から選べる、ユーザモードネットワークのもう1つの仕組み。libvirt の XML でポート転送を書けるのは、こちらを選んだときだけ） 自分を閉じ込めるためにユーザ名前空間を作ろうとして、docker の既定の制限（seccomp）で起動できない（このサイトの土台を作ったときの実測） 仮想マシン型の檻は QEMU 内蔵の slirp を使っている。第7章で、その指定が libvirt の定義のどこにあるかを読む
Secure Boot（鍵の入った NVRAM での起動） 題材が UEFI の鍵の管理に広がり、この記事の範囲を超える 第6章は鍵の入っていない OVMF で起動し、第7章で libvirt の檻が Secure Boot 用の組（.ms.fd。鍵は NVRAM のひな形のほうに入っている）を選んでいることだけを読む

実務のどこで効くか

場面ここで効く理由見落としやすい点関連する章
CI でクラウドイメージを起動して試す 差分ディスクと -snapshot で、元のイメージを汚さずに何度でも起動できる 差分ディスクは土台のパスを覚えている。土台を動かしたり書き換えたりすると壊れる3
仮想マシンが起動しない・応答しない シリアルを端末かファイルにつなげば、ファームウェアからカーネルまでの記録が全部取れる。モニタで QEMU 自身の状態も読める シリアルの先の端末はゲストの命令に従う。表示が壊れたら tput smam か reset2
自作の管理ツールで仮想マシンを操作する QMP は JSON の決まった形でやりとりできる。libvirt も同じ窓口を使っている system_powerdown の {"return": {}} は「ボタンを押した」まで。止まったかは event か状態で確かめる2・7
仮想マシンのネットワークがつながらない 中の OS は NIC の名前（差した位置）で設定を当てている マシン型や PCI の位置を変えると名前が変わり、設定が当たらなくなる5
仮想マシンが遅い TCG で動いているかどうかで、CPU の速さが十倍以上違う コンテナの中や入れ子の仮想化では、気づかないうちに TCG になっていることがある4
