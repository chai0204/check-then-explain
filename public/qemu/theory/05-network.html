5. ネットワークも、QEMU のプロセスの中にある

練習機に NIC を足して起動しても、ip -br a は「ens3 DOWN」で、IP アドレスが付かない。ネットワークが無いのではなく、練習機の設定が enp0s16 という名前の NIC しか知らないからだった。 NIC の名前は、QEMU がその NIC を差した位置で決まる。位置を合わせると、練習機は DHCP で 10.0.2.15 をもらう。 そのアドレスを配ったのも、ゲートウェイの 10.0.2.2 を演じているのも、外から ssh linuc で入る入口（127.0.0.1:2222）で待っているのも、QEMU のプロセス自身である。

前提: 第4章までを同じ端末で終えている（~/work/linuc.qcow2 がある）所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • 練習機の NIC の名前（ens3・enp0s16）が、QEMU が差した位置とマシン型で決まることを説明できる
  • -netdev user と -device virtio-net-pci,addr=… で、練習機をネットワークにつなげられる
  • ユーザモードネットワークの 10.0.2.15・10.0.2.2・10.0.2.3 が誰で、10.0.2.2 への接続が外のどこに届くかを、実際につないで示せる
  • hostfwd で外の 127.0.0.1:2222 を練習機の 22 番へつなぎ、そこで待っているのが QEMU のプロセスだと ss -tlnp で示せる
ここで覚えなくていいこと: netplan の書き方、systemd-networkd の設定、NIC の名前の規則の細部（enx… や eno1 など）、 -netdev user のほかの指定（guestfwd・smb・tftp）、tap やブリッジのネットワーク。

NIC を足しても、つながらない

この節で分かること: NIC を足した練習機の中から、NIC がどう見えるか。練習機の設定が何を待っているか。

第1章で見たとおり、何も指定しない PC にも NIC が付いていた。ここでは、その NIC を自分で指定する。 -netdev user,id=n0 が NIC の先のネットワーク（QEMU の中のネットワーク。名前を n0 にする）、-device virtio-net-pci,netdev=n0 が NIC（virtio の NIC を、n0 につなぐ）である。

ふつうこう考える

NIC を1枚足して、その先をネットワークにつなげば、練習機は DHCP でアドレスをもらって、ネットワークにつながるはずだ。

$ qemu-system-x86_64 -m 1536 -smp 2 -drive file=linuc.qcow2,if=virtio -netdev user,id=n0 -device virtio-net-pci,netdev=n0 -display none -serial mon:stdio

この記録では、ログインの後の最初の ip -br a の行で、プロンプトが消えている（第3章の注）。

だめな理由: NIC はある（ens3）。QEMU の側でも、virtio の NIC（virtio-net-pci.0）がネットワーク n0（type=user,net=10.0.2.0）につながっている。 それでも ens3 は DOWN で、アドレスが無い。練習機の設定（netplan）を読むと、DHCP でアドレスをもらうのは enp0s16 という名前の NIC だけだった。 名前が違う NIC は、つながっていても誰も設定しない。NIC の名前は、NIC の種類ではなく、QEMU がその NIC を差した位置で決まる。この PC（何も指定しないときの i440FX の系統。pc 系）では、3番目のスロットに差したので ens3 になった。

名前は、差した位置で決まる

この節で分かること: ens3 と enp0s16 の読み方。練習機が enp0s16 を待っている理由。

Linux（systemd）は、NIC に「どこに差さっているか」から名前を付ける（予測可能なインターフェース名。起動のたびに eth0・eth1 の順番が入れ替わらないように、位置から名前を作る）。

名前読み方こうなる条件
ens3en（Ethernet）＋ s3（スロット 3）ファームウェアが、抜き差しできるスロットの番号を OS に伝えている（i440FX（pc 系）の PCI のスロット）
enp0s16en ＋ p0（PCI のバス 0）＋ s16（スロット 16）スロットの番号が伝わらないので、PCI の位置から名前を作る（q35 の根っこの PCI Express のバス）

QEMU は、部品を PCI の空いている位置に順に差していく。何も指定しないときの i440FX（pc 系）では 0〜2 番がチップセットと VGA で埋まっているので、足した NIC は 3 番に入って ens3 になった。 練習機の設定が enp0s16（バス 0・スロット 16）を待っているのは、このサイトの仮想マシン型の檻（libvirt）の定義が、q35 のマシン型で、NIC を位置 0x10（16）に差しているからである（第7章でその行を読む）。 同じ位置に差せば、同じ名前になる。-device の addr=0x10 が、差す位置の指定である。

何も指定しない i440FX（pc 系）のまま addr=0x10 に差すと、スロットの番号が伝わるので名前は ens16 になる。著者が試すと、それでもアドレスは付いた。 Linux がこの NIC に別名（altname）として enp0s16 も付け、設定がその別名に当たったためである（ip link show ens16 に altname enp0s16 と出た）。 迷わないよう、この章では libvirt の定義と同じ q35 の系統にそろえる（-machine q35。版まで同じではないことを、次の節で確かめる）。

たとえ: NIC の名前は、郵便の住所に近い。同じ人（同じ NIC）でも、住む場所（差した位置）が変われば宛名が変わり、旧住所あての郵便（設定）は届かない。
ただし崩れる点: 住所は1人に1つだが、Linux は1つの NIC に別名を付けることがあり、設定がどちらの名前に当たるかで結果が変わる。名前を頼りにする設定は、マシン型や位置を変えたときにいちばん先に壊れる。

10.0.2.x は、QEMU が演じている

この節で分かること: ユーザモードネットワークで、誰が何を演じているか。外から練習機に入る入口が、どこにあるか。

今度は、マシン型を q35 にし、NIC を位置 0x10 に差して、外から ssh で入れるようにする。 hostfwd=tcp:127.0.0.1:2222-:22 は、「外（このコンテナ）の 127.0.0.1 の 2222 番に来た TCP の接続を、練習機の 22 番（ssh）へ渡す」という指定である。 シリアルとモニタは第2章と同じくファイルとソケットにつなぎ、-daemonize で端末から切り離す（この端末で ssh を打つため）。

$ qemu-system-x86_64 -machine q35 -m 1536 -smp 2 -drive file=linuc.qcow2,if=virtio -netdev user,id=n0,hostfwd=tcp:127.0.0.1:2222-:22 -device virtio-net-pci,netdev=n0,addr=0x10 -display none -serial file:serial.log -qmp unix:qmp.sock,server=on,wait=off -daemonize
$ ss -tlnp

LISTEN   0        1              127.0.0.1:2222          0.0.0.0:*      users:(("qemu-system-x86",pid=280,fd=13))
$ printf '%s\n' '{"execute":"qmp_capabilities"}' '{"execute":"qom-get","arguments":{"path":"/machine","property":"type"}}' | socat - UNIX-CONNECT:qmp.sock
{"QMP": {"version": {"qemu": {"micro": 2, "minor": 2, "major": 8}, "package": "Debian 1:8.2.2+ds-0ubuntu1.18"}, "capabilities": ["oob"]}}
{"return": {}}
{"return": "pc-q35-8.2-machine"}

pid=280 の数字は毎回違う。

QMP の qom-get で、組み上がった PC のマシン型を尋ねた。-machine q35 で選ばれたのは pc-q35-8.2 で、第1章の一覧の q35 の2行のうち、QEMU 本来の版のほうだった。libvirt の練習機は、同じ q35 の系統の別の版（pc-q35-noble）で動いている（第7章）。版が違っても、NIC を差す位置の決まりは同じなので、名前は同じになる（この後の ip -br a で確かめる）。

練習機はまだ起動の途中なのに、127.0.0.1:2222 ではもう誰かが待っている。待っているのは qemu-system-x86 のプロセス（QEMU）である。 ssh linuc は、この檻の ~/.ssh/config で 127.0.0.1 の 2222 番に行くよう決めてあるので、その接続はまず QEMU が受け取る。 受け取った接続を QEMU は練習機の 22 番へ渡そうとするが、その先は練習機の様子で変わる。練習機の OS がまだネットワークを上げていなければ、QEMU は渡そうとし続け、ssh には何も返らない（ConnectTimeout=3 で、3 秒であきらめる）。OS がネットワークを上げていて、ssh の待ち受けがまだなら、すぐ切られる。どちらにしても、入れるようになるまで 3 秒おきに試す。

$ until ssh -o ConnectTimeout=3 linuc true 2>/dev/null; do sleep 3; done
$ ssh linuc ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s16          UP             10.0.2.15/24 metric 100 fec0::5054:ff:fe12:3456/64 fe80::5054:ff:fe12:3456/64
$ ssh linuc ip route
default via 10.0.2.2 dev enp0s16 proto dhcp src 10.0.2.15 metric 100
10.0.2.0/24 dev enp0s16 proto kernel scope link src 10.0.2.15 metric 100
10.0.2.2 dev enp0s16 proto dhcp scope link src 10.0.2.15 metric 100
10.0.2.3 dev enp0s16 proto dhcp scope link src 10.0.2.15 metric 100
$ ssh linuc ss -tn
State Recv-Q Send-Q Local Address:Port Peer Address:Port Process
ESTAB 0      0          10.0.2.15:22       10.0.2.2:45998

10.0.2.2:45998 の番号は毎回違う。ssh linuc コマンド は、練習機の中でそのコマンドを1つ打って、出力を持ち帰る。

名前は enp0s16 になり、DHCP で 10.0.2.15/24 をもらい、ゲートウェイ（default via）は 10.0.2.2 になった。 練習機の ssh から見ると、いまの ssh の接続（ESTAB）の相手は 10.0.2.2 から来ている。あなたは 127.0.0.1 につないだのに、練習機には 10.0.2.2 からの接続に見える。 この 10.0.2.x のネットワークは、外のどこにも無い。QEMU のプロセスの中に小さな TCP/IP があり（ユーザモードネットワーク。中身は slirp という部品）、練習機に対して次の役を演じている。

アドレス演じている役実体
10.0.2.15練習機に配るアドレス（DHCP）QEMU が DHCP の返事を作る（第1章の iPXE がもらったのも同じ）
10.0.2.2ゲートウェイ（外への出口）QEMU。外へ出る接続は、QEMU が自分のソケットでつなぎ直す。10.0.2.2 そのものへの接続は、QEMU が動いている側の 127.0.0.1 へ届く
10.0.2.3DNS サーバQEMU。問い合わせを、QEMU が動いている側の DNS に取り次ぐ

「10.0.2.2 そのものへの接続は、外の 127.0.0.1 に届く」を確かめる。外（このコンテナ）の 127.0.0.1 の 8000 番で、1回だけ1行を返す小さなサーバを後ろで動かし、練習機の中から 10.0.2.2 の 8000 番につなぐ。

$ socat TCP-LISTEN:8000,bind=127.0.0.1,reuseaddr SYSTEM:'echo hello from the container' &
[1] 306
$ ssh linuc nc -w 3 10.0.2.2 8000
hello from the container
[1]+  Done                    socat TCP-LISTEN:8000,bind=127.0.0.1,reuseaddr SYSTEM:'echo hello from the container'

[1] 306 の番号は毎回違う。Done の行は、後ろで動かしたサーバ（ジョブ1）が1回答えて終わったという、シェルの知らせである。

練習機の中で 10.0.2.2:8000 につないだら、外の 127.0.0.1:8000 で待っていたサーバの返事が来た。外の 127.0.0.1 は外のコンテナの中だけのアドレスで、本来は練習機から見えない。 QEMU が、練習機からの接続を受け取り、自分の側の 127.0.0.1 につなぎ直したのである。 このサイトの仮想マシン型の檻では、練習機の中で打った lab check が、この道で外の lab に届いている（練習機の中の lab は 10.0.2.2 の 7777 番につなぐ）。

たとえ: ユーザモードネットワークは、社員（練習機）の電話を全部取り次ぐ代表電話の受付に近い。社員が外へかけるときも、受付がかけ直す。外からかかってきた電話は、決めた内線（hostfwd）にだけ転送する。
ただし崩れる点: 本物の受付は1人の人だが、ここではルータも DHCP も DNS も、QEMU という1つのプロセスが演じている。プロセスが終われば、ネットワークごと消える。 そして外から社員へ直接かける番号は無い。外から練習機に届くのは、hostfwd で決めた入口だけである。

止める。後ろで動いている QEMU には端末が無いので、第2章の QMP で電源ボタンを押し、プロセスが消えるまで待つ。シリアルの最後の行が、練習機が電源を切った印である。

$ printf '%s\n' '{"execute":"qmp_capabilities"}' '{"execute":"system_powerdown"}' | socat - UNIX-CONNECT:qmp.sock
{"QMP": {"version": {"qemu": {"micro": 2, "minor": 2, "major": 8}, "package": "Debian 1:8.2.2+ds-0ubuntu1.18"}, "capabilities": ["oob"]}}
{"return": {}}
{"timestamp": {"seconds": 1791918565, "microseconds": 410215}, "event": "POWERDOWN"}
{"return": {}}
$ while pgrep -x qemu-system-x86 > /dev/null; do sleep 1; done
$ tail -1 serial.log
[   34.068096] reboot: Power down
たとえ: hostfwd は、代表番号への電話を決まった内線へ転送する設定に近い。
ただし崩れる点: 電話の転送は相手がいなければすぐ分かるが、hostfwd は練習機が起動していなくても入口を開けて待ち、接続を受け取ってしまう。だから起動の途中の ssh は、つながったのに返事が来ないまま待たされるか、すぐ切られる。 入口があることと、その先に相手がいることは別である（until で入れるまで試したのはそのため）。
手を動かす: 実践編の演習05は、自分の差分ディスクから練習機を起動して、ssh linuc で入れるようにする課題である。 判定は、127.0.0.1:2222 で待っているプロセスを ss で探し、それがあなたの QEMU か、どのディスクを開いているか（土台の上の差分か）を /proc と qemu-img で見てから、実際に ssh で入って練習機の NIC を読む。
確認

練習機に NIC を足したら、中で ip -br a が ens3 DOWN と出た。ネットワークが無いのか。そう判断する前に、何を確かめるか。

答え

QEMU の側で NIC が何につながっているか（モニタの info network）と、練習機の中の設定がどの名前の NIC を相手にしているか（この練習機なら /etc/netplan/）。 この章では、NIC はユーザモードネットワークにつながっていたが、設定が enp0s16 しか知らず、ens3 は誰にも設定されていなかった。

確認

練習機の設定は enp0s16 を待っている。-machine q35 のとき、QEMU の -device に何を足せばその名前になるか。

答え

addr=0x10（PCI のバス 0 の、スロット 16 に差す）。-device virtio-net-pci,netdev=n0,addr=0x10 のように書く。 名前は差した位置から作られるので、NIC の種類（e1000 か virtio か）を変えても、位置が同じなら名前は同じになる。

確認

ss -tlnp で、127.0.0.1:2222 を qemu-system-x86 が待ち受けていた。練習機がまだ起動していないときに ssh linuc を打つと、どうなるか。

答え

TCP の接続そのものは、QEMU がすぐに受け取る。入口（hostfwd）は QEMU が開けているもので、練習機が起動しているかとは関係なく開いている。その先は練習機の様子で変わる。 練習機の OS がまだネットワークを上げていなければ（ファームウェア・GRUB・カーネルの起動の途中）、QEMU は練習機につなごうとし続け、ssh には何も返らない。ssh は ConnectTimeout で決めた時間であきらめる（決めなければ、QEMU が接続を切るまで待つ。著者の記録では、つないでから 82 秒後に切れた）。 OS がネットワークを上げていて ssh の待ち受けがまだなら、練習機が断るので、すぐに切られる（ssh は鍵の交換に入れずに失敗する）。

確認

練習機の中の ss -tn で、ssh の接続の相手が 10.0.2.2 に見えた。外では 127.0.0.1 につないだのに、なぜか。

答え

接続は QEMU がいったん受け取り、練習機に対しては、QEMU が新しくつなぎ直しているから。外の 127.0.0.1 から来た接続は、QEMU が演じるゲートウェイ 10.0.2.2 から来たことにして渡す。 ほかのアドレスから来た接続は、そのアドレスのまま練習機に見える（著者が、このコンテナの 172.17.0.x のアドレスから hostfwd でつなぐと、練習機には 172.17.0.x から来たように見えた）。

この章で分かったこと

持ち帰ってほしいこと

  • NIC の名前は、QEMU が差した位置で決まる（i440FX（pc 系）のスロット 3 なら ens3、q35 のバス 0・スロット 16 なら enp0s16）。名前で当てる設定は、位置やマシン型を変えると当たらなくなる
  • -netdev user（ユーザモードネットワーク）は、QEMU のプロセスの中で、DHCP（10.0.2.15 を配る）・ゲートウェイ（10.0.2.2）・DNS（10.0.2.3）を演じる。特権は要らない
  • 10.0.2.2 そのものへの接続は、QEMU が動いている側の 127.0.0.1 に届く。このサイトの檻の、練習機の中の lab check はこの道を通る
  • hostfwd=tcp:127.0.0.1:2222-:22 は、QEMU が外の 127.0.0.1:2222 で待ち受け、来た接続を練習機の 22 番に渡す。ssh linuc の相手は、まず QEMU
