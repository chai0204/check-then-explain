3. ディスクは、書いたところだけを持つファイル

練習機のディスクは 20GiB と名乗るのに、ファイルは 527MiB しかない。その上に重ねたあなたのディスクは、作った直後は 192KiB で、練習機を1回起動して止めると 18MiB 余りになった。 QEMU のディスクはただのファイルで、qcow2 という形式は書いたところだけを持ち、持っていないところは下に重ねた土台のファイルに聞きに行く。 だから土台を1バイトも汚さずに練習機を何台でも作れ、-snapshot は書き込みを捨て、savevm は動いている状態ごとファイルの中にしまう。

前提: 第2章までを同じ端末で終えている（~/work にいる）所要 30分影響度 B最終検証 2026-10-14

この章のゴール

  • raw と qcow2 の違いを、ls -l と du と qemu-img info の数字で説明できる
  • qemu-img create -b … -F qcow2 で、読み取り専用の土台を汚さない差分ディスク（backing chain）を作り、そこから練習機を起動できる
  • -snapshot が「何も書き戻さない」指定であることを、ファイルの大きさとモニタの info block で示せる
  • savevm / loadvm で動いている状態ごと保存して戻し、それが qcow2 のファイルの中に入ることを qemu-img snapshot -l で示せる
  • 練習機の電源の切り方（system_powerdown と quit）の違いを、中の OS がいるときの振る舞いで言える
ここで覚えなくていいこと: qcow2 のファイルの中の表（L1・L2・refcount）の形、qemu-img のサブコマンドの全部（convert rebase commit resize は名前だけ）、 キャッシュの指定（cache=）、外部スナップショット（libvirt の virsh snapshot-create --disk-only）。

練習機のディスクを見る

この節で分かること: 練習機のディスクがどこにあり、何と名乗っているか。

練習機のディスクは、この檻の /var/lib/lab-vm/ にある。このサイトの仮想マシン型の檻も、同じファイルを使っている。

$ ls -l /var/lib/lab-vm/
total 539400
-r--r--r-- 1 root root 552337408 Oct 13 10:34 linuc-guest.qcow2
-r--r--r-- 1 root root        91 Oct 13 10:34 linuc-guest.sha256
$ qemu-img info /var/lib/lab-vm/linuc-guest.qcow2 | head -4
image: /var/lib/lab-vm/linuc-guest.qcow2
file format: qcow2
virtual size: 20 GiB (21474836480 bytes)
disk size: 527 MiB
$ qemu-img check /var/lib/lab-vm/linuc-guest.qcow2
No errors were found on the image.
18878/327680 = 5.76% allocated, 90.38% fragmented, 88.07% compressed clusters
Image end offset: 552337408

持ち主は root で、誰も書けない（r--r--r--）。qemu-img info は、このファイルを「練習機から見ると 20GiB のディスク（virtual size）、ファイルとしては 527MiB（disk size）」と読んだ。 qemu-img check は、中身を 64KiB の塊に分けて数えた。20GiB は 327680 個の塊で、書かれているのはそのうち 18878 個（5.76%、約 1.15GiB）だけだった。 書かれていない残りの約 18.8GiB は、どこにも置かれていない。書かれた約 1.15GiB が 527MiB に収まっているのは、塊の 88.07% が圧縮されているから（compressed clusters）で、この檻を作ったときに、配るために圧縮した。 練習機が後から書く塊は、圧縮されない。

fragmented は、塊がファイルの中で番地の順に並んでいない割合である。QEMU は圧縮した塊をすべてここに数えるので、90.38% のうち 88.07 ポイントは圧縮の分で、ふつうの塊で順に並んでいないのは 2.3% ほどにすぎない。ここでは気にしなくてよい。

20GiB のディスクを作る

この節で分かること: 仮想マシンのディスクの大きさと、ファイルの大きさが別物であること。raw と qcow2 の違い。

ふつうこう考える

仮想マシンに 20GiB のディスクを持たせるには、20GiB のファイルが要る。作るのにも時間がかかり、その分だけ空き容量が減るはずだ。

$ qemu-img create -f raw empty.raw 20G
Formatting 'empty.raw', fmt=raw size=21474836480
$ ls -l empty.raw
-rw-r--r-- 1 lab lab 21474836480 Oct 14 04:02 empty.raw
$ du -h empty.raw
4.0K    empty.raw
$ qemu-img create -f qcow2 empty.qcow2 20G
Formatting 'empty.qcow2', fmt=qcow2 cluster_size=65536 extended_l2=off compression_type=zlib size=21474836480 lazy_refcounts=off refcount_bits=16
$ ls -l empty.qcow2
-rw-r--r-- 1 lab lab 196928 Oct 14 04:02 empty.qcow2
$ head -c 4 empty.qcow2 | od -c
0000000   Q   F   I 373
0000004
$ rm empty.raw empty.qcow2
だめな理由: どちらも一瞬でできた。raw のほうは ls -l では 21474836480 バイト（20GiB）あるのに、実際に場所を取っているのは 4KiB（du）だけ。 qcow2 のほうは、ls -l でも 196928 バイト（192KiB）しかない。どちらも、中の OS から見れば 20GiB のディスクになる。 ディスクの大きさは「どこまで番地があるか」で、ファイルが持っているのは「書かれたところ」だけだった。 raw（raw 形式）は、ディスクの1バイト目から順にそのままファイルにした形式で、まだ書いていないところをファイルシステムの「穴」（スパースファイル）にしている。ls -l は最後の番地までの長さを、du は実際に割り当てた量を数えるので、2つが食い違う。 qcow2 は、ディスクを 64KiB の塊（cluster_size=65536）に分け、書かれた塊だけを自分の中に置く形式で、ファイルの頭には QFI と 0xfb（od では 8 進の 373）の4バイトの印がある。 最後の rm は片付けである。

du の 4.0K は、ボリュームを置いたファイルシステムによって変わることがある（QEMU が作るときに先頭の1区画だけ書く。穴を持てないファイルシステムなら 20G になる）。

rawqcow2
中身ディスクの中身を先頭から並べただけ書かれた 64KiB の塊と、どの塊がどこにあるかの表
書いていないところファイルシステムの穴（ファイルシステム任せ）そもそも持たない（形式が自分で管理する）
下に土台を重ねるできないできる（backing file）
中に状態を保存する（savevm）できないできる
他の道具で読むそのまま読める（ディスクの中身そのもの）qemu-img などで変換してから
たとえ: raw はページ番号だけ振った白紙のノートに近い。書いたページだけインクが要る。qcow2 は書いたページだけを綴じたバインダーで、目次に「何ページ目はここ」と書いてある。
ただし崩れる点: 白紙のノートは白紙でも紙の厚みがあるが、raw の穴は場所を取らない。その代わり、穴を知らない道具でコピーすると、穴が全部 0 で埋まって本当に 20GiB になる。 バインダーは書いたページしか綴じていないので、写しても大きくならない。ただし、後でページを抜いた跡がファイルの穴として残っていることがあり（この章の最後）、穴を知らない道具で写すと、そこは埋まる。

土台を汚さずに、練習機を起動する

この節で分かること: 読み取り専用の土台の上に、差分のディスクを重ねる方法。重ねた差分に何が入るか。

練習機のディスクを、そのまま QEMU に渡してみる。

$ qemu-system-x86_64 -drive file=/var/lib/lab-vm/linuc-guest.qcow2,if=virtio -display none
qemu-system-x86_64: -drive file=/var/lib/lab-vm/linuc-guest.qcow2,if=virtio: Could not open '/var/lib/lab-vm/linuc-guest.qcow2': Permission denied

QEMU は、渡されたディスクを書けるように開こうとして断られた。中の OS は起動のたびにログや時刻を書くので、ディスクは書ける必要がある。 そこで、土台の上に差分のディスクを重ねる。-b が土台（backing file）、-F がその形式である。

$ qemu-img create -f qcow2 -b /var/lib/lab-vm/linuc-guest.qcow2 -F qcow2 linuc.qcow2
Formatting 'linuc.qcow2', fmt=qcow2 cluster_size=65536 extended_l2=off compression_type=zlib size=21474836480 backing_file=/var/lib/lab-vm/linuc-guest.qcow2 backing_fmt=qcow2 lazy_refcounts=off refcount_bits=16
$ ls -l linuc.qcow2
-rw-r--r-- 1 lab lab 196928 Oct 14 04:02 linuc.qcow2
$ qemu-img info --backing-chain linuc.qcow2 | grep -E '^(image|virtual size|disk size|backing file):'
image: linuc.qcow2
virtual size: 20 GiB (21474836480 bytes)
disk size: 196 KiB
backing file: /var/lib/lab-vm/linuc-guest.qcow2
image: /var/lib/lab-vm/linuc-guest.qcow2
virtual size: 20 GiB (21474836480 bytes)
disk size: 527 MiB

できた linuc.qcow2 は、空の qcow2 と同じ 196928 バイトで、土台の中身は1バイトも写していない。--backing-chain を付けると、重なりを上から順にたどって見せる（差分 → 土台）。 差分のファイルの頭には土台のパスが書き込まれていて、QEMU は差分に無い塊を、そのパスのファイルから読む。

この差分ディスクで練習機を起動する。-m 1536 はメモリ（1.5GB）、-smp 2 は CPU を2つにする指定で、-drive の if=virtio はディスクを virtio の部品としてつなぐ（第1章）。 第2章のとおり、端末を壊さない -display none -serial mon:stdio にする。KVM を使わないので、ログインの案内が出るまで 30〜60 秒かかる。 出たら student でログインし（パスワードも student。打っても表示されない）、ディスクを見て、ファイルを1つ作ってから、モニタで電源ボタンを押す。

行の頭の [ 1.468290] は、カーネルが起動してからの秒数で、毎回違う。 練習機の中の表示（「この中でも lab check NN で…」）は他の記事の檻の案内で、この檻では使えない。

流れたのは、第1章の何も無い PC と同じ順番の続きである。GRUB（ディスクの中の起動のプログラム）が出て、Linux のカーネルが起動し、 DMI: QEMU Ubuntu 24.04 PC v2 (i440FX + PIIX, …) と、自分が動いている PC が QEMU の既定のマシン型であることを書き、 vda: vda1 vda14 vda15 vda16 と virtio のディスク（vda）の中の4つの区画を見つけた。lsblk でも、20GiB の vda として見える。 第1章の既定の部品のフロッピー（fd0）と CD-ROM（sr0）も、ここにいる。

止めるときに quit ではなく system_powerdown（電源ボタン）を使った。第2章と違い、今度は中に OS がいるので、ボタンを受け取った systemd が後片付けをして電源を切り（reboot: Power down）、 それを見た QEMU も終わった。quit だと、OS は後片付けをする暇が無い（次の節で、あえて使う）。

ログインの前後で、プロンプトが消えることがある: ログインの案内が出てしばらくすると（著者の記録では十数秒後）、練習機の中の systemd-fsckd（起動のときのファイルシステムの点検の進み具合をコンソールに出す係）が退場し、 そのときコンソール、つまりあなたの端末の、カーソルのある1行を空白で上書きする（著者が測ると、空白 51 個を \r で挟んだ並びで、それが流れた時刻は、練習機の記録（journal）にある systemd-fsckd の退場（Deactivated successfully）と同じ秒だった）。 当たった行が linuc login: や student@linuc:~$ だと、その文字が画面から消え、次に打った文字が行の頭から出る。 どの行に当たるかは、あなたの PC の速さと、打つまでの間で変わる。本文の記録では、ログインして最初に打った行が毎回これに当たり、プロンプトが消えている（記録はログインしてから 15 秒ほど待って打った）。消えて見えても、打ったものはそのまま届いている。

止まった後の差分ディスクと土台を見る。

$ sha256sum /var/lib/lab-vm/linuc-guest.qcow2

698763d45569b666a7c8e41ea4b34eec86d86a803c6c0c562d18c28059234c8d  /build/linuc-guest.qcow2

linuc.qcow2 の大きさは、起動のあいだに書かれた量で決まるので、毎回少し違う。

差分は 192KiB から 18.3MiB に増えた。1回の起動で、OS はログ・時刻の記録・パッケージの状態などを書き、作った hello.txt もその中にある。 土台の sha256 は、この檻を作ったときに記録した値（linuc-guest.sha256）と同じで、1バイトも変わっていない。 練習機が「書いた」ものは全部、土台の上に重ねた差分に入った。このサイトの仮想マシン型の檻の vm reset --yes は、この差分（と、UEFI の設定のファイル linuc_VARS.fd。第6章）を消して作り直すことで、練習機を工場出荷時に戻している。

たとえ: 差分ディスクは、図書館の本に貼った透明なシートに近い。メモはシートに書き、本そのものは汚さない。シートを剥がせば、本は元のまま。
ただし崩れる点: シートなら剥がして別の本に貼れるが、差分ディスクは決まった土台の上でしか意味を持たない（ファイルの頭に土台のパスが書いてある）。 土台を書き換えたり別のものに差し替えたりすると、差分は違う絵の上に重なった落書きになり、中の OS から見たディスクは壊れる。

-snapshot は、何も書き戻さない

この節で分かること: -snapshot を付けた起動では、書き込みがどこへ行くか。

名前から「スナップショットを取る」指定に見える -snapshot を付けて起動し、さっき作った hello.txt を消してから、今度はあえて quit（電源を抜く）で止める。

#block の後ろの数字と、/var/tmp/vl. の後ろの名前は毎回違う。この記録では、ログインの後の最初の rm hello.txt の行で、プロンプトが消えている（上の注）。

中の OS からは確かに消え（ls が何も出さない）、電源も抜いたのに、linuc.qcow2 は大きさも時刻も起動の前のままだった。 info block が理由を書いている。練習機のディスク（virtio0）の実体は /var/tmp/vl. で始まる名前の一時ファイルで、その土台が linuc.qcow2、さらにその土台が練習機の土台で、重なりは2段（chain depth: 2）になっていた。 -snapshot は「スナップショットを取る」ではなく、「その場で作った一時の差分に書かせ、QEMU が終わったら捨てる」指定である。 書き込みは一時ファイルに入った。この一時ファイルは、QEMU が開いた直後に名前を消してあり（動いている間も /var/tmp の一覧には出ず、/proc/PID/fd に (deleted) と付いて見える）、QEMU が終わると中身ごと消える。だから電源を抜いても壊れるものが無い（第2章の Ctrl-a s は、この一時の差分を下へ書き戻す操作）。

たとえ: -snapshot は、試験の下書き用紙に近い。どれだけ書き込んでも、答案（linuc.qcow2）には何も写らず、終わったら回収されて捨てられる。
ただし崩れる点: 下書きなら清書で写せるが、-snapshot の書き込みを残したいなら、捨てられる前に Ctrl-a s（またはモニタの commit）で書き戻すしかない。名前とは逆に、何もしなければ何も残らない。

savevm は、動いている状態ごとしまう

ID        TAG               VM SIZE                DATE     VM CLOCK     ICOUNT
--        clean             347 MiB 2026-10-14 04:05:44 00:00:53.821
(qemu) system_powerdown
（略）
[   65.876836] reboot: Power down

モニタの (qemu) は、2回目からは練習機のプロンプトの後ろに続けて出る（切り替えたときにカーソルがあった場所に出るため）。 VM SIZE・DATE・VM CLOCK は毎回違う。ここでも、ログインの後の最初の ls の行で、プロンプトが消えている。

-snapshot の起動で消した hello.txt は、残っていた（あの削除は一時ファイルごと捨てられた）。 savevm clean の後に消した hello.txt は、loadvm clean で戻った。戻ったのはファイルだけではない。 loadvm は、ディスクの中身と一緒に、メモリの中身・CPU のレジスタ・部品の状態を保存した瞬間に戻すので、練習機の中の OS は「ログインして ls を打った直後」の続きから動き出した。 info snapshots の VM SIZE（347MiB）が、保存した動いている状態（主にメモリの中身）の大きさで、VM CLOCK は練習機の電源を入れてから保存までの時間（54 秒）である。

$ qemu-img snapshot -l linuc.qcow2
Snapshot list:
ID        TAG               VM SIZE                DATE     VM CLOCK     ICOUNT
1         clean             347 MiB 2026-10-14 04:05:44 00:00:53.821
$ ls -l linuc.qcow2
-rw-r--r-- 1 lab lab 399638528 Oct 14 04:06 linuc.qcow2
$ qemu-img info linuc.qcow2 | grep '^disk size'
disk size: 381 MiB
$ qemu-img snapshot -d clean linuc.qcow2
$ ls -l linuc.qcow2
-rw-r--r-- 1 lab lab 399638528 Oct 14 04:06 linuc.qcow2
$ qemu-img info linuc.qcow2 | grep '^disk size'
disk size: 379 MiB

QEMU を止めた後でも、qemu-img snapshot -l で同じ一覧が読めた。保存したものは、どこか別の場所ではなく linuc.qcow2 というファイルの中にある（内部スナップショット）。 そのぶん、ファイルは 18.3MiB から 381MiB（399638528 バイト）に増えた。 qemu-img snapshot -d で消しても、ls -l の長さは変わらなかった。qcow2 は、ファイルを短くはしない。そのうえ、ここでは disk size（実際に場所を取っている量）も、381MiB が 379MiB になっただけだった。 ふつうは、消したスナップショットだけが使っていた塊を、qcow2 がファイルの穴に戻す（下のファイルシステムに「ここはもう要らない」と伝える。discard）ので、ls -l の長さは同じでも disk size は減る。 ここでほとんど減らなかったのは、loadvm clean で保存した瞬間に戻ったとき、保存した状態の塊を、いまのディスクも指すようになったからである（著者が loadvm をせずに消すと、351MiB が 7.63MiB に減った）。

たとえ: savevm はゲームのセーブに近い。持ち物（ディスク）だけでなく、いる場所や体力（メモリ・CPU）まで戻る。
ただし崩れる点: ゲームのセーブは別のファイルになるが、内部スナップショットはディスクのファイルそのものに入る。消すと場所はふつう返るが、loadvm でそのセーブに戻った後は、いまのディスクも同じ場所を使っているので返らない。 もう1つ、セーブはいつでもできるとは限らない。書き込める部品が全部 qcow2 でないと、savevm は断られる（第6章で、UEFI のファームウェアの設定のファイルがそれに当たる）。
手を動かす: 実践編の演習02は、自分の差分ディスクを作って練習機を起動し、正しく止める課題で、判定はディスクのファイルを qemu-img で読んで、土台と書き込みと「いま使われていないか」を確かめ、正しく止めたかを、ディスクの中の / のファイルシステムに「回復が要る」の印が残っていないかで見る。 演習03は、ログインした直後の練習機を savevm で保存する課題で、外から qemu-img snapshot -c で取ったもの（ディスクの中身だけ）と区別できるかを、判定が VM SIZE で見る。
確認

ls -l では 21474836480 バイト、du -h では 4.0K のファイルがある。このファイルについて何が言えるか。

答え

最後の番地までの長さは 20GiB だが、実際に割り当てられているのは 4KiB だけで、残りはファイルシステムの穴（スパースファイル）になっている。 読めば穴のところは 0 が返る。raw のディスクイメージを作った直後は、こうなる。穴を知らない道具でコピーすると、本当に 20GiB を使うファイルになる。

確認

-snapshot を付けて起動した練習機の中でファイルを消し、そのまま QEMU を終えた。次に -snapshot を付けずに同じディスクで起動すると、そのファイルはあるか。理由も。

答え

ある。-snapshot は、その場で作った一時の差分（/var/tmp に作って、すぐ名前を消した一時ファイル）に書き込みを流し、QEMU が終わるときに捨てる指定で、元のディスクには何も書かない。 info block で chain depth: 2（一時ファイル → 元のディスク → 土台）になっていたのが、その印。残したいなら終わる前に Ctrl-a s（モニタなら commit）で書き戻す。

確認

差分ディスク a.qcow2 の土台 base.qcow2 を、別のイメージで上書きしてしまった。a.qcow2 から起動するとどうなりうるか。

答え

壊れたディスクに見える。a.qcow2 は「書いた塊」しか持たず、残りは base.qcow2 の同じ番地を読む。土台の中身が別物になると、差分の塊と土台の塊が食い違い、ファイルシステムの表と中身が合わなくなる。 土台は読み取り専用にしておく（この檻の土台が root の持ち物で r--r--r-- なのはそのため）。

確認

info snapshots の VM SIZE が 347 MiB のスナップショットと、0 B のスナップショットがある。それぞれ、どうやって作られたものと考えられるか。

答え

347 MiB のほうは、動いている練習機のモニタで savevm したもので、メモリの中身などの動いている状態を持つ。loadvm すると保存した瞬間の続きに戻る。 0 B のほうは、ふつうは止まっているディスクに外から qemu-img snapshot -c で取ったもので、ディスクの中身だけを持つ。戻すと「電源を入れる前」の状態に戻る（演習03 の判定はこの違いを見る）。 ただし、savevm で取ったのに 0 B に見えることもある。savevm は動いている状態を、書き込める qcow2 のうち -drive で先に並べた1つにだけ入れるので、ほかの qcow2（たとえば UEFI の NVRAM。第6章）をディスクより先に並べていると、状態はそちらに入っている。

この章で分かったこと

持ち帰ってほしいこと

  • ディスクの大きさ（番地の数）と、ファイルの大きさ（書かれた量）は別物。raw はファイルシステムの穴で、qcow2 は自分の表で、書いていないところを持たない
  • qemu-img create -f qcow2 -b 土台 -F qcow2 差分 の差分は、書いた塊だけを持ち、残りは土台を読む。土台は1バイトも変わらない（sha256sum で確かめた）
  • QEMU はディスクを書ける形で開く。読み取り専用のファイルはそのまま渡せない
  • -snapshot は「一時の差分に書かせて、終わったら捨てる」。名前に反して何も保存しない
  • savevm はディスクと動いている状態（メモリ・CPU）を qcow2 の中にしまい、loadvm でその瞬間の続きに戻る。消しても ls -l の長さは縮まない（中身はふつう穴に戻るが、loadvm で戻った後は戻らない）
  • 中に OS がいれば system_powerdown で後片付けをしてから止まる。quit は電源を抜く
