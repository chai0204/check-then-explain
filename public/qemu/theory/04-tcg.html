4. CPU は、命令を翻訳して動いている

練習機の中で CPU の名前を見ると「QEMU Virtual CPU version 2.5+」と出る。そんな製品は無い。 同じ 20 万回のループが、外（コンテナ）では 0.3 秒、練習機の中では 6.5 秒かかった。 KVM を使わない QEMU は、練習機の CPU の命令をひと塊ずつ読んで、ホストの CPU の命令に翻訳してから実行している（TCG）。 特権が1つも要らない代わりに、遅い。その翻訳の跡は、QEMU のモニタと記録で見られる。

前提: 第3章までを同じ端末で終えている（~/work/linuc.qcow2 がある）所要 18分影響度 B最終検証 2026-10-14

この章のゴール

  • 練習機の CPU が、ホストの CPU ではなく QEMU が作った CPU に見えることを、/proc/cpuinfo で示せる
  • TCG が遅い理由を「命令の翻訳」で説明し、同じ処理の時間を外と中で測って比べられる
  • モニタの info jit と -d in_asm の記録から、TCG が命令を塊（TB）ごとに翻訳していることを読み取れる
  • 翻訳しない方法（KVM）が、この檻では使えない理由を、-accel の出力と /dev/kvm で言える
ここで覚えなくていいこと: TCG が使う中間の命令（TCG ops）、info jit の全項目の意味、x86 の機械語の読み方、 -d の他の項目（out_asm op exec）。KVM の使い方と速さの比べ方は KVM の記事に任せる。

同じ計算を、外と中で測る

この節で分かること: 練習機の中の CPU が何に見えるか。同じ計算にかかる時間の差。

まず外（コンテナ）で、CPU の名前と数を見て、20 万回数えるだけのループの時間を測る。

$ grep -m1 'model name' /proc/cpuinfo
model name      : Intel(R) Core(TM) Ultra 9 285H
$ nproc
16
$ time (i=0; while [ $i -lt 200000 ]; do i=$((i+1)); done)
real    0m0.272s
user    0m0.271s
sys     0m0.001s

CPU の名前・数・かかった時間は、あなたの PC で変わる（コンテナはホストの CPU をそのまま使うので、あなたの PC の CPU が出る）。

ふつうこう考える

仮想マシンの中のプログラムも、結局はこの PC の CPU で動いている。仮想化の手間で少しは遅くなっても、同じループなら、かかる時間はせいぜい数割増しのはずだ。 CPU の名前も、外と同じものが見えるはずだ。

第3章のディスクで練習機を起動し、中で同じことを打つ。ループが終わってプロンプトが戻ってから、Ctrl-a c でモニタに切り替える。

$ qemu-system-x86_64 -m 1536 -smp 2 -drive file=linuc.qcow2,if=virtio -display none -serial mon:stdio
                             GNU GRUB  version 2.12
（略）
Ubuntu 24.04.5 LTS linuc ttyS0

時間と info jit の数は、毎回違い、あなたの PC の速さでも変わる。この記録では、ログインの後の最初のコマンドの行でプロンプトが消えている（第3章の注）。

だめな理由: CPU の名前は「QEMU Virtual CPU version 2.5+」で、数は 2（-smp 2 で決めたとおり）。外の Intel の CPU は見えない。 そして同じループに 6.5 秒、外の約 24 倍かかった。数割増しどころではない。 練習機の中で動いている命令は、この PC の CPU が直接実行しているのではない。QEMU が練習機の命令をひと塊ずつ読み、同じ意味のホストの命令の列に翻訳し、その翻訳を実行している。 この仕組みを TCG（Tiny Code Generator）という。CPU の名前も QEMU が作った CPU のもので、第1章の -cpu help の既定（qemu64）である。

info jit は、その翻訳の作業場の様子である。

行読み方
TB count 650626翻訳の置き場所に、いまある塊（Translation Block）の数。約 65 万。下の TB flush count のとおり一度全部捨てているので、起動からの総数ではない
TB avg target size 181つの塊が、練習機の命令で平均 18 バイト（だいたい分岐の命令までの数個の命令）
TB avg host size 324 bytes (expansion ratio: 17.4)その塊を翻訳したホストの命令は平均 324 バイト。全部の塊を合わせると、元の 17.4 倍に膨らんでいる（平均の欄は小数を切り捨てた値）
gen code size 367596259/1073659904翻訳したホストの命令の置き場所（約 1GiB）のうち、約 350MiB を使っている
TB flush count 1置き場所を一度、全部捨てて作り直した（翻訳はやり直しになる）

翻訳には時間がかかるが、翻訳した塊は取っておき、同じ場所をもう一度通るときはそのまま使う（命令が書き換えられた所は、翻訳し直す）。だからループのように同じ命令を何度も通る処理は、2回目からは翻訳済みのものを実行するだけになる。 それでも、翻訳した命令はバイト数で元の 17 倍ほどの大きさになり、練習機の CPU の状態（レジスタやフラグ）を毎回メモリに読み書きするので、外より何倍も遅い。 起動に 30〜60 秒かかるのも同じ理由で、起動のあいだは初めて通る命令ばかりなので、翻訳そのものにも時間を取られる。

たとえ: TCG は、外国語の台本を場面ごとに訳してから演じる劇団に近い。一度訳した場面は訳本を取っておき、2回目からは訳本を見て演じる。
ただし崩れる点: 劇団の訳は人が読むためのものだが、TCG の訳はホストの CPU がそのまま実行する機械語で、しかもバイト数で元の 17 倍ほどになる。 同じ言葉を話せる役者（同じ種類の CPU）が直接演じれば訳は要らないのに、TCG は同じ x86 の命令でも律儀に訳す。直接演じさせる方法が KVM である（最後の節）。

翻訳の跡を見る

この節で分かること: TCG が最初に翻訳する命令がどこにあり、どんな形で記録されるか。

QEMU には、中で起きていることを記録に書き出す -d がある。項目の一覧の最初の2つが、翻訳の記録である。

$ qemu-system-x86_64 -d help | head -3
Log items (comma separated):
out_asm         show generated host assembly code for each compiled TB
in_asm          show target assembly code for each compiled TB

in_asm は「翻訳した塊（TB）ごとに、元の（target＝練習機の）命令を書く」項目である。ディスクの無い PC を5秒だけ動かし、書き出す先を -D でファイルにする。

$ timeout 5 qemu-system-x86_64 -display none -d in_asm -D tcg.log
qemu-system-x86_64: terminating on signal 15 from pid 250 (timeout)
$ head -9 tcg.log
----------------
IN:
0xfffffff0:
OBJD-T: ea5be000f0
----------------
IN:
0x000fe05b:
OBJD-T: 2e66833e2862000f8545f0
$ grep -c '^IN:' tcg.log
6054
$ rm tcg.log

塊の数（6054）は、5秒のうちにファームウェアがどこまで進むかで決まり、少し変わる（著者が続けて5回取ると 6054〜6056 だった）。PC の速さでも変わる。

「IN:」の1つが翻訳した1つの塊で、次の行がその塊の番地、OBJD-T: の後ろが命令のバイト列である（この Ubuntu の QEMU は、命令を読める形に直す部品を持たないので、バイトのまま出す）。

  • 最初の塊の番地は 0xfffffff0。386 以降の x86 の CPU は電源を入れた直後、必ずこの番地（4GiB の 16 バイト手前）から命令を読む（リセットベクタ。8086 は 0xffff0、80286 は 0xfffff0 だった）。そこにはファームウェアの ROM が見えている
  • そこにあったのは ea 5b e0 00 f0 の1命令で、「f000 の e05b へ跳べ」（遠くへのジャンプ）。だから2つ目の塊は 0x000fe05b（f000:e05b を番地にしたもの）で、ここからが SeaBIOS の本体
  • 5秒で 6054 個の塊を翻訳した。ファームウェアが初めて通る道は、すべて翻訳から始まる

本物の PC の CPU も同じ番地から始めるが、本物は ROM の命令をそのまま実行する。TCG は、その1命令目から翻訳している。

たとえ: リセットベクタは、新入社員が初日に必ず行く受付に近い。受付では仕事をせず、「3階（SeaBIOS の本体）へ」と案内されるだけ。
ただし崩れる点: 受付の場所は会社ごとに違うが、リセットベクタの番地は 386 以降の x86 の CPU なら全部同じで、本物の CPU も、QEMU が作った CPU も、必ずここから始まる。だから TCG の記録の1行目は、誰が取っても同じになる。

翻訳しない方法は、この檻では使えない

この節で分かること: 翻訳をしない方法（KVM）が何を要るか。それがこの檻に無いこと。
$ qemu-system-x86_64 -accel help
Accelerators supported in QEMU binary:
tcg
kvm
$ qemu-system-x86_64 -accel kvm -display none
Could not access KVM kernel module: No such file or directory
qemu-system-x86_64: -accel kvm: failed to initialize kvm: No such file or directory
$ qemu-system-x86_64 -cpu host -display none
qemu-system-x86_64: CPU model 'host' requires KVM or HVF
$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory

QEMU が命令を動かす方法（アクセラレータ）は2つ入っている。tcg（この章で見た翻訳）と kvm である。 KVM は Linux のカーネルの機能で、CPU の仮想化支援機能（Intel VT-x・AMD-V）を使い、練習機の命令をホストの CPU に直接実行させる。翻訳が要らないので、ループも起動もずっと速い。 ただし KVM は /dev/kvm という入口を通して頼むもので、この檻には渡していない（No such file or directory）。 ホストの CPU をそのまま見せる -cpu host も、KVM（macOS なら HVF）があるときにしか選べない。

この檻が KVM を使わないのは、読者に権限を求めないためと、どこでも同じ画面を出すためである。/dev/kvm を渡すには docker run に --device /dev/kvm を足す必要があり、 macOS や、入れ子の仮想化が無効な環境では、そもそも渡せない。そして KVM を使うと、練習機から見える CPU の製造元（vendor_id）や機能が読者の PC ごとに変わる（-cpu host を付ければ、名前もあなたの PC の CPU になる）。 このサイトの仮想マシン型の檻が起動に 30〜90 秒かかるのは、この TCG の翻訳のためで、その代わり誰の PC でも同じ練習機が同じ画面を出す。 KVM で同じ練習機を動かすとどうなるかは、KVM の記事で測っている。

たとえ: KVM は、同じ言葉を話せる役者に直接演じさせることに近い。訳す時間が要らない。
ただし崩れる点: 役者が直接演じられるのは自分の言葉（同じ種類の CPU）だけで、x86 の PC の上で ARM の練習機を動かすなら、やはり訳（TCG）が要る。 そして KVM が引き受けるのは CPU とメモリと、割り込みやタイマーの一部の部品（i8259・IOAPIC・PIT）までで、ディスクや NIC は KVM のときも QEMU が作っている（第1章のそれ以外の部品は、どちらでも同じ）。
手を動かす: 実践編の演習04は、この章の -d in_asm の記録を自分で取る課題である。判定は記録のファイルを読み、最初の塊がリセットベクタ 0xfffffff0 から始まっているか、塊がいくつあるかを見る。
確認

練習機の中で grep -m1 'model name' /proc/cpuinfo を打つと QEMU Virtual CPU version 2.5+ と出た。ここから何が言えるか。

答え

練習機に見えている CPU は、ホストの CPU ではなく、QEMU が作った CPU（既定の型 qemu64）である。 命令はホストの CPU が直接実行しているのではなく、QEMU が翻訳して実行している（KVM で -cpu host にすれば、ホストの CPU の名前が見える）。

確認

info jit に TB avg target size 18 と TB avg host size 324 bytes (expansion ratio: 17.4) と出た。何と何の比か。

答え

翻訳した1つの塊（TB）の大きさを、元の練習機の命令で測ると平均 18 バイト、翻訳したホストの命令で測ると平均 324 バイト。expansion ratio の 17.4 は、全部の塊の大きさの合計どうしの比である（平均の2つの欄は小数を切り捨てて出しているので、324÷18 とは少しずれる）。 翻訳すると、命令はバイト数で元の 17 倍ほどの大きさになる（命令の数の比ではない）。翻訳済みの塊は使い回すが、それでも外より何倍も遅い理由の1つである。

確認

-d in_asm の記録の最初の塊が、何度取っても 0xfffffff0 になるのはなぜか。

答え

386 以降の x86 の CPU は、電源投入（リセット）の直後に必ず 0xfffffff0 から命令を読む決まり（リセットベクタ）で、QEMU が作る CPU もそれに従う。 そこにあるファームウェアの最初の命令（f000:e05b へのジャンプ）が、TCG が最初に翻訳する塊になる。

確認

この檻で -accel kvm を付けると断られた。檻に何を足せば使えるようになるか。その代わりに何が変わるか。

答え

docker run に --device /dev/kvm を足して、KVM の入口を檻に渡す（ホストに KVM があり、使う権限があるときだけ）。 練習機の命令は翻訳されずにホストの CPU で直接動くので速くなるが、練習機から見える CPU の製造元や機能が読者の PC ごとに変わり（-cpu host なら名前も）、本文と同じ画面にはならない。詳しくは KVM の記事。

この章で分かったこと

持ち帰ってほしいこと

  • KVM を使わない QEMU（TCG）は、練習機の命令をひと塊（TB）ずつホストの命令に翻訳してから実行する。特権は要らないが遅い（この記録では同じループが約 24 倍）
  • 練習機に見える CPU は QEMU が作った CPU（既定は qemu64、「QEMU Virtual CPU version 2.5+」）
  • info jit は翻訳の作業場の統計、-d in_asm -D ファイル は翻訳した塊ごとの元の命令の記録。最初の塊はリセットベクタ 0xfffffff0
  • 翻訳しない方法は KVM（-accel kvm）で、/dev/kvm が要る。この檻とこのサイトの仮想マシン型の檻は、権限を求めず同じ画面を出すために使わない
