6. ファームウェアは、差し替えられるファイル

このサイトの練習機は、UEFI で起動するように作ってある。ところが第3章からずっと、QEMU の既定の BIOS（SeaBIOS）で起動していた。 ディスクに BIOS 用の入口と UEFI 用の入口が両方あるからだ。PC の最初のプログラム（ファームウェア）は、QEMU にとってはファイルの1つで、差し替えれば UEFI（OVMF）で起動する。 UEFI には2つのファイルが要る。読むだけのプログラムと、設定を書き込む NVRAM で、NVRAM は練習機の最初の起動で書き換わり、次の起動の道を変える。

この章のゴールと前提所要 25分
前提: 第5章までを同じ端末で終えている（~/work/linuc.qcow2 がある）所要 25分影響度 B最終検証 2026-10-14

この章のゴール

  • 練習機が BIOS と UEFI のどちらで起動したかを、/sys/firmware/efi で見分けられる
  • 1つのディスクが BIOS でも UEFI でも起動できる理由を、区画（BIOS boot・EFI System）の一覧で説明できる
  • -drive if=pflash で OVMF の2つのファイル（プログラムと NVRAM）を渡して UEFI で起動し、NVRAM のファイルが書き換わることを cmp と efibootmgr で示せる
  • UEFI が ESP の中のファイルを読んで起動すること、ESP の無いディスクでは起動できないことを示せる
  • NVRAM を raw で渡すと savevm が断られる理由を言える
ここで覚えなくていいこと: UEFI のブートの項目の書式（HD(15,GPT,…) の読み方）、shim と GRUB の分担、Secure Boot の鍵、 efibootmgr での項目の作り方・並べ替え、BIOS の MBR の中身。

UEFI 用の練習機は、BIOS でも起動していた

この節で分かること: いまの練習機が、どちらのファームウェアで起動しているか。そう見分ける方法。

ふつうこう考える

このサイトの練習機は UEFI で起動するように作った（libvirt の定義は UEFI のファームウェアを使う）。だから BIOS では起動しないし、 これまでの章で起動できていた練習機も、どこかで UEFI が使われていたはずだ。

第5章と同じ形で起動し、ssh で練習機の中を見る。

だめな理由: UEFI で起動した Linux には /sys/firmware/efi がある（ファームウェアが UEFI だと、カーネルがここに UEFI の情報を出す）。それが無い。 この練習機は、第3章からずっと BIOS（SeaBIOS）で起動していた。QEMU は、ファームウェアを指定しなければ SeaBIOS を使う（第1章）。 それでも起動できたのは、ディスクが2つの入口を持っているからである。区画の一覧に、BIOS 用の GRUB の続きが入る BIOS boot（vda14）と、 UEFI が使う EFI System（vda15。ESP。UEFI が読む起動のファイルが入る FAT の区画）が並んでいる。BIOS が読むのはディスクの先頭（MBR）だけで、そこに書いてある GRUB の入口が、続きを BIOS boot から読む。 BIOS はディスクの先頭から、UEFI は ESP から入り、入口の GRUB はそれぞれ別のものだが、どちらも同じ GRUB の設定（/boot/grub/grub.cfg）を読んで、同じカーネルを起動する。ESP は BIOS で起動しているいまも /boot/efi にマウントされているが、BIOS はそれを読まない。
たとえ: 練習機のディスクは、表玄関と勝手口の両方がある家に近い。BIOS は勝手口（ディスクの先頭と BIOS boot）から、UEFI は表玄関（ESP）から入り、奥の部屋（GRUB の設定とカーネル）は同じ。
ただし崩れる点: 家ならどちらの扉から入ったか住人には分からないが、練習機の Linux には分かる（/sys/firmware/efi の有無）。 そして入ったファームウェアによって、OS が使える機能が変わる（UEFI の変数を読み書きする efibootmgr は、BIOS で起動したときは使えない）。

UEFI で起動する: 2つのファイル

この節で分かること: OVMF に渡す2つのファイルの役割。UEFI が何を読んで起動するか。NVRAM が書き換わること。

UEFI のファームウェアは、OVMF（仮想マシン用の UEFI）として入っている。渡すのは2つのファイルである。

  • /usr/share/OVMF/OVMF_CODE_4M.fd … UEFI のプログラム。読むだけ（readonly=on）
  • /usr/share/OVMF/OVMF_VARS_4M.fd … NVRAM（UEFI がブートの項目などの設定を書き込む場所）のひな形。書き換わるので、自分の写しを作って渡す

どちらも、仮想の PC のフラッシュメモリ（if=pflash）としてつなぐ。実機のマザーボードで、ファームウェアと設定が載っている部品に当たる。

$ cp /usr/share/OVMF/OVMF_VARS_4M.fd vars.fd
$ qemu-system-x86_64 -machine q35 -m 1536 -smp 2 -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE_4M.fd -drive if=pflash,format=raw,file=vars.fd -drive file=linuc.qcow2,if=virtio -netdev user,id=n0,hostfwd=tcp:127.0.0.1:2222-:22 -device virtio-net-pci,netdev=n0,addr=0x10 -display none -serial file:serial.log -qmp unix:qmp.sock,server=on,wait=off -daemonize
$ until ssh -o ConnectTimeout=3 linuc true 2>/dev/null; do sleep 3; done

BootCurrent: 0001 は、いまの起動が Boot0001 から来たこと。写しの元にしたまっさらな NVRAM のひな形には、ブートの項目が1つも無い。 0000〜0006 は、起動のときに OVMF が自分で作った項目で、UEFI の設定の画面（0000 の UiApp）、ディスク（0001）、NIC からのネットワーク起動（0002〜0005。第1章の iPXE に当たる UEFI の仕組み）、UEFI のシェル（0006）が並ぶ（つながった装置から作った 0001〜0005 には {auto_created_boot_option} の印が付いている）。 Boot0007* Ubuntu だけは、OVMF ではなく練習機の側が書き込んだ項目で、しかも並び順（BootOrder）の先頭にいる。

UEFI は、NVRAM に項目の無いディスクでは、ESP の決まった場所 \EFI\BOOT\BOOTX64.EFI を読む（Boot0001 の「UEFI Misc Device」はそれ）。 練習機の ESP のそこには、Ubuntu の起動の入口（shim）が置かれている（/boot/efi は root しか読めない設定なので sudo で見た）。 その shim が、隣の fbx64.efi（fallback）を使って ESP の \EFI\ubuntu\ を調べ、「Ubuntu」という項目を NVRAM に書き込んだのが Boot0007 である。 練習機の最初の UEFI の起動で、NVRAM が書き換わった。書き換わった先は、渡した vars.fd というファイルのはずである。

止める前に、第3章の savevm を試した（QMP の human-monitor-command は、HMP の命令をそのまま QMP で送る入れ物）。 断られた。pflash1（2つ目のフラッシュ、つまり vars.fd）が「書き込めるのに、スナップショットに対応していない」。 savevm は、書き込める部品の中身を全部いっしょに保存できないと、保存しない。NVRAM は、練習機が書き込むディスクの1つとして数えられていて、raw のファイルでは中にスナップショットをしまえない。 NVRAM を qcow2 にして渡せば（qemu-img convert -O qcow2 vars.fd vars.qcow2 で写し、format=qcow2 でつなぐ）、savevm は通る（著者は試して通ることを確かめた）。 ただし、動いている状態（メモリの中身）は、書き込める qcow2 のうち -drive で先に並べた1つにだけ入り、この章の並べ方（NVRAM が先）では vars.qcow2 のほうに入った。練習機のディスクの側には、VM SIZE が 0 B のスナップショットの印だけが残る（著者の記録で、vars.qcow2 の側が 395MiB、ディスクの側が 0 B）。

止めた後、vars.fd をひな形と比べると、101 バイト目から違っていた。練習機の起動が、このファイルを書き換えたのである。

たとえ: OVMF の2つのファイルは、電話交換機と電話帳に近い。交換機（プログラム）は誰の家でも同じなので共有し、電話帳（NVRAM）は家ごとに書き込まれるので、家ごとに1冊持つ。
ただし崩れる点: 電話帳は人が自分で書くが、NVRAM はファームウェアや OS（shim や GRUB を入れる道具）が勝手に書き込む。読者は何もしていないのに、最初の起動で中身が変わった。 そして電話帳は紙なので写せば済むが、NVRAM はディスクと同じ扱いで、raw のままでは savevm を止める。

書き換わった NVRAM が、次の起動の道を変える

ESP の無いディスクを、UEFI に渡す

この節で分かること: UEFI がディスクから起動するのに、何が要るか。

最後に、何も書いていない 1GiB のディスクを UEFI に渡し、20 秒だけ動かす。NIC は付けない（-nic none。付けるとネットワーク起動を長く試す）。NVRAM も新しいひな形の写しにする。

UEFI はディスク（Boot0001）を試し、Not Found（起動するファイルが見つからない）で次へ進み、UEFI 自身のシェル（Shell>）を起動して止まった。 空のディスクには区画も ESP も無いので、\EFI\BOOT\BOOTX64.EFI が読めない。UEFI はディスクの先頭のプログラムを実行するのではなく、ESP（FAT）の中のファイルを読む。 第1章の SeaBIOS が空のディスクで「Boot failed: could not read the boot disk」と言ったのと、探しているものが違う。最後の rm は片付けである。

SeaBIOS（BIOS）OVMF（UEFI）
QEMU への渡し方何も指定しない（既定）-drive if=pflash でプログラムと NVRAM の2つ（-bios OVMF.fd なら NVRAM を持ち越さない1つ）
ディスクの何を読むか先頭（MBR）の起動のプログラムESP（FAT の区画）の中の .efi ファイル
どこから起動するかの設定既定の順（ハードディスク・フロッピー・CD・ネットワーク。QEMU の -boot で変えられる）NVRAM のブートの項目と BootOrder（OS からも書き換えられる）
Linux から見た印/sys/firmware/efi が無い/sys/firmware/efi がある。efibootmgr が使える
練習機のディスクvda14（BIOS boot）と MBR から入るvda15（ESP）の shim から入る
たとえ: UEFI は郵便受けまでしか来ない配達員に近い。家の中（ディスクの先頭）には入らず、郵便受け（ESP）にある決まった封筒（.efi ファイル）を取って帰る。
ただし崩れる点: 郵便受けは家に1つだが、ディスクに ESP がいくつあってもよく、どれのどのファイルを読むかは NVRAM の項目が指す。 項目が無いときにだけ、決まった封筒（\EFI\BOOT\BOOTX64.EFI）を探す。
手を動かす: 実践編の演習06は、自分の差分ディスクと自分の vars.fd で練習機を UEFI で起動する課題である。 判定は、vars.fd を開いている QEMU を /proc で探し、ssh で入って /sys/firmware/efi と efibootmgr を見て、vars.fd に「Ubuntu」の項目が書き込まれたかを読む。
確認

練習機の中で ls /sys/firmware/efi が No such file or directory になった。それでも /boot/efi には ESP がマウントされている。どちらのファームウェアで起動したか。なぜ ESP があるのか。

答え

BIOS（QEMU なら既定の SeaBIOS）。/sys/firmware/efi は UEFI で起動したときだけ現れる。 ESP は、同じディスクを UEFI でも起動できるように用意された区画で、BIOS で起動したときも OS は普通の FAT の区画としてマウントする。BIOS 自身は ESP を読まない。

確認

OVMF の NVRAM に、ひな形 /usr/share/OVMF/OVMF_VARS_4M.fd を直接渡すとどうなるか。写しを作る理由は何か。

答え

この檻では、ひな形は root の持ち物で書き込めないので、QEMU が開けずに起動しない（Permission denied）。書き込めたとしても、ひな形そのものが書き換わり、次に別の仮想マシンが同じひな形から始めるときに、前の仮想マシンの項目が残る。 NVRAM は仮想マシンごとの設定なので、仮想マシンごとに写しを持つ（libvirt も、仮想マシンごとに _VARS.fd を作る）。

確認

UEFI の練習機で savevm を打ったら Device 'pflash1' is writable but does not support snapshots と断られた。何が足りないのか。

答え

savevm は、書き込める部品の中身をすべて一緒に保存する。NVRAM（pflash1）も書き込める部品で、raw のファイルでは中に保存できない。 NVRAM を qcow2 にして（qemu-img convert -O qcow2）format=qcow2 で渡せば通る。ただし動いている状態は、-drive で先に並べた書き込める qcow2 に入る。この章の並べ方（NVRAM が先）なら NVRAM の qcow2 のほうに入り、練習機のディスクの側は VM SIZE が 0 B に見える。

確認

同じ vars.fd で2回起動すると、1回目は Boot0001 "UEFI Misc Device"、2回目は Boot0007 "Ubuntu" から起動した。何が変わったのか。

答え

vars.fd（NVRAM）の中身。1回目は、項目の無いディスクとして ESP の \EFI\BOOT\BOOTX64.EFI（shim）を読み、shim の fallback が「Ubuntu」の項目を NVRAM に書き込んで、並び順の先頭に置いた。 2回目は、その項目に従って \EFI\ubuntu\shimx64.efi を読んだ。ディスクは同じでも、ファームウェアの設定のファイルが変わると、起動の道が変わる。

この章で分かったこと

持ち帰ってほしいこと

  • QEMU のファームウェアは差し替えられるファイル。既定は SeaBIOS（BIOS）で、UEFI にするには OVMF を渡す
  • 練習機のディスクは BIOS 用の入口（MBR と BIOS boot の区画）と UEFI 用の入口（ESP）の両方を持つので、どちらでも起動する。どちらで起動したかは /sys/firmware/efi で分かる
  • OVMF は2つのファイルで渡す。プログラム（読むだけ）と NVRAM（書き換わる。仮想マシンごとに写しを持つ）
  • UEFI は ESP の中の .efi ファイルを読む。NVRAM に項目が無ければ \EFI\BOOT\BOOTX64.EFI を探し、ESP が無ければ起動できない
  • 練習機の最初の UEFI の起動で、NVRAM のファイルに「Ubuntu」の項目が書き込まれ、次からはそれで起動する。NVRAM も書き込める部品なので、raw のままだと savevm を止める
