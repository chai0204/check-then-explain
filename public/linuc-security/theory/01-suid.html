1. SUID は、実行する人ではなく持ち主で動く

システムを監査する最初の一歩は、find で特別な権限を持つファイルを洗い出すことである。ところが素朴に find / -perm 4000 と打つと、1つも見つからない。SUID ファイルはこの練習機に15個あるのに、である。原因は「ちょうど」と「含む」の違いにある。

この章のゴールと前提所要 15分
前提: なし前提: 練習機が起動している所要 15分影響度 B出題範囲 1.10.1（重要度3）最終検証 2026-10-13

この章のゴール

  • find -perm 4000 と -perm -4000・-perm /6000 の違いを説明できる
  • SUID/SGID が「実行する人」ではなく「ファイルの持ち主・グループ」の権限で動くことを言える
  • s と S の違い、SUID がシェルスクリプトには効かないことを説明できる
ここで覚えなくていいこと: ケーパビリティ（getcap／setcap）による細かい権限分割、AppArmor や SELinux の強制アクセス制御はレベル1の範囲外である。ここでは伝統的な SUID/SGID・スティッキービットの3つだけを扱う。

「ちょうど 4000」では1つも見つからない

この節で分かること: -perm の数値が「完全一致」か「ビットを含む」かで結果が変わること。

SUID ビットは 8 進で 4000 である。ならばと、その数で探してみる。

ふつうこう考える

SUID ファイルを全部出したいのだから、-perm 4000 と書けばよい。SUID = 4000 なのだから、これで漏れなく出るはずだ。

$ sudo find / -xdev -perm 4000 -type f 2>/dev/null | wc -l
0
だめな理由: 0 件。1つも出ない。-perm 4000 は「モードがちょうど 4000」という意味で、 所有者の読み書き実行も、他人の読み実行も、何も立っていないファイルだけが対象になる。 実在する SUID ファイルは -rwsr-xr-x（8進で 4755）のように他のビットも立っているので、どれも「ちょうど 4000」ではない。 欲しいのは「4000 のビットを含む」で、それには先頭に - を付ける。
$ sudo find / -xdev -perm -4000 -type f 2>/dev/null
/usr/bin/umount
/usr/bin/newgrp
/usr/bin/sudo
/usr/bin/gpasswd
/usr/bin/passwd
/usr/bin/su
/usr/bin/mount
/usr/bin/at
/usr/bin/fusermount3
/usr/bin/chsh
/usr/bin/chfn
/usr/lib/dbus-1.0/dbus-daemon-launch-helper
/usr/lib/openssh/ssh-keysign
/usr/lib/polkit-1/polkit-agent-helper-1
/usr/local/bin/catfile
$ sudo find / -xdev -perm -4000 -type f 2>/dev/null | wc -l
15
$ sudo find / -xdev -perm -u+s -type f 2>/dev/null | wc -l
15
$ sudo find / -xdev -perm /6000 -type f 2>/dev/null | wc -l
22

15 個出た。-4000 は「このビットが立っていれば、他がどうでも一致」という読み方である。記号で -perm -u+s と書いても同じ 15 個になる。SGID（2000）なら -2000、SUID と SGID のどちらかなら /6000（/ は「いずれかのビット」）。/6000 が 22 個なのは、SUID の15個に SGID だけのファイルが加わるからである（/usr/bin/at は両方立っているので1回だけ数える）。

書き方意味
-perm 4000モードがちょうど 4000（実在しない）
-perm -4000 ／ -perm -u+s4000 のビットをすべて含む（＝ SUID が立っている全部）。記号でも書ける
-perm -2000SGID が立っている全部
-perm /6000SUID か SGID のいずれかが立っている
たとえ: 「赤い服の人」を探すのに、-perm 4000 は「赤い服だけを着て、ほかに何も身につけていない人」を探している。 -perm -4000 は「赤い服を着ている人（ほかに何を着ていてもよい）」である。
ただし崩れる点: 服は目で見れば分かるが、モードは複数のビットの重なりなので、人間には「含む」のほうが直感に反する。だから素朴な 4000 で空振りする。

誰が実行しても、持ち主の権限になる

この節で分かること: SUID の s が「実行時に持ち主の権限になる」印であること。

一覧に見慣れない /usr/local/bin/catfile がいた。これが監査で見つけたいものである。

$ ls -l /usr/local/bin/catfile
-rwsr-xr-x 1 root root 39384 Oct 13 19:25 /usr/local/bin/catfile
$ id
uid=1000(student) gid=1000(student) groups=1000(student),4(adm),27(sudo)
$ /usr/local/bin/catfile /etc/shadow | head -2
root:*:20701:0:99999:7:::
daemon:*:20701:0:99999:7:::
$ ls -l /etc/shadow
-rw-r----- 1 root shadow 1026 Oct 13 19:25 /etc/shadow

自分は一般ユーザ student（uid 1000）なのに、一般ユーザには読めないはずの /etc/shadow（この練習機では 640・root:shadow）が読めてしまった。catfile は cat の複製で、持ち主が root、そこに SUID（-rws の s）が立っている。SUID が立った実行ファイルは、誰が起動しても「ファイルの持ち主」の権限で動く（実効ユーザ ID が持ち主になる）。だから持ち主が root の catfile は、student が起動しても root としてファイルを読む。

/usr/bin/passwd が SUID なのも同じ理由である。一般ユーザが自分のパスワードを変えるには、一般ユーザには書けない /etc/shadow を更新する必要がある。だから passwd に SUID を付けて、実行の間だけ root の権限を借りる。SUID は「必要な一瞬だけ権限を貸す」仕組みで、だからこそ持ち主が root の SUID が増えていないかを監査する。

たとえ: 合鍵付きの代行サービスに近い。依頼主（student）が誰であっても、代行業者（catfile）は自分が持っている鍵（root の権限）で金庫（/etc/shadow）を開ける。
ただし崩れる点: 代行業者は依頼内容を選べるが、SUID プログラムは中身のコード次第で何でもしてしまう。cat の複製なら「何でも読める」になる。

SUID はシェルスクリプトには効かない

この節で分かること: カーネルがスクリプトの SUID を無視すること。

では、id を実行するだけのシェルスクリプトに SUID を付けたらどうなるか。root 権限で動くなら euid=0 が出るはずである（! を含むのでシングルクォートで書く。ダブルクォートだと対話シェルの履歴展開で event not found になる）。

$ printf '#!/bin/bash\nid\n' | sudo tee /usr/local/bin/wrap.sh >/dev/null
$ sudo chmod 4755 /usr/local/bin/wrap.sh; ls -l /usr/local/bin/wrap.sh
-rwsr-xr-x 1 root root 15 Oct 13 19:25 /usr/local/bin/wrap.sh
$ /usr/local/bin/wrap.sh
uid=1000(student) gid=1000(student) groups=1000(student),4(adm),27(sudo)

s は確かに立っているのに、uid=1000(student) のままで root になっていない。Linux のカーネルは、スクリプト（#! で始まるテキスト）の SUID を無視する。スクリプトは実体がインタプリタ（/bin/bash）で、途中で中身を差し替える余地があり危険だからである。SUID が効くのはコンパイルされた実行ファイルだけだと覚えておく。

ビットの見え方も押さえる。実行権の有無で s と S が変わる。

$ sudo chmod 4644 /usr/local/bin/wrap.sh; ls -l /usr/local/bin/wrap.sh
-rwSr--r-- 1 root root 15 Oct 13 19:25 /usr/local/bin/wrap.sh
$ sudo chmod 2755 /usr/local/bin/wrap.sh; ls -l /usr/local/bin/wrap.sh
-rwxr-sr-x 1 root root 15 Oct 13 19:25 /usr/local/bin/wrap.sh
$ sudo rm /usr/local/bin/wrap.sh

試したスクリプトは消しておく（残すと、この後の -perm -2000 の一覧に1行増える）。

表示意味
-rwsr-xr-xSUID あり＋所有者に実行権あり（小文字 s）
-rwSr--r--SUID あり＋所有者に実行権なし（大文字 S。効かない状態）
-rwxr-sr-xSGID あり＋グループに実行権あり（グループ側の s）

大文字 S は「ビットは立っているが、実行ビットが無いので宙に浮いている」印である。小文字なら効いている。

たとえ: s と S は、エンジンのかかった車（s）と、鍵は挿さっているがエンジンの切れた車（S）の違いに近い。どちらも鍵（SUID ビット）はあるが、走る（権限が効く）のは実行権のあるほうだけである。
ただし崩れる点: 車はひと目で動くか分かるが、S は chmod の指定ミスで意図せず生まれることが多く、見落としやすい。

SGID とスティッキービットも同じ読み方

この節で分かること: ディレクトリに付く s と t の意味。
$ ls -ld /tmp /var/mail
drwxrwxrwt 10 root root 4096 Oct 13 19:25 /tmp
drwxrwsr-x  2 root mail 4096 Sep  5 20:14 /var/mail
$ sudo find / -xdev -perm -2000 -type f 2>/dev/null
/usr/bin/ssh-agent
/usr/bin/at
/usr/bin/crontab
/usr/bin/chage
/usr/bin/expiry
/usr/lib/x86_64-linux-gnu/utempter/utempter
/usr/sbin/unix_chkpwd
/usr/sbin/pam_extrausers_chkpwd

/tmp の末尾の t がスティッキービット。誰でも書けるディレクトリだが、自分が作ったファイルしか消せないようにする（他人のファイルを消せない）。/var/mail の s はSGIDで、ここに作られるファイルのグループが mail に揃う。ファイルに付く SGID は「グループの権限で動く」、ディレクトリに付く SGID は「中のファイルのグループを継承させる」で、意味が変わる。SGID のファイルには chage・unix_chkpwd（グループ shadow で /etc/shadow を読む）や ssh-agent が並ぶ。

たとえ: スティッキービットは、共用の冷蔵庫に「自分のものには名前を書く。他人のものは捨てない」という貼り紙をするのに近い。置くのは自由だが、捨てられるのは自分のぶんだけである。
ただし崩れる点: 貼り紙は人の良識に頼るが、スティッキービットはカーネルが強制する。root だけは例外で全部消せる。

棚卸しで見つけたら、ビットだけ外す

この節で分かること: 不要な SUID の外し方。

監査で見つけた catfile の SUID を外す。ファイルごと消さず、ビットだけ落とす（u-s）。

$ sudo chmod u-s /usr/local/bin/catfile; ls -l /usr/local/bin/catfile
-rwxr-xr-x 1 root root 39384 Oct 13 19:25 /usr/local/bin/catfile
$ /usr/local/bin/catfile /etc/shadow
/usr/local/bin/catfile: /etc/shadow: Permission denied

s が x に戻り、一般ユーザでは /etc/shadow が読めなくなった。これが監査の目的である。「いま実際にどのファイルが特別な権限を持っているか」を数え、身に覚えのないものを無効化する。

手を動かす: 実践編の演習01が、この棚卸しと無効化をそのまま行う課題である。判定は、練習機の中で catfile の SUID が落ちているかを実際に見る。この章のとおりに打った後なら、演習01 はそのまま達成になる（自力で解きたいなら、この章を打つ前に演習から始める。やり直しは外の端末で vm reset --yes）。
確認

システムの SUID ファイルを漏れなく一覧したい。正しいのはどれか。

ア find / -perm 4000 -type f　イ find / -perm -4000 -type f　ウ find / -perm 755 -type f

答え

イ。-perm 4000（ちょうど一致）は他のビットも立った実在の SUID に当たらず 0 件になる。 「4000 のビットを含む」の -perm -4000 を使う。SGID は -perm -2000、どちらかは -perm /6000。

確認

ls -l で -rwSr--r--（大文字 S）と出た。どういう状態か。

答え

SUID ビットは立っているが、所有者に実行権（x）が無いので効いていない状態。 小文字 s なら実行権があり効いている。chmod 4644 のように実行権を落とすとこうなる。

確認

id を実行するだけのシェルスクリプトに chmod 4755 を付けた。一般ユーザが実行すると euid はどうなるか。

答え

root にならない（uid も実効ユーザも実行者のまま）。カーネルはシェルスクリプトの SUID を無視する。 効くのはコンパイル済みの実行ファイルだけ。

この章で分かったこと

持ち帰ってほしいこと

  • find -perm 4000 は「ちょうど」なので空振りする。棚卸しは「含む」の -perm -4000（SGID は -2000、いずれかは /6000）
  • SUID/SGID は「実行する人」ではなく「ファイルの持ち主・グループ」の権限で動く。だから持ち主 root の SUID は誰が動かしても root になる
  • s は効いている、S は実行ビットが無く宙に浮いている
  • カーネルはシェルスクリプトの SUID を無視する。効くのはコンパイル済みの実行ファイルだけ
  • ディレクトリの t はスティッキービット（自分のファイルしか消せない）、ディレクトリの s はグループの継承
