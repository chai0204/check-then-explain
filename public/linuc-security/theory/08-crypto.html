8. 鍵は、持ち主で非対称になっている

公開鍵暗号では、鍵が2つで一対になっていて、役割が非対称だ。公開鍵で暗号化したものは秘密鍵でしか開けず、秘密鍵で署名したものは公開鍵で検証できる。そして「鍵は長いほど安全」とは限らない——ed25519 は公開鍵がわずか 86 バイト、生成は一瞬なのに、4096 ビットの RSA と同等以上に安全である。

前提: 第7章まで読了前提: 練習機が起動している所要 18分影響度 C出題範囲 1.10.3（重要度3）最終検証 2026-10-13

この章のゴール

  • 公開鍵暗号の非対称性（暗号化⇔復号、署名⇔検証）を説明できる
  • ssh-keygen の3つのアルゴリズム（rsa/ecdsa/ed25519）の違いを言える
  • ssh-agent・SSH ポート転送・gpg の基本の流れを説明できる
ここで覚えなくていいこと: 楕円曲線の数学、証明書認証局（CA）による SSH 証明書、gpg の信頼の輪（web of trust）の細部はレベル1では深追いしない。ここでは「鍵を作る・使う・片方でしか開けない」という骨格だけを扱う。

長い鍵ほど安全、ではない

この節で分かること: 3つのアルゴリズムの鍵の大きさと生成コスト。

ssh-keygen -t でアルゴリズムを選んで鍵を3種類作る。

$ ssh-keygen -q -t rsa     -b 4096 -N "" -f /tmp/k_rsa   -C demo; echo rsa_done
rsa_done
$ ssh-keygen -q -t ecdsa   -b 521  -N "" -f /tmp/k_ecdsa -C demo; echo ecdsa_done
ecdsa_done
$ ssh-keygen -q -t ed25519         -N "" -f /tmp/k_ed    -C demo; echo ed_done
ed_done

ふつうこう考える

暗号は鍵が長いほど安全なのだから、-b 4096 の RSA が一番強い。鍵の大きさを比べれば、どれが頑丈かが分かるはずだ。

$ wc -c /tmp/k_rsa.pub /tmp/k_ecdsa.pub /tmp/k_ed.pub
 730 /tmp/k_rsa.pub
 258 /tmp/k_ecdsa.pub
  86 /tmp/k_ed.pub
だめな理由: RSA の公開鍵は 730 バイト、ed25519 はわずか 86 バイト。 だが 86 バイトの ed25519 のほうが、4096 ビットの RSA と同等以上に安全とされる。 鍵の強さは「ビット長の数字」ではなくアルゴリズムで決まり、別々のアルゴリズムのビット数は直接比べられない。 ed25519 は楕円曲線を使うので、短い鍵で高い強度が出る。おまけに生成も段違いに速い （著者の練習機では RSA 4096 の生成に数秒かかり、ed25519 は一瞬だった。TCG の遅いエミュレーションだと差が目に見える）。 いま新しく作るなら ed25519 が既定の選択で、RSA を使うのは古い機器との互換が要るときである。
アルゴリズム種類公開鍵の大きさいつ使う
ed25519楕円曲線（Ed25519）最小（86 バイト）いまの既定。迷ったらこれ
ecdsa楕円曲線（NIST 曲線）中（258 バイト）ecdsa が要る環境
rsa素因数分解大（4096 ビットで 730 バイト）古い機器との互換
たとえ: 鍵の長さと強度は、錠前の種類と鍵のギザギザの本数の関係に近い。同じ種類の錠前ならギザギザが多いほど強いが、種類が違えば本数での比較は無意味——ダイヤル錠の桁数とシリンダー錠の溝数を比べても意味がないのと同じ。
ただし崩れる点: 錠前の強度は破る時間で測れるが、暗号の強度は「現実的な時間で破れない」という前提の上にあり、将来の計算機（量子計算機など）で前提が変わりうる。

ssh-agent は、鍵を一度だけ開けておく

この節で分かること: パスフレーズを何度も打たずに済ませる仕組み。

秘密鍵にパスフレーズを付けると安全だが、ssh のたびに打つのは面倒である。そこで、鍵をメモリ上で一度だけ開いて預かる常駐が ssh-agent である。以後の ssh はエージェントに署名を頼み、パスフレーズを打ち直さずに済む。鍵を預けるのが ssh-add である。

$ eval $(ssh-agent -s)
$ ssh-add /tmp/ak
Identity added: /tmp/ak (agentdemo)

ssh-agent -s は環境変数（SSH_AUTH_SOCK など）を出力するだけなので、eval $(…) でいまのシェルに取り込む必要がある。これを忘れて ssh-agent とだけ打つと、変数が設定されず、ssh-add が「エージェントに接続できない」と言う。預けた鍵は ssh-add -l で一覧でき、ログアウトでエージェントごと消える。

たとえ: ssh-agent は、建物に入るたびに金庫を開け直さずに済むよう、その日の間だけ鍵を預かる受付に近い。朝に一度だけ本人確認（パスフレーズ）をすれば、あとは受付が代わりに開ける。
ただし崩れる点: 受付は建物内の全員が共有するが、ssh-agent はそのログインセッション専用で、eval で取り込んだシェルとその子だけが使える。別の端末には引き継がれない。

ポート転送は、トンネルの出口を手元に作る

この節で分かること: ssh -L が何を手元に持ってくるか。

練習機の中では 2323（第4章の echo）が動いている。だが外側のホストから直接は触れない（外に転送しているのは 22 だけ）。試すと接続を拒否される。

$ timeout 2 bash -c "exec 3<>/dev/tcp/127.0.0.1/2323 && head -1 <&3" 2>&1; echo rc=$?
bash: connect: Connection refused
bash: line 1: /dev/tcp/127.0.0.1/2323: Connection refused
rc=1

ここで ssh -L を使う。-L 19999:127.0.0.1:2323 は「手元の 19999 番に来たものを、ssh の暗号トンネルを通して練習機側の 127.0.0.1:2323 へ届ける」という意味である。

$ ssh -f -N -L 19999:127.0.0.1:2323 linuc; sleep 1; echo tunnel_up
tunnel_up
$ timeout 3 bash -c "exec 3<>/dev/tcp/127.0.0.1/19999 && head -1 <&3"
linuc-echo

手元の 19999 に繋ぐと、練習機の中の echo サービスが linuc-echo と返した。外からは見えないサービスに、ssh のトンネル越しに手元から届いた。これが -L（ローカル転送）である。逆向きに「リモート側に手元のサービスを見せる」のが -R である。

たとえ: ssh -L は、本社（練習機）の内線にしか繋がっていない電話に、自宅（手元）に引いた専用線を通して外から掛けるのに近い。専用線（ssh トンネル）の中は暗号化されている。
ただし崩れる点: 専用線は物理的に1本だが、ssh -L はトンネルの中に何本でも論理的な転送を通せる。出口はあくまで ssh の相手側から見た宛先である。

GnuPG は、公開鍵で暗号化し秘密鍵で復号する

この節で分かること: gpg の鍵束と、暗号化⇔復号の一往復。

gpg で鍵を作る。ssh の鍵とは別で、ファイルの暗号化や署名に使う。

$ gpg --batch --pinentry-mode loopback --passphrase "" --quick-gen-key "Deploy <deploy@linuc.example>"
$ gpg -k
/home/deploy/.gnupg/pubring.kbx
-------------------------------
pub   ed25519 2026-10-13 [SC] [expires: 2029-10-12]
uid           [ultimate] Deploy <deploy@linuc.example>
sub   cv25519 2026-10-13 [E]

pub が主鍵（[SC] = 署名と鍵の証明）、sub が暗号化用の副鍵（[E]）である。gpg も既定が ed25519 になっている。この鍵で、ファイルを自分宛てに暗号化して復号してみる（--batch は確認を省く指定。対話シェルなら省いて gpg --encrypt --recipient … でもよい）。

$ echo 社外秘のメモ > ~/secret.txt
$ gpg --batch --yes --encrypt -r deploy@linuc.example ~/secret.txt
$ ls -l ~/secret.txt.gpg
-rw-r--r-- 1 deploy deploy 199 Oct 13 10:59 /home/deploy/secret.txt.gpg
$ gpg --decrypt ~/secret.txt.gpg
社外秘のメモ

--encrypt --recipient は受け取る人の公開鍵で暗号化する（ここでは自分宛て）。できた .gpg は、対応する秘密鍵を持つ人だけが復号できる。相手に渡すのは公開鍵だけでよい——これが非対称の便利さである。鍵束・設定・エージェントは ~/.gnupg にまとまっている。

$ ls ~/.gnupg
S.gpg-agent
S.gpg-agent.browser
S.gpg-agent.extra
S.gpg-agent.ssh
openpgp-revocs.d
private-keys-v1.d
pubring.kbx
trustdb.gpg

pubring.kbx が公開鍵束、private-keys-v1.d に秘密鍵、S.gpg-agent は gpg-agent（パスフレーズを預かる、ssh-agent の GnuPG 版）のソケットである。gpg は署名（--sign / --clearsign）と検証（--verify）、鍵の書き出し（--export）と取り込み（--import）も同じ鍵束で行う。

たとえ: 公開鍵は、誰にでも配れる開いた南京錠に近い。相手はそれで箱を閉じる（暗号化）ことはできるが、開ける鍵（秘密鍵）は持ち主だけが持つ。
ただし崩れる点: 南京錠は閉じると自分でも開けられないが、公開鍵で暗号化したものは自分を受取人に含めれば自分でも開ける（ここで自分宛てに暗号化したように）。鍵の対応が本質で、物理の錠とは逆のこともできる。
手を動かす: 実践編の演習06（SSH 鍵の登録と権限）と演習07（gpg で暗号化→復号）が、この章の操作を自分の手で行う課題である。
確認

新しく SSH 鍵を作る。鍵が小さく生成も速く、いまの既定として勧められるアルゴリズムはどれか。

ア rsa（4096 ビット）　イ ecdsa　ウ ed25519

答え

ウ。ed25519 は公開鍵が 86 バイトと小さく生成も一瞬で、4096 ビットの RSA と同等以上の強度。 強さはビット長の数字ではなくアルゴリズムで決まる。RSA は古い機器との互換が要るときに使う。

確認

外側のホストで ssh -L 19999:127.0.0.1:2323 linuc を実行した。この 127.0.0.1 はどこのループバックを指すか。

答え

接続先（linuc＝練習機）のループバック。-L 手元:宛先 の宛先はトンネルの出口（相手側）から見たアドレスである。 だから手元の 19999 に繋ぐと、練習機の中の 127.0.0.1:2323（echo）に届く。

確認

gpg --encrypt --recipient alice ~/m.txt で作った m.txt.gpg を復号できるのは誰か。

答え

alice の秘密鍵を持つ人だけ。公開鍵（alice のもの）で暗号化したので、対応する秘密鍵でしか開けない。 送り手は alice の公開鍵さえあればよく、秘密鍵は渡さない。これが非対称の利点。

この章で分かったこと

持ち帰ってほしいこと

  • 公開鍵暗号は非対称。公開鍵で暗号化→秘密鍵で復号、秘密鍵で署名→公開鍵で検証。配るのは公開鍵だけ
  • 鍵の強さはビット長の数字ではなくアルゴリズムで決まる。ed25519 は小さく速く、いまの既定。RSA は互換用
  • ssh-agent は鍵を預かる。eval $(ssh-agent -s) でシェルに取り込み、ssh-add で鍵を登録する
  • ssh -L 手元:宛先 は、ssh のトンネル越しに相手側のサービスを手元のポートに出す（逆向きは -R）
  • gpg の鍵束・秘密鍵・gpg-agent は ~/.gnupg にある。--encrypt --recipient は相手の公開鍵で暗号化する
