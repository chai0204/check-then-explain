8. 鍵は、持ち主で非対称になっている

公開鍵暗号では、鍵が2つで一対になっていて、役割が非対称だ。公開鍵で暗号化したものは秘密鍵でしか開けず、秘密鍵で署名したものは公開鍵で検証できる。そして鍵の強さは「ビット数の大きさ」だけでは比べられない——256 ビットの ed25519 は、4096 ビットの RSA の16分の1の強さではなく、3072 ビットの RSA と同じくらいの強さを持つ。

この章のゴールと前提所要 22分
前提: 第7章まで読了前提: 練習機が起動している所要 22分影響度 C出題範囲 1.10.3（重要度3）最終検証 2026-10-13

この章のゴール

  • 公開鍵暗号の非対称性（暗号化⇔復号、署名⇔検証）と、共通鍵暗号との違いを説明できる
  • ssh-keygen の3つのアルゴリズム（rsa/ecdsa/ed25519）の違いを言える
  • ssh-agent・SSH ポート転送・gpg の基本の流れを説明できる
ここで覚えなくていいこと: 楕円曲線の数学、認証局（CA）による SSH 証明書、gpg の信頼の輪（web of trust）の細部はレベル1では深追いしない。ここでは「鍵を作る・使う・片方でしか開けない」という骨格と、SSH の鍵・エージェント・ポート転送・GnuPG の基本操作を扱う。

ビット数では強さを比べられない

この節で分かること: 3つのアルゴリズムの鍵長と強さの関係。

ssh-keygen -t でアルゴリズムを選んで鍵を3種類作り、鍵長（ビット）と公開鍵ファイル（.pub）の大きさを見る。

$ ssh-keygen -q -t rsa -b 4096 -N '' -f /tmp/k_rsa -C demo
$ ssh-keygen -q -t ecdsa -b 521 -N '' -f /tmp/k_ecdsa -C demo
$ ssh-keygen -q -t ed25519 -N '' -f /tmp/k_ed -C demo

ふつうこう考える

暗号は鍵が長いほど強い。RSA は 4096 ビット、ed25519 は 256 ビットなのだから、RSA 4096 のほうが16倍強いはずだ。

$ for k in rsa ecdsa ed; do ssh-keygen -lf /tmp/k_$k.pub | awk '{print $1, $NF}'; done
4096 (RSA)
521 (ECDSA)
256 (ED25519)
$ wc -c /tmp/k_rsa.pub /tmp/k_ecdsa.pub /tmp/k_ed.pub
 730 /tmp/k_rsa.pub
 258 /tmp/k_ecdsa.pub
  86 /tmp/k_ed.pub
1074 total
だめな理由: 鍵長は確かに 4096・521・256 と大きく違い、.pub ファイル（公開鍵を文字で書いたもの）も 730・258・86 バイトと違う。 だが強さはアルゴリズムと鍵長の組み合わせで決まり、違うアルゴリズムどうしをビット数で比べることはできない。 強さの目安を「何ビット相当の攻撃の手間か」で揃えると、ed25519 は約 128 ビット相当で、RSA 3072 ビットと同じくらいである（米国 NIST の鍵長の指針 SP 800-57 の表、ed25519 の仕様 RFC 8032）。 RSA 4096 はそれより少し強いが、16倍ではない。そして ed25519 は鍵が小さく、生成も速い（著者の練習機で3回ずつ測ると、RSA 4096 の生成は 4.7〜10.7 秒、ed25519 は 0.1〜0.4 秒だった。RSA は大きな素数を探すので、かかる時間が毎回ばらつく。KVM なしの遅いエミュレーションなので差が目に見える）。
アルゴリズム方式鍵長（この記録）強さの目安.pub の大きさ
rsa素因数分解4096 ビット128 ビット相当より少し上（3072 で 128 相当）730 バイト
ecdsa楕円曲線（NIST 曲線）521 ビット約 256 ビット相当（256 ビットの曲線なら 128 相当）258 バイト
ed25519楕円曲線（Edwards 曲線）256 ビット約 128 ビット相当（RSA 3072 と同程度）86 バイト

何も指定しないで作ると、いまの既定のアルゴリズムが選ばれる。

$ ssh-keygen -q -N '' -f /tmp/k_default -C demo
$ ssh-keygen -lf /tmp/k_default.pub | awk '{print $1, $NF}'
256 (ED25519)
$ ssh -V
OpenSSH_9.6p1 Ubuntu-3ubuntu13.19, OpenSSL 3.0.13 30 Jan 2024
$ rm /tmp/k_rsa* /tmp/k_ecdsa* /tmp/k_ed* /tmp/k_default*

この練習機の OpenSSH 9.6 では既定が ed25519 である。既定が ed25519 になったのは OpenSSH 9.5（2023年10月）からで、8.0〜9.4 の既定は RSA 3072 ビットだった。古い環境では -t ed25519 を明示する。

たとえ: 鍵長と強さは、錠前の種類とピンの本数の関係に近い。同じ種類の錠前ならピンが多いほど強いが、種類が違えば本数での比較は無意味——ダイヤル錠の桁数とシリンダー錠のピン数を比べても強さは分からない。
ただし崩れる点: 錠前の強さは破る時間で測れるが、暗号の強さは「いまの計算機で現実的な時間では破れない」という前提の上にあり、将来の計算機（量子計算機など）で前提が変わりうる。

ssh-agent は、鍵を預かって常駐する

この節で分かること: パスフレーズを何度も打たずに済ませる仕組みと、その後始末。

秘密鍵にパスフレーズを付けると安全だが、ssh のたびに打つのは面倒である。そこで、鍵をメモリ上で一度だけ開いて預かる常駐プログラムが ssh-agent である。以後の ssh はエージェントに署名を頼む。鍵を預けるのが ssh-add である。

$ ssh-add -l
Could not open a connection to your authentication agent.
$ ssh-agent -s
SSH_AUTH_SOCK=/tmp/ssh-l2uXXJ34i6lr/agent.2333; export SSH_AUTH_SOCK;
SSH_AGENT_PID=2334; export SSH_AGENT_PID;
echo Agent pid 2334;
$ ssh-add -l
Could not open a connection to your authentication agent.

ssh-agent -s はエージェントを起動し、その居場所（SSH_AUTH_SOCK など）をシェルの文として出力するだけである。いまのシェルに取り込まないので、ssh-add はまだ「エージェントに接続できない」と言う。eval $(…) で出力を実行して取り込む。

$ eval $(ssh-agent -s)
Agent pid 2337
$ ssh-add -l
The agent has no identities.
$ ssh-keygen -q -t ed25519 -N '' -f /tmp/ak -C agentdemo
$ ssh-add /tmp/ak
Identity added: /tmp/ak (agentdemo)
$ ssh-add -l | awk '{print $1, $NF}'
256 (ED25519)

この後ログアウトして、新しくログインし直してから見る。

$ ps -o pid,ppid,cmd -C ssh-agent
    PID    PPID CMD
   2334       1 ssh-agent -s
   2337       1 ssh-agent -s
$ pkill -u student ssh-agent; ps -o pid,ppid,cmd -C ssh-agent
    PID    PPID CMD
$ rm /tmp/ak /tmp/ak.pub

エージェントは2つともログアウトしても動き続けていた（親が PID 1 になっている）。ssh-agent -s は自分を切り離して常駐するので、起動したシェルが終わっても止まらない。止めるのは、そのシェルの中で eval $(ssh-agent -k)（SSH_AGENT_PID のエージェントを止め、変数も消す）。

$ eval $(ssh-agent -s)
Agent pid 2370
$ eval $(ssh-agent -k)
Agent pid 2370 killed

ssh-agent bash のようにエージェントの子としてシェルを起動する形なら、そのシェルを抜けたときにエージェントも終わる。

たとえ: ssh-agent は、鍵を預かる受付に近い。朝に一度だけ本人確認（パスフレーズ）をすれば、あとは受付が代わりに扉を開ける。
ただし崩れる点: 人の受付は閉館時間に帰るが、ssh-agent -s で起こした受付は、呼んだ人が帰っても残る。帰る前に ssh-agent -k で帰す必要がある。

鍵を置いても、置き場所が緩いと無視される

この節で分かること: sshd が鍵の置き場所の権限を見ていること（StrictModes）。

公開鍵を相手の ~/.ssh/authorized_keys に置けば鍵で入れる。だが sshd は、そのファイルやディレクトリが本人以外に書き換えられる状態だと、鍵を使わない。olduser で確かめる（第2章で localhost のホスト鍵を known_hosts に登録済みの前提。この章から始めるなら、最初の ssh に -o StrictHostKeyChecking=accept-new を足す）。

$ ssh-keygen -q -t ed25519 -N '' -f /tmp/sm_key -C smdemo
$ sudo install -d -m 700 -o olduser -g olduser /home/olduser/.ssh
$ sudo install -m 600 -o olduser -g olduser /tmp/sm_key.pub /home/olduser/.ssh/authorized_keys
$ ssh -i /tmp/sm_key -o BatchMode=yes olduser@localhost id
uid=1001(olduser) gid=1001(olduser) groups=1001(olduser)
$ sudo chmod 777 /home/olduser/.ssh
$ ssh -i /tmp/sm_key -o BatchMode=yes olduser@localhost id; echo rc=$?
olduser@localhost: Permission denied (publickey).
rc=255
$ sudo journalctl --no-pager -n 50 | grep -o 'Authentication refused: .*' | tail -1
Authentication refused: bad ownership or modes for directory /home/olduser/.ssh
$ sudo chmod 700 /home/olduser/.ssh
$ ssh -i /tmp/sm_key -o BatchMode=yes olduser@localhost id
uid=1001(olduser) gid=1001(olduser) groups=1001(olduser)
$ sudo rm -r /home/olduser/.ssh; rm /tmp/sm_key /tmp/sm_key.pub

.ssh を 777 にしただけで、同じ鍵が Permission denied (publickey) で弾かれた。手元には理由が出ず、サーバのログにだけ bad ownership or modes と残る。700 に戻すとまた入れる（確かめたら、試しに置いた鍵は消しておく）。これが sshd の StrictModes（既定で有効）である。ホーム・.ssh・authorized_keys が group や other に書けると、他人が鍵を差し込めるので信用しない。

ポート転送は、トンネルの出口を手元に作る

この節で分かること: ssh -L が何を手元に持ってくるか。

練習機の中では 2323（第4章の echo）が動いている。だが外側のホストから直接は触れない（外に転送しているのは 22 だけ）。試すと接続を拒否される。

$ timeout 2 bash -c 'exec 3<>/dev/tcp/127.0.0.1/2323 && head -1 <&3'; echo rc=$?
bash: connect: Connection refused
bash: line 1: /dev/tcp/127.0.0.1/2323: Connection refused
rc=1

ここで ssh -L を使う。-L 19999:127.0.0.1:2323 は「手元の 19999 番に来たものを、ssh の暗号トンネルを通して相手（練習機）から見た 127.0.0.1:2323 へ届ける」という意味である。

$ ssh -f -N -L 19999:127.0.0.1:2323 linuc; sleep 1; echo tunnel_up
tunnel_up
$ timeout 3 bash -c 'exec 3<>/dev/tcp/127.0.0.1/19999 && head -1 <&3'
linuc-echo
$ pkill -f 19999:127.0.0.1:2323; echo tunnel_down
tunnel_down

手元の 19999 に繋ぐと、練習機の中の echo サービスが linuc-echo と返した。外からは見えないサービスに、ssh のトンネル越しに手元から届いた。これが -L（ローカル転送）である。宛先は「ssh の相手から見た」住所なので、相手を中継に使ってさらに別のホストにも届ける。たとえば ssh -L 8080:db.internal:80 relay は、手元の 8080 番を、中継ホスト relay から見た db.internal の 80 番につなぐ（手元から db.internal に直接届かなくてよい）。逆向きに「相手側のポートに来たものを手元側へ届ける」のが -R（リモート転送）、トンネルの中で暗号化されるのは手元と中継の間である。

たとえ: ssh -L は、本社（中継）の内線にしか繋がっていない電話に、自宅（手元）に引いた専用線を通して掛けるのに近い。専用線（ssh のトンネル）の中は暗号化されている。
ただし崩れる点: 専用線は物理的に1本だが、ssh -L はトンネルの中に何本でも転送を通せる。行き先はあくまで本社（相手側）から見た宛先で、専用線の出口から先（中継から db.internal まで）は暗号化されない。

GnuPG: 公開鍵で暗号化し、秘密鍵で復号する

この節で分かること: gpg の鍵束と、公開鍵方式・共通鍵方式の違い。

gpg で鍵を作る。ssh の鍵とは別で、ファイルの暗号化や署名に使う。対話では gpg --gen-key（名前とメールだけ聞き、方式・長さ・期限は既定）か gpg --full-generate-key（方式・鍵長・有効期限も選ぶ）で作るが、ここでは同じ結果を確認なしで作れる --quick-gen-key を使う（deploy になって打つ）。

$ gpg --batch --pinentry-mode loopback --passphrase '' --quick-gen-key 'Deploy <deploy@linuc.example>'
gpg: directory '/home/deploy/.gnupg' created
gpg: keybox '/home/deploy/.gnupg/pubring.kbx' created
gpg: /home/deploy/.gnupg/trustdb.gpg: trustdb created
gpg: directory '/home/deploy/.gnupg/openpgp-revocs.d' created
...
$ gpg -k
...
/home/deploy/.gnupg/pubring.kbx
-------------------------------
pub   ed25519 2026-10-13 [SC] [expires: 2029-10-12]
...
uid           [ultimate] Deploy <deploy@linuc.example>
sub   cv25519 2026-10-13 [E]
$ ls -1 ~/.gnupg
S.gpg-agent
S.gpg-agent.browser
S.gpg-agent.extra
S.gpg-agent.ssh
openpgp-revocs.d
private-keys-v1.d
pubring.kbx
pubring.kbx~
trustdb.gpg
$ gpgconf --list-dirs agent-socket
/home/deploy/.gnupg/S.gpg-agent

pub が主鍵（[SC] = 署名と鍵の証明）、sub が暗号化用の副鍵（[E]）で、gpg も既定が ed25519（暗号化は cv25519）になっている。~/.gnupg/ には公開鍵束 pubring.kbx、秘密鍵 private-keys-v1.d/、信頼のデータベース trustdb.gpg、失効証明書 openpgp-revocs.d/ が入る。S.gpg-agent は gpg-agent（秘密鍵とパスフレーズを預かる、ssh-agent の GnuPG 版）の窓口で、/run/user/<UID> があるとき（そのユーザが ssh などでログインしているとき）はそちらに作られる。場所は gpgconf --list-dirs agent-socket で分かる。

この鍵で、ファイルを自分宛てに暗号化して復号する。

$ echo '社外秘のメモ' > ~/secret.txt
$ gpg --encrypt --recipient deploy@linuc.example ~/secret.txt
$ ls -l ~/secret.txt.gpg
-rw-rw-r-- 1 deploy deploy 199 Oct 13 19:29 /home/deploy/secret.txt.gpg
$ gpg --decrypt ~/secret.txt.gpg
gpg: encrypted with cv25519 key, ID 57C5D96E1EBF19B0, created 2026-10-13
      "Deploy <deploy@linuc.example>"
社外秘のメモ

--encrypt --recipient（-e -r）は受け取る人の公開鍵で暗号化する（ここでは自分宛て）。できた .gpg は、対応する秘密鍵を持つ人だけが復号できる。相手に渡すのは公開鍵だけでよい——これが非対称の便利さである。署名（--sign / --clearsign）と検証（--verify）、鍵の書き出し（--export）と取り込み（--import）も同じ鍵束で行う。

もう1つの方式が 共通鍵暗号である。gpg -c（--symmetric）は鍵ペアを使わず、パスフレーズ1つから作った鍵で暗号化し、復号にも同じパスフレーズを使う。対話で打つと pinentry の画面でパスフレーズを2回聞かれる。ここでは同じ結果を画面なしで作るため、--passphrase で渡している。

$ gpg --batch --pinentry-mode loopback --passphrase kyoutsuu -o ~/secret.sym.gpg -c ~/secret.txt
$ ls -l ~/secret.txt.gpg ~/secret.sym.gpg
-rw-rw-r-- 1 deploy deploy 102 Oct 13 19:29 /home/deploy/secret.sym.gpg
-rw-rw-r-- 1 deploy deploy 199 Oct 13 19:29 /home/deploy/secret.txt.gpg
$ gpg --list-packets ~/secret.txt.gpg 2>/dev/null | grep -o '^:[a-z]* enc packet'
:pubkey enc packet
$ gpg --batch --pinentry-mode loopback --passphrase kyoutsuu --list-packets ~/secret.sym.gpg 2>/dev/null | grep -o '^:[a-z]* enc packet'
:symkey enc packet
$ gpg --batch --pinentry-mode loopback --passphrase kyoutsuu -d ~/secret.sym.gpg
gpg: AES256.CFB encrypted data
gpg: encrypted with 1 passphrase
社外秘のメモ

ファイルの先頭の包みが違う。公開鍵方式は pubkey enc packet（受け取る人の公開鍵で包んだ鍵が入っている）、共通鍵方式は symkey enc packet（パスフレーズから作った鍵で包んでいる）。

公開鍵方式（gpg -e -r 相手）共通鍵方式（gpg -c）
暗号化に使うもの相手の公開鍵パスフレーズ（共通の秘密）
復号に使うもの相手の秘密鍵（相手しか持たない）同じパスフレーズ
事前に渡すもの公開鍵（知られてよい）パスフレーズ（安全な経路で渡す必要がある）
鍵ペア要る要らない
たとえ: 公開鍵は、誰にでも配れる開いた南京錠に近い。相手はそれで箱を閉じる（暗号化）ことはできるが、開ける鍵（秘密鍵）は持ち主だけが持つ。共通鍵暗号は、閉めるのも開けるのも同じ合言葉の箱である。
ただし崩れる点: 南京錠は閉じると自分でも開けられないが、公開鍵で暗号化したものは自分を受取人に含めれば自分でも開ける（ここで自分宛てに暗号化したように）。鍵の対応が本質で、物理の錠とは違うこともできる。
手を動かす: 実践編の演習06（SSH 鍵の登録と、置き場所の権限）と演習07（gpg で暗号化→復号）が、この章の操作を自分の手で行う課題である。この章の gpg の節を打った後なら、演習07 はそのまま達成になる（演習06 は deploy の鍵なので、この章では先回りしていない）。
確認

いま新しく SSH 鍵を作る。鍵が小さく生成も速く、OpenSSH 9.5 以降の既定にもなっているアルゴリズムはどれか。また、その強さの目安は。

ア rsa（4096 ビット）　イ ecdsa　ウ ed25519

答え

ウ。ed25519 は鍵長 256 ビット、公開鍵ファイルは 86 バイトと小さく、生成も速い。 強さは約 128 ビット相当で RSA 3072 ビットと同程度（RSA 4096 のほうが少し上だが、鍵が大きく遅い）。 違うアルゴリズムどうしはビット数で比べられない。

確認

ホスト A で ssh -L 8080:db:80 relay を実行した。A の 8080 番に繋いだ通信は、どこに届くか。

答え

中継ホスト relay から見た db の 80 番。-L 手元:宛先 の宛先はトンネルの出口（ssh の相手側）から見た住所である。 A と relay の間は ssh で暗号化されるが、relay から db までは通常の通信になる。

確認

パスフレーズだけで暗号化し、同じパスフレーズで復号する（鍵ペアを使わない）gpg のオプションはどれか。

ア -e　イ -c　ウ -s　エ --export

答え

イ（--symmetric。共通鍵暗号）。-e（--encrypt）は相手の公開鍵で暗号化する公開鍵方式、-s は署名、--export は公開鍵の書き出し。

確認

eval $(ssh-agent -s) で起動したエージェントは、ログアウトすると止まるか。

答え

止まらない。ssh-agent は自分を切り離して常駐し（親は PID 1）、ログアウト後も残る。 止めるのは eval $(ssh-agent -k)。ssh-agent bash の形で起動したなら、その bash を抜けると終わる。

この章で分かったこと

持ち帰ってほしいこと

  • 公開鍵暗号は非対称。公開鍵で暗号化→秘密鍵で復号、秘密鍵で署名→公開鍵で検証。共通鍵暗号（gpg -c）は同じパスフレーズで暗号化と復号をする
  • 強さはアルゴリズムと鍵長で決まり、違うアルゴリズムどうしはビット数で比べられない。ed25519 は約 128 ビット相当（RSA 3072 と同程度）で、小さく速く、OpenSSH 9.5 以降の既定
  • ssh-agent は eval $(ssh-agent -s) で取り込み、ssh-add で鍵を預ける。ログアウトしても残るので eval $(ssh-agent -k) で止める
  • sshd は、ホーム・.ssh・authorized_keys が本人以外に書けると鍵を使わない（StrictModes）
  • ssh -L 手元:宛先 相手 は、相手から見た宛先を手元のポートに出す（逆向きは -R）
  • gpg の鍵束・秘密鍵・信頼データベースは ~/.gnupg。gpg-agent が秘密鍵とパスフレーズを預かる
