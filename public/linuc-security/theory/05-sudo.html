5. sudo は、許したものだけに絞る

/etc/sudoers.d/ にルールを書き、visudo -c も通した。その後でファイルの権限を 666 にしただけで、「許したはずのコマンドが通らない」状態になる。sudo は、他人が書き換えられる指示書を信用せず、そのファイルを丸ごと読まずに飛ばすからだ。

前提: 第4章まで読了前提: 練習機が起動している所要 16分影響度 B出題範囲 1.10.1（重要度3）最終検証 2026-10-13

この章のゴール

  • su と sudo の違い、/etc/sudoers と /etc/sudoers.d/ の関係を説明できる
  • 特定ユーザに特定コマンドだけを許すルールを書ける
  • sudo がどんな持ち主・権限のファイルを飛ばすか、visudo が何を検査するかを言える
ここで覚えなくていいこと: Cmnd_Alias / Runas_Alias などのエイリアス、Defaults の細かいオプション、LDAP 連携の sudoers はレベル1では深追いしない。ここでは「誰に・何を・パスワードあり/なし」の基本形と、ファイルの置き場所・持ち主と権限・検査だけを扱う。

su は別人になる、sudo は一件だけ代理する

この節で分かること: 2つの昇格のしかたの違い。

su は別のユーザに切り替える。su - user はそのユーザのログイン環境ごと（- で PATH やホームも）切り替え、切り替え先のパスワードを聞く。su -（ユーザ省略）で root になる。一方 sudo は1つのコマンドだけを別ユーザ（既定は root）として実行し、聞くのは自分のパスワードである。誰が何を実行してよいかは /etc/sudoers に書く。

この練習機の root はパスワード欄が *（第2章で見た）なので、su - で root になることはできない。管理は sudo 経由に一本化されている。クラウドの標準的な構成である。

たとえ: su は制服を着替えてその人になりきること、sudo は「この書類1枚だけ代わりにハンコを押してください」と一件だけ代理を頼むことに近い。
ただし崩れる点: 着替えには相手の鍵（パスワード）が要るが、sudo は自分の身分証（自分のパスワード）だけで、何を代理してよいかは名簿（sudoers）が決める。

既定の行を読む: % はグループ、(ALL) は誰としてでも

この節で分かること: sudoers の1行の読み方。

まず、この練習機に最初から書かれている行を読む。

$ sudo grep -E '^(%|root)' /etc/sudoers
root	ALL=(ALL:ALL) ALL
%admin ALL=(ALL) ALL
%sudo	ALL=(ALL:ALL) ALL
$ sudo cat /etc/sudoers.d/90-cloud-init-users
# Created by cloud-init v. 26.1-0ubuntu1~24.04.1 on Tue, 13 Oct 2026 00:46:50 +0000

# User rules for student
student ALL=(ALL) NOPASSWD:ALL

1行は「誰が　どのホストで＝(誰として:どのグループとして)　何を」の順である。先頭に % が付くとグループを指す。%sudo ALL=(ALL:ALL) ALL は「グループ sudo の人は、どのホストでも、どのユーザ・どのグループとしてでも、どのコマンドでも（自分のパスワードを入れれば）実行できる」。Ubuntu では sudo グループに入れることが管理者にする標準のやり方である（%admin は古い Ubuntu の管理者グループの名残で、互換のために残っている行）。student ALL=(ALL) NOPASSWD:ALL は、student がパスワードなしで何でもできる行（クラウドの初期設定が書いたもの）。

(ALL) は「root に限らず誰としてでも」実行できるという意味なので、-u で別のユーザとして実行できる。

$ sudo -u olduser id
uid=1001(olduser) gid=1001(olduser) groups=1001(olduser)
書き方意味
student ALL=(ALL) ALLユーザ student が、誰としてでも、何でも（パスワードあり）
%sudo ALL=(ALL:ALL) ALLグループ sudo の人が、どのユーザ・どのグループとしてでも、何でも
%lpi ALL=(ALL) NOPASSWD: /sbin/shutdownグループ lpi の人が、shutdown だけをパスワードなしで
deploy ALL=(root) NOPASSWD: /usr/bin/journalctldeploy が、root としてだけ、journalctl だけをパスワードなしで

1コマンドだけ許す

この節で分かること: sudoers ルールの書き方と検査。

deploy は、いまは sudo を一切使えない。ログを読むために journalctl だけを、パスワードなしで許す。本体 /etc/sudoers は直接編集せず、/etc/sudoers.d/ にファイルを1つ置く（本体の最後で取り込まれている）。

$ sudo -l -U deploy
User deploy is not allowed to run sudo on linuc.
$ echo 'deploy ALL=(root) NOPASSWD: /usr/bin/journalctl' | sudo tee /etc/sudoers.d/deploy
deploy ALL=(root) NOPASSWD: /usr/bin/journalctl
$ sudo ls -l /etc/sudoers.d/deploy
-rw-r--r-- 1 root root 48 Oct 13 19:26 /etc/sudoers.d/deploy
$ sudo chmod 440 /etc/sudoers.d/deploy
$ sudo visudo -c
/etc/sudoers: parsed OK
/etc/sudoers.d/90-cloud-init-users: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/deploy: parsed OK
$ sudo -l -U deploy
Matching Defaults entries for deploy on linuc:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin,
    use_pty

User deploy may run the following commands on linuc:
    (root) NOPASSWD: /usr/bin/journalctl

ルールの形は deploy ALL=(root) NOPASSWD: /usr/bin/journalctl。左から「誰が」「どのホストで＝(誰として)」「パスワード指定」「どのコマンド（フルパス）」である。tee で作ったファイルは 644 だったので、推奨の 440 にそろえてから visudo -c で検査した。deploy になって（sudo -u deploy -i）、実際に打つ。

$ sudo -n journalctl -n 1 --no-pager >/dev/null; echo rc=$?
rc=0
$ sudo -n id; echo rc=$?
sudo: a password is required
rc=1

journalctl は通り（rc=0）、id は拒否された（a password is required）。許したものだけが通り、ほかは全部拒否される。これが最小権限である。

持ち主と権限が緩いと、丸ごと読まれない

この節で分かること: sudo が設定ファイルのどんな持ち主・権限を拒むか。

このファイルの権限を変えながら、deploy の sudo がどうなるかを順に見る。まず、グループ（root）に書き込みを足す。

$ sudo chmod 664 /etc/sudoers.d/deploy; sudo ls -l /etc/sudoers.d/deploy
-rw-rw-r-- 1 root root 48 Oct 13 19:26 /etc/sudoers.d/deploy
$ sudo -n journalctl -n 1 --no-pager >/dev/null; echo rc=$?
rc=0

664 でも通った（rc=0）。

ふつうこう考える

グループに書き込みがあっても読まれた。ならば other（誰でも）が書ける 666 にしても、中身が正しければ効くはずだ。ファイルの権限は中身と関係ない。

$ sudo chmod 666 /etc/sudoers.d/deploy; sudo ls -l /etc/sudoers.d/deploy
sudo: /etc/sudoers.d/deploy is world writable
-rw-rw-rw- 1 root root 48 Oct 13 19:26 /etc/sudoers.d/deploy
sudo: /etc/sudoers.d/deploy is world writable
$ sudo -n journalctl -n 1 --no-pager >/dev/null; echo rc=$?
sudo: /etc/sudoers.d/deploy is world writable
sudo: a password is required
rc=1
だめな理由: 666（other も書ける）にした途端、sudo は is world writable と警告を出し、そのファイルを読まなかった。結果、さっきまで通っていた journalctl まで a password is required で拒否される。sudo はルールに従ってコマンドを root で実行するので、 他人が書き換えられる設定ファイルを信用しない。中身が正しくても、入れ物が緩ければ飛ばす。

この状態は visudo -c でも見つかる。visudo -c は構文だけでなく持ち主と権限も検査し、rc=1 で終わる。ルールを置いた後で誰かが権限を変えても、visudo -c を打ち直せば分かる。

$ sudo visudo -c; echo rc=$?
sudo: /etc/sudoers.d/deploy is world writable
/etc/sudoers: parsed OK
/etc/sudoers.d/90-cloud-init-users: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/deploy: bad permissions, should be mode 0440
rc=1

グループが root 以外で書き込める場合も飛ばされる。

$ sudo chmod 660 /etc/sudoers.d/deploy; sudo chgrp deploy /etc/sudoers.d/deploy; sudo ls -l /etc/sudoers.d/deploy
sudo: /etc/sudoers.d/deploy is world writable
sudo: /etc/sudoers.d/deploy is owned by gid 1002, should be 0
-rw-rw---- 1 root deploy 48 Oct 13 19:26 /etc/sudoers.d/deploy
sudo: /etc/sudoers.d/deploy is owned by gid 1002, should be 0
$ sudo -n journalctl -n 1 --no-pager >/dev/null; echo rc=$?
sudo: /etc/sudoers.d/deploy is owned by gid 1002, should be 0
sudo: a password is required
rc=1
$ sudo visudo -c; echo rc=$?
sudo: /etc/sudoers.d/deploy is owned by gid 1002, should be 0
/etc/sudoers: parsed OK
/etc/sudoers.d/90-cloud-init-users: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/deploy: wrong owner (uid, gid) should be (0, 0)
/etc/sudoers.d/deploy: bad permissions, should be mode 0440
rc=1

確かめたら推奨の 440・root:root に戻す（戻さないと、この後どの sudo を打っても警告の行が出る）。

$ sudo chgrp root /etc/sudoers.d/deploy; sudo chmod 440 /etc/sudoers.d/deploy; sudo visudo -c
sudo: /etc/sudoers.d/deploy is owned by gid 1002, should be 0
/etc/sudoers: parsed OK
/etc/sudoers.d/90-cloud-init-users: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/deploy: parsed OK
持ち主・権限sudo の扱い
440・root:root（推奨）／644・664・root:root読まれる（visudo -c は 440 以外を bad permissions と指摘する）
other が書ける（666 など）is world writable と出して読まない
root 以外のグループが書ける（660・グループ deploy など）is owned by gid 1002, should be 0 と出して読まない

主題1.09 の logrotate が、group や other に書ける設定ファイルを無視するのと同じ考え方である（主題1.09 の第6章）。境目の細部は違うが、「root として何かを実行する道具は、他人が書き換えられる設定を信用しない」という形は共通している。

たとえ: 現場に出す作業指示書に近い。指示書どおりに重機を動かす（root 権限で実行する）のだから、 その指示書が部外者でも書き換えられる場所に置いてあったら、現場監督は従わない。 内容が正しいかより先に「この紙は本物か（書けるのは管理側だけか）」を見る。
ただし崩れる点: 人間の監督は「たぶん大丈夫」で従うこともあるが、sudo は機械的に判断する。other が書けるか、root 以外のグループが書けるなら、警告を出して例外なく飛ばす。

壊れた行と、visudo

この節で分かること: なぜ visudo を使うのか、壊れた行で何が起きるか。

visudo -c は構文の誤りも行と桁まで示す。NOPASSWD の綴りを NOPASS と間違えたファイルを置いてみる。

$ echo 'deploy ALL=(root) NOPASS: ALL' | sudo tee /etc/sudoers.d/broken
deploy ALL=(root) NOPASS: ALL
$ sudo visudo -c; echo rc=$?
/etc/sudoers.d/broken:1:30: syntax error
deploy ALL=(root) NOPASS: ALL
                             ^
/etc/sudoers.d/broken:1:30: syntax error
deploy ALL=(root) NOPASS: ALL
                             ^
rc=1
$ sudo -n true; echo rc=$?
/etc/sudoers.d/broken:1:30: syntax error
deploy ALL=(root) NOPASS: ALL
                             ^
rc=0

visudo -c は 1:30: syntax error と場所を指して rc=1 を返した。だが sudo そのものは誤りを報告しながら動き続けた（sudo -n true は rc=0）。いまの sudo は、壊れた行の残りを捨てて残りの設定で動く（error_recovery。既定で有効）。

$ man 5 sudoers | grep -A9 '^ *error_recovery'
       error_recovery=bool
             The  error_recovery  argument  can  be  used  to  control whether
             sudoers should attempt to  recover  from  syntax  errors  in  the
             sudoers  file.  If set to true (the default), sudoers will try to
             recover from a syntax error by discarding the portion of the line
             that contains the error until the end of the line.   A  value  of
             false  will  disable  error recovery.  Prior to version 1.9.3, no
             error recovery was performed.

       ignore_perms=bool
$ sudo rm /etc/sudoers.d/broken
/etc/sudoers.d/broken:1:30: syntax error
deploy ALL=(root) NOPASS: ALL
                             ^

壊れたファイルは消しておく（残すと、この後どの sudo を打っても構文の誤りの行が出る。消す sudo rm 自身もまだ報告する）。この練習機の sudo は 1.9.15p5 で、1.9.3 より前は壊れた sudoers で sudo 全体が止まった（error_recovery=false にした場合も同じ）。いまでも、自分を許している行を壊せば、その権限を失う。root がロックされた構成では、自分の sudo を壊すと管理者に戻れなくなる（この練習機なら外から lab-guest で直せる）。だから編集は visudo で行い、保存の前に検査させる。visudo は検査で誤りを見つけると、そのままでは保存させない。

たとえ: visudo は、校正者が通さないと印刷できない輪転機に近い。誤植のある版は刷られない。
ただし崩れる点: 校正者は内容の良し悪しも見るが、visudo が見るのは文法と持ち主・権限だけである。「全員に全部許す」危険なルールでも、文法が正しければ通してしまう。危険かどうかは人が判断する。
手を動かす: 実践編の演習04は、この deploy に journalctl だけを許す課題である。判定は、deploy として実際に sudo journalctl が通り sudo id が拒否されること、visudo -c が通ることを見る。この章のとおりに打った後なら、演習04 はそのまま達成になる（自力で解きたいなら、この章を打つ前に演習から始める）。
確認

/etc/sudoers.d/deploy を置いて visudo -c も通った。その後で誰かが権限を 666 に変えた。deploy の sudo はどうなり、どう見つけられるか。

答え

sudo は is world writable と警告してそのファイルを読まないので、許していたコマンドも a password is required で拒否される。 visudo -c を打ち直せば bad permissions, should be mode 0440 と出て見つかる。440・root:root に戻す。

確認

グループ lpi に属するユーザ全員に、/sbin/shutdown だけをパスワードなしで root として実行させたい。sudoers に書く行はどれか。

ア lpi ALL=(ALL) NOPASSWD: /sbin/shutdown　イ %lpi ALL=(ALL) NOPASSWD: /sbin/shutdown　ウ @lpi ALL=(ALL) /sbin/shutdown

答え

イ。グループは先頭に % を付ける（アは lpi という名前のユーザになる）。(ALL) は誰としてでも実行できる指定で、root としての実行も含む。 パスワードを聞かないのは NOPASSWD:（ウには無いうえ、@ はグループの書き方ではない）。

確認

/etc/sudoers を直接 vi で編集せず visudo を使うのはなぜか。

答え

visudo は保存の前に構文を検査し、誤りがあればそのままでは保存させないから。 いまの sudo（1.9.3 以降）は壊れた行を捨てて動くが、自分を許す行を壊せばその権限を失い、古い sudo では全体が止まる。 root がロックされていると戻れなくなるので、壊れた設定を書き込ませない仕組みが要る。

この章で分かったこと

持ち帰ってほしいこと

  • su は別ユーザに切り替え（相手のパスワード）、sudo は1コマンドを代理実行（自分のパスワード）
  • ルールは /etc/sudoers.d/ に置く。形は ユーザ ALL=(実行ユーザ) [NOPASSWD:] コマンド（フルパス）。% はグループ、(ALL) は誰としてでも。推奨は 440・root:root
  • sudo は、other が書けるファイルと、root 以外のグループが書けるファイルを読まずに飛ばす（root:root の 664 は読む）
  • visudo -c は構文と持ち主・権限を検査する。visudo は誤りがあれば保存させない
  • いまの sudo（1.9.3 以降）は壊れた行を捨てて動くが、自分を許す行を壊せばその権限を失う
