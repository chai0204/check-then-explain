5. sudo は、許したものだけに絞る

/etc/sudoers.d/ にルールを書き、visudo -c も通した。なのに「許したはずのコマンドが通らない」。ファイルの権限を 646 にしただけで、sudo はそのルールを丸ごと無視していた。他人が書き換えられる指示書を、sudo は信用しないからだ。

前提: 第4章まで読了前提: 練習機が起動している所要 14分影響度 B出題範囲 1.10.1（重要度3）最終検証 2026-10-13

この章のゴール

  • su と sudo の違い、/etc/sudoers と /etc/sudoers.d/ の関係を説明できる
  • 特定ユーザに特定コマンドだけを許すルールを書ける
  • sudo が設定ファイルの権限を見ていること、visudo がなぜ要るかを言える
ここで覚えなくていいこと: Cmnd_Alias / Runas_Alias などのエイリアス、Defaults の細かいオプション、LDAP 連携の sudoers はレベル1では深追いしない。ここでは「誰に・何を・パスワードあり/なし」の基本形と、ファイルの置き場所・権限・検証だけを扱う。

su は別人になる、sudo は一件だけ代理する

この節で分かること: 2つの昇格のしかたの違い。

su は別のユーザに切り替える。su - user はそのユーザのログイン環境ごと（- で PATH やホームも）切り替え、切り替え先のパスワードを聞く。su -（ユーザ省略）で root になる。一方 sudo は1つのコマンドだけを別ユーザ（既定は root）として実行し、聞くのは自分のパスワードである。誰が何を実行してよいかは /etc/sudoers に書く。

この練習機の root はパスワードが *（第2章で見た）なので、su - で root になることはできない。管理は sudo 経由に一本化されている。クラウドの標準的な構成である。

たとえ: su は制服を着替えてその人になりきること、sudo は「この書類1枚だけ代わりにハンコを押してください」と一件だけ代理を頼むことに近い。
ただし崩れる点: 着替えは本人確認に相手の鍵（パスワード）が要るが、sudo は自分の身分証（自分のパスワード）だけで、何を代理してよいかは名簿（sudoers）が決める。

1コマンドだけ許す

この節で分かること: sudoers ルールの書き方と検証。

deploy は、いまは sudo を一切使えない。

$ sudo -l -U deploy 2>&1 | tail -2
User deploy is not allowed to run sudo on linuc.

ログを読むために journalctl だけを、パスワードなしで許す。本体 /etc/sudoers は直接編集せず、/etc/sudoers.d/ にファイルを1つ置く（include されている）。置いたら visudo -c で構文を検査する。

$ echo "deploy ALL=(root) NOPASSWD: /usr/bin/journalctl" | sudo tee /etc/sudoers.d/deploy >/dev/null
$ sudo chmod 440 /etc/sudoers.d/deploy
$ sudo visudo -c
/etc/sudoers: parsed OK
/etc/sudoers.d/90-cloud-init-users: parsed OK
/etc/sudoers.d/README: parsed OK
/etc/sudoers.d/deploy: parsed OK

ルールの形は deploy ALL=(root) NOPASSWD: /usr/bin/journalctl。左から「誰が」「どのホストで＝(誰として)」「パスワード指定」「どのコマンド（フルパス）」である。許可一覧を見て、実際に打ってみる。

$ sudo -l -U deploy 2>&1 | tail -2
User deploy may run the following commands on linuc:
    (root) NOPASSWD: /usr/bin/journalctl
$ sudo -n journalctl -n 1 >/dev/null 2>&1; echo allowed_rc=$?
allowed_rc=0
$ sudo -n id; echo denied_rc=$?
sudo: a password is required
denied_rc=1

journalctl は通り（allowed_rc=0）、id は拒否された（a password is required）。許したものだけが通り、ほかは全部拒否される。これが最小権限である。

権限が緩いと、丸ごと無視される

この節で分かること: sudo が設定ファイルの権限まで見ていること。

ふつうこう考える

ルールを置いて visudo -c も通った。あとは中身が正しければ効くはずだ。ファイルの権限は中身と関係ない。

$ sudo chmod 646 /etc/sudoers.d/deploy
$ sudo -n journalctl -n 1; echo rc=$?
sudo: /etc/sudoers.d/deploy is world writable
sudo: /etc/sudoers.d/deploy is world writable
sudo: a password is required
rc=1
だめな理由: 権限を 646（他人も書ける）にしただけで、sudo は is world writable と警告を出し、そのファイルを読まなかった。結果、さっきまで通っていた journalctl まで a password is required で拒否される。sudo はルールを root の権限で実行するので、 他人が書き換えられる設定ファイルを信用しない。中身が正しくても、入れ物が緩ければ無視する。 （第6章の logrotate が group 書き込み可の設定を無視するのと同じ考え方で、主題をまたいで繰り返し出てくる。）

だから sudoers 系のファイルは 440 にする。戻すと、また journalctl が通るようになる。

$ sudo chmod 440 /etc/sudoers.d/deploy
たとえ: 現場に出す作業指示書に近い。指示書どおりに重機を動かす（root 権限で実行する）のだから、 その指示書が誰でも書き換えられる場所に置いてあったら、現場監督は従わない。 内容が正しいかより先に「この紙は本物か（持ち主しか触れないか）」を見る。
ただし崩れる点: 人間の監督は「たぶん大丈夫」で従うこともあるが、sudo は機械的に、 group か other に書き込みがあれば例外なく無視する。警告は出すが従わない。

visudo が壊れた設定を止める

この節で分かること: なぜ直接編集せず visudo を使うのか。

壊れた sudoers は全員の sudo を止める（root になれなくなり、復旧が難しくなる）。だから編集は visudo で行い、保存時に構文を検査する。visudo -c はいまのファイル群を検査するだけのモードである。試しに壊れたルールを置くと、場所まで指して止める。

$ echo "deploy ALL=(root) NOPASS: ALL" | sudo tee /etc/sudoers.d/deploy >/dev/null
$ sudo visudo -c
/etc/sudoers.d/deploy:1:30: syntax error
deploy ALL=(root) NOPASS: ALL
                             ^

NOPASSWD の綴りを NOPASS と間違えた。visudo -c が 1:30: syntax error と行・桁まで示す。直接 vi で /etc/sudoers を開いて保存していたら、この壊れたまま全員が sudo を失っていた。visudo は保存の前に検査し、壊れていれば書き込ませない。

たとえ: visudo は、校正者が通さないと印刷できない輪転機に近い。誤植のある版は刷られない。
ただし崩れる点: 校正者は内容の良し悪しも見るが、visudo が見るのは文法だけである。「全員に全部許す」危険なルールでも、文法が正しければ通してしまう。危険かどうかは人が判断する。
手を動かす: 実践編の演習04は、この deploy に journalctl だけを許す課題である。判定は、deploy として実際に sudo journalctl が通り sudo id が拒否されること、visudo -c が通ること、ファイルの権限を見る。

確認

/etc/sudoers.d/deploy にルールを書き visudo -c も通ったのに、deploy の sudo が「a password is required」で拒否される。 ls -l すると -rw-rw-rw-（666）だった。なぜ効かないか。

答え

sudo は、設定ファイルが group か other に書き込み可だと「world writable」として丸ごと無視する。 他人が書き換えられる指示書を root 権限で実行しないため。chmod 440 にする。

確認

/etc/sudoers を直接 vi で編集して保存するのが危険なのはなぜか。正しい編集方法は。

答え

構文を壊すと全員が sudo を使えなくなり（root に戻れず）復旧が難しい。 visudo を使えば、保存の前に構文を検査し、壊れていれば書き込ませない。検査だけなら visudo -c。

この章で分かったこと

持ち帰ってほしいこと

  • su は別ユーザに切り替え（相手のパスワード）、sudo は1コマンドを代理実行（自分のパスワード）
  • ルールは /etc/sudoers.d/ に置く。形は ユーザ ALL=(実行ユーザ) [NOPASSWD:] コマンド（フルパス）
  • sudo は設定ファイルが group/other に書けると丸ごと無視する。sudoers 系は 440
  • 編集は visudo。保存前に構文を検査し、壊れた設定を書き込ませない（visudo -c は検査だけ）
  • root のパスワードが * の構成では su - で root になれない。管理は sudo に一本化する
