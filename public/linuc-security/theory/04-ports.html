4. 開いているポートは、数えないと見えない

開いているポートを nmap で調べると、2323/tcp open 3d-nfsd と出る。だが 3d-nfsd というサービスは動いていない。そこで実際に動いているのは ncat である。nmap の「サービス名」は、ポート番号から表を引いた当て推量にすぎない。

前提: 第3章まで読了前提: 練習機が起動している所要 14分影響度 C出題範囲 1.10.1（重要度3）最終検証 2026-10-13

この章のゴール

  • ss・netstat で待ち受けポートと、それを出しているプロセスを辿れる
  • nmap の「SERVICE」列が当て推量であること、既定スキャンの範囲を説明できる
  • lsof・fuser でポートからプロセスを特定できる
ここで覚えなくていいこと: nmap の高度なスキャン（-sS SYN スキャン、OS 判定 -O、NSE スクリプト）はレベル1の範囲外である。ここでは「開いているポートを数え、プロセスまで辿る」ことだけを扱う。

まず待ち受けを並べる

この節で分かること: ss -ltn の読み方。

ss で TCP の待ち受け（-l）を数字のまま（-n）出す。

$ ss -ltn
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      4096      127.0.0.54:53        0.0.0.0:*
LISTEN 0      10           0.0.0.0:2323      0.0.0.0:*
LISTEN 0      4096         0.0.0.0:22        0.0.0.0:*
LISTEN 0      4096   127.0.0.53%lo:53        0.0.0.0:*

22（ssh）と 53（名前解決）のほかに、2323 が 0.0.0.0（全アドレス）で開いている。53 が 127.0.0.53・127.0.0.54 なのは systemd-resolved のスタブで、ローカル専用である。外から届くのは 0.0.0.0 で待つ 22 と 2323 だ。2323 に心当たりがなければ、これが調査対象になる。

nmap のサービス名は当て推量

この節で分かること: nmap が何を見て「サービス名」を出しているか。

ふつうこう考える

nmap はポートスキャンの定番だ。SERVICE 列を見れば、そのポートで何が動いているか分かるはずだ。

$ nmap 127.0.0.1
...
Not shown: 998 closed tcp ports (conn-refused)
PORT     STATE SERVICE
22/tcp   open  ssh
2323/tcp open  3d-nfsd
だめな理由: 2323/tcp が 3d-nfsd と出た。だがこの練習機で 3d-nfsd は動いていない。 動いているのは ncat である（次の節で確かめる）。nmap は、ポート番号を /etc/services の表で引いて「このポートはふつう何に使う」を表示しているだけで、 実際に何が応答したかを見ていない（-sV を付けて初めてバナーを取りに行く）。 SERVICE 列は「よくある用途」であって「いま動いているもの」ではない。 攻撃者が 2323 で別のものを動かしていても、ここには正体が出ない。

もう1つ。Not shown: 998 closed tcp ports とある。nmap の既定は全 65535 ポートではなく、よく使う約 1000 ポートだけを見る。1000 番の外（たとえば 50000 番台）で待ち受けているものは、既定スキャンでは見えない。全部見るには nmap -p- が要る。「nmap で何も出なかった＝安全」ではない。

たとえ: nmap のサービス名は、部屋番号から「ここはふつう会議室」と案内図を見て答えているのに近い。実際にその部屋で何が行われているかは、扉を開けて（-sV でバナーを取って）確かめないと分からない。
ただし崩れる点: 案内図は建物の持ち主が作るが、/etc/services は世界共通の慣習の表で、その部屋の実際の使い方とは無関係である。

ポートからプロセスを辿る

この節で分かること: 待ち受けを出している実プロセスの特定。

正体を知るには、自分のホストの中で「どのプロセスがそのポートを開いているか」を見る。ss -p・netstat -p・lsof・fuser のどれでもよい（-p には root が要る）。

$ sudo ss -ltnp | grep 2323
LISTEN 0      10           0.0.0.0:2323      0.0.0.0:*    users:(("ncat",pid=676,fd=4))
$ sudo lsof -iTCP:2323 -sTCP:LISTEN -P -n
COMMAND PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
ncat    676 root    3u  IPv6   5728      0t0  TCP *:2323 (LISTEN)
ncat    676 root    4u  IPv4   5729      0t0  TCP *:2323 (LISTEN)
$ sudo fuser 2323/tcp
2323/tcp:              676

どれも ncat（PID 676）を指した。nmap の言う 3d-nfsd ではない。外から当てた名前（nmap）より、自分のホストの中から見たプロセス（ss・lsof・fuser）のほうが正しい。

netstat でも同じことができる。こちらは 22 の持ち主が ncat と違うことに気づく。

$ sudo netstat -ltnp | grep -E ":22 |:2323 "
tcp        0      0 0.0.0.0:2323            0.0.0.0:*               LISTEN      676/ncat
tcp        0      0 0.0.0.0:22              0.0.0.0:*               LISTEN      1/init

2323 は 676/ncat だが、22 は 1/init（PID 1 = systemd）である。これは ssh がソケット起動（systemd がポートだけ持ち、接続が来たら sshd を起こす）になっているためで、接続が来るまで sshd というプロセスは常駐していない。「sshd が ps に居ないのに 22 が開いている」のはこのためである。

たとえ: ss／lsof は、建物の中から「どの部屋の誰が窓を開けているか」を名簿で確かめるのに近い。nmap は外から窓の数を数えて案内図で用途を推測する。
ただし崩れる点: 外からの観察（nmap）は攻撃者と同じ視点で価値があるが、正体の特定には中からの名簿（ss・lsof）が要る。両方の視点が要る。
たとえ: ソケット起動の 22 番は、呼び鈴だけ設置して受付は不在の窓口に近い。呼び鈴（ポート）は systemd が持っていて、来客があって初めて担当（sshd）を呼ぶ。
ただし崩れる点: 受付の不在は人には見えるが、ポートだけ開いた状態は ps に sshd が出ないので、慣れないと「誰も待ち受けていない」と誤読する。
手を動かす: 実践編の演習03は、この 2323 を出している lab-echo サービスを見つけて止める課題である。判定は、練習機の中で 2323 が待ち受けていないことを実際に見る。
確認

nmap で 2323/tcp open 3d-nfsd と出た。そのポートで実際に動いているプログラムを特定するには、どれが確実か。

ア nmap の SERVICE 列をそのまま信じる　イ ホストの中で ss -ltnp / lsof -i　ウ /etc/services を見る

答え

イ。nmap の SERVICE 列（ア）はポート番号から /etc/services（ウ）を引いた当て推量で、実体とは限らない。 -sV を付ければバナーを取りに行くが、確実なのは自分のホストの中から ss -p・lsof・fuser でプロセスを見ること。

確認

netstat -ltnp で、22 番の持ち主が sshd ではなく 1/init と出た。なぜか。

答え

ソケット起動（socket activation）のため。systemd（PID 1）がポートだけを持ち、接続が来たら sshd を起こす。 だから接続が無い間は sshd が常駐せず、ポートの持ち主が 1/init になる。

この章で分かったこと

持ち帰ってほしいこと

  • ss -ltn で TCP の待ち受けを数える。0.0.0.0 は外から届く、127.0.0.x はローカル専用
  • nmap の SERVICE 列はポート番号から /etc/services を引いた当て推量。実体は -sV かホスト内の ss/lsof で確かめる
  • nmap の既定はよく使う約 1000 ポートだけ。全部見るのは nmap -p-
  • ポートからプロセスは ss -p・netstat -p・lsof -i・fuser で辿る（-p に root）
  • 22 が 1/init なのはソケット起動。接続が来るまで sshd は常駐しない
