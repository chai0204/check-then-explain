3. 入っている人と、入れる上限

セキュリティ管理には「いま誰が入っているか」を見る道具（who・w・last）と、「1人がどこまで使えるか」を絞る道具（ulimit・TMOUT）がある。後者で油断しやすいのが、ulimit で下げた上限は、同じシェルでは元に戻せないことだ。下げるのは一方通行である。

前提: 第2章まで読了前提: 練習機が起動している所要 14分影響度 C出題範囲 1.10.1（重要度3）最終検証 2026-10-13

この章のゴール

  • who・w・last が何を見ているか（utmp と wtmp）を言える
  • ulimit のソフトとハードの違い、ハードが一方通行であることを説明できる
  • TMOUT と /etc/security/limits.conf がいつ効くかを言える
ここで覚えなくていいこと: cgroup による資源制限（systemd の MemoryMax= など）はレベル1の範囲外である。ここでは1ログインあたりの ulimit と、設定ファイル /etc/security/limits.conf だけを扱う。

下げるのは一方通行

この節で分かること: ソフトリミットとハードリミットの違い。

いまの上限を見る。-n が開けるファイル数、-u がプロセス数である。

$ ulimit -n
1024
$ ulimit -u
5504

ソフトリミットは自分で下げられる。下げてみる。

$ ulimit -n 512; ulimit -n
512
$ ulimit -n 4096; echo rc=$?
rc=0

512 に下げ、また 4096 に戻せた（rc=0）。ソフトはハードリミットの範囲内で上げ下げ自由である。ではハードリミット自体を下げてみる。

ふつうこう考える

ソフトと同じく、ハードリミットも下げたあとで必要になれば戻せるはずだ。一時的に絞って、あとで緩めればよい。

$ ulimit -Hn 2048; ulimit -Hn; ulimit -Hn 4096
2048
bash: line 1: ulimit: open files: cannot modify limit: Operation not permitted
だめな理由: ハードを 2048 に下げるのは通ったが、4096 に戻そうとすると Operation not permitted で拒否された。ハードリミットは、一般ユーザにとって一方通行である。 下げることはできるが、上げられるのは root だけ。 だから「一時的に絞って、あとで戻す」は、ハードに対しては（root でない限り）効かない。 ソフトは天井（ハード）の下で自由、ハードはその天井そのものを下げる操作で、下げたら戻せない。
種類読む／下げる上げる
ソフト（-S・既定）誰でもハードの範囲内なら誰でも
ハード（-H）誰でも読める・下げられるroot だけ

恒久的に効かせるには、ログインのたびに適用される /etc/security/limits.conf に書く。

$ echo "deploy hard nproc 30" | sudo tee -a /etc/security/limits.conf >/dev/null; echo added
added
$ sudo runuser -l deploy -c "ulimit -u"
30

deploy のプロセス数の上限が 30 になった。limits.conf は PAM がログインのときに読むので、いま開いているシェルには効かない。新しくログインし直して初めて効く。設定を書いても現在のセッションで変わらないのはこのためである。

たとえ: ハードリミットは、ダムの最高水位に近い。日々の水位（ソフト）はその下で自由に動かせるが、最高水位そのものを下げたら、権限のない現場では二度と上げ直せない。
ただし崩れる点: ダムは物理的に作り直せば上げられるが、ハードリミットは「root だけ」という権限の壁で、物理ではなく制度の問題である。

who・w・last は、端末の記録を読む

この節で分かること: ログイン状況と履歴がどこに記録されているか。
$ who
student  pts/0        2026-10-13 10:57 (10.0.2.2)
$ last -a | head -5
student  pts/0        Tue Oct 13 10:57   still logged in    10.0.2.2
reboot   system boot  Tue Oct 13 10:56   still running      6.8.0-142-generic

who はいまログインしている端末を /var/run/utmp から読む。pts/0 は疑似端末（SSH 接続）、(10.0.2.2) は接続元である。w は who に加えて負荷や各セッションの処理内容も出す。last は過去の記録を /var/log/wtmp から読み、ログインだけでなく reboot（起動）も並ぶ。失敗したログインは lastb（/var/log/btmp）にある。

ここに落とし穴がある。これらが読むのは端末（tty）を伴うログインの記録である。ssh host コマンド のように端末を持たずにコマンドだけ実行した場合や、cron のジョブは utmp に載らないので、who に出てこない。「who が空だから誰もいない」とは限らない。

たとえ: utmp／wtmp は、建物の入館ゲートの記録に近い。ゲートを通った人（端末ログイン）は残るが、窓から荷物だけ受け渡した人（端末なしのコマンド実行）は記録に出ない。
ただし崩れる点: 実際の建物なら窓の出入りも監視カメラで追えるが、who／last はゲートの記録しか見ない。プロセス側（ps・ss）と併せて見る必要がある。

TMOUT は、放置したシェルを自分で閉じる

この節で分かること: 自動ログアウトの仕組みと、それがいつ効くか。
$ grep -n TMOUT /etc/profile.d/*.sh 2>/dev/null; echo "（既定では未設定）"
（既定では未設定）

TMOUT は bash の環境変数で、無操作が続くと自動でログアウトする秒数である。export TMOUT=600 とすれば、10 分放置したシェルは勝手に閉じる。席を離れた端末が乗っ取られるのを防ぐための仕組みで、全員に効かせるなら /etc/profile.d/ に置く。

ただし TMOUT は対話的な bash の変数にすぎないので、ユーザが unset TMOUT すれば外せる。強制力のある制御ではなく、「うっかり放置」への保険だと理解しておく。

たとえ: TMOUT は、一定時間でロックがかかる画面のスクリーンセーバーに近い。席を立ったときの保険になる。
ただし崩れる点: スクリーンセーバーは OS が強制するが、TMOUT は本人のシェルの設定なので、本人が外せてしまう。悪意ある相手には効かない。
手を動かす: この章には専用の演習はない。練習機に入って（外の端末で vm ssh）、who / w / last -a / ulimit -a を自分で打つと、この章と同じ種類の出力が出る。ulimit -Hn を下げてから上げられないことも確かめられる。
確認

一般ユーザが ulimit -Hn 1024 でハードリミットを下げた。あとで ulimit -Hn 4096 と戻せるか。

答え

戻せない（Operation not permitted）。ハードリミットを上げられるのは root だけで、 一般ユーザにとって引き下げは一方通行。ソフトリミットはハードの範囲内なら自由に上げ下げできる。

確認

/etc/security/limits.conf に deploy hard nproc 30 を書き足した。いま開いている deploy のシェルに効くか。

答え

効かない。limits.conf は PAM がログイン時に読むので、適用されるのは次に deploy がログインしてから。 現在のセッションは変わらない。

確認

who と last は、それぞれどのファイルを読むか。

答え

who（と w）はいまのログインを utmp（/var/run/utmp）から、 last は過去のログインと再起動を wtmp（/var/log/wtmp）から読む。失敗は btmp（lastb）。 端末を持たないログインは記録されない。

この章で分かったこと

持ち帰ってほしいこと

  • ulimit のソフトはハードの範囲内で自由。ハードは一般ユーザには一方通行（下げられるが上げられない。上げられるのは root）
  • /etc/security/limits.conf は PAM がログイン時に読む。いま開いているシェルには効かない
  • who・w は utmp（いま）、last は wtmp（過去）、lastb は btmp（失敗）を読む
  • 端末を持たないログイン（ssh host コマンド・cron）は utmp に載らず who に出ない
  • TMOUT は無操作時間での自動ログアウト。本人が外せる「保険」であって強制ではない
