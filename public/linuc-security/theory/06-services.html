6. シャドウと、使っていないサービスを止める

「メンテナンス中はログインを止めたい」。/etc/nologin にメッセージを置けばよい——と思うと、自分（管理者）も次から入れなくなる。nologin は root 以外のすべてのログインを止めるからだ。いま開いているセッションだけが生き残る。締め出されたときにどう戻すかを、先に知っておく必要がある。

前提: 第5章まで読了前提: 練習機が起動している所要 16分影響度 B出題範囲 1.10.2（重要度3）最終検証 2026-10-13

この章のゴール

  • シャドウパスワード（/etc/passwd の x と /etc/shadow の分離）を説明できる
  • /etc/nologin の効き方と、締め出されたときの戻し方を言える
  • 使っていないサービスの止め方（systemctl・service・/etc/init.d・xinetd）を説明できる
ここで覚えなくていいこと: systemd のユニットファイルの細かい書き方、xinetd の各設定項目、SysV 初期化スクリプトの中身はレベル1では深追いしない。ここでは「どこを見れば有効/無効が分かり、どう止めるか」だけを扱う。

パスワードは passwd に無い

この節で分かること: x が指す先と、分離の理由。
$ grep "^student" /etc/passwd
student:x:1000:1000:LinuC student:/home/student:/bin/bash
$ sudo grep "^student" /etc/shadow | cut -c1-30
student:$y$j9T$zeB7kAA87DbMW.l
$ ls -l /etc/passwd /etc/shadow
-rw-r--r-- 1 root root   1580 Oct 13 10:56 /etc/passwd
-rw-r----- 1 root shadow 1026 Oct 13 10:57 /etc/shadow

/etc/passwd の2列目は x で、パスワードそのものは入っていない。実体のハッシュ（$y$... は yescrypt）は /etc/shadow にある。これがシャドウパスワードである。なぜ分けるか——権限を見れば分かる。/etc/passwd は 644（誰でも読める。id やファイル所有者の表示に名前⇔UID の対応が要る）。/etc/shadow は 640 で root と shadow グループしか読めない。ハッシュを誰でも読める表から追い出し、総当たり攻撃の材料を渡さないために分離した。

たとえ: /etc/passwd は会社の内線電話帳（誰でも見られる名前と番号）、/etc/shadow は人事だけが持つ給与・パスワード台帳に近い。電話帳の各行には「詳細は人事へ」（x）とだけ書いてある。
ただし崩れる点: 電話帳と台帳は別の棚だが、両方とも1つの建物（サーバ）の中にある。読めるかどうかは鍵（ファイル権限）が分けているだけで、物理的に離れてはいない。

nologin は、自分も締め出す

この節で分かること: /etc/nologin の効く範囲と戻し方。

ふつうこう考える

メンテナンス中に一般ユーザのログインを止めたい。/etc/nologin にメッセージを置けばよい。管理者の自分は、これまでどおり ssh で入れるだろう。

$ echo "メンテナンス中です" | sudo tee /etc/nologin
メンテナンス中です
$ vm ssh echo hello
▶ ssh linuc echo hello
メンテナンス中です

Connection closed by 127.0.0.1 port 2222
だめな理由: vm ssh（＝新しい ssh ログイン）が、/etc/nologin の中身を表示して接続を閉じられた。 /etc/nologin はroot 以外のすべてのログインを止める。student で入ろうとした自分も弾かれる。 救いは、すでに開いているセッションは生き残ることと、root は例外で入れること。 だから「置いた瞬間に全ロックアウト」ではないが、いま開いている窓を閉じたら、もう新しくは入れない。

締め出されたときの戻し方を知っておく。この教材の練習機では、外側のコンテナから3通りある。

$ lab-guest 'rm -f /etc/nologin && echo removed_by_root'
removed_by_root
戻し方どういう経路かいつ使うか
vm sshまだ ssh で入れるか試す締め出しが本当か確認する
vm consoleシリアルコンソール（画面）から直接ログインssh が塞がれたとき
lab-guest '…'ゲストエージェント経由で root としてコマンド実行ネットワークも ssh も壊れたとき
vm reset --yes練習機を工場出荷時に戻す最後の手段

lab-guest は ssh を通らない（仮想マシンのエージェント経由）ので、ネットワークや sshd を壊しても root として直せる。実践編の判定（lab check）もこの経路を使うので、読者が自分を締め出しても採点は止まらない。

たとえ: /etc/nologin は、店の入口に貼る「本日休業」の札に近い。来た客（新しいログイン）は札を見て帰る。だがすでに店内にいる人は追い出されない。
ただし崩れる点: 店主は裏口の鍵を持っているが、nologin で「本日休業」を貼った管理者も、いったん外に出たら正面（ssh）からは入れない。裏口（vm console / lab-guest）を覚えておかないと自分が締め出される。

使っていないサービスを止める

この節で分かること: 待ち受けを止める複数の道具と、その関係。

第4章で見つけた余計な待ち受けのように、使っていないネットワークサービスは止めるのがホストの基本である。いまの Ubuntu では systemctl が中心で、古い service コマンドもラッパとして残っている。

$ command -v update-rc.d service
/usr/sbin/update-rc.d
/usr/sbin/service
$ ls /etc/init.d/ | head -6
anacron
apparmor
apport
atd
console-setup.sh
cron
$ service --status-all 2>&1 | head -4
 [ + ]  anacron
 [ + ]  apparmor
 [ + ]  apport
 [ + ]  atd
道具何をする系統
systemctl start/stopいま起動/停止systemd（現行）
systemctl enable/disable次の起動で上がる/上がらないsystemd（現行）
service NAME startsystemctl へのラッパ（/etc/init.d も見る）互換
update-rc.dSysV 初期化スクリプトの自動起動を登録/解除Debian 系
chkconfig同じことを RHEL 系で行うRHEL 系

試験範囲には chkconfig も出るが、これはRHEL 系の道具で Ubuntu には無い。確かめられる。

$ command -v chkconfig || echo "chkconfig: なし（RHEL 系の道具）"
chkconfig: なし（RHEL 系の道具）

Debian 系で SysV スクリプトの自動起動を変えるのは update-rc.d である（chkconfig に相当）。いまは systemctl が /etc/init.d の古いスクリプトも面倒を見るので、ほとんどは systemctl で済む。

xinetd と inetd は、同時には入らない

この節で分かること: スーパーサーバの設定場所と、2実装の排他。

xinetd はスーパーサーバ——自分は待ち受けだけして、接続が来たら対応するサービスを起動する仕組みである。設定は /etc/xinetd.conf と /etc/xinetd.d/ にある。この練習機では入っているが止めてある。

$ ls /etc/xinetd.d/
chargen
chargen-udp
daytime
daytime-udp
discard
discard-udp
echo
echo-udp
servers
services
time
time-udp
$ systemctl is-enabled xinetd; systemctl is-active xinetd
disabled
inactive

試験範囲には、もう1つのスーパーサーバ inetd（設定は /etc/inetd.conf・/etc/inetd.d/）も並ぶ。だが探しても無い。

$ ls /etc/inetd.conf 2>&1
ls: cannot access '/etc/inetd.conf': No such file or directory

無いのには理由がある。xinetd と openbsd-inetd はどちらも同じ役割（inet-superserver）を提供し、互いに衝突するので、同時には入らない。

$ dpkg -s xinetd | grep -E "^(Package|Status|Provides|Conflicts):"
Package: xinetd
Status: install ok installed
Provides: inet-superserver
Conflicts: inet-superserver

Provides: inet-superserver と Conflicts: inet-superserver が同居している。「自分はスーパーサーバを提供する／スーパーサーバを名乗る別物とは共存しない」という宣言である。だから openbsd-inetd を入れようとすると、xinetd が消される（-s は実際には入れずに計画だけ出す）。

$ apt-get -s install openbsd-inetd 2>&1 | grep -A2 "REMOVED"
The following packages will be REMOVED:
  xinetd

第3章で見た主題1.09 の chrony と ntpsec（どちらも time-daemon を提供して衝突）とまったく同じ型である。試験には両方の名前が並ぶが、実機には片方しか入れられない。だから inetd.conf の書式は知識として覚え、手で触るのは入っている xinetd のほうで行う。

たとえ: xinetd と inetd は、同じ部署に2人は要らない受付係に近い。どちらも「来客を取り次ぐ」役なので、新しい受付（openbsd-inetd）を雇うと前任（xinetd）は解雇される。
ただし崩れる点: 人なら引き継ぎ期間を置けるが、パッケージの衝突は一瞬で、入れ替えると前任の設定（/etc/xinetd.d/）ごと消える。
たとえ: スーパーサーバ自体は、各店舗に店員を常駐させず、呼ばれたら駆けつける派遣の受付に近い。使う分だけメモリを食わない。
ただし崩れる点: 駆けつけに一瞬の遅れが出るので、常時高負荷のサービスには向かない。いまは各サービスが systemd のソケット起動（第4章の 22 番）で同じことをするので、xinetd の出番は減っている。
手を動かす: 実践編の演習03で、使っていないサービス（lab-echo）を systemctl disable --now で止め、次の起動でも上がらないことを確かめる。stop だけだと enabled のまま次回また上がることも、判定で分かる。
確認

/etc/nologin にメッセージを置いた。誰がログインできなくなるか。すでに入っている自分のセッションはどうなるか。

答え

root 以外のすべての新規ログインが止まる（メッセージを表示して接続が閉じる）。 すでに開いているセッションは生き残り、root は例外で入れる。自分も次からは入れないので、戻し方（vm console / lab-guest / vm reset）を用意しておく。

確認

いま xinetd が入っている。openbsd-inetd（inetd）を apt install するとどうなるか。

答え

xinetd が削除される。両方とも同じ inet-superserver を提供して衝突するので同時に入らない （主題1.09 の chrony と ntpsec が time-daemon で衝突するのと同じ型）。 dpkg -s xinetd の Provides/Conflicts と apt-get -s install で確かめられる。

確認

SysV サービスの自動起動を切り替えたい。RHEL 系の chkconfig が Ubuntu に無いとき、相当するコマンドは。

答え

update-rc.d（Debian 系）。ただし現行の Ubuntu では systemctl enable/disable が /etc/init.d の古いスクリプトも面倒を見るので、たいていは systemctl で済む。

この章で分かったこと

持ち帰ってほしいこと

  • /etc/passwd の x は「パスワードは /etc/shadow にある」印。passwd は 644、shadow は 640（root と shadow グループだけ）
  • /etc/nologin は root 以外の全ログインを止める。自分も次から入れない。既存セッションと root は例外。戻し方（vm console / lab-guest / vm reset）を先に用意する
  • サービスは systemctl が中心。service はラッパ、update-rc.d は Debian 系、chkconfig は RHEL 系で Ubuntu には無い
  • xinetd と openbsd-inetd は同じ inet-superserver を提供して衝突し、同時に入らない（chrony と ntpsec と同じ型）
