1. 入っているかどうかは、台帳が決める

パッケージの中身を自分の手で / に広げると、ファイルは置かれ、中の関数も動く。それでも dpkg は「そんなパッケージは無い」と答える。パッケージが「入っている」とは、ファイルがそこにあることではない。台帳に書かれていることである。

前提: Debian 系の檻を起動し直した直後前提: 後半の比較は RPM 系の檻所要 15分影響度 B出題範囲 1.04.1（重要度3）出題範囲 1.04.3（重要度3）最終検証 2026-10-13

この章のゴール

  • パッケージのファイルが「中身」と「名前・版・依存関係などの情報」の2つでできていることを、コマンドで示せる
  • 「入っているか」を答えているのがディスクではなく台帳だと説明できる
  • リポジトリが「中身の置き場」と「目録」でできていることを、ディレクトリを見て言える
ここで覚えなくていいこと: パッケージの作り方（dpkg-deb --build や rpmbuild の spec ファイル）、.deb の中の ar 形式や .rpm の中の cpio 形式の細部、zstd などの圧縮形式。この檻のパッケージがどう作られたかは配布元のリポジトリの containers/linuc-packages/ に置いてあるが、試験の範囲外である。

この章の出力は、Debian 系の檻を起動し直した直後から打ったものです。前の章で入れたものがあると、出力が変わります。檻は exit で抜けてもう一度 docker run すれば、最初の状態に戻ります（起動のしかたは実践編）。

パッケージは1つのファイルで、2つのものが入っている

この節で分かること: .deb ファイルの中に何が入っているか。

檻の中には、練習用のパッケージがいくつか置いてある。そのうち1つを見る。

$ ls -l /srv/lab-repo/pool/main/l/labapp/
total 4
-rw-r--r-- 1 root root 1076 Oct 13 09:57 labapp_1.0_all.deb
$ file /srv/lab-repo/pool/main/l/labapp/labapp_1.0_all.deb
/srv/lab-repo/pool/main/l/labapp/labapp_1.0_all.deb: Debian binary package (format 2.0), with control.tar.zst, data compression zst

1076 バイトのファイル1つである。file の答えに2つの名前が出ている。control（情報）と data（中身）だ。それぞれを開けて読むオプションがある。

$ dpkg-deb -I /srv/lab-repo/pool/main/l/labapp/labapp_1.0_all.deb

-I（info）が情報のほう、-c（contents）が中身のほうである。中身は / から見たパスの木になっていて、入れるとそのまま /etc/labapp.conf や /usr/bin/labapp に置かれる。

情報のほうで大事なのは Depends: の1行である。labapp は liblab の 1.0 以上が無いと動かない、と書いてある。これが依存関係で、パッケージ管理の道具はここを読んで「先に何が要るか」を判断する。欲しい欄だけ抜き出すこともできる。

$ dpkg-deb -f /srv/lab-repo/pool/main/l/labapp/labapp_1.0_all.deb Package Version Depends
Package: labapp
Version: 1.0
Depends: liblab (>= 1.0)

dpkg-deb -I と -c は、第4章で使う dpkg -I と dpkg -c と同じものである（dpkg がそのまま dpkg-deb に渡す）。試験では dpkg のほうの綴りで問われることが多い。

ファイル名にも情報が入っている。Debian 系と RPM 系で区切り方が違う。

形式ファイル名読み方
Debian 系（.deb）labapp_1.0_all.deb名前 _ 版 _ アーキテクチャ（all = どの CPU でもよい）
RPM 系（.rpm）labapp-1.0-1.noarch.rpm名前 - バージョン - リリース . アーキテクチャ（noarch = どの CPU でもよい）
たとえ: 送り状を同封した宅配の箱に近い。箱の中には品物（data）と、 品名・型番・「この部品と組み合わせて使うこと」と書いた紙（control）が入っている。
ただし崩れる点: 本物の送り状は箱の外に貼ってあり、開けずに読めるが、 .deb の control は箱の中にある。dpkg-deb -I は、箱を開けて紙だけ取り出して読んでいる。

置いただけでは、入ったことにならない

この節で分かること: 「入っている」かどうかを、誰が何を見て答えているか。

もう1つのパッケージ liblab の中身を、パッケージ管理を通さずに / へ広げてみる。dpkg-deb -x は「中身（data）を指定の場所に展開する」だけのオプションである。

ふつうこう考える

パッケージの中身を正しい場所に置けば、入れたのと同じことのはずだ。 ファイルがあって、中のものが動くなら、dpkg に聞いても「入っている」と答えるだろう。

$ sudo dpkg-deb -x /srv/lab-repo/pool/main/libl/liblab/liblab_1.0_all.deb /
$ ls -l /usr/lib/liblab/liblab.sh
-rw-r--r-- 1 root root 106 Oct  1 09:00 /usr/lib/liblab/liblab.sh
$ . /usr/lib/liblab/liblab.sh; lab_greet "ファイルは置けた"
liblab: ファイルは置けた
$ dpkg -l liblab; echo "exit=$?"
dpkg-query: no packages found matching liblab
exit=1
$ dpkg -S /usr/lib/liblab/liblab.sh; echo "exit=$?"
dpkg-query: no path found matching pattern /usr/lib/liblab/liblab.sh
exit=1
だめな理由: ファイルは置かれ、中の関数 lab_greet も動いた。 それでも dpkg -l は「そんなパッケージは見つからない」、dpkg -S は 「そのパスを持つパッケージは無い」と答えた。どちらもディスクを見ていない。 dpkg が自分で書いている台帳（/var/lib/dpkg/）を見ている。 dpkg-deb -x は箱を開けて中身を並べただけで、台帳には1行も書かない。 だから dpkg から見ると、このファイルは「誰のものでもない」。

同じファイルを、今度は dpkg -i（install）で入れる。

$ sudo dpkg -i /srv/lab-repo/pool/main/libl/liblab/liblab_1.0_all.deb
Selecting previously unselected package liblab.
(Reading database ... 12824 files and directories currently installed.)
Preparing to unpack .../libl/liblab/liblab_1.0_all.deb ...
Unpacking liblab (1.0) ...
Setting up liblab (1.0) ...
$ dpkg -l liblab
Desired=Unknown/Install/Remove/Purge/Hold
| Status=Not/Inst/Conf-files/Unpacked/halF-conf/Half-inst/trig-aWait/Trig-pend
|/ Err?=(none)/Reinst-required (Status,Err: uppercase=bad)
||/ Name           Version      Architecture Description
+++-==============-============-============-====================================
ii  liblab         1.0          all          small shell library for lab programs
$ dpkg -S /usr/lib/liblab/liblab.sh
liblab: /usr/lib/liblab/liblab.sh

置かれたファイルは同じなのに、答えが変わった。dpkg -i がやったことは、展開（Unpacking）と設定（Setting up）と、その間に台帳へ書き込むことである。最初の行の (Reading database ...) は、台帳を読み込んでいるところだ。

台帳の中身を直接見る。

/var/lib/dpkg/info/liblab.md5sums
$ cat /var/lib/dpkg/info/liblab.list

$ grep -A10 '^Package: liblab$' /var/lib/dpkg/status

台帳はテキストファイルの集まりである。役割を並べる。

台帳のファイル書いてあること読むコマンド（第4章）
/var/lib/dpkg/statusパッケージごとの状態・版・依存関係（この檻では 166 件）dpkg -l dpkg -s
/var/lib/dpkg/info/<名前>.listそのパッケージが置いたファイルの一覧dpkg -L dpkg -S
/var/lib/dpkg/info/<名前>.md5sums置いたときの中身の要約（ダイジェスト）dpkg -V

dpkg -S が答えられるようになったのは、liblab.list にパスが1行書かれたからである。ファイルが増えたからではない。

たとえ: 引っ越しと住民票に近い。荷物を新居に運び込めば暮らせるが、 転入届を出さなければ、役所の台帳ではその人はそこに住んでいない。 dpkg-deb -x は届けを出さない引っ越しで、dpkg -i は届けを出す引っ越しである。
ただし崩れる点: 住民票は本人が窓口で書くが、dpkg の台帳を書けるのは dpkg だけである。 利用者が台帳を手で直す手段は用意されていない（直すとそれ自体が壊れる原因になる）。

RPM 系でも、同じことが起きる

この節で分かること: RPM 系の台帳の場所と、同じ確かめ方。

RPM 系の檻に入って、同じことをする。.rpm にも情報と中身が入っている。

$ file /srv/lab-rpm/labapp-1.0-1.noarch.rpm
/srv/lab-rpm/labapp-1.0-1.noarch.rpm: RPM v3.0 bin i386/x86_64 labapp-1.0-1
$ rpm -qpi /srv/lab-rpm/labapp-1.0-1.noarch.rpm
Name        : labapp
Version     : 1.0
Release     : 1
Architecture: noarch
Install Date: (not installed)
...

$ rpm -qpR /srv/lab-rpm/labapp-1.0-1.noarch.rpm

-q は問い合わせ（query）、p は「台帳ではなく、このパッケージファイルに聞け」、i が情報・l がファイル一覧・R が依存関係（requires）である。liblab >= 1.0 が Debian の Depends: にあたる。Install Date: (not installed) は、まだ台帳に無いことを表している。

中身だけを広げる道具は rpm2cpio である（.rpm の中身を cpio 形式で取り出し、cpio が展開する）。

./usr/lib/liblab/liblab.sh
1 block
$ ls -l /usr/lib/liblab/liblab.sh

$ rpm -q liblab; echo "exit=$?"

exit=1
$ rpm -qf /usr/lib/liblab/liblab.sh; echo "exit=$?"

$ sudo rpm -ivh /srv/lab-rpm/liblab-1.0-1.noarch.rpm

$ rpm -q liblab

$ rpm -qf /usr/lib/liblab/liblab.sh
liblab-1.0-1.noarch
$ ls /var/lib/rpm/

rpmdb.sqlite-wal

答え方まで同じである。RPM 系の台帳は /var/lib/rpm/ の SQLite のデータベースで、dpkg と違ってテキストではない。だから中を見るときは必ず rpm -q を通す。

聞きたいことDebian 系RPM 系
台帳の場所/var/lib/dpkg/（テキスト）/var/lib/rpm/（データベース）
このパッケージは入っているかdpkg -l 名前rpm -q 名前
このファイルはどのパッケージのものかdpkg -S パスrpm -qf パス
ファイル（.deb / .rpm）の情報dpkg -I ファイルrpm -qpi ファイル
ファイル（.deb / .rpm）の中身の一覧dpkg -c ファイルrpm -qpl ファイル
台帳を通さずに中身だけ広げるdpkg-deb -x ファイル 先rpm2cpio ファイル | cpio -idmv

リポジトリは、中身の置き場と目録でできている

この節で分かること: apt や yum が「どこから」「何を見て」パッケージを持ってくるか（第2章からの前置き）。

この教材の7章は、全部この2冊の帳簿の話である。第2章から第4章で Debian 系を、第5章から第7章で RPM 系を見る。

たとえ: 図書館の蔵書目録と、自分の本棚の記録に近い。 目録を見れば「借りられる本」が分かり、本棚の記録を見れば「いま手元にある本」が分かる。 同じ本について2つが違うことを言うのは、当然である。
ただし崩れる点: 図書館の目録は図書館へ行けば最新のものが見られるが、 apt の目録は手元に取ってきた写しで、取り直すまで古いままである。第3章はこの差が主役になる。
手を動かす: 実践編の演習03は、配られた .deb を dpkg -I と dpkg -c で読んでから入れる課題である。 判定は、ファイルがあるかではなく、dpkg の台帳が ii（入っていて設定済み）になったかを見る。
確認

パッケージ foo の中身を dpkg-deb -x foo_1.0_amd64.deb / で展開した。 このあと dpkg -S /usr/bin/foo を実行すると、何が返るか。

答え

「そのパスを持つパッケージは無い」（dpkg-query: no path found matching pattern /usr/bin/foo）が返る。 dpkg -S が読むのは dpkg の台帳（/var/lib/dpkg/info/*.list）で、 dpkg-deb -x は台帳に何も書かないからである。実測では dpkg -l も「見つからない」と答えた。 RPM 系の rpm2cpio | cpio -idmv と rpm -qf でも同じことが起きる。

確認

次の2つのファイル名から、パッケージ名・版・アーキテクチャを読み取れ。
nginx_1.24.0-2ubuntu7_amd64.deb と nginx-1.20.1-22.el9.x86_64.rpm

答え

.deb は _ 区切りで、名前 nginx・版 1.24.0-2ubuntu7・アーキテクチャ amd64。 .rpm は名前 nginx・バージョン 1.20.1・リリース 22.el9・アーキテクチャ x86_64。 .rpm は名前・バージョン・リリースを - で、アーキテクチャを . でつなぐ。 CPU を問わないものは .deb が all、.rpm が noarch である。

確認

まだインストールしていない .rpm ファイルについて、中に含まれるファイルの一覧を表示するコマンドはどれか。
(a) rpm -ql pkg.rpm　(b) rpm -qpl pkg.rpm　(c) rpm -qf pkg.rpm　(d) rpm -V pkg.rpm

答え

(b)。p が「台帳ではなくパッケージファイルに聞け」の印である。 (a) は台帳に聞くので、入っていなければ package … is not installed になる。 Debian 系なら dpkg -c pkg.deb（= dpkg-deb -c）が同じ役をする。

この章で分かったこと

持ち帰ってほしいこと

  • パッケージのファイルは「中身」と「情報（名前・版・依存関係）」の2つでできている。.deb は dpkg -I / -c、.rpm は rpm -qpi / -qpl / -qpR で読める
  • 「入っているか」に答えているのはディスクではなく台帳（/var/lib/dpkg/・/var/lib/rpm/）。中身だけ広げても（dpkg-deb -x・rpm2cpio）台帳には載らない
  • 台帳を書くのは dpkg -i と rpm -i。dpkg -S と rpm -qf は台帳のファイル一覧を引いている
  • リポジトリは中身の置き場（pool/・.rpm）と目録（dists/…/Packages・repodata/）でできている
  • 同じパッケージについて apt-cache policy と dpkg -l が違うことを言うのは、目録と台帳という別の帳簿を読んでいるから
