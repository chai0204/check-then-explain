3. 目録は、取りに行くまで古いまま

リポジトリを1行書き足して apt install と打つと、Unable to locate package（見つからない）と言われる。パッケージのファイルはすぐそこにあるのに。apt が見ているのは書いた1行ではなく、手元に取ってきた目録の写しだからだ。

前提: 第2章まで読了前提: Debian 系の檻を起動し直した直後所要 20分影響度 B出題範囲 1.04.1（重要度3）最終検証 2026-10-13

この章のゴール

  • /etc/apt/sources.list の1行（種類・URI・ディストリビューション・コンポーネント）を読み書きできる
  • apt update が何をどこへ取ってくるかを、/var/lib/apt/lists/ で示せる
  • 入っていないパッケージも含めて「このファイルはどのパッケージにあるか」を apt-file で調べられ、dpkg -S との違いを言える
ここで覚えなくていいこと: リポジトリに署名する手順（gpg で Release に署名する作業）、鍵の配り方（/etc/apt/keyrings/ の運用）、ミラーの選び方、deb-src を使ったソースパッケージの取得。Signed-By: と [trusted=yes] は「署名を確かめる鍵を指定する／確かめない」とだけ分かれば足りる。

どこから取るかの表

この節で分かること: apt が「どこへ取りに行くか」を書いた2つの形式。
$ cat /etc/apt/sources.list
# Ubuntu sources have moved to the /etc/apt/sources.list.d/ubuntu.sources
# file, which uses the deb822 format. Use deb822-formatted .sources files
# to manage package sources in the /etc/apt/sources.list.d/ directory.
# See the sources.list(5) manual page for details.

# 檻の中の練習用リポジトリ（確かめて説明する LinuC 主題1.04）。
# 署名していないので [trusted=yes] で署名の確認を外している。本物のリポジトリでは外さない。
deb [trusted=yes] file:/srv/lab-repo lab main

試験が問うのはこの最後の1行の形式である。空白で区切って4つ（[ ] は任意）。

deb  [trusted=yes]  file:/srv/lab-repo  lab                    main
^^^  ^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^  ^^^                    ^^^^
種類  オプション      URI（どこ）          ディストリビューション   コンポーネント（複数並べられる）

種類: deb = バイナリパッケージ / deb-src = ソースパッケージ

Ubuntu 本体の分は、コメントにあるとおり別のファイルに移っている。

$ ls -l /etc/apt/sources.list.d/
total 4
-rw-r--r-- 1 root root 196 Sep 30 19:04 ubuntu.sources
$ cat /etc/apt/sources.list.d/ubuntu.sources
Types: deb
URIs: https://snapshot.ubuntu.com/ubuntu/20260929T000000Z
Suites: noble noble-updates noble-security
Components: main universe
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg

これは deb822 形式という書き方で、Ubuntu 24.04 からの既定である。中身は同じ4つで、欄の名前が付いている。

1行形式（sources.list・*.list）deb822 形式（*.sources）
debTypes: deb
URIURIs:
ディストリビューション（1つ）Suites:（複数並べられる）
コンポーネントComponents:
[signed-by=鍵のファイル]Signed-By:
[trusted=yes]Trusted: yes

上の ubuntu.sources を1行形式で書くと、Suites: の数だけ3行になる（deb [signed-by=…] https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble main universe と、noble-updates・noble-security の行）。/etc/apt/sources.list.d/ には、名前が .list（1行形式）か .sources（deb822 形式）で終わるファイルを何個でも置ける。どちらも /etc/apt/sources.list と同じ扱いで読まれる。

4つの欄は、リポジトリのディレクトリにそのまま対応している。

$ find /srv/lab-repo/dists -type f | sort
/srv/lab-repo/dists/lab/Release
/srv/lab-repo/dists/lab/main/Contents-amd64
/srv/lab-repo/dists/lab/main/Contents-amd64.gz
/srv/lab-repo/dists/lab/main/binary-amd64/Packages
/srv/lab-repo/dists/lab/main/binary-amd64/Packages.gz
file:/srv/lab-repo  /dists/  lab  /  main  /binary-amd64/Packages
URI                          ディストリ  コンポーネント  CPU（自分のアーキテクチャ）

apt は1行を読むと、このパスを組み立てて取りに行く。Release は「このディストリビューションにどの目録があり、それぞれの中身の要約（ダイジェスト）がいくつか」を書いた、目録の目録である。

$ head -9 /srv/lab-repo/dists/lab/Release
Architectures: amd64
Codename: lab
Components: main
Date: Tue, 13 Oct 2026 00:57:22 +0000
Description: LinuC 1.04 practice repository (lab)
Label: lab lab
Origin: check-then-explain
Suite: lab
MD5Sum:
たとえ: 取引先の住所録に近い。住所録には「どこの会社の、どの部署の、どの棚に、カタログがあるか」が書いてある。
ただし崩れる点: 住所録に書き足しても、カタログは向こうから送られてこない。 apt は、利用者が「取りに行け」と言うまで、書き足した住所へ一度も行かない。次の節はそれを確かめる。

1行足しても、まだ何も知らない

この節で分かること: リポジトリを足したあと、入れられるようになるまでに要ること。

檻の中にはまだ使っていないリポジトリ /srv/lab-extra がある。labextra というパッケージが1つ入っている。

$ find /srv/lab-extra -type f | sort
/srv/lab-extra/dists/extra/Release
/srv/lab-extra/dists/extra/main/Contents-amd64
/srv/lab-extra/dists/extra/main/Contents-amd64.gz
/srv/lab-extra/dists/extra/main/binary-amd64/Packages
/srv/lab-extra/dists/extra/main/binary-amd64/Packages.gz
/srv/lab-extra/pool/main/l/labextra/labextra_1.0_all.deb

ディストリビューションは extra、コンポーネントは main である。1行書く。

ふつうこう考える

どこにあるかを apt のソースに書いたのだから、もう apt install labextra で入れられるはずだ。 パッケージのファイルは、すぐそこにある。

$ echo 'deb file:/srv/lab-extra extra main' | sudo tee /etc/apt/sources.list.d/lab-extra.list
deb file:/srv/lab-extra extra main
$ apt-cache policy labextra
$ sudo apt install -y labextra; echo "exit=$?"
...
E: Unable to locate package labextra
exit=100
だめな理由: apt-cache policy は1行も返さず、apt install は 「そんなパッケージは見つからない」で止まった。apt が引くのは sources.list ではなく、 /var/lib/apt/lists/ に置いた目録の写しである。sources.list は 「どこへ取りに行くか」の表にすぎず、書いただけでは何も取りに行かない。 写しを作り直すのが apt update で、それまで apt は新しいリポジトリの中身を1つも知らない。

写しの置き場を見ておく。いまある目録の写しはこれだけである。

$ ls -1 /var/lib/apt/lists/ | grep -v -e lock -e partial -e auxfiles
_srv_lab-repo_dists_lab_Release
_srv_lab-repo_dists_lab_main_Contents-amd64.lz4
_srv_lab-repo_dists_lab_main_binary-amd64_Packages.lz4
snapshot.ubuntu.com_ubuntu_20260929T000000Z_dists_noble-security_InRelease
snapshot.ubuntu.com_ubuntu_20260929T000000Z_dists_noble-security_main_binary-amd64_Packages.lz4
...
snapshot.ubuntu.com_ubuntu_20260929T000000Z_dists_noble_universe_binary-amd64_Packages.lz4

ファイル名は、取りに行った場所のパスの / を _ に置き換えたものである。lab-extra の分はまだ無い。

取りに行く。ただし、署名の無い目録は受け取らない

この節で分かること: apt update の出力の読み方と、[trusted=yes] が何をしているか。
$ sudo apt update; echo "exit=$?"
...
Get:1 file:/srv/lab-repo lab InRelease
Ign:1 file:/srv/lab-repo lab InRelease
Get:2 file:/srv/lab-extra extra InRelease
Ign:2 file:/srv/lab-extra extra InRelease
Get:3 file:/srv/lab-repo lab Release [1983 B]
Get:4 file:/srv/lab-extra extra Release [1991 B]
...
Get:6 file:/srv/lab-extra extra Release.gpg
Ign:6 file:/srv/lab-extra extra Release.gpg
Hit:7 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble InRelease
Hit:8 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble-updates InRelease
Hit:9 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble-security InRelease
Reading package lists...
E: The repository 'file:/srv/lab-extra extra Release' is not signed.
exit=100
$ ls -1 /var/lib/apt/lists/ | grep lab-extra; echo "exit=$?"
exit=1

取りには行ったが、受け取らなかった。Release.gpg（Release への署名）が無く、is not signed（署名されていない）として捨てている。写しは1つも増えていない。apt は「誰が作った目録か確かめられないもの」を既定では信用しない。Ubuntu 本体の行にある Signed-By: は、その確かめに使う鍵を指定している。

この練習用リポジトリには署名をしていないので、確認を外す印 [trusted=yes] を付ける。本物のリポジトリではこれを付けない。偽物の目録を区別する手段を自分で捨てることになるからだ。

$ echo 'deb [trusted=yes] file:/srv/lab-extra extra main' | sudo tee /etc/apt/sources.list.d/lab-extra.list
deb [trusted=yes] file:/srv/lab-extra extra main
$ sudo apt update
...
Get:6 file:/srv/lab-extra extra Release.gpg
Ign:6 file:/srv/lab-extra extra Release.gpg
Get:7 file:/srv/lab-extra extra/main amd64 Packages [448 B]
Get:8 file:/srv/lab-extra extra/main amd64 Contents (deb) [44 B]
Hit:9 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble InRelease
Hit:10 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble-updates InRelease
Hit:11 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble-security InRelease
Reading package lists...
Building dependency tree...
Reading state information...
3 packages can be upgraded. Run 'apt list --upgradable' to see them.
$ ls -1 /var/lib/apt/lists/ | grep lab-extra
_srv_lab-extra_dists_extra_Release
_srv_lab-extra_dists_extra_main_Contents-amd64.lz4
_srv_lab-extra_dists_extra_main_binary-amd64_Packages.lz4
$ apt-cache policy labextra
labextra:
  Installed: (none)
  Candidate: 1.0
  Version table:
     1.0 500
        500 file:/srv/lab-extra extra/main amd64 Packages
$ sudo apt install -y labextra
...

  labextra
...

$ labextra
labextra 1.0 (/srv/lab-extra から入った)

今度は Packages と Contents を取ってきて（Get:7・Get:8）、写しが3つ増えた。そこで初めて Candidate: 1.0 が出て、入れられた。apt update の行頭の印はこう読む。

印意味
Hit前回取ったものから変わっていなかった（取り直さなかった）
Get取った
Ign無かったが、無くてもよいものなので無視した（ここでは署名ファイル）
Err取れなかった（ネットにつながらない等）

Ubuntu 本体の3行が Hit なのは、この檻が最初から目録の写しを持っていて、snapshot（2026-09-29 で止めた Ubuntu の写し）がそれから変わっていないからである。ネットにつながっていない環境では、この3行が Err や Ign になり、警告が出る。それでも手元の古い写しが残るので、檻の中の練習用リポジトリは同じように使える。

リポジトリの1行を書き換えたら、apt update までが1組の作業である。apt edit-sources と打つと sources.list をエディタで開けるが、これも書き換えるだけで、取りには行かない。

たとえ: 差出人の印が押された封書だけを受け取る受付に近い。 印の無い封書は、中身を読む前に送り返す。Signed-By: は「この印鑑なら本物」という見本の登録で、 [trusted=yes] は「この差出人からは印が無くても受け取る」という例外の指示である。
ただし崩れる点: 受付の人は封書の見た目の怪しさにも気づけるが、apt は署名の有無しか見ない。 例外を指示した差出人から偽物が届いても、そのまま受け取る。

ファイル名から探す — apt-file

この節で分かること: 入っていないパッケージの中のファイルを、どの目録で引くか。

「このファイルはどのパッケージにあるか」を答えるコマンドは、第1章で dpkg -S を見た。いまの檻には liblab が入っていない（起動し直した直後なので）。

$ dpkg -S liblab.sh; echo "exit=$?"
dpkg-query: no path found matching pattern *liblab.sh*
exit=1
$ apt-file search liblab.sh
liblab: /usr/lib/liblab/liblab.sh
$ apt-file search bin/labapp
labapp: /usr/bin/labapp
$ apt-file list labapp
labapp: /etc/labapp.conf
labapp: /usr/bin/labapp
labapp: /usr/share/doc/labapp/README
$ apt-file search labextra
labextra: /usr/bin/labextra

dpkg -S は台帳（入っているパッケージのファイル一覧）しか引けない。apt-file は目録のほうを引く。ただし Packages ではない。Packages にあるのは名前と説明文と依存関係だけで、中のファイルの一覧は無いからだ。apt-file が読むのは Contents という別の目録で、さっきの apt update で Contents (deb) として取ってきたものである。

$ ls -1 /var/lib/apt/lists/ | grep Contents
_srv_lab-extra_dists_extra_main_Contents-amd64.lz4
_srv_lab-repo_dists_lab_main_Contents-amd64.lz4
聞きたいこと入っているものだけ（台帳）入っていなくてよい（目録の Contents）
このファイルはどのパッケージにあるかdpkg -S パスapt-file search パス
このパッケージにはどのファイルがあるかdpkg -L 名前apt-file list 名前
索引を新しくする（要らない。入れたときに書かれる）apt-file update（= Contents だけの apt update）

この檻では、apt-file の目録を練習用リポジトリの分だけに絞ってある。だから本物のコマンドを探しても見つからない。

$ apt-file search bin/dig; echo "exit=$?"
exit=1
$ grep -v "^//" /etc/apt/apt.conf.d/60lab-apt-file
Acquire::IndexTargets::deb::Contents-deb-legacy::DefaultEnabled "false";

Ubuntu の Contents は1スイートにつき 51〜75MB（gzip 圧縮後）あり、noble・noble-updates・noble-security の3つで約 195MB になる。apt-file を入れたままだと apt update のたびにそれを取りに行くので、この檻では止めた（設定ファイルのコメントに理由を書いてある）。実機で apt-file search bin/dig と打てば、bind9-dnsutils: /usr/bin/dig のように答えが出る。止めた設定を消して apt update すれば、この檻でも同じになる。

$ sudo apt-file update
Get:1 file:/srv/lab-repo lab InRelease
Ign:1 file:/srv/lab-repo lab InRelease
...
Hit:9 https://snapshot.ubuntu.com/ubuntu/20260929T000000Z noble-security InRelease
Reading package lists...

apt-file update の中身は apt update と同じ処理である（今の apt-file は、目録を取ることを apt に任せている）。

たとえ: 本の目次と巻末の索引に近い。目次（Packages）では章の題名（パッケージ名と説明）しか分からないが、 巻末の索引（Contents）を引けば、ある言葉（ファイル名）がどの章にあるかが分かる。
ただし崩れる点: 本の索引は本と一緒に手元に来るが、Contents は別に取りに行く目録で、 しかも目次よりずっと大きい。だから取らない設定にもできるし、取っていなければ引けない。
手を動かす: 実践編の演習02は、まだソースに入っていないリポジトリから、名前の分からないパッケージに入っている labcalc コマンドを使えるようにする課題である。 1行書く・目録を取りに行く・Contents を引く、の3つが要る。判定は labcalc を実際に動かし、dpkg の台帳と apt の目録を見る。
確認

/etc/apt/sources.list の次の1行について、各欄の意味を答えよ。
deb http://jp.archive.ubuntu.com/ubuntu noble main restricted

答え

deb がバイナリパッケージの取得先であること（ソースパッケージなら deb-src）、 http://jp.archive.ubuntu.com/ubuntu がリポジトリの URI、 noble がディストリビューション（スイート）、main restricted がコンポーネント（2つ並べてある）。 apt はこれを …/ubuntu/dists/noble/main/binary-amd64/Packages のようなパスに組み立てて取りに行く。

確認

/etc/apt/sources.list.d/ に新しいリポジトリの行を足した。続けて apt install したところ E: Unable to locate package になった。まず実行すべきコマンドは何か。

答え

apt update（または apt-get update）。apt が引くのは /var/lib/apt/lists/ の目録の写しで、 行を足しただけでは写しは作られない。実測では、署名の無いリポジトリだと apt update も is not signed で受け取りを断った。その場合は鍵（signed-by）を指定する。

確認

インストールされていないパッケージも含めて、/usr/bin/xyz というファイルを含むパッケージを探すコマンドはどれか。
(a) dpkg -S /usr/bin/xyz　(b) dpkg -L xyz　(c) apt-file search /usr/bin/xyz　(d) apt-cache search xyz

答え

(c)。(a) は入っているパッケージしか引けない（台帳を読むため）。(b) はパッケージ名からファイルの一覧を出すもので向きが逆。 (d) は名前と説明文の検索で、ファイル名は見ない。apt-file が引く Contents の目録は、 先に apt-file update（または apt update）で取ってきておく必要がある。

確認

apt update の出力に Hit: と Get: の行がある。それぞれ何を表すか。

答え

Hit は前回取った目録から変わっていなかったので取り直さなかったこと、Get は取ってきたことを表す。 Ign は無くてもよいもの（署名ファイルなど）が無かったので無視したこと、Err は取れなかったこと。

この章で分かったこと

持ち帰ってほしいこと

  • /etc/apt/sources.list の1行は「種類（deb / deb-src）・URI・ディストリビューション・コンポーネント」。Ubuntu 24.04 は /etc/apt/sources.list.d/*.sources の deb822 形式が既定
  • apt が引くのは /var/lib/apt/lists/ の目録の写し。ソースを書いただけでは写しは変わらず、apt update で初めて取りに行く
  • 署名の無い目録は is not signed で受け取らない。Signed-By で鍵を指定するのが本来の形で、[trusted=yes] は確かめるのをやめる指示
  • ファイル名からパッケージを引くとき、入っているものなら dpkg -S（台帳）、入っていなくてよいなら apt-file search（目録の Contents）
  • Contents は Packages とは別の、大きな目録。apt-file update か apt update で取る
