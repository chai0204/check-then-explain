9. RPM 系で同じことをする

前の章までにやったこと: Debian 系の檻で、パッケージを入れて使って消し、入っているもの・置かれたファイル・台帳・依存関係・リポジトリを調べ、.deb ファイルから入れ、自分で作った（第1〜8章）。この章でやること: RPM 系の Linux に移る。RPM 系は、Red Hat Enterprise Linux（RHEL）と、それと同じ作りの AlmaLinux などで、apt の代わりに yum、dpkg の代わりに rpm を使う。第1〜5章と同じこと ── 入れて・使って・消す、何が入っていてどこに置かれたか、台帳、依存関係 ── を、yum と rpm でやる。

前提: 第8章まで読了前提: RPM 系の檻を起動し直した直後所要 24分影響度 B出題範囲 1.04.3（重要度3）出題範囲 1.04.4（重要度1）最終検証 2026-10-20

この章のゴール

  • sudo yum install・sudo yum remove でパッケージを入れて消し、出力の表と [y/N] の問いを読む
  • 入っているものと置かれたファイルを、rpm -qa・-q・-qi・-ql・-qf・-qd・-qc と yum list installed で調べる
  • RPM 系の台帳がどこにあり、どう読むのかを確かめる
  • 依存関係のあるパッケージを yum remove で消すと、一緒に入ったものがどうなるかを確かめる
ここで覚えなくていいこと: yum の設定ファイルとリポジトリの書き方、署名、rpm でファイルから直接入れる方法、rpm -qR に出る rpmlib(…) の行の細部、台帳を収めたファイルの形式の細部。この章は「Debian 系でやったことを、RPM 系の名前で1回やる」ができれば足りる。

RPM 系の檻を起動する

この節で分かること: 第9〜11章で使う檻の起動のしかた。

Debian 系の檻を exit で抜け、あなたの PC の端末で次の1行を打つ。第9〜11章は、この RPM 系の檻（AlmaLinux 9.7）を使う。起動のしかたの部品は第1章と同じで、名前とイメージだけが違う。

前の版（1.0.x）でこの教材の演習を進めたことがある人は、起動する前に、実践編の「はじめる」の「前の版（1.0.x）で進めた人へ」の箱を読む。RPM 系の檻のボリュームにも、前の版の進み具合が残っている。

docker run --rm -it --name lab-linuc-packages-rpm --hostname linuc \
  -v lab-linuc-packages-rpm-work:/home/lab/work \
  -v lab-linuc-packages-rpm-state:/home/lab/.lab \
  ghcr.io/chai0204/lab-linuc:packages-rpm-1.1.0@sha256:__DIGEST__

ここでも、章ごとに檻を起動し直してから打つ。檻の中で打つコマンドの枠には「RPM 系の檻」と書いてある。

入れて、使って、消す — yum

この節で分かること: yum で入れて消すときの打ち方と、出力の読み方。

第1章と同じく、まだ入っていない。RPM 系でパッケージを入れるのは yum install である。root の権限が要るのも同じである。

行意味

Is this ok [y/N]:続けてよいか。大文字の N が既定で、何も打たずに Enter を押すと「いいえ」になり、入れずに終わる。apt の [Y/n] と逆なので、y を打ってから Enter
Running transaction の下実際に置いている（Installing）・確かめている（Verifying）。Running scriptlet は、入れたときに動く手順（scriptlet）を動かした行（表の下で説明する）
Installed: と Complete!入れたものと、全部終わったという知らせ

Running scriptlet の行には labhello の名前が付いているが、labhello 自身は手順を持っていない。ここで動いたのは、man-db（説明書の索引を受け持つパッケージ）が「説明書の置き場にファイルが置かれたら動く」と登録しておいた手順で、名前の欄には、そのとき入れたパッケージが出る。この檻では、その手順は索引を作り直さない（作り直しを、檻では動いていない別のしくみに頼むため）。

RPM 系では、パッケージの版を「版-リリース」で書く。1.0-1 は、版 1.0 を作った1回目という意味である。noarch は Debian 系の all にあたり、どの CPU でも動くという印である。

labhello 1.0
$ sudo yum remove labhello

$ labhello

$ hash -r

消すのは yum remove である（Removing: の表が出て、Erasing の行で外している。表の Repository の欄の @lab は「リポジトリ lab から入ったもの」という印）。消したあとの bash の言い方も、hash -r で戻るのも第1章と同じである。

たとえ: 同じ仕事を、別の会社の書式でやるのに近い。「入れる・使う・消す」の流れも、root の権限が要ることも同じで、伝票（出力）の見た目が違う。
ただし崩れる点: 書式の違いなら読み替えれば済むが、確認の問いは既定が逆である。apt の [Y/n] は Enter だけで「はい」になり、yum の [y/N] は Enter だけで「いいえ」になる。

何が入っていて、どこに置かれたか — rpm -q

この節で分かること: 第2・3章で dpkg に聞いたことを、rpm に聞く方法。

rpm は、RPM 系でパッケージのファイルを実際に置いたり外したりし、台帳を持っている道具である（Debian 系の dpkg にあたる。yum は中でこれを使っている）。-q（query）で台帳に問い合わせる。labhello をもう一度入れてから聞く（入れる出力は略す）。

$ sudo yum install labhello
...
Installing:
 labhello            noarch            1.0-1               lab            7.4 k

...
Is this ok [y/N]: y
...
Installed:
  labhello-1.0-1.noarch

Complete!

-qa（all）は、入っているもの全部を1行に1つずつ出す。全部だと長いので、行の数だけを数える。wc -l は、受け取った行の数を出すコマンドである。

$ rpm -qa | wc -l
182

この檻には 182 個のパッケージが入っている。名前で絞ることもできる。

$ rpm -qa 'lab*'
labmotd-1.0-1.noarch
labhello-1.0-1.noarch

labmotd は、この檻に最初から入っているものである。答えは「名前-版-リリース.アーキテクチャ」の形で並ぶ。1つの名前を渡す -q 名前 は、入っていればその版を答える。

$ rpm -q labhello
labhello-1.0-1.noarch

yum でも、入っているものの一覧を出せる。

$ yum list installed 'lab*'
Installed Packages
labhello.noarch                            1.0-1                            @lab
labmotd.noarch                             1.0-1                            @lab

右端の @lab は「リポジトリ lab から入った」という印である。1つを詳しく見るのは -qi（info）である。

$ rpm -qi labhello

Version     : 1.0
Release     : 1
Architecture: noarch
Install Date: Tue Oct 20 21:40:37 2026
Group       : Unspecified
Size        : 382

A tiny package used to practice upgrades.

第2章の dpkg -s にあたる。欄はこう読む。

欄何のためにあるかdpkg -s では
Name・Version・Release名前・版・その版を作った回数（1.0-1 の 1）Package・Version
Architectureどの CPU 向けか（noarch はどれでも動く）Architecture（all）
Install Date入れた日時（あなたの画面では違う）—

Signature作った人が付けた署名（作った人を確かめるための印）の情報。この章では使わない—

Packager・Vendor・URL作った人・配っている組織・案内のページ。不具合を誰に知らせるかを知るMaintainer
Summary・Description短い説明と長い説明Description の1行目と2行目から

置かれたファイルは -ql（list）、ファイルからパッケージは -qf（file）で引く。

$ rpm -ql labhello
/usr/bin/labhello
/usr/share/doc/labhello/README
/usr/share/man/man1/labhello.1.gz
$ rpm -qf /usr/bin/labhello
labhello-1.0-1.noarch
$ rpm -qf /etc/sudoers
sudo-1.9.5p2-15.el9_7.x86_64

置き場所は Debian 系と同じで、コマンドは /usr/bin、説明書は /usr/share/doc と /usr/share/man である。/etc/sudoers は sudo パッケージが置いたもので、el9_7 は RHEL 9（の 9.7）向けに作った印、x86_64 は Debian 系の amd64 にあたる CPU の名前である。説明書だけ・設定ファイルだけを出すこともできる。

$ rpm -qd labhello
/usr/share/doc/labhello/README
/usr/share/man/man1/labhello.1.gz
$ rpm -qc sudo
/etc/dnf/protected.d/sudo.conf
/etc/pam.d/sudo
/etc/pam.d/sudo-i
/etc/sudo-ldap.conf
/etc/sudo.conf
/etc/sudoers

-qd（docs）は説明書だけ、-qc（configs）は設定ファイルだけを出す。どれも台帳に書いてある印で分けている。/etc/dnf/protected.d/sudo.conf は、yum に sudo を消させないための設定である（yum の実体は dnf というプログラムで、/etc/dnf/ はその設定の置き場）。

聞きたいことDebian 系RPM 系
入っているもの全部dpkg -lrpm -qa・yum list installed
このパッケージは入っているか（どの版か）dpkg -l 名前rpm -q 名前
1つの詳しい情報dpkg -s 名前rpm -qi 名前
パッケージ → 置いたファイルdpkg -L 名前rpm -ql 名前（説明書だけ -qd・設定ファイルだけ -qc）
ファイル → それを置いたパッケージdpkg -S パスrpm -qf パス

RPM 系の台帳 — /var/lib/rpm

この節で分かること: rpm の答えがどこから来ているか。
$ ls /var/lib/rpm/
rpmdb.sqlite  rpmdb.sqlite-shm  rpmdb.sqlite-wal

RPM 系の台帳は /var/lib/rpm/ にある。dpkg の台帳（テキストのファイル）と違い、これはデータベース（たくさんの記録を、プログラムが速く引けるようにまとめて持つ形式）のファイルで、cat では読めない。読むときは必ず rpm -q を通す。この檻（AlmaLinux 9。RHEL 9 と同じ）では SQLite という形式のデータベース（rpmdb.sqlite）で、RHEL 7・8 では別の形式（Berkeley DB）のファイルが並ぶ。どちらも、入れたときに rpm が書き、rpm だけが書き換える台帳であることは同じである。

たとえ: 同じ帳簿を、紙のノートで付けるか、会計ソフトで付けるかの違いに近い。dpkg の台帳はノートなので開いて読めるが、rpm の台帳はソフトの中のデータなので、ソフト（rpm -q）を通して読む。
ただし崩れる点: 会計ソフトのデータは、形が決まっていて別のソフトでも読めることが多いが、rpm の台帳は、データの形が版によって変わる（この檻は SQLite、RHEL 7・8 は Berkeley DB）。だから形に頼らず、いつも rpm -q を通して読む。

表の Installing dependencies:（依存関係のために入れる）に liblab が出て、一緒に入った（ここの Running scriptlet も、liblab が /usr/lib に置いたファイルに反応した、別のパッケージの手順である）。rpm -qR（requires）は「これが必要とするもの」で、パッケージを作った人が書いた liblab >= 1.0 のほかに、rpm がパッケージを作るときに自動で足したものも並ぶ。/usr/bin/sh は、labapp のコマンドが1行目に #!/usr/bin/sh と書いたシェルのスクリプト（第8章で見た「sh に読ませて動かす」印）なので足された。config(labapp) は、設定ファイル（/etc/labapp.conf）を持つパッケージに付く印で、labapp 自身がそれを満たしている。rpmlib(…) は、rpm 自身が持っていなければならない機能である。--whatrequires は逆向きで、「これを必要としている、入っているもの」を出す（第5章の apt-cache rdepends にあたる）。

ふつうこう考える

第5章の apt と同じで、labapp を消しても、一緒に入った liblab は残るはずだ。片付けるには autoremove のような別の手順が要るだろう。

package labapp is not installed

だめな理由: liblab も消えた。表の Removing unused dependencies:（使われなくなった依存関係を消す）に liblab が出ている。 yum も apt と同じく「どれを依存関係のために自分が入れたか」を覚えていて、消すときにそれを見て、もう誰にも必要とされていないものを一緒に消す。 そうするように、yum の設定ファイル /etc/yum.conf に書いてある。
$ grep clean_requirements_on_remove /etc/yum.conf
clean_requirements_on_remove=True

clean_requirements_on_remove=True が「消すときに、要らなくなった依存関係も消す」という指示である。いまの RHEL 系（RHEL 8 以降）の yum ではこれが既定だが、古い RHEL 7 の yum は既定が False で、yum remove は依存関係を残す。試験の問題は、どちらの前提で書かれているかを見て読む。

たとえ: 第5章のテレビの配達で、引き取りのときにアンテナ線も持って帰ってくれる配達業者に近い。一緒に持ってきた物を覚えていて、要らなくなったら一緒に引き取る。
ただし崩れる点: 配達業者なら「線は残しておきますか」と聞いてくれるが、yum は表に出して [y/N] で全体を聞くだけで、1つずつは聞かない。残したいなら、表を見て N と答えるしかない。
手を動かす: 実践編の演習09は、labapp を yum で入れ、rpm に聞いて設定ファイルを見つけ、挨拶を「こんにちは」に変える課題である。 判定は labapp を実際に動かし、yum のリポジトリから入ったか（@lab）と、書き換わったのが設定ファイルだけかを見る。
確認

/usr/bin/ssh がどの RPM パッケージから来たかを調べるコマンドはどれか（入っている場合）。
(a) rpm -ql /usr/bin/ssh　(b) rpm -qf /usr/bin/ssh　(c) rpm -qi /usr/bin/ssh　(d) rpm -qa /usr/bin/ssh

答え

(b)。-qf はファイルからパッケージを引く（Debian 系の dpkg -S）。逆にパッケージからファイルの一覧を出すのが -ql（dpkg -L）。

確認

labhello-1.0-1.noarch の各部分は何を表すか。

答え

名前 labhello・版 1.0・リリース 1（その版を作った回）・アーキテクチャ noarch（どの CPU でも動く。Debian 系の all）。名前・版・リリースを - で、アーキテクチャを . でつなぐ。

確認

この檻で sudo yum remove labapp を打つと、liblab も一緒に消えた。なぜか。

答え

liblab は labapp の依存関係のために入ったもので、labapp を消すともう誰にも必要とされないから。/etc/yum.conf の clean_requirements_on_remove=True がそうするよう指示している（RHEL 8 以降の既定。RHEL 7 の yum は既定が False で残す）。

この章で分かったこと

持ち帰ってほしいこと

  • RPM 系では、apt にあたるのが yum、dpkg にあたるのが rpm。sudo yum install・sudo yum remove で入れて消す。問いは [y/N] で、既定は「いいえ」
  • 台帳に聞くのは rpm -q…: -qa 全部・-q 版・-qi 詳しく・-ql ファイル・-qf ファイル → パッケージ・-qd 説明書・-qc 設定ファイル。yum では yum list installed
  • RPM 系の台帳は /var/lib/rpm/ のデータベース。rpm -q を通して読む
  • rpm -qR は依存関係、--whatrequires は逆向き。yum remove は要らなくなった依存関係も消す（clean_requirements_on_remove=True）
