3. ifup は、自分が付けたものしか知らない

第2章で手で付けた 10.0.3.50/24 を、そのまま設定ファイルに書いて ifup する。ファイルの中身と今の状態はまったく同じなのに、ifup は失敗し、ifdown は「設定されていない」と言う。ifupdown が見ているのは NIC ではなく、自分の作業記録だからだ。NIC には「持ち主」がいて、持ち主の道具でしか設定は残らない。

この章のゴールと前提所要 21分
前提: 第2章を終えている（enp0s17 に 10.0.3.50/24 が付いている）所要 21分影響度 B出題範囲 1.07.2（重要度4）出題範囲 1.07.3（重要度4）最終検証 2026-10-13

この章のゴール

  • /etc/network/interfaces の書式（auto / iface … inet static / address / gateway / inet dhcp）を読み書きし、ifup / ifdown で反映できる。RHEL 系の ifcfg-名前 の書き方と対応させられる
  • nmcli で接続（プロファイル）を作り、DHCP による自動の設定と固定の設定を切り替えられる
  • NIC ごとの持ち主（ifupdown / NetworkManager / systemd-networkd）を見分け、持ち主に合った道具を選べる
ここで覚えなくていいこと: NetworkManager の画面の道具（nmtui や GUI）、Wi-Fi・ボンディング・VLAN の設定、netplan の YAML の細かい書き方。持ち主の見分け方と、ifupdown・nmcli の基本の操作、RHEL 系の ifcfg ファイルとの対応だけで足りる。

ifupdown は、設定ファイルを読んで実行する

この節で分かること: /etc/network/interfaces の読み方と、ifup が何を読むか。

この練習機では、社内 LAN の lab0 を ifupdown が持っている。設定ファイルを読む。

$ cat /etc/network/interfaces
# interfaces(5) — ifupdown の設定ファイル。ifup / ifdown はこのファイルを読む。
#
# この練習機では、NIC ごとに設定する道具（持ち主）が違う:
#   enp0s16  管理用。netplan（/etc/netplan/）→ systemd-networkd が持つ。触らない
#   enp0s17  練習用。ifupdown が持つ（このファイルに書く）
#   enp0s18  練習用。NetworkManager が持つ（nmcli で設定する）
#   lab0     社内 LAN。ifupdown が持つ（下に書いてある）

source /etc/network/interfaces.d/*

auto lo
iface lo inet loopback

# 社内 LAN
auto lab0
iface lab0 inet static
    address 192.168.10.2/24
    gateway 192.168.10.254

iface lab0 inet6 auto
    privext 0
行意味
source /etc/network/interfaces.d/*このディレクトリのファイルも、ここに書いたものとして読む
auto lab0起動時（networking.service が打つ ifup -a）に上げる NIC。allow-hotplug lab0 と書くと、NIC が見つかったとき（起動時も含む）に上げる
iface lab0 inet staticlab0 の IPv4 を固定（static）で設定する。DHCP なら inet dhcp
address 192.168.10.2/24付けるアドレス（netmask 255.255.255.0 と分けて書く形もある）
gateway 192.168.10.254デフォルトルートの行き先（第4章で、これが問題になる）
iface lab0 inet6 autoIPv6 はルータ広告で自動に作る（第6章）

ifquery は、ifupdown がこのファイルをどう読んだかを答える。--list は auto の付いた NIC の一覧である。

$ ifquery --list
lo
lab0
$ sudo ifup enp0s17
ifup: unknown interface enp0s17

ifupdown は enp0s17 を知らない。ファイルに書いていないからである。ifup は「NIC を上げるコマンド」ではなく、 「ファイルに書かれた手順で NIC を上げるコマンド」である。 第2章の enp0s17 の設定（10.0.3.50/24）を、ファイルに書く。

$ printf 'auto enp0s17\niface enp0s17 inet static\n    address 10.0.3.50/24\n' | sudo tee /etc/network/interfaces.d/enp0s17
auto enp0s17
iface enp0s17 inet static
    address 10.0.3.50/24
$ ifquery --list
lo
enp0s17
lab0
$ ifquery enp0s17
address: 10.0.3.50
broadcast: 10.0.3.255
netmask: 255.255.255.0

同じ状態なのに、断られる

この節で分かること: ifup と ifdown が、何を見て動いているか。

ふつうこう考える

ファイルには、いま付いているのと同じ 10.0.3.50/24 を書いた。ifup すれば「もうその通りです」で何事もなく終わる。 ifdown すれば、付いているアドレスは外れるはずだ。

$ sudo ifup enp0s17
Error: ipv4: Address already assigned.
ifup: failed to bring up enp0s17
$ ifquery --state
lab0=lab0
lo=lo
$ sudo ifdown enp0s17
ifdown: interface enp0s17 not configured
$ ip -4 addr show enp0s17
3: enp0s17: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.3.50/24 brd 10.0.3.255 scope global enp0s17
       valid_lft forever preferred_lft forever
だめな理由: ifup は今の状態とファイルを見比べない。ファイルに書かれた手順（ip addr add 10.0.3.50/24 …）を そのまま実行して、同じアドレスがもうあるので失敗した。 ifdown は逆に、NIC の状態ではなく ifupdown 自身の作業記録（/run/network/ifstate。ifquery --state が読む）を見る。 記録にあるのは lab0 と lo だけで、enp0s17 は「自分が上げたものではない」ので下げない。アドレスは残ったままである。

手で付けたものは、手で外す。そのあとで ifup すれば、ifupdown が自分で付け、記録にも残る。

$ sudo ip addr flush dev enp0s17
$ sudo ifup enp0s17
$ ifquery --state
enp0s17=enp0s17
lab0=lab0
lo=lo
$ ip -4 addr show enp0s17
3: enp0s17: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.3.50/24 brd 10.0.3.255 scope global enp0s17
       valid_lft forever preferred_lft forever

こんどは ifdown が効く。リンクごと下げ、アドレスも外す。もう一度 ifup すれば戻る。

$ sudo ifdown enp0s17
$ ip addr show enp0s17
3: enp0s17: <BROADCAST,MULTICAST> mtu 1500 qdisc fq_codel state DOWN group default qlen 1000
    link/ether 52:54:00:12:34:57 brd ff:ff:ff:ff:ff:ff
$ sudo ifup enp0s17
$ ping -c 1 10.0.3.2
PING 10.0.3.2 (10.0.3.2) 56(84) bytes of data.
64 bytes from 10.0.3.2: icmp_seq=1 ttl=255 time=3.35 ms

--- 10.0.3.2 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 3.349/3.349/3.349/0.000 ms

これで enp0s17 は再起動しても 10.0.3.50/24 になる。起動時に networking.service が ifup -a を打ち、auto の付いた NIC を上げるからである。

たとえ: 手順書どおりに作業し、作業日誌を付ける作業員に近い。 ifup は手順書（/etc/network/interfaces）の作業をして日誌に「enp0s17 済」と書き、ifdown は日誌に書いた作業だけを片付ける。
ただし崩れる点: 人の作業員なら現場を見て「もう付いている」と気づくが、ifup は現場を見ずに手順を実行して失敗する。 誰かが手で付けたものは、日誌に無いので片付けもしない。

ifupdown で DHCP にするなら

inet static の代わりに inet dhcp と書く。ただし ifupdown は DHCP を自分ではせず、外の DHCP クライアント（Debian の伝統では dhclient、この練習機では dhcpcd）を起動する。 その DHCP クライアントが NIC の設定を書き換えて元に戻さないので、著者は第9章まで全部終えたあとに試した（ここで試すと第6章の画面が変わる）。その記録だけ載せる。

$ printf 'auto enp0s17\niface enp0s17 inet dhcp\n' | sudo tee /etc/network/interfaces.d/enp0s17
auto enp0s17
iface enp0s17 inet dhcp
$ sudo ifup enp0s17
dhcpcd-10.0.6 starting
...
enp0s17: offered 10.0.3.15 from 10.0.3.2
enp0s17: probing address 10.0.3.15/24
enp0s17: leased 10.0.3.15 for 86400 seconds
enp0s17: adding route to 10.0.3.0/24
...

DHCP サーバ（10.0.3.2）から 10.0.3.15 を 86400 秒（1日）借りた。ifup の出力は dhcpcd のものである。 試すなら全章を終えてからにし、終わったら外で vm reset --yes で練習機を戻せる。

RHEL 系の ifup は、ifcfg ファイルを読む

ifup / ifdown という名前のコマンドは RHEL・CentOS にもある。ただし読むファイルが違い、 /etc/sysconfig/network-scripts/ifcfg-<NIC の名前> に、1つの NIC を1つのファイルで「名前=値」の形で書く （RHEL 8 以降の ifup / ifdown は、中で nmcli を呼んでこのファイルを読ませる形に変わった）。 この練習機（Ubuntu）にはこのファイルが無いので記録は無いが、試験には両方の形が出る。同じ設定を並べる。

Debian 系（/etc/network/interfaces）RHEL 系（ifcfg-enp0s17）意味
auto enp0s17ONBOOT=yes起動時に上げる
iface enp0s17 inet staticBOOTPROTO=none（static とも書く）IPv4 を固定で設定する
iface enp0s17 inet dhcpBOOTPROTO=dhcpDHCP で借りる
address 10.0.3.50/24IPADDR=10.0.3.50 と PREFIX=24（または NETMASK=255.255.255.0）付けるアドレスとマスク
gateway 10.0.3.2GATEWAY=10.0.3.2（機械全体の既定は /etc/sysconfig/network にも書ける）デフォルトルートの行き先

NetworkManager は、持っている NIC にしか効かない

この節で分かること: nmcli の device と connection、自動（DHCP）と固定の切り替え。

enp0s18 は NetworkManager の持ち物である。NetworkManager に、知っている NIC を聞く。

$ nmcli device status
DEVICE   TYPE      STATE         CONNECTION
enp0s18  ethernet  disconnected  --
enp0s16  ethernet  unmanaged     --
enp0s17  ethernet  unmanaged     --
lab0     ethernet  unmanaged     --
lo       loopback  unmanaged     --

unmanaged は「NetworkManager の持ち物ではない」という意味で、壊れているわけではない。この練習機では、設定でそう決めてある。

$ cat /etc/NetworkManager/conf.d/90-lab.conf
...
[keyfile]
unmanaged-devices=*,except:interface-name:enp0s18
...
$ nmcli connection show

enp0s18 は持ち物だが、まだ disconnected で、接続（connection）が1つも無い。 nmcli では、NIC（device）に「接続」という設定のひとまとまり（プロファイル）を作って当てはめ、それを有効にする（up）。 アドレスの方式を指定しなければ DHCP（ipv4.method auto）になる。

$ sudo nmcli connection add type ethernet ifname enp0s18 con-name lab-dhcp
Connection 'lab-dhcp' (05dc1bbb-f1bd-45e9-a3d3-7372556b74fe) successfully added.
$ nmcli -f NAME,TYPE,DEVICE connection show
NAME      TYPE      DEVICE
lab-dhcp  ethernet  enp0s18
$ sudo nmcli connection up lab-dhcp
Connection successfully activated (D-Bus active path: /org/freedesktop/NetworkManager/ActiveConnection/2)
$ nmcli device status
DEVICE   TYPE      STATE      CONNECTION
enp0s18  ethernet  connected  lab-dhcp
enp0s16  ethernet  unmanaged  --
enp0s17  ethernet  unmanaged  --
lab0     ethernet  unmanaged  --
lo       loopback  unmanaged  --
$ ip -4 addr show enp0s18
4: enp0s18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.4.15/24 brd 10.0.4.255 scope global dynamic noprefixroute enp0s18
       valid_lft 86398sec preferred_lft 86398sec

DHCP サーバから 10.0.4.15/24 を借りた（dynamic と、減っていく残り時間 valid_lft。UUID と秒数はあなたの画面では違う）。 NetworkManager は DHCP クライアントを自分の中に持っている。何を受け取ったかは nmcli で見られる。

$ nmcli -f IP4 device show enp0s18
IP4.ADDRESS[1]:                         10.0.4.15/24
IP4.GATEWAY:                            --
IP4.ROUTE[1]:                           dst = 10.0.4.0/24, nh = 0.0.0.0, mt = 100

IP4.GATEWAY が --。この練習用ネットワークの DHCP サーバはアドレスだけを配り、ゲートウェイも DNS サーバも配らない設定になっている。 DHCP で「つながった」からといって、デフォルトルートや DNS まで来るとは限らない。

固定のアドレスに変える。modify は接続（プロファイル）を書き換えるだけで、NIC には反映しない。up し直して初めて反映される。

$ sudo nmcli connection modify lab-dhcp ipv4.method manual ipv4.addresses 10.0.4.50/24
$ ip -4 addr show enp0s18
4: enp0s18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.4.15/24 brd 10.0.4.255 scope global dynamic noprefixroute enp0s18
       valid_lft 86389sec preferred_lft 86389sec
$ sudo nmcli connection up lab-dhcp
Connection successfully activated (D-Bus active path: /org/freedesktop/NetworkManager/ActiveConnection/3)
$ ip -4 addr show enp0s18
4: enp0s18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.4.50/24 brd 10.0.4.255 scope global noprefixroute enp0s18
       valid_lft forever preferred_lft forever

固定になると dynamic が消え、残り時間は forever になる。DHCP に戻しておく（演習03 の判定は DHCP で見る）。

$ sudo nmcli connection modify lab-dhcp ipv4.method auto ipv4.addresses ''
$ sudo nmcli connection up lab-dhcp
Connection successfully activated (D-Bus active path: /org/freedesktop/NetworkManager/ActiveConnection/4)
$ ip -4 addr show enp0s18
4: enp0s18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    inet 10.0.4.15/24 brd 10.0.4.255 scope global dynamic noprefixroute enp0s18
       valid_lft 86399sec preferred_lft 86399sec
$ nmcli -g ipv4.method,connection.autoconnect connection show lab-dhcp
auto
yes

connection.autoconnect が yes なので、再起動すれば NetworkManager がこの接続を自動で上げる。設定はどこに残ったか。

$ ls /etc/netplan/
01-lab-mgmt.yaml  90-NM-05dc1bbb-f1bd-45e9-a3d3-7372556b74fe.yaml

Ubuntu の NetworkManager は、nmcli で作った接続を netplan の YAML（90-NM-<UUID>.yaml）として保存する。 RHEL 9 以降の既定では /etc/NetworkManager/system-connections/ に置かれ、RHEL 8 までは前の節の ifcfg-<名前> のファイルとして置かれる。 どれでも、nmcli から見れば同じ接続である。

たとえ: 車のメモリーシートに近い。座席や鏡の位置を「プロファイル」として覚えさせ、ボタン1つで呼び出す。 connection add が覚えさせる操作、connection up が呼び出す操作である。
ただし崩れる点: メモリーシートは記憶を書き換えた瞬間に座席が動くことが多いが、nmcli connection modify は記憶を書き換えるだけで、 up し直すまで今の状態は変わらない（上の記録で、modify の直後も 10.0.4.15 のままだった）。
確認

NetworkManager の接続 office の IPv4 アドレスを固定の 192.168.1.10/24 に変え、すぐに反映させたい。正しい手順はどれか。

A. nmcli connection modify office ipv4.addresses 192.168.1.10/24 だけ打つ
B. nmcli connection modify office ipv4.method manual ipv4.addresses 192.168.1.10/24 のあと nmcli connection up office
C. nmcli device set office ipv4.addresses 192.168.1.10/24
D. /etc/network/interfaces に書いて ifup office

答え

B。modify は接続の設定を書き換えるだけなので、up し直して反映させる。 ipv4.method を manual にしないと、DHCP（auto）のまま固定のアドレスが足される形になる。 D は ifupdown の方法で、NetworkManager の持ち物の NIC には使わない。

nmcli も ip と同じく nmcli [オプション] オブジェクト コマンド の形で打つ。ここまで使ったのは device と connection の2つで、全部で7つある。nmcli 自身に聞ける。

...

  n[etworking]    overall networking control
  r[adio]         NetworkManager radio switches
  c[onnection]    NetworkManager's connections
  d[evice]        devices managed by NetworkManager
  a[gent]         NetworkManager secret agent or polkit agent
  m[onitor]       monitor NetworkManager changes

general の後ろに置けるコマンドは5つある。

持ち主は3人いる

この節で分かること: NIC ごとの持ち主の見分け方と、持ち主の違う道具がどう振る舞うか。

管理用の enp0s16 の持ち主は、ifupdown でも NetworkManager でもない。systemd-networkd に聞く。

$ networkctl
IDX LINK    TYPE     OPERATIONAL SETUP
  1 lo      loopback carrier     unmanaged
  2 enp0s16 ether    routable    configured
  3 enp0s17 ether    routable    unmanaged
  4 enp0s18 ether    routable    unmanaged
  5 lab0    ether    routable    unmanaged

5 links listed.
$ sudo cat /etc/netplan/01-lab-mgmt.yaml
# 管理用の NIC。外（コンテナ）からの ssh と、練習機の中からの lab はここを通る。
# この NIC を止めると ssh が切れる。そのときは外で vm console（シリアル）から入る。
#
# ネットワークのコースでは、DHCP からデフォルトルートと DNS を受け取らない（use-routes / use-dns）。
# 練習機の「外」は、中に作った社内 LAN（lab0）だけにしてある。
network:
  version: 2
  ethernets:
    enp0s16:
      dhcp4: true
      dhcp4-overrides:
        use-routes: false
        use-dns: false

enp0s16 だけが configured。Ubuntu では netplan の YAML（/etc/netplan/）を書くと、それが systemd-networkd の設定に変換される。 networkctl でも、enp0s17・enp0s18・lab0 は unmanaged（networkd の持ち物ではない）と出る。どの道具も、自分の持ち物しか configured と言わない。

NIC持ち主設定ファイル状態を聞く道具
enp0s16systemd-networkd（netplan 経由）/etc/netplan/01-lab-mgmt.yamlnetworkctl
enp0s17・lab0ifupdown/etc/network/interfaces（と interfaces.d/）ifquery --state
enp0s18NetworkManager接続（Ubuntu では /etc/netplan/90-NM-*.yaml）nmcli device status

持ち主でない道具で触ると、どうなるか。NetworkManager に enp0s17 をつながせる。

$ sudo nmcli device connect enp0s17
Error: Failed to add/activate new connection: Connection 'enp0s17' is not available on device enp0s17 because device is strictly unmanaged
$ sudo cat /etc/netplan/01-lab-mgmt.yaml
network:
  version: 2
  ethernets:
    enp0s16:
      dhcp4: true
      dhcp4-overrides:
        use-dns: false
        use-routes: false

NetworkManager は断った。enp0s17 は「厳密に（strictly）持ち物でない」。 ところが、そのあと enp0s16 の netplan の YAML を見ると、コメントが全部消え、項目の順番が変わっている。 断ったはずの NetworkManager が、Ubuntu の netplan との連携の中で /etc/netplan/ のファイルを書き直していた（中身の意味は同じなので、enp0s16 の動きは変わらない）。 著者はこれを、記録を取り直して初めて見つけた。持ち主の違うファイルに、別の道具が触ることがある。設定ファイルにコメントで残した経緯は、当てにしないほうがよい。

たとえ: 1つのマンションに、部屋ごとに別の管理会社が入っているようなものだ。 自分の会社の部屋（持ち物）の鍵しか開けられず、他社の部屋のことは「管理外」としか答えない。
ただし崩れる点: 管理会社は他社の書類に手を出さないが、NetworkManager は（Ubuntu では）netplan の書類棚を共有していて、 断った用件のついでに他の書類を清書し直した。持ち主の線は、ファイルの単位ではきれいに引かれていない。
確認

/etc/network/interfaces に次の設定がある。システムの起動時に eth1 に起きることとして正しいものはどれか。

iface eth1 inet static
    address 192.168.50.10/24

A. 192.168.50.10/24 が付く　B. 何も起きない（eth1 は上がらない）　C. DHCP でアドレスを借りる　D. エラーで起動が止まる

答え

B。auto eth1（または allow-hotplug eth1）が無いので、起動時の ifup -a の対象にならない。 手で ifup eth1 と打てば 192.168.50.10/24 が付く。ifquery --list に eth1 が出ないことで確かめられる。

確認

ip addr で eth0 にアドレスが付いているのに、ifdown eth0 が ifdown: interface eth0 not configured と表示して何もしなかった。最も考えられる理由はどれか。

A. eth0 の LAN ケーブルが抜けている　B. eth0 のアドレスは ifup ではなく別の方法（ip addr add や NetworkManager）で付けられた　C. /etc/hostname が無い　D. ifdown には root の権限が要らない

答え

B。ifdown は ifupdown 自身の記録（/run/network/ifstate、ifquery --state）に無い NIC を下げない。 手で付けたアドレスなら ip addr del / flush で外し、持ち主が NetworkManager なら nmcli connection down を使う。

手を動かす: 実践編の演習02（enp0s17 を ifupdown に持たせる）と演習03（enp0s18 を nmcli で DHCP につなぐ）。 演習02 の判定は ifquery --state（ifupdown の作業記録）と ifquery --list（起動時に上げる一覧）と実際のアドレスを見るので、 手で付けたままでは通らない。この章の「断られる」を一度踏むことになる。

この章で分かったこと

持ち帰ってほしいこと

  • ifup は /etc/network/interfaces の手順をそのまま実行する。すでにあるアドレスとぶつかると失敗する
  • ifdown は ifupdown 自身の記録（ifquery --state）にある NIC しか下げない。手で付けたものは手で外す
  • 起動時に上がるのは auto（ifup -a が上げる）か allow-hotplug（NIC が見つかったときに上げる）の付いた NIC。inet static / inet dhcp で方式を選ぶ
  • RHEL 系の ifup / ifdown は /etc/sysconfig/network-scripts/ifcfg-名前 を読む（ONBOOT=yes・BOOTPROTO=none / dhcp・IPADDR と PREFIX・GATEWAY）
  • nmcli connection add で接続を作り、up で反映。modify しただけでは変わらない
  • NIC には持ち主（ifupdown / NetworkManager / systemd-networkd）がいて、持ち主でない道具は unmanaged と言うか、断る
