5. traceroute は、断られた返事で道を知る

traceroute は、ping のように相手に「返事をください」と頼んでいるわけではない。わざと誰も待っていない番号（UDP の 33434 番〜）へ送り、途中のルータの「時間切れです」と、相手の「その番号には誰もいません」という断りの返事（ICMP）を集めて道順を組み立てる。だから、断りを返さない機械は * になる。

前提: 第4章を終えている（デフォルトルートが 192.168.10.1）所要 16分影響度 B出題範囲 1.07.3（重要度4）最終検証 2026-10-13

この章のゴール

  • traceroute と tracepath の出力から、何番目の機械まで届いたかを読める
  • traceroute が TTL と ICMP（Time Exceeded / Port Unreachable）で道順を知る仕組みを説明できる
  • * や !N が何を意味し、何を意味しないかを言える
ここで覚えなくていいこと: mtr などの別の道具、tracepath が経路の MTU を探す仕組みの細部（表示される pmtu の値が読めれば足りる）、traceroute の送り元のアドレスやポートを指定するオプション。tcpdump はこの章で中身を見るために使うが、出題範囲の外なので使い方は覚えなくてよい。

道順を出す

この節で分かること: traceroute の出力の各列の意味。
$ traceroute -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  1.313 ms  0.110 ms  0.055 ms
 2  172.16.20.10  0.420 ms  0.071 ms  0.115 ms

1行が1つの機械（ホップ）で、左から順番・アドレス・3回測った往復時間（ms。あなたの画面では違う）。 1番目がルータ（192.168.10.1）、2番目がサーバで、ここで終わった。30 hops max は「30 個目まで探す」、60 byte packets は送ったパケットの大きさ。 -n を外すと、アドレスを名前に引いて表示する。

$ traceroute 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  _gateway (192.168.10.1)  0.616 ms  0.170 ms  0.062 ms
 2  172.16.20.10 (172.16.20.10)  0.121 ms  0.081 ms  0.064 ms

_gateway は DNS の名前ではない。この練習機の名前解決の中継役（systemd-resolved）が、いまのデフォルトゲートウェイに付けて答える名前である。 2番目は名前が引けず、アドレスのまま。名前がどこから来るかは第8章で変わる。

この道順の1番目にいる router は、練習機の中に作った「別の機械」（名前空間）である。その中に入って、ルータ自身の経路表を見られる。

$ ip netns list
server
oldgw
router
sw (id: 0)
$ sudo ip netns exec router ip route
172.16.20.0/24 dev eth1 proto kernel scope link src 172.16.20.1
192.168.10.0/24 dev eth0 proto kernel scope link src 192.168.10.1

router は社内 LAN（192.168.10.0/24）とサーバの LAN（172.16.20.0/24）の両方に直結している。だからサーバへ渡せる。 第4章の旧ルータ oldgw は、社内 LAN の行しか持っていなかった。ip netns exec 名前 コマンド は「その機械の中で打つ」と読めばよい。

traceroute が送っているもの

この節で分かること: traceroute が何を送り、何を受け取って道順を知るか。

ふつうこう考える

traceroute は、ping と同じ ICMP の「返事をください（echo request）」を、途中の機械に1台ずつ送って、返事をもらっているのだろう。

実際に流れたパケットを tcpdump で見る（1つの端末で、裏で tcpdump を動かしてから traceroute を打つ。-q 1 は1ホップ1回、-N 1 は1つずつ順に送る指定）。

$ sudo tcpdump -l -n -t -i lab0 -c 4 "udp or icmp" 2>/dev/null & sleep 2; traceroute -n -q 1 -N 1 172.16.20.10; wait
[1] 3520
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  1.488 ms
 2  172.16.20.10  0.657 ms
IP 192.168.10.2.53391 > 172.16.20.10.33434: UDP, length 32
IP 192.168.10.1 > 192.168.10.2: ICMP time exceeded in-transit, length 68
IP 192.168.10.2.35298 > 172.16.20.10.33435: UDP, length 32
IP 172.16.20.10 > 192.168.10.2: ICMP 172.16.20.10 udp port 33435 unreachable, length 68
[1]+  Done                    sudo tcpdump -l -n -t -i lab0 -c 4 "udp or icmp" 2> /dev/null
だめな理由: 送っているのは ICMP ではなく UDP で、宛先はサーバの 33434 番と 33435 番（誰も待っていない番号）である。 返ってきたのは「返事」ではなく、どちらもエラーだった。 1通目は TTL（通れるルータの数）を 1 にしてあるので、ルータ 192.168.10.1 で尽きて「時間切れ（time exceeded）」が返る。 2通目は TTL が 2 なのでサーバまで届き、サーバが「その番号には誰もいない（port unreachable）」と返す。 traceroute は、時間切れを返した機械を1行ずつ並べ、port unreachable が返ったところで「着いた」と判断する。 （送り元のポート番号はあなたの画面では違う。行の順番も前後することがある。最初と最後の [1] 3237 と [1]+ Done … は、 & で裏に回した tcpdump について bash が出す「ジョブ1番を始めた（数はプロセス番号）」「終わった」の知らせで、tcpdump の出力ではない。）

TTL の仕組みは ping でも確かめられる。-t で TTL を指定する。

$ ping -c 1 -t 1 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
From 192.168.10.1 icmp_seq=1 Time to live exceeded

--- 172.16.20.10 ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss, time 2ms
$ ping -c 1 -t 2 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
64 bytes from 172.16.20.10: icmp_seq=1 ttl=63 time=1.17 ms

--- 172.16.20.10 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 1ms
rtt min/avg/max/mdev = 1.174/1.174/1.174/0.000 ms

TTL 1 ではルータで尽き、ルータが時間切れを返した。TTL 2 なら届く。返事の ttl=63 は、サーバが 64 で出した返事がルータで1減って届いたことを示す。 ICMP の echo で traceroute をさせることもできる（-I）。ただし Ubuntu の既定では、root でないと断られる。

$ traceroute -I -n 172.16.20.10
You do not have enough privileges to use this traceroute method.
socket: Operation not permitted
$ sysctl net.ipv4.ping_group_range
net.ipv4.ping_group_range = 1	0
$ getcap /usr/bin/ping
/usr/bin/ping cap_net_raw=ep

一般ユーザが ICMP の echo を送れるかは、カーネルの ping_group_range（ICMP を送ってよいグループの番号の範囲）で決まる。 Ubuntu の既定は「1 から 0」という空の範囲で、誰も入っていない。ping が一般ユーザのまま打てるのは、ファイルに付いた権限（cap_net_raw）で動いているからで、traceroute にはそれが付いていない。 RHEL 9 などの既定は 0 2147483647（全部のグループ）で、そこでは一般ユーザでも -I が通る。同じ値にして確かめ、元に戻す。

$ sudo sysctl -w net.ipv4.ping_group_range='0 2147483647'
net.ipv4.ping_group_range = 0 2147483647
$ traceroute -I -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  3.658 ms * *
 2  * 172.16.20.10  0.473 ms *
$ sudo sysctl -w net.ipv4.ping_group_range='1 0'
net.ipv4.ping_group_range = 1 0

root でないまま通った。以後は Ubuntu の既定に戻したので、sudo を付けて打つ。

$ sudo traceroute -I -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  0.718 ms  0.104 ms *
 2  172.16.20.10  0.313 ms * *
$ sudo traceroute -I -n -N 1 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  0.501 ms  0.320 ms  0.088 ms
 2  172.16.20.10  0.091 ms  0.088 ms  0.066 ms

-I の結果に * が混じった。ルータもサーバも生きていて、同じ行のほかの回には答えている（* の位置は打つたびに変わる）。 traceroute は既定で探りを16個まで同時に送る（-N 16）。この取りこぼしはその既定のときに毎回出て（root でないまま通した上の記録にも出ている）、-N 1（1つずつ送る）にすると消えた（著者の環境で3回ずつ試した）。 * は「待ち時間のうちに返事を受け取れなかった」というだけで、その機械が止まっている印ではない。次の節でもう一度確かめる。

たとえ: 乗り換え回数の上限が書かれた切符で、行けるところまで行かせる実験に近い。 上限1回の切符は最初の乗換駅で止められ、駅員が「ここで切れました」と知らせてくる。上限を1ずつ増やして、知らせてきた駅を並べると道順になる。
ただし崩れる点: 駅員は必ず知らせてくれるが、ルータは知らせないこともできる（設定で ICMP を返さない）。 知らせが無い駅は * になり、道順に穴があく。

tracepath は、root なしで経路の MTU も出す

この節で分かること: tracepath の出力の読み方と、traceroute との違い。
$ tracepath -n 172.16.20.10
 1?: [LOCALHOST]                      pmtu 1500
 1:  192.168.10.1                                          2.493ms
 1:  192.168.10.1                                          0.679ms
 2:  172.16.20.10                                          1.158ms reached
     Resume: pmtu 1500 hops 2 back 2

tracepath も UDP と TTL で道順を探す。違いは、経路の途中で通せる最大の大きさ（pmtu、Path MTU）も調べて表示すること。 ここではどこも 1500 バイトで、2つ目で着いた（reached）。back 2 は、返ってきた ICMP の TTL から推定した「帰り道のホップ数」。 root の権限は要らない。1番目の機械が2行出ているのは、そのホップに送った探りの返事を2回表示したもので、読み方は1行のときと同じ。

たとえ: 道順を調べるついでに、途中のトンネルの高さ制限も測っていく下見の車に近い（tracepath）。 traceroute は道順だけ、tracepath は「この道をどの高さの荷物まで通せるか」も持ち帰る。
ただし崩れる点: 下見の車は自分で高さを測るが、tracepath は途中のルータが「大きすぎる」と言い返してきたときにしか制限を知らない。 言い返さない機械があると、pmtu の値は当てにならない。

* は、止まった印ではない

この節で分かること: 返事が来ないホップの読み方。

実際のネットワークでは、時間切れを返さないルータがよくある（負荷を減らすため、構造を隠すため）。 router にそう振る舞わせる。router の中で、時間切れの ICMP を出さないようにする。

$ sudo ip netns exec router iptables -A OUTPUT -p icmp --icmp-type time-exceeded -j DROP
$ traceroute -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  * * *
 2  172.16.20.10  0.095 ms  0.079 ms  0.058 ms
$ tracepath -n 172.16.20.10
 1?: [LOCALHOST]                      pmtu 1500
 1:  no reply
 2:  172.16.20.10                                          0.888ms reached
     Resume: pmtu 1500 hops 2 back 2
$ ping -c 1 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
64 bytes from 172.16.20.10: icmp_seq=1 ttl=63 time=0.834 ms

--- 172.16.20.10 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.834/0.834/0.834/0.000 ms

1番目は * * *（tracepath は no reply）になったが、2番目には着いているし、ping も通る。router は普通にパケットを運んでいて、 時間切れを知らせないだけである。* * * の行で「ここで止まっている」と判断してはいけない。止まっているかどうかは、その先の行や ping で確かめる。 元に戻す。

$ sudo ip netns exec router iptables -D OUTPUT -p icmp --icmp-type time-exceeded -j DROP
$ traceroute -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.1  1.313 ms  0.110 ms  0.055 ms
 2  172.16.20.10  0.420 ms  0.071 ms  0.115 ms
表示意味この教材で見た場面
時間（ms）が3つその機械から時間切れか、着いた印（port unreachable）が返ったこの章のふつうの出力
*待ち時間内に返事を受け取れなかった（理由は分からない）ICMP を返さない router・-I の取りこぼし
!NNetwork Unreachable が返った（その先への道が無い）第4章の旧ルータ
!HHost Unreachable が返った（そのネットワークに相手がいない）第9章の ping の Destination Host Unreachable と同じ知らせ
たとえ: 途中の駅に、問い合わせに一切答えない無口な駅員がいる路線に近い。 その駅の名前は分からないが、終点に着いたことは終点の駅員が知らせてくれる。
ただし崩れる点: 無口な駅員は列車を止めているわけではないが、利用者からは「答えない駅」と「列車が止まっている駅」が同じに見える。 区別するには、その先の駅から知らせが来るかを見るしかない。
確認

Linux の traceroute が既定で送るパケットと、相手に着いたと判断する手がかりの組み合わせとして正しいものはどれか。

A. ICMP echo request ／ ICMP echo reply　B. UDP（33434 番〜）／ ICMP port unreachable　C. TCP の SYN ／ SYN+ACK　D. UDP（53 番）／ DNS の応答

答え

B。誰も待っていない UDP の番号に送り、相手の「その番号には誰もいない（port unreachable）」で着いたと判断する。 途中のルータは TTL が尽きたときの time exceeded で分かる。ICMP echo（A）は -I を付けたとき（Ubuntu の既定では root が要る）。

確認

traceroute の結果が次のようになった。正しい解釈はどれか。

 1  * * *
 2  172.16.20.10  1.264 ms  0.128 ms  0.082 ms

A. 1番目のルータが止まっているので、172.16.20.10 には届かない　B. 1番目の機械は時間切れの知らせを返さないが、パケットは先へ運んでいる　C. 172.16.20.10 が2台ある　D. DNS が引けていない

答え

B。2番目で着いているので、1番目はパケットを運んでいる。* は返事を受け取れなかったというだけで、止まっている印ではない。 この教材では router に time exceeded を出さない設定を入れて、この出力を作った。

手を動かす: この章の演習は無いが、実践編の演習04（デフォルトルートを直す）の前と後で traceroute -n 172.16.20.10 を打つと、 1行目が 192.168.10.254 … !N から 192.168.10.1 と 172.16.20.10 の2行に変わるのが見える。診断に使う道具として手に馴染ませておく。

この章で分かったこと

持ち帰ってほしいこと

  • traceroute は UDP（33434 番〜）を TTL 1, 2, 3… で送り、途中の time exceeded と、相手の port unreachable で道順を知る
  • -I は ICMP echo で調べる。Ubuntu の既定では root が要る（ping_group_range が空。RHEL 9 などの既定なら一般ユーザでも通る）。-n は名前を引かない
  • tracepath は root なしで使え、道順に加えて経路の MTU（pmtu）を出す
  • ping -t N で TTL を決めて送れる。返事の ttl=63 は、64 から1つのルータで1減ったことを示す
  • * は返事を受け取れなかっただけ。止まっている印ではない。!N / !H は途中の機械が届かないことを知らせてきた印
