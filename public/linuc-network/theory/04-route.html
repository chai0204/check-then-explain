4. 返事をしたのは、相手ではなかった

社内のサーバ 172.16.20.10 に ping を打つと、Destination Net Unreachable が返ってくる。サーバが止まっていると考えたくなるが、From に書かれているのは 192.168.10.254 — 撤去予定の旧ルータである。返事をしたのは相手ではなく、こちらの経路表の1行が送りつけた先だった。しかもその1行は、直しても再起動で戻る。

前提: 第3章を終えている所要 18分影響度 B出題範囲 1.07.2（重要度4）出題範囲 1.07.3（重要度4）最終検証 2026-10-13

この章のゴール

  • ip route・route -n・netstat -rn で経路表を読み、ある宛先にどの行が使われるかを言える
  • ping の From と ICMP のエラーの種類から、どこで止まったかを特定できる
  • 不適切なデフォルトルートを ip route と route で直し、ifupdown の設定にも残せる
ここで覚えなくていいこと: ポリシールーティング（ip rule と複数の経路表）、ルーティングプロトコル（OSPF / BGP）、ルータ側で転送を許す設定（ip_forward）。経路表の行を手で読み書きすることと、デフォルトルートの直し方だけで足りる。

サーバに、ping が届かない

この節で分かること: ping の From が何を言っているか。

ふつうこう考える

ping が返ってこないのは、相手のサーバが止まっているか、ネットワークのケーブルが抜けているからだ。 自分の機械の設定は、さっきまで普通に使えていたのだから関係ない。

$ ping -c 3 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
From 192.168.10.254 icmp_seq=1 Destination Net Unreachable
From 192.168.10.254 icmp_seq=2 Destination Net Unreachable
From 192.168.10.254 icmp_seq=3 Destination Net Unreachable

--- 172.16.20.10 ping statistics ---
3 packets transmitted, 0 received, +3 errors, 100% packet loss, time 2004ms
だめな理由: 3回とも返事は来ている。ただし差出人（From）は 172.16.20.10 ではなく 192.168.10.254 で、 中身は「その先のネットワークへの道を知らない（Destination Net Unreachable）」という ICMP のエラーである。 パケットは旧ルータまでは届き、旧ルータが先へ行けずに突き返した。サーバまでは1度も行っていない。 そしてサーバは生きている。IPv6 で聞くと返事が来る。
$ ping6 -c 2 fd00:20::10
PING fd00:20::10 (fd00:20::10) 56 data bytes
64 bytes from fd00:20::10: icmp_seq=1 ttl=63 time=7.76 ms
64 bytes from fd00:20::10: icmp_seq=2 ttl=63 time=0.826 ms

--- fd00:20::10 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1003ms
rtt min/avg/max/mdev = 0.826/4.292/7.758/3.466 ms

同じサーバ（fd00:20::10 は 172.16.20.10 と同じ機械）に IPv6 では届く。IPv4 と IPv6 は別々の経路表を持っていて、壊れているのは IPv4 の表のほうである。 ttl=63 は、サーバが 64 で出した返事がルータを1つ通って届いたことを示す（第5章）。

経路表を読む

この節で分かること: 経路表の各行の意味と、宛先ごとにどの行が選ばれるか。
$ ip route
default via 192.168.10.254 dev lab0 onlink
10.0.2.0/24 dev enp0s16 proto kernel scope link src 10.0.2.15 metric 100
10.0.3.0/24 dev enp0s17 proto kernel scope link src 10.0.3.50
10.0.4.0/24 dev enp0s18 proto kernel scope link src 10.0.4.15 metric 100
192.168.10.0/24 dev lab0 proto kernel scope link src 192.168.10.2

2行目から下は「そのネットワークへは、この NIC から直接」という行（直結の経路）で、アドレスを付けたときにカーネルが足したもの（proto kernel scope link）。 1行目の default がデフォルトルートで、「どの行にも当てはまらない宛先は、192.168.10.254 に渡す」と言っている。 172.16.20.10 はどの直結の行にも当てはまらないので、この行で旧ルータへ送られた。

同じ表を古い道具で見る。試験では route の形もよく出る。

$ route -n
Kernel IP routing table
Destination     Gateway         Genmask         Flags Metric Ref    Use Iface
0.0.0.0         192.168.10.254  0.0.0.0         UG    0      0        0 lab0
10.0.2.0        0.0.0.0         255.255.255.0   U     100    0        0 enp0s16
10.0.3.0        0.0.0.0         255.255.255.0   U     0      0        0 enp0s17
10.0.4.0        0.0.0.0         255.255.255.0   U     100    0        0 enp0s18
192.168.10.0    0.0.0.0         255.255.255.0   U     0      0        0 lab0
$ netstat -rn
Kernel IP routing table
Destination     Gateway         Genmask         Flags   MSS Window  irtt Iface
0.0.0.0         192.168.10.254  0.0.0.0         UG        0 0          0 lab0
10.0.2.0        0.0.0.0         255.255.255.0   U         0 0          0 enp0s16
10.0.3.0        0.0.0.0         255.255.255.0   U         0 0          0 enp0s17
10.0.4.0        0.0.0.0         255.255.255.0   U         0 0          0 enp0s18
192.168.10.0    0.0.0.0         255.255.255.0   U         0 0          0 lab0
列・印意味
Destination 0.0.0.0 と Genmask 0.0.0.0すべての宛先（/0）＝デフォルトルート。ip route の default
Gateway 0.0.0.0ゲートウェイ無し＝直結（ip route の via が無い行）
Flags U / G / HU = 使える（Up）、G = ゲートウェイ経由、H = 1台だけ宛ての経路（ホスト経路）
Metric同じ宛先に複数の行があるときの優先度（小さいほうが優先）
Iface出ていく NIC（ip route の dev）

どの行が選ばれるかは、カーネルに直接聞ける。

$ ip route get 172.16.20.10
172.16.20.10 via 192.168.10.254 dev lab0 src 192.168.10.2 uid 1000
    cache
$ ip route get 10.0.2.2
10.0.2.2 dev enp0s16 src 10.0.2.15 uid 1000
    cache
$ traceroute -n 172.16.20.10
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 60 byte packets
 1  192.168.10.254  1.358 ms !N  0.077 ms !N  0.074 ms !N

10.0.2.2（外のコンテナへの出口）は 10.0.2.0/24 の直結の行で届く。宛先に一致する行が複数あるとき、カーネルは一致する部分がいちばん長い行（最長一致）を選ぶ。 デフォルトルートは /0 で一致の長さが 0 なので、いつも最後に回される。だからデフォルトルートが間違っていても、ssh も練習機の中の lab check も切れない。 traceroute の !N は「ネットワークに届かない（Net Unreachable）」の印で、1番目の機械（旧ルータ）で止まったことを示す（第5章）。

たとえ: 郵便局の仕分け棚に近い。「10.0.2 丁目宛ては1番の棚」「192.168.10 丁目宛ては2番の棚」と並び、最後に「その他」の箱がある。 その他の箱の行き先が、撤去予定の旧ルータになっていた。
ただし崩れる点: 郵便局は棚を上から順に見るが、経路表は書かれた順に関係なく、宛先にいちばん細かく一致する行を選ぶ。 「その他」は表の1行目に書かれていても、いつも最後に回る。

1行を直す

この節で分かること: ip route と route での消し方・足し方。

デフォルトルートを消す。

$ sudo ip route del default
$ ip route
10.0.2.0/24 dev enp0s16 proto kernel scope link src 10.0.2.15 metric 100
10.0.3.0/24 dev enp0s17 proto kernel scope link src 10.0.3.50
10.0.4.0/24 dev enp0s18 proto kernel scope link src 10.0.4.15 metric 100
192.168.10.0/24 dev lab0 proto kernel scope link src 192.168.10.2
$ ping -c 1 172.16.20.10
ping: connect: Network is unreachable

こんどは From が無い。経路表に当てはまる行が1つも無いので、カーネルが送る前に「道が無い」と断った（connect: Network is unreachable）。 「旧ルータが断った」のとは別の失敗で、エラーの出どころが自分の機械である。

たとえ: 出かける前に地図を見て「この町への道が載っていない」と分かるのが connect: Network is unreachable、 途中の交番で「この先は通行止めです」と言われるのが From 192.168.10.254 … Net Unreachable に近い。どちらも着かないが、止まった場所が違う。
ただし崩れる点: 交番なら迂回路を教えてくれるが、ルータが返す ICMP には「行けない」という種類の番号しか入っていない。 どこへ回ればよいかは、自分の経路表を直して決める。

正しいルータを足す。

デフォルトルートがもうあるところへ、もう1本足すとどうなるか。わざと旧ルータを足してみる。

$ sudo ip route add default via 192.168.10.254
RTNETLINK answers: File exists
$ sudo route add default gw 192.168.10.254
$ ip route show default
default via 192.168.10.254 dev lab0
default via 192.168.10.1 dev lab0
$ ip route get 172.16.20.10
172.16.20.10 via 192.168.10.254 dev lab0 src 192.168.10.2 uid 1000
    cache
$ ping -c 1 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
64 bytes from 172.16.20.10: icmp_seq=1 ttl=63 time=3.82 ms

--- 172.16.20.10 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 3.815/3.815/3.815/0.000 ms
$ sudo route del default gw 192.168.10.254
$ ip route show default
default via 192.168.10.1 dev lab0

ip route add は、同じ宛先（0.0.0.0/0）で同じメトリックの行がもうあるので File exists で断った。 route add default gw は断らずに2本目を足した。足した行は先に並び、ip route get もそれ（192.168.10.254）を使うと答えた。 ところが続けて打った ping は、旧ルータの Net Unreachable にならず、サーバに届いた。 同じメトリックのデフォルトルートが複数あると、Linux はゲートウェイが応答しているか（ARP の表の状態）を見て、使う行を切り替えることがある。 どちらが使われるかは打つたびに変わりうる（あなたの画面では、この ping が 192.168.10.254 の Net Unreachable になるかもしれない）。 デフォルトルートを替えるときは2本にしない。先に del するか、ip route replace で置き換える。最後に、足した行を消した。

route での書き方も確かめる。1台だけ宛ての経路（ホスト経路）を、わざと旧ルータに向けて足す。

-n は「アドレスを名前に引かない（数字のまま出す）」。付けないと Destination や Gateway の列が名前に置き換わる （この練習機ではゲートウェイが _gateway という名前で出る。systemd-resolved が付ける名前で、第5章の traceroute にも出てくる）。 試験の選択肢も -n 付きの形が多い。 ip は逆で、何も付けなければ数字のまま出し、-r（resolve）を付けたときだけ名前に引く（第2章の ip の書き方）。

$ ip -r route
default via _gateway dev lab0
10.0.2.0/24 dev enp0s16 proto kernel scope link src 10.0.2.15 metric 100
10.0.3.0/24 dev enp0s17 proto kernel scope link src 10.0.3.50
10.0.4.0/24 dev enp0s18 proto kernel scope link src 10.0.4.15 metric 100
192.168.10.0/24 dev lab0 proto kernel scope link src 192.168.10.2

ゲートウェイが _gateway になった。引ける名前が無いもの（ネットワークの番号や自分のアドレス）は数字のまま残る。

確認

デフォルトゲートウェイを 192.168.1.1 に設定するコマンドとして正しいものを2つ選べ。

A. route add default gw 192.168.1.1　B. ip route add default via 192.168.1.1　C. ip addr add default 192.168.1.1　D. route add gw 192.168.1.1 default　E. ip route add 192.168.1.1 default

答え

A と B。route はゲートウェイを gw、ip route は via で書く。ip addr はアドレスを扱うコマンドで、経路は扱わない。 すでに別のデフォルトルートがあるときは、足す前に del するか、ip route replace で置き換える。 足そうとすると、ip route add は File exists で断られ、route add default gw は断られずに2本目が足される（どちらが使われるかは定まらない。この章の記録）。

直したのに、戻る

この節で分かること: その場の修正と、設定ファイルの関係。

いまの経路表は正しい。ここで lab0 を ifupdown で下げて、上げ直す（再起動したときと同じことが起きる）。

$ sudo ifdown lab0
RTNETLINK answers: No such process
$ sudo ifup lab0
$ ip route show default
default via 192.168.10.254 dev lab0 onlink
$ ping -c 1 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
From 192.168.10.254 icmp_seq=1 Destination Net Unreachable

--- 172.16.20.10 ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss, time 0ms

旧ルータに戻った。lab0 の持ち主は ifupdown で、ifup は /etc/network/interfaces の gateway 192.168.10.254 を読んでデフォルトルートを入れ直した。 ifdown の RTNETLINK answers: No such process は、ifdown がファイルに書かれた 192.168.10.254 の経路を消そうとして、 それがもう無かった（手で 192.168.10.1 に直してあった）という意味である。第3章と同じく、ifupdown は今の状態ではなくファイルを見ている。 設定ファイルを直す。

$ sudo sed -i 's/gateway 192.168.10.254/gateway 192.168.10.1/' /etc/network/interfaces
$ ifquery lab0
address: 192.168.10.2
gateway: 192.168.10.1
broadcast: 192.168.10.255
netmask: 255.255.255.0
privext: 0
accept_ra: 2
request_prefix: 0
ll-attempts: 60
ll-interval: 0.1
$ sudo ifdown lab0
RTNETLINK answers: No such process
$ sudo ifup lab0
$ ip route show default
default via 192.168.10.1 dev lab0 onlink
$ ping -c 2 172.16.20.10
PING 172.16.20.10 (172.16.20.10) 56(84) bytes of data.
64 bytes from 172.16.20.10: icmp_seq=1 ttl=63 time=1.28 ms
64 bytes from 172.16.20.10: icmp_seq=2 ttl=63 time=0.959 ms

--- 172.16.20.10 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1003ms
rtt min/avg/max/mdev = 0.959/1.120/1.282/0.161 ms

2回目の No such process は、ifdown が新しいファイルの 192.168.10.1 を消そうとして、その時点の経路が 192.168.10.254 だったため。 ifup のあとは 192.168.10.1 になり、ファイルにも残った。onlink は ifupdown が付ける印で、「ゲートウェイはこの NIC に直接つながっているものとして扱う」という意味である。

IPv6 の表は最初から正しかった。

$ ip -6 route show default
default via fe80::5054:ff:fe0a:1 dev lab0 proto ra metric 1024 expires 1793sec hoplimit 64 pref medium

IPv6 のデフォルトルートは、ルータ（router）が LAN に流す広告（proto ra）から自動で入る。ifupdown の gateway 行は IPv4 にしか効いていない（expires の秒数は見るたびに減る）。

たとえ: ホワイトボードと台帳の関係に近い。ip route で直すのはホワイトボードの書き換えで、すぐ効くが、 朝になると台帳（/etc/network/interfaces）の内容で書き直される。
ただし崩れる点: 人ならホワイトボードの新しい値に気づいて台帳を直すが、ifupdown は気づかない。 台帳を直すのは、いつも人の仕事である。
確認

ping 10.1.1.1 を打つと次のように表示された。原因として最も考えられるものはどれか。

From 192.168.0.254 icmp_seq=1 Destination Net Unreachable

A. 10.1.1.1 のサーバが停止している　B. 自分の機械に経路表の行が1つも無い　C. 192.168.0.254 のルータが 10.1.1.1 への経路を持っていない　D. 自分の NIC が down している

答え

C。返事を出したのは 192.168.0.254 で、内容は「その先のネットワークへの道を知らない」。 自分の経路表がそのルータに送り、ルータが行き止まりだった。自分に経路が無いとき（B）は ping: connect: Network is unreachable になり、From は付かない。 デフォルトゲートウェイが正しいかどうかを ip route で疑う。

手を動かす: 実践編の演習04が、このデフォルトルートを直す課題である。 判定は経路表・判定の中での ping 172.16.20.10・ifquery lab0 の gateway の3つを見るので、ip route だけで直すと ✗ のまま （「設定ファイルの gateway が 192.168.10.1 ではない」と出る）。

この章で分かったこと

持ち帰ってほしいこと

  • ping の From は返事（エラー）を出した機械。相手とは限らない。Destination Net Unreachable は途中のルータが道を知らなかった印
  • 経路表は ip route / route -n / netstat -rn で見る。宛先に一致する行のうち、いちばん長く一致する行が選ばれる（デフォルトルートは /0 で最後）
  • 直結の宛先はデフォルトルートに関係なく届く。だからデフォルトルートを壊しても ssh は切れない
  • ip route add default via X ＝ route add default gw X。消すのは del
  • その場の修正は持ち主（ここでは ifupdown）が設定ファイルから書き直す。残すなら gateway の行を直す
