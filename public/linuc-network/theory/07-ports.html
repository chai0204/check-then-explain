7. LISTEN していても、外からは入れない

ss で見ると、練習機の 8080 番は LISTEN している。curl http://127.0.0.1:8080/ には返事が来る。ところが同じ練習機の中から 192.168.10.2:8080 に接続すると、Connection refused で断られる。待っているのは「8080 番」ではなく「127.0.0.1 の 8080 番」だった。

この章のゴールと前提所要 19分
前提: 第4章を終えている（サーバ 172.16.20.10 に届く）所要 19分影響度 B出題範囲 1.07.1（重要度4）出題範囲 1.07.3（重要度4）最終検証 2026-10-13

この章のゴール

  • 22・25・53・80・123・443 番が、どのサービスで TCP か UDP かを言える
  • ss と netstat の待ち受けの表から、どのアドレスの何番で誰が待っているかを読める
  • nc / ncat で TCP と UDP の待ち受けを確かめ、TCP（コネクション型。RST で断る）と UDP（コネクションレス型。ICMP で断られる）の違いを説明できる
ここで覚えなくていいこと: TCP の状態の移り変わり全体（TIME_WAIT など）、ss の絞り込みの式（sport = :8080 など）、ファイアウォールでの遮断（主題1.10）。待ち受けの表の読み方と、つながるかの確かめ方だけで足りる。

-c（continuous）が入ったので、1秒ごとに表を出し続けた（Ctrl+C まで終わらない。ここでは timeout で2秒で止めたので、終了コードが 124）。 -p も入ったが、root でないので「プロセスの情報を読めない」と言っている。TCP だけを出す長い形は --tcp（-t と同じ）。-n が無いので、アドレスと番号が名前（linuc:ssh）に置き換わっている（相手側の番号と Send-Q の数は打つたびに違う）。

-p に root が要るのは、ほかのユーザのプロセスを見るときだけである。自分で動かしたプロセスなら、sudo なしでも出る。 自分で 9000 番の待ち受けを1つ作って（ncat -lk 9000 &）、sudo なしで比べる。

$ ncat -lk 9000 & sleep 1; ss -tlnp | grep -E 'State|8080|9000'; kill %1; wait
[1] 4125
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      10         127.0.0.1:8080      0.0.0.0:*
LISTEN 0      10           0.0.0.0:9000      0.0.0.0:*    users:(("ncat",pid=4125,fd=4))
LISTEN 0      10              [::]:9000         [::]:*    users:(("ncat",pid=4125,fd=3))
[1]+  Terminated              ncat -lk 9000

自分の ncat（9000 番）には users:(("ncat",…)) が付き、root が動かしている掲示板（8080 番）には付かない。 [1] … と Terminated の行は、bash が裏で動かしたジョブの始まりと終わりを知らせたもの（番号は毎回違う）。

たとえ: /etc/services は電話帳の「部署名と内線番号の一覧」、ss -l は「いま実際に電話機がつながっている内線」の一覧に近い。 電話帳に載っていても、電話機が無ければ誰も出ない。
ただし崩れる点: 内線は誰がかけても同じ電話機が鳴るが、待ち受けはどのアドレス宛てに来たかまで決まっている。次の節がそれである。

127.0.0.1 で待つと、外からは入れない

この節で分かること: 待ち受けのアドレス（Local Address）の意味。

練習機では「社内掲示板」（lab-board）が 8080 番で動いている。

ふつうこう考える

ss に LISTEN と出ていて、自分の機械から curl で返事が来るのだから、 このサービスはほかの機械からも 8080 番で使えるはずだ。

$ curl -s http://127.0.0.1:8080/
lab-board: no news today
$ nc -zv 127.0.0.1 8080
Connection to 127.0.0.1 8080 port [tcp/http-alt] succeeded!
$ nc -zv 192.168.10.2 8080
nc: connect to 192.168.10.2 port 8080 (tcp) failed: Connection refused
$ sudo ip netns exec router nc -zv 192.168.10.2 8080
nc: connect to 192.168.10.2 port 8080 (tcp) failed: Connection refused
$ sudo ip netns exec router nc -zv 192.168.10.2 22
Connection to 192.168.10.2 22 port [tcp/ssh] succeeded!
だめな理由: 練習機の中から自分の LAN 側のアドレス（192.168.10.2）宛てに繋いでも断られ、隣の router からも断られた。 ss の Local Address は 127.0.0.1:8080 で、受け付けるのは 127.0.0.1 宛ての接続だけである。 192.168.10.2 の 8080 番には誰もいないので、カーネルが代わりに断った（Connection refused）。 22 番は 0.0.0.0:22 で待っているので、router からも入れる。ポート番号が同じでも、待ち受けのアドレスで入れるかどうかが変わる。

待ち受けのアドレスは、サービスの設定で決まっている。

$ cat /etc/default/lab-board
# lab-board.service（社内掲示板）が読む設定。変えたら: sudo systemctl restart lab-board
# 待ち受けるアドレス
LISTEN_ADDRESS=127.0.0.1
$ systemctl cat lab-board | grep ExecStart
ExecStart=/usr/bin/ncat --keep-open --listen ${LISTEN_ADDRESS} 8080 --sh-exec /usr/local/lib/lab-net/board-reply

この掲示板は ncat で作ってある。ncat --listen アドレス ポート は「そのアドレスのその番号で待つ」という意味で、--keep-open は1回で終わらず待ち続ける指定。 待ち受けを全部のアドレス（0.0.0.0）に変える。

$ sudo sed -i 's/^LISTEN_ADDRESS=.*/LISTEN_ADDRESS=0.0.0.0/' /etc/default/lab-board
$ sudo systemctl restart lab-board
$ ss -tln
State    Recv-Q   Send-Q     Local Address:Port     Peer Address:Port  Process
...
LISTEN   0        10               0.0.0.0:8080          0.0.0.0:*
...
$ nc -zv 192.168.10.2 8080
Connection to 192.168.10.2 8080 port [tcp/http-alt] succeeded!
$ sudo ip netns exec router curl -s http://192.168.10.2:8080/
lab-board: no news today
たとえ: 社員通用口にだけ受付を置いた店に近い。店は営業中（LISTEN）で、社員（同じ機械の中のプログラム）は入れるが、 正面玄関（192.168.10.2）から来た客は「ここには受付が無い」と断られる。
ただし崩れる点: 店なら客を通用口へ案内できるが、カーネルは案内しない。宛先のアドレスと番号に待ち受けが無ければ、その場で断るだけである。
確認

あるサーバで ss -tln を打つと、次の行があった。正しい説明はどれか。

LISTEN 0 80 127.0.0.1:3306 0.0.0.0:*

A. 3306 番はすべてのネットワークから接続できる　B. 3306 番はこのサーバの中のプログラムからだけ接続できる　C. 3306 番は UDP で待ち受けている　D. 3306 番は 127.0.0.1 から別のサーバへ接続している

答え

B。Local Address が 127.0.0.1（ループバック）なので、そのサーバ自身の中からの接続しか受け付けない。-t なので TCP（C は誤り）。 外から使わせるなら、サービスの設定で待ち受けを 0.0.0.0 か外向きのアドレスに変える（そのうえで、ファイアウォールで守るのは主題1.10）。

TCP と UDP は、断り方が違う

この節で分かること: nc / ncat の結果の読み方と、TCP・UDP・ICMP の違い。

サーバ（172.16.20.10）が待ち受けているものを、サーバの中で見る。

$ sudo ip netns exec server ss -tulnp
Netid   State    Recv-Q   Send-Q     Local Address:Port     Peer Address:Port   Process
udp     UNCONN   0        0           172.16.20.10:53            0.0.0.0:*       users:(("dnsmasq",pid=830,fd=4))

HTTP/1.0 200 OK

Content-Length: 50

hello from www.lab.example (172.16.20.10, 80/tcp)

nc は TCP の接続に手で文字を流し込める。Web サーバに HTTP の要求を書いて送ると、応答の見出しと本文がそのまま返ってくる。UDP では様子が変わる（-u）。

$ nc -zuv 172.16.20.10 53
Connection to 172.16.20.10 53 port [udp/domain] succeeded!
$ nc -zuv 172.16.20.10 123; echo $?
1
$ ncat -zuv 172.16.20.10 123
Ncat: Version 7.94SVN ( https://nmap.org/ncat )
Ncat: Connected to 172.16.20.10:123.
Ncat: Connection refused.
$ ncat -zv 172.16.20.10 25
Ncat: Version 7.94SVN ( https://nmap.org/ncat )
Ncat: Connection refused.

誰もいない UDP の 123 番に対して、nc は何も表示せず終了コード 1 で終わった。ncat は「Connected（つながった）」と言ってから「Connection refused」と言い直した。 UDP には接続というものが無いので、送った時点では断られたか分からない。何が起きているかをパケットで見る。

  • TCP の 25 番: 接続の申し込み（[S] = SYN）に、サーバのカーネルが [R.]（RST = お断り）を返した。nc の Connection refused はこれ

  • TCP の 80 番: SYN → SYN+ACK（[S.]）→ ACK（[.]）の3通で接続ができた（3ウェイハンドシェイク）。-z はここで切る

試験では「TCP はコネクション型で信頼性が高い、UDP はコネクションレス型でリアルタイム性が高い」「ブロードキャストやマルチキャストができるのは UDP」の形で問われる。 この節の記録の言葉で言い直すと、TCP は接続を作る3通（SYN → SYN+ACK → ACK）を交わしてから送り、UDP はいきなり1通を投げていた。

UDP の「返らないこともある」が大事である。断りの ICMP をファイアウォールが止めていると、閉じた番号でも何も返らず、nc -zu は開いているのと区別できない。 UDP の待ち受けを確かめるいちばん確かな方法は、相手の機械で ss -uln を見ることである。

たとえ: TCP は電話、UDP はハガキに近い。電話は相手が出なければその場で分かるが、ハガキは投函した時点では届いたか分からない。
ただし崩れる点: 宛先不明のハガキは郵便局が必ず差し戻すが、UDP の差し戻し（ICMP）は途中で捨てられることがあり、 そのとき送り主は「届いた」と「捨てられた」の区別がつかない。
確認

次のうち、UDP を使うサービスとポート番号の組み合わせとして正しいものを2つ選べ。

A. SSH 22　B. DNS 53　C. SMTP 25　D. NTP 123　E. HTTP 80

答え

B と D。DNS は UDP（応答が大きいときや、ゾーン転送では TCP も使う）、NTP は UDP。 SSH・SMTP・HTTP は TCP。HTTPS（443）は TCP で、HTTP/3 だけは UDP を使う。

持ち帰ってほしいこと

  • 22 SSH / 25 SMTP / 80 HTTP / 443 HTTPS は TCP、123 NTP は UDP、53 DNS は UDP と TCP の両方
  • /etc/services は番号の辞書。開いているかは ss -tuln（netstat -tuln）で見る。-p でプロセス（自分のプロセスは sudo なしでも出る。他のユーザのものまで見るには root）
  • TCP はコネクション型（信頼性）、UDP はコネクションレス型（リアルタイム性。ブロードキャスト・マルチキャストもできる）
  • Local Address が 127.0.0.1 なら、その機械の中からしか入れない。0.0.0.0 / [::] なら全部のアドレスで受ける
  • TCP の閉じた番号は RST で即座に断られる。UDP の閉じた番号は ICMP の port unreachable でしか分からない（nc -zu は何も言わない）
  • ICMP にはポートが無い。ping は ICMP なので、ping が通ってもポートが開いているとは限らない
