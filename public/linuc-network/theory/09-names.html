9. dig と ping は、別の表を引いている

dig +short www.lab.example は 172.16.20.10 と答える。同じ名前で ping を打つと、172.16.20.99 へ飛んでいって Destination Host Unreachable になる。dig は DNS サーバだけに聞き、ping は先に /etc/hosts を読む。同じ名前でも、道具が違えば読む表が違う。

前提: 第8章を終えている（resolv.conf が 172.16.20.10 を向いている）所要 18分影響度 B出題範囲 1.07.4（重要度2）出題範囲 1.07.2（重要度4）最終検証 2026-10-13

この章のゴール

  • /etc/nsswitch.conf の hosts: 行から、名前をどの表からどの順に引くかを言える
  • getent ahosts で ping と同じ引き方をして、/etc/hosts と DNS のどちらが答えたかを特定できる。getent hosts との違い（IPv6 を先に聞く）を言える
  • ホスト名の3つの置き場所（今の名前・/etc/hostname・/etc/hosts の 127.0.1.1）の関係を説明できる
ここで覚えなくていいこと: nsswitch.conf の hosts 以外の行（passwd / group などは主題1.08 のアカウント管理で使う）、mDNS（.local の名前）、hostnamectl の pretty / transient の名前の区別。

dig と ping が、違うアドレスへ行く

この節で分かること: ping が名前をどこから引いているか。

ふつうこう考える

名前からアドレスを引くのは DNS の仕事である。dig で 172.16.20.10 と確かめたのだから、 同じ名前で打つ ping も curl も 172.16.20.10 へ行くはずだ。

$ dig +short www.lab.example
172.16.20.10
$ ping -c 1 www.lab.example
PING www.lab.example (172.16.20.99) 56(84) bytes of data.
From router.lab.example (192.168.10.1) icmp_seq=1 Destination Host Unreachable

--- www.lab.example ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss, time 0ms
$ curl -s -m 3 http://www.lab.example/; echo $?
28
だめな理由: ping は 172.16.20.99 へ行った。router が「そのネットワーク（172.16.20.0/24）に 172.16.20.99 という機械はいない」と返している（Host Unreachable）。 curl も3秒待って時間切れ（終了コード 28）。dig は DNS サーバだけに聞く道具で、ping と curl は OS の名前解決の仕組み（glibc の NSS）を通して引く。 その仕組みが見る表と順番は、別のファイルに書いてある。
$ grep '^hosts' /etc/nsswitch.conf
hosts:          files dns
$ getent ahosts www.lab.example
172.16.20.99    STREAM www.lab.example
172.16.20.99    DGRAM
172.16.20.99    RAW
$ cat /etc/hosts
127.0.0.1 localhost
127.0.1.1 linuc
172.16.20.99 www.lab.example

# The following lines are desirable for IPv6 capable hosts
::1 ip6-localhost ip6-loopback
fe00::0 ip6-localnet
ff00::0 ip6-mcastprefix
ff02::1 ip6-allnodes
ff02::2 ip6-allrouters
ff02::3 ip6-allhosts

hosts: files dns は「先に files（/etc/hosts）、見つからなければ dns」。/etc/hosts の3行目に、前任者が書いた古い行が残っていた。 getent ahosts 名前 は、ping や curl が名前を引くのと同じ関数（getaddrinfo）で NSS を通して引き、使う順に並べる道具で、 ping がどのアドレスを使うかを確かめるときに使う（先頭の行が ping の使うアドレス）。同じアドレスが3行並ぶのは、接続の種類（STREAM は TCP、DGRAM は UDP、RAW はそれ以外）ごとに1行ずつ出すためである。古い行を消す。

$ sudo sed -i '/www.lab.example/d' /etc/hosts
$ getent ahosts www.lab.example
172.16.20.10    STREAM www.lab.example
172.16.20.10    DGRAM
172.16.20.10    RAW
$ ping -c 1 www.lab.example
PING www.lab.example (172.16.20.10) 56(84) bytes of data.
64 bytes from server.lab.example (172.16.20.10): icmp_seq=1 ttl=63 time=0.508 ms

--- www.lab.example ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.508/0.508/0.508/0.000 ms
$ curl -s http://www.lab.example/
hello from www.lab.example (172.16.20.10, 80/tcp)

ping の返事の行が server.lab.example になっているのは、返事の差出人のアドレス（172.16.20.10）を逆引きした名前だから。ping に渡した名前とは別に引いている（第8章の逆引き）。

たとえ: 電話をかけるとき「まず自分の手帳、載っていなければ番号案内（104）」という決まりで動く秘書に近い（ping）。 dig は、いつも番号案内に直接かける人である。手帳に古い番号が残っていると、秘書だけが古い番号にかけ続ける。
ただし崩れる点: 人の秘書なら「最近この番号つながりませんね」と気づいて手帳を直すが、NSS は files で見つかった時点で dns を見に行かない。 つながらなくても、何度でも古い行を使う。

順番を入れ替える

この節で分かること: nsswitch.conf の順番が、答えをどう変えるか。

わざと ns.lab.example の偽の行を /etc/hosts に足し、順番を入れ替えて比べる。

$ echo '172.16.20.88 ns.lab.example' | sudo tee -a /etc/hosts
172.16.20.88 ns.lab.example
$ getent ahosts ns.lab.example
172.16.20.88    STREAM ns.lab.example
172.16.20.88    DGRAM
172.16.20.88    RAW
$ sudo sed -i 's/^hosts:.*/hosts:          dns files/' /etc/nsswitch.conf
$ grep '^hosts' /etc/nsswitch.conf
hosts:          dns files
$ getent ahosts ns.lab.example
172.16.20.10    STREAM ns.lab.example
172.16.20.10    DGRAM
172.16.20.10    RAW
$ sudo sed -i 's/^hosts:.*/hosts:          files dns/' /etc/nsswitch.conf
$ sudo sed -i '/172.16.20.88/d' /etc/hosts

files dns のときは /etc/hosts の偽の行（.88）が、dns files にすると DNS の答え（.10）が勝った。 順番を変えると練習機のすべての名前の引き方が変わるので、ふつうは /etc/hosts の行のほうを直す。最後に元に戻した。

たとえ: 図書館で「まず自分の書棚、無ければ図書館」と決めている人と、「まず図書館、無ければ自分の書棚」と決めている人に近い。 同じ本の古い版が自分の書棚にあると、前の人だけが古い版を読み続ける。
ただし崩れる点: 人は図書館に新しい版があれば気づけるが、NSS は先に見つけた方で止まり、もう一方を見に行かない。 「どちらが新しいか」ではなく「どちらを先に見るか」で答えが決まる。

もう1つ、getent hosts（a の付かない方）との違いを押さえておく。IPv4 と IPv6 の両方を持つ名前で比べる。

$ getent hosts server.lab.example
fd00:20::10     server.lab.example
$ getent ahosts server.lab.example
fd00:20::10     STREAM server.lab.example
fd00:20::10     DGRAM
fd00:20::10     RAW
172.16.20.10    STREAM
172.16.20.10    DGRAM
172.16.20.10    RAW

getent hosts は IPv6（AAAA）を先に聞き、見つかればその種類（IPv6）のアドレスだけを出す。IPv4 の 172.16.20.10 は出てこない。 getent ahosts は両方を、使う順に並べる。この違いが、答えの食い違いになる場面を作る。 /etc/hosts に server.lab.example の IPv4 の行だけを足す（DNS には IPv4 と IPv6 の両方がある）。

$ echo '172.16.20.77 server.lab.example' | sudo tee -a /etc/hosts
172.16.20.77 server.lab.example
$ getent hosts server.lab.example
fd00:20::10     server.lab.example
$ getent ahosts server.lab.example
172.16.20.77    STREAM server.lab.example
172.16.20.77    DGRAM
172.16.20.77    RAW
$ ping -c 1 server.lab.example
PING server.lab.example (172.16.20.77) 56(84) bytes of data.
From router.lab.example (192.168.10.1) icmp_seq=1 Destination Host Unreachable

--- server.lab.example ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss, time 1ms
$ sudo sed -i '/172.16.20.77/d' /etc/hosts

getent hosts は IPv6 を探し、/etc/hosts には無いので DNS まで聞きに行って、DNS の fd00:20::10 を答えた。 getent ahosts は /etc/hosts で名前を見つけた時点で止まり、172.16.20.77 だけを答えた。ping が向かったのは 172.16.20.77 で、getent ahosts の答えと同じである。 ping の答えを確かめる道具は getent ahosts（IPv4 だけを見るなら getent ahostsv4）。getent hosts も NSS の順に従って引くが、IPv6 を先に聞くぶん、ping と違う答えを出すことがある。最後に、足した行を消した。

道具読む表/etc/hosts を見るか
dig / host / nslookupDNS サーバ（resolv.conf の nameserver、または指定したサーバ）見ない（ただし問い合わせ先が 127.0.0.53 なら、systemd-resolved が /etc/hosts を混ぜて答える。第8章）
ping / curl / ssh / tracerouteNSS（/etc/nsswitch.conf の hosts: の順）見る（files が先なら最優先）
getent ahosts（ahostsv4）NSS。ping・curl と同じ関数（getaddrinfo）で引く見る。ping の答えを確かめる道具（先頭の行が ping の使うアドレス）
getent hostsNSS。ただし IPv6 を先に聞く見る。IPv4 と IPv6 の両方がある名前では、ping と答えが違うことがある
確認

/etc/nsswitch.conf が hosts: files dns で、/etc/hosts に 10.0.0.5 app.example.com があり、DNS では app.example.com は 10.0.0.9 である。 getent hosts app.example.com と dig +short app.example.com の結果の組み合わせとして正しいものはどれか（IPv6 のアドレスは無いものとする）。

A. 10.0.0.5 と 10.0.0.5　B. 10.0.0.5 と 10.0.0.9　C. 10.0.0.9 と 10.0.0.9　D. 10.0.0.9 と 10.0.0.5

答え

B。getent は NSS の順（files が先）で /etc/hosts の 10.0.0.5 を返す。dig は DNS サーバだけに聞くので 10.0.0.9。 ping や ssh で app.example.com に接続すると 10.0.0.5 に行く。この練習機の www.lab.example と同じ形である。 （IPv6 のアドレスがあると getent hosts は IPv6 を先に聞くので、問題文で「無いものとする」と断ってある。）

ホスト名は、3か所にある

この節で分かること: hostname・/etc/hostname・/etc/hosts の関係と、どれが再起動で残るか。
$ hostname
linuc
$ cat /etc/hostname
linuc
$ grep 127.0.1.1 /etc/hosts
127.0.1.1 linuc
$ hostname -I
10.0.2.15 10.0.3.50 10.0.4.15 192.168.10.2 fd00:10::5054:ff:fe0a:2
$ hostname -s
linuc
$ hostname -i
127.0.1.1
$ hostname -f
linuc

今のホスト名（カーネルが持っている値。hostname が出す）、起動時に読む名前（/etc/hostname）、 その名前を自分のアドレスに引くための行（/etc/hosts の 127.0.1.1。Debian 系の慣習）の3つがある。 hostname のオプションは、表示を変えるものが多い。-I は自分のアドレスを並べる（リンクローカルとループバックは除く）。-i は自分の名前を名前解決して得たアドレス（ここでは /etc/hosts の 127.0.1.1）、 -s は短い名前（最初の . より前）、-f は完全な名前（FQDN。ここではドメインが付いていないので linuc のまま）。 hostname で名前を変える。

$ sudo hostname web01
$ hostname
web01
$ cat /etc/hostname
linuc
$ sudo true
sudo: unable to resolve host web01: Temporary failure in name resolution
$ hostname -f
hostname: Temporary failure in name resolution

変わったのは今の値だけで、/etc/hostname は linuc のまま。そして sudo が「web01 を引けない」と言い出した。 sudo は自分のホスト名を名前解決で確かめる。/etc/hosts には 127.0.1.1 linuc しか無く、DNS にも web01 は無い（hostname -f も完全な名前を出せない）。 練習機を再起動する（ssh は切れるので、1分ほど待って外から ssh linuc で入り直す）。

$ sudo systemctl reboot
sudo: unable to resolve host web01: Temporary failure in name resolution
...
$ hostname
linuc
$ sudo true

起動時に /etc/hostname が読まれ、linuc に戻った。sudo も黙った。 ついでに、この章までに直したものが再起動を越えて残っているかを確かめる。

$ ip route show default
default via 192.168.10.1 dev lab0 onlink
$ ifquery --state
lo=lo
lab0=lab0
enp0s17=enp0s17
$ nmcli device status
DEVICE   TYPE      STATE      CONNECTION
enp0s18  ethernet  connected  lab-dhcp
enp0s16  ethernet  unmanaged  --
enp0s17  ethernet  unmanaged  --
lab0     ethernet  unmanaged  --
lo       loopback  unmanaged  --
$ cat /etc/resolv.conf
nameserver 172.16.20.10
search lab.example
$ ss -tln | grep 8080
LISTEN 0      10           0.0.0.0:8080      0.0.0.0:*

デフォルトルート（第4章・ifupdown のファイル）、enp0s17（第3章・ifupdown）、enp0s18（第3章・NetworkManager）、resolv.conf（第8章・ふつうのファイル）、 掲示板の待ち受け（第7章・サービスの設定）。全部、持ち主の設定ファイルに書いたので残った。 名前を残す形で変えるなら hostnamectl を使う。

$ sudo hostnamectl set-hostname web01
$ cat /etc/hostname
web01
$ hostnamectl hostname
web01
$ sudo true
sudo: unable to resolve host web01: Temporary failure in name resolution
$ sudo hostnamectl set-hostname linuc
sudo: unable to resolve host web01: Temporary failure in name resolution
$ sudo true
$ cat /etc/hostname
linuc

hostnamectl set-hostname は今の値と /etc/hostname の両方を変える。それでも sudo は文句を言う。/etc/hosts の 127.0.1.1 の行は変えてくれないからである。 名前を変えるなら、3か所目（/etc/hosts）も自分で直す。

NetworkManager からも変えられる（第3章の nmcli general）。hostname コマンドにも、名前を決める形がもう2つある。

$ sudo nmcli general hostname web03
$ cat /etc/hostname
web03
$ sudo nmcli general hostname linuc
sudo: unable to resolve host web03: Temporary failure in name resolution
$ cat /etc/hostname
linuc

nmcli general hostname 名前 は /etc/hostname まで書き換えた（今の名前も変わる。hostnamectl と同じく /etc/hosts は変えないので、次の sudo が文句を言った）。

$ sudo hostname -b web02
$ hostname
web02
$ sudo hostname -F /etc/hostname
sudo: unable to resolve host web02: Temporary failure in name resolution
$ hostname
linuc

hostname -b 名前 は名前を決める（hostname 名前 と同じく今の値だけ）。hostname -F ファイル はファイルに書いてある名前にする。 -F /etc/hostname なら、再起動せずに起動時と同じ名前へ戻せる。

打ち方何をするか
hostname今の名前を出す
hostname -s / -f短い名前 / 完全な名前（FQDN）を出す
hostname -i自分の名前を名前解決して得たアドレスを出す
hostname -INIC に付いている自分のアドレスを並べる（ループバックとリンクローカルは出ない）
hostname 名前 / hostname -b 名前今の名前を変える（再起動で /etc/hostname の名前に戻る）
hostname -F ファイルファイルに書いてある名前にする
置き場所役割変える道具再起動すると
今の名前（カーネル）プロンプトやログに出る名前hostname 名前/etc/hostname の値に戻る
/etc/hostname起動時に読む名前hostnamectl set-hostname・nmcli general hostname（またはファイルを直接）残る
/etc/hosts の 127.0.1.1自分の名前を自分のアドレスに引く手で書く残る（hostnamectl は直さない）
たとえ: 名札（今の名前）、社員名簿（/etc/hostname）、内線表（/etc/hosts）に近い。 名札だけ付け替えても、翌朝は名簿の名前の名札が配られる。名簿を直しても、内線表が古いと「その名前の人は内線表にいない」と言われる。
ただし崩れる点: 会社なら総務が名簿と内線表をまとめて直すが、Linux では hostnamectl は名簿までしか直さない。内線表は自分で直す。
確認

ホスト名を hostname newname で変更したあと、システムを再起動した。再起動後のホスト名はどうなるか。

A. newname のまま　B. /etc/hostname に書かれている名前に戻る　C. /etc/hosts の 127.0.0.1 の行の名前になる　D. localhost になる

答え

B。hostname コマンドはカーネルが持つ今の値だけを変える。起動時には /etc/hostname が読まれる。 再起動後も残したいなら hostnamectl set-hostname を使うか /etc/hostname を書き換え、/etc/hosts の 127.0.1.1 の行も合わせる。

手を動かす: 実践編の演習07が、www.lab.example を正しいサーバに向ける課題である。 判定は getent ahostsv4 www.lab.example の答えと、判定の中で実際に http://www.lab.example/ を取りに行った結果を見る（DNS が引けない状態では「この環境では判定できません」と出る）。

9章を通して見たもの

この節で分かること: 9つの章が1つの事実から出ていたこと。

この9章で驚いたことは、どれも「道具が読んだ表が違った」だけだった。

章食い違ったものそれぞれが読んでいた表
1254 台の半分が 127 台にならないマスクが引く線（ネットワークアドレスとブロードキャストが分けた数だけ要る）
2ifconfig と ip addr名前ごとに1つのアドレスを返す古い窓口 ／ NIC の全部のアドレス
3ifup / ifdown と NIC の実際ifupdown 自身の作業記録 ／ カーネルの状態
4ping の相手と、返事をした機械経路表のデフォルトルートの1行
5traceroute の * と、実際の到達途中の機械が返す ICMP（返さないこともある）
6設定に無い IPv6 アドレスルータ広告と MAC アドレス
7LISTEN と、外からの接続待ち受けの表の Local Address
8resolv.conf に書いた1行systemd-resolved が作り直す /run のファイル
9dig と pingDNS サーバ ／ NSS（/etc/hosts が先）

ネットワークの「見え方」は、道具が読んだ表で決まる。 ifconfig と ip、ifup と nmcli、dig と ping は、同じものを別々の表から読んでいる。 つながらないときは、相手を疑う前に「どの道具が、どの表の、どの1行を読んだか」を確かめる。

主題1.07 の詳細欄にコマンドと設定ファイルが並んでいるのは、試験が「どの道具が何を読むか」を問うているからである。 表の場所（/etc/network/interfaces（RHEL 系なら /etc/sysconfig/network-scripts/ifcfg-名前）・/etc/resolv.conf・/etc/nsswitch.conf・/etc/hosts・/etc/hostname）と、それを読む道具を組で覚えれば、選択肢の大半は消去できる。

この章で分かったこと

持ち帰ってほしいこと

  • /etc/nsswitch.conf の hosts: files dns は「先に /etc/hosts、無ければ DNS」。順番を変えると全部の名前の引き方が変わる
  • dig / host は DNS サーバだけに聞く。ping / curl / ssh は NSS を通す。ping が使うアドレスは getent ahosts（IPv4 だけなら getent ahostsv4）で確かめる。先頭の行が ping の使うアドレス
  • getent hosts は IPv6 を先に聞き、見つかれば IPv6 のアドレスだけを出す。/etc/hosts に IPv4 だけ・DNS に IPv6 がある名前では、ping と違う答えになる
  • hostname 名前 は今だけ。再起動で /etc/hostname に戻る。hostnamectl set-hostname は /etc/hostname まで変えるが、/etc/hosts の 127.0.1.1 は変えない
  • 直したものを再起動で残すには、それぞれの持ち主の設定ファイルに書く
