3. 書き込みは、まとめると270倍速い

同じ 2000 行の挿入が、12.996 秒と 0.048 秒になる。 差を作っているのは SQL の書き方ではなく、ディスクの返事を何回待つかであり、その待ちを発生させているのは、いまあなたが起動したプロセス自身である。

前提: 第1章前提: 第2章前提: sqlite3 が打てる所要 16分影響度 A最終検証 2026-09-30

この章のゴール

  • BEGIN で囲まないと1行ごとにディスク同期が起きることを、実測の秒数で示せる
  • なぜ遅いのかを「誰が fsync を呼んでいるか」で説明できる
ここで覚えなくていいこと: PRAGMA synchronous にどんなモードがあり、どれが何を省くのかは覚えなくていい。 WAL をいつどうやってチェックポイントするかも扱わない。 OS が「書き終わった」と返した先で、データが物理的にどこまで残る形になっているか（ディスク側のキャッシュ、電源が落ちたときの扱い）も、この章では追わない。 押さえるのはコミットの回数が待ちの回数を決めるという関係ひとつだけで、モードの選択はその関係が分かったあとの話である。

同じ 2000 行が、13 秒と 0.05 秒になる

この節で分かること: 実測した2つの秒数と、その差が SQL の書き方から来ていないこと。

使うのは、採取時に置いた2つのシェルスクリプトである。 naive.sh は 2000 行の INSERT 文を sqlite3 に流すだけのもの。 txn.sh は同じ 2000 行の前に BEGIN;、後ろに COMMIT; を足して流すもの。 違いはこの2行だけである。

先に naive.sh のほうを走らせた記録を見る。 各コマンドのあとの [exit 0] は採取スクリプトが終了コードを書き足したもので、sqlite3 の出力ではない。

実測
--- 1行1トランザクション（既定） ---
$ time bash naive.sh

real	0m12.996s
user	0m0.078s
sys	0m0.472s
[exit 0]
$ sqlite3 t3a.db 'SELECT count(*) FROM a;'
2000
[exit 0]

12.996 秒。行数は 2000 で、狙った分だけ入っている。 次に BEGIN; と COMMIT; を足したほうを走らせる。

実測
--- BEGIN...COMMIT で囲む ---
$ time bash txn.sh

real	0m0.048s
user	0m0.033s
sys	0m0.012s
[exit 0]
$ sqlite3 t3b.db 'SELECT count(*) FROM b;'
2000
[exit 0]

0.048 秒。12.996 を 0.048 で割ると約 270 になる。 入った行数はどちらも 2000 で同じ。仕事の量は変わっていない。 変わったのは SQL 2行ぶんだけで、それが 270 倍の差になっている。

ふつうこう考える

2000 行の挿入に 13 秒かかるなら、重いのは SQL の処理側だろう。 インデックスが張られていれば1行ごとに索引を更新するので、まずインデックスを落とす。 それでも遅ければ INSERT の書き方を見直す。 あるいは逆に、SQLite は軽量だと聞いているので 2000 行で 13 秒は出ないはずで、自分の測り方が間違っている、と考える。

だめな理由: 上の記録には、それを否定する行が最初から入っている。 user が 0.078 秒、sys が 0.472 秒。合わせて 0.550 秒。 13 秒のうち CPU が回ったのは 0.55 秒だけである。 SQL の解析にも索引の更新にも CPU を使う。CPU が動いていないなら、そこは律速ではない。 落とすべきインデックスを探しても、削れるのは 0.550 秒の内側にすぎない。 残りの 12.4 秒でプロセスは何かを待っている。次の節はその 12.4 秒だけを見る。

13 秒のうち 12.4 秒は、CPU が動いていない

この節で分かること: time が出す3行の読み方と、real から user+sys を引いた残りが何を表すか。

time は3行を出す。real は走り始めてから終わるまでの経過時間。 user はユーザ空間で CPU を使った時間。sys はカーネルの中で CPU を使った時間。 前者は時計の進みで、後者2つは CPU が回った量である。単位が同じだけの別物なので、引き算には意味がある。

たとえ: real は家を出てから帰るまでの時間、user と sys は実際に口を動かして用件を話していた時間にあたる。13 分出かけて 33 秒しか話していなければ、残りは並んでいた時間である。
ただし崩れる点: 行列の前には他の客がいるが、ここには他の客がいない。窓口は空いている。自分が出した書き込みが落ち切るのを、自分で待つと決めているから待っている。混雑ではなく仕様である。
realusersysuser+sysreal −(user+sys)
BEGIN なし0m12.996s0m0.078s0m0.472s0.550 秒約 12.4 秒
BEGIN あり0m0.048s0m0.033s0m0.012s0.045 秒約 0.003 秒

読むべきは右端の列である。BEGIN なしでは経過時間の 96 パーセントが CPU を回していない時間で、BEGIN ありではほぼゼロになる。 速くなった側は「同じ仕事を速く計算した」のではない。待たなくなっただけである。

厳密には、real から user と sys を引いた残りには、他のプロセスに CPU を譲っていた時間も混ざる。 ただしその筋はこの記録では立たない。同じ機械で直後に走った txn.sh が 0.048 秒で終わっているので、機械が混んでいたのではない。 BEGIN なしの側だけが、12.4 秒ぶん何かの完了を待っている。

もう1列、sys も動いている。0.472 秒から 0.012 秒へ落ちている。 sys はカーネルに頼んだ仕事に使われた CPU である。 減ったのは SQL の処理ではなく、カーネルへの依頼のほうだった。

確認問題

  1. real が 12.996s、user+sys が 0.550 秒のとき、残りの約 12.4 秒間、このプロセスは何をしているか。
  2. インデックスを落として測り直したら real はどこまで縮むと見積もれるか。上の6つの数字だけから答える。
答え

1. 待っている。CPU を回さずに、何かの完了を待って止まっている。「処理が重い」と「時間がかかる」は、この2行で切り分けられる。

2. ほとんど縮まない。索引の更新は CPU を使う仕事なので、削れるのは user+sys の 0.550 秒の内側だけである。12.4 秒には手が届かず、real は 13 秒近くのままになる。

待っているのは、自分が呼んだ同期の返事

この節で分かること: BEGIN を書かないと1文ごとにコミットが起き、コミットごとに同期の返事を待つ。その待ちを出しているのは自分のプロセスである。

BEGIN を書かなかった SQL 文は、それ単独で1つのトランザクションになる。 2000 行流したなら、区切りが 2000 個できる。 区切りのたびに、書いた内容がもう消えない場所まで落ちたという返事を待つ。 この待ちが 2000 回直列に並んだものが、前節の 12.4 秒である。

ディスクへの同期をカーネルに頼むシステムコールが fsync で、返事が返るまで呼んだ側は止まる。 前節で sys が減ったのは、この依頼が減ったからである。 そして fsync を呼んでいるのは常駐サーバではない。 sqlite3 と打って起動した、そのプロセス自身である。

ここで前提が効いてくる。SQLite にはサーバがない。 返事を待っているプロセスと、待たせているプロセスが、同じ1つのプロセスである。 自分でファイルに書き、自分で同期を頼み、自分で返事を待って止まっている。 待ち時間を短くしてくれる係が、どこにもいない。

たとえ: 1文ずつコミットするのは、手紙を1通出すたびに窓口へ行き、受領印をもらって帰ってくることにあたる。2000 通なら 2000 往復する。BEGIN と COMMIT で囲むのは、2000 通を1つの袋に入れて1回だけ持っていくことにあたる。
ただし崩れる点: 窓口の人は他人だが、ここには他人がいない。往復しているのは自分の足で、窓口に座っているのも自分である。他人が遅いのではなく、自分が 2000 回歩いている。
たとえ: コミットは、書いた紙を机に置くことではなく、金庫に入れて扉を閉め、閉まったことを確かめてから手を離すことにあたる。扉が閉まるまで次に進まないと決めているぶんだけ時間がかかる。
ただし崩れる点: 金庫の扉が閉まったかは目で見えるが、ディスクの内側は見えない。見えるのは OS が「終わった」と返したところまでで、その返事の先でデータが物理的にどこまで残る形になっているかは、この章では追わない。

常駐プロセスがいる作りなら、複数の書き込みを束ねる判断をその常駐プロセスに置くことができる。 SQLite にはその置き場所がない。束ねるかどうかを決める場所は1つだけで、あなたが流す SQL の中である。 BEGIN はそのための語で、設定を変えているのではなく、自分のプロセスに「まだ待つな」と伝えている。

確認問題

  1. BEGIN を書かずに 2000 行流したとき、トランザクションはいくつ作られるか。
  2. naive.sh と txn.sh は、終わったあとの行数がどちらも 2000 だった。この一致は、この章の主張にとってなぜ必要か。
答え

1. 2000 個。文が単独でトランザクションになるので、行数と同じ数になる。区切りの数が待ちの数になる。

2. 速いほうが手を抜いていない、という確認になるからである。「同じ仕事が 270 分の1の時間で終わった」と言えるのは、両方が 2000 行を入れ終えているときだけ。片方が 1500 行しか入れていなければ、秒数を並べても比較にならない。速さを比べる前に、結果が同じであることを先に見る。

BEGIN は書式ではなく、待つ回数の宣言

この節で分かること: 同じ 2000 文でも、囲むと待ちが 2000 回から1回になる。囲む単位を決めるのは流す側である。

数字の出どころは割れた。残るのは、この差をどう使うかである。 結論は単純で、まとめて書けるものはまとめて囲む。2000 行を1つの BEGIN で囲めば、待ちは1回になる。

1回のコミットで同期が何回起きるかは、SQLite が journal をどう扱うかによって変わる。この章ではそこを数えない。 数えなくても結論は動かない。コミットの数が待ちの数を決めるので、コミットを 2000 から1にすれば待ちは減る。

たとえ: BEGIN と COMMIT は SQL に付ける括弧にあたる。中の 2000 文が1つのまとまりとして扱われる。
ただし崩れる点: 括弧はふつう読みやすさのための記法で、付けても実行されるものは変わらない。この括弧は違う。付けた瞬間に、ディスクの返事を待つ回数が 2000 から1に変わる。見た目の整理ではなく、実行される待ちの回数を書き換えている。

逆から読むと、囲む範囲の決め方がそのまま速さの決め方になる。 2000 行を1つに囲めば待ちは1回、200 行ずつ10個に囲めば10回、囲まなければ 2000 回。 後ろの2つは上の記録から測ったものではなく、コミットの数が待ちの数を決めるという読みからの帰結である。 どこで区切るかを SQLite は決めない。流す側が書いた BEGIN の位置が、そのまま待ちの回数になる。

対応する演習は lab start 03。判定は lab check 03。 naive.sh と txn.sh は演習の中に置いてある。 手元の real は機械によって変わるが、real と user+sys の差が BEGIN の有無で消えることは変わらない。そこを見る。

確認問題

  1. 2000 行を1つの BEGIN で囲んだときと、200 行ずつ10個に分けて囲んだときで、同期の待ちは何回ずつになるか。
  2. BEGIN を足したのに real がほとんど縮まなかった、という報告を受けた。time の3行のどこを最初に見るか。
答え

1. 1回と10回。コミットの数がそのまま待ちの数になる。

2. user と sys を見て、real との差が消えているかを確かめる。差が消えていれば待ちは無くなっていて、残っているのは CPU の仕事である（それ以上は縮まないのが正しい）。差がまだ大きければ待ちが残っているので、囲んだつもりの範囲が実際には囲めていない可能性を疑う。

この章で分かったこと

持ち帰ってほしいこと

  • 同じ 2000 行の挿入が 12.996 秒と 0.048 秒になる。違いは BEGIN; と COMMIT; の2行だけで、約 270 倍。
  • 遅い側の 13 秒のうち CPU が回ったのは 0.550 秒。残りの約 12.4 秒は待ち時間で、SQL やインデックスを直しても届かない。
  • BEGIN を書かない文は1文で1トランザクションになり、区切りごとに同期の返事を待つ。待ちの回数はコミットの回数で決まる。
  • 待たせているのも待っているのも、同じ1つのプロセスである。束ねてくれる常駐プロセスはいない。束ねる位置を決めるのは、流す SQL の中の BEGIN である。
