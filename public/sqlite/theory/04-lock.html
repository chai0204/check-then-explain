4. 同時に書けるのは1人だけ

database is locked は、DB が返してきた拒否通知ではない。自分が起動したプロセスが、ファイルに掛かった印を見て、自分で書いた1行である。

前提: 第3章まで所要 14分影響度 A最終検証 2026-09-30

この章のゴール

  • database is locked が出る条件を、そのとき誰がロックを持っているかで説明できる
  • ロック中の読み取りが 0 を返す理由を説明できる
  • WAL にして変わることと変わらないことを、出力を根拠に区別できる
ここで覚えなくていいこと: ロックの5状態（SHARED / RESERVED / PENDING / EXCLUSIVE）の遷移図は覚えなくていい。この章は「印が掛かっているか、いないか」の2値だけで進む。
busy_timeout に何秒を入れるべきかも決めなくていい。既定が「待たない」であることだけ押さえる。
WAL ファイルの内部形式も読まなくていい。この章で扱うことは全部、外から観測できる。

この行を出しているのは、自分のプロセス

この節で分かること: ロックを持っている側と、エラーを出している側は別のプロセスである。

まず、この DB がどのモードで動いているかを確かめる。テーブルを1つ作り、モードを聞く。

$ sqlite3 lock.db 'CREATE TABLE t(n INTEGER);'
$ sqlite3 lock.db 'PRAGMA journal_mode;'
delete

delete が既定である。切り替えた覚えがなければ、手元の DB もこれで動いている。

この lock.db に対して、別のプロセスが書き込みのトランザクションを開いたまま、まだ終えていない状態を作る。相手側を作る手順はこのページには出てこない。演習 04 が用意する。ここでは、その状態のときにもう1つのプロセスから1行入れると何が返るかを見る。

$ sqlite3 lock.db 'INSERT INTO t VALUES(2);'
Error: stepping, database is locked (5)

手元では database is locked という趣旨のメッセージが出る（文言は環境で変わる）。末尾の (5) は SQLite の結果コードで、プロセスの終了コードも 5 になる。

この1行に何が書かれていないかを見てほしい。ロックを持っている相手の名前もプロセス ID も入っていない。つまりこのメッセージから分かるのは「自分ではない誰かが持っている」ところまでで、それが誰かは書いていない。障害の切り分けで「誰が持っているか」を知りたいなら、このメッセージの外を見に行くことになる。

たとえ: ロックは、受付が順番を管理する予約ではなく、ドアに掛かった札に近い。次に来たプロセスが自分で札を見て、掛かっていたら引き返す。
ただし崩れる点: 実物の札には掛けた人の名前や戻り時刻が書いてある。ここでは何も書いていない。だから引き返した側は、相手が誰でいつ終わるのかを知らないまま引き返す。

もう1つ、時間の感覚に注意する。このエラーは待った末に諦めた結果ではない。既定の busy_timeout は 0 で、印が掛かっていればその場で返る。競合が長く続いたから出たのではなく、その瞬間に印があったという観測でしかない。だから「たまに出る」ではなく「当たれば必ず出る」性質のものになる。

たとえ: このエラーは、閉まった店の前で自分がメモ帳に「閉店」と書いたのに近い。店から連絡が来たわけではない。
ただし崩れる点: 店なら営業時間の札を出しているので、次にいつ来ればいいか分かる。DB 側は何も掲示しない。次に来た者が自分で確かめ直すしかない。

ここが SQLite の輪郭が出るところである。順番待ちを仲裁する常駐プロセスが居ない。だから列ができない。印を見て引き返すか書き込むかを決めているのは、そのつど起動されたプロセス自身であり、ロックはファイルシステム上に置かれた印にすぎない。

確認問題

  1. database is locked が、ほとんど待ち時間なしで返ってきた。ここから相手のプロセスの状態について何か言えるか。
  2. その database is locked という文字列を画面に出力したのは、どのプロセスか。
答え

1. 何も言えない。待ち時間の長短は相手の状態ではなく、自分側の busy_timeout が決めている。既定は「待たない」なので、相手が 1 ミリ秒後に終わる場合でも同じように即座に返る。

2. 自分が起動した sqlite3 プロセス。相手のプロセスから送られてきた返事ではない。だから相手の名前も入っていない。

ロック中でも読める。ただし 0 が返る

この節で分かること: 書き込みが弾かれた同じ瞬間に読み取りは通り、返る値はコミット済みの分だけになる。

書き込みが弾かれたのと同じ状況で、読み取りを投げる。相手は1行入れたところで止まっている。

$ sqlite3 lock.db 'SELECT count(*) FROM t;'
0

読み取りは通っている。終了コードは 0 で、エラーも出ていない。そして返ってきた値は 0 である。

この 0 は「読めなかった」でも「DB が壊れている」でもない。確定している行数が 0 である、という正しい答えだと読む。相手が入れた1行は相手のトランザクションの中にあり、まだ確定していないので数に入らない。相手が終わったあと、同じコマンドを同じ DB に投げるとこうなる。

$ sqlite3 lock.db 'SELECT count(*) FROM t;'
1

つまり 0 と 1 の差は、DB の状態の差ではなく、いつ聞いたかの差である。障害報告で「データが消えている」と言われたとき、この違いを切り分けられるかどうかが効く。

たとえ: 書き込み中の行は、まだ封をしていない封筒の中身に近い。外から数えられるのは、封をして箱に入った分だけである。
ただし崩れる点: 封筒は1通ずつ数えるものだが、ここでは1つの封に何百行でも入る。第3章で 2000 行を1つにまとめたのが、まさにその封である。

ゴールの形に言い直すと、こうなる。印を持っているのは書き込み側で、その側が印を外していないから2人目は書けない。一方、この記録では印が掛かっている間も読み取りは通っている。「ロックされている」は「何もできない」ではない。誰が何を持っているかで、通るものと弾かれるものが分かれる。

確認問題

  1. ロック中の SELECT count(*) FROM t; が 0 を返した。DB が壊れている可能性を疑うべきか。
  2. 同じコマンドが後から 1 を返した。この記録から言えることは何か。
答え

1. 疑う必要はない。エラーも出ておらず終了コードも 0 で、確定した行が 0 行だという答えが返っている。相手が入れた行はまだ確定していないので見えないだけである。

2. 相手のトランザクションが終わり、行が確定したこと。あわせて、印が消えて読み取りが何も待たされずに通ったこと。印は、走っているプロセスが居る間だけの状態である。

journal_mode は「取り消すための控えをどう取るか」

この節で分かること: delete と WAL が、それぞれ何をファイルに書いているか。

次の節で journal_mode を切り替えるので、先にそれが何の設定なのかを見る。

SQLite は書き込みの途中で電源が落ちても、DB が半端な状態で残らないようにしている。 そのために元に戻せる材料を、書き込む前にファイルへ書き出しておく。 その材料をどう取るかの方式が journal_mode である。既定は delete。

$ sqlite3 d.db 'PRAGMA journal_mode;'
delete

delete: 変更前の内容を別ファイルに退避し、終わったら消す

書き込みを始めると、SQLite はこれから書き換えるページの「変更前の内容」を <DB名>-journal というファイルに写す。そのうえで本体を直接書き換える。 途中で落ちたら、次に開いたプロセスがこのファイルを見つけて、写してあった内容を本体へ戻す。

書き込みを保持したまま、同じディレクトリを見るとこうなる。

$ ls -l d.db*
-rw-r--r-- 1 lab lab 8192 d.db
-rw-r--r-- 1 lab lab 4616 d.db-journal

そして相手がコミットしたあと、もう一度見るとこうなる。

$ ls d.db*
d.db

-journal が消えている。このファイルを削除することが「コミットが完了した」という 印そのもので、だからモード名が delete である。次に開いたプロセスは、 -journal が無ければ「前回は無事に終わった」と判断する。

たとえ: 書き換える前のページをコピー機で控えておき、本に直接書き込む。 無事に書き終えたら控えをシュレッダーに掛ける。控えが残っていたら、 前回の作業が途中で止まったということなので、控えから本を元に戻す。
ただし崩れる点: 控えを捨てる行為が「完了」の合図なので、 捨てられない場所では作業自体を始められない。ここは第5章で踏む。

ロールバックジャーナル系には delete 以外にも truncate（消さずに長さ0に切る）、persist（消さずに先頭を潰す）、 memory（ディスクに書かない）、off（取らない）がある。 どれも「控えをどう始末するか」の違いで、控えを取ること自体は変わらない （off だけは取らないので、落ちたら壊れる）。

WAL: 本体を触らず、変更後の内容を別ファイルに書き足す

WAL は Write-Ahead Log の略で、向きが逆になる。 本体はそのまま置いておき、これから反映したい「変更後の内容」を <DB名>-wal に追記していく。本体はあとでまとめて更新する。 その「あとでまとめて」をチェックポイントと呼ぶ。

$ sqlite3 w.db 'PRAGMA journal_mode=WAL;'
wal

$ ls -l w.db*
-rw-r--r-- 1 lab lab  8192 w.db
-rw-r--r-- 1 lab lab 32768 w.db-shm
-rw-r--r-- 1 lab lab     0 w.db-wal

ファイルが3つになる。-wal が書き足し先で、-shm は どのプロセスがどこまで読んでよいかを共有するための領域である （shared memory の shm）。複数のプロセスが同じ -wal を見るので、 「いまどこまでが確定済みか」を互いに知る場所が要る。

自動のチェックポイントは、-wal が一定のページ数を超えたときに走る。既定値は確かめられる。

$ sqlite3 d.db 'PRAGMA wal_autocheckpoint;'
1000
たとえ: 本には一切書き込まず、変更したい内容を付箋に書いて貼っていく。 読む人は本と付箋を合わせて読む。付箋が溜まったら、まとめて本に書き写して付箋を剥がす。
ただし崩れる点: 付箋を貼れるのは同時に1人である。付箋の束は1つしかないので、 2人が同時に書き足すことはできない。だから書き込みの本数は増えない。
journal_mode の値はファイルに保存される。 接続ごとの設定ではないので、一度 WAL にすれば、別のプロセスが開いても WAL のままである。 
$ sqlite3 w.db 'PRAGMA journal_mode;'
wal
元に戻すこともできる（PRAGMA journal_mode=DELETE; が delete を返す）。

どちらのモードでも、本体とは別のファイルを DB と同じディレクトリに作る。 名前が違い、書く内容が逆で、始末の仕方が違うだけである。 この「別のファイルを作る」が効いてくるのが第5章になる。

WAL にしても、書けるのは1つだけ

この節で分かること: WAL が変えないのは書き込みの本数である。ここが最も誤解される。

ふつうこう考える

書き込みが1つしか通らないなら、journal_mode を WAL に切り替えればいい。WAL は同時実行のためのモードとして紹介されるのだから、切り替えれば2つ目の INSERT も通るはずだ。

$ sqlite3 wal.db 'PRAGMA journal_mode=WAL; CREATE TABLE t(n INTEGER);'
wal

切り替えは成功している。wal が返っている。この DB に対して、さきほどと同じことをする。別のプロセスが書き込みのトランザクションを開いたまま止まっている状態で、もう1つのプロセスから1行入れる。

$ sqlite3 wal.db 'INSERT INTO t VALUES(2);'
Error: stepping, database is locked (5)
だめな理由: 返ってきた文字列が1文字も変わっていない。結果コードも (5) のままである。WAL に切り替えても、1つの DB に書き込めるプロセスは同時に1つだけで、2人目は同じように弾かれる。WAL は書き込みの本数を増やすモードではない。

では WAL に切り替えて何が変わったのか。記録を並べて、言えることと言えないことを分ける。

観測したこと既定（delete）WAL
PRAGMA journal_mode の返り値deletewal
2つ目のプロセスの INSERTError: stepping, database is locked (5)Error: stepping, database is locked (5)
その瞬間の SELECT count(*)00
ls で見えたファイルこの記録には無いwal.db

2行目が、この章で正す誤解の全部である。モードを替えても、同時に書ける本数は 1 から動いていない。

3行目も見ておく。読み取りはどちらのモードでも通り、返り値も同じ 0 だった。つまりこの記録は「WAL にしないと読めない」という逆向きの誤解も支持していない。

ただしこの記録だけでは、WAL が何を解決するのかが分からない。 上の実験はどちらも「書き込みを保持して、別の書き込みと読み取りを試す」形だった。 WAL の効き目が出るのは向きが逆のとき、つまり読み取りを保持して書き込みを試すときである。 それは次の節で別に測る。

前の節の付箋のたとえで言えば、付箋の束は1つしかない。 「各自が自分の紙に書ける」ようにはならないので、2つ目の INSERT は弾かれる。

最後に、WAL に切り替えた直後のディレクトリを見る。同じコマンドを、切り替えた直後と、すべて終わったあとの2回撮っている。返ってきたのはどちらも同じ1行だった。

$ ls wal.db*
wal.db

ここから言えるのは「その瞬間、ディスクに見えたのは wal.db だけだった」ということだけである。だから ls の結果で WAL かどうかを判定してはいけない。判定に使うのは PRAGMA journal_mode; の返り値である。

ロックもモードの効き方も、ファイル一覧には現れない。状態を持っているのは走っているプロセスのほうで、相手が終わった直後の SELECT が何も待たされずに 1 を返したのがその証拠になる。仲裁する者が居ないので、印が残るのも消えるのも、印を掛けたプロセスが生きている間の話である。

対応する演習は lab start 04。ロックを持つ側のプロセスは演習が用意する。判定は lab check 04。

確認問題

  1. 「WAL にすれば2つのプロセスから同時に INSERT できる」は正しいか。記録のどの行が根拠になるか。
  2. WAL に切り替えたあと ls wal.db* が wal.db の1行しか返さなかった。ここから「WAL になっていない」と結論できるか。
答え

1. 誤り。根拠は sqlite3 wal.db 'INSERT INTO t VALUES(2);' が、既定モードのときと同じ Error: stepping, database is locked (5) を返している行。文字列も結果コードも変わっていない。

2. 結論できない。PRAGMA journal_mode=WAL; は wal を返している。ls から言えるのは、その瞬間に見えたファイルが wal.db だけだったということまでで、モードの判定材料にはならない。判定には PRAGMA journal_mode; の返り値を使う。

では WAL は何を解決するのか — 読み手が書き手を止めなくなる

この節で分かること: 向きを逆にした実験で、2つのモードの差がはじめて出る。

こんどは読み取りを保持したまま、書き込みを試す。 別のプロセスで BEGIN; と SELECT を打って、そのまま止めておく。 既定の delete モードでやるとこうなる。

$ sqlite3 d.db 'INSERT INTO t VALUES(2);'
Error: stepping, database is locked (5)

読んでいる人が居るだけで、書き込みが弾かれた。 相手は1行も書き換えていない。ただ読んでいるだけである。 相手が終わったあとに同じコマンドを打つと、こうなる。

$ sqlite3 d.db 'INSERT INTO t VALUES(2); SELECT count(*) FROM t;'
3

同じことを WAL モードの DB でやる。

$ sqlite3 w.db 'INSERT INTO t VALUES(2);'
$ sqlite3 w.db 'SELECT count(*) FROM t;'
3

エラーが出ていない。読み取りを保持したままでも書き込めた。 これが WAL が解決することである。

保持しているもの試すことdeleteWAL
書き込み別の書き込み弾かれる弾かれる（同じ）
書き込み読み取り通る（古い値）通る（古い値）
読み取り書き込み弾かれる通る

表の最後の行だけが違う。言い換えるとこうなる。

  • delete では、読み手と書き手が互いを止める
  • WAL では、読み手は書き手を止めない。書き手同士だけが排他になる

理由は前の節の仕組みから出る。delete は本体を直接書き換えるので、 読んでいる途中で書き換えられると、読み手は半端な状態を見てしまう。だから読み手が居る間は書けない。 WAL は本体に触らず別ファイルに書き足すので、読み手は本体を読み続けられる。 だから同時でも構わない。

たとえ: delete は本に直接書き込むので、 誰かが読んでいる最中にページを書き換えられない。WAL は付箋に書くので、 読んでいる人はそのまま本を読み続けられる。
ただし崩れる点: 読み手が見ているのは付箋を貼る前の状態である。 上の実測でも、書き込んだあとの SELECT は 3 を返しているが、 保持している側のプロセスは最初に見た値を見続けている。 「同時に読める」は「最新が読める」ではない。

WAL の代償

この節で分かること: 「とりあえず WAL」で済まない場面が3つある。

いいことばかりではない。実測で出た代償を挙げる。

1. 読み取り専用の場所では、条件が揃わないと開けない

WAL の DB を、書き込めないディレクトリに置いて SELECT するだけでこうなる。

$ chmod 555 ro
$ sqlite3 ro/w.db 'SELECT count(*) FROM t;'
Error: in prepare, attempt to write a readonly database (8)

読むだけなのに失敗した。-shm（プロセス間で読み取り位置を共有する領域）を 作ろうとして、ディレクトリに書けずに止まっている。

ただし「WAL だと読み取り専用で開けない」と覚えるのは正確ではない。 これは 3.22.0（2018-01-22）より前の制約で、現在は緩和されている。 公式の WAL 解説は、次のいずれか1つを 満たせば読めると書いている。

  • -shm と -wal が既に存在して、読めること
  • DB のあるディレクトリに書き込み権限があること（-shm を作れる）
  • immutable を付けて開くこと

上の実測は3つとも満たしていない（ディレクトリを読み取り専用にし、-shm も無く、 immutable も付けていない）。3つ目を満たすと読める。

$ sqlite3 'file:ro/w.db?immutable=1' 'SELECT count(*) FROM t;'
4000

そのうえで公式はこう添えている。読み取り専用メディアに焼く前には journal_mode=DELETE に戻しておくのが良い作法であると。 CD-ROM、読み取り専用マウント、コンテナイメージに焼き込んだ DB を配る場合は、 WAL のままにしない。

2. ファイルが増え、しかも見える時間が限られる

-wal と -shm は接続が開いている間だけ存在する。 最後の接続が閉じるとき、SQLite は自動でチェックポイントして2つとも削除する。 だから1000行入れたあとでも、コマンドが終わった時点ではこう見える。

$ ls -l w.db*
-rw-r--r-- 1 lab lab 45056 w.db

これは便利でもあり、厄介でもある。便利なのは、ふだんは1ファイルのままでいられること。 厄介なのは、サーバが動いたまま本体だけコピーすると、-wal にある分が欠けること。 バックアップは3つまとめて取るか、.backup のようにロックを見て整合を取る方法を使う。

3. ネットワークファイルシステムで使えない

公式の欠点リストの先頭がこれである。 「WAL を使うすべてのプロセスは同じホストにある必要がある。別のマシンのプロセス同士は メモリを共有できないからだ」と書かれている。

-shm（wal-index）を各プロセスが mmap して共有メモリとして使うためで、 NFS 越しではこの共有が成立しない。

なぜ /dev/shm のような専用の場所ではなく、DB の隣に普通のファイルを置いて mmap しているのか。公式に理由が書かれている。chroot でルートが違うプロセスは 別のファイルを見てしまい、別々の共有メモリを使って DB を壊すから、 「同じ DB ファイルを開くプロセスが必ず同じ共有メモリを使う」ことを保証する唯一の方法として、 DB と同じディレクトリのファイルを mmap している。

ここでも「別のファイルを DB の隣に作る」が出てくる。第5章と同じ構造である。

4. 速さの大半は、耐久性を売って買っている

これが見落とされやすい。journal_mode と対になる synchronous という設定があり、こちらは「どこまでディスクの返事を待つか」を決める。 既定は 2（FULL）で、WAL にしても自動では変わらない。

$ sqlite3 d.db 'PRAGMA synchronous;'
2

公式が載せている組み合わせの表がこうなっている。

synchronousロールバック方式WAL
EXTRA (3)ACIDACID
FULL (2)（既定）耐久性が無いかもしれないACID
NORMAL (1)一貫性が無いかもしれない耐久性が無いかもしれない
OFF (0)一貫性が無い一貫性が無い

WAL + NORMAL の欄が「耐久性が無いかもしれない」である。 これは電源が落ちると、直近のコミットが巻き戻ることがあるという意味である （壊れるのではなく、無かったことになる）。

そして公式自身が、WAL にするなら FULL から NORMAL へ変えることを推奨している。 WAL では NORMAL でも整合性は保証され、コミットが大幅に速くなるからである。

たとえ: FULL は毎回「書けましたね？」と相手に確認してから次へ進む。 NORMAL は確認を省いて進み、区切りのいいところでまとめて確認する。
ただし崩れる点: 省いているのは確認だけで、書く順番は守られている。 だから「途中まで混ざった壊れ方」にはならない。消えるのは末尾のまとまりだけである。

つまり「WAL は速い」と言われる速さの大部分は、この取引で買っている。 何を売ったのかを知らずに WAL を既定にするのが、いちばん危ない。

「とりあえず WAL」という風潮はあるのか

この節で分かること: 実在する。ただし SQLite 公式の既定ではなく、周辺が既定にしている。

WAL を勧める記事は多い。実際にどうなっているかを、各プロジェクトの公式ドキュメントと 実際の設定値で確かめた。既定にしている側と、していない側が同じくらいある。

既定で WAL にする・必須にする既定にしない
Rails（ActiveRecord、7.1 以降）
Room（Android。3 では明示的に既定）
Core Data（iOS 7 / OS X Mavericks 以降）
Litestream（WAL 必須。自動で設定する） 		SQLite 本体（既定は delete）
Django（設定も推奨もしていない）
Laravel（キーはあるが既定は未設定）
Python 標準の sqlite3（言及すら無い）
Android の SQLiteDatabase（既定は truncate）

推奨はするが自動では設定しない、という中間もある（better-sqlite3、Expo SQLite、Bun の bun:sqlite はいずれもドキュメントで推奨しつつ、既定は delete のまま）。

「とりあえず」ではない例 — Rails の設定

Rails が既定にしているのは journal_mode だけではない。 同時にこれらを設定している。

設定何に対応しているか
journal_mode: wal読み手が書き手を止めないようにする
synchronous: normal速さのために耐久性を売る（代償4を承知の上で選んでいる）
journal_size_limit: 64MB-wal が無限に伸びるのを止める（代償2への対策）

つまりこの章で挙げた代償を1つずつ潰した結果としての WALである。 「とりあえず」ではない。真似するなら、この3つをまとめて真似するのが筋になる。

代償が実際に起きた例 — Core Data

Apple は iOS 7 で Core Data の既定を WAL に変えた。その結果、 ストアのファイルをコピーしたり移動したりすると失敗するという事例が出て、 Apple はそれ専用の技術 Q&A（QA1809）を書いている。対処として案内されているのは journal_mode を DELETE に戻す設定である。

代償2（ファイルが増える）が、実際に大規模に発生した記録として読める。

なぜ SQLite 公式は既定を変えないのか

公式がこれを説明している箇所は見つけられなかった。 wal.html、pragma.html、「SQLite が向く用途」のページまで探したが、 欠点の一覧と「既定は delete である」という事実しか書かれていない （そもそも「SQLite が向く用途」のページには WAL の語が1度も出てこない）。

推測としていちばん強いのは後方互換性である。WAL にすると DB ヘッダの2バイトが 1 から 2 に変わり、3.7.0（2010年）より前の SQLite は そのファイルを「暗号化されているか、DB ではない」と報告して開けなくなる。 既定を WAL にすれば、新しく作られるすべての DB が古い実装から読めなくなる。 加えて、-wal と -shm が増えることは 「1ファイルで持ち運べる」という SQLite の最大の売りを削る。

ただしこれは推測である。公式がそう書いているわけではない。 この章でここだけが、実測でも一次情報でも裏が取れていない部分である。

結論

「とりあえず WAL」で困らない場面は多い。1つのプロセスだけが書き、読み手が複数いて、 ローカルのディスクに置いてあり、電源断で直近の数件が消えても困らないなら、 WAL は素直に効く。そうでない条件が1つでもあるなら、この章の4つの代償を確認する。

こういう場合見るべき代償
読み取り専用メディアやイメージに焼いて配る代償1（DELETE に戻す）
ファイルをコピー・バックアップして運用する代償2（3つまとめて扱う）
NFS など複数マシンから開く代償3（WAL は使えない）
電源断で直近のコミットを失えない代償4（synchronous を確認する）
書き込みが複数から同時に来るそもそも WAL では解決しない（この章の主題）

この章で分かったこと

持ち帰ってほしいこと

  • database is locked は、自分のプロセスが印を見てその場で諦めた記録である。相手の名前は書かれていないので、「誰が持っているか」はこのメッセージの外を見る
  • 既定では待たない。だからこのエラーは「たまに出る」ではなく、当たれば必ず出る
  • ロック中でも読める。返る値は確定済みの分だけで、0 は異常ではない
  • WAL にしても、同時に書けるプロセスは1つ。エラーの文字列も結果コードも変わらない
  • モードの確認は PRAGMA journal_mode; の返り値で行う。ファイル一覧では判定できない
  • journal_mode は「取り消すための控えをどう取るか」の設定。delete は変更前の内容を -journal に退避して本体を直接書き換え、コミット時にその控えを削除する（名前の由来）。WAL は本体に触らず変更後の内容を -wal に書き足し、あとでまとめて反映する（チェックポイント）
  • WAL が解決するのは「読み手が書き手を止めること」だけ。delete では読み取りを保持するだけで書き込みが弾かれるが、WAL では通る。書き手同士が排他なのは両方とも同じ
  • WAL には代償がある。読み取り専用の場所に置くと読むことすらできなくなり（-shm を作れない）、ファイルが3つに増え、ネットワークファイルシステムでは使えない
  • どちらのモードでも本体とは別のファイルを同じディレクトリに作る。これが第5章で踏む落とし穴の原因になる
  • WAL の速さの大半は耐久性を売って買っている。synchronous の既定は FULL のままで WAL にしても変わらず、公式は WAL なら NORMAL への変更を推奨している。NORMAL では電源断で直近のコミットが巻き戻りうる
  • 「とりあえず WAL」は実在する風潮だが、SQLite 公式の既定ではない。Rails は WAL と同時に synchronous: normal と journal_size_limit も設定している。真似するならまとめて真似する
