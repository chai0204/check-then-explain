1. これはファイルである

SQLite のデータベースは、ディスクの上にある1個のファイルである。 この章では、そのファイルの先頭16バイトと、プロセス一覧という2箇所から、それを目で確かめる。

前提: sqlite3 が打てる・ls が読める・ps を見たことがある所要 12分影響度 A最終検証 2026-09-30

この章のゴール

  • データベースがファイル1個であることを、ヘッダのバイト列で示せる
  • データを預かる常駐プロセスが存在しないことを、プロセス一覧で示せる
  • サーバが無いことが何を楽にし、何を難しくするかを言える
ここで覚えなくていいこと: B-tree のページがどう連結されているかは要らない。この章で使うのは「ページという単位がある」という事実だけである。 ヘッダ100バイトの全フィールドも要らない。読むのは先頭16バイトと、file が拾ってくる2項目だけである。 VACUUM が内部で何をするかも要らない。「ファイルを詰め直す操作がある」で先に進める。

「データベースを作る」はファイルを作ることである

この節で分かること: 表を1つ作ると、ディスクに何が増えるのか

表を作って1行入れる。その前に立ち上げるサービスは無い。 sqlite3 に渡す引数はホスト名でもポート番号でもなく、パスである。

$ sqlite3 notes.db 'CREATE TABLE notes(id INTEGER PRIMARY KEY, body TEXT); INSERT INTO notes(body) VALUES("hello");'
$ ls -la notes.db
-rw-r--r-- 1 lab lab 8192 Sep 30 19:07 notes.db

増えたのは notes.db という1ファイルである。所有者と権限が付いている。 つまりこのデータベースに対するアクセス制御は、いま画面に出ている -rw-r--r-- 1 lab lab がそのまま担っている。

次に、そのファイルが何であるかを file に聞く。

$ file notes.db
notes.db: SQLite 3.x database, last written using SQLite version 3045001, file counter 2, database pages 2, cookie 0x1, schema 4, UTF-8, version-valid-for 2

ここから2つだけ読む。database pages 2 と、ファイルサイズ 8192 バイトである。 割ると 1 ページ 4096 バイトになる。1行しか入れていないのにファイルが 8192 バイトあるのは、 確保の単位がバイトではなくページだからである。残りのフィールドはこの章では読まない。

たとえ: 一冊のノート。sqlite3 notes.db の引数は「どのサーバに繋ぐか」ではなく「棚のどこにそのノートがあるか」である。
ただし崩れる点: ノートは書いた分だけ埋まっていくが、このファイルは1行書いた時点で 8192 バイトある。 大きさは書いた文字数ではなくページ数で決まっていて、紙のノートのように「使った分」とは対応しない。

先頭16バイトに書名が書いてある

この節で分かること: このファイルが SQLite のものだと、どこを見て判断されているのか

先頭16バイトを16進で見る。暗号化も圧縮もされていないので、文字がそのまま読める。

実測
$ xxd -l 16 notes.db
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
          │                                  │ └ 16バイト目 0x00 が終端
          │                                  └ 0x33 = 文字 '3'
          └ 0x53 0x51 0x4c 0x69 … = S Q L i …（ASCII）

右端の SQLite format 3. は xxd が同じ16バイトを ASCII として並べ直したものである。 末尾のドットは表示できない 0x00 の代わりに置かれた記号で、ピリオドという文字が入っているわけではない。 file がこのファイルを「SQLite 3.x database」と言い当てられたのは、この並びを見たからである。

さきほどの file の出力には last written using SQLite version 3045001 があった。 3桁ずつ区切ると 3 / 045 / 001 になる。手元の版を聞くとこうなる。

$ sqlite3 --version
3.45.1 2024-01-30 16:01:20 e876e51a0ed5c5b3126f52e532044363a014bc594cfefa87ffb5b82257ccalt1 (64-bit)

3.45.1 と一致する。ファイルの中に、最後に書き込んだライブラリの版が刻まれている。 書いた主体がファイルに署名を残しているわけで、この時点ですでに「誰が書いたのか」の答えが常駐プロセスではないことが見えている。

たとえ: この16バイトは背表紙の書名である。中を1ページも読まずに、何の本かが分かる。
ただし崩れる点: 本は背表紙が剥がれていても読める。この16バイトは飾りではなく判定に使われるので、 違っているとライブラリはそのファイルをデータベースとして扱わない。次の節でそれを実際に起こす。

プロセス一覧にデータベースがいない

この節で分かること: いま SELECT を実行しているのは誰のプロセスか

サーバ型のデータベースなら、ここに常駐プロセスの行が並ぶ。その行が接続先である。数えてみる。

$ ps -ef | grep -c "[s]qlite"
1

1 である。この 1 は、いま打ったこの検査そのもののコマンドラインが数えられたものであって、 データを預かって待っているプロセスではない。データベースのために常駐しているプロセスは1つも無い。

では前の節の CREATE TABLE と INSERT は誰が実行したのか。 sqlite3 というコマンドを起動したそのプロセス自身である。SQLite はライブラリで、 呼び出した側のプロセスの中で動き、ファイルを直接読み書きして、終われば消える。 待ち受けている相手がいないので、接続という段階そのものが存在しない。

たとえ: レストランと自炊の違いである。サーバ型は厨房に注文を出し、厨房が作る。 SQLite は自分の手で作る。だから厨房にあたるプロセスが ps に出てこない。
ただし崩れる点: 厨房が無いことは、何人でも同時に料理できることを意味しない。 台所は1つで、そこに置いてあるノートも1冊である。この制約は後の章で扱う。
対応する演習は lab start 01。判定は lab check 01。
詰まったら: unable to open database file が出る場合
$ sqlite3 notes.db 'CREATE TABLE notes(id INTEGER PRIMARY KEY, body TEXT);'
Error: unable to open database "notes.db": unable to open database file
このメッセージは「ファイルが開けない」と言うが、原因はたいてい いまいるディレクトリに書き込めないことである。pwd と ls -ld . を打って、自分に w が付いているか確かめる。 演習なら cd ~/work/01 が先に要る。

なぜディレクトリの権限が関係するのか。SQLite は書き込みのとき DB ファイルの隣にもう1つファイルを作る。新しい名前を作る操作は ファイルへの書き込みではなくディレクトリへの書き込みなので、 DB ファイル側の権限だけでは足りない。

なお sqlite3 を引数なしで打つとプロンプトは出る。これは メモリ上の一時データベースを開いていて、ファイルを作らないからである。 「プロンプトは出るのにファイルを指定すると失敗する」は、この切り分けに使える。

メッセージが指すものと実際の原因が食い違うこの現象は、 第5章の主題そのものである。 ここで踏んだなら、第5章は半分終わっている。

確認問題

  1. file notes.db が「SQLite 3.x database」と答えた。これでファイルの中身が壊れていないと言えるか。
  2. ps にデータベースのプロセスが1行も出ないのに INSERT が成立したのはなぜか。
答え

1. 言えない。file が見たのは先頭の並びである。先頭16バイトが揃っていることと、そのあとに続く 8000 バイト余りが筋の通った内容であることは別の話である。次の節で、先頭さえ揃っていない場合ですら操作が通ってしまう例を見る。

2. sqlite3 を起動したプロセス自身がファイルを開いて書いたからである。SQLite はライブラリなので、呼び出した側のプロセスの中で動く。実行を頼む相手がいないから、頼み先のプロセスも ps に出ない。

「開けた」は「正しい」ではない

この節で分かること: 中身が SQLite のものでなくても通ってしまう操作がある

ふつうこう考える

手元のファイルが壊れていないかを確かめたい。いちばん手軽なのは、開いて軽いクエリを1本投げてみることだろう。 通れば正常、エラーが出れば壊れている、という判定である。まず、確実に壊れているファイルを用意して試す。

$ printf "not a database at all, just text" > broken.db
$ sqlite3 broken.db 'SELECT 1;'
1

中身はただのテキストである。それでも SELECT 1; は 1 を返して正常終了した。 同じファイルに整合性検査をかけると、こうなる。

$ sqlite3 broken.db 'PRAGMA integrity_check;'
Error: in prepare, file is not a database (26)

file is not a database という趣旨のメッセージ（文言は環境で変わる）が出て、今度は失敗する。

だめな理由: 軽いクエリが通ったことは、ファイルが読まれた証拠にならない。 SELECT 1; は表を1つも参照しないので、スキーマもデータページも必要ない。 必要ないものをライブラリは読まない。開く操作が成功したのではなく、読む理由がまだ発生していなかっただけである。 一方 PRAGMA integrity_check; は中身を見ないと答えが出せないので、そこで先頭16バイトが SQLite format 3 で始まっていないことが露見する。エラーが in prepare の段で出ているのは、 文の準備の時点でもう中身が要る種類の問い合わせだということである。

ここが背骨の効くところである。ファイルを掴んだ瞬間に検査をしてくれる常駐プロセスがいないのではなく、 「掴む瞬間」そのものが無い。読むのは呼び出し側のプロセスで、読むのは必要になったときである。 だから「開けた」という事実が、サーバ型のデータベースで接続が成立したときほどの意味を持たない。

受付が無いと何が楽で、何が難しいか

この節で分かること: サーバの不在が、運用のどこを軽くしてどこを重くするか

ここまでで見た事実だけから整理できる。左の列は常駐プロセスがいれば用意されていたもので、右の列がその代わりである。

サーバがいれば担っていたものSQLite での代わり
接続先の指定（ホスト名・ポート）パス1つ。sqlite3 notes.db の引数がそれである
使う前に起動しておくこと不要。ライブラリは呼ばれた瞬間に動き、終われば消える
データベース側のユーザとパスワードファイルの所有者と権限（-rw-r--r-- 1 lab lab）
受け入れ時に中身を検める役自分で PRAGMA integrity_check; を呼ぶ
「いま誰が触っているか」を尋ねる窓口無い。ps にも行は出ない

上3行が楽になったところで、下2行が難しくなったところである。同じ1つの原因から両方が出ている。 楽さと難しさは別の性質ではなく、常駐プロセスがいないという1つの事実の裏表である。

たとえ: 図書館の貸出カウンターと、玄関に置いた本棚。カウンターがあれば「いま誰が何を借りているか」を尋ねられる。 本棚だけなら、尋ねる相手がいない。
ただし崩れる点: 玄関の本棚は誰が持っていったか一切分からないが、ファイルには所有者と権限がある。 何も分からないのではなく、OS が知っている範囲だけ分かる。カウンターの仕事がそっくり消えるのではなく、OS に移っている。

残る問いが1つある。調停する相手がいないのなら、2つのプロセスが同じファイルに同時に書こうとしたときに何が起きるのか。 ファイルの上だけで折り合いを付けることになるはずである。これは後の章で扱う。

確認問題

  1. SQLite の接続情報にホスト名とポート番号が無いのはなぜか。
  2. 同じファイルに対して SELECT 1; は成功し、PRAGMA integrity_check; は失敗した。この差は何を示しているか。
答え

1. 接続する相手が存在しないからである。ホスト名とポート番号は「どの機械のどの待ち受けプロセスに繋ぐか」を指すが、SQLite には待ち受けプロセスがない。指す必要があるのは読み書きする対象そのもの、つまりファイルのパスだけである。

2. ライブラリが、その問い合わせに答えるために必要な分しかファイルを読まないことを示している。SELECT 1; は表を参照しないので中身が要らず、PRAGMA integrity_check; は中身が要る。したがって「操作が1つ通った」ことをファイルの健全性の根拠にはできない。健全性を知りたいなら、中身を要求する操作を自分で呼ぶ必要がある。

この章で分かったこと

持ち帰ってほしいこと

  • データベースは1ファイルである。ls に1行、先頭16バイトに SQLite format 3 が平文で入っている
  • データを預かる常駐プロセスは存在しない。ps -ef | grep -c "[s]qlite" が数えた 1 は検査自身の行である
  • 書き込んだのは sqlite3 を起動したプロセス自身で、その版がファイルの中に 3045001 として残っている
  • 読むのは必要になったときなので、操作が1つ通ったことはファイルが正しいことの証明にならない
  • 接続先も起動順もユーザ管理も消えるが、検める役と「いま誰が触っているか」を尋ねる窓口も同時に消える
