2. 型は宣言ではなく提案

INTEGER と宣言した列に、文字列がそのまま入る。これはバグではなく、SQLite では型宣言が「弾く条件」ではなく「変換の優先傾向」だからである。

前提: 第1章所要 12分影響度 B最終検証 2026-09-30
この章のコマンドは DB ファイルを新しく作る。すべて配布イメージの中で実行し、母艦では実行しない。

この章のゴール

  • INTEGER と宣言した列に文字列が入る理由を type affinity の語で説明できる
  • typeof() で実際に格納された型を確かめられる
  • STRICT テーブルで何が変わるかを言える
ここで覚えなくていいこと: affinity は全部で5種類あるが、その全組み合わせ表は覚えない。この章で見るのは INTEGER 宣言の列だけである。 CHECK 制約の書き方も扱わない。値の範囲を縛る話は型の話とは別の層にある。 照合順序（COLLATE）も扱わない。文字列の比較規則は型が決まった後の話である。

INTEGER と書いても、文字列は入る

この節で分かること: 宣言に反する値を INSERT したとき、SQLite が何を返すか。

結論から言う。ふつうに CREATE TABLE したテーブルでは、列の型宣言は INSERT を止めない。

ふつうこう考える

n INTEGER と宣言したのだから、数値以外を入れれば INSERT は失敗するはずである。確かめるなら、テーブルを作って数値を1行、文字列を1行入れてみればよい。成功か失敗かで判定できる。

$ sqlite3 t2.db 'CREATE TABLE loose(n INTEGER);'
[exit 0]
$ sqlite3 t2.db 'INSERT INTO loose VALUES(42);'
[exit 0]
$ sqlite3 t2.db 'INSERT INTO loose VALUES("abc");'
[exit 0]
だめな理由: 3行目も [exit 0] である。文字列を入れても失敗しない。そして失敗しなかったという情報しか返ってこないので、この観測では「そのまま入ったのか、別の型に変換されて入ったのか」を区別できない。成否を見る方法では、宣言と実際の格納内容の関係が何ひとつ分からない。確かめたいのは INSERT の結果ではなく、格納されたあとの値である。

SQLite の列宣言は、値を受け付ける条件ではない。格納するときにどの型へ寄せたいかという優先傾向であり、これを type affinity と呼ぶ。寄せられなければ寄せないまま格納する。宣言には「拒否する」という選択肢が用意されていない。

たとえ: 列の型宣言は入国審査官ではなく、荷物に貼る仕分け希望票に近い。希望票は「この荷物は整数の棚へ」と書いてあるだけで、違う荷物を持ち帰らせる権限を持たない。
ただし崩れる点: 希望票が完全に無視されるわけではない。次の節で見るように、整数として読める荷物は実際に書き換えられて整数の棚に入る。「無視される」と覚えると、この書き換えを説明できなくなる。

入った型を typeof() で見る

この節で分かること: 宣言ではなく実際に格納された型を1行ずつ確かめる方法と、そこに現れる非対称。

格納された値の型は typeof() で取れる。前節で 2 行入れた loose を、値と型を並べて読む。

$ sqlite3 t2.db 'SELECT n, typeof(n) FROM loose;'
42|integer
abc|text
[exit 0]

宣言が 1 つしかない loose の n 列から、integer と text の 2 種類が返ってきた。型は列に付いているのではなく、値ごとに付いている。同じ列に別の型が同居できる。

ここで、整数として読める文字列を入れてみる。

$ sqlite3 t2.db 'INSERT INTO loose VALUES("123"); SELECT n, typeof(n) FROM loose;'
42|integer
abc|text
123|integer
[exit 0]

"123" は引用符を付けた文字列として渡したのに、typeof は integer を返す。一方 "abc" は text のまま残っている。同じ列、同じ書き方、違う結果である。

この非対称が affinity の実体である。INTEGER affinity を持つ列は、渡された値を整数に変換できるなら変換してから格納し、変換できないなら渡されたままの型で格納する。分岐するのは変換の成否だけで、格納の成否は分岐しない。だから前節の INSERT は 3 回とも [exit 0] だった。

たとえ: 硬貨を入れると自動で数えてくれるコインカウンターに似ている。硬貨は数えられて金額になる。紙で作ったコインが混ざっても機械は止まらず、数えずに受け皿へ落とす。
ただし崩れる点: 実物のカウンターは異物を外へ返すが、SQLite は変換できなかった値も同じ列にそのまま保管する。あとから読むと、数えられた値と数えられなかった値が同じ場所から出てくる。

確認問題

  1. SELECT n, typeof(n) FROM loose; の 2 列目を捨てて 1 列目だけをプログラムで受け取るとき、何に備える必要があるか。
  2. "123" が integer になり、"abc" が text のまま残ったのはなぜか。
答え

1. 同じ列から integer と text の両方が返ってくることに備える。型は列宣言ではなく値ごとに決まっているので、宣言を読んで「この列は必ず整数」と決め打ちできない。実際に何が入っているかは typeof(n) を一緒に取れば行ごとに分かる。

2. INTEGER affinity は「整数に変換できるなら変換する」であって「整数でなければ拒否する」ではない。"123" は変換できたので integer として格納され、"abc" は変換できなかったので渡された text のまま格納された。どちらの経路でも INSERT は成功する。

なぜ弾かないのか — 弾く主体がいない

この節で分かること: この挙動が、SQLite の置かれ方そのものから出てくること。

厳格な型検査には、すべての書き込みが通る関門が要る。SQLite にはその関門を置く場所が無い。

前章で見たとおり、DB はファイル 1 個であり、それを世話する常駐プロセスは存在しない。CREATE TABLE を実行したのも INSERT を実行したのも、コマンドを打った瞬間に起動したそのプロセス自身であり、中にリンクされたライブラリがファイルを直接書いている。

サーバ型の DB なら、宣言に反する値を送るクライアントが現れても、サーバ側が書き込みを拒否できる。関門はクライアントの外にある。SQLite で同じことをしようとすると、検査のコードを置ける場所は 1 つしかない。書き込む当のプロセスの中である。検査する側と検査される側が同じプロセスに同居する。

この構造の下では、宣言に反する値でエラーを投げるかどうかは「ファイルを守る仕組み」ではなく、呼び出し側にとって都合がいいかどうかの問題になる。実測では、ふつうに作ったテーブルは投げない側に倒れている。倒れ方を変えたいなら、テーブルを作るときに指定する。

たとえ: サーバ型の DB が受付のある倉庫なら、SQLite は受付のない共同倉庫である。荷物を運び込む人が、自分で棚札を読んで自分で判断する。
ただし崩れる点: 倉庫の比喩だと「あとから受付を雇える」ように聞こえる。SQLite に常駐の受付は現れない。次の節で見る仕組みも、受付を置くのではなく、運び込む人が読む札を増やすものである。

確認問題

  1. SQLite で型検査のコードを置ける場所は 1 つしかない。どこか。
  2. スキーマに INTEGER と書いてあるファイルを渡された。「この列には整数しか入っていない」と言えるか。
答え

1. 書き込みを行うプロセスの中。SQLite はライブラリなので、DB を読み書きしているのは常駐プロセスではなく、いま起動したそのプロセス自身である。検査する側と検査される側が同じプロセスにいる。

2. 言えない。宣言は変換の優先傾向であり、変換できなかった値はそのままの型で格納される。何が入っているかを知るには、スキーマではなく値を typeof() で見る。

STRICT — 同じファイルの中に、厳しいテーブルを作る

この節で分かること: STRICT を付けたテーブルで何が変わり、何が変わらないか。

CREATE TABLE の末尾に STRICT を付けると、変換できない値は INSERT の時点でエラーになる。

$ sqlite3 t2.db 'CREATE TABLE tight(n INTEGER) STRICT;'
[exit 0]
$ sqlite3 t2.db 'INSERT INTO tight VALUES("abc");'
Error: stepping, cannot store TEXT value in INTEGER column tight.n (19)
[exit 19]

cannot store TEXT value in INTEGER column という趣旨のメッセージが出る（文言は環境で変わる）。終了コードも [exit 0] ではなく [exit 19] になっている。第1節でまったく同じ値を loose に入れたときは [exit 0] だった。違いはテーブルの作り方だけである。

ここで見落としてはいけないのは、loose と tight が同じ t2.db の中にあることである。STRICT は DB ファイル全体の設定ではない。CREATE TABLE ごとに付ける宣言で、効く範囲はそのテーブルだけである。

宣言と合う値は、STRICT でも当然そのまま入る。

$ sqlite3 t2.db 'INSERT INTO tight VALUES(7); SELECT n, typeof(n) FROM tight;'
7|integer
[exit 0]

そして [exit 19] を返したのは、サーバではない。sqlite3 を起動したそのプロセスである。STRICT は倉庫の外に関門を置く仕組みではなく、書き込む側のライブラリが従う規則を、そのテーブルに結び付ける仕組みである。検査する側と検査される側が同じプロセスにいるという構造は、STRICT を付けても変わらない。変わるのは、そのプロセスが自分の書き込みを止めるかどうかである。

たとえ: STRICT は棚 1 本ごとに貼る「この棚には決まった物だけ」という札である。札があるので運び込む人は自分で判断して持ち帰る。
ただし崩れる点: 札は棚ごとであって、倉庫の入口の掲示ではない。実測どおり、隣の loose には何の効果もない。同じファイルを開いたのだから全体に効く、と考えると外す。
対応する演習は lab start 02。判定は lab check 02。

確認問題

  1. tight を STRICT で作った。これで loose への文字列 INSERT はどうなるか。
  2. INSERT INTO tight VALUES("abc") の失敗を判定したのは、どのプロセスか。
答え

1. 何も変わらない。同じ t2.db の中にあっても別のテーブルであり、STRICT はテーブルごとの宣言である。loose への INSERT は引き続き [exit 0] で通り、値は typeof で text のまま見える。

2. sqlite3 コマンドを起動したそのプロセス自身。常駐しているサーバが拒否したのではなく、プロセス内のライブラリが自分の書き込みを止めた。だから終了コード 19 はそのプロセスから返る。

この章で分かったこと

持ち帰ってほしいこと

  • ふつうに作ったテーブルでは、列の型宣言は INSERT を止めない。型は値ごとに付き、同じ列に integer と text が同居しうる
  • INTEGER affinity は「変換できるなら変換し、できないならそのまま格納する」。"123" は integer になり、"abc" は text のまま残る。この非対称が type affinity の正体である
  • スキーマの宣言からファイルの中身は分からない。確かめたいときは typeof() で値ごとに見る
  • 宣言どおりに弾かせたいなら CREATE TABLE ごとに STRICT を付ける。効く範囲はそのテーブルだけで、同じファイルの隣のテーブルには及ばない
  • 弾いたのはサーバではなく、あなたが起動したプロセスの中のライブラリである
