5. ディレクトリに書けないと、DB にも書けない

DB ファイルには書き込み権限がある。所有者も自分。それでも INSERT が attempt to write a readonly database で落ちる。この章はその状況を自分の手で作り、 エラーメッセージが名指ししている場所と本当の原因がずれている理由を明かす。

前提: 1〜4章所要 16分影響度 B使い捨てコンテナの中だけで実行する最終検証 2026-09-30

この章のゴール

  • DB ファイルに書き込み権限があるのに書けない状況を、自分の手で作れる
  • その状況の原因を、エラーメッセージの文言に引きずられずに言える
  • attempt to write a readonly database を、ファイル権限以外の原因まで含めて切り分けられる
ここで覚えなくていいこと: ジャーナルモードごとに作られるファイルの一覧。 SQLITE_FCNTL の詳細。 ネットワークファイルシステム上の既知の問題の全部。 この3つは知らないまま先へ進んでよい。この章の切り分けは、どれも使わずに終わる。

書ける DB が書けなくなる檻を、3手で作る

この節で分かること: DB ファイルを1バイトも触らずに、書き込みを拒否させる手順。

まず普通に書ける DB を、サブディレクトリの中に作る。

$ sqlite3 subdir/d.db 'CREATE TABLE t(n INTEGER); INSERT INTO t VALUES(1);'
[exit 0]
$ ls -la subdir/
total 16
drwxr-xr-x 2 lab lab 4096 Sep 30 19:08 .
drwx------ 3 lab lab 4096 Sep 30 19:08 ..
-rw-r--r-- 1 lab lab 8192 Sep 30 19:08 d.db
[exit 0]

[exit 0] の行は、この記録を採取したスクリプトが付けたものである。手元のシェルには出ない。 日時とサイズも実行した時刻のものになる。それ以外の文字は、同じイメージの中なら同じものが出る。

次に、DB ファイルの権限は一切変えず、それを入れているディレクトリからだけ書き込みビットを落とす。

$ chmod 555 subdir
[exit 0]
$ ls -ld subdir; ls -l subdir/d.db
dr-xr-xr-x 2 lab lab 4096 Sep 30 19:08 subdir
-rw-r--r-- 1 lab lab 8192 Sep 30 19:08 subdir/d.db
[exit 0]

2行の出力が、この章の全部である。上の行はディレクトリで w が消えている。 下の行は DB ファイルで、所有者に rw が残っている。この状態で 1 行足す。

$ sqlite3 subdir/d.db 'INSERT INTO t VALUES(2);'
Error: stepping, attempt to write a readonly database (8)
[exit 8]

attempt to write a readonly database という趣旨のメッセージ（文言は環境で変わる）が出て、 終了コードは 8 になる。メッセージ末尾の (8) と同じ番号である。 読み取りは何も変わらずに通る。

$ sqlite3 subdir/d.db 'SELECT count(*) FROM t;'
1
[exit 0]
たとえ: 引き出しには鍵がかかっていない。鍵がかかっているのは、引き出しを置いてある部屋の扉で、 しかも「新しい物を持ち込むな」という向きの鍵である。中身を読むのは自由に通る。
ただし崩れる点: 持ち込み禁止だけなら、既にある紙を書き換えることはできそうに思える。 SQLite ではそれができない。書き換える前に必ず新しい物をひとつ持ち込むので、持ち込み禁止が書き換え禁止まで波及する。 理由は3節目で見る。

エラーは database と言うが、原因はディレクトリにある

この節で分かること: このエラーで読者が最も長く迷う理由と、その迷いの抜け方。

結論から言う。メッセージは database を名指しているが、直すべき対象は DB ファイルではなくディレクトリである。 メッセージが正しく指しているのは「書き込めなかった」という結果だけで、どこが原因かは何も言っていない。

ふつうこう考える

readonly database と言われたのだから、DB ファイルの権限が読み取り専用になっているのだろう。 まず ls -l で DB ファイルの権限を確かめる。

-rw-r--r-- 1 lab lab 8192 Sep 30 19:08 subdir/d.db

書き込みビットは立っている。所有者も自分。読み取り専用ではない。ここで手が止まる。 次に思いつくのは chmod 644 を打ち直すことだが、 この出力が示している権限がすでに 644 なので、打っても何も変わらない。

だめな理由: 権限を疑ったのは正しい。見る対象が1つ足りなかった。 SQLite が書き込みのときに要求するのは、DB ファイルへの w だけではなく、 DB ファイルと同じディレクトリに新しいファイルを作る権限である。 ディレクトリへの w は「ディレクトリの中身の一覧を書き換える権限」、つまりファイルを作る・消す・名前を変える権限であり、 既にあるファイルの中身を書き換える権限とは別物として管理されている。 片方だけ落とせば、いまの状態が作れる。

切り分けとして効くのは、さきほどの SELECT count(*) が通ったという事実である。 開けている。読めている。パスもファイル形式も権限も、読む側は全部通っている。 壊れているのはファイルへの到達ではなく、書き込みのために SQLite がやろうとしている別の作業である。

確認問題

  1. 状況: 自分が書いたアプリが、書き込みのときだけ attempt to write a readonly database で落ちる。原因を探すため ls -l を打つと、DB ファイルは -rw-r--r-- で自分の所有だった。
    この観測から言えることと、言えないことをそれぞれ述べる。
  2. 状況: 同じアプリを別のマシンに置いたところ、そちらでも書き込みは同じエラーで落ちる。 ただしそのマシンでは SELECT だけは通ることを確認した。
    この事実は原因の候補をどう狭めるか。
答え

1. 言えるのは「DB ファイルの権限は原因ではない」ことだけ。言えないのは、書き込みが通るかどうか。 SQLite の書き込みはこのファイル1つだけを対象にした操作ではないので、このファイルの権限は必要条件の1つにすぎない。

2. ファイルまで到達できていて、中身が SQLite の形式として読めていることが確定する。 つまりパスの間違い・ファイルの破損・読み取り権限の不足は候補から外れる。残るのは書き込み側だけに効く条件である。

なぜディレクトリが要るのか — 控えを置く場所が、DB の隣しかない

この節で分かること: SQLite が書き込みの前にディレクトリを使う理由。ここが背骨の見える場所である。

SQLite は DB ファイルを書き換える前に、書き換わる前の内容の控えを取る。途中で電源が落ちても、 控えから元の状態に戻せるようにするためである。この控えをロールバックジャーナルと呼ぶ。

問題は置き場所である。ジャーナルは DB ファイルと同じディレクトリに、新しいファイルとして作られる。 だから書き込みは「DB ファイルを書き換える権限」だけでは始まらず、「そのディレクトリにファイルを1つ増やす権限」を先に要求する。 さきほどの実行は、DB ファイルに手が届く前に、この1歩目で止まっていた。

ここがこの教材の山場である。なぜ DB の隣なのか。他に置ける場所がないからである。 サーバとして常駐しているデータベースは、自分の作業領域を自分で持っている。 ログもジャーナルも、サーバが起動時に決めた自分の場所に書く。データファイルの隣である必要はない。 SQLite にはその「自分の場所」がない。常駐しているプロセスがないので、 起動時に作業領域を確保しておく主体が存在しない。書き込みをしているのは、いまあなたが打った sqlite3 というプロセスであり、 そのプロセスが知っている場所は、引数で渡された DB ファイルのパスだけである。だから控えは DB の隣に置くしかない。

たとえ: 自前の工場を持つ引越業者は、梱包を工場でやってから客の家に運べる。 SQLite は工場を持たない業者で、客の部屋の床の上で梱包する。だから部屋に物を置く許可が要る。
ただし崩れる点: 引越業者は作業が終われば床を空にして帰るのが正しい。 ジャーナルは「作業中に倒れたときに元へ戻せること」が目的なので、残っていることにも意味がある。 片付けられずに残ったジャーナルは、事故ではなく仕様の一部として扱われる。

確認問題

  1. サーバ型のデータベースなら、データファイルと同じディレクトリに書き込み権限がなくても書き込めることがある。なぜか。
  2. ディレクトリを読み取り専用にしたとき、SELECT が通って INSERT が落ちた。この非対称はどこから来ているか。
答え

1. 作業領域を自分で決めて持っているから。ジャーナルやログの置き場所はサーバの設定で決まり、 データファイルの隣である必要がない。書き込みを実行しているのもサーバのプロセスであって、 コマンドを打った側のプロセスではない。

2. 読み取りは既にあるファイルを開いて読むだけで、新しいファイルを作らない。 書き込みは控えを作るところから始まるので、ディレクトリにファイルを増やす権限を要求する。 同じディレクトリ権限が、片方には要らず片方には要る。

WAL に変えて回避しようとすると、同じ壁に当たる

この節で分かること: 設定を変えて逃げる道が、この状況では最初から閉じている理由。

ジャーナルの作り方が原因なら、ジャーナルの方式を変えれば通るのではないか。そう考えて journal_mode を変えにいくと、こうなる。

$ sqlite3 subdir/d.db 'PRAGMA journal_mode=WAL;'
Error: stepping, attempt to write a readonly database (8)
[exit 8]

同じメッセージ、同じ番号である。理由は単純で、journal_mode の変更それ自体が書き込みだからである。 どの方式を使うかは DB ファイルに記録されている値なので、方式を切り替えるには DB ファイルを書き換える必要があり、 書き換えるには控えを置く場所が必要で、その場所がないからここまで来ている。

たとえ: 入れない部屋の中に、その部屋の鍵の種類を書いた台帳がある。 台帳を書き換えれば入れるようになるが、書き換えるには部屋に入る必要がある。
ただし崩れる点: 台帳の例では「誰か中の人に頼む」という抜け道が残る。 SQLite には中の人がいない。頼める相手が構造的に存在しないので、抜け道は閉じたままになる。

設定で回避できないことは、悪い知らせではなく切り分けの材料である。 設定を変える操作まで同じエラーで落ちるなら、原因は SQLite の設定の外側にある。 残っているのは、ファイルシステムがそのプロセスに何を許しているかだけになる。

切り分けの順序 — 番号ではなく、どこを見るかを決める

この節で分かること: このエラーを見たときに最初に見る場所と、その理由。

ディレクトリを戻すと、他に何も変えていないのに書けるようになる。

$ chmod 755 subdir
[exit 0]
$ sqlite3 subdir/d.db 'INSERT INTO t VALUES(2); SELECT count(*) FROM t;'
2
[exit 0]

この検証で確かめたのは、原因のうちディレクトリ権限の1つだけである。 番号 8 は他の原因でも出る。だから (8) を見て原因を当てにいくのではなく、 何が観測できているかを積む。積むべきものは3つしかない。

観測そこから言えること
SELECT が通るパス・ファイル形式・読み取り権限は原因から外れる。開けてはいる
ls -l で DB ファイルに w があり、自分の所有であるDB ファイルの権限は原因から外れる
ls -ld でそのディレクトリに w がない控えを置けない。この1つで書き込み全部が止まる

3つ目を見ていない状態が、このエラーで最も長く足を止める。 順序は ディレクトリを先に見るでよい。メッセージが database と言っているので、 ディレクトリは最後に回されがちだが、読み取りが通っているならファイル側の候補はすでに減っている。

たとえ: (8) は体温計の数字ではなく、診断名のない「発熱」という語に近い。 状態の名前であって、原因の名前ではない。
ただし崩れる点: 発熱は程度が読めるので重さの判断に使える。 (8) には程度も候補の数もなく、次にどこを見ればよいかの手がかりを何も持たない。

番号から名前へ降りる道はある。SQLite の結果コードは sqlite3.h に定数として定義されていて、 8 に対応する名前は SQLITE_READONLY である。その下に細分の名前が並んでいて、 そこには SQLITE_READONLY_DIRECTORY という名前も含まれている。 メッセージが database と言っている一方で、定義の側にはディレクトリという語がある。 コマンドラインの sqlite3 が括弧に出すのは細分される前の 8 なので、この名前は画面には出てこない。 番号を見たら、次は sqlite3.h の定義名を引く。一次情報の入口はここになる。

対応する演習は lab start 05。判定は lab check 05。 演習では、この章と同じ状態を作ったうえで、ディレクトリを元に戻さずに1行足す方法があるかどうかを確かめる。

確認問題

  1. あるサーバで attempt to write a readonly database が出ている。ファイル権限とディレクトリ権限の両方を確認したが、どちらにも w があった。この時点で立てるべき問いを1つ挙げる。
  2. 同じ attempt to write a readonly database に対して、 「DB ファイルを書き込み可能な別のディレクトリにコピーする」という対処が効くことがある。 効いた場合、それは何を示しているか。
答え

1. 「そのプロセスは、いま本当にそのディレクトリへファイルを作れるのか」。 権限ビットが立っていることと、そのプロセスが実際に作成できることは別の話である。 権限ビットの外側で書き込みを止める仕組みは複数あるので、ビットの確認で終わらせない。

2. 原因が DB ファイルの中身ではなく置かれている場所にあったことを示している。 ファイルは1バイトも変えていないのに結果が変わったのだから、変数はディレクトリ側にあったと確定する。 ただし、コピーは元の場所への書き込みを諦めた対処なので、切り分けとしては強いが解決ではない。

1章から4章は、全部この1つの理由から出ていた

この節で分かること: ここまでの4章がばらばらの雑学ではなく、1つの帰結だったこと。

常駐しているプロセスがいない。だから状態をプロセスの中に持てず、置き場所はファイルシステムしかない。 ここまで見てきたものは、この1文の言い換えである。

  • DB がファイル1個である（1章）— 状態を保持する常駐プロセスがないので、DB の実体はファイルそのものになる。 プロセスの一覧に相手が出てこないのは、相手がいないからである。
  • 型が列の宣言より緩い（2章）— 宣言を守らせる番人が常駐していない。 値がどの型で格納されるかを決めるのは、いま書き込んでいるプロセス自身である。 STRICT で締められるのも、締める判断がそのプロセスの中で行われているからである。
  • 囲まないと1行ごとに遅い（3章）— 1回の書き込みごとに控えを作り、消す。 その作成と削除が、いまこの章で権限を要求していたものである。3章で見た速度差と、この章で見た拒否は、 同じ1つの動作を別の角度から見たものにすぎない。
  • ロックがファイル上の印である（4章）— 誰が書いているかを教えてくれる相手がいない。 調停する常駐プロセスがないので、ファイルシステムの上に印を置いて互いに見るしかない。

そしてこの章が示したのは、その帰結の最後の1歩である。 ファイルシステムしか使えないということは、ファイルシステムが禁止したことは何一つできないということである。 DB ファイルへの権限は、その禁止の一部でしかない。

この章で分かったこと

持ち帰ってほしいこと

  • DB ファイルの権限がそのままでも、ディレクトリの書き込みビットを落とすだけで書き込みは止まる。 chmod 555 と chmod 755 で行き帰りできる
  • 書き込みはディレクトリに新しいファイルを作ることから始まる。控えを DB の隣に置くしかないからである
  • attempt to write a readonly database は結果の名前であって原因の名前ではない。 SELECT が通るなら、見る先はファイルではなくディレクトリから始める
  • journal_mode の変更も書き込みなので、設定で回避する道は最初から閉じている。 それは切り分けの材料になる
  • ここまでの4章は、常駐プロセスがないという1点から出ていた。ファイルシステムが禁じたことは、そのまま DB の禁止になる
